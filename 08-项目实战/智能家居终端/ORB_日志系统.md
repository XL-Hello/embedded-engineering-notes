# 嵌入式裸 Flash 日志系统设计方案

## 1. 设计目标与边界

面向资源受限的嵌入式设备，设计一套不依赖文件系统的离线日志系统。日志从 `printf` 路径采集，经 RAM 缓冲、LZ4 压缩后写入裸 Flash；网络可用时由上传任务读取并上传。

本版目标如下：

* 不阻塞业务代码和中断中的日志输出；
* 降低 Flash 写入量与上传流量；
* 使用固定大小 Flash Block 循环存储，RAM 占用可控；
* 压缩、Flash 写入和上传均由后台任务异步完成。

本版明确不处理掉电保护、掉电后的写入恢复和上传确认删除等可靠性问题。这些属于后续优化，统一在文末说明，避免给基础流程引入额外状态机和元数据维护。

---

## 2. 总体架构

日志采集必须位于 UART 输出之前。原因是系统的 `printf` 输出发生在中断上下文中：采集模块只做快速复制/入队，随后仍走原有 UART 输出，不在中断中执行压缩、擦除或写 Flash 等耗时操作。

```text
printf / LOG_xxx（可能在中断中调用）
              |
              v
      +-----------------+
      | Log Collector   |  <- 先采集，快速写入当前 RAM Buffer
      +-----------------+
              |
              v
      +-----------------+
      | UART 输出       |  <- 保持原有串口调试能力
      +-----------------+

满 Buffer 通知后台任务
              |
              v
      +-----------------+       +------------------+
      | 双循环 Buffer   | ----> | LZ4 压缩任务     |
      +-----------------+       +------------------+
                                           |
                                           v
                                  +------------------+
                                  | 压缩日志链表队列 |
                                  +------------------+
                                           |
                                           v
                                  +------------------+
                                  | Flash 写入任务   |
                                  +------------------+
                                           |
                                           v
                                  +------------------+
                                  | HTTP 上传任务    |
                                  +------------------+
```

各模块职责：

| 模块 | 职责 | 上下文 |
| --- | --- | --- |
| Log Collector | 格式化并快速写入 RAM 缓冲；记录丢失日志计数 | 中断/任务 |
| UART 输出 | 输出原始日志到串口 | 沿用现有实现 |
| LZ4 压缩任务 | 读取已封存 Buffer，生成 LZ4 数据包 | 后台任务 |
| 压缩日志链表队列 | 暂存等待落盘的压缩包，解耦生产与写 Flash | 后台任务 |
| Flash 写入任务 | 擦除并顺序写入固定 Block | 后台任务 |
| HTTP 上传任务 | 读取已存储日志并按策略上传 | 后台任务 |

## 3. 日志采集模块：Log Collector 在前，UART 在后

将原来的输出路径：

```text
printf -> UART
```

调整为：

```text
printf -> Log Collector -> UART
```

Log Collector 接收格式化后的日志文本，建议统一组织为：

```text
[时间][等级][模块] 消息\r\n
```

例如：

```text
[10:30:01.125][ERROR][SPI] DMA timeout\r\n
```

采集模块的处理原则：

1. 不等待压缩任务、Flash 写入或网络上传；
2. 仅在当前循环 Buffer 中复制数据并推进写指针；
3. 临界区只保护读写指针、Buffer 状态和切换动作，保持足够短；
4. 当剩余空间不足以容纳一条完整日志时，封存当前 Buffer、切换到备用 Buffer，并通知压缩任务；
5. 两个 Buffer 都不可写时，丢弃当前日志并累计 `lost_log_count`，绝不能在中断中等待。

这样即使 `printf` 在中断中调用，日志功能也不会因压缩或 Flash 忙而拉长中断响应时间。UART 输出仍在采集之后执行，因此采集失败不影响已有串口调试链路。

## 4. 双循环 Buffer 设计

使用两个固定大小的环形 Buffer，例如 `Buffer A` 与 `Buffer B`。任一时刻仅一个 Buffer 处于 `FILLING` 状态，另一个可处于 `FREE`、`READY` 或 `COMPRESSING` 状态。

```text
                 日志写入
                    |
                    v
        +-----------------------+
        | Buffer A: FILLING     |
        | circular write        |
        +-----------------------+
                    |
             满 / 到达阈值
                    |
                    v
        A 标记 READY，立即切换至 Buffer B
                    |
                    +--------------------------+
                                               |
                                               v
                              +-----------------------+
                              | Buffer B: FILLING     |
                              +-----------------------+

        +-----------------------+
        | Buffer A: COMPRESSING | <- LZ4 后台任务读取
        +-----------------------+
                    |
                    v
                 释放为 FREE
```

建议状态定义：

```c
typedef enum {
    LOG_BUF_FREE,
    LOG_BUF_FILLING,
    LOG_BUF_READY,
    LOG_BUF_COMPRESSING,
} log_buf_state_t;
```

双循环 Buffer 的核心价值是生产与消费并行：Log Collector 填充一个 Buffer 时，压缩任务处理此前封存的另一个 Buffer。它避免把压缩开销放进 `printf`/中断上下文，并吸收短时间的突发日志。

注意：双 Buffer 只能吸收有限突发。当压缩速度持续低于日志产生速度时，两个 Buffer 最终都会占满。基础版本采取“丢弃新日志并计数”的明确退化策略，避免阻塞实时业务。

## 5. LZ4 压缩任务

压缩任务等待 `READY` Buffer，读取其中有效长度的原始日志，生成一个独立的 LZ4 数据包，并将其放入压缩日志队列。

```text
READY Buffer
    |
    v
LZ4 Compress
    |
    +-- 压缩成功 --> 压缩日志链表队列
    |
    +-- 压缩不划算/失败 --> 可按原始数据封装或丢弃并计数
    |
    v
Buffer 释放为 FREE
```

### 5.1 选择 LZ4 的优点

* 压缩与解压速度快，适合 MCU/RTOS 后台任务；
* 日志中重复的模块名、格式串、字段名较多，通常具有较好的压缩效果；
* 解压实现成熟，服务端或调试工具容易支持；
* 相比更高压缩比算法，CPU 时间更可预测，减少与实时业务争用。

### 5.2 LZ4 的缺点与约束

* 压缩率通常低于 Zstd、gzip 等算法；
* 随机、短小或已压缩的数据可能几乎不能压缩，甚至会略膨胀；
* 压缩需要工作内存和输出缓冲区，必须在任务栈/RAM 预算中预留；
* 每个 Buffer 独立压缩，无法利用跨 Buffer 的重复内容，压缩比受 Buffer 大小影响；
* LZ4 只解决数据体压缩，不负责 Flash 写入可靠性。

因此，压缩任务应比较 `compressed_size` 与 `raw_size`。若压缩后无收益，可使用“原始数据包”标志直接入队；该策略作为实现选项，不影响本版主流程。

---

## 6. 压缩日志队列：链表队列

压缩任务与 Flash 写入任务之间使用 FIFO 链表队列。每压缩完成一个 Buffer，便为结果申请一个节点，追加到队尾；Flash 写入任务从队头取出并落盘。

```text
head                                                     tail
  |                                                        |
  v                                                        v
+---------+    next    +---------+    next    +---------+
| Packet A| ---------> | Packet B| ---------> | Packet C|
+---------+            +---------+            +---------+
```

节点示例：

```c
typedef struct log_packet_node {
    struct log_packet_node *next;
    uint64_t rtc_time;
    uint32_t raw_size;
    uint32_t lz4_size;
    uint8_t *lz4_data;
} log_packet_node_t;
```

采用链表队列的原因：

* 压缩包长度可变，无须将最大包长固定到数组槽位；
* 入队、出队仅操作队尾/队头，适合作为生产者—消费者队列；
* 将压缩速度与 Flash 写入速度解耦。

队列必须设置节点数、总字节数或内存池上限。达到上限时，基础版本应丢弃新生成的压缩包并计数，或由产品策略选择丢弃最旧包；不可无限动态分配 RAM。

## 7. Flash 空间与 Block 格式

Flash 日志区划分为固定大小 Block，例如每个 Block 为 4 KB：

```text
+---------+---------+---------+---------+
| Block 0 | Block 1 |   ...   | Block N |
+---------+---------+---------+---------+
```

基础版本中，一个 Block 保存一个压缩日志数据包。若单个压缩包超过可用空间，应在进入队列前拆包，或增大 Buffer/Block 规格；不允许跨 Block 写入，以简化读写逻辑。

Block 的字节布局严格为：**自定义数据（魔法数字 + RTC 时间）+ LZ4 头 + LZ4 数据包 + `0xFF` 填充**。

```text
+-------------------------+
| Custom Data             |
| magic + rtc_time        |
+-------------------------+
| LZ4 Header              |
+-------------------------+
| LZ4 Compressed Packet   |
+-------------------------+
| Padding (0xFF)          |
+-------------------------+
```

其中：

```c
typedef struct {
    uint32_t magic;       // 例如 0x5A4C4F47，"ZLOG"
    uint64_t rtc_time;    // 本压缩包开始采集或封存时的 RTC 时间
} log_custom_header_t;
```

紧随其后的 LZ4 Header 使用 LZ4 Frame 格式头，用于描述 LZ4 数据流；其后写入对应的 LZ4 Frame 数据包。LZ4 Frame 自身可选携带内容大小和校验信息，具体启用项由所选 LZ4 库配置决定。

解析顺序为：先校验 `magic`，读取 `rtc_time`，再将剩余有效区按 LZ4 Frame 解码。Flash 空白区域保持擦除态 `0xFF`。

## 8. Flash 写入与循环覆盖

Flash 写入任务从压缩日志链表队列依次取包，按 Block 顺序写入：

```text
Block 0 -> Block 1 -> Block 2 -> ... -> Block N -> Block 0
```

基础写入流程：

1. 取得下一个目标 Block；
2. 擦除该 Block；
3. 写入自定义数据：`magic + rtc_time`；
4. 写入 LZ4 Header；
5. 写入 LZ4 数据包；
6. 剩余空间保持 `0xFF`；
7. 释放队列节点及其数据缓冲。

当写指针回绕到 Block 0 时，覆盖最早写入的日志。固定 Block 顺序循环使用，使各 Block 的擦写次数趋于均衡，形成基础的静态磨损均衡。

当前版本的运行期写位置可保存在 RAM 中：

```c
uint32_t next_write_block;
```

系统正常运行期间无需每次写入都扫描 Flash。由于本版不考虑掉电保护，重启后的写位置恢复不在本设计范围内；可按产品启动策略清空日志区或从 Block 0 重新开始记录。

## 9. HTTP 上传任务

HTTP 上传任务从 Flash 日志区读取完整 Block，解析自定义头后，将 `magic` 之后的 LZ4 数据流上传至服务端；服务端可依据 `rtc_time` 排序并解压。

```text
扫描已写入 Block
       |
       v
读取 custom data + LZ4 packet
       |
       v
HTTP POST
       |
       v
服务端解压、解析、存储
```

上传应在网络可用且不影响核心业务时执行。基础版本可采用周期上传或按日志区占用阈值触发上传。上传后是否立即擦除 Block、以及如何保证“仅删除已确认上传的日志”，属于可靠性增强范畴，本版暂不展开。

## 10. 关键参数与容量估算

以下参数需要根据 MCU RAM、Flash 擦写粒度、平均日志速率和网络条件确定：

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| `LOG_BUFFER_SIZE` | 单个循环 Buffer 容量 | 4 KB 或 8 KB |
| `FLASH_BLOCK_SIZE` | Flash 擦除 Block 大小 | 4 KB |
| `FLASH_BLOCK_COUNT` | 日志区 Block 数量 | 64 |
| `QUEUE_MAX_NODES` | 链表队列最大节点数 | 4～16 |
| `QUEUE_MAX_BYTES` | 队列占用 RAM 上限 | 按 RAM 预算设置 |
| `LZ4_WORK_MEM` | LZ4 工作内存 | 由库和压缩模式确定 |

实际可用数据空间为：

```text
FLASH_BLOCK_SIZE
  - sizeof(log_custom_header_t)
  - LZ4 Header 长度
```

需要确保最大压缩包不超过该空间；否则采用拆包策略，而非让一次写入跨越两个 Block。

## 11. 面试总结版

> 我设计了一套裸 Flash 离线日志系统。`printf` 的调用路径先进入 Log Collector，再进行 UART 输出；因为日志输出可能在中断中发生，Collector 只做快速写入双循环 Buffer，不执行压缩和 Flash 操作。Buffer 满后立即切换到备用 Buffer，后台任务使用 LZ4 压缩已封存的日志。压缩结果进入一个带上限的链表队列，由 Flash 任务异步落盘。Flash 按固定 Block 循环使用，每个 Block 的格式是自定义数据（魔法数字和 RTC 时间）、LZ4 Header、LZ4 数据包及尾部 `0xFF` 填充。这样既保留 UART 调试能力，也将日志产生、压缩、存储和上传解耦，在有限 RAM 下避免阻塞实时业务。

## 12. 后续优化版本建议（不纳入本版设计）

### 12.1 掉电保护与启动恢复

当前设计假定一次 Block 写入能够正常完成。优化版采用“**先写 LZ4 数据体，最后写固定块头**”的两段式写入。块头使用显式的紧凑结构体描述；通过 `__attribute__((packed))` 禁止编译器插入对齐填充，使结构体字段布局与 Flash 中的字节布局一一对应。

```c
typedef struct __attribute__((packed)) {
    uint64_t rtc_time;   // Offset 0x00，8 B
    uint32_t lz4_size;   // Offset 0x08，4 B：LZ4 Header + LZ4 数据包的有效长度
    uint32_t crc32;      // Offset 0x0C，4 B：对 LZ4 Header + LZ4 数据包计算
    uint32_t magic;      // Offset 0x10，4 B：例如 0x5A4C4F47（ZLOG），提交标记
} log_custom_header_t;  // sizeof = 20 B
```

Block 中的存储顺序为：

```text
log_custom_header_t（20 B）+ LZ4 Header + LZ4 数据包 + 0xFF 填充
```

写入流程如下：

```text
1. 擦除目标 Block，整块为 0xFF；
2. 跳过 `sizeof(log_custom_header_t)` 预留空间，从其后的地址开始按 Flash 页编程 LZ4 Header 和 LZ4 数据包；
3. 回读 LZ4 数据体，校验长度和 crc32；
4. 按固定偏移依次写入 rtc_time、lz4_size、crc32；
5. 最后单独写入 magic，完成提交。
```

本方案中，4 KB 是 Block 擦除对齐单位；LZ4 数据体按照 Flash 的页编程大小分段写入，且不得跨页。数据写入期间，Block 起始的 `log_custom_header_t` 预留区域始终保持擦除态 `0xFF`。在元数据字段写入期间掉电时，`magic` 尚未写入；在 LZ4 数据体写入期间掉电时，块头同样不存在。因此启动扫描不会将该 Block 识别为已提交，后续循环写入时可将其擦除复用。

`lz4_size` 用于确定 LZ4 数据体边界；`crc32` 用于在实际读取和上传时校验数据完整性。虽然启动阶段仅依赖 `magic` 判断 Block 是否已提交，但上传任务读取 `rtc_time`、`lz4_size` 和对应 LZ4 数据体后，必须重新计算 CRC32；校验失败则不上报该 Block，并记录异常计数或等待后续回收。

`magic` 放在 `log_custom_header_t` 的最后一个字段，并使用独立的页编程命令写入。这样在写入其他字段或数据体时掉电，Block 都不会出现有效 `magic`；将 `magic` 写到一半时也难以恰好形成完整预设值。该顺序将 `magic` 作为最终提交标记。

启动恢复时扫描所有 Block：

```text
magic 正确（最后提交）
```

启动时仅以 `magic` 判断 Block 是否已提交：头区域全为 `0xFF` 或 `magic` 错误，均表示未使用或未完成记录；应在后续循环写入时擦除复用。扫描已提交 Block 后，可按 `rtc_time` 找到最新记录并确定下一写位置。数据 CRC 校验则放在上传读取路径执行。

### 12.2 上传确认与保留策略

可为 Block 增加上传状态或服务端确认序号，只有收到服务端确认后才允许回收。日志区写满时，需要明确“优先保留错误日志”“覆盖最旧未上传日志”或“暂停采集”的产品策略。

### 12.3 日志优先级与过载控制

为 ERROR/WARN/INFO/DEBUG 设置不同保留策略：队列和双 Buffer 紧张时优先丢弃 DEBUG/INFO；记录按等级丢弃的计数，便于定位日志系统自身的过载情况。

### 12.4 Flash 寿命与异常 Block

基础版本按 `Block 0 -> Block 1 -> ... -> Block N -> Block 0` 顺序循环覆盖，本身已经使日志区内各 Block 的擦除次数大致相同，属于静态磨损均衡。对于“所有 Block 都只承载日志、写入大小相近”的场景，优先保留这一策略，收益通常高于引入复杂的全局动态均衡。

若要增强寿命管理，建议按由轻到重的顺序实施：

1. **擦写计数与最大/最小差值监控**：为每个 Block 维护 `erase_count`；周期性统计 `max_erase_count - min_erase_count`。如果顺序循环正常，该差值理论上不应超过 1（异常 Block 被跳过时除外）。该指标可用于诊断异常覆盖、错误重试或个别 Block 失效。
2. **写入后校验与重试**：每次擦除、写入后读取并校验状态、长度和 CRC。擦除或写入失败时可在同一 Block 重试一次；连续失败则将 Block 标记为异常，避免持续占用 Flash 总线。
3. **坏 Block 隔离表**：为日志区维护一个 `bad_block_bitmap`，位为 1 表示该 Block 不再参与擦除、写入和上传。循环写指针遇到异常 Block 时直接跳过，选择下一个可用 Block。位图应有冗余副本或校验，防止其自身损坏后误用坏 Block。
4. **预留备用 Block**：日志区不要全部参与正常循环，预留少量 Spare Block。例如 64 个物理 Block 中 60 个用于日志、4 个备用。发现异常 Block 后将其移出可用集合，并启用一个备用 Block，使可用日志容量和循环顺序保持稳定。
5. **动态选择低擦写次数 Block（可选）**：如果因为坏 Block、不同日志类型的保留时间或上传策略，导致各 Block 擦写不均，可不再严格使用“下一个物理地址”，而是在可写 Block 中选择擦写计数较低者。为避免频繁扫描，可将候选 Block 按擦写计数分桶，或仅在差值超过阈值时重排。

推荐的写 Block 选择逻辑如下：

```text
候选 Block = 从当前写指针开始顺序查找的第一个非坏 Block
    |
    +-- 擦写计数差值 <= 阈值：直接使用候选 Block，保持顺序循环
    |
    +-- 擦写计数差值 > 阈值：在非坏 Block 中选择 erase_count 更低的 Block
```

`erase_count`、`bad_block_bitmap` 与备用 Block 映射都属于关键元数据。可靠性要求较高时，建议将其设计为双副本、带版本号和 CRC 的小型元数据区，并通过“写新副本后再切换有效标记”的方式更新；否则掉电可能使磨损均衡信息丢失。若日志 Flash 容量较小、擦写频率可接受，最实用的组合是：**顺序循环 + 写后校验 + 坏 Block 隔离 + 少量备用 Block**，而不是一开始就实现复杂的动态均衡算法。

### 12.5 压缩与队列内存优化

可改用预分配内存池替代通用动态分配，减少碎片；也可根据压缩率动态调整 Buffer 大小、压缩阈值与上传批次，以平衡 CPU、RAM、Flash 和网络流量。
