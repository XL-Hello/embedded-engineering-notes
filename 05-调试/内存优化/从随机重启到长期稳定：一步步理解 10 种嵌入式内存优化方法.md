# 从随机重启到长期稳定：一步步理解 10 种嵌入式内存优化方法

假设你正在做一台工业采集网关。它每隔 10 毫秒读取传感器，把数据交给网络任务上传，还要保存日志、处理远程命令。功能测试时一切正常，放到现场连续运行后，却开始偶尔重启。

此时最需要回答的是：**内存分别花在了哪里？哪些对象同时存在？最坏情况下，系统还剩多少余量？**

本文用这台网关贯穿讲解，从内存布局讲到分配策略，再处理任务栈、数据搬运、安全边界和长期监控。前 2 章建立容量与分配模型，第 3、4 章减少栈和缓冲区压力，第 5、6 章处理保护与工具链，第 7 章建立监控，第 8 章用三个工程案例串起完整排查过程。

这里的“优化”同时包含容量、时序和可靠性。MPU 与 Rust 主要减少内存错误，并不直接等于降低 RAM 占用。示例以 C/C++、FreeRTOS 和 Cortex-M 为主；带平台接口的代码用于说明机制，需要结合项目头文件、芯片手册、RTOS 端口与链接脚本适配，不能当作完整工程直接烧录。

## 第 1 章 先算清内存：设备的 RAM 到底去了哪里

网关启动以后，RTOS、协议栈、任务栈、队列、日志和业务缓冲区都会占用内存。要判断该用哪种优化方法，先分清物理存储器、程序段和运行时对象三个层次。

### 1.1 内部 SRAM、外部 RAM 和 Flash 怎样分工？

同样是“还有一块空闲内存”，不同存储器的访问延迟、带宽和硬件可达性也可能不同。

| 存储器 | 主要特点 | 本案例优先放什么 | 需要确认什么 |
| --- | --- | --- | --- |
| 内部 SRAM | 通常延迟低、容量有限，不需要 DRAM 式刷新 | 任务栈、控制变量、高频对象；硬件允许时放 DMA 描述符 | 哪个 SRAM Bank 可被 CPU、DMA 和其他总线主设备访问 |
| 外部 DRAM / SDRAM | 容量较大、单位成本较低，需要控制器和刷新 | 帧缓冲、大数组、文件缓存和大块数据 | 初始化、带宽、访问延迟、Cache 与 DMA 一致性 |
| PSRAM | 内部采用 DRAM 存储单元，对外提供较易用的接口并封装刷新 | 可容忍访问延迟的大缓冲区和资源缓存 | 接口带宽、访问抖动、DMA 支持及平台对任务栈的限制 |
| Flash | 掉电保持，适合代码和只读资源 | 固件、字库、常量表、配置默认值 | 擦写限制、执行方式和同 Bank 读写约束 |

先把实时控制所需的小块高速数据留在内部 SRAM，再考虑把大块、低频或可容忍延迟的数据放到外部 RAM。**外部 RAM 增加了容量，却不自动提供与内部 SRAM 相同的访问特性。**

很多 MCU 可以直接从内部 Flash 执行代码。支持 XIP（Execute In Place，就地执行）的外部 Flash 也可通过映射窗口取指，减少把整段代码复制到 RAM 的需求。不过 Cache 未命中、频繁跳转和共享总线访问，仍可能造成延迟波动。

某些芯片在擦除或编程一个 Flash Bank 时，无法继续从同一 Bank 取指。这样的 Flash 操作代码可能需要放到 RAM，连同依赖函数、常量和必要中断路径一起检查。第 6 章再说明如何安排链接与启动复制。

### 1.2 一个变量写在 C 文件里，最后会放到哪里？

物理内存回答“芯片有哪些空间”，程序段回答“链接器怎样使用这些空间”。下面是常见的 MCU 布局，最终位置仍以项目链接脚本和 Map 文件为准。

| 区域 | 常见内容 | Flash 与 RAM 的关系 |
| --- | --- | --- |
| `.text` | 机器指令 | 通常在 Flash，也可把选定代码搬到 RAM 执行 |
| `.rodata` | 只读常量、字符串、查找表 | 通常在 Flash |
| `.data` | 有非零初始值的全局变量和静态变量 | 初值占 Flash，运行时对象占 RAM，启动时复制 |
| `.bss` | 未显式初始化或零初始化的全局变量和静态变量 | 运行时占 RAM，启动时清零，通常无需在镜像中保存整块零数据 |
| 栈 | 调用现场、部分局部变量、保存的寄存器 | 通常在 RAM；RTOS 每个任务通常有独立任务栈 |
| 堆 | 运行时动态申请的对象 | 来自指定 RAM 区域，由所选分配器管理 |

```c
const uint8_t gamma_table[256] = { /* 位于只读区 */ };

uint32_t boot_count = 1;      /* 位于 .data */
static uint8_t rx_cache[512]; /* 位于 .bss */

void process_frame(void)
{
    uint8_t header[32];       /* 通常位于栈 */
    uint8_t *frame;

    frame = malloc(4096);     /* 指向堆上的对象 */
    if (frame == NULL) {
        return;
    }

    memset(header, 0, sizeof(header));
    free(frame);
}
```

局部变量也可能在寄存器里，或被编译器优化掉；上表描述的是常见布局。`static` 延长了对象生命周期，不能自动解决多个任务同时读写造成的竞态。

这里还有一个容易误判的现象：把 4 KB 的局部数组改成静态数组，确实减轻了栈压力，但 RAM 中仍然要为它保留 4 KB。**改变存放位置，不一定减少总容量。** 是否真的节省内存，要看能否进一步缩小原任务栈，或者复用工作区。

### 1.3 从链接脚本和 Map 文件建立容量账本

在常见 Cortex-M 布局中，可以看到 `0x08000000` 附近的 Flash、`0x20000000` 附近的 SRAM、`0x40000000` 附近的外设空间和 `0xE0000000` 附近的系统控制空间。它们只是帮助理解的例子，实际地址必须以芯片内存映射为准。

下面是一段简化链接脚本：

```ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
    SRAM1 (xrw) : ORIGIN = 0x20000000, LENGTH = 192K
    SRAM2 (xrw) : ORIGIN = 0x20030000, LENGTH = 64K
}

SECTIONS
{
    .text :
    {
        KEEP(*(.isr_vector))
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data :
    {
        _sdata = .;
        *(.data*)
        _edata = .;
    } > SRAM1 AT> FLASH

    .bss (NOLOAD) :
    {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        _ebss = .;
    } > SRAM1

    .dma_buffer (NOLOAD) :
    {
        . = ALIGN(32);
        *(.dma_buffer*)
        . = ALIGN(32);
    } > SRAM2
}
```

这段脚本展示了 `.data` 的加载位置和运行位置不同，也展示了把 DMA 缓冲区独立放到 SRAM2 的思路。实际工程还要补齐启动所需的符号、初始化流程和其他段。

接手网关项目时，先列出下面这张表，再谈优化：

| 对象 | 容量依据 | 生命周期 | 放置位置 | 谁负责回收或复用 |
| --- | --- | --- | --- | --- |
| 采样任务栈 | 最深调用链、上下文和实测水位 | 整个运行期 | 内部 SRAM | 不回收，固定保留 |
| 网络会话对象 | 连接数、TLS 峰值和重连路径 | 一次会话 | 网络专用池 | 会话关闭路径 |
| 采样数据块 | 单块样本数 × 块数量 | 采集到上传完成 | DMA 可达 RAM | 发送完成后归还池 |
| 日志缓存 | 最大积压量和丢弃规则 | 写入到输出完成 | 日志专用区 | 日志任务 |
| 算法工作区 | 最大输入和处理方式 | 一次运算或任务私有 | 内部或外部 RAM | 算法任务 |

容量估算要看**同时存在的峰值**。还要避免重复计数：如果动态任务栈已经从 RTOS 堆分配，就不能把“整块堆容量”和“这部分任务栈容量”再相加一遍。

### 1.4 先按问题选方法，再进入实现

下面十种方法解决的问题不同，实际项目通常组合使用。先根据对象特点和故障现象缩小范围，再进入具体实现。

| 方法 | 主要解决什么 | 先用在哪类对象 | 主要边界 |
| --- | --- | --- | --- |
| 1. 静态分配 | 长期对象的容量与创建时序不确定 | 任务、队列、关键缓冲区 | 需要预留空间，仍可能越界或发生竞态 |
| 2. 内存池 | 固定规格对象频繁创建销毁 | 消息节点、采样块、协议控制块 | 存在内部浪费，也可能耗尽 |
| 3. TLSF | 可变尺寸分配的搜索耗时 | 尺寸变化较大的受控动态业务 | 仍有管理开销、碎片和并发成本 |
| 4. 栈空间管理 | 栈预留过大或最坏路径溢出 | 每个任务和中断路径 | 实测水位不能覆盖未执行路径 |
| 5. 对齐优化 | 结构体填充、访问效率和硬件约束 | 大量对象、DMA 缓冲区 | `packed` 和 Cache 维护都需谨慎 |
| 6. 零拷贝 | 重复搬运和多份大缓冲区 | 图像、音频、网络和高速采样 | 必须明确所有权与归还时机 |
| 7. MPU | 越界后的破坏范围和访问权限 | 关键任务、代码区和私有数据 | 区域数量有限，需 RTOS 与布局配合 |
| 8. Rust 所有权 | 悬垂引用、重复释放等内存错误 | 边界清晰的新模块 | `unsafe`、FFI 和硬件操作仍需审查 |
| 9. 编译器与链接器优化 | 固件体积、无用段和热点执行 | 整个固件及计算热点 | 结果需在目标板测量 |
| 10. 检测与运行时监控 | 泄漏、碎片、耗尽和现场证据不足 | 全系统与每个资源池 | 指标与阈值必须匹配真实负载 |

## 第 2 章 让分配行为可预测：静态分配、内存池与 TLSF

网关里有些对象从开机一直存在，有些按固定规格反复使用，还有些尺寸变化很大。先按生命周期和尺寸分类，再选择分配方式，通常比全项目统一使用一种分配器更合适。

### 2.1 方法一：让长期对象在启动前就有固定空间

静态分配意味着对象的存储空间在编译、链接阶段确定，运行时不再从通用堆申请。采样任务、队列控制块、固定通信缓冲区都适合这样安排。

以 FreeRTOS 静态创建任务为例：

```c
#define SENSOR_TASK_STACK_DEPTH 512U

static StaticTask_t sensor_task_tcb;
static StackType_t sensor_task_stack[SENSOR_TASK_STACK_DEPTH];

static void sensor_task(void *argument)
{
    (void)argument;

    for (;;) {
        sensor_sample();
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

void create_sensor_task(void)
{
    TaskHandle_t handle;

    handle = xTaskCreateStatic(
        sensor_task,
        "sensor",
        SENSOR_TASK_STACK_DEPTH,
        NULL,
        4,
        sensor_task_stack,
        &sensor_task_tcb
    );

    configASSERT(handle != NULL);
}
```

启用 `configSUPPORT_STATIC_ALLOCATION`，并满足所用内核配置要求后，应用可以为任务等对象提供存储。这里的 `SENSOR_TASK_STACK_DEPTH` 是栈深度参数，不能未经核对就按字节理解；通常应结合 `StackType_t` 和具体端口换算。

静态分配提供两种确定性：链接时能检查固定区域是否放得下，运行时不必再为这个对象搜索空闲块。它也不会因该对象的反复创建、释放而形成堆外部碎片。

但这不等于“100% 可靠”。数组越界、栈溢出、并发访问和错误的容量规划照样会破坏内存。它省去了运行时分配动作，对象初始化和数据清零仍然需要执行。

代价是按上限预留。例如一个通道通常只用 256 字节，偶尔需要 4 KB，静态设计可能要一直保留 4 KB。通道数量增加后，应检查这些最坏情况是否会同时出现，再决定是否共享专用池。

如果项目要求初始化后禁止动态创建对象，可以把分配入口集中管理：

```c
static bool system_started;

void *safe_alloc(size_t size)
{
    if (system_started) {
        system_fault(FAULT_RUNTIME_ALLOCATION);
        return NULL;
    }

    return pvPortMalloc(size);
}

void system_mark_started(void)
{
    system_started = true;
}
```

这个入口只能约束经过它的调用。第三方库直接使用的 `malloc()`、其他堆或对象创建接口，也需要纳入设计；初始化时从堆分配后长期持有，和编译链接阶段确定地址的静态分配仍是两种实现。

### 2.2 方法二：为固定规格对象建立内存池

假设网关每次采集生成一块固定大小的数据。与其反复向通用堆申请，不如预留一组块：需要时取一块，发送完成后放回去。

固定块池通常使用空闲链表、位图或索引表管理。下面用空闲链表实现一个简单的固定块池：

```c
typedef struct PoolNode {
    struct PoolNode *next;
} PoolNode;

typedef struct {
    uint8_t *memory;
    size_t block_size;
    size_t block_count;
    PoolNode *free_list;
} FixedPool;
```

```c
void pool_init(FixedPool *pool,
               void *memory,
               size_t block_size,
               size_t block_count)
{
    if (pool == NULL || memory == NULL ||
        block_size < sizeof(PoolNode) || block_count == 0U) {
        return;
    }

    pool->memory = memory;
    pool->block_size = block_size;
    pool->block_count = block_count;
    pool->free_list = NULL;

    for (size_t i = 0; i < block_count; ++i) {
        PoolNode *node =
            (PoolNode *)(pool->memory + i * pool->block_size);

        node->next = pool->free_list;
        pool->free_list = node;
    }
}

void *pool_alloc(FixedPool *pool)
{
    PoolNode *node;

    if (pool == NULL || pool->free_list == NULL) {
        return NULL;
    }

    node = pool->free_list;
    pool->free_list = node->next;
    return node;
}

void pool_free(FixedPool *pool, void *ptr)
{
    PoolNode *node;

    if (pool == NULL || ptr == NULL) {
        return;
    }

    node = (PoolNode *)ptr;
    node->next = pool->free_list;
    pool->free_list = node;
}
```

分配从链表头取节点，释放插回链表，核心操作可以是 O(1)。不过这只是**单线程机制示例**：调用前必须保证内存起点和块步长满足节点及业务对象的对齐要求，容量乘法不溢出，释放的是本池块首地址且没有重复释放。多任务或中断访问时，还需合适的同步与错误检测。

固定块池避免了可变尺寸堆的外部碎片，却仍有内部浪费：申请 33 字节，使用 64 字节块，就留下 31 字节未使用空间。

对象尺寸较多时，可以分成几档：

```text
Pool A    32 字节 × 64 块
Pool B    64 字节 × 48 块
Pool C   128 字节 × 32 块
Pool D   256 字节 × 16 块
Pool E  1024 字节 ×  8 块
```

申请时选择能容纳对象的最小规格，并明确对应池耗尽后是返回失败、借用更大块，还是丢弃低优先级数据。规格数量和块数应来自实际申请尺寸与并发量统计。分得越细，并不一定越省；某个池耗尽时，其他池的空闲块未必能直接替代。

### 2.3 C++ 对象池还要处理构造、析构和并发

对于 C++ 对象，池管理的不只是字节，还包括对象的构造和析构。可以用模板固定对象类型与容量：

```cpp
#include <array>
#include <cstddef>
#include <cstdint>
#include <new>
#include <type_traits>
#include <utility>

template <typename T, std::size_t Capacity>
class StaticObjectPool {
public:
    StaticObjectPool() = default;

    StaticObjectPool(const StaticObjectPool&) = delete;
    StaticObjectPool& operator=(const StaticObjectPool&) = delete;

    template <typename... Args>
    T* create(Args&&... args)
    {
        for (std::size_t i = 0; i < Capacity; ++i) {
            if (!used_[i]) {
                used_[i] = true;

                void* address = static_cast<void*>(&storage_[i]);
                return new (address) T(std::forward<Args>(args)...);
            }
        }

        return nullptr;
    }

    bool destroy(T* object)
    {
        if (object == nullptr) {
            return false;
        }

        const auto base =
            reinterpret_cast<std::uintptr_t>(storage_.data());
        const auto current =
            reinterpret_cast<std::uintptr_t>(object);

        if (current < base ||
            current >= base + sizeof(Storage) * Capacity) {
            return false;
        }

        const std::size_t offset = current - base;

        if ((offset % sizeof(Storage)) != 0U) {
            return false;
        }

        const std::size_t index = offset / sizeof(Storage);

        if (!used_[index]) {
            return false;
        }

        object->~T();
        used_[index] = false;
        return true;
    }

    std::size_t available() const
    {
        std::size_t count = 0;

        for (bool used : used_) {
            if (!used) {
                ++count;
            }
        }

        return count;
    }

private:
    using Storage =
        std::aligned_storage_t<sizeof(T), alignof(T)>;

    std::array<Storage, Capacity> storage_{};
    std::array<bool, Capacity> used_{};
};
```

这个版本通过线性扫描寻找空位，因此 `create()` 是 O(Capacity)，不能因为名字叫对象池就声称它是 O(1)。维护空闲索引栈可以进一步缩短查找路径：

```cpp
template <std::size_t Capacity>
class FreeIndexStack {
public:
    FreeIndexStack()
    {
        for (std::size_t i = 0; i < Capacity; ++i) {
            indexes_[i] = Capacity - 1U - i;
        }
        top_ = Capacity;
    }

    bool pop(std::size_t& index)
    {
        if (top_ == 0U) {
            return false;
        }

        index = indexes_[--top_];
        return true;
    }

    bool push(std::size_t index)
    {
        if (top_ >= Capacity || index >= Capacity) {
            return false;
        }

        indexes_[top_++] = index;
        return true;
    }

private:
    std::array<std::size_t, Capacity> indexes_{};
    std::size_t top_{};
};
```

示例还需要按工程约束完善：若允许构造函数抛异常，要恢复已占用标记；池销毁前要处理仍存活的对象；并发访问需要同步；旧指针不能在槽位复用后再次参与释放。采用哪个 C++ 标准，也会影响底层存储设施的选择。

对于我们的采样块，如果对象只是固定格式数据，简单的固定块池就可能已经足够。复杂对象生命周期出现后，再增加构造、析构和句柄管理。

### 2.4 FreeRTOS 的 heap 和固定块池有什么区别？

看到“RTOS 提供了内存管理”，还要继续确认提供的是哪一种分配器。

| 实现 | 主要行为 | 选型时关心什么 |
| --- | --- | --- |
| FreeRTOS `heap_1` | 只分配，不释放 | 适合只创建、不销毁的使用模式 |
| FreeRTOS `heap_2` | 支持释放，不合并相邻空闲块 | 可变尺寸负载下要注意碎片 |
| FreeRTOS `heap_3` | 封装标准库 `malloc()` / `free()` | 行为依赖底层库及适用的并发保护方式 |
| FreeRTOS `heap_4` | 分配、释放，并合并相邻空闲块 | 能缓解外部碎片，不能保证碎片消失 |
| FreeRTOS `heap_5` | 在类似 `heap_4` 的机制上管理多个不连续区域 | 核对区域初始化与各区域硬件属性 |
| ThreadX Block Pool | 固定大小块 | 适合固定规格对象 |
| ThreadX Byte Pool | 可变尺寸字节分配 | 评估分配耗时与碎片 |

FreeRTOS 的这些 heap 实现不能直接等同于固定块对象池。在网关中，可以让关键任务静态创建、采样块走固定池、网络中的变长对象走受控堆。

### 2.5 方法三：用 TLSF 约束可变尺寸分配的查找路径

网络消息、文件对象等尺寸差异较大，全部使用固定块会浪费空间。TLSF（Two-Level Segregated Fit）通过两级尺寸分类、空闲链表和位图定位可用块。

它的基本过程是：

1. 把请求尺寸映射到两级类别。
2. 用位图寻找能容纳该请求的非空类别。
3. 取出空闲块，必要时拆分。
4. 释放时检查相邻块，能合并就合并，再挂回对应类别。

TLSF 核心分配与释放路径具有常数级复杂度，避免搜索时间随空闲块数量线性增长。**O(1) 描述算法路径，不保证每次调用耗时完全相同。** 锁竞争、中断、Cache 和具体内存速度仍会影响实际响应时间。

同样，TLSF 不保证所有负载下碎片率都低于 5%。请求尺寸、对象生命周期、对齐、最小块和池容量都会影响结果。项目若采用某个碎片率目标，应定义统计口径并用实际负载验证。

可以在分配入口记录申请次数、失败次数和峰值占用：

```c
typedef struct {
    size_t current_used;
    size_t peak_used;
    size_t allocation_count;
    size_t free_count;
    size_t failed_count;
    size_t largest_request;
} HeapMetrics;

static HeapMetrics heap_metrics;

void *tracked_alloc(size_t size)
{
    void *ptr = tlsf_malloc(tlsf_handle, size);

    heap_metrics.allocation_count++;

    if (size > heap_metrics.largest_request) {
        heap_metrics.largest_request = size;
    }

    if (ptr == NULL) {
        heap_metrics.failed_count++;
        return NULL;
    }

    size_t actual_size = tlsf_block_size(ptr);
    heap_metrics.current_used += actual_size;

    if (heap_metrics.current_used > heap_metrics.peak_used) {
        heap_metrics.peak_used = heap_metrics.current_used;
    }

    return ptr;
}
```

这里仅展示分配侧，完整监控还要在释放侧扣减、统计失败并处理并发。`current_used` 也只是按所用接口口径统计的块大小，不能直接当作所有管理开销之和。

### 2.6 按业务隔离资源，给失败安排不同出口

如果图像、网络、日志和控制共用一个池，网络突发流量可能耗尽控制任务所需资源。按业务建立独立池，可以限制资源竞争范围：

```c
typedef enum {
    MEM_POOL_CONTROL,
    MEM_POOL_NETWORK,
    MEM_POOL_IMAGE,
    MEM_POOL_GENERAL
} MemoryPoolId;

void *system_alloc(MemoryPoolId pool_id, size_t size)
{
    switch (pool_id) {
    case MEM_POOL_CONTROL:
        return NULL; /* 控制域禁止动态分配 */

    case MEM_POOL_NETWORK:
        return tlsf_malloc(network_tlsf, size);

    case MEM_POOL_IMAGE:
        return tlsf_malloc(image_tlsf, size);

    case MEM_POOL_GENERAL:
        return tlsf_malloc(general_tlsf, size);

    default:
        return NULL;
    }
}
```

不同业务域应设置不同的失败策略：控制域可以禁止动态分配，网络域处理分配失败，日志域丢弃低优先级记录。

独立池提供容量隔离，但不是硬件访问隔离：错误指针仍可能写坏另一个池，第 5 章的 MPU 才处理访问权限问题。分池也会减少资源互相借用的灵活性，要同时观察各池的峰值和空闲量。

## 第 3 章 管住任务栈：减少预留浪费，也守住最坏路径

网关每个任务都有自己的调用链。正常采样时栈占用很小，不代表重连、格式化日志和错误回调同时发生时也够用。栈管理既要发现不足，也要识别没有依据的过量预留。

### 3.1 方法四：先找到最深调用链，再决定栈大小

假设通信任务栈为 6 KB，函数里增加两个 2 KB 临时数组，调用链上还有 TLS、日志格式化和驱动回调。普通测试可能通过，重连压测时却可能出现 HardFault。

栈越界通常不会像堆分配失败那样返回 `NULL`，而是直接覆盖相邻数据。因此评估任务栈时，需要一起考虑：

- 最深调用链中同时存在的局部变量和调用现场。
- C 库、浮点格式化、协议栈及第三方库的需求。
- 最坏输入触发的深层分支、递归或动态栈分配。
- RTOS 保存的上下文，以及端口中任务栈与中断栈的实际分工。

“简单任务几百字节、网络任务几 KB”只能帮助形成初始估算，不能作为最终配置。

编译器可以提供函数栈使用信息：

```sh
arm-none-eabi-gcc \
  -O2 \
  -fstack-usage \
  -c protocol_parser.c
```

```text
protocol_parser.c:42:5:parse_header    96    static
protocol_parser.c:87:5:parse_payload   224   static
protocol_parser.c:131:5:decode_frame   560   dynamic,bounded
```

`.su` 文件能辅助分析单个函数，但还要结合调用关系。间接调用、递归、汇编和预编译库都可能留下分析缺口，因此需要运行时水位配合。

### 3.2 用高水位观察历史余量，但别把它当成证明

常见方法是在任务启动前用固定模式填充栈，运行后检查哪些区域仍未被改写，从而估计历史使用量：

```c
#define STACK_PATTERN 0xA5U

void stack_fill(uint8_t *stack, size_t size)
{
    if (stack == NULL) {
        return;
    }

    memset(stack, STACK_PATTERN, size);
}

size_t stack_unused_bytes(const uint8_t *stack, size_t size)
{
    size_t unused = 0;

    if (stack == NULL) {
        return 0;
    }

    while (unused < size && stack[unused] == STACK_PATTERN) {
        ++unused;
    }

    return unused;
}
```

这段扫描逻辑假设未使用区域位于数组低地址侧，必须结合栈增长方向和 RTOS 布局调整。**不能对正在使用的活动栈执行填充。** 在 RTOS 中优先采用内核提供的查询与溢出检测机制。

```c
void report_task_stack(TaskHandle_t task, const char *name)
{
    UBaseType_t watermark =
        uxTaskGetStackHighWaterMark(task);

    log_info("%s stack watermark=%lu",
             name,
             (unsigned long)watermark);
}
```

`uxTaskGetStackHighWaterMark()` 表示任务运行以来观察到的最小剩余栈空间。单位必须核对所用端口；若按 `StackType_t` 元素返回，才可乘以 `sizeof(StackType_t)` 换算字节，不能对所有平台统一套用。

水位只是已经执行路径的证据。未触发过的握手失败、超长输入或异常日志分支不会自动包含在测量里，填充扫描也不等于精确捕捉所有栈指针变化。

### 3.3 把大工作区移出栈后，继续检查所有权

两个大数组就可能占去整个任务栈：

```c
void bad_decode(void)
{
    uint8_t input[4096];
    uint8_t output[4096];

    /* 两个数组已经占用 8KB 栈 */
}
```

如果解码任务独占工作区，可以改成任务私有的长期缓冲区：

```c
typedef struct {
    uint8_t input[4096];
    uint8_t output[4096];
} DecoderWorkspace;

static DecoderWorkspace decoder_workspace;

void decode_frame(void)
{
    decode(decoder_workspace.input,
           decoder_workspace.output);
}
```

接下来要回答：是否有第二个任务或重入回调也调用 `decode_frame()`？如果有，共用这个静态工作区会引入竞态。可以为任务分别配置工作区，或从专用池获取并在结束后归还。

其他有效手段包括缩短同时存活的局部数据范围、控制调用深度、限制递归，以及减少高开销格式化。修改后重新测量最坏路径，再决定能否缩小任务栈，不能只看到“大数组已经改成 static”就宣布省下了同等 RAM。

## 第 4 章 减少数据开销：先对齐，再消除重复搬运

采样数据从 DMA 到算法，再到网络发送，可能经过多个模块。这里既要避免结构体填充造成的容量浪费，也要保证 CPU 与 DMA 看到同一份有效数据。

### 4.1 方法五：从结构体填充开始，验证每个对象的实际尺寸

看下面这个配置结构体：

```c
typedef struct {
    uint8_t  enabled;
    uint32_t baudrate;
    uint8_t  channel;
    uint16_t timeout_ms;
} ConfigA;
```

成员大小相加是 8 字节，但在常见的 4 字节对齐 ABI 下，填充可能让 `sizeof(ConfigA)` 变成 12。数组中有一千个对象，就会放大这部分差异。

调整顺序后：

```c
typedef struct {
    uint32_t baudrate;
    uint16_t timeout_ms;
    uint8_t  enabled;
    uint8_t  channel;
} ConfigB;
```

`ConfigB` 在同类 ABI 下通常为 8 字节。实际结果可以用 `sizeof()` 和 `offsetof()` 验证：

```c
printf("ConfigA=%u\n", (unsigned)sizeof(ConfigA));
printf("enabled=%u\n",
       (unsigned)offsetof(ConfigA, enabled));
printf("baudrate=%u\n",
       (unsigned)offsetof(ConfigA, baudrate));
printf("channel=%u\n",
       (unsigned)offsetof(ConfigA, channel));
printf("timeout=%u\n",
       (unsigned)offsetof(ConfigA, timeout_ms));
```

已经用于协议、文件或其他模块 ABI 的结构体，不能直接随意改布局。内部对象与外部数据格式应明确区分。

也不要给所有结构体加 `packed`。打包可能产生未对齐成员，访问成本和支持程度取决于目标平台。可以用 `memcpy()` 取出多字节字段：

```c
typedef struct __attribute__((packed)) {
    uint8_t  type;
    uint32_t timestamp;
    uint16_t length;
} PacketHeader;
```

```c
uint32_t packet_get_timestamp(const PacketHeader *header)
{
    uint32_t value;

    memcpy(&value,
           &header->timestamp,
           sizeof(value));

    return value;
}
```

这种方式避免直接按未对齐整数地址解引用，但**不会完成字节序转换**。如果字段来自网络或文件，还要按格式约定解码。

### 4.2 DMA 缓冲区需要同时满足地址、长度和可达性要求

CPU 允许访问的内存，DMA 未必都能访问；CPU 允许的未对齐访问，DMA 也未必支持。先查芯片总线与 DMA 约束，再安排缓冲区。

```c
static uint8_t dma_rx_buffer[2048]
    __attribute__((aligned(32), section(".dma_buffer")));
```

这里的 32 字节是示例值。真正的对齐要求应来自处理器、Cache Line、DMA 外设和所用维护接口。

带 D-Cache 的系统还可能出现两种不同问题：

| 数据方向 | 可能出现的旧数据 | 常见处理思路 |
| --- | --- | --- |
| CPU 写，DMA 读 | CPU 新数据仍在脏 Cache Line 中，RAM 尚未更新 | DMA 启动前 Clean 对应缓存区域，并按平台要求完成同步 |
| DMA 写，CPU 读 | DMA 更新了 RAM，CPU 仍读缓存副本 | 接收前安排好缓存状态；DMA 完成并交还所有权后，再按平台要求 Invalidate |

缓存维护的地址范围可以通过辅助函数扩展到 Cache Line 边界：

```c
#define CACHE_LINE_SIZE 32U

static uintptr_t align_down(uintptr_t value, size_t alignment)
{
    return value & ~(uintptr_t)(alignment - 1U);
}

static uintptr_t align_up(uintptr_t value, size_t alignment)
{
    return (value + alignment - 1U) &
           ~(uintptr_t)(alignment - 1U);
}

void dma_prepare_tx(void *buffer, size_t length)
{
    uintptr_t start =
        align_down((uintptr_t)buffer, CACHE_LINE_SIZE);

    uintptr_t end =
        align_up((uintptr_t)buffer + length,
                 CACHE_LINE_SIZE);

    SCB_CleanDCache_by_Addr(
        (void *)start,
        (int32_t)(end - start)
    );
}

void dma_finish_rx(void *buffer, size_t length)
{
    uintptr_t start =
        align_down((uintptr_t)buffer, CACHE_LINE_SIZE);

    uintptr_t end =
        align_up((uintptr_t)buffer + length,
                 CACHE_LINE_SIZE);

    SCB_InvalidateDCache_by_Addr(
        (void *)start,
        (int32_t)(end - start)
    );
}
```

这只是维护接口的示意，还需要保证：对齐值是有效的 2 的幂，地址和长度计算不溢出，范围符合接口参数限制，屏障与调用顺序符合平台规定。对于接收缓冲区，尤其要防止 DMA 期间脏缓存回写覆盖新数据。

**不要只把维护范围向两端扩展，而让无关变量继续共用边界 Cache Line。** Invalidate 可能丢弃同一行里其他尚未写回的数据。专用段、独占缓存行和明确的交接协议，比事后补一个函数调用更完整。

多核系统还有伪共享：不同核心写不同变量，却因变量共用一条 Cache Line 而反复争用。需要时可以隔开这些高频变量，但增加的填充空间也应计入预算。

### 4.3 方法六：模块之间传递缓冲区，不再复制整块数据

假设摄像头采集一帧，算法复制一份，编码器再建输出缓冲区，网络层又复制一次。消耗的不只是 CPU 时间，还有同时存在的多份数据。

零拷贝的核心是传递同一块数据的所有权或引用。可以采用描述符记录数据地址与长度：

```c
typedef struct {
    uint8_t *data;
    size_t length;
    uint32_t timestamp;
    uint16_t buffer_id;
} FrameBuffer;
```

任务间传递指向描述符的指针：

```c
FrameBuffer *frame;

if (xQueueReceive(camera_queue,
                  &frame,
                  portMAX_DELAY) == pdPASS) {
    image_process(frame);
    xQueueSend(encoder_queue,
               &frame,
               portMAX_DELAY);
}
```

这个片段展示了“队列复制指针，而不是整帧数据”。实际创建队列时，队列项大小也必须与指针类型一致。还要检查投递结果：只有交接成功才转移所有权，失败、取消和超时路径必须安排归还。

这里使用无限等待只是在简化流程。实际链路是否允许阻塞、队列满时如何降级，应由业务决定；中断路径必须使用适合中断上下文的接口。

Linux 可以借助 `mmap()` 映射设备或共享内存，RTOS 常用 DMA 直接写预分配缓冲区，多核系统则可能共享同一片 RAM。它们都需要处理有效范围、生命周期和同步；使用某个接口名称，不代表整条链路自动实现零拷贝。

### 4.4 双缓冲能并行采集和处理，但不能解决持续过载

双缓冲让 DMA 写 A 时，CPU 处理 B，完成后交换。它成立的前提是处理速度能跟上采集速度。

如果 CPU 处理一块数据，比 DMA 填满下一块还慢，第二次交换时仍可能覆盖未处理内容。增加到三缓冲或环形缓冲可以吸收短时抖动，却不能消除长期吞吐不足。

为每块数据建立状态，比只交换两个指针更容易审查：

```c
typedef enum {
    BUFFER_FREE,
    BUFFER_DMA_WRITING,
    BUFFER_READY,
    BUFFER_PROCESSING
} BufferState;
```

```text
FREE → DMA_WRITING → READY → PROCESSING → FREE
```

对应的交接规则应明确：

1. 只有空闲块可以交给 DMA。
2. DMA 完成、缓存维护结束后，数据才交给 CPU。
3. 业务或网络仍在引用时，不得提前回收或覆盖。
4. 发送完成、失败或取消后，由约定的唯一责任方归还。
5. 没有空闲块时，执行预先定义的停采、丢弃或背压策略。

网络包、图像、显示和音频等大数据更容易从少拷贝中获益。对于一个 8 字节命令，直接复制可能比维护指针、引用计数和回收队列更简单。

## 第 5 章 给错误设置边界：MPU 与 Rust 所有权

前面的策略主要管理容量、时序和数据流。接下来处理另一类问题：如果代码写错地址，或者释放了仍被使用的对象，怎样尽早发现并限制破坏范围？

### 5.1 方法七：用 MPU 限制任务能够访问的区域

MPU（Memory Protection Unit，内存保护单元）根据配置区域检查权限与内存属性。它通常不承担 MMU 式的虚拟地址转换，而是约束哪些地址能读、能写、能执行。

对网关的普通业务任务，可以先形成这样的权限设计：

| 区域 | 期望权限 | 目的 |
| --- | --- | --- |
| 任务私有栈和数据 | 读写、禁止执行 | 限制数据区被当作代码执行 |
| 共享只读配置 | 只读 | 防止普通任务误改配置 |
| 代码与受控系统调用入口 | 按架构能力设置读、执行权限 | 提供必要执行入口 |
| 内核私有数据和关键外设 | 普通任务不可访问 | 限制错误写入与越权操作 |

RTOS 可以在任务切换时更新区域配置，让普通任务在非特权模式运行，需要内核服务时通过受控入口处理。

这需要内核端口和内存布局配合。Armv7-M 与 Armv8-M 在区域描述、大小、对齐和属性配置上存在差异，不能直接混用一段 MPU 寄存器初始化代码。区域数量也有限，应先设计权限表，再写平台配置。

MPU 不能检测所有越界：错误访问如果仍落在允许区域内，就可能继续发生。它也不应被默认视作对所有 DMA 主设备的访问保护。非法访问触发 Fault 后，还需要故障处理程序记录现场并进入约定状态。

### 5.2 方法八：把对象所有权写进语言规则

C/C++ 中常见的错误包括返回局部数组地址、重复释放、释放后使用，以及异常分支忘记回收。对异步网关程序，更难的是回答“发送失败、超时和取消同时发生时，到底由谁释放”。

Rust 通过所有权与借用规则，把一部分检查提前到编译期。下面的例子展示了所有权转移：

```rust
fn consume_buffer(data: Vec<u8>) {
    println!("{}", data.len());
}

fn main() {
    let packet = vec![1, 2, 3, 4];

    consume_buffer(packet);

    // println!("{:?}", packet);
    // 编译失败，所有权已经转移
}
```

调用以后，`packet` 的所有权已经交给函数，原变量不能继续访问。这个例子使用 `Vec` 和标准库，主要解释语义；裸机 `no_std` 项目还需另外评估分配器或使用固定容量容器。

如果只是临时读取，可以借用切片：

```rust
fn checksum(data: &[u8]) -> u32 {
    data.iter()
        .fold(0u32, |sum, value| sum + *value as u32)
}

fn main() {
    let packet = [1u8, 2, 3, 4];

    let value = checksum(&packet);

    println!("{}", value);
}
```

借用规则允许多个共享引用，或在相应使用期间存在独占可变引用，阻止不合法的重叠访问。生命周期标注表达引用之间的有效期关系，不负责延长底层对象的实际寿命：

```rust
fn choose_longer<'a>(
    left: &'a [u8],
    right: &'a [u8],
) -> &'a [u8] {
    if left.len() >= right.len() {
        left
    } else {
        right
    }
}
```

所有权不需要依赖垃圾回收器。不过安全保证仍依赖 `unsafe`、FFI、底层抽象和硬件交互遵守契约；Rust 也允许资源泄漏，不能把它理解成“所有内存问题都会被编译器消除”。

### 5.3 评估迁移成本，同时把所有权规则用于现有 C 工程

Tock OS、Hopter OS 等项目展示了 Rust 在嵌入式操作系统中的应用。具体项目是否采用，仍要核对目标芯片支持、厂商 SDK、工具链、已有驱动和团队维护能力。

更容易落地的起点是边界清晰的新模块，例如协议解析、升级包校验或独立数据处理服务，再通过受控 FFI 与旧系统连接。

“零成本抽象”也不等于任何 Rust 写法都不占空间。泛型单态化、格式化、边界检查和库选择都要通过生成代码与板上测量评估。

即使继续用 C，也可以把前面零拷贝链路的规则写进接口契约：谁创建、借用多久、成功后谁拥有、失败后谁释放、取消如何处理。MPU 负责访问边界，所有权设计负责对象生命周期，两者可以配合使用。

## 第 6 章 让工具链参与优化：体积、热点与硬件能力

代码逻辑没有改变，编译选项、链接段和库配置也可能显著影响 Flash、RAM 与执行时间。这里的核心是比较产物和实测结果，而不是选择名字看起来最激进的选项。

### 6.1 方法九：分别评估代码体积和执行时间

| 目标 | 可以尝试的配置 | 验证重点 |
| --- | --- | --- |
| 日常调试 | `-Og -g3` | 单步与变量可见性，同时保留一定优化 |
| 受限容量固件 | `-Os`；工具链支持时评估 `-Oz` | 固件体积、运行时间和栈需求 |
| 计算热点 | 对特定模块尝试 `-O3` | 周期、代码膨胀、Cache 与 Flash 带宽 |
| 浮点与控制逻辑 | 与业务语义匹配的选项 | 精度、边界输入、NaN 与无穷大处理 |

`-O3` 可能通过内联、循环变换等提高速度，也可能因代码增大而降低指令 Cache 命中率。`-ffast-math` 等选项会改变浮点语义，不能仅因“更快”就全局启用。

比较时要保持输入、功能和构建条件可比，并使用量产配置重新执行关键路径测试。Debug 版本的栈水位和时序，不能直接代替 Release 结果。

### 6.2 通过 LTO 和段回收删除未使用内容

LTO 在链接阶段跨源文件分析，可以带来跨模块优化。函数与数据分段后，链接器还能回收未引用的输入段：

```sh
arm-none-eabi-gcc \
  -Os \
  -flto \
  -ffunction-sections \
  -fdata-sections \
  -c app.c
```

链接阶段同样要正确启用 LTO，并加入：

```text
-Wl,--gc-sections
```

对于中断向量、注册表、启动入口等特殊段，要防止它们因为缺少普通引用而被删除：

```ld
.isr_vector :
{
    KEEP(*(.isr_vector))
} > FLASH

.driver_registry :
{
    KEEP(*(SORT(.driver_registry.*)))
} > FLASH
```

仅在链接脚本写 `KEEP()`，也不能替代所有编译期和归档库保留机制。采用特殊段注册时，还应检查对象文件是否被提取、编译器是否生成对应对象，并在最终 Map 文件中确认条目确实存在。

优化后不只比较总字节数，还要验证驱动注册、中断入口、启动初始化和必要资源是否仍正常。

### 6.3 把少量关键代码放到 RAM，并完成启动复制

Flash 编程例程、高频中断或短控制环可能需要从 RAM 执行。安排运行地址只是第一步，还要保留 Flash 中的加载镜像，并在执行前复制。

下面以控制环为例，将函数放入专用代码段：

```c
__attribute__((section(".fastcode")))
void motor_current_loop(void)
{
    float ia = adc_get_phase_a();
    float ib = adc_get_phase_b();

    motor_foc_step(ia, ib);
}
```

链接脚本可以这样安排，并补齐启动复制所需的加载地址符号：

```ld
.fastcode :
{
    . = ALIGN(4);
    __fastcode_start__ = .;
    *(.fastcode*)
    . = ALIGN(4);
    __fastcode_end__ = .;
} > SRAM1 AT> FLASH

__fastcode_load__ = LOADADDR(.fastcode);
```

启动阶段在调用之前复制：

```c
extern uint8_t __fastcode_load__[];
extern uint8_t __fastcode_start__[];
extern uint8_t __fastcode_end__[];

void copy_fastcode(void)
{
    size_t length = (size_t)((uintptr_t)__fastcode_end__ -
                            (uintptr_t)__fastcode_start__);
    memcpy(__fastcode_start__, __fastcode_load__, length);
}
```

这里按嵌入式链接符号的地址约定取范围。带 Cache 或执行权限约束的平台，还需完成相应同步和权限设置。函数内部调用的其他函数、常量表和中断依赖，也应检查是否仍访问暂时不可用的 Flash。

**RAM 执行通常是在用 RAM 换取时序或可用性，不是同时节省 Flash 和 RAM。** 只搬经过测量确认的必要代码，并把运行区占用计入预算。

### 6.4 正确使用 FPU、DSP 与 SIMD，并计算上下文成本

具备相应 FPU 的目标可以使用硬件浮点，但编译参数必须与具体芯片、浮点单元和库 ABI 一致。下面是一组面向相应 Cortex-M7 单精度 FPU 的配置示例：

```text
-mcpu=cortex-m7
-mthumb
-mfpu=fpv5-sp-d16
-mfloat-abi=hard
```

它不能直接套到任意 Cortex-M7 或其他型号。链接的预编译库也必须采用兼容 ABI。

DSP/SIMD 能让某些计算更高效，例如使用 CMSIS-DSP 完成 Q15 向量加法：

```c
#include "arm_math.h"

void q15_vector_add(const q15_t *a,
                    const q15_t *b,
                    q15_t *out,
                    uint32_t count)
{
    arm_add_q15(a, b, out, count);
}
```

硬件加速有时可以缩短数据驻留时间，或改变算法的工作区需求，但不保证自动减少内存。浮点上下文还可能增加任务切换和异常保存成本，因此要同时测周期、栈与固件体积。

## 第 7 章 让长期问题留下证据：泄漏检测与运行时监控

网关运行二十天后重启，单次调试很难还原原因。容量规划解决“应该够用”，长期监控则检查“实际是否持续回到预期状态”。

### 7.1 方法十：从异常路径和统一清理出口开始

泄漏经常藏在连接失败、超时和取消路径。下面的发送函数在连接失败时直接返回，遗漏了 `packet_free()`：

```c
int send_packet(const uint8_t *data, size_t length)
{
    Packet *packet = packet_alloc(length);

    if (packet == NULL) {
        return -1;
    }

    if (network_connect() != 0) {
        return -2; /* packet 泄漏 */
    }

    if (network_send(packet) != 0) {
        packet_free(packet);
        return -3;
    }

    packet_free(packet);
    return 0;
}
```

统一清理出口能减少重复释放逻辑：

```c
int send_packet(const uint8_t *data, size_t length)
{
    int result = -1;
    Packet *packet = packet_alloc(length);

    if (packet == NULL) {
        return -1;
    }

    if (network_connect() != 0) {
        result = -2;
        goto cleanup;
    }

    if (network_send(packet) != 0) {
        result = -3;
        goto cleanup;
    }

    result = 0;

cleanup:
    packet_free(packet);
    return result;
}
```

这两个片段聚焦资源清理，尚未展示把 `data` 复制或引用到包中的业务过程。示例也假设 `network_send()` 在返回前已经完成对包的使用；若异步发送接管对象，应由完成或取消路径释放，不能继续照抄函数尾部的释放动作。

多个资源按顺序获取时，逐项记录是否获取成功，并按依赖关系清理。C++ 可以用 RAII 进一步约束生命周期；无论哪种写法，都要覆盖成功、失败、超时与取消。

### 7.2 同时记录空闲总量、最大连续块和栈水位

FreeRTOS 常见查询接口包括 `xPortGetFreeHeapSize()`、`xPortGetMinimumEverFreeHeapSize()` 和任务栈高水位接口。它们的可用性与统计口径取决于所选 heap 和端口，不代表系统中所有内存区域的总余量。

```c
typedef struct {
    size_t free_heap;
    size_t minimum_free_heap;
    UBaseType_t sensor_stack_watermark;
    UBaseType_t network_stack_watermark;
} MemorySnapshot;

void memory_collect_snapshot(MemorySnapshot *snapshot)
{
    if (snapshot == NULL) {
        return;
    }

    snapshot->free_heap =
        xPortGetFreeHeapSize();

    snapshot->minimum_free_heap =
        xPortGetMinimumEverFreeHeapSize();

    snapshot->sensor_stack_watermark =
        uxTaskGetStackHighWaterMark(sensor_task_handle);

    snapshot->network_stack_watermark =
        uxTaskGetStackHighWaterMark(network_task_handle);
}
```

支持堆统计时，可以继续观察块分布：

```c
void report_heap_stats(void)
{
    HeapStats_t stats;

    vPortGetHeapStats(&stats);

    log_info(
        "heap free=%u min=%u largest=%u blocks=%u",
        (unsigned)stats.xAvailableHeapSpaceInBytes,
        (unsigned)stats.xMinimumEverFreeBytesRemaining,
        (unsigned)stats.xSizeOfLargestFreeBlockInBytes,
        (unsigned)stats.xNumberOfFreeBlocks
    );
}
```

这些指标回答不同问题：

| 指标 | 能帮助判断什么 | 不能直接推断什么 |
| --- | --- | --- |
| 当前空闲堆 | 当前余量与负载变化 | 不能说明能申请同样大小的连续块 |
| 历史最低空闲堆 | 曾经出现的最坏容量压力 | 不会在对象释放后回升，单独下降不证明泄漏 |
| 最大连续空闲块 | 当前大块申请能力 | 还需考虑对齐与分配器管理开销 |
| 空闲块数量与尺寸 | 碎片分布变化 | 不能脱离实际申请模式评价好坏 |
| 各任务栈高水位 | 已运行路径的栈余量 | 不能证明未执行的异常路径安全 |
| 池占用与失败次数 | 哪类资源正在耗尽 | 失败后业务是否恢复仍需另外记录 |

总空闲 30 KB、最大连续空闲块只有 2 KB 时，大块申请仍可能失败。判断泄漏时，应比较相同业务阶段、资源清理完成后的当前占用与对象数量，而不只看历史最低值。

### 7.3 用静态分析和 Trace 补齐时间线

静态分析可以提前发现数组越界、空指针解引用、释放后使用、未初始化变量、资源泄漏和危险转换。可用工具包括编译器警告、Clang-Tidy、Cppcheck、Coverity 和 PVS-Studio。

可以从支持的编译器警告开始：

```text
-Wall
-Wextra
-Wshadow
-Wconversion
-Wsign-conversion
-Wcast-align
-Wformat=2
-Wundef
-Wdouble-promotion
-Werror=return-type
```

对于已有大量警告的项目，先建立基线，要求新增代码不引入新问题，再分模块治理。工具报告仍要结合真实路径判断，不能把“零警告”理解成“零内存错误”。

现场故障与指标采集可以使用 Memfault，运行事件与堆事件记录可以使用 SystemView。将自定义分配入口接入 Trace 的示例如下：

```c
void *debug_malloc(size_t size)
{
    void *ptr = pvPortMalloc(size);

    if (ptr != NULL) {
        SEGGER_SYSVIEW_HeapAlloc(
            HEAP_ID,
            ptr,
            (unsigned)size
        );
    }

    return ptr;
}

void debug_free(void *ptr)
{
    if (ptr == NULL) {
        return;
    }

    SEGGER_SYSVIEW_HeapFree(
        HEAP_ID,
        ptr
    );

    vPortFree(ptr);
}
```

接入时需匹配所用版本和 SDK，并配置对应堆。记录机制自身也会占空间、消耗时间，应避免递归调用分配器，且在内存紧张时仍能留下必要证据。

有了分配事件、任务切换、栈水位和重启原因，才能还原“网络对象增加 → 最大连续块缩小 → 申请失败 → 异常循环 → 看门狗复位”的时间线。

### 7.4 让预警触发具体动作，并在相同业务阶段比较趋势

量产系统可以按内存状态分级处理：

| 状态 | 触发依据 | 可以执行的动作 |
| --- | --- | --- |
| 正常 | 各池、堆和栈有足够余量 | 低频记录指标 |
| 警告 | 接近经验证的业务峰值边界 | 提高采样频率、限制低优先级请求、减少非必要缓存 |
| 危险 | 无法保证下一关键操作所需资源 | 保留上下文、拒绝新请求、降级或进入约定安全状态 |

下面的函数展示了分级判断逻辑，数值仅用于演示：

```c
typedef enum {
    MEMORY_LEVEL_NORMAL,
    MEMORY_LEVEL_WARNING,
    MEMORY_LEVEL_CRITICAL
} MemoryLevel;

MemoryLevel memory_evaluate(size_t free_heap,
                            size_t largest_block,
                            size_t minimum_stack)
{
    if (free_heap < 4096U ||
        largest_block < 2048U ||
        minimum_stack < 64U) {
        return MEMORY_LEVEL_CRITICAL;
    }

    if (free_heap < 12288U ||
        largest_block < 8192U ||
        minimum_stack < 192U) {
        return MEMORY_LEVEL_WARNING;
    }

    return MEMORY_LEVEL_NORMAL;
}
```

调用前先统一 `minimum_stack` 的单位。阈值必须来自项目真实峰值、最大单次请求和故障注入测试，不能直接把 4096、2048、64 等值复制到量产配置。

趋势统计同样重要：空闲量每小时下降 500 字节，与正常的业务峰谷不同。可以使用采样差值估算每小时变化：

```c
int32_t memory_leak_rate(const MemorySample *old_sample,
                         const MemorySample *new_sample)
{
    uint32_t elapsed =
        new_sample->timestamp_s -
        old_sample->timestamp_s;

    if (elapsed == 0U) {
        return 0;
    }

    return (int32_t)(
        ((int64_t)new_sample->free_heap -
         (int64_t)old_sample->free_heap) *
        3600 /
        elapsed
    );
}
```

这里的 `MemorySample` 代表包含 `timestamp_s` 和 `free_heap` 的采样记录。返回负值表示空闲堆在下降，它更准确地说是“空闲堆变化速率”，不能单凭两点就认定泄漏。还要控制采样阶段、时间差范围、整数范围，并排除正常缓存增长。

记录失败时至少保留业务阶段、池名、申请尺寸、当前余量、最大连续块、相关任务水位和重启原因。预留一个有界的故障记录通道，避免出错后还要向已经耗尽的堆申请日志对象。

## 第 8 章 把方法接起来：三个工程案例与实施顺序

单项技巧解决局部问题，工程故障往往跨越容量、生命周期、缓存和异常恢复。下面通过摄像头、工业网关和高速采样三个案例，说明怎样用证据选择策略。

### 8.1 摄像头 RAM 不足：先计算同时存在的帧缓冲区

以一台拥有 512 KB 内部 SRAM 和 8 MB PSRAM 的摄像头终端为例，它需要采集、识别、JPEG 编码和网络上传。初版存在完整 RGB 双缓冲、算法输入副本、编码输出和网络发送副本。

640 × 480 的 RGB565 图像，每像素 2 字节：

```text
640 × 480 × 2 = 614400 字节 = 600 KiB
```

一帧已经超过 512 KiB 内部 SRAM 容量。启动成功，只能说明当时部分功能尚未同时占用资源，不能说明网络重传与算法并发时也够用。

优化围绕减少同时存活的数据展开：选择适合后续处理的输出格式，算法分块处理，编码器直接读取采集缓冲区，网络引用编码输出，大缓冲区进入专用 PSRAM 池，控制数据留在内部 SRAM。

```text
摄像头 DMA
    ↓
采集缓冲区
    ↓ 传描述符
分块识别
    ↓ 同一缓冲区
JPEG 编码
    ↓ 输出块链表
网络发送
    ↓ 发送完成
缓冲区归还池
```

描述符还需要记录容量、有效长度、标识和状态：

```c
typedef struct {
    uint8_t *address;
    size_t capacity;
    size_t valid_length;
    uint16_t id;
    BufferState state;
} ImageBuffer;

static ImageBuffer image_buffers[3];

ImageBuffer *image_acquire(BufferState expected,
                           BufferState next)
{
    taskENTER_CRITICAL();

    for (size_t i = 0; i < 3U; ++i) {
        if (image_buffers[i].state == expected) {
            image_buffers[i].state = next;
            taskEXIT_CRITICAL();
            return &image_buffers[i];
        }
    }

    taskEXIT_CRITICAL();
    return NULL;
}
```

这个获取函数只说明在临界区内改变状态。实际工程需初始化各描述符和底层内存、约束合法状态迁移，并覆盖发送失败与取消后的归还；它本身没有完成全部所有权管理。

优化效果应通过相同负载下的峰值占用、数据搬运耗时和吞吐量比较确认。具体做法是画出缓冲区生命周期，统计每个阶段同时存在多少块，再验证格式、内存可达性和吞吐是否满足要求。

### 8.2 工业网关二十天后重启：沿重连路径寻找未归还对象

一台工业网关在短期测试中正常，运行约二十天后偶发重启。加入循环故障日志后发现，重连过程的内存压力逐步增加，最大连续空闲块缩小，最终 TLS 会话创建失败，异常循环触发看门狗。

继续检查资源路径，发现 DNS 结果在部分失败分支未释放，重传节点也因释放顺序错误发生丢失。原始重连函数如下：

```c
int reconnect_server(void)
{
    DnsResult *dns = dns_lookup(server_name);

    if (dns == NULL) {
        return -1;
    }

    Connection *connection =
        connection_create(dns->address);

    if (connection == NULL) {
        return -2; /* dns 没有释放 */
    }

    if (connection_handshake(connection) != 0) {
        connection_destroy(connection);
        return -3; /* dns 仍然没有释放 */
    }

    dns_result_free(dns);
    active_connection = connection;
    return 0;
}
```

改为统一清理，并在成功时显式转移连接所有权：

```c
int reconnect_server(void)
{
    int result = -1;
    DnsResult *dns = NULL;
    Connection *connection = NULL;

    dns = dns_lookup(server_name);
    if (dns == NULL) {
        result = -1;
        goto cleanup;
    }

    connection = connection_create(dns->address);
    if (connection == NULL) {
        result = -2;
        goto cleanup;
    }

    if (connection_handshake(connection) != 0) {
        result = -3;
        goto cleanup;
    }

    active_connection = connection;
    connection = NULL;
    result = 0;

cleanup:
    if (connection != NULL) {
        connection_destroy(connection);
    }

    if (dns != NULL) {
        dns_result_free(dns);
    }

    return result;
}
```

这里的 `connection = NULL` 表示对象已经交给 `active_connection`，清理出口不再销毁它。示例假设旧连接已在其他流程妥善处理，不能覆盖仍持有资源的旧句柄。

随后把网络会话对象放入独立池，并检查重连后临时对象是否回到基线：

```c
void network_pool_assert_baseline(void)
{
    NetworkPoolStats stats;

    network_pool_get_stats(&stats);

    if (stats.allocated_temp_nodes != 0U) {
        log_error(
            "network temp node leak count=%u",
            (unsigned)stats.allocated_temp_nodes
        );

        fault_capture(FAULT_NETWORK_POOL_LEAK);
    }
}
```

断言必须放在临时操作确实结束的阶段，基线也要与业务状态一致。若仍有合法异步操作进行，临时对象不一定应该为零。

修复后用反复断网、超时、失败握手和恢复过程进行长时间压测。是否修好，要看同一阶段的当前空闲量、对象数量和连续块能力是否稳定，不能只看历史最低水位是否下降。

### 8.3 DMA 偶尔读到旧数据：把缓存和缓冲区交接一起检查

一块 Cortex-M7 控制板通过 DMA 接收高速 ADC 数据，低速正常，高速时偶尔读到旧数据。临时关闭 D-Cache 后现象消失，排查方向转向缓存一致性。

关闭 Cache 可以作为诊断线索，但长期方案仍应明确下面的流程：

```text
选择 DMA 可达的独立缓冲区
    ↓
按实际 Cache Line 对齐地址和占用范围
    ↓
接收前完成平台要求的缓存维护并把所有权交给 DMA
    ↓
DMA 传输期间 CPU 不读写该缓冲区
    ↓
确认完成，按平台要求失效接收范围并同步
    ↓
把描述符交给处理任务，处理结束后归还
```

可以将 DMA 缓冲区放入独立段，并让段首、段尾对齐：

```ld
.dma_buffer (NOLOAD) :
{
    . = ALIGN(32);
    __dma_buffer_start__ = .;

    *(.dma_buffer)
    *(.dma_buffer*)

    . = ALIGN(32);
    __dma_buffer_end__ = .;
} > SRAM2
```

变量也显式指定段和对齐：

```c
static uint16_t adc_buffer[ADC_SAMPLE_COUNT]
    __attribute__((section(".dma_buffer"),
                   aligned(32)));
```

这里的 SRAM2、32 字节和 `ADC_SAMPLE_COUNT` 都必须按目标工程定义。`NOLOAD` 也意味着不能依赖该段从固件镜像加载初值；DMA 尚未写入的数据，不应当作有效样本读取。

独立段的意义是让缓存维护范围不误伤相邻状态变量，而不仅是“起点能被 32 整除”。最终还要从 Map 文件和实际地址确认布局，检查接收前后维护、DMA 完成条件和任务间交接是否一致。

### 8.4 接手已有项目，按什么顺序实施这十种方法？

不要一次修改分配器、任务栈和所有缓冲区。先建立可比较的基线，再根据证据逐项推进。

1. **盘点布局。** 阅读芯片内存映射、链接脚本和 Map 文件，列出 `.data`、`.bss`、堆、任务栈和大缓冲区，检查重复计数。
2. **确定负载。** 把正常运行、网络重连、TLS 握手、最大输入、日志突发和功能并发都纳入观察。
3. **增加指标。** 记录各域当前与峰值占用、最大连续块、任务栈水位、分配失败和重启原因。
4. **分类分配。** 长期关键对象静态创建，固定规格高频对象进入块池，可变尺寸需求评估受控堆或 TLSF。
5. **检查数据流。** 缩减不必要的副本，明确描述符、所有权和回收时机，同时核对 DMA 可达性与 Cache 维护。
6. **控制错误边界。** 梳理异常清理路径，结合静态分析、MPU 和适用的语言机制减少内存错误。
7. **比较工具链产物。** 对体积优化、LTO、段回收、RAM 热点和硬件加速分别测量，复核必要代码是否保留。
8. **用量产配置复验。** 检查最坏路径、耗尽后的降级、失败恢复和长期趋势，确认余量有依据。

回到最初那台网关，真正有用的结果是：任务知道自己能用多少栈，模块知道缓冲区归谁，分配失败有明确处理，现场故障有数据可查。十种方法最终都要落到这些可以检查、测量和验证的行为上。
