# 嵌入式系统内存优化指南

## 第一章、全文导读与目录

### 1.1、这份文档讲什么

嵌入式设备的内存永远是稀缺资源：Flash 决定了固件能装下多少功能，SRAM 决定了运行期能同时存活多少数据。内存优化不是某颗芯片的专属技巧，而是一套**与平台无关的思维方式**：

> 先搞清楚数据存在哪里 → 测出真实用量 → 用更省的表示方式 → 用更可控的分配方式 → 持续监控不让它劣化。

因此本文只讨论方法与取舍，不绑定具体芯片型号、开发板或 IDE。凡是必须用代码说明的地方，一律使用 C 语言与 ESP32 风格的伪代码示例；换成任何一款 MCU、SoC 或 RTOS，结论都同样成立。

### 1.2、内存优化的主线

全文按照读者建立能力的顺序推进，可以概括为五个阶段：

| 阶段 | 要回答的问题 | 对应章节 |
|---|---|---|
| 认知 | 数据到底存在哪里？哪些占 Flash，哪些占 RAM？ | 第二章 |
| 测量 | 现在用了多少？谁是大户？余量还有多少？ | 第三章 |

| 固化 | 编译期能省的、案例中验证过的、出问题怎么查、如何长期不劣化 | 第七章至第十章 |

## 第二章、内存架构与分区模型

优化的第一步不是改代码，而是先回答一个问题：**这份数据现在放在哪里，代价是多少？**

### 2.1、存储介质及其特点

| 介质 | 用途 | 特点 | 典型容量 |
|---|---|---|---|
| Flash | 程序代码、常量数据 | 非易失、读快写慢、擦写次数有限 | 数百 KB ~ 数 MB |
| SRAM | 变量、栈、堆 | 易失、读写快、单位成本高 | 数 KB ~ 数百 KB |
| PSRAM / SDRAM | 大缓冲、帧缓存 | 容量大、访问较慢、需控制器或刷新 | 数 MB 起 |
| EEPROM / NVS | 配置参数 | 非易失、容量小、写入慢 | 数 KB |
| SD 卡 / 外部存储 | 日志、资源文件 | 容量最大、速度最慢、需文件系统 | GB 级 |

一条通用的判断原则：**只读的放 Flash，热点小数据放片内 SRAM，大块冷数据放外部 RAM 或外部存储。**

以 ESP32 类 SoC 为例，地址空间大致是这样分工的（伪示意，不作为具体型号的精确映射）：

```text
外部 Flash（经 Cache 映射） : 指令段 IROM / 只读数据段 DROM
片内 IRAM                  : 需要常驻、不能走 Cache 的关键代码（如中断处理）
片内 DRAM                  : .data / .bss / 堆 / 各任务栈
外部 PSRAM（可选）          : 大缓冲区、图像/音频帧
RTC 慢速内存               : 深度睡眠期间需要保留的少量数据
```

关键结论：同一个变量放在不同区域，占用的资源种类完全不同——Flash 富裕而 RAM 紧张时，把数据从 RAM 挪到 Flash 就是最直接的优化。

### 2.2、程序的六个内存分区

**代码段（`.text`）**：存放在 Flash。

```c
void function(void) {
    // 函数代码
}

const char message[] = "Hello";  // 常量字符串
```

**只读数据段（`.rodata`）**：同样在 Flash。

```c
const int lookup_table[256] = { /* ... */ };  // 查找表
const char *strings[] = {"str1", "str2"};     // 字符串数组
```

**初始化数据段（`.data`）**：初值存 Flash，运行期副本占 RAM，启动时由 Flash 拷贝到 RAM——**占双份空间**。

```c
int global_var = 100;        // 初始化的全局变量
static int static_var = 50;  // 初始化的静态变量
```

**未初始化数据段（`.bss`）**：只占 RAM，启动时清零，不占 Flash。

```c
int uninitialized_var;              // 未初始化的全局变量
static char buffer[1024];           // 未初始化的静态数组
```

**堆（heap）**：运行期动态分配，占 RAM，存在碎片风险。

```c
void *ptr = malloc(100);  // 动态分配的内存
```

**栈（stack）**：函数局部变量与调用现场，占 RAM，深度不可控时会溢出。

```c
void function(void) {
    int local_var;           // 局部变量
    char buffer[256];        // 局部数组
}
```

### 2.3、从分区推导优化方向

把六个分区与两类资源对应起来，优化方向自然浮现：

| 资源 | 由哪些分区构成 | 主要优化手段 |
|---|---|---|
| Flash 占用 | `.text` + `.rodata` + `.data` 的初值 | 编译选项、去除死代码、数据压缩 |
| RAM 占用 | `.data` + `.bss` + 堆 + 栈 | 常量入 Flash、缩小数据表示、池化分配、控制栈深度 |

一个反复出现的技巧：给只读数据加上 `const`，它就从 `.data`（占 RAM + Flash）变成 `.rodata`（只占 Flash），这是零风险、零成本的净收益。

## 第三章、内存用量的测量与分析

**先测量，再优化**。没有数据支撑的优化，多半优化了不痛不痒的地方，却牺牲了可读性。

### 3.1、编译期分析：段大小

GNU 工具链的 `size` 可以给出各段大小（实际调用时加上各自工具链前缀，或使用构建系统封装的命令，例如 ESP-IDF 的 `idf.py size`）：

```bash
$ size firmware.elf
   text    data     bss     dec     hex filename
  45678    1234    5678   52590    cd6e firmware.elf
```

各列含义：

- `text`：代码与只读数据，占 Flash；
- `data`：已初始化数据，**同时占 Flash（存初值）和 RAM（存副本）**；
- `bss`：未初始化数据，只占 RAM；
- `dec` / `hex`：合计大小的十进制与十六进制表示。

据此换算实际占用：

```text
Flash 使用 = text + data
RAM  使用 = data + bss + heap + stack
```

注意 `size` 看不到堆和栈的运行期真实水位，它们必须靠 3.3、3.4 节的运行期手段测量。

### 3.2、编译期分析：符号与映射文件

定位"内存大户"靠符号表和链接映射文件：

```bash
# 查看各段的详细信息
$ objdump -h firmware.elf

# 按体积排序符号，找出最大的若干个
$ nm --size-sort -S firmware.elf | tail -20
```

生成并阅读映射文件：

```bash
$ gcc -Wl,-Map=output.map ...
$ cat output.map
```

映射文件的典型结构：

```text
Memory Configuration

Name             Origin             Length             Attributes
FLASH            0x08000000         0x00100000         xr
RAM              0x20000000         0x00020000         xrw

Linker script and memory map

.text           0x08000000    0x12345
 .text.main     0x08000000      0x100 main.o
 .text.func1    0x08000100      0x200 module1.o

.data           0x20000000     0x1000
 .data.var1     0x20000000        0x4 main.o

.bss            0x20001000     0x2000
 .bss.buffer    0x20001000      0x400 module2.o
```

批量提取大对象：

```bash
$ grep -E "^[[:space:]]+0x[0-9a-f]+[[:space:]]+0x[0-9a-f]+" output.map | \
  awk '{print $2, $1, $3}' | sort -rn | head -20
```

这一步的产出应当是一张"Top 20 大符号"清单——后续优化从清单顶部开始做，收益最高。

### 3.3、运行期分析：栈水位

栈的真实用量无法静态求出，通用做法是**填充特征字 + 统计未被覆盖的区域**。注意：以下实现**假设栈向上增长**（低地址→高地址），如 RISC-V 某些配置；ARM Cortex-M 等平台的栈向下增长，需反向遍历：

```c
#define STACK_FILL_PATTERN 0xA5A5A5A5

void stack_init(void) {
    extern uint32_t _stack_start;
    extern uint32_t _stack_end;

    uint32_t *p = &_stack_start;
    // 无论栈向上还是向下增长，初始化时都从低地址 _stack_start 填充到高地址 _stack_end
    // 只有检测时的扫描方向改变
    while (p < &_stack_end) {
        *p++ = STACK_FILL_PATTERN;
    }
}

uint32_t stack_get_usage(void) {
    extern uint32_t _stack_start;
    extern uint32_t _stack_end;

    uint32_t *p = &_stack_start;
    uint32_t unused = 0;

    // 栈向上增长：从低地址扫到高地址，统计未覆盖的特征字
    while (p < &_stack_end && *p == STACK_FILL_PATTERN) {
        unused += 4;
        p++;
    }

    uint32_t total = (uint32_t)&_stack_end - (uint32_t)&_stack_start;
    return total - unused;
}

// 若栈向下增长（如 ARM），改用以下逻辑：
// uint32_t stack_get_usage_descending(void) {
//     extern uint32_t _stack_start;
//     extern uint32_t _stack_end;
//
//     uint32_t *p = &_stack_end;
//     uint32_t unused = 0;
//
//     while (p > &_stack_start && *p == STACK_FILL_PATTERN) {
//         unused += 4;
//         p--;
//     }
//
//     uint32_t total = (uint32_t)&_stack_end - (uint32_t)&_stack_start;
//     return total - unused;
// }
```

在 RTOS 环境中，这套机制通常已由内核内建，直接查询即可（ESP32 上的 FreeRTOS 伪代码）：

```c
// 返回该任务栈的历史最小剩余量
UBaseType_t headroom = uxTaskGetStackHighWaterMark(task_handle);
if (headroom < STACK_SAFETY_MARGIN) {
    LOGW("task stack headroom too low: %u", (unsigned)headroom);
}
```

### 3.4、运行期分析：堆水位与趋势

堆要关注三个指标：已用量、空闲量、**最大连续空闲块**——第三个指标才是碎片程度的真实体现。

```c
typedef struct {
    uint32_t total_size;
    uint32_t used_size;
    uint32_t free_size;
    uint32_t largest_free_block;
    uint32_t allocation_count;
} HeapStats_t;

void heap_get_stats(HeapStats_t *stats) {
    // 遍历堆块链表，统计使用情况
    // 具体实现取决于所用的堆管理器
}
```

单点采样不足以发现泄漏，还需要按时间记录趋势：

```c
typedef struct {
    uint32_t timestamp;
    uint32_t stack_used;
    uint32_t heap_used;
    uint32_t heap_free;
} MemorySnapshot_t;

#define SNAPSHOT_COUNT 100
MemorySnapshot_t snapshots[SNAPSHOT_COUNT];
int snapshot_index = 0;

void memory_take_snapshot(void) {
    MemorySnapshot_t *snap = &snapshots[snapshot_index];

    snap->timestamp = get_tick_count();
    snap->stack_used = stack_get_usage();

    HeapStats_t heap_stats;
    heap_get_stats(&heap_stats);
    snap->heap_used = heap_stats.used_size;
    snap->heap_free = heap_stats.free_size;

    snapshot_index = (snapshot_index + 1) % SNAPSHOT_COUNT;
}

void memory_print_history(void) {
    printf("\n=== Memory Usage History ===\n");
    printf("Time(ms)  Stack(B)  Heap Used(B)  Heap Free(B)\n");

    for (int i = 0; i < SNAPSHOT_COUNT; i++) {
        MemorySnapshot_t *snap = &snapshots[i];
        if (snap->timestamp > 0) {
            printf("%8lu  %8lu  %12lu  %12lu\n",
                   snap->timestamp,
                   snap->stack_used,
                   snap->heap_used,
                   snap->heap_free);
        }
    }
}
```

**判读方法**：空闲量长期单调下降 → 疑似泄漏；空闲量平稳但最大连续块持续缩小 → 碎片化。两类问题的处理方式完全不同，详见第九章。

## 第四章、数据表示与结构优化

测量之后的第一类优化，是让同样的信息占更少的字节。这类优化改动局部、收益直接，通常应当最先做。

### 4.1、选择足够用的最小类型

**用够用的宽度，而不是顺手的宽度**：

```c
// 不好：使用过大的类型
typedef struct {
    uint32_t age;          // 0-120，用8位足够
    uint32_t month;        // 1-12，用8位足够
    uint32_t day;          // 1-31，用8位足够
    uint32_t hour;         // 0-23，用8位足够
} DateTime_Bad;  // 占用16字节

// 好：使用合适的类型
typedef struct {
    uint8_t age;
    uint8_t month;
    uint8_t day;
    uint8_t hour;
} DateTime_Good;  // 占用4字节，节省75%
```

**用位域压缩标志位**：

```c
// 不好：每个标志占用一个字节
typedef struct {
    uint8_t flag1;
    uint8_t flag2;
    uint8_t flag3;
    uint8_t status;  // 0-7
    uint8_t mode;    // 0-3
} Flags_Bad;  // 占用5字节

// 好：使用位域
typedef struct {
    uint8_t flag1 : 1;
    uint8_t flag2 : 1;
    uint8_t flag3 : 1;
    uint8_t status : 3;
    uint8_t mode : 2;
} Flags_Good;  // 占用1字节，节省80%

// 注意：位域访问比普通变量慢
// 适合空间敏感但访问不频繁的场景
```

**用枚举代替字符串表示状态**：

```c
// 不好：使用字符串
typedef struct {
    char state[20];  // "IDLE", "RUNNING", "STOPPED"
} StateMachine_Bad;  // 占用20字节

// 好：使用枚举
typedef enum {
    STATE_IDLE = 0,
    STATE_RUNNING,
    STATE_STOPPED
} State_t;

typedef struct {
    State_t state;  // 1-4字节（取决于编译器）
} StateMachine_Good;
```

### 4.2、对齐与打包

#### 4.2.1、理解对齐

编译器默认按自然对齐排布字段，字段之间会插入填充字节：

```c
typedef struct {
    uint8_t a;     // 1字节
    // 3字节填充
    uint32_t b;    // 4字节
    uint8_t c;     // 1字节
    // 3字节填充
} Aligned_t;  // 总共12字节

printf("sizeof(Aligned_t) = %zu\n", sizeof(Aligned_t));
printf("offsetof(a) = %zu\n", offsetof(Aligned_t, a));
printf("offsetof(b) = %zu\n", offsetof(Aligned_t, b));
printf("offsetof(c) = %zu\n", offsetof(Aligned_t, c));
```

对齐遵循三条规则：

```c
// 规则1：字段按其自身大小对齐
// - char: 1字节对齐
// - short: 2字节对齐
// - int: 4字节对齐
// - long long: 8字节对齐
// - 指针: 4字节（32位）或8字节（64位）对齐

// 规则2：结构体整体按其最大字段对齐
typedef struct {
    char a;
    int b;
} Struct1_t;  // 按4字节对齐

typedef struct {
    char a;
    long long b;
} Struct2_t;  // 按8字节对齐

// 规则3：数组元素按元素类型对齐
Struct1_t array[10];
```

#### 4.2.2、消除填充的两种办法

```c
// 方法1：重新排列字段（推荐，无副作用）
typedef struct {
    uint32_t b;    // 4字节
    uint8_t a;     // 1字节
    uint8_t c;     // 1字节
    // 2字节填充
} Optimized_t;  // 总共8字节，节省33%

// 方法2：使用 packed（牺牲访问速度）
typedef struct __attribute__((packed)) {
    uint8_t a;
    uint32_t b;    // 未对齐！
    uint8_t c;
} Packed_t;  // 总共6字节，节省50%
```

**选型原则**：内部数据结构优先用字段重排；`packed` 只用于必须与外部字节流严格一致的场合（通信协议帧、存储记录格式）。未对齐访问在部分架构上会显著变慢，甚至触发异常。

#### 4.2.3、查看结构体布局

```c
#define PRINT_STRUCT_LAYOUT(type, field) \
    printf("%-20s offset: %3zu, size: %3zu\n", \
           #field, offsetof(type, field), sizeof(((type*)0)->field))

void print_layout(void) {
    printf("Structure layout:\n");
    PRINT_STRUCT_LAYOUT(MyStruct, field1);
    PRINT_STRUCT_LAYOUT(MyStruct, field2);
    PRINT_STRUCT_LAYOUT(MyStruct, field3);
    printf("Total size: %zu\n", sizeof(MyStruct));
}
```

### 4.3、数据结构选型

**数组 vs 链表**：

```c
// 数组：连续内存，缓存友好
#define MAX_ITEMS 100
typedef struct {
    Item items[MAX_ITEMS];
    int count;
} ArrayList_t;  // 固定大小，可能浪费空间

// 链表：分散内存，灵活但每个节点多出一个指针
typedef struct Node {
    Item data;
    struct Node *next;  // 额外的4-8字节开销
} Node_t;
```

选择建议：

| 场景 | 推荐 |
|---|---|
| 元素数量固定或可预测 | 数组 |
| 需要频繁中间插入/删除 | 链表 |
| 内存紧张、元素体积小 | 数组（无指针开销、无分配头开销） |

**静态分配 vs 动态分配**：

```c
// 静态分配：编译期确定，无运行时开销，用量可被 size 工具看见
static char buffer[1024];

// 动态分配：运行期灵活，但有管理开销与碎片风险
char *buffer = malloc(1024);

// 混合方案：小对象走栈，大对象走堆
void process_data(size_t size) {
    if (size <= 256) {
        char buffer[256];
        // 处理数据
    } else {
        char *buffer = malloc(size);
        // 处理数据
        free(buffer);
    }
}
```

**位图 vs 布尔数组**：

```c
// 布尔数组：每个标志1字节
bool flags[100];  // 100字节

// 位图：每个标志1位
uint32_t bitmap[4];  // 16字节（128位），节省84%

#define SET_BIT(bitmap, n)    ((bitmap)[(n)/32] |= (1U << ((n)%32)))
#define CLEAR_BIT(bitmap, n)  ((bitmap)[(n)/32] &= ~(1U << ((n)%32)))
#define TEST_BIT(bitmap, n)   (((bitmap)[(n)/32] >> ((n)%32)) & 1U)

SET_BIT(bitmap, 50);
if (TEST_BIT(bitmap, 50)) {
    // 位50已设置
}
```

## 第五章、栈的优化与保护

栈的危险之处在于：它的峰值出现在最深的调用路径上，而那条路径可能极少被执行——问题往往在现场才暴露。

### 5.1、降低栈占用的三种手段

**避免大型局部数组**：

```c
// 不好：大数组在栈上
void process_data(void) {
    char buffer[4096];  // 4KB栈空间！
}

// 好：改为静态分配，落到 .bss
void process_data_static(void) {
    static char buffer[4096];  // 不占栈
}

// 或改为动态分配，落到堆
void process_data_dynamic(void) {
    char *buffer = malloc(4096);
    // 处理数据...
    free(buffer);
}
```

注意 `static` 方案会让该缓冲区常驻 RAM，且不可重入；多任务共享时需要加锁或改用堆。

**控制调用深度，递归改迭代**：

```c
// 不好：深度递归，栈深度随输入增长
int fibonacci_recursive(int n) {
    if (n <= 1) return n;
    return fibonacci_recursive(n-1) + fibonacci_recursive(n-2);
}

// 好：迭代实现，栈占用固定
int fibonacci_iterative(int n) {
    if (n <= 1) return n;

    int prev = 0, curr = 1;
    for (int i = 2; i <= n; i++) {
        int next = prev + curr;
        prev = curr;
        curr = next;
    }
    return curr;
}
```

**大结构体传指针而非传值**：

```c
typedef struct {
    char data[1024];
    int size;
} LargeStruct;

// 不好：复制1028字节到栈
void process(LargeStruct s) { }

// 好：只复制一个指针
void process_optimized(const LargeStruct *s) { }
```

### 5.2、栈大小的配置

裸机工程中，栈区通常由链接脚本划定：

```text
/* 在链接脚本中定义栈大小 */
STACK_SIZE = 0x1000;  /* 4KB */

SECTIONS
{
    .stack (NOLOAD) :
    {
        . = ALIGN(8);
        _stack_start = .;
        . = . + STACK_SIZE;
        . = ALIGN(8);
        _stack_end = .;
    } > RAM
}
```

启动代码在跳转到 `main` 之前把栈指针指向栈顶，随后完成运行时初始化。

RTOS 工程中，栈按任务粒度分配，配置点在创建任务时（ESP32 上的 FreeRTOS 伪代码）：

```c
#define SENSOR_TASK_STACK   4096   // 按实测水位 + 30% 余量确定
#define SENSOR_TASK_PRIO    5

xTaskCreate(sensor_task, "sensor", SENSOR_TASK_STACK,
            NULL, SENSOR_TASK_PRIO, &sensor_task_handle);
```

**定值方法**：先给一个偏大的值跑通，再用 3.3 节的水位测量取得峰值，最后按"峰值 + 20%~30% 余量"收敛。注意中断/异常处理若共用任务栈，余量还要再放宽。

### 5.3、栈溢出检测

```c
// 方法1：栈保护字（哨兵）
#define STACK_GUARD 0xDEADBEEF

void stack_init_guard(void) {
    extern uint32_t _stack_start;
    *(uint32_t*)&_stack_start = STACK_GUARD;
}

void stack_check_guard(void) {
    extern uint32_t _stack_start;
    if (*(uint32_t*)&_stack_start != STACK_GUARD) {
        error_handler("Stack overflow detected!");
    }
}

// 方法2：内存保护单元（MPU / PMP 等硬件机制）
void mpu_protect_stack(void) {
    // 将栈底部一小段配置为不可写区域
    // 一旦越界写入即触发异常，可立即定位到越界瞬间
}
```

两者的差别：哨兵字只能在检查点发现"已经溢出过"，硬件保护能在越界的**那一刻**中断，定位精度高得多。条件允许时优先用硬件机制，把哨兵作为兜底。

## 第六章、堆与内存池

堆的问题不只是"用了多少"，更是"还能不能分配出来"。碎片会让总空闲量充足的系统照样 `malloc` 失败，而这类失败往往在连续运行数天后才出现。

### 6.1、碎片是怎么产生的

```c
// 导致碎片的分配模式
void *p1 = malloc(100);  // [100]
void *p2 = malloc(200);  // [100][200]
void *p3 = malloc(100);  // [100][200][100]

free(p2);  // [100][空200][100]  <- 碎片

void *p4 = malloc(300);  // 分配失败！虽然总空闲空间足够
```

根因是**变长分配 + 乱序释放**。据此，下面三条解法都指向同一个方向：让分配变得规整、可预测。

### 6.2、解法一：定长内存池

**基础实现（标志位标记）**：

```c
#define POOL_BLOCK_SIZE 64
#define POOL_BLOCK_COUNT 20

typedef struct {
    uint8_t blocks[POOL_BLOCK_COUNT][POOL_BLOCK_SIZE];
    bool used[POOL_BLOCK_COUNT];
    int allocated_count;
} MemoryPool_t;

static MemoryPool_t pool;

void pool_init(void) {
    memset(&pool, 0, sizeof(pool));
}

void *pool_alloc(void) {
    for (int i = 0; i < POOL_BLOCK_COUNT; i++) {
        if (!pool.used[i]) {
            pool.used[i] = true;
            pool.allocated_count++;
            return pool.blocks[i];
        }
    }
    return NULL;  // 池已满
}

void pool_free(void *ptr) {
    if (ptr == NULL) return;

    ptrdiff_t offset = (uint8_t*)ptr - (uint8_t*)pool.blocks;
    int index = offset / POOL_BLOCK_SIZE;

    if (index >= 0 && index < POOL_BLOCK_COUNT) {
        pool.used[index] = false;
        pool.allocated_count--;
    }
}

int pool_get_free_count(void) {
    return POOL_BLOCK_COUNT - pool.allocated_count;
}
```

**优化实现（空闲链表，分配/释放均为 O(1)）**：

```c
typedef struct Block {
    union {
        struct Block *next;             // 空闲时指向下一个空闲块
        uint8_t data[POOL_BLOCK_SIZE];  // 使用时存储数据
    };
} Block_t;

typedef struct {
    Block_t blocks[POOL_BLOCK_COUNT];
    Block_t *free_list;
    int allocated_count;
} FastPool_t;

static FastPool_t fast_pool;

void fast_pool_init(void) {
    fast_pool.free_list = &fast_pool.blocks[0];

    for (int i = 0; i < POOL_BLOCK_COUNT - 1; i++) {
        fast_pool.blocks[i].next = &fast_pool.blocks[i + 1];
    }
    fast_pool.blocks[POOL_BLOCK_COUNT - 1].next = NULL;

    fast_pool.allocated_count = 0;
}

void *fast_pool_alloc(void) {
    if (fast_pool.free_list == NULL) {
        return NULL;  // 池已满
    }

    Block_t *block = fast_pool.free_list;
    fast_pool.free_list = block->next;
    fast_pool.allocated_count++;

    return block->data;
}

void fast_pool_free(void *ptr) {
    if (ptr == NULL) return;

    Block_t *block = (Block_t*)((uint8_t*)ptr - offsetof(Block_t, data));

    block->next = fast_pool.free_list;
    fast_pool.free_list = block;
    fast_pool.allocated_count--;
}
```

定长池的代价是内部碎片：申请 40 字节也会占满一个 64 字节块。块大小应按实际对象尺寸分布来定。

### 6.3、解法二：多级内存池

当对象尺寸分布跨度较大时，用几档定长池覆盖主流尺寸，超大块再回落到系统分配：

```c
#define SMALL_SIZE 32
#define MEDIUM_SIZE 128
#define LARGE_SIZE 512

typedef struct {
    MemoryPool_t small_pool;   // 32字节块
    MemoryPool_t medium_pool;  // 128字节块
    MemoryPool_t large_pool;   // 512字节块
} MultiLevelPool_t;

static MultiLevelPool_t ml_pool;

void ml_pool_init(void) {
    pool_init_with_size(&ml_pool.small_pool, SMALL_SIZE, 50);
    pool_init_with_size(&ml_pool.medium_pool, MEDIUM_SIZE, 20);
    pool_init_with_size(&ml_pool.large_pool, LARGE_SIZE, 10);
}

void *ml_pool_alloc(size_t size) {
    if (size <= SMALL_SIZE) {
        return pool_alloc(&ml_pool.small_pool);
    } else if (size <= MEDIUM_SIZE) {
        return pool_alloc(&ml_pool.medium_pool);
    } else if (size <= LARGE_SIZE) {
        return pool_alloc(&ml_pool.large_pool);
    } else {
        return malloc(size);  // 超大块交给系统分配
    }
}

void ml_pool_free(void *ptr, size_t size) {
    if (ptr == NULL) return;

    if (size <= SMALL_SIZE) {
        pool_free(&ml_pool.small_pool, ptr);
    } else if (size <= MEDIUM_SIZE) {
        pool_free(&ml_pool.medium_pool, ptr);
    } else if (size <= LARGE_SIZE) {
        pool_free(&ml_pool.large_pool, ptr);
    } else {
        free(ptr);
    }
}
```

各档的块数量应由实测峰值并发量决定，而不是拍脑袋。

### 6.4、解法三：合并分配与 bump 分配器

**合并分配**：把一个对象的多次小分配合成一次。

```c
// 不好：4次分配，产生碎片，且每次都有分配头开销
typedef struct {
    char *name;
    char *description;
    int *data;
} Object_Bad;

Object_Bad *create_object_bad(void) {
    Object_Bad *obj = malloc(sizeof(Object_Bad));
    obj->name = malloc(32);
    obj->description = malloc(128);
    obj->data = malloc(100 * sizeof(int));
    return obj;
}

// 好：1次分配，无碎片
typedef struct {
    char name[32];
    char description[128];
    int data[100];
} Object_Good;

Object_Good *create_object_good(void) {
    return malloc(sizeof(Object_Good));
}
```

**bump 分配器**：只增长、不单独释放，整批重置。适用于"一帧/一次事务内临时分配、结束时全部作废"的场景。

```c
typedef struct {
    uint8_t *buffer;
    size_t size;
    size_t offset;
} BumpAllocator_t;

void bump_init(BumpAllocator_t *alloc, void *buffer, size_t size) {
    alloc->buffer = buffer;
    alloc->size = size;
    alloc->offset = 0;
}

void *bump_alloc(BumpAllocator_t *alloc, size_t size) {
    size = (size + 3) & ~3;  // 对齐到4字节

    if (alloc->offset + size > alloc->size) {
        return NULL;  // 空间不足
    }

    void *ptr = alloc->buffer + alloc->offset;
    alloc->offset += size;
    return ptr;
}

void bump_reset(BumpAllocator_t *alloc) {
    alloc->offset = 0;  // 重置，此前所有分配一并失效
}

// 典型用法：帧内临时分配，帧末统一回收
void process_frame(void) {
    static uint8_t frame_buffer[4096];
    BumpAllocator_t alloc;
    bump_init(&alloc, frame_buffer, sizeof(frame_buffer));

    void *temp1 = bump_alloc(&alloc, 100);
    void *temp2 = bump_alloc(&alloc, 200);

    // 处理...

    bump_reset(&alloc);
}
```

### 6.5、堆大小的规划

裸机工程中堆区同样由链接脚本划定：

```text
/* 定义堆大小 */
HEAP_SIZE = 0x4000;  /* 16KB */

SECTIONS
{
    .heap (NOLOAD) :
    {
        . = ALIGN(8);
        _heap_start = .;
        . = . + HEAP_SIZE;
        . = ALIGN(8);
        _heap_end = .;
    } > RAM
}
```

更常见的做法是把 `.bss` 之后到栈之前的全部剩余 RAM 都交给堆：

```c
extern uint32_t _heap_start;
extern uint32_t _stack_start;

void heap_init(void) {
    size_t heap_size = (uint32_t)&_stack_start - (uint32_t)&_heap_start;
    heap_manager_init(&_heap_start, heap_size);
}
```

若采用保护区域方案，则需显式预留空间：

```c
extern uint32_t _heap_start;
extern uint32_t _guard_start;    /* 保护区域起始 */

void heap_init(void) {
    /* 堆大小从 _heap_start 到 _guard_start（不包括保护区域） */
    size_t heap_size = (uint32_t)&_guard_start - (uint32_t)&_heap_start;
    heap_manager_init(&_heap_start, heap_size);
}
```

**注意**：堆和栈的边界必须在链接脚本中显式划分。堆向上增长（低地址→高地址），栈向下增长（高地址→低地址），若无保护区域，长期运行中两者可能相交导致崩溃。推荐给栈预留 20%~30% 的保护空间：

```text
HEAP_SIZE = 0x2000;   /* 8KB */
STACK_SIZE = 0x2000;  /* 8KB */
STACK_GUARD = 0x400;  /* 1KB 保护区域 */

SECTIONS {
    .heap (NOLOAD) : {
        _heap_start = .;
        . = . + HEAP_SIZE;
    } > RAM
    
    .guard (NOLOAD) : {
        _guard_start = .;
        . = . + STACK_GUARD;
    } > RAM
    
    .stack (NOLOAD) : {
        _stack_start = .;
        . = . + STACK_SIZE;
        _stack_end = .;
    } > RAM
}
```

带多种 RAM 的 SoC 上，堆还可以按能力分区管理，把大缓冲导向外部 RAM，把对速度敏感的小对象留在片内（ESP32 伪代码）：

```c
// 大缓冲优先走外部 PSRAM，失败再回落到片内 DRAM
void *buf = heap_alloc_caps(size, CAPS_SPIRAM);
if (buf == NULL) {
    buf = heap_alloc_caps(size, CAPS_INTERNAL);
}
```

## 第七章、常量数据与编译期优化

前几章优化的是"数据怎么存"，本章优化的是"编译器能替你省掉多少"。这类手段改动量最小，通常应当在项目早期就固化进构建配置。

### 7.1、用 const 把数据搬进 Flash

```c
// 不好：查找表在RAM中
uint8_t sin_table[256] = {
    0, 3, 6, 9, /* ... */
};  // 占用256字节RAM

// 好：查找表在Flash中
const uint8_t sin_table[256] = {
    0, 3, 6, 9, /* ... */
};  // 占用256字节Flash，0字节RAM
```

字符串数组要注意"指针本身"也需要 `const`，否则指针数组仍留在 RAM：

```c
// 不好：字符串内容在Flash，但指针数组在RAM
char *messages[] = {
    "Error",
    "Warning",
    "Info"
};

// 好：内容和指针都在Flash
const char *const messages[] = {
    "Error",
    "Warning",
    "Info"
};
```

### 7.2、常量数据的压缩

**位打包**：按实际精度需求压缩字段宽度。

```c
// 不好：每个分量占用完整字节
typedef struct {
    uint8_t red;    // 0-255
    uint8_t green;  // 0-255
    uint8_t blue;   // 0-255
} Color24_t;  // 3字节

// 好：RGB565格式
typedef struct {
    uint16_t value;  // R:5位, G:6位, B:5位
} Color16_t;  // 2字节，节省33%

uint8_t color16_get_red(Color16_t c)   { return (c.value >> 11) & 0x1F; }
uint8_t color16_get_green(Color16_t c) { return (c.value >> 5)  & 0x3F; }
uint8_t color16_get_blue(Color16_t c)  { return  c.value        & 0x1F; }
```

**稀疏表 + 插值**：用计算换空间，适合平滑变化的查找表。

```c
// 不好：完整的查找表
const uint16_t full_table[1000] = { /* ... */ };  // 2000字节

// 好：稀疏表 + 线性插值
const uint16_t sparse_table[100] = { /* 每10个值取一个 */ };  // 200字节

uint16_t lookup_interpolated(int index) {
    int base_index = index / 10;
    int offset = index % 10;

    uint16_t v1 = sparse_table[base_index];
    uint16_t v2 = sparse_table[base_index + 1];

    return v1 + (v2 - v1) * offset / 10;
}
```

**字符串去重**：提取公共前缀，或干脆只传错误码。

```c
// 优化前：重复的 "Error: " 前缀
const char *errors[] = {
    "Error: File not found",
    "Error: Permission denied",
    "Error: Out of memory"
};

// 优化后：前缀只存一份
const char error_prefix[] = "Error: ";
const char *error_messages[] = {
    "File not found",
    "Permission denied",
    "Out of memory"
};

void print_error(int code) {
    printf("%s%s\n", error_prefix, error_messages[code]);
}

// 更彻底：只保留错误码，文本交给上位机解析
typedef enum {
    ERR_FILE_NOT_FOUND,
    ERR_PERMISSION_DENIED,
    ERR_OUT_OF_MEMORY
} ErrorCode_t;

void print_error_formatted(ErrorCode_t code) {
    printf("Error %d occurred\n", code);
}
```

### 7.3、编译与链接选项

```bash
# -Os: 以代码体积为目标优化
gcc -Os -o firmware.elf main.c

# -flto: 链接期优化，跨文件内联与消除
gcc -Os -flto -o firmware.elf main.c

# 按函数/数据分段 + 回收未引用段，删除死代码与死数据
gcc -ffunction-sections -fdata-sections \
    -Wl,--gc-sections -o firmware.elf main.c
```

选型不要凭感觉，直接横向对比后用数据决定：

```bash
gcc -O0 -o firmware_O0.elf main.c && size firmware_O0.elf   # 无优化
gcc -Os -o firmware_Os.elf main.c && size firmware_Os.elf   # 空间优先
gcc -O2 -o firmware_O2.elf main.c && size firmware_O2.elf   # 速度优先
```

`--gc-sections` 往往是收益最大且几乎无风险的一项；`-flto` 收益次之，但可能放大未定义行为，启用后需要完整回归测试。

### 7.4、常用编译器属性

```c
// section：把代码或数据放进指定段，便于分配到特定内存区域
__attribute__((section(".fast_code")))
void critical_function(void) {
    // 例如放入片内 RAM，避免走 Flash Cache
}

__attribute__((section(".slow_data")))
const uint8_t large_table[10000] = { /* ... */ };

// unused：标记有意保留但未使用的符号，抑制警告
__attribute__((unused))
static int debug_counter = 0;

// packed：紧凑排布，消除填充
typedef struct __attribute__((packed)) {
    uint8_t a;
    uint32_t b;
    uint8_t c;
} PackedStruct_t;  // 6字节而不是12字节

// aligned：指定对齐，满足 DMA 等硬件要求
__attribute__((aligned(32)))
uint8_t dma_buffer[1024];
```

## 第八章、工程案例：三类结构的瘦身

前面的技巧单独看都不复杂，真实收益来自组合使用。以下三个案例都来自常见的嵌入式数据结构。

### 8.1、案例一：传感器数据缓冲

问题：浮点字段 + 大容量环形缓冲，是 RAM 消耗的典型大户。

```c
// 优化前
typedef struct {
    uint32_t timestamp;
    float temperature;
    float humidity;
    float pressure;
} SensorData_t;  // 16字节

#define BUFFER_SIZE 1000
SensorData_t sensor_buffer[BUFFER_SIZE];  // 16KB
```

优化手段：**浮点改定点**，按传感器实际精度选择整数宽度。

```c
// 优化后
typedef struct {
    uint32_t timestamp;
    int16_t temperature;  // 0.01°C精度
    uint16_t humidity;    // 0.01%精度
    uint16_t pressure;    // 0.1Pa精度
} SensorDataOptimized_t;  // 10字节，节省37.5%

#define BUFFER_SIZE 1000
SensorDataOptimized_t sensor_buffer[BUFFER_SIZE];  // 10KB

// 仅在对外呈现时还原为物理量
float get_temperature(const SensorDataOptimized_t *data) {
    return data->temperature / 100.0f;
}
```

附带收益：无硬件浮点单元的平台上，定点运算同时省下了软浮点库的代码空间。

### 8.2、案例二：状态机

问题：用字符串表示状态，既费空间又费比较时间。

```c
// 优化前
typedef struct {
    char current_state[20];
    char previous_state[20];
    uint32_t state_duration;
    uint32_t transition_count;
} StateMachine_t;  // 48字节
```

优化手段：**字符串改枚举 + 位域 + 收窄计数器宽度**。

```c
// 优化后
typedef enum {
    STATE_IDLE = 0,
    STATE_RUNNING,
    STATE_PAUSED,
    STATE_STOPPED
} State_t;

typedef struct {
    State_t current_state : 4;
    State_t previous_state : 4;
    uint32_t state_duration;
    uint16_t transition_count;
    uint16_t reserved;
} StateMachineOptimized_t;  // 8字节，节省83%
```

### 8.3、案例三：日志系统

问题：为每条日志预留定长大字符串，绝大部分空间被空字节占据。

```c
// 优化前
typedef struct {
    char message[128];
    uint32_t timestamp;
    uint8_t level;
} LogEntry_t;  // 133字节

#define LOG_SIZE 100
LogEntry_t log_buffer[LOG_SIZE];  // 13.3KB
```

优化手段：**定长记录 + 变长字符串池**，记录里只存偏移与长度。

```c
// 优化后：环形缓冲区 + 字符串池
#define LOG_SIZE 100
#define STRING_POOL_SIZE 4096

typedef struct {
    uint16_t message_offset;  // 在字符串池中的偏移
    uint16_t message_length;
    uint32_t timestamp;
    uint8_t level;
    uint8_t pool_generation;  // 标记该条日志对应的字符串池回绕代
} LogEntryOptimized_t;  // 11字节

LogEntryOptimized_t log_entries[LOG_SIZE];  // 1.1KB
char string_pool[STRING_POOL_SIZE];         // 4KB
uint16_t pool_offset = 0;
uint8_t pool_generation = 0;

void log_message(uint8_t level, const char *message) {
    uint16_t len = strlen(message) + 1;

    if (pool_offset + len > STRING_POOL_SIZE) {
        pool_offset = 0;
        pool_generation++;  // 每次回绕，递增代计数器
    }

    LogEntryOptimized_t *entry = &log_entries[log_index];
    entry->message_offset = pool_offset;
    entry->message_length = len;
    entry->timestamp = get_tick_count();
    entry->level = level;
    entry->pool_generation = pool_generation;  // 记录当前代

    memcpy(&string_pool[pool_offset], message, len);
    pool_offset += len;

    log_index = (log_index + 1) % LOG_SIZE;
}

// 读取时校验该条记录内容是否仍有效
const char *log_get_message(int index) {
    LogEntryOptimized_t *entry = &log_entries[index];
    
    // 若 generation 不匹配当前值，说明该字符串已被覆盖
    if (entry->pool_generation != pool_generation) {
        return NULL;  // 数据无效
    }
    
    return &string_pool[entry->message_offset];
}
```

总用量从 13.3KB 降到约 5.2KB（log_entries 1.1KB + string_pool 4KB）。通过 `pool_generation` 计数器，读取时可以判断字符串内容是否仍然有效，防止读取已被覆盖的数据。

## 第九章、常见故障与排查

本章集中处理内存相关的四类典型故障。排查顺序统一遵循：**先定位是哪块资源不够 → 再定位是谁占用 → 最后才动手改。**

### 9.1、链接期 RAM/Flash 溢出

**现象**：

```text
region `RAM' overflowed by 2048 bytes
```

**诊断**：先看分段用量，再按符号体积排序。

```bash
# 查看各段大小
size -A firmware.elf

# 找出最大的若干符号
nm --size-sort -S firmware.elf | tail -20
```

**处理**：

```c
// 1. 定位并优化大数组（可先用文本搜索找出可疑声明，
//    例如搜索方括号内为四位及以上数字的数组定义）

// 2. 只读的大数据加 const，从 RAM 移到 Flash
const uint8_t lookup[4096] = { /* ... */ };

// 3. 超大数据外置，放到外部存储或外部 RAM
__attribute__((section(".external_data")))
const uint8_t large_data[100000] = { /* ... */ };
```

### 9.2、栈溢出

**现象**：程序随机崩溃、变量值被莫名改写、触发硬件异常。三者叠加出现时基本可以确定是栈越界。

**诊断**：

```c
void check_stack_usage(void) {
    uint32_t used = stack_get_usage();
    uint32_t total = STACK_SIZE;

    printf("Stack usage: %lu / %lu bytes (%.1f%%)\n",
           used, total, (float)used * 100 / total);

    if (used > total * 0.9) {
        printf("WARNING: Stack usage > 90%%!\n");
    }
}
```

条件允许时，用硬件内存保护在越界瞬间触发异常，可直接定位到肇事函数（见 5.3 节）。

**处理**：

```c
// 1. 扩大栈：裸机改链接脚本，RTOS 改任务创建参数
//    STACK_SIZE = 0x2000;  /* 4KB -> 8KB */

// 2. 把大局部变量移出栈
void function_optimized(void) {
    static char buffer[1024];  // 或改用堆分配
}

// 3. 递归改迭代，消除不可控深度
```

### 9.3、堆碎片导致分配失败

**现象**：`malloc` 返回 `NULL`，但统计出来的总空闲内存明显够用。

**诊断**：关键看**最大连续空闲块**与总空闲量的比值。

```c
void diagnose_heap_fragmentation(void) {
    HeapStats_t stats;
    heap_get_stats(&stats);

    printf("Total free: %lu bytes\n", stats.free_size);
    printf("Largest block: %lu bytes\n", stats.largest_free_block);

    if (stats.largest_free_block < stats.free_size / 2) {
        printf("WARNING: Heap is fragmented!\n");
    }
}
```

**处理**：三条路径都在第六章展开过，此处只列决策顺序。

| 优先级 | 手段 | 适用场景 |
|---|---|---|
| 1 | 改用定长内存池 | 对象尺寸集中、生命周期交错 |
| 2 | 合并为单次分配 | 一个逻辑对象被拆成多次小分配 |
| 3 | 初始化阶段预分配 | 用量可预估、运行期不再增长 |

```c
// 路径3示例：启动时一次性分配，运行期不再申请
void init(void) {
    global_buffer = malloc(BUFFER_SIZE);
}
```

### 9.4、对齐问题导致性能下降

**现象**：功能正常但运行明显偏慢，且慢在特定的数据访问路径上——常见于滥用 `packed` 之后。

**诊断**：

```c
void check_alignment(void) {
    printf("MyStruct alignment: %zu\n", _Alignof(MyStruct));
    printf("MyStruct size: %zu\n", sizeof(MyStruct));

    MyStruct s;
    printf("Address: %p\n", (void*)&s);
    printf("Aligned: %s\n",
           ((uintptr_t)&s % _Alignof(MyStruct) == 0) ? "Yes" : "No");
}
```

**处理**：

```c
// 1. 用字段重排代替 packed，做到零填充且保持对齐
typedef struct {
    uint32_t a;
    uint32_t b;
    uint16_t c;
    uint16_t d;
    uint8_t e;
    uint8_t f;
    uint16_t g;
} Aligned_t;  // 16字节，无填充

// 2. 对硬件有对齐要求的缓冲区显式指定对齐
__attribute__((aligned(32)))
uint8_t dma_buffer[1024];

// 3. 需要手工对齐时，多申请一段再向上取整
void *alloc_aligned(size_t size, size_t alignment) {
    void *ptr = malloc(size + alignment - 1);
    uintptr_t addr = (uintptr_t)ptr;
    uintptr_t aligned = (addr + alignment - 1) & ~(alignment - 1);
    return (void*)aligned;
}
```

## 第十章、最佳实践与要点速查

内存优化不是一次性活动，而是贯穿项目四个阶段的持续动作。

### 10.1、设计阶段

**评估内存需求**：

- 按最坏情况估算用量，而不是典型情况；
- 预留 20%~30% 的安全余量；
- 分别评估峰值与均值——峰值决定会不会崩，均值决定能不能长跑。

**选择合适的数据结构**：优先静态分配，避免无谓的指针开销，标志位用位域、状态用枚举。

**规划内存布局**：常量与变量分离，栈与堆边界明确，为 DMA、Cache 等硬件约束预留对齐的缓冲区。

### 10.2、实现阶段

```c
// 只读数据一律加 const，让它落在 Flash
const uint8_t table[] = { /* ... */ };

// 模块内部数据用 static，缩小作用域也便于统计
static char buffer[256];

// 用够用的最小类型
uint8_t count;  // 而不是 int
```

配套的三项习惯：结构体字段按大小降序排列、频繁分配释放的同尺寸对象走内存池、每次引入大数组时同步更新内存预算表。

### 10.3、测试阶段

**内存用量与泄漏测试**：

```c
void test_memory_usage(void) {
    uint32_t initial_free = get_free_heap();

    run_test();

    uint32_t final_free = get_free_heap();
    assert(final_free == initial_free);  // 有进有出，用量应当归零
}
```

**压力测试**：

```c
void stress_test(void) {
    for (int i = 0; i < 10000; i++) {
        // 重复执行分配/释放路径
        // 每轮检查用量与最大连续块，观察是否单调劣化
    }
}
```

**长时间运行测试**：连续运行 24 小时以上，记录内存趋势曲线，重点看空闲量是否单调下降（泄漏）、最大连续块是否持续缩小（碎片）。

### 10.4、维护阶段

```c
void periodic_check(void) {
    // 周期性自检，异常时上报而不是等待崩溃
    check_stack_usage();
    check_heap_usage();
    check_fragmentation();
}
```

配套动作：每次发版记录固件体积并与上一版对比，代码评审时把"大数组、动态分配、对齐假设"列为固定检查项。

```bash
size firmware.elf > size_v2.txt
diff size_v1.txt size_v2.txt
```

### 10.5、要点速查

**八条核心结论**：

| 序号 | 要点 | 一句话说明 |
|---|---|---|
| 1 | 理解内存架构 | 先知道数据存在哪里，才谈得上省 |
| 2 | 测量优先 | 用 size、map、水位统计拿到真实数据 |
| 3 | 选对数据结构 | 空间与时间的权衡要显式做出 |
| 4 | 重视对齐 | 既影响空间，也影响性能与正确性 |
| 5 | 善用内存池 | 定长分配从根上消除碎片 |
| 6 | 规划栈与堆 | 按实测峰值加余量定值，并加检测 |
| 7 | 借力编译器 | `-Os`、`--gc-sections`、`const` 是低成本高收益项 |
| 8 | 持续监控 | 内存问题靠趋势发现，而非靠崩溃发现 |

**五条优化原则**：

1. 先测量，再优化；
2. 优先优化最大的那几个对象；
3. 保持代码可读性，不为几十字节牺牲可维护性；
4. 把维护成本计入收益评估；
5. 在空间与时间之间自觉取舍，并在注释中写明取舍理由。

**三条实践建议**：项目立项起就建立内存预算表；每个版本记录基准数据；把内存审查纳入常规代码评审，而不是等到 RAM 溢出才补救。
