# 嵌入式内存泄漏基础知识总结

> 目标：用于定位嵌入式 C/C++ 中的堆内存泄漏。重点记住：泄漏是什么、怎样与碎片化和栈溢出区分、PC 端如何提前发现、RTOS/裸机如何监控和定位。
>
> 来源：围绕 C/C++、FreeRTOS 和常用内存检查工具整理，仅供参考；具体 API 以所用 RTOS、C 库和 SDK 文档为准。

## 1. 先用一句话理解内存泄漏

**内存泄漏是已申请的动态内存在不再需要后没有被释放，导致可用堆内存持续减少。**

```text
malloc / new
    -> 使用
    -> 正常路径或错误路径遗漏 free / delete
    -> 可用堆持续减少
    -> 分配失败、功能异常或重启
```

严格来说，指针完全丢失的块是“确定泄漏”；即使仍有指针指向它，只要程序已不再需要且长期不释放，也属于需要修复的资源泄漏。

常见根因：

- `malloc/new` 后遗漏 `free/delete`。
- 错误分支提前返回，跳过清理。
- 指针被覆盖，原地址丢失。
- 循环、定时器或重连路径持续分配。
- 跨模块、跨任务传递指针，所有权不明确。
- `realloc` 直接赋回原指针，失败时丢失旧地址。

安全写法：

```c
void *new_ptr = realloc(ptr, new_size);
if (new_ptr == NULL) {
    /* ptr 仍有效，按原有策略处理。 */
    return -1;
}
ptr = new_ptr;
```

## 2. 先区分三个常见问题

| 问题 | 本质 | 典型现象 | 主要手段 |
| --- | --- | --- | --- |
| 内存泄漏 | 分配后未归还 | 空闲堆长期下降 | 分配记录、ASan/LSan、趋势监控 |
| 内存碎片 | 空闲块总量够，但大块不连续 | 总空闲不少却申请大块失败 | 最大连续块、内存池、减少变长分配 |
| 栈溢出 | 任务/中断栈空间不足 | HardFault、数据被踩、随机崩溃 | 栈水位、栈溢出 Hook |

> `free heap` 下降不一定就是泄漏：可能是正常缓存、一次性初始化或碎片化。要看“业务稳定后是否仍单调下降”，并结合分配记录确认。

## 3. 推荐的排查顺序

1. **PC 端先复现。** 对单元测试、协议解析和业务逻辑启用 ASan/LSan；必要时用 Valgrind 复核。
2. **确认趋势。** 记录可用堆、最小历史可用堆、最大连续空闲块和分配次数。
3. **锁定模块。** 为分配接口加文件、行号、大小、任务名和时间戳记录。
4. **检查所有权。** 每个 buffer 明确“谁创建、谁释放、何时转移所有权”。
5. **检查错误路径。** 尤其是超时、取消、重连、队列满、初始化失败和异常退出路径。
6. **同时看栈。** 内存踩踏和栈溢出会破坏堆管理信息，表面上像泄漏或 `free` 崩溃。

## 4. PC / Linux：优先使用自动化工具

### 4.1 AddressSanitizer 与 LeakSanitizer

对可以在 PC 或资源足够的 Linux 环境运行的代码，优先使用编译器 Sanitizer：

```bash
gcc -g -O1 -fno-omit-frame-pointer -fsanitize=address,undefined app.c -o app
./app

# 单独关注泄漏时（工具链支持时）
gcc -g -O1 -fsanitize=leak app.c -o app
./app
```

ASan 擅长发现越界、use-after-free、double-free 等；LSan 用于泄漏检查。是否默认启用泄漏报告、运行时内存开销和目标架构支持取决于编译器与运行库，因此以实际工具链输出为准。

### 4.2 Valgrind Memcheck

Valgrind 适合 PC Linux 的测试和复现环境，信息全面但速度很慢：

```bash
valgrind --leak-check=full --show-leak-kinds=all ./app
```

重点看：

| 报告 | 含义 |
| --- | --- |
| `definitely lost` | 无法再找到该分配块，确定泄漏 |
| `indirectly lost` | 被确定泄漏块引用的内存，通常随根块一起修复 |
| `possibly lost` | 存在不确定引用，需结合代码确认 |
| `still reachable` | 退出时仍可达；不一定是 bug，但应确认是否为预期的全局/缓存对象 |

> Valgrind 一般不适合裸机、RTOS 或强实时目标板。它更适合把业务代码移到 PC 端做自动化测试。

### 4.3 静态分析

静态分析无法替代运行时检测，但能提前发现明显路径问题：

```bash
cppcheck --enable=warning,style,performance ./src
gcc -fanalyzer -c app.c
```

对 CI 的价值通常很高：每次提交就检查未释放、空指针、重复释放等可静态推断的问题。

## 5. RTOS / 裸机：重点做监控和分配追踪

### 5.1 堆统计看趋势

以 FreeRTOS 为例，可使用所选 heap 实现支持的统计接口，例如：

```c
HeapStats_t stats;
vPortGetHeapStats(&stats);

printf("free=%u, largest=%u, min_ever=%u, alloc=%u, free=%u\n",
       (unsigned)stats.xAvailableHeapSpaceInBytes,
       (unsigned)stats.xSizeOfLargestFreeBlockInBytes,
       (unsigned)stats.xMinimumEverFreeBytesRemaining,
       (unsigned)stats.xNumberOfSuccessfulAllocations,
       (unsigned)stats.xNumberOfSuccessfulFrees);
```

重点观察：

- `available`：当前可用堆是否在稳定业务期持续下降。
- `largest free block`：最大连续块是否持续变小，判断碎片风险。
- `min ever free`：历史最低余量，用于容量评估，不代表当前泄漏。
- `alloc/free`：只能辅助判断；库的内部缓存、一次性分配和不同分配器行为都可能影响解释。

### 5.2 分配包装：记录，而不是替换一切

调试版本可为项目自己的分配入口增加记录：

```c
void *mem_alloc_dbg(size_t size, const char *file, int line);
void  mem_free_dbg(void *ptr, const char *file, int line);

#define MEM_ALLOC(size) mem_alloc_dbg((size), __FILE__, __LINE__)
#define MEM_FREE(ptr)   mem_free_dbg((ptr), __FILE__, __LINE__)
```

每条记录至少包含：地址、大小、文件行号、任务名/线程 ID 和时间戳。测试结束或堆持续下降时输出仍未释放的记录。

注意：

- 包装器内部必须调用**真实分配器**，不能被宏再次替换而递归调用。
- 记录表和分配器访问需要按任务/中断上下文做并发保护。
- 若加入前后哨兵检测越界，要保证返回地址满足原始分配器要求的对齐；不要用固定 4 字节头破坏 8/16 字节对齐。
- 调试记录本身占内存，只应在调试版本或受控容量下启用。

### 5.3 栈监控不能省略

栈溢出不是泄漏，但常伪装成堆问题。FreeRTOS 可通过栈水位和栈溢出 Hook 监控：

```c
UBaseType_t words = uxTaskGetStackHighWaterMark(task_handle);
printf("minimum free stack: %u words\n", (unsigned)words);
```

启用 `configCHECK_FOR_STACK_OVERFLOW`，并实现 `vApplicationStackOverflowHook()`。对大局部数组、递归、深层调用、格式化日志和中断嵌套重点评估栈空间。

## 6. 预防：明确所有权，减少动态分配

### 6.1 C 的集中清理模式

```c
int send_packet(void)
{
    int ret = -1;
    uint8_t *header = NULL;
    uint8_t *payload = NULL;

    header = malloc(16);
    if (header == NULL) {
        goto out;
    }

    payload = malloc(256);
    if (payload == NULL) {
        goto out;
    }

    ret = 0;
out:
    free(payload);
    free(header);
    return ret;
}
```

该模式的要点是：指针初始化为 `NULL`，所有出口统一释放；`free(NULL)` 是安全的。

### 6.2 C++ 使用 RAII

```cpp
auto buf = std::make_unique<uint8_t[]>(1024);
/* 离开作用域自动释放。 */
```

RAII / `std::unique_ptr` 能显著减少错误路径遗漏释放的问题。嵌入式是否使用异常、STL 和动态内存，仍要按项目资源和编码规范决定。

### 6.3 内存池的正确定位

固定块内存池可以减少碎片、限制最大内存使用并让 buffer 所有权更清晰；但如果申请后不归还，依然会耗尽。因此它是降低风险的设计手段，不是“自动杜绝泄漏”的机制。

适用场景：固定大小消息、网络包、音频块、传感器帧等高频短生命周期对象。

## 7. 高频易错点

| 错误说法 | 更准确的说法 |
| --- | --- |
| 指针还在就不算泄漏 | 不再需要却长期不释放就是资源泄漏；指针丢失只是最典型的确定泄漏 |
| 空闲堆减少一定是泄漏 | 可能是缓存、一次性初始化或碎片化，要看趋势和分配记录 |
| `free(p); p = NULL;` 能避免所有问题 | 只影响当前指针变量，其他别名仍可能悬空 |
| 内存池不会泄漏 | 忘记归还仍会耗尽，只是没有传统堆碎片 |
| 只监控总空闲堆即可 | 还要看最大连续空闲块、最小余量、栈水位和分配来源 |
| 直接 `p = realloc(p, n)` 没问题 | 失败时会丢失旧指针，应该用临时指针 |
| 宏替换 `malloc/free` 很简单 | 包装器递归、对齐、并发和第三方库分配都要处理 |

## 8. 面试回答

> 我会先在 PC 端用 ASan/LSan 和静态分析跑核心测试，尽量在目标板前发现泄漏和越界。RTOS 或裸机上，我会定期监控当前可用堆、最大连续空闲块、历史最低余量和任务栈水位；若堆在业务稳定后仍下降，就对项目的分配接口记录地址、大小、文件行号和任务名，输出未释放记录定位模块。修复时重点检查错误返回、超时取消、跨任务 buffer 所有权和 `realloc` 路径。对于高频固定大小对象，优先用内存池降低碎片和动态分配风险。

## 9. 最简记忆版

- 泄漏：不再需要的动态内存没有释放，长期运行时可用堆持续下降。
- 先区分泄漏、碎片和栈溢出，不能只看剩余堆。
- PC 端优先 ASan/LSan；Valgrind 用于 PC Linux 深度复核。
- RTOS 看可用堆、最大连续块、历史最低余量、分配记录和栈水位。
- `realloc` 用临时指针；C 用统一 `cleanup`；C++ 用 RAII。
- 内存池减少碎片和容量失控，但忘记归还仍然会泄漏。
