# 嵌入式 工厂模式

> 核心原则：**把“使用对象”和“创建对象”分开；调用方只依赖统一接口，不关心具体对象由哪个型号、驱动或协议实现。**
>
> 背景：嵌入式项目经常需要兼容不同芯片、传感器、通信模块或产品型号。若业务代码里到处出现 `if (type == ...)` 和具体驱动初始化，新增硬件时会牵动大量代码。工厂模式把这种选择集中在创建处，让上层逻辑保持稳定。

## 1. 核心思想

工厂模式的核心是：**由工厂决定“创建谁”，由调用方决定“怎么用”。**

例如温湿度模块可能使用 SHT30、AHT20 或 DHT11。控制层只需要“读取温湿度”，不应知道 SPI/I2C 时序或每种芯片的初始化细节；这些差异应由工厂在启动时根据板型、配置或探测结果封装起来。

```text
业务层：温控 / 显示 / 上报
          ↓  只依赖 sensor_read()
抽象接口：sensor_t
          ↓
工厂：根据型号创建具体驱动
          ↓
SHT30 驱动    AHT20 驱动    模拟驱动
```

这样新增一种传感器时，通常只需新增一个具体实现，并在工厂中登记；原有的温控、显示和云端上报代码无需修改。

## 2. 简单工厂、工厂方法与抽象工厂

“工厂模式”常泛指三种相关做法，嵌入式项目不必拘泥于名称，重点是选合适的复杂度。

| 形式 | 做法 | 适合场景 | 代价 |
|------|------|----------|------|
| 简单工厂 | 一个创建函数根据类型返回具体对象 | 同一类设备有少量型号 | 工厂会随型号增多而变长 |
| 工厂方法 | 每个具体工厂负责创建一种对象 | 创建步骤复杂，或需避免改动中心工厂 | 文件和类型更多 |
| 抽象工厂 | 一个工厂创建一整套相互匹配的对象 | 多板型、多芯片平台需要成套适配 | 抽象层较多，简单项目易过度设计 |

实际 MCU 项目里最常用的是**简单工厂 + 函数指针接口表**。它不依赖 C++ 继承，也没有动态内存的必要，却能达到运行时替换驱动的目的。

## 3. C 语言中的基本实现

C 没有类，可以用“结构体保存状态 + 函数指针保存行为”模拟接口。以下以温度传感器为例：

```c
typedef enum {
    SENSOR_SHT30 = 0,
    SENSOR_AHT20,
    SENSOR_MOCK,
} sensor_type_t;

typedef struct sensor sensor_t;

struct sensor {
    bool (*init)(sensor_t *self);
    bool (*read_temperature)(sensor_t *self, float *temp);
    void (*deinit)(sensor_t *self);
    void *priv;                 // 具体驱动的私有状态
};

// 工厂接口：根据类型返回一个满足 sensor_t 接口的对象
sensor_t *sensor_factory_create(sensor_type_t type);
```

调用方只面向 `sensor_t` 编程：

```c
static void temperature_task(sensor_t *sensor)
{
    float temp;

    if (sensor->init(sensor)) {
        while (1) {
            if (sensor->read_temperature(sensor, &temp)) {
                thermal_control_update(temp);
                cloud_report_temperature(temp);
            }
            vTaskDelay(pdMS_TO_TICKS(1000));
        }
    }
}
```

无论底层最终是 SHT30 还是 AHT20，`temperature_task()` 都不需要改变。

## 4. 一个完整的简单工厂例子

对于资源受限的系统，优先使用静态对象，避免在工厂中 `malloc`。下面的实现只展示关键结构：

```c
typedef struct {
    I2C_HandleTypeDef *hi2c;
    uint8_t address;
} sht30_ctx_t;

static bool sht30_init(sensor_t *self)
{
    sht30_ctx_t *ctx = self->priv;
    return sht30_probe(ctx->hi2c, ctx->address);
}

static bool sht30_read_temperature(sensor_t *self, float *temp)
{
    sht30_ctx_t *ctx = self->priv;
    return sht30_read(ctx->hi2c, ctx->address, temp, NULL);
}

static void sht30_deinit(sensor_t *self) { (void)self; }

static sht30_ctx_t g_sht30_ctx = { .hi2c = &hi2c1, .address = 0x44 };
static sensor_t g_sht30 = {
    .init = sht30_init,
    .read_temperature = sht30_read_temperature,
    .deinit = sht30_deinit,
    .priv = &g_sht30_ctx,
};

static sensor_t g_mock = {
    .init = mock_sensor_init,
    .read_temperature = mock_sensor_read_temperature,
    .deinit = mock_sensor_deinit,
    .priv = NULL,
};

sensor_t *sensor_factory_create(sensor_type_t type)
{
    switch (type) {
    case SENSOR_SHT30: return &g_sht30;
    case SENSOR_AHT20: return aht20_sensor_instance();
    case SENSOR_MOCK:  return &g_mock;
    default:           return NULL;
    }
}
```

系统启动时根据硬件配置选择实现：

```c
sensor_t *sensor = sensor_factory_create(board_cfg.sensor_type);
if (sensor == NULL) {
    system_enter_safe_mode();
} else {
    temperature_task(sensor);
}
```

这里的 `switch` 并不是坏味道：它被限制在唯一的“对象创建点”，而没有散落到每个业务模块中。新增型号时只改工厂和新驱动，不会扩散到调用方。

## 5. 对比例子：多协议网关模块

需求：网关需要把统一的采集数据发送给下游设备。不同项目现场可能使用 Modbus RTU、CAN 或自定义 UART 协议；业务层只关心“向指定设备发送一帧数据”和“接收一帧有效数据”。

**直接在业务层判断**时，协议差异会不断渗入转发代码：

```c
bool gateway_forward(uint8_t device_id, const uint8_t *data, uint16_t len)
{
    if (g_protocol == PROTOCOL_MODBUS_RTU) {
        return modbus_rtu_write_registers(device_id, data, len);
    } else if (g_protocol == PROTOCOL_CAN) {
        return can_send_frames(device_id, data, len);     // 分帧、仲裁 ID
    } else if (g_protocol == PROTOCOL_UART_PRIVATE) {
        return private_uart_send(device_id, data, len);   // 帧头、长度、校验
    }
    return false;
}
```

问题：每增加一种下游协议，转发、轮询、超时重试和状态统计等功能都可能要改；业务层还被迫知道 CRC、CAN 分帧和私有协议封包等细节。

**使用工厂后**，业务层只依赖统一的网关端口接口：

```c
typedef struct gateway_port gateway_port_t;
struct gateway_port {
    bool (*init)(gateway_port_t *self);
    bool (*send)(gateway_port_t *self, uint8_t device_id,
                 const uint8_t *data, uint16_t len);
    bool (*receive)(gateway_port_t *self, uint8_t *device_id,
                    uint8_t *data, uint16_t *len);
    void *priv;
};

gateway_port_t *gateway_port_factory_create(protocol_type_t type);

bool gateway_forward(gateway_port_t *port, uint8_t device_id,
                     const uint8_t *data, uint16_t len)
{
    return port->send(port, device_id, data, len);
}
```

应用启动时按项目配置创建协议实现：

```c
gateway_port_t *port = gateway_port_factory_create(gateway_cfg.protocol_type);
if (port != NULL && port->init(port)) {
    (void)gateway_forward(port, target_id, payload, payload_len);
}
```

工厂分别返回 `modbus_rtu_port_instance()`、`can_port_instance()` 或 `private_uart_port_instance()`。每个具体实现自行处理报文封包、校验、分帧和底层总线状态，网关业务只处理统一的数据和设备编号。

优点：转发、重试和状态管理不依赖具体协议；需要支持新协议时只实现 `gateway_port_t` 接口并登记到工厂；测试时可传入假的端口实现，验证路由和重试逻辑，而不必连接真实总线。

## 6. 工厂方法与抽象工厂的实践

当“创建对象”本身也存在多套策略时，可以把简单工厂继续拆开。例如不同板型不仅传感器不同，显示屏、存储和通信芯片也必须成套匹配：

```c
typedef struct {
    sensor_t  *(*create_sensor)(void);
    display_t *(*create_display)(void);
    storage_t *(*create_storage)(void);
    network_t *(*create_network)(void);
} board_factory_t;

static const board_factory_t g_board_a_factory = {
    .create_sensor  = board_a_create_sht30,
    .create_display = board_a_create_oled,
    .create_storage = board_a_create_w25qxx,
    .create_network = board_a_create_wifi,
};
```

这就是抽象工厂的思想：调用方选择 `board_factory_t` 后，得到的是一组兼容的设备。它很适合产品有多个 PCB 版本或需要移植到不同 MCU 平台的情况。

但如果系统只需要在两种传感器间二选一，使用上一节的简单工厂更清晰。工厂层级应随变化的复杂度增加，而不是为了“模式完整”而增加。

## 7. 嵌入式中的实用建议

- 工厂返回失败时必须有明确策略：返回 `NULL` 后进入安全模式、使用降级实现，或在启动阶段报错停机；不要让空指针进入业务任务。
- 小型 MCU 优先返回静态实例或对象池中的实例。若必须动态分配，要配套 `destroy()` 接口，并明确对象所有权。
- 接口函数应覆盖真正稳定的业务能力，不要为了统一而暴露底层寄存器或总线句柄。
- 初始化失败可在工厂创建后统一检查，也可让工厂只返回已完成探测和初始化的可用对象；同一项目内约定一种方式即可。
- 工厂的类型来源要可追溯：可来自编译期板型宏、Flash 配置、拨码开关或硬件探测，并记录最终选择的型号，方便现场定位。
- 用 mock 实现作为一种正式的工厂产物，能在 PC 单元测试或硬件未到位时复用上层业务代码。

一个常见的错误是让工厂承担所有业务决策，例如“温度高就创建风扇对象”。工厂负责的是对象选择与装配；温度控制策略仍应属于业务层。

## 8. 适用范围

适合使用工厂模式的情况：

- 同一接口有多个硬件驱动实现，如不同传感器、屏幕、Flash 或通信模组。
- 产品有多个板型、地区版本或客户定制版本，需要在启动时装配不同组件。
- 希望上层业务可在真实硬件和模拟驱动之间切换，提升可测试性。
- 对象的初始化步骤较复杂，希望集中处理参数校验、资源申请和错误回收。

不适合或需谨慎使用的情况：

- 只有一个实现且近期没有替换可能：直接调用更直观，工厂只会增加间接层。
- 极端实时路径：函数指针间接调用和统一接口可能掩盖关键时序，应直接使用经过验证的底层实现。
- 所谓“类型”只是一次简单算法选择：若不涉及对象状态和资源初始化，普通函数表或策略模式往往更轻。

## 9. 最终结论

工厂模式在嵌入式中的核心价值是**隔离变化**：把芯片型号、板型配置和驱动初始化等易变细节集中在创建阶段，让温控、显示、存储和联网等业务逻辑只依赖稳定接口。

实战中建议从一个静态的简单工厂开始：**定义最小接口 → 为每种硬件实现接口 → 在唯一的工厂函数中选择实现 → 业务层只保存接口指针。** 当多个组件需要按板型成套替换时，再演进为抽象工厂。

不要为了使用工厂而抽象。只有当“同一能力存在多个实现，并且这种差异会持续变化”时，工厂带来的解耦、可测试性和移植便利才会真正超过它的复杂度。
