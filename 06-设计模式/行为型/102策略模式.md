# 嵌入式 策略模式

> 核心原则：**把“会变化的算法或规则”封装成可替换的策略；业务流程只定义何时执行，不把具体计算、判断或控制方法写死。**
>
> 背景：嵌入式项目中，设备控制、采样滤波、通信重试、告警判定和节能逻辑往往有多种实现。若这些差异散落在业务代码的 `if/else` 中，新增产品档位或调整规则时容易牵动主流程。策略模式把“采用哪种做法”从流程中分离出来，让变化集中在策略实现和选择处。

## 1. 核心思想

策略模式的核心是：**调用方负责“什么时候做”，策略负责“具体怎么做”。**

例如温控模块需要根据当前温度输出风扇 PWM。普通恒温控制、带回差控制和 PID 控制的输入输出形式可能相同，但计算过程不同。采样任务只需要在每次拿到温度后调用“计算控制输出”，不应把每一种控制公式都混在任务循环里。

```text
采样 / 控制任务：获取温度，调用控制算法，输出 PWM
                         ↓
抽象接口：control_strategy_t
                         ↓
开关控制策略    回差控制策略    PID 控制策略
```

这样切换产品版本、调试控制效果或进行 A/B 验证时，通常只需替换策略实例；采样、执行器驱动和故障保护等稳定流程不必修改。

## 2. 策略模式解决什么问题

策略模式适合处理“目标相同、做法不同”的情况。各策略对外提供相同能力，但内部算法、参数和状态可以不同。

| 对比项 | 直接在流程中判断 | 使用策略模式 |
|------|------|------|
| 差异位置 | `if/else`、`switch` 散落在业务流程 | 集中在独立策略实现中 |
| 新增算法 | 往往需要修改主流程 | 新增一个策略并在选择处登记 |
| 单元测试 | 要覆盖多个分支和完整任务环境 | 可单独给策略输入并检查输出 |
| 运行时切换 | 容易遗留旧状态或漏改分支 | 替换策略接口，并显式处理状态 |
| 代价 | 初期代码少，但分支会持续增长 | 多一层接口和策略对象 |

这里的“策略”不是单纯把一段代码搬到函数里。它应当代表一个可独立选择、可替换、可测试的规则。例如“采用何种滤波算法”“采用何种重试退避方式”“采用何种充电控制曲线”都是策略；而固定的 GPIO 写高低、寄存器读写通常不需要抽象成策略。

## 3. C 语言中的基本实现

C 没有接口或继承，可以用“结构体保存状态 + 函数指针保存行为”表达策略。以下以风扇控制为例：

```c
typedef struct control_strategy control_strategy_t;

struct control_strategy {
    void (*reset)(control_strategy_t *self);
    uint16_t (*calculate)(control_strategy_t *self,
                          float setpoint, float measurement);
    void *priv;                 // 策略自己的参数和运行状态
};
```

控制任务只依赖统一接口：

```c
static void thermal_control_task(control_strategy_t *strategy)
{
    float temperature;

    strategy->reset(strategy);

    while (1) {
        if (sensor_read_temperature(&temperature)) {
            uint16_t pwm = strategy->calculate(strategy,
                                               g_target_temperature,
                                               temperature);
            fan_set_pwm(pwm);
        }
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
```

无论实际选用回差控制还是 PID，`thermal_control_task()` 的采样周期、故障处理和 PWM 下发流程都保持不变。

## 4. 一个完整的策略例子

对散热要求不高的设备，回差控制通常比 PID 更容易调试，也能避免温度在阈值附近频繁启停。它的状态只需要记录当前风扇是否已经开启：

```c
typedef struct {
    float on_error;             // 超过设定值多少度时开启
    float off_error;            // 降到设定值多少度时关闭
    bool fan_on;
} hysteresis_ctx_t;

static void hysteresis_reset(control_strategy_t *self)
{
    hysteresis_ctx_t *ctx = self->priv;
    ctx->fan_on = false;
}

static uint16_t hysteresis_calculate(control_strategy_t *self,
                                     float setpoint, float measurement)
{
    hysteresis_ctx_t *ctx = self->priv;
    float error = measurement - setpoint;

    if (!ctx->fan_on && error >= ctx->on_error) {
        ctx->fan_on = true;
    } else if (ctx->fan_on && error <= ctx->off_error) {
        ctx->fan_on = false;
    }
    return ctx->fan_on ? 1000U : 0U;
}

static hysteresis_ctx_t g_hysteresis_ctx = {
    .on_error = 2.0f,
    .off_error = -1.0f,
};

static control_strategy_t g_hysteresis_strategy = {
    .reset = hysteresis_reset,
    .calculate = hysteresis_calculate,
    .priv = &g_hysteresis_ctx,
};
```

若产品升级后要求更平滑的输出，可以新增 PID 策略，而不改控制任务：

```c
typedef struct {
    float kp, ki, kd;
    float integral;
    float previous_error;
} pid_ctx_t;

static uint16_t pid_calculate(control_strategy_t *self,
                              float setpoint, float measurement)
{
    pid_ctx_t *ctx = self->priv;
    float error = measurement - setpoint;
    float derivative;
    float output;

    ctx->integral += error * 0.5f;       // 控制周期为 500 ms
    ctx->integral = CLAMP(ctx->integral, -100.0f, 100.0f);
    derivative = (error - ctx->previous_error) / 0.5f;
    ctx->previous_error = error;

    output = ctx->kp * error + ctx->ki * ctx->integral + ctx->kd * derivative;
    return (uint16_t)CLAMP(output, 0.0f, 1000.0f);
}
```

PID 策略还应提供 `reset()`，在切换策略、修改目标温度或传感器恢复后清除积分项，避免旧状态导致输出突变。示例省略了具体参数和初始化，但接口形态与回差策略完全一致。

## 5. 对比例子：通信重试策略

需求：设备向云端发送数据失败后需要重试。调试阶段可以固定每秒重试；量产设备则应采用指数退避，避免网络异常时持续占用蜂窝流量和 CPU。

**直接在发送任务中判断**时，重试规则很容易和状态机混在一起：

```c
if (cloud_send(data, len)) {
    retry_count = 0;
} else {
    retry_count++;
    if (g_retry_mode == RETRY_FIXED) {
        delay_ms(1000);
    } else if (g_retry_mode == RETRY_EXPONENTIAL) {
        delay_ms(1000U << MIN(retry_count, 5));
    }
}
```

问题：一旦加入随机抖动、不同错误码的退避上限、断网后的重新入网等需求，发送任务会同时承担传输、计数、时间计算和策略选择，难以验证边界情况。

**使用策略后**，发送状态机只询问下一次允许重试的时间：

```c
typedef struct retry_strategy retry_strategy_t;

struct retry_strategy {
    void (*reset)(retry_strategy_t *self);
    uint32_t (*next_delay_ms)(retry_strategy_t *self, int error_code);
    void *priv;
};

static void cloud_send_task(retry_strategy_t *retry)
{
    if (cloud_send(g_payload, g_payload_len)) {
        retry->reset(retry);
    } else {
        uint32_t delay = retry->next_delay_ms(retry, cloud_last_error());
        schedule_next_upload(delay);
    }
}
```

固定间隔策略总是返回 `1000`；指数退避策略维护失败次数，返回 `base_ms * 2^n` 并限制最大值；对鉴权失败可直接返回较长等待时间，或通知上层先刷新令牌。发送任务不需要了解这些细节。

优点：重试算法可脱离网络栈进行测试；现场发现流量异常时可单独调整退避参数；以后增加“仅关键数据立即重试”的策略，也不会破坏既有发送流程。

## 6. 策略的选择与切换

策略可以在编译期、启动期或运行期选择。选择时机取决于变化来源和状态安全性：

```c
control_strategy_t *strategy;

switch (board_cfg.control_mode) {
case CONTROL_HYSTERESIS:
    strategy = &g_hysteresis_strategy;
    break;
case CONTROL_PID:
    strategy = pid_strategy_instance();
    break;
default:
    strategy = &g_safe_stop_strategy;
    break;
}

thermal_control_task(strategy);
```

- **编译期选择**适合板型或功能裁剪固定的产品，可减少 Flash 和 RAM 占用。
- **启动期选择**适合由 Flash 配置、拨码开关或产品型号决定的行为，通常是嵌入式项目最简单可靠的方式。
- **运行期切换**适合调参、远程配置或故障降级，但必须定义好切换点，并调用旧/新策略的 `reset()` 或 `deinit()`，防止积分项、计数器等状态跨策略残留。

策略的选择逻辑可以由配置模块完成，也可以交给工厂模式创建。两者并不冲突：**工厂负责“得到哪个策略对象”，策略模式负责“业务如何通过统一接口使用它”。**

## 7. 嵌入式中的实用建议

- 接口要围绕稳定的业务输入和输出设计。例如滤波策略可使用 `filter(input)`，不要把 ADC 寄存器、DMA 缓冲区等底层细节塞进每个策略。
- 明确策略是否有状态。无状态策略可以共用常量实例；PID、滑动平均、重试退避等有状态策略应各自保存上下文，避免多个通道误共享计数或积分值。
- 为数值策略定义边界：输入范围、输出限幅、采样周期、溢出处理和异常值行为必须一致，否则同一接口难以真正替换。
- 极端实时路径可使用静态函数表或编译期选择，避免在中断中动态创建、销毁或频繁切换策略。
- 不要让策略绕过安全保护。过温关机、看门狗喂狗条件、最大 PWM 限制等系统级约束应放在策略外层统一执行。
- 为每种策略准备表驱动测试：给定输入序列和期望输出序列，重点覆盖阈值边界、状态复位和异常输入。

一个常见错误是为每个 `if` 都创建策略。只有当分支代表会独立演进、可替换的算法或业务规则时，策略模式才有价值；一次性的异常处理或固定硬件差异，保留简单条件判断通常更清晰。

## 8. 适用范围

适合使用策略模式的情况：

- 同一控制目标可采用不同算法，如开关、回差、PID 或前馈控制。
- 同一采样数据需要可切换的处理规则，如均值、中值、限幅或卡尔曼滤波。
- 通信、存储或升级流程有多种重试、校验、压缩或调度规则。
- 同一产品因功耗档位、地区规范或客户配置需要不同的业务判定逻辑。
- 希望分别验证算法与主流程，并能通过 mock 策略覆盖边界条件。

不适合或需谨慎使用的情况：

- 算法只有一个实现且短期内没有变化：直接调用函数更直观。
- 策略之间的接口差异很大：强行统一会产生大量无意义参数，应先拆分业务能力。
- 选择策略本身比算法还复杂：需要先梳理产品配置和状态机，而不是继续叠加抽象层。
- 关键控制策略必须经认证或严格时序验证：运行期随意切换会带来安全和可追溯性风险，应限制为受控配置。

## 9. 最终结论

策略模式在嵌入式中的核心价值是**隔离算法和规则的变化**：把控制、滤波、重试和判定等易变逻辑封装为可替换实现，让采样、状态机、执行器驱动和安全保护保持稳定。

实战中建议从一个最小函数接口开始：**识别可变算法 → 定义统一输入输出 → 把参数和状态放入策略上下文 → 在启动或受控切换点选择策略 → 用输入输出序列独立测试。** 当策略对象的创建和装配也变复杂时，再配合工厂模式处理。

不要为了使用策略而抽象。只有当“同一个目标确实存在多种会持续变化的做法”时，策略带来的可维护性、可测试性和产品复用价值才会超过它增加的一层间接性。
