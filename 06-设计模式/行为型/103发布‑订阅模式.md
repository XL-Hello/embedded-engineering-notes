# 嵌入式 发布-订阅模式

> 核心原则：**发布者只说明“发生了什么”，不直接调用具体业务；订阅者只声明自己关心什么事件，不需要知道事件来自哪个模块。**
>
> 背景：按键、传感器、通信和定时器常常会同时触发显示、控制、日志和上报等多个动作。若生产者逐个调用这些模块，新增一个功能就会反复修改原模块。发布-订阅模式通过事件通道和订阅表实现一对多通知，使模块可以独立演进。

## 1. 核心思想

发布-订阅模式的核心是：**发布者负责“通知发生”，订阅者负责“响应事件”，中间层负责“按订阅关系分发”。**

例如温度采样完成后，风扇控制需要判断阈值、日志模块需要记录数据、云端模块可能需要上报。传感器任务只发布 `EVENT_TEMP_READY`，不应依次调用 `fan_update()`、`log_write()` 和 `cloud_report()`。

```text
按键 / 传感器 / UART / 定时器
              ↓  发布事件
        事件队列 / 事件总线
              ↓  按主题分发
风扇控制     日志记录     云端上报
```

这样新增“温度异常时蜂鸣报警”时，只需增加一个订阅 `EVENT_TEMP_READY` 的处理器；采样任务和已有订阅者都不必修改。

## 2. 与事件驱动、观察者模式的关系

发布-订阅模式通常是事件驱动架构的一种实现方式。两者都围绕事件工作，但关注点不同：事件驱动强调“由事件触发处理”；发布-订阅强调“生产者和多个消费者不直接依赖”。

| 概念 | 关注点 | 发布者是否认识订阅者 | 常见实现 |
|------|--------|----------------------|----------|
| 直接回调 | 一个模块通知另一个明确模块 | 认识 | 保存回调函数并直接调用 |
| 观察者模式 | 一个主题通知其观察者 | 通常认识观察者列表 | `subject` 持有 observer 列表 |
| 发布-订阅模式 | 按主题或事件类型解耦多个模块 | 不认识 | 事件总线、消息队列、消息代理 |
| 事件驱动模型 | 用事件组织系统流程 | 不固定 | 中断 + 队列 + 分发器 / 状态机 |

在单 MCU 固件中，“事件总线”通常就是一个事件队列加订阅表，不必引入复杂的消息中间件。发布者投递本地事件，事件任务从队列取出后，调用所有匹配的订阅处理器。

## 3. 最小动态发布-订阅实现：温度采样、订阅与退订

以下示例只围绕 `EVENT_TEMP_READY`：温度采样任务发布事件；日志和云端模块订阅；风扇模块按自身启用状态动态绑定或解绑。没有编译期静态订阅表，分发器每次只读取当前已注册的订阅关系。

```c
#define EVENT_MAX_SUBSCRIPTIONS 8

typedef enum {
    EVENT_TEMP_READY = 0,
    EVENT_BUTTON_PRESS,
    EVENT_COUNT,
} event_type_t;

typedef struct {
    float temperature;
} temperature_event_data_t;

typedef struct {
    event_type_t type;
    const void *data;
    uint16_t data_len;
} event_t;

typedef void (*event_handler_t)(const event_t *event);

typedef enum {
    EVENT_OK = 0,
    EVENT_INVALID_ARGUMENT,
    EVENT_NO_SPACE,
    EVENT_NOT_FOUND,
} event_status_t;

typedef struct {
    event_type_t type;
    event_handler_t handler;
    bool used;
} event_subscription_slot_t;

static event_subscription_slot_t g_slots[EVENT_MAX_SUBSCRIPTIONS];
```

`event_subscribe()` 在空槽中登记“事件类型 + 处理器”；同一处理器重复登记时直接返回成功，不产生两次回调。`event_unsubscribe()` 则删除这条关系。`event_lock()` / `event_unlock()` 应替换为与项目 RTOS 匹配的互斥锁或临界区，且只能由任务上下文调用。

```c
event_status_t event_subscribe(event_type_t type, event_handler_t handler)
{
    if (type >= EVENT_COUNT || handler == NULL) {
        return EVENT_INVALID_ARGUMENT;
    }

    event_lock();
    for (size_t i = 0; i < ARRAY_SIZE(g_slots); ++i) {
        if (g_slots[i].used && g_slots[i].type == type &&
            g_slots[i].handler == handler) {
            event_unlock();
            return EVENT_OK;  // 已订阅：幂等成功，不重复登记
        }
    }
    for (size_t i = 0; i < ARRAY_SIZE(g_slots); ++i) {
        if (!g_slots[i].used) {
            g_slots[i] = (event_subscription_slot_t){ type, handler, true };
            event_unlock();
            return EVENT_OK;
        }
    }
    event_unlock();
    return EVENT_NO_SPACE;
}

event_status_t event_unsubscribe(event_type_t type, event_handler_t handler)
{
    event_lock();
    for (size_t i = 0; i < ARRAY_SIZE(g_slots); ++i) {
        if (g_slots[i].used && g_slots[i].type == type &&
            g_slots[i].handler == handler) {
            g_slots[i].used = false;
            event_unlock();
            return EVENT_OK;
        }
    }
    event_unlock();
    return EVENT_NOT_FOUND;
}
```

发布时不认识任何具体模块。为了避免持锁执行用户处理器，分发器先复制本次要调用的函数指针快照，再逐个调用；因此退订成功后不再进入**新的**分发快照，但已经取到快照的调用仍可能执行一次。

```c
static void event_dispatch(const event_t *event)
{
    event_handler_t handlers[EVENT_MAX_SUBSCRIPTIONS];
    size_t count = 0;

    event_lock();
    for (size_t i = 0; i < ARRAY_SIZE(g_slots); ++i) {
        if (g_slots[i].used && g_slots[i].type == event->type) {
            handlers[count++] = g_slots[i].handler;
        }
    }
    event_unlock();

    for (size_t i = 0; i < count; ++i) {
        handlers[i](event);
    }
}

static void event_publish_temperature(float temperature)
{
    temperature_event_data_t data = { .temperature = temperature };
    event_t event = {
        .type = EVENT_TEMP_READY,
        .data = &data,
        .data_len = sizeof(data),
    };
    event_dispatch(&event);
}
```

日志和云端在各自模块启动时订阅；风扇模块则由“是否启用温度响应”这一状态控制绑定与解绑。发布者 `sensor_task()` 始终只调用 `event_publish_temperature()`。

```c
static void log_on_temperature(const event_t *event)
{
    const temperature_event_data_t *data = event->data;
    log_write("temp=%.1f", data->temperature);
}

static void report_on_temperature(const event_t *event)
{
    const temperature_event_data_t *data = event->data;
    if (data->temperature >= 55.0f) {
        cloud_report_temperature(data->temperature);
    }
}

static void fan_on_temperature(const event_t *event)
{
    const temperature_event_data_t *data = event->data;
    fan_set_output(data->temperature >= 60.0f);
}

event_status_t fan_set_enabled(bool enabled)
{
    if (enabled) {
        return event_subscribe(EVENT_TEMP_READY, fan_on_temperature);
    }

    fan_set_output(false);
    return event_unsubscribe(EVENT_TEMP_READY, fan_on_temperature);
}

void app_start(void)
{
    (void)event_subscribe(EVENT_TEMP_READY, log_on_temperature);
    (void)event_subscribe(EVENT_TEMP_READY, report_on_temperature);
    (void)fan_set_enabled(true);   // 风扇状态为开：绑定温度事件
}

void app_stop_fan(void)
{
    (void)fan_set_enabled(false);  // 风扇状态为关：解绑温度事件
}
```

**重要说明：**这里的“风扇状态开/关”表示风扇控制功能是否启用。若把“物理风扇已停转”也当作解绑条件，风扇将收不到之后升温的事件，无法自动再次开启；这种恒温控制场景应保持订阅，在 `fan_on_temperature()` 内仅控制输出状态。对于异步队列版本，`event_publish_temperature()` 还必须复制 `data` 或使用对象池，不能把栈变量指针排队。

## 4. 发布与分发：任务和中断的边界

发布动作可发生在普通任务、中断服务程序（ISR）或驱动回调中，但处理复杂度必须与上下文匹配。

```c
// 采样任务：可拷贝数据后投递队列
static void sensor_task(void *argument)
{
    while (1) {
        temperature_event_data_t data = {
            .temperature = sensor_read_temperature(),
        };
        event_publish(EVENT_TEMP_READY, &data, sizeof(data));
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

// ISR：只做最短路径的确认和投递，绝不直接分发耗时业务
void HAL_GPIO_EXTI_Callback(uint16_t pin)
{
    if (pin == BUTTON_PIN) {
        event_publish_from_isr(EVENT_BUTTON_PRESS, NULL, 0);
    }
}

static void event_task(void *argument)
{
    event_t event;

    while (event_queue_pop(&event, portMAX_DELAY)) {
        event_dispatch(&event);
    }
}
```

ISR 中不要打印日志、访问慢速总线、动态分配内存或逐个调用订阅者；这些操作会拉长中断时间，影响其他中断和实时性。若 RTOS 队列支持 ISR 版本 API，应使用对应接口，并在需要时请求任务切换。

## 5. 对比例子：温度事件的一对多处理

需求：温度每秒更新。超过 60°C 时开启风扇，所有采样数据记录到日志，超过 55°C 的数据上报云端。

**直接调用**时，传感器模块会逐渐知道太多业务细节：

```c
void sensor_task(void *argument)
{
    while (1) {
        float temp = sensor_read_temperature();

        fan_update(temp);
        log_temperature(temp);
        if (temp >= 55.0f) {
            cloud_report_temperature(temp);
        }
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

问题：新增蜂鸣器、屏幕显示或本地存储都会修改 `sensor_task()`；云端故障或日志写入变慢也可能拖慢采样周期。

**使用发布-订阅后**，采样模块只发布数据；第 3 节中的当前订阅关系决定日志、云端和已启用的风扇控制是否收到它：

```c
void sensor_task(void *argument)
{
    while (1) {
        float temperature = sensor_read_temperature();
        event_publish_temperature(temperature);
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}
```

优点：采样、风扇、日志和上报相互独立；每个处理器可直接传入构造的 `event_t` 做单元测试；风扇关闭时调用退订即可停止接收温度事件。新增蜂鸣器则在其模块中调用 `event_subscribe(EVENT_TEMP_READY, buzzer_on_temperature)`，不修改采样任务。

## 6. 事件数据的所有权与生命周期

事件总线最容易出错的部分不是“怎么调用”，而是“事件里的数据由谁创建、谁释放、何时有效”。不能把指向任务栈局部变量的指针排队后再异步使用。

常见方案如下：

| 方案 | 做法 | 适用场景 | 注意事项 |
|------|------|----------|----------|
| 值拷贝 | 将小型事件和数据直接拷入队列 | 按键、状态变化、小型采样值 | 最安全；注意队列 RAM 占用 |
| 固定对象池 | 从对象池申请事件块，处理后归还 | 报文、传感器批量数据 | 明确申请、归还和队列满策略 |
| 引用计数 | 每个异步消费者持有一个引用 | 多订阅者共享较大只读数据 | 实现复杂，原子操作和释放路径要完整 |
| 静态缓冲区 | 事件只传索引或只读快照 | DMA 双缓冲、固定采样槽 | 防止生产者覆盖仍在消费的数据 |

对于几十字节以内的控制事件，优先采用值拷贝；对于 UART 帧或图像块等较大数据，优先使用“对象池 + 指针/句柄”，并把释放责任写在接口注释中。不要让多个订阅者随意修改共享数据；需要修改时各自复制。

## 7. 背压、优先级与处理器隔离

发布-订阅只解决依赖关系，不会自动解决吞吐量问题。发布速度长期高于消费速度时，队列终会满；任一订阅者过慢，也可能阻塞后续订阅者。

- 明确每类事件的溢出策略：丢弃最新、丢弃最旧、合并为最新状态、阻塞发布者，或触发告警。不同事件不能共用默认策略。
- 控制、故障和安全事件应使用独立队列或更高优先级；日志、遥测等可延后或合并，不能挤占紧急命令。
- 处理器只完成快速、确定的工作。文件写入、网络发送、复杂计算应再次投递到专用工作队列，避免事件任务被一个订阅者长期占用。
- 为队列长度、丢弃次数、最长处理时长和订阅者失败次数做统计；这些指标是现场定位“偶发漏事件”的关键证据。
- 需要顺序时，应在同一消费者上下文串行处理；多个任务并行消费同一主题时，不能假定全局顺序仍然成立。

例如温度每秒一条时，日志订阅者可以异步批量落盘；而 `EVENT_OVER_TEMPERATURE` 应直接进入高优先级控制队列，以免被大量普通遥测阻塞。

## 8. 动态订阅与退订的安全性

运行期订阅、退订或模块卸载时，订阅槽与分发过程必须同步：不能在分发器正准备调用某个处理器时，把该处理器的上下文释放掉。

可选择以下约束之一：

- 订阅关系只允许在明确的阶段切换点更新，例如风扇控制功能启用或停止时。
- 更新订阅槽时加锁，分发时使用读锁或复制一份快照；锁内不执行用户处理器。
- 使用引用计数或 RCU 一类延迟回收机制，确保所有正在进行的分发结束后才释放订阅项。

小型 MCU 的动态订阅数量应设上限，并优先把注册和退订放入明确的模块状态切换点；这样既保留动态绑定能力，也更容易验证。

## 9. 适用范围

适合使用发布-订阅模式的情况：

- 一个事件天然有多个独立反应，如按键同时更新 UI、记录日志和上报。
- 传感器、协议、驱动与业务模块需要独立演进，避免相互直接调用。
- 希望新增监控、诊断、告警等旁路功能时不改动原生产者。
- 需要为每个处理器单独构造事件并进行单元测试。

不适合或需谨慎使用的情况：

- 只有一个调用者和一个明确的接收者：直接函数调用更直观，也更容易追踪错误返回值。
- 电流环、PWM 更新等极端实时控制路径：队列、分发和函数指针会增加不可忽略的时延和抖动。
- 事件必须得到同步结果才能继续：应使用请求-应答接口、同步消息或状态机，不要伪装成单向事件。
- 高频连续数据流，如音频 PCM、1 kHz 以上的 IMU 原始数据：使用 DMA、环形缓冲和批处理通常更合适。

## 10. 最终结论

发布-订阅模式在嵌入式中的核心价值是**让生产者和消费者解耦**：发布者只产生事件，订阅者按需响应，事件总线负责一对多分发。它特别适合把控制、日志、显示、上报和诊断等相互独立的反应从驱动或采样任务中拆出来。

实战中建议从受限的动态订阅开始：**定义小而明确的事件 → 为每个订阅者定义绑定和解绑条件 → 在 ISR 中只投递 → 在任务中串行分发 → 明确数据所有权 → 为关键事件设计容量和优先级 → 用统计指标验证队列没有长期积压。**

不要为了“解耦”而把每次函数调用都变成事件。只有当一个事实确实可能被多个模块独立消费，或生产者与消费者会持续变化时，发布-订阅带来的扩展性和可测试性才值得这层机制的复杂度。
