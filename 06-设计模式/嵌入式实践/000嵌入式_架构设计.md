# 嵌入式系统常见架构设计思想

本文整理嵌入式软件中常见的架构与设计思想。重点是理解每种思想要解决的问题、基本做法和典型使用位置；复杂架构的实现细节、性能取舍和完整方案另行分析。

文中的框图和伪代码用于帮助建立直观印象：框图强调模块边界和流向，伪代码强调处理顺序，并不等同于可直接编译的工程代码。

## 一、分层与模块组织

### 分层架构

分层架构把软件按职责划分为若干层。例如，应用层负责产品功能，业务服务层负责业务规则，驱动接口层负责统一访问硬件，最底层才是寄存器和具体外设。上层只使用下层提供的能力，不需要了解下层如何实现。

它解决的是“业务代码与硬件细节混在一起”的问题。比如产品从一颗 MCU 换到另一颗 MCU 时，通常只需调整驱动和适配层，设备控制流程、通信协议和人机交互等上层逻辑可以基本保持不变。常见于有一定规模、需要长期维护或存在硬件改版可能的 MCU、Linux 嵌入式项目。

```text
┌──────────────┐  产品功能、界面、协议
│   应用层     │
├──────────────┤  控制流程、业务规则
│  业务服务层  │
├──────────────┤  统一的硬件访问接口
│ HAL / 驱动层 │
├──────────────┤  寄存器、外设、芯片
│   硬件层     │
└──────────────┘
```

关键点是依赖方向从上到下。应用层不应越过 HAL 直接改寄存器，也不应让底层驱动反过来决定业务流程；否则硬件改动仍会传播到整套软件。

### 硬件抽象层（HAL）

HAL 是分层架构中专门面向硬件的一层。它把 GPIO、串口、SPI、I2C、ADC 等寄存器操作封装成较容易理解的函数或接口，例如“读取传感器”“发送一帧数据”，而不是让业务代码直接配置寄存器位。

它的目的不是隐藏所有硬件差异，而是把差异集中在少量代码里。常用于同一产品需要更换芯片、同一业务运行在不同平台，或上层功能希望用模拟驱动做测试的情况。HAL 之上应描述“要做什么”，HAL 之下才处理“具体怎么驱动硬件”。

```text
业务：读取温度
      │ 调用统一接口
      ▼
sensor_read_temperature()
      │
      ├── 方案 A：ADC + 热敏电阻
      └── 方案 B：I2C 数字温度计

业务层只关心结果，不关心具体器件。
```

### 板级支持包（BSP）

BSP 负责一块具体电路板的初始化和基础支持，例如时钟配置、引脚分配、板载 LED、按键、电源控制和外设连接方式。它与芯片通用驱动不同：芯片驱动描述“这颗芯片能做什么”，BSP 描述“这块板实际接了什么、怎样连接”。

当一颗芯片被用于开发板、量产板和不同客户版本时，BSP 可以把这些板级差异隔离开。常见于需要维护多个硬件版本的项目，也常作为芯片驱动、HAL 与应用软件之间的适配层。

```text
                ┌── 板卡 A：LED 在 PA1，传感器走 I2C1
同一 MCU 驱动 ──┤
                ├── 板卡 B：LED 在 PB4，传感器走 I2C2
                │
                └── 板卡 C：无 LED，增加电源使能脚

不同之处放进各自 BSP，芯片通用驱动保持不变。
```

### 驱动与应用分离

驱动层只负责完成硬件相关动作，例如从 ADC 取值、向 Flash 写入数据、从串口收取字节；应用层负责判断这些数据意味着什么，以及下一步应采取什么业务动作。驱动不应知道“设备是否进入故障模式”，应用也不应直接拼接寄存器配置。

这种划分使基础能力可以被多个业务复用，也使测试和故障定位更清晰。例如通信驱动只保证可靠收发，协议解析和设备控制流程放在上层。它适用于几乎所有包含外设驱动和业务逻辑的嵌入式项目。

```text
应用：收到“启动电机”命令
        │
        ▼
业务：检查条件、决定目标转速
        │
        ▼
驱动：配置 PWM、读取故障脚
        │
        ▼
硬件：定时器 / 引脚 / 电机驱动器
```

### 面向接口编程

面向接口编程强调模块之间只依赖稳定的对外约定，而不依赖对方的内部变量、数据结构或实现方式。调用方只知道“可以读取温度”或“可以保存参数”，不必知道底层究竟使用 ADC、I2C 传感器还是哪一种 Flash。

这样做能减少模块之间的连带修改。常见于传感器、存储、通信、操作系统适配等可能被替换的部件，也适合为单元测试准备模拟实现。接口应尽量描述业务能力，而不是暴露内部实现细节。

```c
/* 上层只依赖这份约定 */
int storage_save(const void *data, size_t size);

/* 实现可替换：内部 Flash / 外部 EEPROM / 文件系统 */
```

当实现替换时，调用 `storage_save()` 的业务代码无需跟着修改；这就是接口隔离带来的价值。

### 组件化与可裁剪设计

组件化是将日志、参数存储、网络协议、升级等功能组织为相对独立的单元，每个单元有自己的接口、配置和依赖关系。可裁剪则表示产品不需要某组件时，可以不编译或不启用它，而不影响其他功能。

它适合一套基础软件需要服务多个产品型号的情况。例如基础版没有网络和日志存储，高配版启用这些组件；两者仍能共享大部分代码。组件之间的边界要清楚，否则只是把相互依赖的大文件拆成了多个目录。

```text
                 ┌── 日志组件（可选）
产品公共框架 ────┼── 参数存储组件（必选）
                 ├── 网络组件（高配可选）
                 └── OTA 组件（高配可选）

基础版：公共框架 + 参数存储
高配版：公共框架 + 参数存储 + 网络 + OTA + 日志
```

### 单一职责原则

单一职责原则要求一个模块只对一类变化负责。日志模块专注于记录和输出日志，存储模块专注于读写介质，设备控制模块专注于控制流程；不要让日志模块顺便决定设备动作，也不要让通信模块承担所有业务判断。

它的价值在于降低理解、修改和测试的难度。当需求变化时，通常只需找到负责该事情的模块。常用于任何项目的模块划分，尤其适合防止“万能管理模块”不断膨胀。

```text
日志模块     → 记录“发生了什么”
存储模块     → 保存“数据放在哪里”
通信模块     → 处理“如何收发”
控制模块     → 决定“设备下一步做什么”

一个模块跨越多种职责时，通常就是继续拆分的信号。
```

## 二、任务执行与控制流程

### 轮询（Super Loop）

轮询架构以一个无限主循环为中心，程序按固定顺序检查按键、采样、通信和控制等工作。每一轮循环都处理一部分已准备好的事务，因此实现简单、运行路径直观，也不需要 RTOS 的任务和调度资源。

它适合功能少、响应时间要求不高的小型裸机设备，例如简单遥控器、传感器节点或低成本控制板。关键是每次处理都要尽快返回；若某个函数长时间等待或延时，就会拖慢其他所有功能。复杂流程通常会配合状态机拆分为多次短处理。

```c
while (1) {
    key_process();       // 只检查一次，不等待按键松开
    sensor_process();    // 到采样时间才做一次采样
    comm_process();      // 处理已收到的数据
    control_process();   // 推进当前控制状态
}
```

主循环不是“按顺序把所有事情做完”，而是反复、快速地推进每件事情一点点。

### 多任务优先级调度

在 RTOS 中，可以把采集、通信、显示、日志等工作拆成独立任务，并为它们设置不同优先级。调度器优先让更紧急的任务获得运行机会，低优先级工作则在系统空闲或高优先级任务等待时运行。

它适合同时存在多类工作、且响应时限不同的产品。例如高速采集通常需要及时处理，通信需要稳定响应，界面刷新和日志写入可以相对靠后。任务拆分并不等于任务越多越好；每个任务应有明确职责，并避免在高优先级任务中执行耗时操作。

```text
高优先级  ┌──────────┐  采样到期后快速采集、投递数据
          │ 采集任务 │
中优先级  ├──────────┤  协议解析、通信收发
          │ 通信任务 │
低优先级  ├──────────┤  按键、显示刷新
          │ UI 任务  │
最低优先级└──────────┘  日志、巡检等后台工作
```

优先级表达的是响应紧急程度，不是模块的重要程度。低优先级任务长期得不到运行机会，往往说明高优先级任务做得过多或没有及时阻塞等待。

### 事件驱动

事件驱动让任务在没有事情可做时主动等待，只有收到“数据到了”“按键按下”“定时到期”等事件后才被唤醒处理。事件可以来自中断、消息队列、信号量、任务通知或软件定时器。

相比持续轮询，它能减少无意义的 CPU 消耗，也更利于低功耗。常用于串口接收、按键唤醒、网络数据处理和 RTOS 任务协作。事件只表达“发生了什么”，实际处理仍应放在合适的任务或后台流程中完成。

```text
串口中断                通信任务
   │ 收到数据              │ 平时阻塞等待
   ▼                       ▼
投递“数据到达”事件 ───→ 被唤醒，读取并解析数据
                              │
                              ▼
                         再次进入等待
```

### 有限状态机（FSM）

状态机适合描述“系统目前处于什么阶段，以及在不同输入下该如何变化”。它先列出有限个状态，再明确每个状态可接收的事件、状态转换和相应动作。这样可以把复杂流程从层层嵌套的条件判断中抽离出来。

常见于通信协议收发、按键组合识别、开机流程，以及设备从待机、运行、告警到故障的模式管理。Moore 型状态机的输出主要由当前状态决定，Mealy 型则还会受当前输入影响；在普通应用中，更重要的是把状态、事件和转换关系写清楚。

```text
             启动命令              故障事件
 [待机] ─────────────→ [运行] ─────────────→ [故障]
   ▲                    │                     │
   └──── 停止命令 ──────┘       故障解除 ──────┘
```

```c
switch (state) {
case STANDBY: if (start) state = RUNNING; break;
case RUNNING: if (fault) state = FAULT; else if (stop) state = STANDBY; break;
case FAULT:   if (fault_cleared) state = STANDBY; break;
}
```

### 前台中断 + 后台主循环

这是经典裸机分工方式：前台的中断服务程序负责尽快响应硬件事件，例如记录串口字节、采样完成标志或定时到期；后台主循环根据这些标志完成解析、计算和控制等较耗时的业务。

它兼顾了中断响应速度和主程序可维护性，适用于没有 RTOS、但仍要处理异步外设事件的系统。中断中应避免长延时、复杂计算、阻塞等待和大量日志输出，否则会影响其他中断和系统实时性。

```text
前台：硬件中断                   后台：主循环
UART 收到一个字节 ──→ 放入接收缓冲区 ──→ 解析完整报文并执行业务
定时器到期         ──→ 置采样标志     ──→ 读取传感器、计算和控制
```

```c
void timer_isr(void) { sample_due = true; }  // 前台：短
void loop(void) { if (sample_due) { sample_due = false; sample_and_control(); } }
```

### 管道-过滤器

管道-过滤器将一段数据处理流程拆成连续的处理单元，每个单元只接收输入、完成一种变换，然后把结果交给下一单元。数据像沿管道流动一样，处理单元之间不需要了解彼此的内部细节。

它很适合处理链路稳定的数据，例如传感器数据依次经历滤波、单位换算、异常判断、编码、打包和上报；音频、图像和协议数据处理也常采用类似方式。好处是容易替换或增加某一步，前提是每一步的输入输出格式要约定清楚。

```text
原始采样 ─→ [滤波] ─→ [单位换算] ─→ [异常判断] ─→ [编码打包] ─→ 上报
             噪声降低     统一量纲         标记状态         形成报文
```

某一步只应关注自己的输入和输出。例如滤波器不需要知道数据最终是显示在屏幕上还是通过网络上报。

### 主从架构

主从架构将总体协调和专用实时工作分配给不同处理单元。主控通常负责业务流程、界面、通信和策略；从控负责电机控制、功率驱动、高速采集等独立且实时性更强的任务，双方通过串口、SPI、CAN 或共享机制交换命令和状态。

它适合单个 MCU 的算力、接口或实时性不足以同时承担所有任务的场景，也适用于多核处理器的分工。设计重点是明确主从边界、通信协议和异常情况下的职责，而不是把所有工作简单地“丢给从机”。

```text
┌────────────── 主控 MCU ──────────────┐
│ 业务流程 │ UI │ 网络 │ 设备策略       │
└───────────────┬─────────────────────┘
                │ CAN / SPI / UART：命令、状态、故障
┌───────────────▼─────────────────────┐
│ 从控 MCU：电机闭环 / 功率控制 / 高速采集 │
└─────────────────────────────────────┘
```

## 三、模块间通信与数据共享

### 消息队列与生产者-消费者

消息队列提供一个有序缓冲区：产生数据或命令的模块作为生产者放入消息，负责处理的模块作为消费者取出消息。双方通过队列交接，不需要同时直接读写同一变量，也不必在同一时间运行。

它是 RTOS 中常用的任务通信方式，适用于采集任务向通信任务交数据、按键任务向业务任务发命令等情况。队列容量和消息格式需要根据数据速率设计；生产速度长期高于消费速度时，仍要处理满队列、丢弃或限流问题。

```text
采集任务（生产者） ── put(sample) ──→ [消息队列] ── get() ──→ 上报任务（消费者）
                                         ↑
                                      队列有上限
```

```c
/* 生产者 */ queue_send(sample_queue, &sample);
/* 消费者 */ queue_receive(sample_queue, &sample, WAIT_FOREVER); // 无数据时休眠
```

### 发布-订阅（Pub/Sub）

发布-订阅用于“一份信息需要通知多个模块”的情况。发布者只负责发布某类事件或数据，订阅者按需要注册接收；发布者不需要知道有多少订阅者，也不需要逐个调用它们。

例如设备状态变化后，显示、日志、报警和通信模块都可能需要响应；传感器数据也可能同时服务于控制算法和上报功能。它能降低模块耦合，但消息主题、数据生命周期和订阅者处理速度仍需要有明确约定。

```text
                         ┌→ 显示模块
设备状态发布者 ─→ [状态变化事件] ─┼→ 日志模块
                         ├→ 报警模块
                         └→ 通信上报模块
```

发布者只发出“状态变化”这一事实，不直接调用各个接收模块；新增订阅者也不必修改发布者。

### 共享内存与同步保护

共享内存是让多个任务或中断共同访问同一块缓冲区或状态变量。因为共享数据不需要反复复制，适合图像、波形、音频等大块数据；但如果两个执行单元同时读写，就可能读到不完整数据或互相覆盖。

因此通常要配合互斥锁、临界区、双缓冲等同步手段，明确谁可以写、谁可以读、何时可以访问。它适用于复制成本较高或数据必须集中保存的场景；对于少量控制命令和状态传递，优先使用消息通信通常更容易维护。

```text
任务 A 写入 ──┐
              ├── [共享波形缓冲区] ──→ 任务 B 读取
任务 C 读取 ──┘          ▲
                           └─ 互斥锁 / 临界区 / 双缓冲保证一致性
```

```c
lock(buffer_lock);
copy_waveform(shared_buf, new_data);
unlock(buffer_lock);
```

### 信号量

信号量是一种轻量的同步工具，用来表示“某件事已经发生”或“某类资源还有可用数量”。二值信号量只有有/无两种状态，常用于中断通知任务；计数信号量可以记录多个同类资源或多次发生的事件。

典型场景包括 DMA 传输完成后唤醒处理任务、等待某个外设操作结束，或限制若干任务对有限资源的并发使用。信号量适合通知和协调，不适合承载完整业务数据；需要传递数据时通常要结合队列或共享缓冲区。

```text
DMA 完成中断 ── give(二值信号量) ──→ 算法任务被唤醒

资源池：3 个相同缓冲区
计数信号量初值 = 3
每借出一个缓冲区 -1；归还后 +1
```

### 数据同步与事件通知分离

“把数据交给别人”和“提醒别人现在该处理了”看起来相似，实际是两件事。数据同步关心数据内容、一致性和所有权；事件通知关心某个时刻发生了什么，以及谁需要被唤醒。

例如采样结果可以通过队列或双缓冲提供给算法任务，而“新一批采样完成”可以用信号量或任务通知触发处理。将两者分开思考，有助于选择合适的通信原语，也能避免只靠一个全局标志同时承担数据和通知而产生竞态。

```text
数据同步：采集任务 ──→ 双缓冲 / 队列 ──→ 算法任务
事件通知：采集完成 ──→ 信号量 / 任务通知 ──→ 唤醒算法任务

数据回答“内容是什么”；事件回答“什么时候该处理”。
```

## 四、可靠性与资源保护

### 看门狗分层监护

看门狗用于发现系统长时间没有正常运行并采取恢复措施。硬件看门狗通常由独立电路计时，软件即使卡死也可能触发复位；软件任务看门狗则用于检查关键任务是否按预期执行，以便发现“系统没死、但某个功能已经卡住”的问题。

它常用于无人值守、需要长期稳定运行的工控设备、家电和汽车电子。看门狗应由真正能够代表系统健康状态的流程喂狗，不能因为某个独立死循环仍在喂狗而掩盖故障。

```text
关键任务 ── 定期上报“我正常” ──→ 软件监控任务 ──→ 喂硬件看门狗
采集正常 ─┐                                │
通信正常 ─┼── 任一长期缺失 ──→ 记录故障 / 不再喂狗
控制正常 ─┘                                │
                                           ▼
                                     硬件看门狗复位
```

### 故障隔离

故障隔离的目标是让一个功能模块的异常尽量停留在局部。例如通信模块失去连接时，核心控制功能仍可按安全策略运行；日志写入失败时，不应阻塞采集和控制任务。

常见做法包括任务独立运行、限制模块对全局资源的占用、对异常输入进行检查，以及为关键功能保留独立的运行路径。它适合包含多个功能模块的设备，尤其是“部分功能可暂时不可用、核心功能必须继续可控”的场景。

```text
通信模块异常 ──→ 标记“离线” ──→ 停止上报 / 周期重连
                                  │
                                  └── 核心控制任务继续按安全策略运行
```

隔离的重点不是忽略错误，而是将错误转换成可管理的局部状态。

### 冗余与双备份

冗余是为关键内容准备额外副本或替代路径，以应对单点故障。双备份参数区就是将重要配置保存到两个 Flash 区域；读取时校验有效性，某一区损坏后还能使用另一区恢复。

这种思想适合设备参数、升级镜像、关键配置和重要通信链路。冗余并不只是复制两份数据，还需要定义校验方式、版本选择规则和恢复流程，才能在异常断电或部分损坏时真正发挥作用。

```text
Flash 区 A：版本 12 + 校验正确  ─┐
                                  ├── 选择版本较新且校验通过的一份
Flash 区 B：版本 13 + 校验正确  ─┘

若写 B 时突然掉电，A 仍可作为可用副本。
```

### 分级异常处理与降级运行

分级异常处理不把所有错误都当成“必须立刻重启”。系统可以先记录和告警，再做局部重试；若仍失败，则关闭或限制相关功能，最后才在必要时整机复位。降级运行指核心功能以较低能力继续提供服务。

它适合网络短暂断开、传感器偶发读错、非关键外设失效等可恢复或局部故障。这样既避免小问题频繁重启，也能在问题无法立即恢复时保持系统处于可预期的安全状态。

```text
发生错误
   │
   ├─→ 记录 + 告警
   ├─→ 有限次数重试
   ├─→ 关闭局部功能 / 使用默认值（降级）
   └─→ 核心安全无法保证时，复位或进入安全停机
```

### 防雪崩与背压控制

当输入速度持续超过处理速度时，消息、日志、缓存或重试请求会不断堆积，最终耗尽内存、占满 CPU，连原本正常的功能也被拖垮，这就是常说的“雪崩”。背压控制是让系统在接近处理能力上限时限制输入、丢弃非关键内容或降低处理频率。

常见于突发通信数据、大量日志输出、云端断连后的重传和高频采集。队列长度上限、采样降频、日志限速、超时丢弃和优先保留关键消息，都是常见的实现方式。

```text
输入速率 >>> 处理速率
      │
      ▼
[有限队列] 满 ──→ 非关键消息丢弃 / 降频 / 通知发送方减速
      │
      └── 保留控制命令、故障告警等关键消息
```

### 最小化同步保护范围

互斥锁和临界区可以保护共享数据，但保护范围过大时，其他任务会长时间等待，甚至带来优先级反转或响应变慢。最小化保护范围就是只包住真正需要原子访问的那几行共享数据操作，其他计算和耗时工作放在保护区外完成。

它适用于多任务或中断与任务共享计数器、状态、缓冲区的场景。实践中除了缩短临界区，还应避免在持锁期间等待事件、访问慢速外设或调用可能阻塞的函数。

```c
lock();
local_count = shared_count;  // 只保护共享变量读写
unlock();

slow_calculation(local_count); // 耗时计算放到锁外
```

## 五、数据流思想

### 单向数据流

单向数据流将数据处理方向固定下来：数据从硬件采集进入，经过预处理、业务计算，最后形成控制输出或上报结果。每个环节只处理属于自己的那一步，尽量不反向修改前面环节的数据。

它能减少“同一份数据被多个模块随意改写”造成的混乱，也使调试时更容易追踪数据来源和变化过程。常用于传感器采集、数据记录、通信打包和控制算法等流水式业务；可与管道-过滤器架构结合使用。

```text
传感器 ─→ 原始数据 ─→ 滤波数据 ─→ 物理量 ─→ 控制量 / 上报报文
             │             │           │
          采集模块       算法模块    业务模块

每一步生成下一阶段结果，尽量不回头修改前一阶段的数据。
```

## 使用时的基础原则

- 中断负责快速响应和通知，耗时业务交给主循环或任务执行。
- 模块优先通过接口、队列或事件协作，避免到处直接读写全局变量。
- 高优先级任务只处理紧急且短小的工作，避免长期占用 CPU。
- 共享数据无法避免时，再选择合适的互斥锁、临界区或缓冲机制保护。
- 先根据“谁产生、谁消费、是否多人接收、数据是否很大”判断通信方式，而不是固定只用一种原语。
