# 嵌入式前端帧率调优与性能优化指南

## 第一章、为什么不能只看 FPS：建立正确的性能认知

在 PC、手机等平台上，我们习惯使用 60 FPS、90 FPS、120 FPS 描述界面流畅度。但在 MCU、RTOS 和嵌入式 Linux GUI 系统中，单纯观察 FPS 往往无法准确判断系统是否流畅。

原因在于嵌入式 UI 通常同时受到以下几个环节限制：

```text
业务数据更新
    ↓
GUI 对象更新
    ↓
脏区域计算
    ↓
GUI 绘制
    ↓
绘图缓冲
    ↓
DMA / SPI / RGB / MIPI 传输
    ↓
LCD 刷新
```

任何一个阶段变慢，都可能导致卡顿。

因此可以建立一个最基本的性能模型：

```text
实际 UI 刷新能力
≈ min(
    GUI 绘制能力,
    显示接口传输能力,
    LCD 刷新能力,
    系统调度能力
)
```

对于 SPI LCD，很多时候瓶颈首先出现在显示总线；对于 RGB、MIPI 等高速显示接口，瓶颈则更可能转移到 CPU/GPU 绘制、内存带宽或者 GUI 框架本身。

因此本文的核心原则不是：

> “怎样把 FPS 调高？”

而是：

> **先确定时间到底消耗在哪里，再针对真正的瓶颈优化。**

---

### 1.1、优化前先建立性能模型

#### 1.1.1、一帧到底经历了什么

以 LVGL 为例，一次界面更新大致经历：

```text
对象属性变化
    ↓
区域 invalid
    ↓
LVGL 刷新任务启动
    ↓
计算需要重绘的区域
    ↓
绘制到 draw buffer
    ↓
flush_cb()
    ↓
SPI / DMA 传输
    ↓
LCD 接收像素
    ↓
lv_disp_flush_ready()
```

于是一次刷新耗时可以粗略表示为：

```text
Tframe
=
Twait
+
Trender
+
Tflush
+
Tschedule
```

其中：

```text
Twait      等待下一次 GUI 刷新调度
Trender    GUI 绘制耗时
Tflush     像素数据传输耗时
Tschedule  RTOS 调度、抢占、中断等产生的额外时间
```

理论最大帧率约为：

```text
FPSmax ≈ 1000 / Tframe(ms)
```

但实际项目中，比平均 FPS 更值得关注的是：

```text
平均帧耗时
最大帧耗时
P95 帧耗时
P99 帧耗时
```

因为用户真正能感受到的往往不是平均值，而是偶尔出现的 100 ms、200 ms 长帧。

---

### 1.2、不要只定义一个 FPS

嵌入式 UI 性能调优至少需要观察四类指标。

| 指标             | 含义             | 主要用途         |
| -------------- | -------------- | ------------ |
| Refresh FPS    | 每秒真正完成多少轮有效刷新  | 观察总体刷新频率     |
| Frame Time     | 一次刷新需要多长时间     | 判断是否存在长帧     |
| Refresh Pixels | 每轮实际刷新多少像素     | 判断脏区域是否异常    |
| Flush Time     | 像素提交到 LCD 所需时间 | 判断显示总线是否成为瓶颈 |

另外建议记录：

```text
Render Time
Flush Count
CPU Usage
GUI Task CPU Usage
DMA Busy Time
最大帧耗时
P95 / P99 帧耗时
Free Heap
DMA Heap
PSRAM Free
```

---

### 1.3、静态页面 FPS 低，不一定是性能问题

很多 GUI 框架采用脏区域刷新。

如果页面完全静止：

```text
没有对象变化
→ 没有 invalid area
→ 不需要绘制
→ 不需要 flush
```

这时候 FPS 可能非常低，甚至接近 0。

这是正常现象。

因此判断 UI 流畅度时应该分别测试：

```text
静态页面
局部动态页面
连续动画
页面切换
列表滚动
图片切换
```

真正值得关注的是：

> 用户操作发生以后，新的画面多久真正出现在屏幕上。

这个指标比静态 FPS 有意义得多。

---

## 第二章、计算显示链路的理论上限

帧率调优的第一件事不应该是改代码，而应该拿计算器。

否则很容易出现一种嵌入式开发经典行为：

```text
硬件理论只能跑 30 FPS
↓
软件工程师努力优化到 28 FPS
↓
产品要求 60 FPS
↓
继续修改线程优先级
```

硬件不会因为会议开得够久就突破物理定律。

---

### 2.1、单帧数据量

假设 LCD 分辨率为：

```text
Width × Height
```

颜色格式为 RGB565：

```text
2 Byte / Pixel
```

则全屏像素数据量：

```text
FrameBytes
=
Width × Height × 2
```

例如：

```text
240 × 320 × 2
=
153600 Byte
≈ 150 KiB
```

---

### 2.2、SPI 理论帧率

假设：

```text
SPI Clock = 40 MHz
```

RGB565 每个像素需要：

```text
16 bit
```

理论全屏 FPS：

```text
FPS
=
SPI Clock
/
(Width × Height × BitsPerPixel)
```

代入：

```text
40,000,000
/
(240 × 320 × 16)

≈ 32.5 FPS
```

这还是完全理想的结果。

实际系统还存在：

```text
LCD 指令
地址窗口设置
SPI Transaction
DMA 调度
中断
任务切换
LVGL 绘制
锁竞争
缓存操作
```

所以真实全屏刷新达到：

```text
20~30 FPS
```

并不一定意味着软件存在严重问题。

---

## 第三章、建立性能观测与瓶颈判断体系

没有数据之前不要优化。

否则所谓性能优化很容易退化成：

```text
改一个宏
编译
感觉快了一点
再改一个宏
再感觉一下
```

这是性能玄学，不是性能工程。

---

### 3.1、推荐的埋点位置

至少记录以下阶段：

```text
Frame Begin
    ↓
Render Begin
    ↓
Render End
    ↓
Flush Begin
    ↓
DMA Complete
    ↓
Frame End
```

得到：

```text
Render Time
DMA / Flush Time
Total Frame Time
```

同时统计：

```text
Refresh Pixels
Flush Count
Invalid Area
```

---

### 3.2、日志不要逐帧打印

逐帧日志本身可能明显降低性能。

例如：

```text
30 FPS
×
每帧打印数条日志
```

串口、文件日志、锁竞争都可能成为新的瓶颈。

更加合理的方法是：

```text
每秒统计一次
```

示例：

```text
UI PERF
FPS              : 24
Avg Frame        : 35 ms
P99 Frame        : 51 ms
Avg Render       : 9 ms
Avg Flush        : 25 ms
Avg Pixels       : 26800
Avg Flush Count  : 2.4
```

---

### 3.3、如何通过数据判断瓶颈

这是整个性能优化过程中最重要的一步。

---

#### 3.3.1、DMA / Flush 耗时明显最高

例如：

```text
Frame Time : 42 ms

Render     : 8 ms
Flush      : 31 ms
Other      : 3 ms
```

说明：

```text
显示接口 / SPI
```

可能成为主要瓶颈。

优先检查：

```text
刷新面积
SPI Clock
DMA
绘图 Buffer
flush 实现
LCD 接口
```

---

#### 3.3.2、Render Time 明显最高

例如：

```text
Frame Time : 40 ms

Render     : 29 ms
Flush      : 8 ms
Other      : 3 ms
```

重点检查：

```text
PNG/JPEG 解码
大字体
中文字体
透明
阴影
圆角
渐变
旋转
缩放
Mask
复杂 Layout
大量控件
```

---

#### 3.3.3、Render 和 Flush 都很低，但界面仍然响应慢

例如：

```text
Render : 5 ms
Flush  : 8 ms
```

但点击以后：

```text
100 ms
```

界面才更新。

重点检查：

```text
lv_timer_handler()
GUI Task 调度
RTOS Tick
任务优先级
锁竞争
业务线程阻塞
消息队列
事件处理
```

---

#### 3.3.4、小范围变化却刷新大量像素

例如只是：

```text
温度：
25°C → 26°C
```

结果刷新：

```text
240 × 320
```

那么问题通常不是 SPI 太慢。

而是：

```text
脏区域管理
对象生命周期
页面架构
样式更新
```

出了问题。

---

## 第四章、第一优先级：减少刷新面积

对于 SPI LCD，这是软件层面最值得优先做的优化。

核心原则：

```text
少发送像素
通常比
更快发送像素

更加有效
```

假设全屏：

```text
240 × 320
```

需要发送：

```text
76800 Pixel
```

如果只是更新：

```text
100 × 20
```

只需要：

```text
2000 Pixel
```

数据量只有全屏：

```text
约 2.6%
```

这类优化收益通常远高于把：

```text
SPI 40 MHz
```

强行提高一点。

---

### 4.1、最常见的错误：频繁重建整个页面

很多嵌入式 UI 会写成：

```c
lv_obj_clean(lv_scr_act());

create_page();
```

逻辑非常简单，也非常容易维护。

性能也非常容易一起消失。

因为这意味着：

```text
删除对象
↓
重新创建
↓
重新布局
↓
重新绘制
↓
大量区域 invalid
↓
大量像素重新发送
```

对于 SPI 屏，最终往往演变成：

```text
局部数据发生变化
↓
整个页面重新刷新
```

---

### 4.2、页面架构如何减少无效刷新

推荐把页面拆成：

```text
Screen
├── Status Bar
├── Content
│   ├── Label
│   ├── Image
│   └── Widget
└── Navigation
```

数据更新时只修改对应控件。

例如：

```text
温度改变
```

只更新：

```text
temperature_label
```

而不是：

```text
重新创建首页
```

---

#### 4.2.1、高频页面可以保留对象树

对于首页、控制中心等高频访问页面，可以使用：

```text
create once
+
update
+
show / hide
```

而不是：

```text
destroy
+
create
+
destroy
+
create
```

这样能够减少：

```text
内存分配
对象初始化
Layout
Style
Invalid Area
```

---

#### 4.2.2、数据没有变化时不要更新 UI

例如：

```c
if (new_temperature != old_temperature) {
    lv_label_set_text(...);
}
```

避免每个周期都无条件：

```c
lv_label_set_text(...);
```

即使最终文字一样，也可能带来：

```text
布局计算
对象 invalid
重新绘制
```

---

## 第五章、第二优先级：显示接口优化

当刷新面积已经正常以后，再优化显示链路。

对于 SPI LCD，主要检查：

```text
SPI Clock
DMA
Transaction
max_transfer_sz
queue depth
flush_cb
```

---

### 5.1、SPI Clock 怎么调

不要直接：

```text
40 MHz → 80 MHz
```

然后看到 LCD 亮了就宣布优化成功。

推荐逐档测试：

```text
10 MHz
20 MHz
26 MHz
40 MHz
更高频率
```

具体取值根据：

```text
LCD Controller
PCB
SPI Driver
SoC
```

决定。

每一个频率至少验证：

```text
纯色全屏
文字
图片
渐变
动画
快速页面切换
长时间运行
Wi-Fi 工作
触摸工作
高温环境
```

重点观察：

```text
花屏
错色
闪屏
DMA Error
传输 Timeout
随机异常
```

---

### 5.2、max_transfer_sz 不等于越大越快

假设 LVGL Buffer：

```text
240 × 80
```

RGB565：

```text
240 × 80 × 2
=
38400 Byte
```

那么：

```text
max_transfer_sz
```

至少应满足：

```text
>= 38400 Byte
```

但设置成：

```text
300 KB
```

通常不会让 SPI 自动跑得更快。

因为 SPI 带宽没有变化。

反而可能增加：

```text
DMA 描述符
驱动资源
内部 RAM
```

占用。

基本原则：

```text
max_transfer_sz
≈
最大单次 Buffer 传输大小
```

即可。

---

## 第六章、第三优先级：正确理解双缓冲

双缓冲是嵌入式 UI 中最容易被误解的概念之一。

假设：

```text
Buffer A
Buffer B
```

理想流程：

```text
CPU Draw A
     ↓
DMA Send A

同时

CPU Draw B
```

形成：

```text
CPU 绘制
和
DMA 传输
```

一定程度上的并行。

---

### 6.1、双缓冲能解决什么

它主要减少：

```text
CPU 等待 DMA
```

使：

```text
Draw
和
Flush
```

形成流水线。

因此当：

```text
绘制耗时
≈
传输耗时
```

时，收益通常比较明显。

---

### 6.2、双缓冲不能解决什么

双缓冲不会增加：

```text
SPI 原始带宽
```

也不会自动消除：

```text
SPI LCD 扫屏
```

例如 ILI9341 这类显示方案，MCU 最终仍然需要：

```text
通过 SPI
逐像素写入 GRAM
```

即使 MCU 内存里已经准备好了完整一帧：

```text
240 × 320
```

LCD 仍然要等待数据一点点传过去。

因此：

```text
LVGL 双 Draw Buffer
≠
真正意义上的 Display Frame Buffer 双缓冲
```

---

### 6.3、为什么双全屏 Buffer 不一定值得

RGB565：

```text
240 × 320 × 2
=
153600 Byte
```

双全屏：

```text
153600 × 2
=
307200 Byte
```

大约：

```text
300 KiB
```

对于 MCU 来说已经相当可观。

如果 LCD 仍然使用 SPI：

```text
Full Frame
↓
SPI
↓
LCD
```

真正的瓶颈仍然存在。

因此 MCU + SPI LCD 更常见的方案是：

```text
双部分 Buffer
```

例如：

```text
双 20 行
双 40 行
双 80 行
```

---

### 6.4、Buffer 大小应该怎么选

建议测试：

```text
20 行
40 行
80 行
```

例如：

```text
240 × 40 × 2
=
19200 Byte / Buffer
```

双缓冲：

```text
38400 Byte
```

观察：

| 现象               | 判断             |
| ---------------- | -------------- |
| CPU 经常等 DMA      | 增大 Buffer 可能有效 |
| DMA 长时间忙         | Buffer 再大意义有限  |
| 内部 RAM 紧张        | 减小 Buffer      |
| Flush 次数非常多      | 可以适当增大 Buffer  |
| 大 Buffer FPS 没变化 | SPI 很可能已经成为瓶颈  |

因此 Buffer 选择本质上是在平衡：

```text
RAM
DMA 效率
Flush 次数
CPU 绘制
```

而不是追求最大。

---

## 第七章、第四优先级：降低 GUI 绘制成本

当显示链路不是主要瓶颈以后，就需要分析 Render Time。

重点关注以下特性。

---

### 7.1、Alpha 透明

透明对象通常涉及：

```text
Read
Blend
Write
```

而不是普通覆盖。

大量透明对象可能明显增加 CPU 运算。

---

### 7.2、阴影

阴影可能产生比对象本身更大的绘制范围。

例如一个：

```text
100 × 100
```

控件。

如果存在：

```text
20 px shadow
```

实际绘制范围可能明显扩大。

---

### 7.3、圆角

大量圆角对象会产生额外像素混合和 Mask 计算。

静态页面通常问题不大。

如果整个对象持续动画：

```text
圆角
+
透明
+
移动
```

CPU 压力会迅速增加。

---

### 7.4、图片是嵌入式 UI 的性能大户

重点检查：

```text
PNG
JPEG
图片缩放
图片旋转
透明图片
```

例如：

```text
800 × 600 PNG
```

实际只显示：

```text
200 × 150
```

如果运行时：

```text
Decode
+
Scale
+
Blend
```

就是典型的资源浪费。

更加合理的策略：

```text
PC 端预处理
↓
转换成实际显示尺寸
↓
转换为适合平台的格式
↓
运行时直接绘制
```

用存储空间换 CPU，往往是嵌入式设备非常划算的交易。

---

### 7.5、字体同样需要优化

大字体尤其是中文字体可能涉及：

```text
字体查找
字形解码
抗锯齿
Alpha Blend
```

需要重点关注：

```text
大字号
高频数字变化
大量中文
滚动文本
```

比如：

```text
CPU : 41%
```

每 50 ms 更新一次。

如果整个 Label 每次重新布局和绘制，就可能成为明显负担。

---

## 第八章、第五优先级：GUI 调度与系统级优化

显示和绘制都没有明显问题以后，再检查：

```text
GUI Task
RTOS
```

以 LVGL 为例：

```text
lv_timer_handler()
```

负责驱动：

```text
刷新
动画
Timer
输入设备
```

如果 GUI Task 长时间得不到调度：

```text
理论绘制能力再强
```

也没有用。

---

### 8.1、LV_DISP_DEF_REFR_PERIOD 怎么设置

例如：

```c
#define LV_DISP_DEF_REFR_PERIOD 30
```

意味着显示刷新检查周期约：

```text
30 ms
```

理论上约：

```text
33 Hz
```

如果修改为：

```text
16 ms
```

理论检查频率约：

```text
62.5 Hz
```

但这不意味着 LCD 自动达到：

```text
60 FPS
```

如果：

```text
SPI 全屏只能跑 25 FPS
```

那么将：

```text
30 ms → 16 ms
```

大多数情况下只是让 CPU 更频繁醒来查看一次：

```text
“总线还是忙着呢。”
```

---

### 8.2、LVGL Tick 越快不代表 FPS 越高

例如：

```text
LVGL Tick = 2 ms
```

改成：

```text
1 ms
```

可能提高：

```text
Timer
动画时间基准
```

精度。

但显示 FPS 最终仍然取决于：

```text
绘制
显示总线
GUI Task 调度
```

因此不能简单认为：

```text
Tick 越快
=
FPS 越高
```

---

### 8.3、RTOS Tick 与任务优先级

如果 FreeRTOS：

```text
100 Hz
```

那么 Tick：

```text
10 ms
```

普通：

```c
vTaskDelay()
```

调度粒度自然会受到影响。

提高：

```text
CONFIG_FREERTOS_HZ
```

有可能改善：

```text
GUI 响应延迟
```

但同时会增加：

```text
Tick Interrupt
Context Switch
调度成本
```

所以应该通过数据决定，而不是条件反射般把 Tick 调到更高。

---

### 8.4、GUI Task 优先级也不是越高越好

如果 GUI Task 优先级过低：

```text
Network
Sensor
Storage
```

可能频繁抢占 GUI。

表现为：

```text
偶发长帧
动画顿挫
点击响应慢
```

但如果 GUI 优先级过高：

```text
GUI
```

又可能反过来影响：

```text
Wi-Fi
Bluetooth
Sensor
Storage
```

正确方法是：

```text
trace
↓
确认抢占
↓
调整优先级
↓
回归整个系统
```

---

### 8.5、CPU 频率优化应该放在后面

例如 MCU：

```text
160 MHz
```

提高到：

```text
240 MHz
```

确实可能提高：

```text
LVGL Render
图片解码
字体绘制
```

但如果测出来：

```text
Render 5 ms
SPI   30 ms
```

把 CPU 加速 50%，最终可能只变成：

```text
Render 3 ms
SPI   30 ms
```

整帧：

```text
35 ms → 33 ms
```

收益很有限。

因此：

```text
CPU 提频
```

应该建立在确认 CPU 绘制成为瓶颈之后。

---

## 第九章、一套推荐的帧率调优流程

整个流程可以归纳成：

```text
理论分析
↓
建立监控
↓
固定场景
↓
采集数据
↓
判断瓶颈
↓
单变量优化
↓
重新测试
↓
回归稳定性
```

这是本文最核心的方法论。

---

### 9.1、第一步：固定基线配置

记录：

```text
CPU Frequency
Display Resolution
Pixel Format
SPI / RGB / MIPI Clock
Draw Buffer Size
Draw Buffer Count
Refresh Period
RTOS Tick
GUI Task Priority
Compiler Optimization
```

同时记录：

```text
FPS
Avg Frame
P95 Frame
P99 Frame
Render Time
Flush Time
Refresh Pixels
Memory
```

之后所有优化都与这个版本比较。

---

### 9.2、第二步：建立标准测试场景

建议至少建立四类 Benchmark。

---

#### 9.2.1、场景 A：局部文本刷新

例如：

```text
时间
温度
CPU 占用
```

每秒刷新。

目的：

```text
测试局部刷新效率
```

---

#### 9.2.2、场景 B：连续动画

例如：

```text
Progress Bar
Slider
数字变化
```

目的：

```text
测试持续刷新性能
```

---

#### 9.2.3、场景 C：页面切换

例如：

```text
Home
→ Setting
→ Control
→ Album
→ Home
```

目的：

```text
测试大面积刷新
页面创建
内存峰值
```

---

#### 9.2.4、场景 D：系统压力

同时运行：

```text
Wi-Fi
MQTT
Sensor
Storage
GUI Animation
```

目的：

```text
测试真实系统中的调度竞争
```

---

### 9.3、第三步：判断瓶颈属于哪一层

可以使用下面的决策树。

```text
UI 卡顿
│
├── Refresh Pixels 很大？
│      │
│      ├── YES → 优化 invalid area / 页面结构
│      │
│      └── NO
│
├── Flush Time 很高？
│      │
│      ├── YES → SPI / DMA / Display
│      │
│      └── NO
│
├── Render Time 很高？
│      │
│      ├── YES → GUI 绘制复杂度
│      │
│      └── NO
│
└── 调度延迟高？
       │
       ├── YES → RTOS / Priority / Lock
       │
       └── NO → 检查业务逻辑
```

---

### 9.4、第四步：一次只修改一个变量

例如测试 Buffer：

```text
Baseline
双 20 行

Test A
双 40 行

Test B
双 80 行
```

其他参数完全不变。

否则同时修改：

```text
SPI Clock
Buffer
CPU
Priority
Tick
```

最后即使 FPS 提高，也无法判断：

```text
究竟是谁起作用。
```

无法解释的优化，也就很难维护。

---

### 9.5、第五步：不要只比较平均 FPS

假设：

优化前：

```text
Average FPS = 27
P99 Frame   = 80 ms
```

优化后：

```text
Average FPS = 26
P99 Frame   = 45 ms
```

虽然平均 FPS 下降了：

```text
1 FPS
```

但用户实际感受很可能明显变好。

原因是：

```text
长帧减少了。
```

UI 性能最终应该围绕：

```text
稳定性
响应延迟
帧时间波动
```

评价，而不是执着于漂亮的整数 FPS。

---

### 9.6、第六步：最后做系统级优化

当：

```text
刷新面积
SPI
Buffer
绘制
```

都合理以后，再优化：

```text
RTOS Tick
Task Priority
CPU Frequency
PSRAM
Compiler Optimization
Cache
```

这些属于：

```text
系统级优化
```

通常不应该成为第一个动作。

---

## 第十章、案例：ESP32-S3 + ILI9341 + LVGL

下面使用一个实际配置说明整个分析过程。

硬件配置：

```text
MCU        ESP32-S3
LCD        ILI9341
Resolution 240 × 320
Color      RGB565
SPI        40 MHz
CPU        160 MHz
```

LVGL：

```text
Double Buffer
240 × 80 × 2
```

单 Buffer：

```text
240 × 80 × 2
=
38400 Byte
```

双 Buffer：

```text
76800 Byte
```

---

### 10.1、计算理论上限

全屏数据量：

```text
240 × 320 × 16
=
1,228,800 bit
```

SPI：

```text
40,000,000 bit/s
```

理论：

```text
≈ 32.5 FPS
```

因此如果实际全屏：

```text
25 FPS
```

首先不能直接判断：

```text
LVGL 性能差
```

因为已经比较接近显示链路的物理上限。

---

### 10.2、分析页面切换扫屏

如果页面切换时出现：

```text
从上往下逐段更新
```

需要判断：

```text
LVGL 是否按照多个 Buffer
逐块 Flush 到 LCD
```

如果 LCD 没有：

```text
Frame Buffer Address Switch
```

那么即使 MCU 使用双缓冲：

```text
SPI
```

仍然必须逐段传输。

因此这并不是简单把：

```text
双 80 行
→
双全屏
```

就一定能够解决的问题。

---

### 10.3、优化顺序

这个平台推荐按照：

```text
① 减少页面重建
② 减少刷新像素
③ 验证 SPI Clock
④ 调整 Draw Buffer
⑤ 优化图片和复杂控件
⑥ 检查任务调度
⑦ 最后考虑 CPU 提频
```

进行。

这套顺序同样适用于大量：

```text
MCU
+
SPI LCD
+
LVGL
```

项目。

## 第十一章、不同显示架构的优化重点并不相同

### 11.1、MCU + SPI LCD

重点：

```text
刷新面积
SPI 带宽
DMA
Buffer
```

---

### 11.2、MCU + RGB LCD

重点逐渐转向：

```text
Frame Buffer
SDRAM 带宽
DMA2D
Cache
CPU Render
```

---

### 11.3、Embedded Linux + DRM / Framebuffer

重点更多是：

```text
CPU/GPU Render
Framebuffer
VSync
Compositor
Memory Bandwidth
```

---

### 11.4、MIPI DSI

由于：

```text
显示传输能力
```

明显高于普通 SPI，瓶颈可能进一步向：

```text
GPU
DDR
GUI Render
```

迁移。

因此不能把：

```text
SPI LCD 的优化经验
```

机械套用到：

```text
所有显示架构。
```

真正通用的是：

> **建立整条显示链路的性能模型。**

## 第十二章、帧率优化 Checklist

遇到 UI 卡顿时，可以按下面顺序检查。

```text
[ ] 当前 FPS 的定义是什么？
[ ] 单帧数据量是多少？
[ ] 显示接口理论 FPS 是多少？
[ ] 平均帧耗时是多少？
[ ] P99 帧耗时是多少？
[ ] Render Time 是多少？
[ ] Flush Time 是多少？
[ ] 实际刷新了多少 Pixel？
[ ] 是否频繁全屏 Invalid？
[ ] 页面是否频繁 Destroy / Create？
[ ] SPI / RGB / MIPI 是否达到稳定频率？
[ ] DMA 是否正常使用？
[ ] Draw Buffer 是否合理？
[ ] 图片是否运行时缩放？
[ ] 是否大量使用透明、阴影和渐变？
[ ] GUI Task 是否频繁被抢占？
[ ] 是否存在锁竞争？
[ ] CPU 是否真的成为瓶颈？
[ ] 优化后是否重新测量？
[ ] 是否进行了长时间稳定性测试？
```

## 第十三章、面试问答精选

面试官真正想判断的通常不是：

```text
你会不会改 LVGL 宏。
```

而是：

```text
你是否真正理解显示链路
你是否具备性能分析能力
你是否能够用数据定位问题
你是否理解软硬件边界
```

下面是比较值得准备的问题。

---

### 13.1、FPS 由什么决定

推荐回答思路：

```text
GUI Render
Display Transfer
LCD Refresh
OS Scheduling
```

实际 FPS 取决于其中最慢的环节。

可以回答：

> 我通常把嵌入式 UI 刷新拆成 GUI 绘制、显示传输和任务调度三个主要阶段。实际帧率受最慢环节限制，所以优化前需要分别测量 Render Time、Flush Time 和调度延迟，而不是直接修改刷新周期。

---

### 13.2、如何判断 SPI 是不是瓶颈

首先计算理论吞吐。

例如：

```text
240 × 320
RGB565
40 MHz SPI
```

理论全屏：

```text
约 32.5 FPS
```

然后测：

```text
Render Time
Flush Time
```

如果：

```text
Flush Time >> Render Time
```

并且真实 FPS 已经接近理论 SPI 上限，就基本可以判断：

```text
显示总线是主要瓶颈。
```

---

### 13.3、为什么不能只看 FPS

因为：

```text
静态页面可以没有刷新
```

因此：

```text
低 FPS
```

并不一定代表卡顿。

同时平均 FPS 也可能掩盖：

```text
偶发长帧。
```

更合理的指标应该包括：

```text
Frame Time
P95 / P99
Refresh Pixels
Render Time
Flush Time
```

---

### 13.4、为什么双缓冲能提高性能

因为它可以让：

```text
CPU Draw
```

和：

```text
DMA Transfer
```

形成一定程度上的并行。

例如：

```text
DMA Send A
```

时：

```text
CPU Draw B
```

减少等待。

---

### 13.5、双缓冲为什么不能解决 SPI LCD 扫屏

因为 LVGL Draw Buffer 只是：

```text
MCU 端绘图缓存
```

LCD 仍然需要：

```text
SPI
```

逐步接收像素。

它没有实现：

```text
Frame Buffer Address Switch
```

所以无法像某些 RGB/LTDC/GPU 架构一样：

```text
整帧瞬间切换。
```

---

### 13.6、Draw Buffer 是不是越大越好

不是。

Buffer 增大会：

```text
减少 Flush 次数
```

但同时增加：

```text
RAM 占用
DMA 内存压力
```

而且如果：

```text
SPI 已经满载
```

继续增加 Buffer 通常不会提高最终 FPS。

所以需要通过：

```text
20 / 40 / 80 行
```

这样的实验找到平衡点。

---

### 13.7、页面卡顿应该首先优化什么

不能一概而论。

应该先测：

```text
Render
Flush
Refresh Pixels
Scheduling
```

但对于：

```text
SPI LCD
```

通常应该优先检查：

```text
Invalid Area
```

是否过大。

因为减少像素传输往往比提高 SPI 频率更加直接。

---

### 13.8、为什么提高 CPU 主频以后 FPS 没明显提高

因为瓶颈可能不在 CPU。

例如：

```text
Render 5 ms
Flush 30 ms
```

CPU 提速：

```text
5 ms → 3 ms
```

整帧只减少：

```text
2 ms
```

此时：

```text
SPI
```

才是主要瓶颈。

---

### 13.9、为什么降低 LVGL 刷新周期没有明显作用

例如：

```text
30 ms → 16 ms
```

只意味着：

```text
更频繁检查是否需要刷新。
```

它并不会增加：

```text
SPI
CPU
LCD
```

本身的处理能力。

如果单帧实际需要：

```text
40 ms
```

那么刷新周期设置成：

```text
16 ms
```

也不可能真正得到：

```text
60 FPS。
```

---

### 13.10、为什么页面切换最好避免整页重新创建

因为重新创建意味着：

```text
Object Create
Memory Allocate
Style
Layout
Invalid
Render
Flush
```

会带来：

```text
CPU
内存
显示传输
```

三方面的额外开销。

高频页面更加合理的策略通常是：

```text
保留对象树
+
更新数据
+
控制显示隐藏
```

---

### 13.11、如何设计一次完整的性能优化实验

一个比较完整的回答应该包含：

```text
建立 Baseline
↓
固定 Benchmark
↓
增加性能埋点
↓
确定瓶颈
↓
一次修改一个变量
↓
重新测量
↓
比较 P99 / FPS / Memory
↓
压力测试
↓
稳定性回归
```

这比回答：

```text
加大 Buffer
提高 CPU
提高 SPI
```

更能体现实际工程能力。

---

### 13.12、如何描述一次完整的 UI 性能优化经历

可以按照：

```text
问题
→
数据
→
判断
→
方案
→
结果
```
