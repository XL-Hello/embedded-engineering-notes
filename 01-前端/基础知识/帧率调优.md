# 本项目 UI 帧率性能调优：面试操作指南

## 1. 先给出结论

本项目是 ESP32-S3 + ILI9341 SPI 屏 + LVGL 的架构。UI 帧率不是单一参数决定，而取决于：

```text
实际 UI 刷新率
≈ min(SPI 像素传输能力、LVGL 绘制能力、刷新调度频率)
```

当前最主要的限制通常是 SPI 全屏传输，而不是 LVGL 的 `lv_timer_handler()`。

项目参数：

| 项目 | 当前配置 |
|---|---:|
| LCD 分辨率 | 240 × 320 |
| 像素格式 | RGB565，2 B/像素 |
| 单屏数据量 | 153,600 B |
| SPI 时钟 | 40 MHz |
| 双绘图缓冲 | 2 × 240 × 80 像素 |
| 双缓冲总内存 | 76,800 B |
| 单次最大 SPI 传输 | 38,400 B |
| LVGL 默认刷新周期 | 30 ms |
| FreeRTOS tick | 100 Hz，即 10 ms |
| CPU 主频 | 160 MHz |
| PSRAM | 40 MHz |

40 MHz SPI 下，全屏仅传输像素数据的理论上限约为：

```text
40,000,000 / (240 × 320 × 16) ≈ 32.5 FPS
```

实际还要扣除 LCD 命令、DMA 调度、LVGL 绘制、任务切换等开销，因此全屏实际帧率低于该值是正常的。

---

## 2. 面试中如何定义“帧率”

本项目应区分两种指标：

| 指标 | 含义 | 用途 |
|---|---|---|
| 自定义 Refresh FPS | 一秒内完成多少次 LVGL 刷新周期 | 判断屏幕实际发生多少次更新 |
| LVGL 内置 FPS | 大面积刷新时的 LVGL 绘制/刷新吞吐估算 | 判断 LVGL 渲染性能 |
| 帧耗时 | 一次刷新从开始绘制到 DMA 完成的时间 | 定位 CPU 还是 SPI 瓶颈 |
| 刷新像素数 | 本轮实际发送的像素量 | 判断是否出现不必要的大面积重绘 |

推荐回答：

> 我不会只看 FPS。静态页面的 FPS 低并不代表卡顿，因为屏幕没有内容需要刷新。对嵌入式 UI，更重要的是交互触发后到像素真正完成传输的延迟，以及动画期间连续更新的稳定性。

---

## 3. 建立性能观测能力

### 3.1 现有项目中的两套 FPS

项目已有：

- 自定义 FPS：`components/adapters/lvgl_port/lv_port_disp.c` 的 `disp_monitor_callback()`
- LVGL 内置性能监视器：`LV_USE_PERF_MONITOR = 1`
- 首页显示的自定义 FPS：`home_temp_humidity.c`

自定义 FPS 的计数点是 `monitor_cb`，它在一轮有脏区域的 LVGL 刷新完成后触发。一次刷新可包含多个脏矩形、多个绘图缓冲块和多次 SPI DMA，但总共计为一次。

### 3.2 建议补充的埋点

面试中可以说会增加以下指标：

```text
刷新开始时间
绘制耗时
SPI DMA 提交到完成的耗时
本轮刷新像素数
本轮 flush 次数
最大/平均/99 分位帧耗时
```

推荐把日志设计为按秒汇总，不要逐帧打印，否则日志本身会拖慢 UI：

```text
Refresh FPS: 18
Average refresh time: 42 ms
P99 refresh time: 58 ms
Average pixels refreshed: 21,600
Average flush count: 2.3
```

判断原则：

| 现象 | 可能瓶颈 |
|---|---|
| DMA 耗时占绝大部分 | SPI 时钟、LCD 总线、全屏刷新 |
| 绘制耗时高、DMA 耗时较低 | 字体、PNG、透明、阴影、圆角、复杂布局 |
| CPU 和 DMA 都不高，但响应慢 | `lv_timer_handler()` 调度、任务优先级、FreeRTOS tick |
| 小改动却频繁全屏刷新 | 脏区域管理或页面实现方式有问题 |

## 4. 第一优先级：控制刷新面积

这是 SPI 屏最有效的软件优化。

### 原则

```text
优先减少发送像素数，
其次才是提高发送速度。
```

本项目整屏是 153,600 B。若只更新一个 100 × 20 的数值区域，则仅约 4,000 B，传输量只有全屏的约 2.6%。

### 项目中的典型问题

多个页面使用：

```c
lv_obj_clean(lv_scr_act());
```

然后重新创建整个页面，例如首页、控制中心、设置页、相册页。这样会删除旧控件、创建新控件，并使大部分甚至整屏区域失效。

在 ILI9341 SPI 屏上，LVGL 会按缓冲条带逐段发送到 LCD，所以能看到从上到下的“扫屏”。

### 优化策略

- 仅修改发生变化的 `label`、`bar`、`image`，不要重复创建父容器。
- 数据未变化时，不调用 `lv_label_set_text()`、不改样式。
- Tab 切换只重建内容区，不重建状态栏、时钟和底部导航。
- 对首页、设置页等高频往返页面，可保留对象树，通过隐藏/显示或更新数据恢复。
- 避免对全屏父对象重复设置背景、尺寸、样式。
- 图片在加载前缩放至显示尺寸，避免运行时缩放大图。
- 动画只使必要对象失效，避免动画期间反复重绘整个页面。

面试表达：

> 我首先看 invalidation 面积。对 SPI 屏，减少一半刷新像素，通常比优化一半绘制指令更直接，因为总线传输是硬上限。

## 5. 第二优先级：SPI 传输调优

### 5.1 SPI 时钟

当前参数为：

```c
#define LCD_PIXEL_CLOCK_HZ (40 * 1000 * 1000)
```

调优方式是逐档测试：

```text
10 MHz → 20 MHz → 26 MHz → 40 MHz
```

每一档验证：

- 全屏颜色填充是否花屏；
- 图片、文字和渐变是否错色；
- 长时间连续刷新是否稳定；
- DMA 是否有报错或超时；
- Wi‑Fi 工作时是否稳定。

不能只以“能点亮”为标准；应连续运行页面切换、列表滚动、图片切换和传感器刷新场景。

### 5.2 `max_transfer_sz`

当前值由：

```c
LCD_H_RES × LCD_TEST_LINES × sizeof(uint16_t)
```

计算得到。当前 80 行即：

```text
240 × 80 × 2 = 38,400 B
```

原则：

```text
max_transfer_sz >= 单个 LVGL 绘图缓冲的最大字节数
```

它不应小于缓冲区，否则可能提交失败；也不应随意远大于缓冲区，因为它不提高 SPI 带宽，只会增加驱动的 DMA 资源开销。

### 5.3 `trans_queue_depth`

当前为 `10`。但本项目当前的 `flush_cb` 是 DMA 完成后才调用 `lv_disp_flush_ready()`，LVGL 不会无限制连续提交颜色传输，所以队列深度不是当前核心瓶颈。

面试可回答：

> 队列深度只在软件能持续准备并提交多笔 DMA 事务时才可能提升流水线利用率。当前 LVGL port 的同步完成模型下，盲目从 10 调到更大不会提升实际帧率。

## 6. 第三优先级：LVGL 双缓冲与帧缓冲配置

### 6.1 当前双缓冲

当前为双 80 行缓冲：

```text
每块：240 × 80 × 2 = 38,400 B
总计：76,800 B
```

优势：

- DMA 发送缓冲 A 时，LVGL 可绘制缓冲 B；
- 降低 CPU 绘制与 SPI 传输之间的等待；
- 有利于连续大面积刷新。

限制：

- 不会改变 SPI 的原始传输带宽；
- 不会让 ILI9341 实现“原子换帧”；
- 整页切换仍会显示条带式刷新。

### 6.2 推荐配置策略

| 场景 | 推荐绘图缓冲 |
|---|---|
| 内部 RAM 紧张 | 双 20 行 |
| 默认平衡配置 | 双 40 行 |
| 页面绘制较复杂且 RAM 充足 | 双 80 行 |
| SPI ILI9341 页面切换 | 不建议双全屏缓冲 |

双 40 行的内存：

```text
240 × 40 × 2 × 2 = 38,400 B
```

它通常是内部 RAM、DMA 流水与分块开销之间的均衡点。

### 6.3 不建议双全屏缓冲

双全屏 RGB565 缓冲需要：

```text
240 × 320 × 2 × 2 = 307,200 B
```

对当前 SPI ILI9341 没有帧缓冲地址切换能力的场景，收益非常有限。即使在 MCU 内存中准备好完整画面，仍要经 SPI 逐段写到 LCD，扫屏现象不会消失。

## 7. 第四优先级：LVGL 调度参数

### 7.1 `LV_DISP_DEF_REFR_PERIOD`

当前：

```c
#define LV_DISP_DEF_REFR_PERIOD 30
```

它是 LVGL 显示刷新定时器的默认周期，理论刷新检查上限约 33 FPS。

调优原则：

- 静态/普通仪表盘 UI：30 ms 通常合适；
- 快速动画：可测试 16~20 ms；
- SPI 明显无法跟上时：调得比传输能力更快没有意义，只会提高 CPU 唤醒频率。

### 7.2 `lv_timer_handler()`

当前任务会读取 `lv_timer_handler()` 的返回值，再动态 `vTaskDelay()`；它并不是固定 30 ms 周期调用。

影响它的参数包括：

- `LVGL_TICK_PERIOD_US = 2000`
- FreeRTOS tick = 10 ms
- `LVGL_IDLE_FALLBACK_DELAY_MS = 10`
- LVGL 任务优先级 = 5
- LVGL 定时器周期，如时钟 1 s、Wi‑Fi 刷新 300 ms、性能刷新 250 ms

关键结论：

> 把 LVGL tick 从 2 ms 改成 1 ms，通常不会直接提升显示 FPS；因为当前 FreeRTOS 的任务延时粒度是 10 ms，且最终还受 SPI 和绘制耗时限制。

### 7.3 FreeRTOS tick 与任务优先级

可优化但需谨慎：

- 提高 `CONFIG_FREERTOS_HZ` 可减小调度延迟；
- 提高 LVGL 任务优先级可改善交互响应；
- 但两者都会增加系统调度成本或挤占 Wi‑Fi、传感器等任务。

面试回答：

> 我不会直接把所有优先级拉高，而是先看 LVGL 任务是否因抢占而错过刷新窗口，再做局部调整并验证 Wi‑Fi 和输入任务的实时性。

---

## 8. 第五优先级：降低 LVGL 绘制成本

本项目中，LVGL 动态对象、文本和图片解码内存使用 PSRAM；绘图 DMA 双缓冲使用内部 DRAM。

重点排查：

- 大尺寸 PNG 解码；
- 运行时图片缩放；
- 半透明对象；
- 阴影、圆角、渐变；
- 旋转、缩放、遮罩；
- 高频更新的大字体、中文标签；
- 大范围样式修改；
- Wi‑Fi 列表扫描结果的频繁整体重建。

项目相关配置：

| 参数 | 当前值 | 调优建议 |
|---|---:|---|
| `LV_DRAW_COMPLEX` | 1 | 不需要阴影、渐变、变换时可关闭或减少使用 |
| `LV_LAYER_SIMPLE_BUF_SIZE` | 24 KiB | 复杂透明对象较多时影响绘制效率与 PSRAM 压力 |
| `LV_IMG_CACHE_DEF_SIZE` | 0 | 重复显示 PNG/JPG 时可评估开启缓存 |
| `LV_SHADOW_CACHE_SIZE` | 0 | 阴影频繁使用时可评估缓存 |
| CPU 主频 | 160 MHz | SPI 已优化后，CPU 绘制仍不足时可测试 240 MHz |
| 编译优化 | Debug | 发布固件应验证性能优化构建后的帧耗时变化 |

## 9. 推荐的实际调优流程

### 步骤 1：固定基线

记录以下数据：

```text
SPI 时钟
绘图缓冲行数和数量
max_transfer_sz
自定义 Refresh FPS
LVGL 内置 FPS
全屏切页耗时
局部文本更新耗时
空闲堆、内部 DMA 堆、PSRAM 剩余量
```

### 步骤 2：构造三类测试场景

| 场景 | 目的 |
|---|---|
| 静态首页，每秒更新时间 | 验证局部更新成本 |
| 连续数值/进度条动画 | 验证中等脏区刷新稳定性 |
| 首页、控制中心、相册连续切换 | 验证全屏刷新、扫屏与峰值内存 |

### 步骤 3：先调 SPI 时钟

逐档提高 SPI 时钟，并在每档记录：

```text
整页切换耗时
画面稳定性
平均/99 分位帧耗时
Wi‑Fi 与触摸是否异常
```

### 步骤 4：调整绘图缓冲

以双 40 行为基准，测试双 20、40、80 行：

| 观察项 | 判断 |
|---|---|
| CPU 在等待 DMA | 增大缓冲可能有效 |
| DMA 长时间忙、CPU 不忙 | 增大缓冲收益有限，应优先提高 SPI 或减小刷新面积 |
| 内部 RAM 紧张 | 减少缓冲行数 |
| 单次传输超限 | 缓冲行数与 `max_transfer_sz` 不匹配 |

### 步骤 5：处理最大脏区来源

用刷新像素数、`flush` 次数和页面切换耗时定位：

- 小数据变化却整屏刷新：修正对象层级和失效范围；
- 页面创建耗时高：保留对象、延迟加载、缓存图片；
- 图片页慢：预缩放、改用更易绘制的资源格式；
- 动画慢：减少透明/阴影/缩放，缩小动画对象范围。

### 步骤 6：最后调调度与 CPU

仅当 SPI 和失效面积已优化后，再评估：

- LVGL 刷新周期；
- FreeRTOS tick；
- 任务优先级；
- CPU 频率；
- 发布级编译优化；
- PSRAM 时钟与图片缓存。

## 10. 面试中的标准回答模板

> 我会把嵌入式 UI 帧率拆成显示传输、LVGL 渲染和任务调度三部分分析。这个项目使用 240×320 RGB565 SPI ILI9341，一屏是 153.6 KB，因此全屏刷新首先受 SPI 带宽限制。  
>
> 我不会只看 LVGL 内置 FPS，还会通过 `monitor_cb` 统计实际完成的刷新周期，结合刷新像素数、DMA 耗时和 99 分位帧耗时判断瓶颈。  
>
> 调优顺序是先减少脏区域和不必要的整页重建，再确认 SPI 时钟稳定并配置合适的双缓冲，最后才处理复杂绘制、PNG 解码、任务优先级和 CPU 频率。  
>
> 对当前 SPI 屏，双缓冲的价值是让绘制与 DMA 并行，不是实现无扫屏换页；完全不同的全屏页面仍需逐段写入 LCD。要实现真正原子换帧，需要具备帧缓冲扫描与地址切换能力的 RGB/LTDC 类显示架构。
