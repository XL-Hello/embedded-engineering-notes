# 嵌入式前端 性能优化

> 目标：整理嵌入式 GUI 在渲染、内存、CPU、显示链路和页面架构上的性能优化方法，重点说明每种方法解决什么问题、适用条件、常见副作用，以及面试时如何结合实际项目表达。
>
> 说明：本文以 LVGL、AWTK 等保留模式嵌入式 GUI 框架为主要背景，但脏区域、缓冲、DMA、资源生命周期和 UI 线程模型同样适用于自研 GUI。FrameBuffer、像素格式、对象树、基础脏矩形等知识可先结合《嵌入式前端基础知识》阅读。

## 1. 先建立性能分析框架

嵌入式 UI 卡顿、掉帧、花屏或内存逐渐下降，不能一上来就“开 DMA”或“降低分辨率”。先把一帧拆开，确定瓶颈在哪一段。

```text
业务状态变化 / 输入事件
        ↓
控件属性变化、布局计算、生成脏区
        ↓
CPU / GPU / 2D 引擎绘制 draw buffer
        ↓
DMA / CPU 将像素传到 FrameBuffer 或 LCD
        ↓
LCD 扫描显示
```

一帧的总耗时可以粗略理解为：

```text
T_frame = T_layout + T_draw + T_blend + T_decode + T_flush + T_wait
```

- `T_layout`：控件尺寸、位置、Flex/Grid 等布局计算时间。
- `T_draw`：填充、画线、文字、图片、圆角、阴影等软件绘制时间。
- `T_blend`：透明度、图层混合、颜色转换带来的额外时间。
- `T_decode`：PNG/JPEG、压缩图片、字体字形的解码时间。
- `T_flush`：把像素交给 LCD、FrameBuffer、DRM 或显示控制器的时间。
- `T_wait`：等 DMA、等 VSYNC、等锁、等待高优先级任务释放 CPU 的时间。

目标帧率决定预算：

| 目标 | 单帧预算 | 典型场景 |
| --- | ---: | --- |
| 60 FPS | 16.7 ms | 手势、快速滚动、较流畅动画 |
| 30 FPS | 33.3 ms | 一般仪表盘、页面转场 |
| 15 FPS | 66.7 ms | 参数刷新、低功耗界面 |
| 静态页 | 按需刷新 | 设置页、信息展示页 |

注意：嵌入式设备不必所有页面都追求 60 FPS。没有动画、数据变化慢的页面，重点是按需刷新和低功耗；只有手势、滚动和关键动画页面才需要严格的帧预算。

### 1.1 先测什么

至少建议记录以下指标：

| 指标 | 用途 | 典型异常 |
| --- | --- | --- |
| FPS / 帧间隔 | 判断用户感知流畅度 | 帧间隔抖动比平均 FPS 更影响手感 |
| 单帧绘制时间 | 判断 CPU / 2D 绘制是否重 | 圆角、阴影、文字、透明混合过多 |
| 单帧 flush 时间 | 判断显示链路是否慢 | SPI 带宽不足、DMA 未使用、全屏传输 |
| 脏区数量和总面积 | 判断是否误刷新大范围 | 一个小数字变化却触发全屏刷新 |
| UI 线程 CPU 占用 | 判断是否被业务阻塞或绘制打满 | 回调中做 I/O、解码、日志 |
| 堆总剩余和最大连续块 | 判断泄漏和碎片 | 总空闲尚可但大块 buffer 申请失败 |
| UI 任务栈高水位 | 判断栈是否不足 | 大图片解码或深层回调后异常 |

排查时优先用 GPIO 翻转、系统 trace、框架性能监控或时间戳，在 `layout`、`render`、`flush_cb`、DMA 完成中断等位置打点。不要只根据“感觉卡”判断。

### 1.2 一个重要的带宽估算

全屏刷新需要传输的数据量为：

```text
带宽 = 宽 × 高 × 每像素字节数 × FPS
```

例如 800 × 480、RGB565（2 B/像素）、30 FPS：

```text
800 × 480 × 2 × 30 ≈ 23 MB/s
```

这还是纯像素数据，不含协议命令、等待时间和软件开销。若屏幕通过 SPI 接口连接，实际有效吞吐低于标称时钟换算值，全屏 30 FPS 往往就不现实。因此，脏区刷新通常比微调几行绘制代码更有效。


## 2. 渲染优化

渲染优化的核心是：**少画像素、少做每像素计算、让适合的硬件去画。**

### 2.1 脏区裁剪和合并

脏区（dirty area / invalid area）是本帧发生变化、需要重新绘制并刷新的矩形区域。

例如一个 30 × 20 的数字区域变化，理想情况只重绘其附近几十像素，而不是重绘 800 × 480 的整屏。脏区优化会同时减少：

- 控件遍历和绘制像素数。
- CPU 填充、混合、颜色转换时间。
- draw buffer 到 LCD / FrameBuffer 的传输量。
- 总线占用和功耗。

典型流程：

```text
控件属性变化
  -> 将旧区域和新区域标记为 dirty
  -> 与父容器裁剪区域求交集
  -> 合并相邻或重叠的 dirty rect
  -> 只绘制和 flush 合并后的区域
```

工程要点：

- 控件移动时，旧位置和新位置都要失效，否则原位置会留下残影。
- 脏区要受父容器裁剪；不可见区域、被完全遮挡区域不应再绘制。
- 透明、阴影、抗锯齿边缘可能让实际影响区域大于控件本身，需要包含扩展边界。
- 脏区太碎时，频繁设置 LCD 窗口和启动 DMA 的固定开销可能超过收益。框架通常会把相近矩形合并；达到阈值后直接全屏刷新也可能更划算。
- 不要在高频定时器里无条件调用全屏 `invalidate`。数据没变就不刷新，数值变化时只失效对应控件。

面试表达：

> 我先统计每帧脏区面积和 flush 耗时。发现只是状态文本变化却走了整屏刷新后，把刷新入口收敛到具体控件，页面容器不再无条件失效；同时保留旧位置和新位置的脏区。这样既减少 CPU 绘制，也减少 LCD 总线传输。对于碎片化脏区，会根据框架的合并阈值平衡多次小刷和一次大刷。

### 2.2 减少 Alpha 叠加和复杂特效

不透明填充通常只需要直接写像素；Alpha 混合需要读取背景像素，再做每像素计算：

```text
C_out = α × C_foreground + (1 - α) × C_background
```

如果存在多层半透明对象，底层可能被反复读取和混合。再叠加圆角、阴影、渐变、模糊、抗锯齿，软件渲染的负担会很快升高。

常见优化：

- 大面积背景尽量使用不透明颜色或预合成图片，避免运行时多层半透明覆盖。
- 避免全屏蒙层下面还持续刷新复杂页面；弹窗出现后可暂停下层动画或缓存背景。
- 阴影、模糊、渐变只给重点控件使用，控制半径和覆盖面积。
- 同一套装饰效果可离线烘焙为图片或九宫格资源，换取 Flash 占用，减少运行时计算。
- 图像资源预转换到目标色深和排列方式，避免每帧 RGB888 → RGB565 或 ARGB → RGB 的转换。
- 硬件 2D 引擎支持 blend 时，把规则的透明混合交给硬件；不支持时更要控制使用范围。

取舍：预合成资源会增大包体，也可能不适合动态换肤；因此更适合固定背景、固定阴影、固定装饰，而不是动态数据内容。

### 2.3 硬件 2D 加速

不少 MCU / MPU 有 DMA2D、PXP、G2D、GPU 等模块，可加速内存到内存拷贝、颜色填充、像素格式转换、Alpha 混合、缩放或旋转。

适合下放的工作：

| 操作 | 软件 CPU 的特点 | 2D 硬件加速的价值 |
| --- | --- | --- |
| 大面积填充 | 大量循环写像素 | 快速填色，释放 CPU |
| buffer 拷贝 | `memcpy` 占用总线和 CPU | DMA 异步搬运 |
| RGB565 / ARGB 转换 | 每像素计算 | 专用流水线处理 |
| Alpha 混合 | 读改写密集 | 降低 CPU 压力 |
| 图片缩放/旋转 | 算法成本高 | 视硬件能力卸载 |

落地时不能只“调用 DMA”：

1. buffer 地址、长度和 stride 要满足硬件对齐要求。
2. DMA 正在读 draw buffer 时，CPU / 框架不能提前复用或覆盖它。
3. 有 D-Cache 的平台要在 DMA 读取前 clean，在 DMA 写入后按方向 invalidate，避免 CPU cache 与 DDR/SDRAM 数据不一致。
4. 启动 DMA 后最好异步返回，完成中断或回调再通知框架 flush ready，才能让 CPU 与搬运并行。
5. 小区域 DMA 的启动开销未必低于 CPU 直接拷贝，要设置面积阈值。

常见问题：DMA 完成前就调用 `flush_ready`，会造成花屏；没有处理 cache 会出现“偶现旧图”；多个 DMA 任务共享同一通道但没有串行化，会导致区域错乱。

### 2.4 虚拟列表

长列表最常见的错误是：有 1 000 条数据，就创建 1 000 个列表项控件。即使只有十几项可见，布局、对象树遍历、事件和内存也会随总数据量增长。

虚拟列表的思路是：数据有很多，控件只保留可见区和少量缓冲区。

```text
数据模型：1000 条
屏幕可见：8 条
实际创建：8 + 上下预留 2 ~ 4 条 item

滚动时：复用移出屏幕的 item，绑定新的数据索引
```

关键实现点：

- 数据源与 item 控件分离，item 只负责显示当前绑定的数据。
- 根据滚动偏移计算首个可见索引，而不是逐项移动全部控件。
- item 复用时必须完整重置文本、选中态、图片、事件上下文等状态，避免“上一项的状态带到下一项”。
- 图片异步加载时，要给 item 绑定数据 ID / generation；回调回来后先确认 item 仍对应该数据，防止滚动复用后图片串位。
- item 高度固定时最简单；动态高度列表需要缓存测量结果或使用锚点算法，复杂度更高。

面试表达：

> 长列表我不会让控件数跟数据量线性增长。会把数据和视图分开，只创建可见项加少量预加载项；滚动时复用离屏 item 并重新绑定数据。这样对象数、布局和绘制开销基本与屏幕可见数量相关。异步图片回调还要校验数据 ID，避免复用后错绑到新的列表项。


## 3. 内存优化

嵌入式 UI 的内存问题不仅是“剩余多少 KB”，更要看生命周期、最大连续块、峰值内存和重复进出页面后的趋势。

### 3.1 资源池与内存池

控件、事件、动画、临时绘制对象频繁 `malloc/free`，且大小差异大时，堆容易产生碎片。最终可能出现总空闲内存看起来还够，但无法申请连续的大图片 buffer。

资源池 / 内存池的做法：

- 为固定大小、数量可预估的小对象预分配块，例如列表 item、事件对象、消息节点。
- 页面反复使用的图片解码 buffer、文字测量 buffer 预留并复用。
- 大小差异明显的对象可用多档 slab / block pool，不宜全部塞进同一个固定块池。
- 记录池的当前使用量和峰值，容量不足时有明确的降级行为。

优点是申请释放时间稳定、碎片少；代价是容量预留不当会浪费 RAM，资源峰值超过池容量时需要回退策略。

### 3.2 控件复用

页面切换、弹窗显示、列表滚动时频繁创建删除控件，会带来堆碎片、布局抖动和 CPU 峰值。

适合复用的对象：

- 列表项、表格行、键盘按键等重复结构。
- 高频打开的 Toast、确认弹窗、加载框。
- 固定页面框架中的标题栏、导航栏、状态栏。

复用不等于“永远不释放”。对于很少进入、资源很大的页面，常驻反而浪费内存。应按访问频率、创建成本、资源大小决定保留、缓存还是销毁。

### 3.3 懒加载与预加载

懒加载是在真正需要资源时才加载；预加载是在用户即将需要时提前准备。两者要配合使用。

| 场景 | 推荐策略 |
| --- | --- |
| 首屏关键图标、主字体 | 启动时加载，保证首屏稳定 |
| 下一个高概率进入的页面 | 空闲时预加载少量关键资源 |
| 大图、帮助页、低频页面 | 进入页面时懒加载，退出后释放 |
| 长列表缩略图 | 可见区优先加载，离屏项取消或降级 |

注意：懒加载不能放在 UI 线程同步解码大图，否则“省了启动时间，换来首次进入卡顿”。推荐后台任务读取 / 解码，UI 线程只接收完成消息并更新控件。

### 3.4 控制图片缓存

图片缓存能减少重复读 Flash、文件系统和重复解码，但无上限缓存是 UI 内存泄漏的常见来源之一。

建议：

- 明确缓存对象：缓存压缩文件、解码后的像素，还是缩放后的缩略图；三者 RAM 成本差异很大。
- 设置容量上限，并按 LRU、按页面、按优先级淘汰。
- 缓存 key 要包含路径、尺寸、颜色格式、缩放比例等，避免同一图片产生不可控的多个版本。
- 页面退出时释放页面私有缓存；共享缓存由统一资源管理器维护引用计数或淘汰策略。
- 大图优先考虑分块解码、缩略图、外部存储或显示时流式读取，不要默认整张展开到 RAM。

经验判断：RGB565 图片解码后的 RAM 大小约为 `宽 × 高 × 2`。例如 800 × 480 的一张全屏图就约 750 KB；ARGB8888 则约 1.46 MB。看资源文件只有几十 KB 的 PNG 并不能说明运行期占用小。

### 3.5 内存排查清单

- 页面连续进入、退出 20~100 次，观察堆剩余、最大连续块和对象数是否回到基线。
- 分别统计控件、图片、字体、draw buffer、DMA buffer、动画、消息队列的峰值。
- 检查定时器、事件回调、异步请求取消后是否仍持有页面指针。
- 检查父对象删除时，子对象和附加用户数据是否由框架自动释放；自管资源要明确释放责任。
- UI 任务里避免大局部数组，图片解码临时 buffer 尽量放静态池或外部 RAM。


## 4. CPU 与任务调度优化

### 4.1 UI 线程不能阻塞

UI 线程通常既要处理输入、定时器、动画，也要布局、绘制和提交刷新。只要在其中同步等待几十到几百毫秒，触摸、动画和脏区处理都会延后。

UI 回调中应避免：

- 同步读写 Flash、文件系统、网络、串口。
- 等待互斥锁、信号量、队列很长时间。
- 大量 JSON 解析、数据排序、图片解码、字体生成。
- 大循环计算、批量创建大量控件。
- 高频打印日志，尤其是串口波特率低时。

推荐模型：

```text
触摸回调 / 页面事件（UI 线程）
  -> 投递业务请求
  -> 立即更新 loading / 禁用按钮等轻量 UI

工作线程
  -> 通信、文件 I/O、解析、计算、解码
  -> 投递结果消息

UI 线程
  -> 校验页面仍有效
  -> 更新控件并触发局部刷新
```

不要让工作线程随意直接调用 GUI API。对象树刷新、事件回调和删除通常不具备完全线程安全性；统一由 UI 线程消费消息能减少锁和并发问题。

### 4.2 耗时任务异步化

异步化不是简单创建线程，而是要定义任务状态、取消规则和结果归属。

例如页面 A 发起图片加载，用户很快切走：

- 页面销毁时取消可取消的请求，或使其 generation 失效。
- 异步回调到 UI 线程后，先判断页面和控件是否仍有效。
- 不要在回调中持有已经销毁控件的裸指针。
- 对连续输入做合并，例如滑条拖动只处理最新值，丢弃中间过时任务。

这种设计既防止崩溃，也避免后台结果回来后又把已离开页面重新刷一遍。

### 4.3 合理降低帧率和刷新频率

降低帧率不是让界面“更卡”，而是根据内容变化速度设置刷新策略。

- 静态设置页：仅数据变化或输入事件发生时刷新。
- 温度、电量、传感器数值：可 1~10 Hz 刷新，不需要每帧刷新。
- 进度条：通常 10~30 FPS 已有足够连续感。
- 滚动、拖拽：根据体验目标使用 30~60 FPS。
- 无输入、无动画时：停止周期性无效刷新，并可降低 UI task 唤醒频率。

还可以做事件合并 / 节流：高频数据来了 100 次，不必更新文本 100 次；保留最新值，在下一帧统一渲染即可。

### 4.4 定点运算

在没有 FPU、FPU 性能较弱或软浮点的 MCU 上，频繁浮点计算可能明显占用 CPU。坐标、动画插值、传感器比例换算常可改用定点数。

例如用 Q16.16 表示小数：

```c
/* 1.5 用 1.5 * 65536 表示 */
int32_t scale_q16 = 98304;
int32_t x_scaled = (x * scale_q16) >> 16;
```

使用原则：

- 先通过 profiling 确认浮点确实是热点，不要为了“看起来底层”而全项目替换。
- 选择足够的整数位和小数位，评估溢出与精度。
- 乘法中间值用更宽类型，避免溢出。
- 对三角函数、曲线等可预计算查表；但要平衡 Flash、精度和插值成本。
- 有高性能硬件 FPU 的 MPU 上，强行改定点不一定更快，代码可读性可能更差。


## 5. 显示底层优化

### 5.1 DMA 刷屏

DMA 刷屏是把 draw buffer 中的像素异步搬到 LCD 接口、FrameBuffer 或显存。它的核心价值是 CPU 不再逐像素搬运，可以同时进行下一部分准备或其他业务。

适用条件：

- 显示控制器、SPI / 8080 / RGB 接口或内存控制器支持 DMA。
- 刷新区域足够大，DMA 启动开销可被摊薄。
- buffer 生命周期和 cache 一致性能正确管理。

常见流程：

```text
GUI 绘制脏区到 draw buffer
  -> 设置 LCD 窗口 / DMA 描述符
  -> 启动 DMA
  -> DMA 完成中断
  -> 通知 GUI 本次 flush 完成
```

若使用局部 draw buffer，可采用 ping-pong 缓冲：DMA 刷 buffer A 时，CPU 绘制下一块到 buffer B。但前提是框架、驱动和内存带宽都能真正并行，否则只是增加复杂度。

### 5.2 双缓冲与撕裂控制

单缓冲中，显示控制器扫描同一块内存，CPU / DMA 又在修改它，恰好扫描到一半就可能出现撕裂。

双缓冲的基本方式：

```text
前台 buffer：LCD 当前扫描显示
后台 buffer：CPU / GPU 绘制下一帧
VSYNC 到来：交换前后台 buffer 指针
```

优点是显示稳定、CPU 和显示扫描更容易并行；代价是整屏双缓冲至少需要两帧显存。例如 800 × 480、RGB565 单帧约 750 KB，双缓冲约 1.5 MB，还未算 draw buffer 和其他资源。

实践选择：

- RAM 很紧张的 MCU：局部 buffer + 脏区刷新，接受局部刷新策略的限制。
- 有外部 SDRAM、RGB/LTDC/DRM 等显示控制器：考虑整屏双缓冲或多缓冲，并在 VSYNC 时交换。
- SPI 屏：通常仍以局部 DMA 刷新为主；双缓冲不一定能解决总线带宽不足。

### 5.3 提升总线速率，但先判断是不是瓶颈

显示接口可能是 SPI、8080 并口、RGB、MIPI DSI、LVDS 等。提高时钟、改用更宽总线或开启 burst 能提升吞吐，但要先确认 `flush` 确实是主要耗时。

检查项：

- SPI 时钟是否处于屏和走线可稳定支持的范围。
- 是否每个小脏区都重复发送较多窗口设置命令；能否合理合并。
- DMA 是否使用 burst、合适的传输宽度和对齐。
- FrameBuffer 是否放在带宽足够的 SDRAM / DDR，是否被 CPU、摄像头、网络等主设备争抢。
- RGB / MIPI 时序是否允许提高像素时钟，EMI、功耗和屏幕规格是否满足。

总线升速的副作用可能是 EMI、发热、功耗、信号完整性和屏幕稳定性问题，不能只看理论带宽。


## 6. 架构和页面生命周期优化

性能问题常常不是某个绘图 API 慢，而是页面组织方式让无效对象、无效资源和无效刷新长期存在。

### 6.1 简化布局和对象树

对象树越深、控件越多，布局、命中测试、样式继承、裁剪和绘制遍历的成本越高。

优化方向：

- 不要为了排版堆很多只起占位作用的 container；能合并的静态层级合并。
- 静态背景、边框、装饰可合并为一张资源或一个自绘控件，减少多个独立对象。
- 避免在每帧或每次数据变化时重复触发布局；尺寸和文本未变化就不重新 layout。
- 为频繁更新的数值区域划定小容器，避免父级大容器因一个子控件变化而整体重排、整体失效。
- 对复杂页面做分层：高频变化层、低频变化层、静态背景层分别管理刷新。

注意：对象树不是越扁越好。合理的容器能提供裁剪、复用和生命周期边界；关键是每一层都有明确语义，而不是为对齐随意嵌套。

### 6.2 页面资源生命周期管理

建议为页面定义清晰生命周期，例如：

```text
create：创建控件树，绑定基础事件
enter ：加载首屏必需资源，订阅数据，启动必要定时器
active：接收数据并局部更新
pause ：页面被遮挡，暂停动画、轮询和可取消任务
resume：恢复订阅和必要资源
exit  ：取消异步请求，停止定时器，解除订阅
destroy：释放页面私有资源和控件
```

这样能避免两类典型问题：

1. 页面只隐藏不释放，反复进入后控件、图片和定时器持续累积。
2. 页面已经退出，后台任务或定时器仍回调并操作旧控件，导致泄漏、野指针或无效刷新。

资源可分为三类管理：

| 资源类型 | 示例 | 策略 |
| --- | --- | --- |
| 全局常驻 | 主字体、主题、通用小图标 | 启动加载，统一管理 |
| 页面共享缓存 | 频道封面、列表缩略图 | 有上限缓存，按引用或 LRU 淘汰 |
| 页面私有 | 大背景图、图表 buffer、临时弹窗 | 退出或 destroy 时释放 |

面试表达：

> 我会把页面资源按全局、共享和私有分层。页面进入时只加载首屏必需资源，退出时取消异步任务、停止 timer、解绑数据订阅并释放私有大资源。对于高频进入页面保留轻量控件树或资源缓存，但缓存要有上限；不能把“复用”做成永久常驻。


## 7. 常见现象、原因与处理

| 现象 | 优先怀疑 | 排查与优化 |
| --- | --- | --- |
| 小控件变化也卡顿 | 全屏失效、透明层扩大脏区 | 打印脏区面积；收敛 invalidate；裁剪和合并脏区 |
| 滚动列表越用越慢 | item 数跟数据量增长、图片未取消 | 虚拟列表；复用 item；异步回调校验数据 ID |
| 首次进页面卡 | UI 线程同步读文件、解码大图 | 懒加载改后台解码；首屏资源预加载；显示 loading |
| 反复进出页面内存下降 | 控件 / timer / 图片缓存泄漏 | 看对象数、最大连续块；完善 exit/destroy |
| 平均 FPS 尚可但动画抖 | UI 线程被锁、I/O 或高优先级任务打断 | trace 帧间隔；缩短回调；异步化；调整任务优先级 |
| DMA 后偶现花屏 | 提前复用 buffer、cache 未同步 | DMA 完成再 ready；clean/invalidate；检查对齐和 stride |
| 满屏动画 CPU 很高 | Alpha、阴影、软件 blend | 减少层数；预合成；使用 2D 硬件；限制动画面积和帧率 |
| 刷屏占用很长 | 接口带宽不足或 DMA 未发挥作用 | 测 flush 时间；局部刷新；合理合并；提高接口有效吞吐 |


## 8. 面试角度常见问题

### 8.1 你优化嵌入式 UI 时的总体方法是什么？

可以这样回答：

> 我先量化而不是直接改代码：看帧间隔、绘制耗时、flush 耗时、脏区面积、UI 线程占用和内存峰值，先区分瓶颈在 CPU 绘制、资源解码、LCD 传输还是任务调度。渲染侧优先减少无效像素，比如脏区裁剪、减少大面积 Alpha 和复杂特效；列表数据多时做虚拟化。CPU 侧保证 UI 线程不阻塞，把 I/O、解析、解码放后台。显示链路上根据硬件使用 DMA、2D 加速和合适的缓冲策略。最后通过页面资源生命周期控制缓存、定时器和异步任务，避免性能和内存随使用时间劣化。

### 8.2 脏区刷新一定比全屏刷新好吗？

不一定。

> 脏区刷新在局部变化、总线带宽紧张时收益很大。但如果脏区非常碎、覆盖面积接近全屏，频繁设置窗口和发起 DMA 的固定开销可能更高；视频、全屏转场这类场景也天然接近全屏刷新。因此通常要做脏区合并，并根据面积或数量阈值切换到整屏刷新。关键是用实际 `draw + flush` 耗时决定，而不是只看理论。

### 8.3 为什么透明效果会让 UI 变慢？

> 不透明控件通常是直接写像素；透明混合需要读取背景、计算并回写像素，多层透明会造成重复的读改写。再加上圆角、阴影、抗锯齿，影响区域会扩大。优化上我会尽量让大背景不透明，限制大面积半透明层，对固定装饰做预合成；硬件支持时把 blend 下放到 DMA2D 或 GPU。

### 8.4 虚拟列表如何避免图片、点击事件串位？

> item 被复用时，我会重新绑定数据索引并完整重置显示状态，点击事件不捕获旧索引，而是从 item 当前绑定的数据 ID 取值。异步图片加载会携带数据 ID 或 generation，回调到 UI 线程后校验 item 仍绑定同一条数据才更新。这样快速滚动时不会把旧请求结果显示到新 item 上。

### 8.5 双缓冲能解决所有卡顿和撕裂吗？

> 双缓冲主要解决显示扫描和写 buffer 并发导致的撕裂，也方便在 VSYNC 交换帧。它不增加 SPI 或 LCD 总线实际带宽，也不减少 CPU 绘制时间；如果瓶颈是全屏传输或软件混合，仍要做脏区、DMA、特效控制等优化。此外双缓冲会显著增加显存需求。

### 8.6 DMA 刷屏最容易踩哪些坑？

> 一是 DMA 尚未完成就复用 draw buffer 或通知框架 flush 完成；二是带 cache 的平台没有按方向 clean/invalidate，导致偶现旧数据或花屏；三是地址、stride、传输长度、颜色格式和对齐不匹配；四是小区域也强行 DMA，启动开销反而更大。我会把 DMA 完成回调作为 buffer 归还和 `flush_ready` 的唯一时机，并给 CPU copy 和 DMA 设置面积阈值。

### 8.7 你如何避免 UI 线程卡死或线程安全问题？

> 所有 GUI API 尽量只在 UI 线程调用。事件回调只做轻量状态更新和任务投递，网络、文件、解码、计算放后台；后台通过消息队列把结果送回 UI 线程。页面退出时取消任务或使 generation 失效，回调更新前先检查页面仍有效。这样既避免对象树并发修改，也避免 UI 线程等待业务锁形成死锁。

### 8.8 有一个页面越用内存越少，你怎么排查？

> 我会先做重复进入退出压测，记录堆总剩余、最大连续块、对象数量、图片缓存和 UI 栈高水位，判断是泄漏还是碎片。然后检查页面创建的控件、定时器、事件监听、异步请求、图片和字体缓存是否在 exit/destroy 对称释放。尤其关注异步回调持有页面指针、只隐藏不销毁页面，以及无限制图片缓存。若总空闲变化不大但最大连续块持续下降，更倾向堆碎片，考虑资源池和控件复用。


## 9. 项目经验回答模板

没有实际做过某项优化时，不要虚构具体百分比。可以按“现象—定位—措施—验证—取舍”表达真实参与部分。

模板：

> 项目中我负责 / 参与了 ___ 页面性能排查。现象是 ___，我先通过 ___ 统计到瓶颈主要在 ___。随后把 ___ 改为 ___，并处理了 ___ 这个边界问题。优化后用 ___ 指标验证，___ 从 ___ 改善到 ___。这项方案的代价是 ___，所以我只在 ___ 场景启用。

示例（请按真实项目替换数据）：

> 某设备状态页有多个实时数值和趋势列表，切换页面时偶发卡顿。我在刷新入口和 flush 回调打点，发现数据更新会触发父容器失效，导致接近全屏的刷新。后续改为只更新变化的文本和图表局部区域，并把列表改成可见项复用；图片加载由 UI 线程同步读取调整为后台解码、UI 线程提交。验证时主要看单帧 flush 时间、脏区面积、UI 任务占用和连续进出页面后的内存基线。对于数据快速变化场景，还做了节流，只保留最新值，避免无意义的中间帧。


## 10. 速记总结

- 优化先测量：看 `layout / draw / flush / wait` 分别耗时多少。
- 脏区裁剪的本质是少画、少传；旧位置和新位置都要失效。
- 脏区过碎要合并，接近全屏时整屏刷新可能更划算。
- 大面积 Alpha、阴影、模糊和渐变是软件渲染热点，固定装饰可预合成。
- DMA2D / GPU 适合填充、拷贝、转换、混合；要处理 buffer 生命周期和 cache 一致性。
- 长列表要虚拟化，控件数与可见数相关，而不是与数据总量相关。
- 内存优化重点是资源池、控件复用、懒加载和有上限的图片缓存。
- UI 线程只做轻量逻辑；I/O、解码、解析和计算异步化，后台不直接改 UI。
- 帧率应按内容变化速度设置，静态页按需刷新，高频数据要节流和合并。
- DMA 刷屏、双缓冲、提高总线速率分别解决不同问题，不能互相替代。
- 页面必须有明确资源生命周期：进入加载、遮挡暂停、退出取消任务、销毁释放私有资源。
