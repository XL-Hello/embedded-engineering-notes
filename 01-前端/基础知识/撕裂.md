# 第一章 什么是撕裂？

在嵌入式 GUI 里，**撕裂（Screen Tearing）本质上不是“画错了”，而是“显示器正在读这一帧时，你把这一帧的一部分改成了下一帧”**。

于是屏幕某一时刻显示的是：

```text
上一帧
────────────────────
        ← 撕裂线
────────────────────
下一帧
```

比如页面左右滑动时，最容易看到一条横向“断层”：

```text
理想画面：

┌──────────────────────────┐
│        ABCDEFGHI         │
│        ABCDEFGHI         │
│        ABCDEFGHI         │
│        ABCDEFGHI         │
└──────────────────────────┘

发生撕裂：

┌──────────────────────────┐
│        ABCDEFGHI         │ ← 旧帧
│        ABCDEFGHI         │
├──────────────────────────┤ ← tearing line
│      ABCDEFGHI           │ ← 新帧
│      ABCDEFGHI           │
└──────────────────────────┘
```

人类发明了动画，然后又花大量工程时间确保动画看起来不像屏幕坏了。下面把这个问题系统拆开。

---

## 1.1 撕裂为什么会出现

关键是理解显示设备通常不是“瞬间显示一整帧”，而是**逐行扫描**。

假设 LCD 刷新率为 60Hz：

```text
一帧时间 ≈ 16.67 ms
```

LCD 实际工作过程类似：

```text
时间 →

LCD扫描：

第0行   █
第1行    █
第2行     █
...
第319行                   █
```

假设 framebuffer：

```text
Framebuffer
┌─────────────────────────────┐
│ Line 0                      │
│ Line 1                      │
│ Line 2                      │
│ ...                         │
│ Line 319                    │
└─────────────────────────────┘
```

此时 CPU / GPU / DMA 又在修改 framebuffer：

```text
LCD：
        ↓ 正在读取

Framebuffer
┌─────────────────────────────┐
│ 旧帧                        │
│ 旧帧                        │
│ ← LCD扫描到这里             │
│ 新帧 ← CPU已经修改          │
│ 新帧                        │
└─────────────────────────────┘
```

结果这一屏就变成：

```text
上半部分：旧帧
下半部分：新帧
```

这就是最典型的撕裂。

---

## 1.2 如何一句话概括

> 撕裂的本质是显示扫描和 framebuffer 更新没有同步。LCD 是逐行扫描的，如果在一帧尚未扫描完成时，CPU 或 DMA 修改了当前正在显示的 framebuffer，或者切换到了下一帧，就可能导致屏幕一部分显示旧帧、一部分显示新帧，从而形成撕裂线。

对 RGB/LTDC 屏，通常采用双 framebuffer，并在 VSYNC 时切换前后缓冲区；对于 SPI LCD，由于 MCU 写 LCD GRAM 和 LCD 自身扫描是异步的，可以利用 TE 信号同步刷新。同时还需要保证 DMA buffer 在传输完成前不被复用，并检查 SPI/PSRAM 带宽、Cache 一致性和显示时序等问题。

# 第二章 常见撕裂原因及对应的解决办法

先用下表建立全局视角。后文将按这些类别逐项说明其发生机制与处理方式；部分“看起来像撕裂”的现象（例如 DMA 数据竞争、Cache 不一致）不一定属于严格意义上的帧撕裂，但排查时应一并考虑。

| 类别 | 典型原因 | 解决方案 |
| --- | --- | --- |
| 帧同步问题 | LCD 扫描时修改当前帧 | 双 Framebuffer |
| Buffer 切换问题 | 非 VSYNC 时交换 Buffer | VSYNC 同步 |
| SPI LCD 问题 | 写 GRAM 和 Panel 扫描冲突 | TE 同步 |
| 数据传输问题 | DMA 未完成就复用 Buffer | DMA Done 后 `flush_ready` |
| 带宽问题 | SPI / PSRAM / 总线带宽不足 | 提速、局部刷新、降帧率 |
| Cache 问题 | DMA 和 CPU 数据不一致 | Clean / Invalidate Cache |
| 并发问题 | 多线程同时操作 GUI / Buffer | GUI 单线程 + Queue |
| 性能问题 | 绘制超过一帧时间 | Dirty Area、硬件加速 |
| 时序问题 | RGB Timing 错误 | 校准 PCLK / HSYNC / VSYNC / Porch |

## 2.1 显示和绘制访问同一个 Buffer

这是第一大类，也是最标准的 tearing。

## 场景

例如 RGB LCD / LTDC：

```text
                FrameBuffer
CPU/LVGL ───────→ RAM ←────── LCD Controller
                   ↑
                 同一块
```

LCD Controller 不停从 RAM 取像素：

```text
RAM → LCD Controller → Panel
```

与此同时 LVGL：

```text
LVGL → 修改 RAM
```

于是：

```text
LCD正在读取 Line 100

CPU突然把 Line 150~319 更新成下一帧

最终：

Line   0~149：Frame N
Line 150~319：Frame N+1
```

### 解决方法 1：双缓冲

这是最经典方案。

```text
              ┌──────────────┐
LVGL绘制 ────→│ Back Buffer  │
              └──────────────┘

              ┌──────────────┐
LCD扫描 ─────→│ Front Buffer │
              └──────────────┘
```

当前：

```text
LCD  → Buffer A
CPU  → Buffer B
```

绘制完成后：

```text
等待 VSYNC
      ↓

交换：

LCD  → Buffer B
CPU  → Buffer A
```

关键不是“双 Buffer”这四个字，而是：

> **必须在安全时机交换 Buffer。**

否则：

```text
双缓冲 + 随便什么时候交换
```

依然能撕。

正确的是：

```text
Render Frame N+1
        ↓
绘制完成
        ↓
等待 VSYNC
        ↓
Swap Front/Back Buffer
        ↓
LCD开始扫描完整 Frame N+1
```

---

## 2.2 Buffer 切换没有和 VSYNC 同步

这是很多人“我都双缓冲了怎么还撕”的罪魁祸首。

假设：

```text
LCD正在扫描 Buffer A

Line 0
Line 1
...
Line 150   ← 当前扫描位置
```

这时候直接：

```c
lcd_set_framebuffer(buffer_b);
```

那么屏幕可能变成：

```text
Line   0~150：Buffer A
Line 151~319：Buffer B
```

依然撕裂。

## 解决

使用：

```text
VSYNC
```

Vertical Sync，垂直同步。

帧扫描过程：

```text
              Active Display
        ┌──────────────────────┐
VSYNC ──┘                      └─────
        ↑
        最适合切换 FrameBuffer
```

典型流程：

```c
render(back_buffer);

wait_vsync();

swap(front_buffer, back_buffer);
```

实际驱动通常是：

```text
VSYNC ISR
   ↓
设置新的 framebuffer 地址
   ↓
下一帧 LCD 使用新 framebuffer
```

因此可以记住：

> **双缓冲解决的是“绘制和显示分离”，VSYNC 解决的是“什么时候交换”。**

两个经常要一起使用。

---

## 2.3 SPI LCD：写 GRAM 与 Panel 扫描冲突

这类在 ESP32、STM32 + ILI9341/ST7789/GC9A01 之类的项目里尤其常见。

架构通常是：

```text
MCU RAM
   │
   │ SPI DMA
   ↓
LCD Controller GRAM
   │
   ↓
LCD Panel
```

这里其实存在两个“扫描者”：

```text
MCU：
RAM ─SPI→ LCD GRAM

LCD：
GRAM ─扫描→ Panel
```

问题就在于：

> MCU 正在修改 LCD GRAM，而 LCD Controller 同时正在读取 GRAM。

例如 LCD 当前正在扫描第 100 行：

```text
LCD扫描：

0
1
...
100 ← 当前
101
...
319
```

MCU 恰好从：

```text
Line 0 → Line 319
```

重新写 GRAM。

两边扫描速度不一致：

```text
LCD Scan   ↓↓↓↓↓↓↓↓↓
MCU Write     ↓↓↓↓↓↓↓↓↓↓↓↓↓
```

两条“扫描线”发生追赶时，就出现 tearing line。

---

## 2.4 SPI LCD 的解决方案：TE 信号

很多 LCD 控制器提供：

```text
TE
Tearing Effect
```

引脚。

例如：

```text
LCD
┌────────────┐
│            │
│ TE ────────┼────→ MCU GPIO
│            │
│ SPI        │
└────────────┘
```

LCD 会告诉 MCU：

> “现在到了安全刷新的时间窗口。”

典型流程：

```text
LCD扫描一帧
      ↓
TE触发
      ↓
MCU开始 SPI DMA
      ↓
更新LCD GRAM
```

代码思想：

```c
wait_te();

lcd_flush(framebuffer);
```

这里的前提是：实际发送的数据必须能在 TE 所代表的安全窗口内完成。若整帧或区域传输时间超过该窗口，单次等待 TE 并不能保证后续写 GRAM 不会再次与 Panel 扫描重叠。

或者：

```text
TE GPIO中断
     ↓
唤醒刷新任务
     ↓
SPI DMA发送
```

这是 SPI MCU 屏抗撕裂非常重要的一种方式。

---

## 2.5 SPI 带宽不足

这是另一类非常现实的问题。

例如你的屏幕：

```text
240 × 320
RGB565 = 2 Byte/pixel
```

一帧：

```text
240 × 320 × 2
= 153600 Byte
≈ 150 KB
```

假设 SPI：

```text
10 MHz
```

理论吞吐：

```text
10 Mbps / 8
≈ 1.25 MB/s
```

那么完整一帧至少：

```text
153600 / 1.25MB
≈ 123 ms
```

理论最高整屏刷新率只有：

```text
1 / 0.123
≈ 8 FPS
```

实际还会更低。

但 LCD 自己可能：

```text
60Hz
≈ 16.7ms / frame
```

于是：

```text
LCD已经扫描了：
Frame 1
Frame 2
Frame 3
Frame 4
Frame 5
Frame 6
Frame 7

MCU才终于把一帧写完
```

这种情况下想靠“每帧整屏刷新”做到完美同步，基本属于拿自行车追高铁。

## 解决方式

### 1. 提高 SPI 时钟

例如：

```text
10MHz
↓
40MHz
↓
80MHz
```

40MHz RGB565：

```text
40Mbps / 8 = 5MB/s

153600 / 5MB
≈ 30.7ms
≈ 32FPS 理论值
```

明显改善。

---

### 2. 局部刷新

不要每次：

```text
320 × 240 整屏
```

而只刷新：

```text
Dirty Area
```

例如按钮：

```text
┌──────────────────────────┐
│                          │
│       ┌──────────┐       │
│       │  Button  │ ← 只刷这里
│       └──────────┘       │
│                          │
└──────────────────────────┘
```

LVGL 天生就非常适合这种模式。

---

### 3. TE + 分块刷新

进一步可以：

```text
TE
 ↓
刷新 Area 1
 ↓
刷新 Area 2
 ↓
...
```

避免写入区域和 LCD 当前扫描区域撞车。分块策略必须结合控制器的 TE 模式、Panel 扫描方向和实际可用窗口设计；不能简单地认为一次 TE 后连续发送的所有区域都同样安全。

---

## 2.6 DMA Buffer 被提前复用

这在 LVGL + SPI DMA 中很容易踩。

典型：

```text
LVGL Draw Buffer A
      ↓
SPI DMA传输 Buffer A
      ↓
DMA还没结束
      ↓
LVGL又开始写 Buffer A
```

于是：

```text
CPU写        DMA读
  ↓           ↓
Buffer A ←────────
```

DMA读到的数据可能是：

```text
前半部分：旧数据
后半部分：新数据
```

屏幕就出现：

```text
错行
撕裂
花屏
局部异常
```

严格来说其中一些属于**数据竞争导致的显示破坏**，不全是经典 tearing，但肉眼看上去非常相似。

## 正确方案

LVGL：

```c
flush_cb()
{
    spi_dma_start(buffer);

    // 不能马上：
    // lv_disp_flush_ready();
}
```

必须：

```text
flush_cb
   ↓
DMA Start
   ↓
DMA transmitting...
   ↓
DMA Done ISR
   ↓
lv_disp_flush_ready()
```

即：

```c
void dma_done_callback(...)
{
    lv_disp_flush_ready(disp_drv);
}
```

告诉 LVGL：

> 这块 buffer DMA 已经不用了，你现在才能重新画。

---

## 2.7 单 Buffer + DMA 异步传输

再看一个典型问题：

```text
LVGL
 ↓
Buffer
 ↓
DMA
 ↓
LCD
```

如果只有一个 Buffer：

```text
CPU：
████████████

DMA：
   ████████████
```

两边可能同时使用它。

解决：

```text
Draw Buffer A
Draw Buffer B
```

流程：

```text
CPU Draw A
    ↓
DMA Send A

同时：

CPU Draw B
    ↓
DMA Send B

CPU Draw A
...
```

也就是：

```text
Ping-Pong Buffer
```

但这里必须强调：

> **LVGL 双 draw buffer ≠ LCD 双 framebuffer。**

这是非常容易混淆的概念。

---

## 2.8 LVGL 双 Draw Buffer 和真正双 Framebuffer 的区别

例如 LVGL：

```c
static lv_color_t buf1[240 * 40];
static lv_color_t buf2[240 * 40];

lv_disp_draw_buf_init(
    &draw_buf,
    buf1,
    buf2,
    240 * 40
);
```

这两个只是：

```text
Render Buffer
```

也就是：

```text
40行的小块缓存
```

工作方式：

```text
LVGL画 buf1
   ↓
DMA发送 buf1

与此同时
LVGL画 buf2
   ↓
DMA发送 buf2
```

目的是：

> **CPU绘图和 DMA 传输流水线化。**

它不能天然保证：

```text
LCD Panel不撕裂
```

因为 LCD 内部：

```text
GRAM
 ↓
Panel Scan
```

仍然和 MCU：

```text
SPI
 ↓
GRAM Write
```

异步。

所以：

```text
LVGL双Draw Buffer
        ↓
主要解决性能 / DMA等待

LCD双Framebuffer + VSYNC
        ↓
解决真正帧级撕裂
```

这两个概念面试里经常有人混为一谈，然后整个讨论就开始向玄学发展。

## 2.9 Cache 一致性问题

如果平台带 DCache：

```text
CPU
 │
 ↓
DCache
 │
 ↓
RAM
 │
 ↓
DMA
```

CPU 修改 framebuffer：

```text
CPU → Cache
```

但 DMA 从：

```text
RAM
```

读取。

如果没有：

```c
cache_writeback();
```

可能：

```text
CPU看到：Frame N+1

RAM还是：Frame N
```

DMA 就发送旧数据。

甚至不同 cache line 状态不同：

```text
Line 0~100：新数据
Line 101~200：旧数据
Line 201~319：新数据
```

视觉表现：

```text
撕裂
局部错乱
旧帧残留
花屏
```

## 解决

当 DMA 从 framebuffer **读取**数据并发送到显示器前：

```text
Clean / Writeback DCache
```

当 DMA **写入**内存、随后需要由 CPU 读取时：

```text
Invalidate DCache
```

具体依平台：

```c
SCB_CleanDCache_by_Addr();
```

ESP32 等平台则使用对应的 DMA 内存和 Cache API。

---

## 2.10 Framebuffer 放在 PSRAM 导致带宽不足

例如：

```text
CPU
  ↓
PSRAM ←→ Cache
  ↓
LCD DMA
```

如果：

```text
LCD刷新
+
CPU绘制
+
Wi-Fi
+
PSRAM访问
```

同时争抢总线：

```text
             ┌── CPU
             │
PSRAM BUS ───┼── LCD DMA
             │
             ├── Other DMA
             │
             └── Cache
```

可能导致：

```text
LCD FIFO Underflow
```

结果通常表现为：

```text
画面撕裂
闪烁
局部错位
横线
```

这类在 RGB LCD / LTDC 场景比较明显。

## 解决

优先考虑：

```text
1. Framebuffer放高速内部RAM
2. 提高PSRAM带宽
3. 调整DMA burst
4. 提高LCD FIFO
5. 降低分辨率
6. 降低刷新率
7. 使用RGB565代替RGB888
8. 减少同时访问PSRAM的任务
```

---

## 2.11 CPU 绘制时间过长

例如：

```text
Frame N

VSYNC
 ↓
开始绘制
 ↓
10ms
 ↓
20ms
 ↓
30ms
 ↓
绘制完成
```

但是：

```text
60Hz → 16.67ms/frame
```

意味着你错过了 VSYNC。

理想：

```text
|------16ms------|
Render ███████
              ↑
             VSYNC
```

实际：

```text
|------16ms------|------16ms------|
Render ██████████████████████
```

于是 buffer 切换可能错过时间窗口。

## 解决

### 降低绘制复杂度

例如：

```text
减少透明混合
减少大面积 alpha
减少阴影
减少旋转缩放
避免软件逐像素绘制
```

### 使用硬件加速

例如：

```text
DMA2D
PXP
GPU
2D Accelerator
```

### Dirty Region

只画变化部分。

---

## 2.12 刷新任务和绘图任务并发访问

比如：

```text
Task A
LVGL Render
     ↓
Framebuffer

Task B
LCD Refresh
     ↓
Framebuffer
```

如果没有同步：

```text
Task A正在写
Task B同时读
```

结果同样有问题。

甚至：

```text
Task A：修改控件
Task B：lv_timer_handler()
Task C：flush
```

一起碰 LVGL 内部状态。

## 解决

通常：

```text
只有一个GUI线程调用LVGL
```

其他任务：

```text
Sensor Task
WiFi Task
MQTT Task
```

不要直接：

```c
lv_label_set_text();
```

而是：

```text
MQTT Task
   ↓
Queue
   ↓
LVGL Task
   ↓
更新UI
```

即：

```text
GUI单线程化
```

## 2.13 显示时序参数错误

RGB LCD 还有一类问题并不是 framebuffer 的锅，而是：

```text
PCLK
HSYNC
VSYNC
HBP
HFP
VBP
VFP
```

配置不正确。

例如：

```text
HSYNC
│
├─ HBP ─ Active Pixels ─ HFP
```

Vertical：

```text
VSYNC
│
├─ VBP
│
├─ Active Lines
│
└─ VFP
```

如果：

```text
Pixel Clock过高

```

可能导致：

```text
画面错位
跳动
横线
局部撕裂
闪屏
```

## 解决

严格按照 LCD Datasheet：

```text
Pixel Clock
HSYNC pulse
HBP
HFP

VSYNC pulse
VBP
VFP

CLK polarity
DE polarity
SYNC polarity
```

配置。

# 第三章 针对常见硬件架构，解决方案其实不同

这点尤其重要。

## 3.1 RGB / LTDC LCD

架构：

```text
         RAM Framebuffer
              │
              ↓
        LCD Controller
              │
RGB ──────────┤
              ↓
            Panel
```

最优方案：

```text
Double Framebuffer
       +
      VSYNC
```

即：

```text
Render Back Buffer
        ↓
Wait VSYNC
        ↓
Swap Buffer
```

这是最标准的。

---

## 3.2 SPI + ILI9341/ST7789

架构：

```text
LVGL
 ↓
Draw Buffer
 ↓
SPI DMA
 ↓
LCD GRAM
 ↓
Panel
```

推荐：

```text
LVGL双Draw Buffer
        +
SPI DMA
        +
DMA完成后flush_ready
        +
TE同步
        +
Dirty Area
```

如果没有 TE：

```text
提高SPI速率
+
局部刷新
+
合理控制刷新的区域和顺序
```

只能尽量降低 tearing，未必能做到理论上的绝对无撕裂。

---

## 3.3 ESP32-S3 + RGB LCD

例如：

```text
ESP32-S3
    │
 PSRAM FrameBuffer
    │
 RGB LCD Peripheral
    │
   LCD
```

重点排查：

```text
① Framebuffer是否双缓冲
② 是否VSYNC切换
③ PSRAM带宽是否够
④ PCLK是否过高
⑤ Cache一致性
⑥ RGB DMA是否underflow
⑦ LVGL render mode
```

一般优先方案：

```text
Full Refresh / Direct Mode
        ↓
Double Framebuffer
        ↓
VSYNC Swap
```

# 第四章 建立一套排查思路

以后遇到屏幕所谓“撕裂”，不要第一反应就乱改 SPI 时钟。建议按照这条链路排：

```text
发现画面异常
      │
      ↓
是否是一条明显的横向断层？
      │
      ├─ 是 → 优先检查帧同步：是否单 Framebuffer？
      │              │
      │              ├─ 是 → 改为前后 Buffer 分离
      │              │
      │              └─ 否 → 是否在 VSYNC / TE 安全窗口切换或写入？
      │                           │
      │                           ├─ 否 → 增加 VSYNC / TE 同步
      │                           └─ 是 → 继续检查 DMA、带宽与时序
      │
      └─ 否 → 也继续检查下列“类似撕裂”的数据与时序问题
      │
      ↓
DMA 传输期间 Buffer 是否被修改或提前复用？
      │
      ├─ 是 → DMA Done 后再释放 Buffer，并使用 Ping-Pong Buffer
      └─ 否 → 继续
      │
      ↓
传输或存储带宽是否足够？是否发生 FIFO underflow？
      │
      ├─ 否 → SPI：提高 SPI 时钟、局部刷新
      │         RGB：降低 PCLK / 刷新率或分辨率，优化 DMA 与存储带宽
      └─ 是 → 继续
      │
      ↓
是否涉及 Cache / PSRAM？
      │
      ├─ 是 → 按 DMA 方向检查 Cache 一致性，并检查 PSRAM / DMA 带宽
      └─ 否 → 继续
      │
      ↓
核对 LCD Timing：PCLK、HSYNC / VSYNC、Porch 与极性
```

你可以把**嵌入式屏幕撕裂**记成一个很清晰的根因：

```text
撕裂的根因 = 显示扫描与图像更新未同步
```

而常见解决技术其实都围绕两个字：

```text
                同 步
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
      VSYNC      TE       DMA Done
        │         │         │
Framebuffer切换  GRAM刷新   Buffer复用
```

其中最容易混淆、也最值得你单独掌握的一点是：

> **LVGL 双 Draw Buffer、双 Framebuffer、VSYNC、TE 是四个不同层面的东西。**

把这四个东西彻底分清，嵌入式 GUI 中八成的“为什么还会撕裂”问题就没那么神秘了。
