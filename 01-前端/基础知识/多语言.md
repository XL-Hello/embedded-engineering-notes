# LVGL 多语言开发方案

> 目标：整理 LVGL 在企业产品中最常用、最容易长期维护的多语言开发方案。重点说明语言资源怎么组织、如何切换语言、页面怎样统一刷新，以及字体、布局、动态文案、OTA 和测试怎样形成完整工程闭环。
>
> 说明：这里的“多语言”不只是把中文替换成英文，而是国际化（i18n）和本地化（l10n）的组合：同一套业务逻辑和页面结构，随用户语言、地区和文本规则展示正确的文字、字体、排版、时间和单位。本文以 C API 开发的 LVGL 项目为主；LVGL 9 的 `lv_translation`、LVGL 8 的自研字典/`lv_i18n` 都会说明。

## 阅读路线

本文按“先能说清楚，再能解决问题”的顺序组织：

| 层次 | 适合谁 | 学完应达到的目标 | 建议阅读范围 |
| --- | --- | --- | --- |
| 第一层：总体扫盲 | 刚接触 LVGL 多语言、需要做技术沟通或面试复习的人 | 能用自己的话说清楚多语言的主方案、核心组成和基本选型 | 第 1～4 节 |
| 第二层：工程进阶 | 已理解主方案、准备实现或维护产品的人 | 能处理资源生成、版本差异、页面刷新、字体、OTA 和自动化验收 | 第 5～17 节 |

如果当前只需要回答“项目如何做多语言”，先完整读第一层即可；遇到具体实现、缺字、布局溢出、切换崩溃或语言包升级问题时，再按第二层对应章节深入。

## 第一层：总体扫盲——先能说清楚方案

### 1. 先说结论：企业项目最常用的方案是什么

**最常用、最稳妥的方案是：业务和 UI 代码只写稳定的语言键（key / ID），所有翻译放在集中管理的语言资源中；构建时校验并生成只读 C 表或资源包；运行时由唯一的 LanguageManager 切换当前语言，并通知所有可见页面重新取词和布局。**

可以把它称为：

> `语言键 + 资源表 + 统一语言管理 + 页面绑定/刷新` 方案。

典型链路如下：

```text
产品文案 / 翻译平台 / Excel
        ↓ 导出、审核
locale/zh-CN.yml、locale/en-US.yml、locale/ja-JP.yml
        ↓ 脚本校验：键、占位符、字符、版本
生成 i18n_generated.c / i18n_generated.h 或语言资源包
        ↓ 编译/打包
固件 Flash / 文件系统 / OTA 语言包
        ↓
LanguageManager 读取持久化语言并设置当前 locale
        ↓
页面创建时 bind(key)；语言变化时统一 refresh / 事件通知
        ↓
lv_label_set_text(label, tr(I18N_SETTINGS_TITLE))
```

这套方案适合大多数“中文 + 英文 + 少量海外语言”的 MCU、RTOS 和嵌入式 Linux 产品，原因是：

- 文案不散落在页面 C 文件中，改词、补翻译、做语言审校都有唯一入口。
- 语言键稳定，中文原文改写不会影响代码和统计；同一词条也能按页面语义拆分，避免错误复用。
- UI、业务、翻译和测试可以并行协作，Git diff 也清晰。
- 全量词条可编译进 Flash，运行时不需要解析 JSON/YAML，确定性好、RAM 占用小。
- 若产品以后要 OTA 下发语言包、增加地区或接入翻译平台，资源层可以扩展，页面 API 不必推倒重来。

不要把“每处 `if (lang == EN) lv_label_set_text(...)`”当成多语言方案。页面少时看似快，页面和语言一多就会出现漏改、无法审校、切语言不完整、字体缺字和布局溢出等问题。


### 2. 多语言实际由哪几部分组成

多语言至少有四层，字符串表只是第一层：

| 层次 | 要解决的问题 | 典型内容 |
| --- | --- | --- |
| 文案资源 | 同一语义在各语言中如何表达 | 标题、按钮、错误码、提示、单位名称 |
| 字体与文字系统 | 字符能否正确显示 | UTF-8、字库、CJK 字符集、fallback、RTL |
| UI 布局 | 翻译变长后会不会遮挡或截断 | Flex/Grid、换行、省略、字号、镜像布局 |
| 业务本地化 | 数值和规则是否符合地区习惯 | 复数、日期、温度、货币、地区格式 |

常见误区：

- “已经是 UTF-8，所以中文一定能显示”：UTF-8 只是编码；字体中没有对应字形，仍然会显示方块或空白。
- “中英文切成功就完成了”：德语、俄语等通常更长；阿拉伯语还涉及从右到左（RTL）排版和界面方向。
- “字符串格式化就够了”：`%d file(s)` 对英语、俄语、阿拉伯语等复数规则不正确，日期和单位也不应拼接。
- “设置语言后重进页面即可”：用户可能在当前页面、弹窗或键盘中立即切换语言，必须定义可见 UI 的刷新策略。

### 3. 用五步说清楚一个多语言方案

初学阶段不需要先记住 LVGL 的所有 API，只要能把下面五步讲完整：

1. **给每句 UI 文案一个语义 key**，例如 `settings.title`，页面不直接写“设置”或 “Settings”。
2. **为每种语言维护一份词条资源**，例如 `zh-CN.yml`、`en-US.yml`；同一个 key 在不同语言中对应不同文本。
3. **在构建期把资源生成 C 表或资源包**，量产设备通常把静态表放入 Flash，运行时直接查表。
4. **用唯一的 LanguageManager 保存当前语言并完成切换**，语言选择写入设备配置，重启后仍有效。
5. **通知当前可见 UI 重新取词和布局**，因此页面、弹窗、状态栏不会出现新旧语言混杂。

用一句项目描述串起来：

> 页面通过 key 查询当前语言的文本；翻译文件集中管理并在构建期生成资源；用户切换语言后，LanguageManager 在 UI 线程统一刷新可见界面和布局。

这就是企业项目的最小闭环。字体、复数规则、动态语言包等不是另一套方案，而是在这个闭环上增加的工程能力。

### 4. 初学者怎么做基本选型

先按设备能力和语言数量做粗选，不必一开始就设计 OTA 语言包：

| 你的项目情况 | 第一选择 | 原因 |
| --- | --- | --- |
| MCU、中文/英文、随固件发布 | 静态 C 词条表 + `tr(key)` | 稳定、占 RAM 小、实现最简单 |
| 新建 LVGL 9 项目 | 静态资源 + `lv_translation` | 可直接使用原生查词和语言变化通知 |
| LVGL 8 存量项目 | 自研薄封装或 `lv_i18n` | 保持统一 `tr()/language_set()` 接口，不依赖 v9 API |
| 语言多、文案要单独 OTA | 运行时语言资源包 | 只有明确需要独立交付时才承担其复杂度 |

初学时可以把默认方案记为：**两三种语言的嵌入式设备，优先使用构建期生成的静态表；任何版本的 LVGL 都由页面 key、资源表和统一语言管理器组成。**

读完第一层，应能回答三个问题：

- 为什么不能在每个页面写 `if (lang == EN)`？因为文案会分散、难审校、容易漏刷新。
- 多语言最少需要哪些模块？语言 key、翻译资源、生成/查表、语言管理和 UI 刷新。
- 切语言后为什么要重新布局？不同语言长度不同，按钮、弹窗和列表高度都可能变化。

## 第二层：工程进阶——把方案做稳、做可维护

> 这一层默认你已经理解“key → 资源 → LanguageManager → UI 刷新”的主链路。下面不再重复概念，而是解释不同实现方式的取舍，以及量产项目最容易踩坑的细节。

### 5. 方案选型：静态表、生成式 i18n 和运行时语言包

#### 5.1 企业默认选择：构建期生成、全量静态词条表

大多数量产嵌入式项目推荐把审核后的语言文件在构建期转换为 `const` C 数组，所有语言随固件发布。

```text
locale/*.yml
     ↓ i18n_gen.py / lv_i18n compile
i18n_generated.c + i18n_generated.h
     ↓
Flash 中的 const 字符串表
```

适用场景：

- 2～5 种语言，文案数量中等，语言版本与固件版本一起发布。
- MCU 没有可靠文件系统，或不希望引入运行时解析、堆分配和异常恢复。
- 设备网络能力弱，语言不需要独立 OTA。
- 希望启动快、运行时路径简单、问题容易复现。

优点是稳定、占 RAM 少、无需运行时解析；代价是增加一种语言通常会增加 Flash，文案修订需随固件或资源包发布。

#### 5.2 LVGL 9 原生 `lv_translation`

LVGL 9 已提供 `lv_translation` 模块。已知翻译在编译期确定时，可用 `lv_translation_add_static()` 注册语言、标签和翻译数组；运行时用 `lv_translation_set_language()` 选择语言，用 `lv_tr("tag")` 获取文本。部分控件还提供 `*_set_translation_tag()`，语言变化时能自动更新其文本。

简化示例：

```c
static const char * const s_languages[] = {
    "zh-CN", "en-US", NULL
};

static const char * const s_tags[] = {
    "settings.title", "settings.language", "common.confirm", NULL
};

/* 顺序：第 1 个 tag 的所有语言，再到第 2 个 tag。 */
static const char * const s_translations[] = {
    "设置", "Settings",
    "语言", "Language",
    "确定", "Confirm",
};

void app_i18n_init(void)
{
    lv_translation_add_static(s_languages, s_tags, s_translations);
    lv_translation_set_language("zh-CN");
}

void settings_page_create(lv_obj_t * parent)
{
    lv_obj_t * title = lv_label_create(parent);
    lv_label_set_translation_tag(title, "settings.title");
}
```

它非常适合作为**运行时查询和语言变更通知层**。但企业工程仍建议在它上面保留自己的语言键命名、资源目录、生成脚本、版本校验和页面规范，而不是把所有文案数组手写在某一个页面 `.c` 文件里。

对于动态载入的语言，LVGL 9 也支持动态翻译包；不过该方式会涉及内存分配。资源受限的设备不要在 UI 线程中临时解析和逐条申请内存，更推荐“后台读文件/校验 → 一次性建立资源 → UI 线程切换”的流程。

#### 5.3 LVGL 8 或存量项目：自研薄封装，或使用 `lv_i18n`

LVGL 8 没有 LVGL 9 的 `lv_translation` 这一原生 API。企业存量项目最常见的做法是保留一个很薄的自研 `i18n` 层：页面只依赖 `tr(key)`、`tr_fmt(key, ...)` 和 `language_set(locale)`，底层再选择静态 C 表、`lv_i18n` 或文件语言包。

官方 `lv_i18n` 是一套构建工具：它可从 C/C++ 源码中提取标记的字符串到 YAML，翻译完成后再生成 C/H 文件，并支持复数形式。它适合词条以 C 代码为主要入口、希望自动提取和生成的项目。

需要注意：`lv_i18n` 解决的是“查词和复数规则”，**不会自动知道哪些已经创建的 label、button、弹窗需要重绘**。无论 LVGL 8 还是 9，团队仍要实现统一的语言变更通知和页面刷新生命周期。

#### 5.4 运行时文件/OTA 语言包：按需采用

把 JSON、YAML、二进制表或 LVGL XML 翻译资源放到文件系统/分区中，适合：

- 嵌入式 Linux 或有可靠 Flash 文件系统的产品。
- 海外语言多、单个客户需要定制术语，或运营希望独立修正文案。
- 语言包需要通过 OTA 单独交付，避免为小文案升级整个固件。

代价也很明确：需要资源格式、签名/校验、容量上限、版本兼容、掉电恢复、回滚和内存策略。不要为了“两种语言的几个设置项”在 MCU 中引入复杂的 JSON 解析器。

#### 5.5 详细选型表

| 场景 | 推荐方案 | 说明 |
| --- | --- | --- |
| 小 MCU，中文/英文，量产固件 | 生成 `const` C 表 + 自研 `tr()` | 最简单可靠，RAM 小 |
| LVGL 9 新项目 | 生成资源 + `lv_translation` + 页面绑定 | 直接利用原生语言事件和 tag API |
| LVGL 8 多页面项目 | 生成 C 表或 `lv_i18n` + 页面刷新总线 | 统一抽象，未来可升级 LVGL |
| 多国家、多版本、文案独立 OTA | 带 manifest 的二进制语言包 | 需完整的校验、回滚和兼容设计 |
| 仅一台设备演示、页面极少 | 静态表也足够 | 不建议用 `#ifdef` 分裂两套页面 |


### 6. 推荐的工程目录与职责划分

一个可维护的目录可以这样组织：

```text
project/
├─ ui/
│  ├─ pages/                 # 只创建控件、绑定语言键、处理业务状态
│  └─ ui_i18n_bind.c         # 可见控件的绑定和统一刷新
├─ i18n/
│  ├─ locale/
│  │  ├─ zh-CN.yml           # 基准语言，产品确认的源文案
│  │  ├─ en-US.yml
│  │  └─ ja-JP.yml
│  ├─ i18n_keys.yml          # 可选：统一键清单/说明/页面归属
│  ├─ tools/i18n_gen.py      # 校验、生成、字库字符收集
│  ├─ generated/             # 自动生成，禁止手改
│  │  ├─ i18n_generated.c
│  │  └─ i18n_generated.h
│  ├─ i18n_manager.c         # 当前语言、持久化、切换和事件
│  └─ i18n_format.c          # 参数、复数、日期/单位等格式化
└─ fonts/
   ├─ app_latin_20.c
   └─ app_cjk_20.c
```

职责要划清：

| 角色/模块 | 应负责什么 | 不应负责什么 |
| --- | --- | --- |
| 产品/翻译 | 词条语义、目标语言、术语一致性 | 改动 C 代码中的文本 |
| 生成脚本/CI | 键完整性、占位符、字符集、生成表 | 手工猜测翻译语义 |
| `i18n_manager` | 当前 locale、持久化、fallback、切换通知 | 直接保存页面对象指针 |
| 页面 | 绑定 key、响应语言变化、处理布局 | 自行维护 `if/else` 语言分支 |
| 字库工具 | 收集所有目标字符并生成/校验字体 | 因缺字临时改成别的文案 |


### 7. 词条设计：先定义稳定 key，再写翻译

#### 7.1 key 应表达语义和位置，而不是中文原文

推荐命名：

```text
settings.title
settings.language
network.wifi.connect
ota.download.progress
dialog.factory_reset.confirm
error.network.timeout
```

不推荐：

```text
setting1                    # 看不出语义
text_001                    # 无法查找和审校
设置                        # 源文案一改，key 就失效
confirm                     # 不同页面可能需要“确认/继续/删除”的不同语气
```

“确认”是否复用不能只看中文是否相同。例如删除弹窗的 `dialog.delete.confirm` 往往需要更明确的动作词；蓝牙配对的确认又可能是“配对”。优先保证翻译语境清楚，少量重复 key 的成本远低于海外文案出错的成本。

#### 7.2 一个词条文件示例

以 YAML 为例，翻译平台也可使用 CSV/XLSX，但最终应导出到可版本控制、可自动校验的格式：

```yaml
# zh-CN.yml
settings:
  title: "设置"
  language: "语言"
ota:
  download_progress: "正在下载：%d%%"
network:
  connected_count:
    one: "已连接 %d 台设备"
    other: "已连接 %d 台设备"
```

```yaml
# en-US.yml
settings:
  title: "Settings"
  language: "Language"
ota:
  download_progress: "Downloading: %d%%"
network:
  connected_count:
    one: "%d device connected"
    other: "%d devices connected"
```

建议同时维护词条注释或上下文，例如页面名、最大显示行数、变量含义和截图链接。翻译人员看到 `ota.download.progress` 和“`%d` 为 0~100 的百分比”后，质量会明显高于只得到孤立的“下载中”。

#### 7.3 用 enum 还是字符串 key

两者可以结合：外部资源和翻译平台使用可读字符串 key，生成代码为内部 enum 和数组下标。

```c
typedef enum {
    I18N_SETTINGS_TITLE,
    I18N_SETTINGS_LANGUAGE,
    I18N_OTA_DOWNLOAD_PROGRESS,
    I18N_KEY_COUNT,
} i18n_key_t;

const char * i18n_tr(i18n_key_t key);
```

这样页面编译期能发现不存在的 key，运行时查表是 `O(1)`，又不丢失资源文件的可读性。LVGL 9 原生 API 使用字符串 tag 时，也可以由生成脚本输出 `I18N_TAG_SETTINGS_TITLE` 宏，避免手写拼写错误。


### 8. 运行时架构：LanguageManager 必须是唯一入口

#### 8.1 语言状态不能分散在各页面

语言选择应由唯一模块保存和切换：

```text
设置页点击语言
      ↓
LanguageManager 校验 locale 是否已安装
      ↓
写入持久化配置（NVS / KV / 配置文件）
      ↓
在 UI 线程设置当前语言
      ↓
通知活动页面、弹窗、键盘、状态栏刷新
      ↓
重新布局并重绘
```

基本接口可以控制在很小范围：

```c
typedef enum {
    APP_LOCALE_ZH_CN,
    APP_LOCALE_EN_US,
    APP_LOCALE_JA_JP,
} app_locale_t;

bool app_language_set(app_locale_t locale);   /* 只允许 UI 线程调用 */
app_locale_t app_language_get(void);
const char * i18n_tr(i18n_key_t key);
```

关键约束：

- 默认语言必须明确，通常为 `en-US` 或产品定义的基准语言；不能让“数组第 0 项”成为隐式规则。
- 持久化值无效、语言包丢失或新固件删除该语言时，应回退默认语言并修正存储值。
- 语言切换、创建/删除控件、调用 LVGL API 都应在同一个 UI 线程/任务完成。后台线程只投递消息，不能直接改 label 文本。
- 语言切换是一次 UI 状态变更。应禁用重复点击或做幂等判断，避免连续两次切换导致部分页面取到旧语言。

#### 8.2 页面如何响应语言切换

推荐按页面生命周期实现：

```c
typedef struct {
    lv_obj_t * title;
    lv_obj_t * language_row;
} settings_page_t;

static void settings_page_refresh_i18n(settings_page_t * page)
{
    lv_label_set_text(page->title, i18n_tr(I18N_SETTINGS_TITLE));
    lv_label_set_text(page->language_row, i18n_tr(I18N_SETTINGS_LANGUAGE));
    lv_obj_update_layout(lv_obj_get_parent(page->title));
}
```

页面创建后注册“语言变化”观察，销毁前解除注册；管理器只持有观察者句柄或弱生命周期对象，不能永久保存已销毁 `lv_obj_t *`。对于复杂页面，通常只刷新当前 screen、顶层 popup、公共状态栏和仍保活的页面；不在对象树中的页面可在下次进入时按当前语言创建。

LVGL 9 使用 `lv_label_set_translation_tag()` 等原生绑定 API 时，控件语言文本可随 `lv_translation_set_language()` 自动更新；但下列内容仍应由页面的语言变化回调处理：

- 含参数的动态文本，如进度、计数、错误码和设备名称。
- 下拉选项、表格、列表数据、键盘候选词、图表图例等复合控件。
- 本地化日期、单位、页面标题和业务状态组合文案。
- 因翻译长度改变而需重新选择布局、图片或方向的页面逻辑。

#### 8.3 不要缓存翻译字符串的裸指针

若语言包允许替换、卸载或动态加载，不要把 `const char *` 从 `tr()` 返回后长期存入业务对象。语言变化后该指针可能代表旧语言甚至已失效资源。

推荐保存 key 和业务参数，需要显示时再格式化；或者在收到语言事件后立刻通过 `lv_label_set_text()` 复制文本。只有静态常驻 C 字符串且控件明确使用 `lv_label_set_text_static()` 时，才可以安全复用常量指针。


### 9. 动态文案：参数、复数、时间和单位

#### 9.1 不能用字符串拼接表达语义

错误写法：

```c
snprintf(buf, sizeof(buf), "%s%d%s", i18n_tr(I18N_DOWNLOADED), value,
         i18n_tr(I18N_PERCENT));
```

不同语言的词序、空格和标点不同，正确做法是让整句成为一个词条：

```c
lv_label_set_text_fmt(label, i18n_tr(I18N_OTA_DOWNLOAD_PROGRESS), progress);
```

注意 `lv_label_set_text_fmt()` 会分配并保存格式化结果；高频刷新（例如每 10 ms 的进度）要限制刷新频率，或使用页面自有缓冲区和 `lv_label_set_text_static()`，同时保证缓冲区生命周期正确。

#### 9.2 占位符必须由 CI 校验

每种语言中同一个 key 的占位符数量和类型必须兼容：

| 基准词条 | 允许的翻译 | 不允许的翻译 |
| --- | --- | --- |
| `"温度：%.1f °C"` | `"Temperature: %.1f °C"` | `"Temperature: %d °C"` |
| `"正在下载：%d%%"` | `"Downloading: %d%%"` | `"Downloading: %s"` |
| `"设备 %s 已连接"` | `"Device %s connected"` | 漏掉 `%s` |

生成脚本至少要检查：key 集合是否一致、`printf` 占位符是否匹配、字符串是否为合法 UTF-8、是否包含不允许的控制字符。对于参数位置会变化的语言，应采用支持位置参数的格式约定，或封装命名参数格式化，不能靠固定拼接顺序。

#### 9.3 复数和业务状态要建模

英文的“1 device / 2 devices”、俄语等语言的复数形式与中文不同。不要维护 `I18N_FILE_SINGULAR` 和 `I18N_FILE_PLURAL` 后在页面里写英语规则；应提供：

```c
const char * i18n_tr_plural(i18n_key_t key, int32_t count);
```

由语言资源或 `lv_i18n` 根据 locale 选择 `one / other / few / many` 等形式。`lv_i18n` 已支持从 YAML 生成复数规则；若项目只面向中英文，也应先保留这个 API，避免后续扩展时改遍业务代码。

时间、日期、温度、距离、货币等同理：业务层传递数值和单位枚举，`i18n_format` 根据 locale 输出显示字符串。通信协议、存储和计算层仍使用统一的 SI 单位/UTC，不能因为切换显示语言而改变底层数据语义。


### 10. 字体、编码与 RTL：最容易在真机暴露的问题

#### 10.1 UTF-8 不是字库

LVGL 的文本使用 UTF-8；工程文件、生成的 C 文件和语言资源统一用 UTF-8 保存。但真正决定能否显示的是当前 `lv_font_t` 是否包含对应 Unicode 字形。

字体处理建议：

1. 从所有 locale 文件收集字符，去重后额外加入数字、英文、标点、单位和 LVGL 图标符号。
2. 按字号、字重和语言生成字库子集，不要直接把完整 CJK TTF 转成巨大的 C 数组。
3. 使用 LVGL Font Converter 或离线转换工具生成 C 字库；将生成过程纳入构建脚本。
4. 对“拉丁主字体 + CJK fallback 字体”建立明确链路，并在真机检查回退字形的视觉一致性。
5. 新增词条时，CI 重新收集字符并检查字库覆盖；不要等海外用户看到方块才补字。

字体取舍：

| 做法 | 优点 | 风险/适用条件 |
| --- | --- | --- |
| C 数组子集字体 | 无文件系统、启动稳定、速度可控 | CJK 字符多时 Flash 增长明显 |
| binfont/文件字体 | 可独立升级字体，固件更小 | 依赖文件系统和读取延迟策略 |
| Tiny TTF / FreeType 运行时字形 | 覆盖广、字号灵活 | RAM/CPU/缓存和授权评估更复杂 |

#### 10.2 布局必须按最长语言设计

语言切换后不仅改 label 的文本，还会影响对象尺寸、换行和滚动。企业项目应优先使用 Flex/Grid、内容自适应和合理的最大行数，而不是给每个中文标签写固定像素宽度。

- 按目标语言的最长已审校文案验收，不按中文长度猜。
- 关键操作按钮优先保证可见和可点击；空间不足时重排为两行/纵向，而不是静默截断。
- 允许省略号时，保留完整含义到详情/tooltip；错误、告警和确认动作不宜只显示半句。
- 切语言后调用布局更新，检查弹窗高度、列表项高度、滚动范围和焦点位置。
- 截图自动化测试要覆盖短文本、长文本和极端伪本地化文本。

##### 10.2.1 中文切换英文后显示不全：排查与解决

这类问题通常不是“英文显示异常”，而是页面按中文长度写死了宽高。英文单词、短语和按钮文案往往更长；切换语言后如果仍保留中文状态下的控件尺寸或布局结果，就会出现截断、重叠、按钮文字不完整、弹窗高度不足等现象。

可按下面顺序处理：

| 优先级 | 处理方法 | 适用说明 |
| --- | --- | --- |
| 1 | 改为 Flex/Grid、百分比宽度和内容自适应高度 | 根本方案。避免给 label、按钮和弹窗写死仅够中文使用的像素宽高 |
| 2 | 空间不足时重排 | 按钮改为两行或纵向排列；列表项、弹窗随内容增高，优先保证关键操作可点击 |
| 3 | 为文字选择正确的溢出策略 | 标题/说明允许换行；非关键辅助信息可用省略号；必须完整阅读的长文本放到滚动区或详情页 |
| 4 | 优化目标语言文案 | 由翻译人员给出符合语境的短文案；不要依赖生硬缩写，更不要为了塞下文字无限缩小字号 |
| 5 | 切换语言后统一重新布局 | 更新文本后刷新当前页面、popup 和列表，重新计算对象尺寸、滚动范围和焦点位置 |
| 6 | 用极端文本做回归 | 对最长已审校文案和伪本地化长文本做截图/真机验证，尽早发现溢出 |

实践原则：**布局要适应文本，不能让文本硬塞进中文尺寸的控件。** 对“删除、确认、告警、升级”等关键动作，不应仅用省略号隐藏后半句；宁可换行、增高或改为纵向布局，也要让用户看清完整含义。

排查时先确认以下三点：控件是否使用固定宽高、label 是否被设置为单行/省略模式、语言切换后是否执行了页面刷新和布局更新。三个都正常后，再检查字体度量、父容器裁剪和翻译文案本身是否异常。

#### 10.3 RTL 不是把字符串反过来

阿拉伯语、波斯语、希伯来语涉及文字方向和双向文本。LVGL 支持 RTL/双向文本相关能力，但产品还需在目标真机验证数字、括号、单位、图标方向、列表顺序和返回箭头。

如果产品正式支持 RTL，应在页面规范中明确：哪些容器镜像、哪些图标保持物理方向、输入框和数字如何处理。不要简单反转 UTF-8 字节或把所有图片水平翻转。


### 11. 语言切换与资源 OTA 的工程细节

#### 11.1 启动和切换顺序

推荐顺序：

```text
启动
  → 读取设备配置中的 locale
  → 检查该语言资源与当前固件/API 是否兼容
  → 加载默认语言或目标语言字体/词条
  → 创建首页
  → 用户切换语言
  → 校验后写入并确认持久化 locale
  → UI 线程原子应用新语言、刷新当前可见 UI、重新布局
```

如果目标语言资源加载失败，界面应继续可用并回退到默认语言，记录清晰日志和错误码；不能把 key 名、空指针或半套新旧语言暴露给用户。

#### 11.2 OTA 语言包不能只替换一个文件

支持独立语言包时，至少应有 manifest：

```text
locale: en-US
pack_version: 12
min_firmware_i18n_api: 3
keyset_hash: 7f...ab
font_version: 5
payload_crc / signature: ...
```

更新流程建议为：后台下载临时文件 → 验签/CRC/长度/版本/键集校验 → 写入新 slot 或临时目录 → 原子切换 manifest → 下次加载。运行中的语言包不能被直接覆盖；掉电后要么使用旧包，要么使用完整新包。

对于安全或合规产品，语言包也应纳入签名验证。攻击者篡改文案可能诱导用户执行危险操作，不能把它当成纯 UI 资源而放弃校验。


### 12. 自动化验收：把“漏翻译”和“缺字”挡在发布前

建议在 CI 加入下面的检查：

| 检查项 | 应发现的问题 |
| --- | --- |
| key 集合一致性 | 某语言漏译、无用 key、拼写不一致 |
| fallback 报告 | 目标语言实际回退到默认语言的词条 |
| 格式串检查 | `%d/%s/%.1f` 数量或类型不匹配 |
| UTF-8 与控制字符检查 | 编码损坏、换行/不可见字符混入 |
| 字体字符覆盖 | 新增汉字、日文、重音字符显示为方块 |
| 禁止硬编码扫描 | 页面中遗留中文/英文 UI 文案 |
| 伪本地化截图 | 长文本溢出、控件遮挡、弹窗高度不足 |
| 真机切换回归 | 切换后当前页、弹窗、键盘、状态栏是否全部刷新 |

伪本地化是一种很实用的布局测试。例如把 `Settings` 变为 `［Šëţţïñğş———］`，既能明显看出未走 `tr()` 的硬编码文本，也能放大长度问题。它不是实际翻译，但能在没有全部海外译文时提前发现布局缺陷。

运行时日志也应可诊断：记录 locale、语言包版本、缺失 key、fallback 次数、加载失败原因。开发版可以对缺失 key 显示 `⟦missing: settings.title⟧`；量产版应回退默认语言并上报诊断，避免用户看到内部 key。


### 13. 常见失败方式与处理

| 现象 | 常见根因 | 处理方式 |
| --- | --- | --- |
| 切到英文后只有部分页面变了 | 页面没有订阅语言事件，或缓存了旧文本 | 建立统一 refresh 注册/解除机制 |
| 显示方块、问号或乱码 | 字体没有字形、文件编码不一致 | 统一 UTF-8，按全部 locale 生成字库并做覆盖检查 |
| 英文按钮被截断 | 固定宽度按中文设计，未重布局 | Flex/Grid、最长文案验收、必要时换行 |
| 切语言后崩溃 | 页面已销毁但仍被回调，或后台线程直调 LVGL | 解除观察者；所有 LVGL 修改回 UI 线程 |
| 弹窗里仍是旧语言 | 只刷新 screen，没有管理顶层 popup/keyboard | 将全局 overlay 纳入语言刷新范围 |
| 进度文本偶发错乱 | 多线程同时改同一 label，或格式化缓冲生命周期错误 | UI 消息队列串行更新，明确 buffer 所有权 |
| 翻译中 `%d` 导致异常 | 占位符类型/数量与基准不一致 | 构建期格式串校验，翻译平台限制占位符编辑 |
| 新固件启动后回到中文 | 存储的 locale 不存在或新包不兼容 | fallback 默认语言，同时更新/迁移配置 |
| OTA 后语言切一半 | 直接覆盖运行中的资源文件 | 双 slot/临时文件 + manifest 原子切换 |


### 14. 一个可落地的最小实施步骤

如果现有 LVGL 项目已经有中文硬编码页面，可以按以下顺序改造：

1. 先确定目标语言、默认语言和语言包发布方式；通常从 `zh-CN + en-US + 静态 C 表` 起步。
2. 建立 `i18n_key_t`、`i18n_tr()` 和 `LanguageManager`，先不大改页面。
3. 从设置、首页、公共弹窗、错误提示开始，把硬编码文案换成 key；禁止在新页面继续写 UI 字面量。
4. 建立 `zh-CN.yml` 基准词条和 `en-US.yml`，用脚本生成 C/H 文件并接入构建。
5. 给页面加入语言变化刷新；优先覆盖当前 screen、公共状态栏、toast、modal、键盘。
6. 从所有词条收集字符，生成字体子集，在真机验证中文、英文、数字、符号和单位。
7. 加入 key、格式串、字体覆盖和硬编码扫描 CI；用伪本地化做布局回归。
8. 词条和字体规模稳定后，再评估是否需要 LVGL 9 原生绑定、`lv_i18n` 复数能力或独立 OTA 语言包。

这比一次性把全部页面重写为两套语言分支风险小，也便于逐步验证。


### 15. 面试角度常见问题

#### 15.1 你在 LVGL 项目里如何实现多语言？

可以这样答：

> 我们没有在页面里直接判断中英文，而是把 UI 文案抽成稳定的语言 key。翻译源文件按 locale 管理，构建时校验 key、格式化占位符和字体字符集，再生成只读 C 表放入 Flash。运行时由统一的 LanguageManager 保存和切换当前语言，页面创建时绑定 key；切语言时通过 UI 线程通知当前页面、弹窗和公共组件刷新并重新布局。这样文案、翻译、字体和页面逻辑可以分别维护，后续增加语言或做 OTA 语言包也不会改动业务代码。

#### 15.2 为什么不能在每个页面用 `if (lang == EN)`？

因为它会把翻译、页面逻辑和语言切换耦合在一起：改一条文案要改多处代码，难以统计漏翻译，也无法让翻译人员独立审校。语言增加后条件分支会迅速膨胀，当前页面、弹窗和保活页面也容易漏刷新。集中词条和统一刷新能让问题在构建期或单一模块中被发现。

#### 15.3 多语言时中文显示不出来，你怎么排查？

先确认资源和源码是否是 UTF-8，再检查 label 使用的 `lv_font_t` 是否真正包含目标汉字，最后检查字体是否正确编译和链接。不能只看 `LV_TXT_ENC_UTF8`；编码正确但字体没有字形同样会显示方块。工程上应从全部语言资源自动收集字符，生成字库并做覆盖检查。

#### 15.4 切换语言时如何避免 UI 崩溃或卡顿？

语言切换只在 UI 线程执行，后台加载语言包后通过消息队列投递；页面销毁时解除语言观察，避免回调访问悬空 `lv_obj_t *`。对当前可见页面做批量刷新和一次布局更新，不在每个 label 更新后立即刷新屏幕。大字库或文件语言包提前加载/校验，失败时完整回退默认语言。


### 16. 速记总结

- **主方案**：`语言 key + 集中资源 + 构建生成 + LanguageManager + UI 刷新`。
- **默认落地**：小到中等资源设备优先把审核后的词条编译为 `const` C 表，放 Flash，不在 UI 线程解析 JSON。
- **LVGL 9**：可用 `lv_translation_add_static()`、`lv_tr()`、`lv_translation_set_language()` 和控件 translation tag；复杂动态内容仍要页面刷新。
- **LVGL 8**：用薄封装保持 `tr()/language_set()` API，底层可接自研表或 `lv_i18n`；不要把 LVGL 9 API 直接搬过去。
- **字体**：UTF-8 不等于有字形；从所有词条收集字符并生成字体子集。
- **布局**：按最长语言做 Flex/Grid 和真机截图验证，不能按中文固定宽度。
- **动态文本**：整句做词条，校验占位符；复数、日期、单位由 locale 规则处理，禁止字符串拼接。
- **切换语言**：唯一管理器、UI 线程、刷新 screen + popup + keyboard、页面销毁即解除观察。
- **OTA 语言包**：需要版本、键集、CRC/签名、原子切换和回滚，不能直接覆盖正在使用的文件。
- **验收**：key/占位符/字体覆盖/硬编码扫描/伪本地化截图/真机切换回归缺一不可。
