# 页面卡顿排查与验证记录

## 目标

定位相册页面切换卡顿的主要来源，区分以下阶段的耗时：

- LittleFS 目录扫描和图片文件读取；
- PNG 解码及图片缩放；
- LVGL 布局和 Tile 绘制；
- SPI DMA 传输与 LCD 物理刷新。

显示屏分辨率为 240×320，像素格式为 RGB565。本文所有刷新数据均来自实际设备日志。

## 时序观测方法

为避免把其它 LVGL 定时器（例如温湿度刷新）混入显示刷新时间，在 LVGL
`_lv_disp_refr_timer()` 中、布局更新前触发 `render_start_cb`，记录微秒级 `T0`。

一次有实际脏矩形输出的刷新帧记录以下节点：

```text
T0                    LVGL 刷新开始：布局与脏区处理之前
Tf1 ... TfN           第 N 个 Tile 进入 flush_cb 并提交 SPI DMA
Td1 ... TdN           第 N 个 Tile 的 SPI DMA 完成
LVGL frame draw end   monitor_cb：LVGL 本帧绘制处理结束
LCD physical done     最后一个 Tile DMA 完成，屏幕物理刷新完成
```

各时间点的含义如下：

- `T0`：一次 LVGL 刷新真正开始。在 `_lv_disp_refr_timer()` 中、布局更新和脏矩形处理之前记录；不包含温湿度等其它 `lv_timer_handler()` 任务。
- `Tf1 ... TfN`：第 N 个 Tile 进入 `flush_cb` 的时刻。该 Tile 已完成 LVGL 绘制，随后调用 `lcd_draw_bitmap()` 提交 SPI DMA。
- `Td1 ... TdN`：第 N 个 Tile 的 SPI DMA 完成时刻，在 LCD SPI 完成回调中记录；表示该 Tile 的像素数据已传输到 LCD 控制器。
- `LVGL frame draw end`：`monitor_cb` 被调用的时刻，表示 LVGL 已完成本帧的布局、脏区处理和所有 Tile 的绘制/提交；最后一笔 DMA 仍可能在进行。
- `LCD physical done`：最后一个 Tile 的 `TdN`，表示最后一笔 DMA 已完成，是本帧物理刷新完成点。

`Tf(N+1) - TdN` 表示前一个 Tile DMA 完成后，LVGL 准备和绘制下一个 Tile 的时间。
它通常包含图片解码、缩放、图像混合、PSRAM 写入及控件绘制，不包含 SPI 传输。

可由这些时间点计算：

```text
首 Tile 的布局与绘制耗时 = Tf1 - T0
第 N 个 Tile 的 DMA 耗时  = TdN - TfN
下一 Tile 的绘制处理耗时 = Tf(N+1) - TdN
LVGL 本帧处理耗时         = frame_draw_end - T0
物理刷新总耗时             = Td_last - T0
绘制结束后的 DMA 尾延迟    = Td_last - frame_draw_end
```

日志仅在 Tile 数达到配置门槛时输出，避免小面积局部刷新干扰串口和观察结果。

## 基线：PNG 相册页，8 Tile

使用 `LCD_TEST_LINES=40`，整屏刷新被拆成 8 个 240×40 Tile。原相册页从
LittleFS 读取 PNG，并在 `lv_img` 中缩放显示。

| 指标 | 耗时 |
|---|---:|
| `T0` 到物理刷新完成 | 1,351.106 ms |
| 首 Tile 提交前 | 45.989 ms |
| 8 次 SPI DMA 合计 | 41.952 ms |
| Tile 间绘制处理合计 | 1,263.165 ms |

最大的 Tile 间处理时间为 256.398 ms 和 251.183 ms。SPI DMA 仅占总耗时约 3.1%，
卡顿发生在 LVGL 下一 Tile 的准备和绘制阶段。

## 分块大小对照

将缓冲区改为两个 240×160 Tile 后，PNG 相册刷新为 655.782 ms，相比 8 Tile 的
1,351.106 ms 减少 695.324 ms（51.5%）。DMA 总耗时仍约 38.5 ms，基本未变。

这说明慢操作会随 Tile 次数重复；仅增大缓冲区能缓解问题，但不能消除根因。

返回首页从 8 Tile 的 162.039 ms 降至 2 Tile 的 140.183 ms（13.5%）。首页对 Tile
数量不敏感，也说明相册图片路径才是主要的重复性负载。

## 预解码图片对照实验

为排除 LittleFS、PNG 解码和缩放，使用 `app/ui/home/sub_home/album/photo/1.png` 进行临时测试：

- 原图尺寸为 240×160；
- 构建期转换为 RGB565 原始数据，直接内嵌进应用固件；
- 页面跳转时跳过 `album_flash_init()`，不扫描目录、不读取 PNG 文件；
- 图片视口设置为 240×160，直接以原始尺寸显示，不缩放；
- 保持 `LCD_TEST_LINES=40`，确保仍为 8 Tile，便于与基线对比。

预解码测试的结果如下：

| 指标 | PNG 相册页 | 预解码 RGB565 页 | 差异 |
|---|---:|---:|---:|
| `T0` 到物理刷新完成 | 1,351.106 ms | 283.091 ms | -1,068.015 ms（-79.0%） |
| 8 次 SPI DMA 合计 | 41.952 ms | 42.136 ms | 基本不变 |
| Tile 间绘制处理 | 1,263.165 ms | 182.577 ms | -1,080.588 ms |

预解码页仍有两个明显热点：

```text
Tile3 DMA 完成 → Tile4 提交：79.694 ms
Tile4 DMA 完成 → Tile5 提交：77.570 ms
```

这些 Tile 位于图片主体区域。预解码后仍需由 LVGL 将 240×160 RGB565 图像混合并写入绘图缓冲，
因此仍存在图像绘制和内存写入成本；但它远小于 PNG 路径的成本。

## 首页基线与剩余绘制成本

返回首页的 8 Tile 刷新为 162.703 ms，其中 8 次 DMA 为 39.924 ms。预解码相册页相比首页
额外约 120.388 ms，这部分主要是原始图片的 LVGL 绘制和相册页面视觉元素开销。

预解码实验不能再区分“文件读取”和“PNG 解码”各自的精确比例，因为两者同时被移除；同时也移除了
缩放。但它已足以证明原 PNG 文件路径及缩放占原相册刷新耗时的主要部分。

## 结论

1. 页面卡顿的主因不是 SPI 时钟或 DMA。不同实验中整屏 DMA 始终约为 40–42 ms。
2. 原 PNG 相册页约 79% 的刷新时间可通过去除 LittleFS/PNG/缩放路径消除。
3. 预解码后的剩余耗时来自 LVGL 原始图像绘制、PSRAM 绘图缓冲写入及相册页面控件效果。
4. 增大 Tile 可以减少重复解码次数，但只是缓解措施；最终方案应避免在刷新路径中解码或缩放 PNG。

## 推荐优化顺序

1. 为相册缩略图在构建期生成目标尺寸 RGB565，或在后台任务中预解码到 PSRAM 缓存。
2. 启动时或后台维护相册索引，避免点击时列目录和加载文件。
3. 页面切换前预创建相册控件，降低首 Tile 的布局和对象创建成本。
4. 减少图片缩放、半透明混合、圆角裁剪、阴影和大面积渐变等高成本效果。
5. 完成图片缓存后，再根据内存余量调整 Tile 大小；此时 DMA 的约 40 ms 才会成为主要固定成本。

## 复现与判读

1. 使用 `./build.sh build` 构建，并烧录到同一硬件环境。
2. 保持 `LCD_TEST_LINES=40`，确保一帧输出 8 个 Tile。
3. 分别记录 PNG 页面和预解码页面的 `T0`、`TfN`、`TdN` 与物理完成时间。
4. 对每帧计算：

   ```text
   DMA 总耗时 = Σ(TdN - TfN)
   Tile 绘制处理 = (Tf1 - T0) + Σ(Tf(N+1) - TdN)
   刷新总耗时 = Td_last - T0
   ```

5. 若预解码页面的 Tile 间处理时间显著低于 PNG 页面，而 DMA 接近，则可确认瓶颈在图片文件/解码/缩放路径，而非 SPI DMA。
