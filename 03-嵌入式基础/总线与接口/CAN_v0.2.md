# CAN FD 和 CAN XL 基础知识总结

> 目标：这篇文档接在 CAN 基础之后，只讲经典 CAN 到 CAN FD、再到 CAN XL 的演进逻辑，不展开汽车网络架构、AUTOSAR 协议栈和功能安全。重点记住：经典 CAN 卡在哪里、CAN FD 改了什么、CAN XL 又改了什么、三者的帧格式和速率差在哪、能不能混在一条总线上、各自适合什么场景。
>
> 前置阅读：建议先看 `CAN.md`，本文默认你已经理解差分电平、显性隐性、仲裁、终端电阻和 ACK 这些概念。
>
> 来源：围绕 CAN FD / CAN XL 主题AI整理的基础总结文档，本人未在量产项目中接触过 CAN XL，所以仅供参考，适合扫盲和建立整体认识。

## 第一章、从经典 CAN 的瓶颈说起

**CAN FD 和 CAN XL 不是新总线，而是经典 CAN 在“帧里能装多少”和“数据段能跑多快”这两件事上的两次扩容。**

### 1.1、三代演进总览

```text
三代演进（双线差分介质、显隐性规则、逐位仲裁三者完全相同）：

  经典 CAN
    ├─ 数据区 8 字节
    └─ 全程 ≤ 1 Mbps

  ↓ 扩容

  CAN FD
    ├─ 数据区 64 字节
    └─ 数据段 2 ~ 5 Mbps（仲裁段仍 ≤ 1 Mbps）

  ↓ 再扩容

  CAN XL
    ├─ 数据区 2048 字节
    ├─ 数据段 10 ~ 20 Mbps（仲裁段仍 ≤ 1 Mbps）
    └─ 数据段可改用 PWM 编码，此时需要 SIC XL 收发器
```

| 名称 | 全称 | 标准 | 数据区 | 数据段速率 |
| --- | --- | --- | --- | --- |
| `CAN` | Classical CAN | ISO 11898-1 | `8` 字节 | 同仲裁段，≤ `1 Mbps` |
| `CAN FD` | CAN with Flexible Data-Rate | ISO 11898-1:2015 | `64` 字节 | `2 ~ 5 Mbps` |
| `CAN XL` | CAN with eXtra Long payload | CiA 610-1 / ISO 11898-1:2024 | `2048` 字节 | `10 ~ 20 Mbps` |

三代共同保留的东西：

| 保留项 | 说明 |
| --- | --- |
| 差分信号线 | 还是 `CAN_H` / `CAN_L` 两根线 |
| 电平特性 | 还是显性覆盖隐性 |
| 仲裁机制 | 还是逐位比较，ID 数值小的优先 |
| 通信模型 | 还是广播式多主，没有目标设备地址 |
| 终端电阻 | 还是总线两端各一个 `120Ω` |

**结论：** 仲裁阶段的玩法完全没变，变的是仲裁赢了之后那一段。

### 1.2、瓶颈一：一帧只有 8 字节

经典 CAN 一帧最多 `8` 字节，传车速、转速、温度这类小信号完全够用，遇到下面这些场景就不够：

| 场景 | 数据量 | 经典 CAN 下的代价 |
| --- | --- | --- |
| 传标定参数 | `1 KB` | 拆成约 147 帧（ISO-TP 下连续帧只装 7 字节） |
| 刷写 ECU 固件 | 几百 KB | 拆成上万帧 |
| 带时间戳的多字段诊断响应 | `10 ~ 30` 字节 | 一帧装不下，要分包 |
| 带消息认证码 `MAC` | 额外 `4 ~ 8` 字节 | 8 字节里挤不出来 |

拆帧的代价不只是慢，还要在应用层做分包协议（比如 ISO-TP / ISO 15765-2 的多帧传输），需要流控帧、序号、超时重组，软件复杂度和出错概率都上去了。

直白说法：

> 经典 CAN 最难受的不是“慢”，而是“一帧太小”。为了传大块数据，被迫在上层再造一层分包协议。

### 1.3、瓶颈二：速率被仲裁卡住

经典 CAN 最高 `1 Mbps`，这个上限不是电路做不到，而是**仲裁机制的物理约束**：一个节点发出的电平，必须在同一个位时间内传到总线最远端，再传回来被自己采样到，否则两个节点比不出谁优先级高。

```text
仲裁期的时序约束（节点 A 发送，节点 B 在总线最远端）：

  ① A 发出电平 ──> 经 t 传播到 B
  ② B 处的电平 ──> 经 t 回读到 A 并被 A 采样
  ③ ①② 必须全部落在同一个位时间内

  结论：位时间 ≥ 信号在总线上往返一次的时间
        速率越高 → 位时间越短 → 允许的总线长度越短
```

| 波特率 | 典型最大总线长度 |
| --- | --- |
| `125 kbps` | 约 500 m |
| `250 kbps` | 约 250 m |
| `500 kbps` | 约 100 m |
| `1 Mbps` | 约 40 m |

**关键点：** 这个约束只在仲裁阶段成立。仲裁一结束，总线上只剩一个节点在发，没人要比位了，这时候再跑高速完全没问题。CAN FD 抓住的就是这个漏洞：

> 仲裁段保持低速保证仲裁正确，仲裁赢了以后切到高速把数据甩出去，发完再切回低速去做 ACK。

### 1.4、瓶颈三：开销占比高，而新需求还在加码

经典 CAN 标准帧传 8 字节数据，整帧大约 `111` 位（未算位填充，最坏可能到 `135` 位左右），将近一半的总线时间在传 SOF、ID、CRC、ACK、EOF 和帧间隔：

| 单帧数据量 | 有效载荷比例 |
| --- | --- |
| 8 字节 | 约 58% |
| 4 字节 | 约 40% |
| 1 字节 | 不到 15% |

与此同时，新需求还在往上压：

| 新需求 | 对总线的压力 |
| --- | --- |
| 信息安全 | 每帧要带 MAC 和新鲜度值，8 字节不够 |
| 高级驾驶辅助 | 雷达、摄像头的目标列表数据量大 |
| 服务化通信 | SOME/IP 这类面向服务的报文远超 8 字节 |
| 域控架构 | 网络往“少量高性能域控 + 大量传感执行器”演进，中间链路要比 CAN 快、比以太网便宜 |

## 第二章、CAN FD 和 CAN XL 各改了什么

### 2.1、CAN FD：三个新控制位与格式变化

这三个位是区分 CAN FD 帧和经典帧的根本：

| 位 | 全称 | 电平 | 作用 |
| --- | --- | --- | --- |
| `FDF` | FD Format | 隐性 = FD 帧 | 标识帧类型，早期叫 `EDL` |
| `BRS` | Bit Rate Switch | 隐性 = 数据段提速 | 控制是否切换比特率 |
| `ESI` | Error State Indicator | 隐性 = error passive | 指示发送节点的错误状态 |

| 要点 | 说明 |
| --- | --- |
| `FDF` 是兼容性的根源 | 它占用的是经典 CAN 的保留位，经典控制器看到会当成格式错误，详见第四章 |
| `BRS` 是可选的 | 可以只扩容不提速（`BRS` 显性），这种叫 **FD 无 BRS**，兼容性风险更小 |
| `ESI` 有诊断价值 | 接收方能看出发送节点是否已进入错误被动状态 |

数据变长以后，`15` 位 CRC 的检错能力不够了，同时远程帧也被取消：

| 改动 | 说明 |
| --- | --- |
| CRC 长度可变 | 数据 ≤16 字节用 `CRC-17`，>16 字节用 `CRC-21` |
| CRC 计入填充位 | 经典 CAN 的 CRC 不算填充位，CAN FD 算 |
| 新增填充计数 | CRC 场前有 3 位填充位计数 + 1 位奇偶校验 |
| CRC 场固定填充 | CRC 场每 4 位插一个固定填充位，而不是动态填充 |
| 取消远程帧 | `RTR` 位置变成恒显性的 `RRS`，写驱动时不能再当 RTR 用 |

加填充计数的原因：经典 CAN 存在一类罕见的漏检场景，填充位出错可能导致接收方对帧边界理解错误但 CRC 仍然通过。CAN FD 用“告诉接收方总共插了多少个填充位”来堵这个洞。

### 2.2、CAN FD：DLC 重新编码到 64 字节

经典 CAN 的 `DLC` 是 4 位，`0 ~ 8` 直接表示字节数，`9 ~ 15` 全都当成 8。CAN FD 把 `9 ~ 15` 这几个没用上的值重新定义了：

| DLC | 0~8 | 9 | 10 | 11 | 12 | 13 | 14 | 15 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 字节数 | 0~8 | 12 | 16 | 20 | 24 | 32 | 48 | 64 |

注意这是**离散的**，不是连续的，CAN FD 没有 40 字节这种长度：

| 想传 | 实际占用 | 浪费 |
| --- | --- | --- |
| `9` 字节 | `12` 字节帧 | 3 字节 |
| `17` 字节 | `20` 字节帧 | 3 字节 |
| `33` 字节 | `48` 字节帧 | 15 字节 |

所以设计 CAN FD 报文布局时，**尽量把信号打包到 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64 这些档位上**，不然白白浪费总线时间。

### 2.3、CAN FD：一帧两个速率

这是 CAN FD 最有意思的地方，一帧里有两个比特率：

```text
一帧之内的速率切换（以 500 kbps 仲裁段 / 2 Mbps 数据段为例）：

  [仲裁段 500 kbps]  SOF | ID | ... | FDF | res | BRS
        ↓ 在 BRS 的采样点之后切到数据段速率
  [数据段 2 Mbps  ]  ESI | DLC | Data | SC | CRC | CRC 界定符
        ↓ 在 CRC 界定符的采样点之后切回仲裁段速率
  [仲裁段 500 kbps]  ACK | ACK 界定符 | EOF | IFS

  两头必须慢的原因：前段要逐位仲裁，后段要多个节点在同一位内应答
```

| 规则 | 说明 |
| --- | --- |
| 切快的时刻 | `BRS` 位的**采样点**之后切到数据段比特率（该位前半段仍在仲裁段速率） |
| 切回的时刻 | CRC 界定符的**采样点**之后切回仲裁段比特率（该位前半段仍在数据段速率） |
| 位时序 | 两个速率各有一套独立参数（段长度、采样点、`SJW`） |

为什么 ACK 也要切回低速：ACK 位需要总线上任意节点同时应答，本质上和仲裁一样需要全网在一个位时间内达成一致，所以必须用慢速率。

**注意：** CAN FD 要配两套位时序——**标称位时序**（即前文的仲裁段速率，标准术语 nominal bit rate，ACK 段也用它）和**数据位时序**（数据段速率）。很多人只配了标称那套，数据段参数用默认值，结果高速段出错。

### 2.4、CAN XL：帧头重构与连续长度

如果说 CAN FD 是“把数据区撑大、数据段提速”，CAN XL 就是**在保留 CAN 仲裁的前提下，把帧结构重新设计了一遍**，目标是接住以太网的活。

| 字段 | 位宽 | 作用 |
| --- | --- | --- |
| `Priority ID` | 11 bit | **只管优先级，不再表示报文含义** |
| `XLF` | 1 bit | 标识这是 CAN XL 帧 |
| `SDT` | 8 bit | Service Data Unit Type，说明数据区装的是什么（CAN 映射、以太网帧、隧道数据等） |
| `SEC` | 1 bit | Simple Extended Content，指示是否带安全扩展头 |
| `DLC` | 11 bit | 直接编码 `1 ~ 2048` 字节，连续可取 |
| `VCID` | 8 bit | Virtual CAN Network ID，在一条物理总线上划分虚拟网络 |
| `AF` | 32 bit | Acceptance Field，接收过滤字段，把“寻址”从 ID 里剥离出来 |

最重要的观念转变是 ID 职责的拆分：

```text
经典 CAN / CAN FD：
    ID ─┬─> 仲裁优先级
        └─> 这是什么数据（含义 + 寻址）      一个字段干两件事

CAN XL：
    PID (11 bit) ──> 仲裁优先级
    SDT (8 bit)  ──> 数据区内容类型
    AF  (32 bit) ──> 寻址与接收过滤          三个字段各司其职
```

**注意：** CAN XL 取消了 29 位扩展 ID，仲裁标识固定为 11 位 `PID`，没有扩展帧格式。原先压在 ID 里的寻址和过滤职责改由数据段中的 32 位 `AF` 承担——`AF` 不参与仲裁，只用于接收过滤。好处是优先级和寻址可以独立设计，不用再为了“让这个报文优先级高一点”去硬凑 ID 数值；代价是从经典 CAN / CAN FD 迁移时，原有的 29 位 ID 体系必须重新映射。

数据区长度也和 CAN FD 完全不同：

| 特性 | CAN FD | CAN XL |
| --- | --- | --- |
| 最小长度 | `0` 字节 | `1` 字节（**没有 0 字节帧**） |
| 最大长度 | `64` 字节 | `2048` 字节 |
| 取值方式 | 离散档位 | **连续可取**，要 33 字节就是 33 字节 |

`2048` 这个数字不是随便定的，它能完整装下一个以太网帧（`1500` 字节 MTU 加上头部），所以 CAN XL 可以**直接隧道传输以太网帧**，这是它和 CAN FD 定位上最大的区别。

### 2.5、CAN XL：速率切换、编码与双 CRC

CAN FD 用 `BRS` 一个位切速率，CAN XL 改用两段专门的**同步序列**，并且数据段可以换掉 NRZ 编码：

| 机制 | 内容 | 说明 |
| --- | --- | --- |
| `ADS` | Arbitration to Data Sequence | 从仲裁段切入数据段 |
| `DAS` | Data to Arbitration Sequence | 从数据段切回仲裁段 |
| 仲裁段编码 | NRZ + 位填充 | 和经典 CAN 完全一样 |
| 数据段编码 | NRZ，或使能 `TMS` 后用 PWM | PWM 每个位自带跳变，接收端能持续恢复时钟 |
| 数据段填充 | 固定位填充 | 帧长度可精确预测，便于实时性分析 |

用固定的位模式序列而不是单个位切速率，是因为 CAN XL 的数据段速率太高（可到 `20 Mbps`），单个位的切换点容错太小。PWM 模式的代价是需要专门的 **SIC XL 收发器**（CiA 610-3），普通 CAN FD 收发器不行。

**注意：** 是否使用 PWM 由控制器的 `TMS`（Transceiver Mode Switch）配置决定，使能后收发器通过识别 `ADS` / `DAS` 序列自行切换模式，帧里并没有单独的 `TMS` 位。

CAN XL 还用了两级 CRC：

| CRC | 位宽 | 覆盖范围 | 作用 |
| --- | --- | --- | --- |
| 头部 CRC（`PCRC`） | 13 位 | 帧头 | 尽早确认 `DLC` 等关键字段没错 |
| 帧 CRC（`FCRC`） | 32 位 | 整帧 | 最终数据完整性校验 |

头部 CRC 是必需的：数据区最大 2048 字节，如果 `DLC` 传错了，接收方会按错误长度去收，整个帧同步就乱了。先校验头部再收数据，能大幅降低这个风险。

## 第三章、三者横向对比

### 3.1、完整对比表

这是本文最该记住的一张表：

| 对比项 | 经典 CAN | CAN FD | CAN XL |
| --- | --- | --- | --- |
| 标准 | ISO 11898-1 | ISO 11898-1:2015 | CiA 610-1 / ISO 11898-1:2024 |
| 数据区长度 | `0 ~ 8` 字节 | `0 ~ 64` 字节（离散档位） | `1 ~ 2048` 字节（连续） |
| 仲裁标识 | 11 / 29 位 ID | 11 / 29 位 ID | 11 位 Priority ID，**无扩展帧** |
| 寻址 / 过滤 | 靠 ID 本身 | 靠 ID 本身 | 32 位 AF 字段 |
| 仲裁段速率 | ≤ `1 Mbps` | ≤ `1 Mbps` | ≤ `1 Mbps` |
| 数据段速率 | 同仲裁段 | 常见 `2 / 5 Mbps` | `10 ~ 20 Mbps` |
| 双速率 | 不支持 | `BRS` 位控制 | `ADS` / `DAS` 序列 |
| 数据段编码 | NRZ | NRZ | NRZ 或 PWM |
| CRC | `15` 位 | `17` / `21` 位 | 头部 `13` 位 + 帧 `32` 位 |
| 远程帧 | 支持 | 不支持 | 不支持 |
| 虚拟网络 | 无 | 无 | `VCID` 支持 |
| 承载以太网帧 | 不行 | 不行 | 可以（`SDT` 指示） |
| 收发器要求 | 普通 CAN 收发器 | CAN FD 收发器 / SIC | PWM 模式必须用 SIC XL；NRZ 模式下可用满足目标速率的高速收发器 |
| 终端电阻 | `120Ω` ×2 | `120Ω` ×2 | `120Ω` ×2 |

两点补充：

| 说明项 | 内容 |
| --- | --- |
| `SIC` 是什么 | Signal Improvement Capability 收发器（CiA 601-4），抑制隐性边沿的振铃，其指标按 `5 Mbps` 数据段速率规定；有利拓扑下有跑到 `8 Mbps` 的案例，但不是规范保证值 |
| `20 Mbps` 怎么看 | 这是 CAN XL **数据段**的标准上限，不是可用净吞吐；实际能跑多少仍取决于拓扑、线缆和收发器 |

### 3.2、帧格式对照与类型判别

简化示意，省略了填充位和部分细节：

```text
经典 CAN 标准帧（全程单一比特率）：
SOF | ID(11) | RTR | IDE | r0 | DLC(4) | Data(0~8B) | CRC(15) | CRC 界定符 | ACK | ACK 界定符 | EOF | IFS

CAN FD 标准帧（按速率分三段列出）：
仲裁段速率：SOF | ID(11) | RRS | IDE | FDF | res | BRS
      ↓ 在 BRS 的采样点之后切到数据段速率
数据段速率：ESI | DLC(4) | Data(0~64B) | SC(4) | CRC(17/21) | CRC 界定符
      ↓ 在 CRC 界定符的采样点之后切回仲裁段速率
仲裁段速率：ACK | ACK 界定符 | EOF | IFS

CAN XL 帧：
仲裁段（≤1 Mbps）：SOF | PID(11) | RRS | IDE | FDF | XLF | resXL
切入序列          ：ADS
数据段（≤20 Mbps，可 PWM 编码）：
                    SDT(8) | SEC(1) | DLC(11) | SBC | PCRC(13) | VCID(8) | AF(32)
                  | Data(1~2048B) | FCRC(32)
切回序列          ：DAS
仲裁段（≤1 Mbps）：ACK | ACK 界定符 | EOF | IFS
```

三种帧靠开头几个位区分：

```text
SOF + 11 位基本 ID（三者一样，共同参与仲裁）
    │
    └─ 跳过 RTR / SRR / RRS 位（该位不用于类型判别）
        │
        └─ 读 IDE 位
            │
            ├─ 隐性 = 扩展帧 ──> 只可能是经典 CAN 或 CAN FD
            │
            └─ 显性 = 标准帧
                │
                └─ 读 FDF 位
                    │
                    ├─ 显性 ──> 经典 CAN 帧
                    │
                    └─ 隐性 ──> 读 XLF 位
                                │
                                ├─ 显性 ──> CAN FD 帧
                                │
                                └─ 隐性 ──> CAN XL 帧
```

**注意：** 扩展帧的 IDE 之后还有 18 位扩展 ID，`FDF` 位相应后移；CAN XL 没有扩展帧格式，所以扩展帧只可能是经典 CAN 或 CAN FD。

| 字段 | 说明 |
| --- | --- |
| `SC` / `SBC` | 填充位计数 |
| `PCRC` | CAN XL 的头部 CRC |
| `FCRC` | CAN XL 的帧 CRC |

直白说法：

> 三种帧在仲裁阶段长得一模一样，谁优先级高谁赢。赢了之后才亮明身份：我是经典帧、FD 帧还是 XL 帧。

### 3.3、速率和效率到底提升了多少

仲裁段固定 `500 kbps`，配不同数据段速率传 64 字节，做个粗略估算（CAN FD 整帧约 `580` 位，已含位填充，未计填充时为 `572` 位；其中约 `30` 位跑在仲裁段速率上，约 `550` 位跑在数据段速率上）：

| 方案 | 帧数 | 大致耗时 | 说明 |
| --- | --- | --- | --- |
| 经典 CAN `500 kbps` | 8 帧 | 约 `2000 μs` | 每帧按约 `125` 位估算（含位填充与 `3` 位帧间隔），约 `250 μs` |
| CAN FD 无 BRS | 1 帧 | 约 `1160 μs` | 只扩容不提速，省掉了 7 份帧头开销 |
| CAN FD `500k/2M` | 1 帧 | 约 `340 μs` | 数据段跑 `2 Mbps` |
| CAN FD `500k/5M` | 1 帧 | 约 `170 μs` | 数据段跑 `5 Mbps` |

**注意：** 经典 CAN 那一行按裸 `8` 字节/帧整除估算，未计 ISO-TP 的 PCI 字节和流控帧开销；实际用多帧传输时帧数和耗时都会更差。

这些数字是量级估算，实际还要看位填充、帧间隔和具体位时序，但结论很清楚：**扩容和提速两件事各自都有贡献，合起来能把大数据传输从毫秒级压到百微秒级。**

有效载荷比例的变化更直观：

| 方案 | 数据位 | 整帧约（未计位填充） | 效率 |
| --- | --- | --- | --- |
| 经典 CAN 8 字节 | 64 | ~111 | 约 58% |
| CAN FD 64 字节 | 512 | ~572 | 约 90% |
| CAN XL 2048 字节 | 16384 | ~16500 | 约 99% |

**注意：** 三行都未计入位填充，计入之后效率都会低一些（CAN XL 数据段还有固定填充位），但三者的相对关系不变。

规律很简单：**帧头开销是固定的，数据区越大，固定开销被摊得越薄。**

反过来看小报文（例如 2 字节）要分两种情况：

| 情况 | 结果 |
| --- | --- |
| FD 无 BRS | **略微变慢**，因为多了 `FDF` / `res` / `BRS` / `ESI` 等控制位和 `4` 位填充计数，CRC 也从 `15` 位变成 `17` 位并带固定填充位 |
| FD 带 BRS | 仍然比经典帧快，但帧头固定开销占比高，收益远不如大块数据明显 |

直白说法：

> CAN FD / CAN XL 的收益主要来自“大块数据”。小信号周期报文即使开了 BRS，省下的时间也很有限。

### 3.4、提速的物理代价

数据段速率越高，对物理层要求越苛刻：

| 约束项 | 高速下的要求 |
| --- | --- |
| 支线长度 | stub 要更短 |
| 拓扑形状 | 要更接近标准直线型，星型和多分支会引入反射 |
| 隐性边沿 | 振铃更容易导致误采样，这正是 SIC 收发器要解决的问题 |
| 阻抗匹配 | 线缆特性阻抗和终端电阻的要求更高 |

**注意：** 仲裁段速率仍然受总线长度限制，这一点三代都一样。CAN FD 和 CAN XL 提的是数据段速率，不是整体速率。

## 第四章、兼容性：最容易踩坑的一章

这是实际项目中最关键的问题：**能不能混在一条总线上？**

### 4.1、经典 CAN 节点 + CAN FD 报文 = 出事

先说结论：**一条总线上只要有一个纯经典 CAN 节点，就不能跑 CAN FD 帧。** 故障链条如下：

```text
        FD 节点发送 CAN FD 帧
                 ↓
    经典控制器读到 FDF = 隐性（经典 CAN 规定此位必须显性）
                 ↓
            判定为格式错误
                 ↓
     经典控制器发出错误帧（连续 6 个显性位）
                 ↓
        正在传输的 FD 帧被破坏
                 ↓
            FD 节点自动重传  ──┐
                 ↓             │
        经典节点再次报错 ───────┘  循环
                 ↓
   FD 发送节点 TEC 持续累加 → TEC > 255 → 该 FD 节点进入 bus off
   （经典节点是接收方，只累加 REC，最多停在 error passive）
                 ↓
        总线被错误帧淹没，正常通信瘫痪
```

**注意：** 真正进入 bus off 的是不断重传的 **CAN FD 发送节点**，不是报错的经典节点——按错误界定规则，接收错误只会把节点推到 error passive，不会导致 bus off。

这不是“收不到”那么简单，而是**整条总线无法正常通信**。常见的三种处理方式：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 全网换 FD | 所有节点都换成 CAN FD 控制器 | 新设计首选 |
| FD-Tolerant 器件 | 用能“看到 FD 帧但不报错、静默忽略”的经典控制器 | 老节点不改功能 |
| 分段 + 网关 | 经典 CAN 和 CAN FD 分成两段，中间加网关转发 | 老节点确实换不了 |

**注意：** FD-Tolerant（容忍）和 FD-Capable（支持）是两回事，选型时看数据手册要分清。

| 术语 | 能力 |
| --- | --- |
| FD-Tolerant | 只收发经典帧；遇到 FD 帧不报错、直接丢弃 |
| FD-Capable | 能正常收发 FD 帧 |

### 4.2、CAN XL 的共存策略与收发器要求

CAN XL 设计时吸取了教训，兼容性做得好得多：

| 事实 | 说明 |
| --- | --- |
| XL 控制器必须支持 FD | 标准强制要求，所以 XL 节点能正常收发 FD 帧 |
| FD 控制器仍会被 XL 帧打死 | `XLF` 位落在 CAN FD 的保留位上，FD 控制器会判定格式错误并发错误帧 |
| 实际组网更容易 | 全网升级到 XL 控制器后，可按需混发 FD 帧和 XL 帧，不必全部改成 XL 帧 |

控制器支持不代表能用，收发器是另一道坎：

| 收发器类型 | 支持速率 | 说明 |
| --- | --- | --- |
| 经典 CAN 收发器 | ≤ `1 Mbps` | 高速下波形来不及建立，FD 数据段会出错 |
| CAN FD 收发器 | ≤ `2 ~ 5 Mbps` | 满足常规 FD 需求 |
| SIC 收发器 | 按 `5 Mbps` 规范 | 抑制隐性边沿振铃，复杂拓扑下更稳；`8 Mbps` 属有利拓扑下的案例值 |
| SIC XL 收发器 | ≤ `20 Mbps` | 支持 PWM 模式，**PWM 模式下必需**；NRZ 模式可用满足目标速率的高速收发器 |

一个很典型的坑：

> 控制器换成了 CAN FD，收发器还是老的经典 CAN 收发器。仲裁段能通，数据段一提速就大量 CRC 错误。这种问题在示波器上表现为高速段波形明显变形、上升沿拖尾。

### 4.3、兼容性速查

| 组合 | 结果 |
| --- | --- |
| 经典节点 + 经典帧 | 正常 |
| FD 节点 + 经典帧 | 正常，FD 控制器向下兼容经典帧 |
| 经典节点 + FD 帧 | **总线瘫痪**，除非经典节点是 FD-Tolerant |
| FD 节点 + XL 帧 | **总线瘫痪**，且没有类似 FD-Tolerant 的成熟规避器件，只能全网升级到 XL 控制器或分段加网关 |
| XL 节点 + FD 帧 | 正常，XL 控制器强制支持 FD |
| XL 节点 + 经典帧 | 正常 |

一句话总结：**向下兼容没问题，向上不兼容。新协议的帧扔到老网络上，老节点会用错误帧把总线打死。**

## 第五章、场景与选型

### 5.1、三代各自适合什么

| 协议 | 适用场景 | 典型应用 |
| --- | --- | --- |
| 经典 CAN | 周期性小信号广播；老平台延续设计；成本极度敏感的节点；长距离低速场合；单帧天然 ≤ 8 字节 | 车身控制、仪表信号、简单传感器上报、工业 CANopen / J1939 |
| CAN FD | ECU 刷写和标定；UDS 诊断响应；带信息安全 MAC 的报文；中等数据量传感器；高负载网络升级 | 动力域和底盘域控制、BMS 详细电池数据、ADAS 传感器融合中间链路 |
| CAN XL | 隧道传输以太网协议；区域架构中速骨干；带宽夹在 FD 与以太网之间；需要 `VCID` 虚拟网络；需要原生安全扩展 `SEC` | 区域架构骨干链路、需要软件定义网络分区的新平台 |

两点现状判断：

| 协议 | 现状 |
| --- | --- |
| CAN FD | **新车型的主流选择**，生态成熟、芯片便宜、工具链完整 |
| CAN XL | 生态仍在建设中，量产芯片选择远少于 FD，工具和协议栈支持也在跟进。除非有明确技术需求，新项目默认选 CAN FD 更稳妥 |

### 5.2、什么时候该直接上车载以太网

三代 CAN 都解决不了的场景：

| 场景 | 原因 |
| --- | --- |
| 摄像头原始视频流、激光雷达点云 | 动辄几百 Mbps 甚至 Gbps |
| 需要交换机做全双工转发的骨干网 | CAN 是共享总线，做不到无冲突并行 |
| 需要标准 TCP/IP 协议栈 | 直接复用现成的 IT 生态 |

各条总线的定位对比：

| 总线 | 数据段位速率 | 拓扑 | 成本 | 定位 |
| --- | --- | --- | --- | --- |
| 经典 CAN | `≤1 Mbps` | 总线型 | 最低 | 控制信号 |
| CAN FD | `2 ~ 5 Mbps` | 总线型 | 低 | 控制 + 中等数据 |
| CAN XL | `10 ~ 20 Mbps` | 总线型 | 中 | 中速骨干 |
| 100BASE-T1 | `100 Mbps` | 点对点 + 交换机 | 中高 | 数据骨干 |
| 1000BASE-T1 | `1 Gbps` | 点对点 + 交换机 | 高 | 高带宽数据 |

**注意：** CAN 系列这三行是**数据段**的位速率，不能和以太网那两行的线速直接对比。仲裁段和 ACK 段仍是低速，加上帧头、填充位和帧间隔，实际净吞吐明显低于表中数值。

直白说法：

> CAN 系列的核心优势从来不是带宽，而是**确定性的优先级仲裁**和**低成本的多点总线**。需要“高优先级消息一定先到”就用 CAN，需要“大带宽随便传”就用以太网。CAN XL 是在这两者之间补了一块。

### 5.3、选型决策树

```text
第一步：看老节点的约束
网络里有纯经典 CAN 节点？
 ├─ 是 ──> 这些节点能升级控制器和收发器吗？
 │          ├─ 能 ──> 视同全新网络，进入第二步
 │          └─ 不能 ──> 能换成 FD-Tolerant 器件吗？
 │                       ├─ 能 ──> 其余节点用 CAN FD
 │                       └─ 不能 ──> 经典 CAN，或分段 + 网关隔离
 └─ 否 ──> 进入第二步

第二步：看数据量与吞吐需求
单帧最大数据 ≤ 8 字节，且不需要加 MAC / 新鲜度值？
 ├─ 是 ──> 经典 CAN（换 FD 收益很小）
 └─ 否
     │
     单帧最大数据 ≤ 64 字节？
      ├─ 是 ──> CAN FD
      └─ 否
          │
          需要的持续净吞吐超过约 10 Mbps？
           ├─ 是 ──> 车载以太网
           └─ 否 ──> CAN XL
```

**补充：** 即使数据量不大，只要需要隧道传输以太网协议或需要 `VCID` 虚拟网络分区，也应直接选 CAN XL。

还有三个现实约束：

| 约束 | 要确认什么 |
| --- | --- |
| 芯片选型 | 目标 MCU 的 CAN 控制器 IP 支持到哪一代（如 Bosch M_CAN 支持 FD，X_CAN 支持 XL） |
| 收发器能力 | 目标数据段速率是否落在收发器数据手册的 `Data Rate` 范围内；PWM 模式需要 SIC XL |
| 工具链 | 分析仪、上位机软件授权、DBC / ARXML 工具是否支持所选协议 |

## 第六章、调试与排查

经典 CAN 的坑（接反、共地、终端电阻、收发器使能）在 FD 和 XL 上全都还在，本章只讲**新增的**部分。

### 6.1、容易出问题的点

| 归属 | 问题 | 表现或说明 |
| --- | --- | --- |
| CAN FD | 只配了一套位时序 | 忘了配数据段位时序，或数据段采样点不合理 |
| CAN FD | 数据段速率不一致 | 仲裁段一样能通，数据段一提速就 CRC 错 |
| CAN FD | 忘了使能 FD 模式 | FD 使能位、BRS 使能位没打开，发出去还是经典帧 |
| CAN FD | 收发器不支持高速 | 控制器配好了，收发器是老的，数据段波形出不来 |
| CAN FD | DLC 档位没对齐 | 要传 33 字节实际占了 48 字节帧，总线负载估算错 |
| CAN FD | 补齐字节没定义（padding，非位填充） | DLC 档位补齐出来的多余字节（如 48 字节帧只用 33 字节）需在协议里约定填 `0x00` 或 `0xAA`，与位填充无关 |
| CAN FD | 老工具抓不到 | 分析仪不支持 FD，显示为错误帧，误以为是硬件问题 |
| CAN FD | 中断负载突变 | 单次中断要搬运 64 字节，DMA 或 FIFO 配置要跟上 |
| CAN XL | PWM 模式下收发器必须是 SIC XL | 使能 `TMS` 后普通 FD 收发器完全跑不了 PWM |
| CAN XL | PID 和 AF 职责搞混 | 还按老习惯把 `PID` 当报文标识用，忘了配 `AF` 过滤 |
| CAN XL | SDT 配错 | 接收方按错误的内容类型解析数据区 |
| CAN XL | 两个 CRC 混淆 | 看到 CRC 错误要先分清是头部还是数据 |
| CAN XL | 缓冲区管理 | 单帧 2 KB，RAM 紧张的 MCU 上要仔细规划接收缓冲 |
| CAN XL | VCID 规划混乱 | 虚拟网络划分没做好，反而增加调试难度 |
| 通用 | 用好 `ESI` | 现在能看到对端是不是 error passive，是很有用的诊断信息 |
| 通用 | 总线负载算法变了 | 不能再简单用“帧数 × 每帧位数 ÷ 波特率”，要分别算仲裁段和数据段 |
| 通用 | 实时性分析更复杂 | 一帧 64 字节在低速段的阻塞时间可能比几个经典帧还长，最坏响应时间要重算 |

### 6.2、先分清是哪个阶段出错

这是 FD / XL 调试和经典 CAN 最大的差别：**要判断问题出在仲裁段还是数据段。**

| 现象 | 大概率原因 |
| --- | --- |
| 经典帧能通，FD 帧全错 | 网络里有经典节点，或对端没使能 FD |
| FD 无 BRS 能通，带 BRS 就错 | 数据段位时序、数据段速率、或收发器不支持高速 |
| 偶发 CRC 错，负载高时更明显 | 数据段采样点不合适、波形振铃、终端电阻或支线问题 |
| 总线上全是错误帧，**发送方**很快 bus off | 典型的经典节点混入 FD 网络 |
| 能收到帧但长度不对 | DLC 档位理解错，或头部解析错 |

### 6.3、分层检查清单

| 层次 | 检查项 | 说明或常见取值 |
| --- | --- | --- |
| 硬件 | 基础连接 | `CAN_H` / `CAN_L`、共地、终端电阻、收发器供电和使能 |
| 硬件 | **收发器速率能力** | 翻数据手册的 `Data Rate` 一栏，确认支持目标数据段速率 |
| 控制器 | FD / XL 模式使能 | 对应使能位是否已打开 |
| 控制器 | 两套位时序 | 标称位时序和数据位时序都要配 |
| 控制器 | 采样点 | 标称段（即仲裁段）常见 `75% ~ 80%`，数据段 `70% ~ 80%` |
| 控制器 | 数据段 `SJW` | 要足够容忍时钟偏差 |
| 控制器 | 时钟源 | FD 对精度要求更高，通常要求晶振而不是内部 RC |
| 网络 | 节点能力 | 总线上是否还有不支持 FD / XL 的节点 |
| 网络 | 速率一致性 | 所有节点的数据段速率是否完全一致 |
| 网络 | 网关配置 | 网关两侧的协议配置是否匹配 |
| 波形 | 差分幅值 | 高速段不能明显低于仲裁段 |
| 波形 | 隐性边沿 | 是否有明显振铃、过冲（SIC 收发器要解决的就是这个） |
| 波形 | 位宽 | 是否和配置的数据段速率对得上 |
| 波形 | 速率切换点 | FD 看 `BRS` 位、XL 看 `ADS` / `DAS` 序列，切换那一刻波形是否干净 |

### 6.4、速率问题的逐级降级排查

怀疑是速率问题时，按这个顺序一级一级往回退：

```text
带 BRS 高速 → 降低数据段速率 → 关掉 BRS（FD 无 BRS）→ 退回经典帧
```

| 退到哪一步能通 | 说明问题在哪 |
| --- | --- |
| 降低数据段速率后能通 | 数据段位时序裕量不足，或物理层余量不够（振铃、支线、终端电阻） |
| 关掉 BRS 后能通 | 数据段速率或物理层根本跑不动高速，不是帧格式问题 |
| 只有经典帧能通 | 问题在 FD 帧格式识别，多半是网络里有经典节点 |
| 经典帧也不通 | 回到经典 CAN 的排查流程，是基础硬件问题 |

## 第七章、面试常见问法和直白回答

### 7.1、CAN FD 相关

**CAN FD 相比经典 CAN 改进了什么？**

> 两点：数据区从 8 字节扩到 64 字节，以及支持在一帧内切换比特率，仲裁段保持低速、数据段可以跑到 2 到 5 Mbps。配套改动包括新增 FDF / BRS / ESI 三个控制位、CRC 加长到 17 或 21 位、增加填充位计数，以及取消远程帧。

**CAN FD 为什么只有数据段能提速？**

> 因为速率上限是被仲裁机制限制的。仲裁要求节点发出的电平能在一个位时间内传到总线最远端再传回来被自己采样，所以位时间不能短于信号往返时间。仲裁结束后总线上只剩一个发送节点，不需要再比位，这时候就可以提速。ACK 位需要全网应答，所以也要切回低速。

**CAN FD 的 DLC 是怎么编码的？**

> 0 到 8 和经典 CAN 一样直接表示字节数，9 到 15 被重新定义为 12、16、20、24、32、48、64 字节。注意长度是离散的，没有中间值，传 33 字节只能用 48 字节的帧，剩余部分要填充。

**配置 CAN FD 时要注意什么？**

> 最关键的是要配两套位时序：标称段和数据段各一套，段长度、采样点和 SJW 都要分别算。另外要确认控制器使能了 FD 模式和 BRS、收发器支持目标数据段速率、时钟源精度足够，以及总线上所有节点的数据段速率完全一致。

**CAN FD 的 ESI 位有什么用？**

> ESI 指示发送节点当前处于 error active 还是 error passive 状态。经典 CAN 里接收方无法直接知道对端的错误状态，CAN FD 把这个信息放进帧里，方便网络诊断和故障定位。

### 7.2、CAN XL 相关

**CAN XL 和 CAN FD 的核心区别是什么？**

> 三点。第一，数据区从 64 字节扩到 2048 字节，而且长度连续可取；第二，帧头重新设计，11 位 Priority ID 只管优先级，另外用 32 位 AF 字段做寻址过滤、8 位 SDT 说明内容类型；第三，数据段速率提到 10 到 20 Mbps，可以用 PWM 编码，需要 SIC XL 收发器。CAN XL 还能直接隧道传输以太网帧。

**CAN XL 为什么要做两个 CRC？**

> 因为数据区最大 2048 字节，如果 DLC 字段传错，接收方会按错误的长度去接收，整个帧同步都会乱掉。所以先用 13 位头部 CRC 校验帧头，确认长度等关键字段正确后再接收数据，最后用 32 位帧 CRC 做整体完整性校验。

**有了车载以太网为什么还要 CAN XL？**

> 定位不同。以太网带宽高但是点对点加交换机的拓扑，成本高，而且没有 CAN 那种基于优先级的非破坏性仲裁，实时性保证方式完全不同。CAN XL 保留了 CAN 的低成本多点总线和确定性优先级仲裁，同时把带宽补到十几 Mbps，填的是“CAN FD 不够用但上以太网太浪费”这段空缺。

### 7.3、兼容性与选型相关

**经典 CAN 节点能不能接在 CAN FD 总线上？**

> 不能直接接。CAN FD 的 FDF 位在经典 CAN 里是必须为显性的保留位，经典控制器看到隐性会判定格式错误并发出错误帧，破坏正在传输的 FD 帧，导致反复重传直到 bus off，整条总线瘫痪。解决办法是全网换 FD 控制器、使用 FD-Tolerant 器件，或者分段加网关。

**FD-Tolerant 和 FD-Capable 有什么区别？**

> FD-Tolerant 是能识别出 FD 帧但不报错、静默丢弃，自己只收发经典帧；FD-Capable 是能正常收发 FD 帧。选型时如果老节点不需要用 FD 功能，选 FD-Tolerant 就够了。

**CAN XL 怎么保证和 CAN FD 共存？**

> 标准要求 CAN XL 控制器必须同时支持 CAN FD，所以 XL 节点可以正常收发 FD 帧。但反过来不行，纯 FD 节点遇到 XL 帧会因为 XLF 位报错。实际做法是把全网节点都升级到 XL 控制器，然后按需混发 FD 帧和 XL 帧。

**什么场景该用 CAN FD 而不是经典 CAN？**

> 单帧数据超过 8 字节、或者传输大块数据的场景收益最明显，典型的是 ECU 刷写、UDS 诊断和带信息安全 MAC 的报文。如果都是 2 到 8 字节的周期性小信号，换 CAN FD 的收益就很有限：开了 BRS 还能快一点，不开 BRS 反而因为控制位变多、CRC 变长而略微变慢。

## 第八章、高频易错点与最简记忆版

### 8.1、高频易错点

| 错误说法 | 更准确的说法 |
| --- | --- |
| CAN FD 是新的总线协议 | CAN FD 是经典 CAN 的扩展，物理层和仲裁机制完全一样 |
| CAN FD 整帧都跑 2 Mbps | 只有数据段提速，仲裁段和 ACK 段仍是低速 |
| CAN FD 一定要开 BRS | BRS 是可选的，可以只扩容不提速，兼容性风险更小 |
| CAN FD 支持 0 到 64 任意长度 | 长度是离散档位：0~8、12、16、20、24、32、48、64 |
| CAN FD 帧还能用远程帧 | CAN FD 取消了远程帧，RTR 位置变成恒显性的 RRS |
| 经典节点收不到 FD 帧就算了 | 经典节点会发错误帧破坏总线，可能让整条总线瘫痪 |
| 控制器支持 FD 就能跑高速 | 收发器也要支持，还要看拓扑、线缆和终端电阻 |
| FD-Tolerant 就是支持 CAN FD | FD-Tolerant 只是不报错，不能收发 FD 帧 |
| CAN FD 提速后线可以拉更长 | 仲裁段速率仍受总线长度限制，提速反而让物理层更敏感 |
| CAN XL 的 ID 还是表示报文含义 | CAN XL 的 11 位 PID 只管优先级，含义由 SDT 和 AF 承担 |
| CAN XL 的数据长度也是离散的 | CAN XL 是 1 到 2048 字节连续可取 |
| CAN XL 用普通 FD 收发器就行 | PWM 模式必须用 SIC XL 收发器 |
| CAN XL 能替代车载以太网 | 带宽差一个数量级以上，两者定位互补不是替代 |
| 换成 CAN FD 总线负载一定下降 | 小报文不开 BRS 反而略微变慢，明显收益只来自大块数据 |
| CAN FD 只配一套波特率就行 | 必须配标称段和数据段两套位时序 |

### 8.2、最简记忆版

只想快速记住，可以背下面几句：

- 经典 CAN、CAN FD、CAN XL 用同一套差分物理层和同一套仲裁机制，仲裁阶段三者帧头一样。
- 经典 CAN 卡在两点：一帧只有 `8` 字节，最高 `1 Mbps` 且被仲裁的往返时间限制。
- CAN FD = `64` 字节 + 数据段提速，靠 `FDF` / `BRS` / `ESI` 三个新位实现。
- CAN FD 的长度是离散档位，`9 ~ 15` 的 DLC 对应 `12 / 16 / 20 / 24 / 32 / 48 / 64` 字节。
- CAN FD 要配**两套**位时序：标称段（即仲裁段）和数据段。
- CAN XL = `2048` 字节连续长度 + `10 ~ 20 Mbps`，帧头拆成 `PID`（优先级）/ `AF`（寻址）/ `SDT`（内容类型）。
- CAN XL 有两个 CRC：`13` 位头部 CRC 保护长度字段，`32` 位帧 CRC 保护整帧。
- 兼容性只能向下：老节点遇到新帧会发错误帧打死总线，新节点能正常处理老帧。
- 控制器和收发器要同时升级，收发器速率能力是最常见的隐藏坑。
- 选型口诀：`≤8` 字节且不带 MAC 用经典，`≤64` 字节用 FD，`>64` 字节（或要隧道以太网、要虚拟网络）用 XL，持续净吞吐超过约 `10 Mbps` 直接用车载以太网。
- CAN XL 没有扩展帧，仲裁标识固定 11 位 `PID`，从 29 位 ID 体系迁移要重新映射。
- CAN 系列真正的优势是**确定性优先级仲裁 + 低成本多点总线**，不是带宽。
