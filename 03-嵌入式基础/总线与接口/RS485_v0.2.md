## 第1章 先分清楚：接口、协议和它们的分工

### 1.1 RS485 到底是接口还是协议

先给结论：

> **RS485 是一个电气层（物理层）标准，不是数据协议。** 它规定差分驱动器和接收器的电压、共模范围、负载能力等电气特性，完全不规定字节格式、地址、命令和校验。

所以下面这句现场常听到的话其实是**不完整**的：

```text
“我们这台设备是 RS485 的。”
```

它只说明了“线怎么接、电平什么样”，没有说明：

- 波特率、数据位、校验位、停止位是多少；
- 从机地址是几号；
- 用的是 Modbus RTU 还是厂商私有协议；
- 寄存器表长什么样、数值怎么换算。

拿到一台 RS485 设备时，至少要追问四件事：**串口参数、设备地址、上层协议、寄存器/命令表**。缺一样都无法通信。

### 1.2 一条完整的数据路径

把 UART、RS485、Modbus RTU 放在一起，职责是分层叠加的：

```text
业务：读取 1 号设备的温度
    ↓                       ← 谁负责什么
Modbus（应用层）            功能码、数据模型、异常语义
    ↓
Modbus RTU（链路封装）      二进制帧、CRC16、帧间静默 t3.5
    ↓
UART（字符成帧）            起始位、数据位、校验位、停止位、波特率
    ↓
RS485 收发器（电气层）      单端 TTL 电平 ↔ A/B 差分信号
    ↓
双绞线 + 终端电阻           实际线缆与阻抗匹配
```

对应的分工表：

| 名称 | 层次 | 规定了什么 | 没规定什么 |
| --- | --- | --- | --- |
| RS485 | 电气层 | 差分电平、共模范围、驱动能力、节点负载 | 字节含义、地址、校验、谁先说话 |
| UART | 字符层 | 一个字节怎么按位串行发出 | 多个字节组成什么帧 |
| Modbus RTU | 链路封装 | 帧结构、CRC16、帧边界靠静默时间 | 电压和接线 |
| Modbus | 应用层 | 功能码、四类数据区、异常码 | 寄存器代表什么业务量 |
| 设备手册 | 业务层 | 寄存器地址、含义、量纲、倍率、字序 | —— |

### 1.3 常见的三种搭配

| 物理层 | 上层协议 | 说明 |
| --- | --- | --- |
| RS485 | Modbus RTU | 工业现场最常见的组合，本文主线 |
| RS485 | 厂商私有协议 | 同样是 A/B 两根线，但帧格式、校验完全不同，Modbus 工具无法直接用 |
| RS232 / TTL UART | Modbus RTU | 协议一样，只是换了电气层，通常只能点对点 |

两张表放在一起就能得到本文最重要的一句话：

> **RS485 ≠ Modbus。** 看到 A/B 接线端子不代表能用 Modbus 工具读到数据；看到 Modbus RTU 也不代表一定跑在 RS485 上。

### 1.4 RS485 解决什么问题

普通 UART（TTL 或 RS232）在工业现场有三个明显短板，RS485 正是针对它们：

| 问题 | 单端 UART | RS485 |
| --- | --- | --- |
| 距离 | 通常几米 | 低速下可达数百米到约 1200 m（经验值，非标准保证） |
| 抗干扰 | 参考 GND，易受共模噪声影响 | 差分传输，共模干扰被大幅抵消 |
| 节点数 | 点对点 | 一对线可挂多个节点 |

典型用途：电表水表等仪表、PLC 与变频器/伺服/远程 IO、门禁消防等楼宇安防、多 MCU 板间通信。

**本章小结：** RS485 是电气层，Modbus RTU 是链路封装 + 应用语义。拿到设备先确认串口参数、地址、协议和寄存器表这四件事。

## 第2章 RS485 的电气层：差分、A/B 与接线

### 2.1 差分传输为什么抗干扰

RS485 的发送器驱动 A、B 两根线形成差分电压，接收器只看 **A 与 B 之间的压差**，不看任一根线相对地的绝对电平。

```text
单端信号：判断某根线相对 GND 的电平    ← 噪声叠加在信号上，直接影响判决
差分信号：判断 A 与 B 之间的电压差     ← 噪声同时耦合到两根线，作差后基本抵消

           噪声 ↓↓↓↓
A ─────────~~~~~~~~~────────
B ─────────~~~~~~~~~────────
           A - B 的差值几乎不受影响
```

直白理解：

> 两个人同时被同样的环境噪声影响时，单独听其中一个人容易听错；比较两个人声音的差别，反而更容易还原原来的信息。

要注意的边界：

- 差分不是“不怕干扰”，双绞线、屏蔽、终端匹配和接地仍然重要——**A/B 必须走在同一对双绞线里**，否则噪声不再等量耦合，差分优势大打折扣。
- 距离和速率不能同时拉满。经验上在良好线缆、正确终端匹配的条件下，`9600 bps` 及以下可达约 1200 m；这不是 RS485 标准的保证值。高速时距离要明显缩短。
- 差分抑制的正是**共模**噪声，但有前提：共模电压必须落在收发器的共模输入范围内（常见器件约 `-7 V ~ +12 V`）。两端地电位差过大而超出该范围时，差分也无能为力，见 [2.4](#24-要不要接-gnd)。

### 2.2 MCU 侧怎么连

MCU 的 UART 不能直接接到 A/B，中间必须有 RS485 收发器（如 MAX485 系列、SP3485，或 ADM2483 等隔离型器件）。

```text
MCU                       RS485 收发器                RS485 总线
+----------+             +-----------------+
| TX ----- | ──────────► | DI            A | ────────── A
| ----- RX | ◄────────── | RO            B | ────────── B
| GPIO --- | ──────────► | DE              |
| (常并联) | ──────────► | /RE             |
+----------+             +-----------------+
```

引脚含义：

| 引脚 | 全称 | 含义 | 常见连接 |
| --- | --- | --- | --- |
| `DI` | Driver Input | 发送数据输入 | MCU `TX` |
| `RO` | Receiver Output | 接收数据输出 | MCU `RX` |
| `DE` | Driver Enable | 发送驱动使能，**高有效** | MCU GPIO 或 UART 硬件 RS485 方向脚 |
| `/RE` | Receiver Enable | 接收使能，**低有效** | 常与 `DE` 并接同一 GPIO |
| `A` / `B` | —— | 差分总线 | 接总线双绞线 |

记牢一句：**`A/B` 是总线，不是 MCU 的 `TX/RX`**。很多初学者的第一个错误就是把 A 当 TX、B 当 RX 去交叉连接。

### 2.3 A/B 怎么接

基本规则是**同一差分极性相连**。如果两端厂家的命名一致，表现就是同名直连：

```text
主机 A ───────────────── 从机 A
主机 B ───────────────── 从机 B
```

| 本机端子 | 对端接法 |
| --- | --- |
| `A` | 接对方 `A` |
| `B` | 接对方 `B` |
| `GND` / `COM` | 按系统设计建立参考地或等电位连接 |

但这里有 RS485 最大的坑：

> **不同芯片、模块、厂家对 A/B 的标号可能相反。** 有的把非反相端叫 `A`，有的模块却把同一个端子标成 `B`；`D+/D-`、`TR+/TR-`、`485+/485-` 也是常见别名，含义未必对齐。

所以不能只机械相信字母。实际原则：

- 优先看**芯片数据手册或模块说明**中对 `A/B`、`D+/D-` 的定义，以“非反相/反相”为准。
- 极性接反的典型现象是：**能发出去但完全收不到，或持续乱码**，而不是完全没有波形。
- 在点对点、单节点或已隔离的验证环境中，若定义确实不清楚，可在**断电后**对调其中一端的 A/B 验证极性；**不要在已经跑起来的多节点现场总线上盲目交换**。
- 整条总线上所有设备必须采用同一套极性定义；确认后给线缆和端子做统一标识。

### 2.4 要不要接 GND

这是一个经常被“RS485 只要两根线”误导的问题。

RS485 的有效信号确实是 A、B 之间的差分电压，但收发器有**允许的共模电压范围**（常见器件约 `-7 V ~ +12 V`，具体看手册）。当两端设备的地电位差超出这个范围时，即使 A/B 接得完全正确，接收器也可能无法正常判决，甚至损坏器件。

按场景处理：

| 场景 | 做法 |
| --- | --- |
| 短距离、同一供电系统 | 通常连接 `A`、`B` 和信号地 / `COM` 三根 |
| 不同供电系统、地电位差不确定 | 使用**隔离型** RS485 收发器，按手册设计参考地 |
| 户外、跨建筑、雷击风险 | 隔离 + 浪涌保护 + 屏蔽层按规范单点接地 |

不要把“RS485 只要两根线”理解成任何场景都不需要处理地线问题。

### 2.5 两线半双工与四线全双工

项目里绝大多数是**两线制半双工**：所有节点共用同一对 A/B，同一时刻只能有一个节点驱动总线。

```text
两线制半双工：

主机 ────┬──── A/B 总线 ────┬────────┬────────┐
         │                  │        │        │
       从机1              从机2    从机3    从机4

同一时刻：只能一个节点发送，其余全部接收。
```

为什么常见半双工：

- 多节点共享一对线，线缆成本低、施工简单；
- 多个发送器同时驱动总线会产生冲突（总线争用），数据必然损坏；
- 常见主从协议天然是“主机问、从机答”，本来就适合轮流说话。

四线制可以实现全双工：一对线专供主机发给从机，另一对线专供从机回给主机，常用于点对点，也可用于特定的多节点主从网络。但要注意：**多个从机共享返回方向时，同一时刻仍然只能有一个从机驱动**，冲突仍须由协议避免。四线制不等于“所有从机可以同时说话”，且布线更多、设备支持更少，现场远少于两线制。

**本章小结：** A/B 走同一对双绞线、同极性直连、以手册定义为准；地线按共模范围和供电关系决定；默认按两线半双工设计。

## 第3章 拓扑、终端电阻与偏置电阻

这一章解决的是“能通，但偶尔出错”的那类问题。

### 3.1 总线要怎么布线

RS485 推荐**手拉手（菊花链）**的总线型拓扑，节点并接在同一对主干线上，**不是**由前一个节点转发数据。

```text
推荐：主干总线（daisy chain）

主机 ──── 从机1 ──── 从机2 ──── 从机3 ──── 从机4
└─ 端点                                  端点 ─┘

不推荐：星形 / 长支线

               从机1
                 │  ← 长支线（stub）产生反射
主机 ────────────┼──────────── 从机2
                 │
               从机3
```

原因：长支线和星形分叉会造成阻抗不连续，产生信号反射与振铃。**波特率越高、线越长，问题越明显**，典型表现就是偶发丢包、CRC 错误。

布线经验：

- 用双绞线，`A/B` 必须在同一对里；
- 支线尽量短（高速下控制在几十厘米级别），节点串接在主干上；
- 远距离或强干扰环境用屏蔽双绞线，屏蔽层按规范**单点接地**，两端都接容易形成地环流；
- 不要与变频器输出电缆、接触器动力线长期并行走线，必须交叉时尽量垂直交叉。

### 3.2 120 Ω 终端电阻做什么

线缆是传输线。当信号的上升沿在线上传播到末端时，如果末端阻抗与线缆特性阻抗不匹配，能量会**反射**回来，叠加在原信号上形成振铃和过冲，导致接收器误判。

终端电阻的作用就是**匹配线缆特性阻抗，把到达末端的能量吸收掉**。

常见的工业双绞线特性阻抗约 100 ~ 120 Ω，所以取 `120 Ω` 这个经验值——**120 不是协议规定的魔法数字，而是“接近线缆特性阻抗”的常用取值**。

装法：

```text
        主机                                      从机3
      （端点）                                  （端点）
A --------+-------------+-------------+-------------+------ A
          |             |             |             |
       [120 Ω]        从机1         从机2        [120 Ω]
          |             |             |             |
B --------+-------------+-------------+-------------+------ B

总线两个物理末端各并一个 120 Ω 终端电阻；中间节点只并接在主干上，不装终端电阻。
注意所有节点都是「并接」在同一对 A/B 上，信号不经过前一个节点转发。
```

要点：

| 问题 | 回答 |
| --- | --- |
| 装几个？ | 通常 **2 个**，在总线的两个**物理末端**各一个 |
| 中间节点要装吗？ | 不装 |
| 每个节点都装会怎样？ | 总线负载过重，差分幅度被拉低，反而通信变差甚至完全不通 |
| 一个都不装行吗？ | 短距离、低波特率有时能工作，但不要据此忽略规范设计 |
| 阻值一定是 120 吗？ | 应接近实际线缆特性阻抗，并参考设备手册 |

很多 RS485 模块带一个可选的 120 Ω 跳帽或拨码开关（常标 `T`、`TERM`、`120R`），**只有处于总线两端的那两台设备才打开**。现场一个非常典型的错误是：所有模块出厂默认都拨在 ON，几十台设备的 120 Ω 并联后等效电阻只剩几欧姆（负载极重），差分幅度被彻底拉垮，总线直接被拉死。

> 快速判据：断电后用万用表量总线 A-B 之间的直流电阻。只有两端装终端时，约为 `120 / 2 = 60 Ω`（再并上偏置电阻会略低）。若量到 20 ~ 30 Ω 甚至更低，说明装了太多终端电阻。

### 3.3 偏置电阻做什么

终端电阻和偏置电阻解决的是**两个不同的问题**，不能互相替代。

当总线上所有节点都关闭发送驱动器时，A/B 处于**高阻悬空**状态。此时即使装了终端电阻，A、B 也只是被电阻拉到彼此相等，差分电压接近 `0 V`——落在传统接收器的判决门限不确定区里。任何一点噪声都可能让接收器输出翻转，被 UART 误判成起始位，产生假字节和乱码。

偏置电阻（fail-safe bias）的作用就是**在空闲时把 A/B 强制拉开一个确定的差分电压**，让总线空闲状态等价于 UART 的空闲电平。

```text
            VCC
             |
         [上拉 R]
             |
A -----------+-------------------+------ A
                                 |
                           [120 Ω 终端]
                                 |
B -----------+-------------------+------ B
             |
         [下拉 R]
             |
            GND

本图为示例画法：上拉接 A、下拉接 B，终端电阻跨接在 A、B 之间（两者是不同的元件，位置也不同）。
空闲时：A、B 被偏置成固定压差 → 接收器输出稳定，不会误触发。
```

要点：

- **整条总线通常只在一个位置提供一组偏置**（一般在主机端或总线控制器端）。
- 哪根线上拉、哪根线下拉，取决于具体收发器的 A/B 极性定义和所需的空闲状态，**不能机械照抄**。
- 多个节点重复加偏置会加重总线负载、改变电平，甚至把差分电压压到判决门限以下。
- 许多现代收发器带 **true fail-safe**（内部保证输入悬空或短路时输出为确定态），外部偏置需求降低；仍应以器件手册和现场实测为准。

### 3.4 一张表区分两种电阻

| 对比项 | 终端电阻（Termination） | 偏置电阻（Bias / Fail-safe） |
| --- | --- | --- |
| 解决的问题 | 信号反射、振铃 | 空闲时电平不确定、假起始位 |
| 何时起作用 | 有节点在发送时 | 所有节点都不发送时 |
| 典型值 | 约 120 Ω（匹配线缆阻抗） | 数百 Ω ~ 数 kΩ，需按总线负载计算 |
| 装几处 | 总线两个物理末端各一个 | 整条总线通常只一组 |
| 装错的后果 | 装太多 → 幅度不足；不装 → 高速丢包 | 装太多 → 负载过重；不装 → 空闲乱码 |

**本章小结：** 手拉手拓扑 + 两端各一个 120 Ω + 全网一组偏置。这三条是 RS485 现场稳定性的地基。

## 第4章 半双工方向控制

这是 RS485 软件侧**最容易出错、也最容易被忽略**的地方。

### 4.1 为什么需要方向控制

MCU 的 UART `TX/RX` 本身是全双工的两根独立线，而两线 RS485 总线是半双工共享介质。因此必须由软件（或硬件）告诉收发器：**当前这一刻，我是在发还是在收。**

常见接法是把 `DE` 和 `/RE` 并接到同一个 GPIO：

| GPIO 状态 | `DE` | `/RE` | 收发器状态 |
| --- | --- | --- | --- |
| `0` | 0（禁止发送） | 0（使能接收） | **接收态**：驱动器高阻，不占用总线 |
| `1` | 1（使能发送） | 1（禁止接收） | **发送态**：驱动总线，本机不收 |

默认状态必须是 `0`（接收态）。上电初始化时如果 GPIO 悬空或默认为高，这一个节点就会一直霸占总线，导致**整条总线全部失效**——这是现场“突然全网瘫痪”的常见原因之一。

需要注意的是，多数 MCU 复位后 GPIO 为浮空输入，从复位到固件配置引脚之间存在一段**软件无法覆盖**的窗口。因此仅靠初始化代码不够，`DE` 应在硬件上加一只下拉电阻（典型 10 kΩ 到 GND），把默认态钉在接收侧。

### 4.2 正确的发送时序

```text
            (1)                                          (4)
             v                                            v
             +-- 高 = 发送态：驱动器使能，本机占用总线 ---+
DE   --------+                                            +--------

                 +--[byte0][byte1] ... [byteN]--+
TX   ------------+                              +--------
                 ^                              ^
                (2)                            (3)

(1) 拉高 DE，切到发送态              (2) 启动 UART 发送
(3) 等到 TC 置位（最后一个停止位已真正发到线上）
(4) 拉低 DE，关闭驱动器、释放总线，切回接收态

顺序必须是 (1) → (2) → (3) → (4)：
提前拉低会截断帧尾，延后拉低会压住从机响应的开头。
```

四个步骤：

1. GPIO 拉高，切到发送态（有些收发器需要一小段使能建立时间）；
2. UART 发送数据；
3. **等待 UART 线路发送完成**——是“最后一个停止位已经发到线上”，不是“发送寄存器空”。
   注意 `TC` 是**粘滞标志**：上一帧发完后会一直保持置位，直到被显式清除。清除方式因芯片系列而异：带 `ICR` 寄存器的新系列（如 STM32F0/F3/L0/L4/G0/G4/H7/U5 等）向 `ICR` 写 `TCCF` 即可；不带 `ICR` 的经典系列（F1/F2/F4/L1 等）必须执行“先读 `USART_SR`，再写 `USART_DR`”的软件序列才能清除 `TC`，单独写 `USART_DR` 并不保证清除该标志——使用 HAL 库时这一序列由库内部处理，手写寄存器级驱动需自行按此顺序操作。
   用中断 / DMA 发送时，启动传输后首字节可能还没写进 `TDR`，此时若直接轮询 `TC`，读到的是上一帧的残留置位，等待会立刻返回，效果等同于“切回接收太早”——所以发送前先按上述方式清一次最保险；
4. GPIO 拉低，关闭驱动器，释放总线并进入接收态。

第 3 步是重灾区。以 STM32 为例：

| 标志 | 含义 | 能否用来切方向 |
| --- | --- | --- |
| `TXE` / `TXFNF` | 发送数据寄存器（FIFO）空，可以写下一个字节 | ❌ 太早，移位寄存器里还有数据 |
| `TC`（Transmission Complete） | 移位寄存器也空了，最后一位已上线 | ✅ 正确判据 |
| DMA `TransferComplete` | DMA 把最后一个字节搬进了 UART 数据寄存器 | ❌ 还要再等 `TC` |

```c
void rs485_send(const uint8_t *buf, int len)
{
    rs485_set_tx_enable(true);          /* DE=1, /RE=1 */

    uart_clear_tc_flag(UART1);          /* 关键：先清掉上一帧残留的 TC，否则会立刻“完成”；
                                            经典系列内部需“先读 SR 再写 DR”，不能只写 DR */
    uart_write(UART1, buf, len);
    uart_wait_transmission_complete(UART1);  /* 等 TC，不是 TXE / DMA 完成 */

    rs485_set_tx_enable(false);         /* DE=0, /RE=0，释放总线 */
}
```

### 4.3 四种典型错误

| 错误 | 现象 |
| --- | --- |
| **切回接收太早**（用了 TXE 或 DMA 完成） | 报文尾部被截断，从机侧永远 CRC 错误；帧越短越明显 |
| **一直停在发送态**（忘记拉低、GPIO 默认高） | 本机霸占总线，所有节点都通信不了 |
| **切回接收太慢** | 从机响应很快时，主机漏掉开头几个字节，收到半帧 |
| **从机侧方向控制有问题** | 主机能发出去，但从机的回复上不了总线，表现为全网超时 |

第一种和第三种正好是一对矛盾：切太早丢自己的尾巴，切太慢丢对方的头。所以判据必须准确用 `TC`，切换动作本身要足够快（放在中断里，或用硬件方向控制）。

### 4.4 硬件方向控制

有三种减少软件时序风险的做法：

| 方案 | 说明 | 注意 |
| --- | --- | --- |
| MCU 硬件 RS485 模式 | 部分 UART 外设支持 `DE` 自动输出（STM32 的 `DEM` 位，可配置 `DEAT/DEDT` 建立/保持时间） | 仍需确认极性和引脚复用 |
| Linux RS485 ioctl | 通过 `TIOCSRS485` 让驱动用 RTS 控制 DE | 需驱动支持，`SER_RS485_RTS_ON_SEND` 极性要配对 |
| 自动方向转换模块 | 常见 USB-RS485 模块内部检测 TX 跳变自动切换方向 | **不要再叠加软件 RTS 控制**，重复配置会互相打架 |

最后一条值得强调：现场用 USB-RS485 转换器时，如果程序又去控制 RTS，很容易出现“有时能通有时不通”。先确认转换器是自动方向还是需要 RTS，二选一。

### 4.5 RTOS 里的组织方式

RS485 相比普通 UART，多出来的核心就是**方向控制、请求—应答时序和总线独占**。常见模型是让一个任务串行管理一条总线：

```text
业务任务 ──► RS485 请求队列 ──► RS485 通信任务 ──► UART + 收发器
                                       │
                                       └─► 等待回复 → 校验 → 通知业务任务
```

```c
void rs485_task(void *arg)
{
    rs485_request_t *req;
    int rx_len;

    while (1) {
        rtos_queue_recv(rs485_req_queue, &req, WAIT_FOREVER);

        rs485_send(req->tx_buf, req->tx_len);

        rx_len = uart_receive_frame(req->rx_buf, req->rx_max_len, req->timeout_ms);
        if (rx_len > 0) {
            req->result = protocol_check_frame(req->rx_buf, rx_len)
                        ? RS485_OK : RS485_PROTOCOL_ERROR;
        } else {
            req->result = RS485_TIMEOUT;
        }
        rtos_sem_release(req->done_sem);   /* 所有终止路径都必须通知等待方 */
    }
}
```

设计要点：

- **一条半双工总线由一个任务串行管理**，绝不让多个任务同时操作方向脚和 UART。
- 中断 / DMA 回调只负责快速收数据和通知任务，不在中断里做完整协议解析。
- 接收侧低速可轮询，常规用「中断 + 环形缓冲」，不定长高速报文用「DMA + 空闲中断（IDLE）」。
- 无论成功、校验失败还是超时，都要写入明确结果并通知等待方，否则调用方会一直死等。
- 不要把 `uart_rx_flush()` 当成发送前的固定动作——它可能丢掉合法报文，也会掩盖真正的时序问题。只在确认缓冲区里是历史无效数据时才清。
- 广播报文没有从机回复，不能按普通请求去等应答。

**本章小结：** `DE` / `/RE` 默认接收态；发送后等 `TC` 再释放；一条总线一个通信任务；自动方向模块不要叠加软件 RTS。

## 第5章 Modbus RTU 帧格式

RS485 把比特送到了线上，接下来要解决“这些字节是什么意思”。

### 5.1 主从请求—响应模型

传统称主站（Master）/ 从站（Slave），新文档也称客户端（Client）/ 服务器（Server）；**本文统一称“主机”/“从机”**，指的就是 Master / Slave。在串行总线上行为不变：

1. 主机选定一个从机地址，发送请求；
2. 被点名的从机处理并返回响应；
3. 其他从机保持静默；
4. 主机收到完整响应或等待超时后，才能发起下一笔事务。

```text
Master                     Slave 1                 Slave 2
  |                           |                       |
  |--- ID=1, 读保持寄存器 --->|                       |
  |<--- 响应：寄存器数据 -----|                       |
  |                           |                       |
  |--------------- ID=2, 写保持寄存器 --------------->|
  |<---------------- 响应：写入确认 ------------------|
  |                           |                       |

注：Slave 1、Slave 2 下方的竖线是各自的“生命线”，全程都在线。
第 3 ~ 4 行事务与 Slave 2 无关；第 6 ~ 7 行事务的横线直接横穿 Slave 1 所在的那一列（画面上盖住了它的竖线），表示这笔事务与 Slave 1 无关；
未被点名的从机只是保持静默，并不代表它已离线。
```

从机**不会主动上报**，主机也**不能同时**向两个从机发起事务。地址 `0` 是广播写：所有从机执行但都不响应，因此无法确认结果，可靠系统通常禁用。

### 5.2 RTU 帧结构

```text
+------------+-------------+------------------+-------------+
| 从机地址   | 功能码      | 数据             | CRC16       |
| 1 Byte     | 1 Byte      | N Bytes          | 2 Bytes     |
+------------+-------------+------------------+-------------+
```

- **从机地址**：`1 ~ 247`（`0` 为广播，`248 ~ 255` 保留）；
- **功能码**：说明读还是写、访问哪个数据区；
- **数据**：起始地址、数量或待写入的值；
- **CRC16**：检测位错误，**低字节先发送**（与帧内 16 位数据高字节在前的规则相反，是常见踩坑点）。

注意 RTU 帧**没有帧头和帧尾标志**，帧边界完全依靠总线静默时间识别，见 [7.2](#72-rtu-的时间边界)。

### 5.3 一个完整实例

读取 1 号从机从地址 `0x0000` 开始的 2 个保持寄存器：

```text
请求帧（8 Bytes）

+----------+----------+---------------+----------+----------+
| Slave ID | Function | Start address | Quantity | CRC16    |
+----------+----------+---------------+----------+----------+
|    01    |    03    |    00 00      |  00 02   |  C4 0B   |
+----------+----------+---------------+----------+----------+
| 1 Byte   | 1 Byte   |   2 Bytes     | 2 Bytes  | 2 Bytes  |
+----------+----------+---------------+----------+----------+

线上字节流：01 03 00 00 00 02 C4 0B
```

若两个寄存器值分别为 25 和 100：

```text
响应帧（9 Bytes）

+----------+----------+------------+----------------+----------+
| Slave ID | Function | Byte count | Register data  | CRC16    |
+----------+----------+------------+----------------+----------+
|    01    |    03    |     04     |  00 19  00 64  |  2A 1F   |
+----------+----------+------------+----------------+----------+

线上字节流：01 03 04 00 19 00 64 2A 1F
寄存器 0：0x0019 = 25
寄存器 1：0x0064 = 100
```

抓到一帧字节流后，逐项对照这个结构就能判断问题出在哪一层。

### 5.4 四类数据对象与常用功能码

Modbus 的数据模型有四个逻辑区：

| 数据区 | 位宽 | 访问 | 常用功能码 | 直观理解 |
| --- | ---: | --- | --- | --- |
| Coil（线圈） | 1 bit | 读写 | `0x01`、`0x05`、`0x0F` | 可控开关量输出 |
| Discrete Input（离散输入） | 1 bit | 只读 | `0x02` | 只读开关量输入 |
| Input Register（输入寄存器） | 16 bit | 只读 | `0x04` | 只读测量值 |
| Holding Register（保持寄存器） | 16 bit | 读写 | `0x03`、`0x06`、`0x10` | 可读写参数 / 数据 |

常用功能码：

| 功能码 | 含义 | 请求主要参数 | 单次上限 |
| ---: | --- | --- | --- |
| `0x01` | 读线圈 | 起始地址、数量 | 2000 位 |
| `0x02` | 读离散输入 | 起始地址、数量 | 2000 位 |
| `0x03` | 读保持寄存器 | 起始地址、数量 | 125 个寄存器 |
| `0x04` | 读输入寄存器 | 起始地址、数量 | 125 个寄存器 |
| `0x05` | 写单个线圈 | 地址、`0xFF00` 或 `0x0000` | 1 |
| `0x06` | 写单个保持寄存器 | 地址、16 位值 | 1 |
| `0x0F` | 写多个线圈 | 起始地址、数量、字节数、值 | 1968 位 |
| `0x10` | 写多个保持寄存器 | 起始地址、数量、字节数、值 | 123 个寄存器 |

工程代码应在**发送前**校验数量上限和 `start_address + quantity <= 0x10000`，不要等通信失败才发现参数非法。

### 5.5 地址：最常见的差 1 问题

Modbus 寄存器本质只是 16 位无符号数，业务含义完全由厂商定义。而地址表示法有多种：

```text
手册常见写法：40001    ← 传统 4xxxx 编号，1 基
PDU 帧中地址：0x0000   ← 协议帧里实际发的偏移量，0 基
库函数 addr 参数：0
```

```text
4xxxx  → 保持寄存器（0x03 / 0x06 / 0x10）
3xxxx  → 输入寄存器（0x04）
1xxxx  → 离散输入（0x02）
0xxxx  → 线圈（0x01 / 0x05 / 0x0F）
```

但是**不要仅凭 `4xxxx` 机械减 40001**：也有厂商手册直接给 0 基或 1 基地址，还有厂商自定义编号。正确做法是用手册给出的**示例帧**或调试工具先验证一个已知寄存器，确认基准后再批量映射。

> 地址差 1 是 Modbus 项目最常见的问题，没有之一。典型现象是读到的值整体偏移一格，或返回异常码 `0x02`（Illegal Data Address）。

### 5.6 16 位之外的数据与字序

单个寄存器在帧中按高字节在前传输，但一个 32 位值横跨两个寄存器时，**寄存器的先后顺序没有统一的设备级约定**。`0x11223344` 可能是：

```text
ABCD：0x1122 0x3344    （big-endian，最常见）
CDAB：0x3344 0x1122    （word swap）
BADC：0x2211 0x4433    （byte swap）
DCBA：0x4433 0x2211    （full swap）
```

浮点数同理。此外还要确认：值是否有符号、缩放倍率（原始值 253 表示 25.3 ℃）、单位、是否掉电保存、写入后何时生效。

建议把这些转换**集中在一个寄存器映射层**，不要散落在业务或 UI 代码里。

### 5.7 正常响应与异常响应

从机理解了请求但无法完成时，返回异常帧：

```text
异常功能码 = 原功能码 | 0x80
```

例如请求 `0x03`，异常响应功能码为 `0x83`：

```text
01 83 02 C0 F1
│  │  │  └──── CRC16（低字节先）
│  │  └─────── 异常码 0x02：Illegal Data Address
│  └────────── 0x03 | 0x80
└───────────── 从机地址
```

| 异常码 | 名称 | 常见含义 | 现场怎么改 |
| ---: | --- | --- | --- |
| `0x01` | Illegal Function | 不支持该功能码 | 用错了 `0x03`/`0x04`，查数据区 |
| `0x02` | Illegal Data Address | 地址或范围非法 | **多半是 0/1 基地址差 1**，或一次读太多 |
| `0x03` | Illegal Data Value | 数量或写入值非法 | 检查数量上限、值域 |
| `0x04` | Slave Device Failure | 从机内部处理失败 | 设备侧故障，需告警 |
| `0x05` | Acknowledge | 已接受，需较长时间处理 | 延后读状态，不要立即重发 |
| `0x06` | Slave Device Busy | 从机忙 | 退避后重试 |

**关键认知：收到合法异常响应，恰恰证明这台设备是可达的。** 它是协议或业务错误，绝不能算成“设备掉线”去做重连。很多系统在这里误判，把一台只是地址写错的健康设备反复踢下线。

**本章小结：** 帧 = 地址 + 功能码 + 数据 + CRC（低字节先）；先确认功能码与数据区对应、地址基准和字序；异常响应说明设备在线。

## 第6章 CRC16 校验

### 6.1 为什么需要 CRC

UART 自带的奇偶校验只能覆盖单个字节，且只能发现奇数个错误位。RS485 现场的干扰往往成串出现，必须有帧级的差错检测——这就是 CRC 的作用。

Modbus RTU 使用 **CRC-16/Modbus**：

| 参数 | 值 |
| --- | --- |
| 多项式 | `0x8005`，反射形式 `0xA001` |
| 初始值 | `0xFFFF` |
| 输入反射 / 输出反射 | 是 / 是 |
| 结果异或值 | `0x0000` |
| 计算范围 | 从**从机地址字节**到**数据区最后一个字节**（不含 CRC 自身） |
| 传输顺序 | **低字节在前，高字节在后** |

### 6.2 参考实现

逐位实现，易读、无查表开销，适合资源紧张的 MCU：

```c
uint16_t modbus_crc16(const uint8_t *buf, uint16_t len)
{
    uint16_t crc = 0xFFFF;

    for (uint16_t i = 0; i < len; i++) {
        crc ^= (uint16_t)buf[i];          /* 注意：与低字节异或 */
        for (uint8_t bit = 0; bit < 8; bit++) {
            if (crc & 0x0001) {
                crc = (uint16_t)((crc >> 1) ^ 0xA001);
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;
}

/* 组帧时 */
uint16_t crc = modbus_crc16(frame, n);
frame[n]     = (uint8_t)(crc & 0xFF);   /* CRC Lo 先发 */
frame[n + 1] = (uint8_t)(crc >> 8);     /* CRC Hi 后发 */
```

对速度敏感时可改用半字节（16 项）或整字节（256 项）查表法，用空间换时间。

### 6.3 接收端校验的两种写法

```c
/* 写法一：算出 CRC 与帧尾两字节比较 */
uint16_t calc = modbus_crc16(rx, rx_len - 2);
uint16_t recv = (uint16_t)rx[rx_len - 2] | ((uint16_t)rx[rx_len - 1] << 8);
bool ok = (calc == recv);

/* 写法二：把 CRC 一起算进去，结果应为 0 */
bool ok2 = (modbus_crc16(rx, rx_len) == 0x0000);
```

写法二更简洁，且能自然处理 CRC 的字节序。

### 6.4 校验一下前面的例子

```text
01 03 00 00 00 02        → CRC = 0x0BC4 → 线上 C4 0B  ✔
01 03 04 00 19 00 64     → CRC = 0x1F2A → 线上 2A 1F  ✔
01 83 02                 → CRC = 0xF1C0 → 线上 C0 F1  ✔
```

手动核对抓包数据时，这就是判断“是线上出错”还是“是我组帧错了”的直接手段。

### 6.5 CRC 的能力边界

CRC 能做的：发现传输过程中的位错误。

CRC **不能**做的：

- 不能**纠正**错误——只能发现，然后重传；
- 不提供加密、身份认证、防重放；
- **不能区分“线路干扰”和“帧边界识别错误”**。这一点很关键：如果两帧粘在一起、或一帧被截成两段，算出来同样是 CRC 错误。所以**持续的 CRC 错误不一定是干扰，很可能是方向控制时序或帧间隔的问题**。

如果用 libmodbus 等成熟库，CRC 的生成和校验已经自动完成，业务代码不应再算一遍；只有在分析裸帧、写抓包工具或实现私有链路时才需要手算。

**本章小结：** CRC-16/Modbus，初值 `0xFFFF`、反射多项式 `0xA001`、低字节先发；CRC 错不等于电气干扰，先排除帧边界问题。

## 第7章 主从轮询与时间边界

### 7.1 为什么必须是主从轮询

RS485 两线半双工只提供了共享线路，**不提供任何仲裁机制**（这点与 CAN 不同，CAN 有基于显隐性电平的非破坏性仲裁）。所以冲突只能靠上层协议避免。

Modbus 采用最简单可靠的方式：**严格主从轮询**。

```text
一轮轮询（严格串行，任何时刻总线上只有一笔事务）：

  第 1 笔： 主机发请求给从机1 → 从机1 响应 → t3.5 静默
  第 2 笔： 主机发请求给从机2 → 从机2 响应 → t3.5 静默
  第 3 笔： 主机发请求给从机3 → 等待超时（该从机离线）→ guard → t3.5 静默
  ...
  轮完最后一台后回到从机1，开始下一轮
```

规则：

- 只有主机能主动发起请求；
- 只有被点名的从机能回复；
- 从机不能主动上报，除非协议专门设计了时隙或令牌机制；
- 主机确认发送完成后必须释放总线，并留出收发切换与从机响应的时间；
- **一条总线只能有一个通信执行者**，所有请求统一排队串行执行。

如果两个节点同时发送：

- 总线差分电平被相反方向驱动，数据必然损坏；
- 两个节点读到的都是错误数据；
- 两个驱动级形成总线争用，产生异常电流（现代器件通常有限流 / 热保护，但持续争用仍应避免）；
- 现场表现为：偶发 CRC 错、随机超时、某些节点时好时坏。

对多线程场景，务必记住：

```text
1 条物理 RS485 总线
    = 1 个串口设备
    = 1 个通信上下文（如 1 个 modbus_t）
    = 1 个通信任务 / Worker
    → 连接 N 个不同地址的从机
```

**不要为 32 台从机开 32 个并发通信线程。**

### 7.2 RTU 的时间边界

RTU 帧没有帧头帧尾，**靠总线静默识别边界**，所以时间参数是协议的一部分。

先算字符时间：

```text
字符位数 = 1 起始位 + 数据位 + 可选校验位 + 停止位
字符时间 = 字符位数 / 波特率
```

| 串口格式 | 每字符位数 | 9600 下单字符 | 9600 下 t3.5 |
| --- | ---: | ---: | ---: |
| 8N1 | 10 | 1.042 ms | 3.646 ms |
| 8E1 / 8O1 | 11 | 1.146 ms | 4.010 ms |
| 8N2 | 11 | 1.146 ms | 4.010 ms |

> 规范前提：Modbus over Serial Line 规范把 RTU 的一个字符固定定义为 **11 位**，并规定
> **无校验时使用 2 个停止位**（即 8N2）。因此规范语境下 9600 的 t3.5 通常引作 4.01 ms。
> 现场大量设备实际按 8N1（10 位）实现，两者互通时，帧间隔按 **11 位**计算并向上取整最安全。

规范常用规则：

- 波特率 **≤ 19200**：按 1.5 和 3.5 字符时间实算；
- 波特率 **> 19200**：建议采用固定 `t1.5 = 750 µs`、`t3.5 = 1.750 ms`。

三个容易混淆的时间：

| 参数 | 约束对象 | 触发时机 | 目的 |
| --- | --- | --- | --- |
| `t1.5` | 帧**内部**相邻字符的最大间隔 | 接收过程中 | 超过则认为帧结束（可能是坏帧） |
| `t3.5`（帧间隔） | 两帧**之间**的最小静默 | 每笔实际收发之后 | 满足 RTU 帧边界要求 |
| `guard interval` | 通信**异常**后的隔离等待 | 超时、坏帧之后 | 隔离可能迟到的旧响应 |

```text
正常事务：

  ① 主机发送请求帧
  ② 从机处理（延时不确定）
  ③ 主机接收响应帧
  ④ 保持 t3.5 静默
  ⑤ 发送下一帧

  response timeout 从“请求帧发完”开始计时，到“响应帧收完”为止，
  即只覆盖 ② + ③；它既不包含 ① 发送请求本身的时间，也不包含 ④ 的 t3.5。
  响应帧内部相邻字节的间隔另由 t1.5 / byte timeout 约束。

通信异常（超时或坏帧）：

  ① 主机发送请求帧
  ② response timeout 耗尽，未收到可用响应
  ③ flush：丢弃此刻已到达接收缓冲区的残留字节
  ④ 等待 guard interval —— 隔离“未来才到达”的迟到响应
  ⑤ 发送下一帧之前再 flush 一次（清掉 guard 期间才到达的迟到响应）
  ⑥ 保持 t3.5 静默后发送下一帧

  ③ ~ ⑤ 必须按序执行，其间不得发起新事务：flush 只能清掉调用时已到达的字节，
  ④ 的 guard 负责把迟到响应“等出来”，再由 ⑤ 的第二次 flush 把它们清掉。
```

回到上面的表格：`t1.5` 管帧内、`t3.5` 管帧间、`guard interval` 管通信异常之后，三者目的不同，不能互相替代。

### 7.3 迟到响应为什么危险

主机等待从机 A 超时，**不代表 A 不会稍后响应**。如果主机立刻去问从机 B，A 的迟到响应就可能落进 B 的接收窗口：

```text
请求 A ──── 等待 ──── timeout
                          ├── 立即请求 B ─────────┐
                          └──── A 的迟到响应 ─────┘  交叠 / 错配
```

好的协议栈通常能靠地址、功能码和长度发现错配，但残留数据仍会造成坏帧、CRC 错和下一笔事务异常。所以**通信错误之后要先隔离，不要立刻访问下一个从机**：

```text
保存错误码 → 必要时 flush → 等待 guard → 下次发送前再 flush 一次 → 保持 t3.5 静默 → 发送下一帧
```

`flush` 只能丢弃**调用时已经到达**接收缓冲区的数据，**无法删除未来才到的迟到响应**——这就是必须有 guard 的原因。guard 初值可取 10 ms，并用抓包校准。

也不要在每次正常请求前无条件 flush：它会掩盖真正的时序问题，还可能丢掉有诊断价值的数据。

### 7.4 超时不是越长越稳

这是轮询系统的核心权衡：

```text
32 台设备，其中 1 台离线
timeout = 5 s    → 每一轮至少多阻塞 5 s；连同重试共 3 次尝试就是 15 s
                   一台坏设备拖垮整条总线的实时性
timeout = 100 ms → 同样场景每轮只多 0.1 ~ 0.3 s
```

合理做法：

1. 对每种设备、每个功能码实测响应时间：P95 至少 100 次事务，P99 建议 1000 次以上（样本不足时只用 P95 和最大值，不要据 100 次样本谈 P99）；
2. timeout 取值覆盖合理的尾延迟，但不要大到能掩盖故障；
3. 对判定离线的设备采用**退避探测**（如 5 s → 10 s → 30 s 封顶），而不是每轮都去问；
4. 区分**单设备故障**和**总线故障**：连续多台不同设备同时失败，多半是总线级问题（断线、终端、方向控制），应走总线恢复流程而不是逐台判离线。

一组可用作起点的基线参数（**必须用现场实测校准**）：

| 参数 | 初始值 |
| --- | --- |
| 串口 | `9600 8N1` 或 `115200 8N1`；须与从机完全一致，部分设备为 `8E1` |
| response timeout | 100 ms 起步（低速长帧需放大） |
| byte timeout | 第一版关闭，避免把调度抖动误判为失败 |
| 帧间隔 `t3.5` | 115200 下 1.75 ms；≤19200 按字符时间实算并上取整 |
| guard interval | 10 ms |
| 离线阈值 | 连续 3 次逻辑请求通信失败 |
| 离线探测退避 | 5 s → 10 s → 30 s |
| 目标总线利用率 | 60% ~ 70% |

### 7.5 写超时意味着什么

**写请求超时只说明主机没收到确认，不能证明从机没有执行。** 响应可能在链路上丢了，而写入已经生效。

因此必须区分：

| 类型 | 例子 | 超时后能否自动重试 |
| --- | --- | --- |
| 幂等写 | “把模式设为 3”“把设定值写成 25.0” | 可以，重复执行结果相同 |
| 动作类写 | “计数加一”“切换状态”“触发一次动作” | **不能**，应返回“结果未知”，由上层读状态或人工确认 |

协议设计阶段就应优先采用 set-value 语义，避免 toggle / increment / trigger。

**本章小结：** 严格主从、一条总线一个执行者；`t1.5` 管帧内、`t3.5` 管帧间、guard 管异常后；timeout 要短而准；写超时 = 结果未知。

## 第8章 现场通信故障排查

排查必须**分层、由近及远**，否则很容易在错误的层面反复试错。推荐顺序：

```text
① 供电与收发器 → ② A/B 极性与接线 → ③ 方向控制时序
                                      → ④ 串口参数与协议 → ⑤ 总线质量与干扰
```

一个快速分流判据：

| 现象 | 最可能的层 |
| --- | --- |
| 完全没有任何响应，示波器上 A/B 无波形 | ① 供电 / 收发器 / 接线 |
| 能发出波形，但对方完全不回，或持续乱码 | ② A/B 极性 |
| 对方回了，但主机只收到半帧 / 尾部截断 | ③ 方向控制时序 |
| 收到完整帧但内容不对、或返回异常码 | ④ 参数、地址、寄存器表 |
| 大部分正常，**偶发** CRC 错 / 随机掉线 | ⑤ 拓扑、终端、偏置、干扰 |

### 8.1 先确认供电与收发器

- 收发器供电正常，TTL 侧电平与 MCU 的 3.3 V / 5 V 匹配（5 V 收发器的 `RO` 直接接 3.3 V MCU 可能超压）；
- `DI` 接 MCU `TX`，`RO` 接 MCU `RX`（**这一侧是直连，不是交叉**）；
- `DE`、`/RE` 被正确驱动，**没有悬空**；
- 隔离型模块的隔离侧供电（隔离 DC-DC 或外部供电）是否齐全——隔离侧没电是“完全无波形”的高频原因；
- 接线端子与设备手册定义一致，线没有压在绝缘皮上、没有虚接。

### 8.2 A/B 极性不确定怎么办

典型现象：设备看起来都正常，主机能发，但**完全没有回复或持续乱码**。

步骤：

1. 先核对两端设备手册中 `A/B`、`D+/D-`、`485+/485-` 的定义，以“非反相/反相”为准；
2. 断电后确认接线无误、所有设备极性一致；
3. 用万用表量空闲时 A-B 的直流压差，可以判断偏置方向是否符合预期；
4. 若定义确实不清楚，**仅在点对点、单节点或已隔离的验证环境**中对调一端的 A/B 再测；多节点现场总线不要盲目交换；
5. 一旦确认，立即给线缆和端子做统一标识，避免下次重复踩坑。

### 8.3 检查方向控制时序

“主机能发但收不到回复”时，重点查：

- 主机发完后是否**真的把 `DE` 拉低**、释放了总线；
- 是否等到**最后一个停止位发完**（`TC`）才切换，而不是 `TXE` 或 DMA 完成；
- 主机是否**在从机开始回复之前**已经打开接收器；
- **从机侧**是否也正确控制了自己的方向脚；
- 有没有某个节点的 `DE` 因为上电默认值或程序跑飞而一直有效，霸占了总线——可以逐台断电排除。

仪器用法：

| 仪器 | 看什么 |
| --- | --- |
| 逻辑分析仪 | MCU 侧 `UART_TX`、`UART_RX`、`DE` 的相对时序；能直接看出切换早了还是晚了 |
| 示波器（配差分探头） | 总线 A/B 的差分幅度、上升沿、反射与振铃；看电气质量 |
| 串口抓包 / 协议分析仪 | 完整字节流，用于核对帧结构和 CRC |

注意：软件 debug 打印只能看到**操作系统交给程序的字节**。怀疑方向切换、电气干扰、终端匹配时，必须上硬件仪器。

### 8.4 确认串口参数与协议

- 波特率、数据位、校验位、停止位在**所有节点**上完全一致（`8N1` 与 `8E1` 不匹配的典型现象不是报错，而是乱码或超时）；
- 从机地址正确、**全总线唯一**（两台同地址设备会同时应答，必然冲突）；
- 没有误用广播地址 `0` 却又在等回复；
- 功能码与数据区对应（`0x03` 读保持寄存器 vs `0x04` 读输入寄存器）；
- 寄存器地址的 0/1 基处理正确——**先用手册示例帧验证一个已知寄存器**；
- 单次读写数量未超过协议上限；
- 主机等待回复的超时不要设得过短（低波特率下长帧本身就要几十毫秒）；
- 数据解析时字序、符号、倍率与手册一致。

联调建议：

```text
1. 只接一台从机，用 modpoll 或厂商工具先确认参数能通
2. 打开协议库的 debug（如 modbus_set_debug），看 Tx/Rx 十六进制
3. 对照手册逐字节核对：地址 / 功能码 / 协议地址 / 数量 / CRC
4. 上仪器看 UART TX、RX、DE 和总线 A/B
5. 单台稳定后再扩展到 4、16、32 台，重新验证时序和利用率
```

### 8.5 最后排查总线质量与干扰

这一层对应的是**偶发**故障：大部分时间正常，但随机出现 CRC 错、超时、某台设备时好时坏。

| 检查项 | 判据 |
| --- | --- |
| 拓扑 | 是否手拉手，有没有星形分叉或过长支线 |
| 终端电阻 | 是否**只**在两个物理末端各一个；断电量 A-B 直流电阻，约 60 Ω 合理，20 ~ 30 Ω 说明装多了 |
| 偏置 | 空闲时 A-B 是否有稳定压差；是否多处重复加偏置 |
| 线缆 | `A/B` 是否在同一对双绞线内；是否误用了网线中两根不同对的线 |
| 走线 | 是否与变频器输出、动力电缆长期并行 |
| 屏蔽 | 屏蔽层是否单点接地，有没有两端接地形成地环流 |
| 共模 | 跨配电箱 / 跨建筑时是否有地电位差，是否需要隔离型收发器 |
| 负载 | 节点数是否超出收发器单位负载能力 |
| 扩展时机 | 是否在加了某台设备后才开始出问题——优先怀疑这台的终端跳帽和方向控制 |

一个实用手法：**逐段缩短总线**。把总线从末端逐段断开并加临时终端，看故障在哪一段消失，通常能快速定位到某个分支或某台设备。

关于节点数：传统收发器常按 32 个单位负载（假设每个节点计 1 UL）估算，现代低单位负载器件（1/2 UL、1/4 UL、1/8 UL）可支持更多。**这是电气负载上限，不是 Modbus 的地址上限**（地址可到 247），工程上应按器件手册和现场实测确定。

### 8.6 区分“设备故障”和“总线故障”

这两类的处理方式完全不同，必须分开：

| 判据 | 结论 | 处理 |
| --- | --- | --- |
| 只有 1 台设备持续失败，其他正常 | 单设备故障 | 该设备标记离线 + 退避探测，不影响其他设备轮询 |
| 连续多台**不同**设备同时开始失败 | 总线级故障 | 走总线恢复流程：停止轮询、检查链路、重连串口 |
| 串口设备本身消失（如 USB 被拔） | 链路故障 | 关闭并重新打开串口，指数退避重连 |
| 收到合法异常响应（`0x8X`） | **设备在线**，是协议 / 业务错误 | 修正地址或参数，**不要**判离线 |

同样重要的是**不要盲目重试**。重试必须基于语义：

- 本地参数错误 → 不重试，重试多少次都错；
- 合法异常响应 → 通常不重试（`Busy` 可退避后重试）；
- 超时 / CRC 错 → 有限次重试，且写操作要看幂等性；
- 串口不可用 → 不在原地重试，走重连流程。

### 8.7 日志与可观测性

现场问题往往不能复现，所以日志决定了排查效率。每笔事务建议记录：

```text
时间戳、请求ID、SlaveID、功能码、地址、数量、结果、
原始错误码、异常码、重试次数、
排队耗时、收发耗时、端到端耗时、
错误分类、连续失败计数、设备状态迁移、总线状态
```

把耗时拆成三段很有价值：

- **排队耗时**高 → 调度或总线容量不足；
- **收发耗时**高 → 从机慢、timeout 过大或物理链路异常；
- **端到端**高但前两者正常 → 重试、guard 或回调处理过慢。

告警要能区分「单设备离线」「多设备同时失败」「串口设备消失」「队列持续过载」，否则现场只会看到一条没有行动指导意义的 “Modbus error”。

**本章小结：** 按供电 → 极性 → 方向 → 参数 → 总线质量分层排查；偶发故障优先看拓扑 / 终端 / 偏置；异常响应不等于掉线。

## 第9章 高频易错点与速查

### 9.1 常见误解对照表

| 常见说法 | 更准确的说法 |
| --- | --- |
| RS485 就是 Modbus | RS485 是电气层，Modbus RTU 只是可以跑在它上面的协议之一 |
| 设备是 485 的，所以能直接通信 | 还得确认波特率、校验、地址、上层协议和寄存器表 |
| A/B 要像 TX/RX 一样交叉接 | 总线侧通常 A 接 A、B 接 B，但必须以厂家的极性定义为准 |
| RS485 只有两根线，永不需要地线 | 差分仍受共模范围限制，地电位差和参考地要按系统设计处理 |
| 每个设备都要加 120 Ω | 通常只在总线两个**物理末端**各加一个 |
| 有终端电阻就不需要偏置 | 终端解决反射，偏置解决空闲电平不确定，是两件事 |
| DMA 发送完成就能切回接收 | DMA 完成 ≠ 最后一位已上线，还要等 UART 线路完成（STM32 的 `TC`） |
| 多个从机都能随时主动上报 | 半双工总线没有仲裁，必须由协议保证轮流说话 |
| RS485 抗干扰强，所以布线随意 | 长线、高速、强干扰场景更依赖双绞、拓扑、终端和隔离 |
| CRC 错就是现场有干扰 | 也可能是方向切换时序或帧间隔问题导致的帧边界错误 |
| 手册写 40001，代码就填 40001 | 帧中通常是 0 基偏移 `0x0000`，但必须用示例帧验证 |
| 返回异常码 = 设备掉线 | 恰恰相反，能返回异常响应说明设备可达 |
| 超时设长一点更稳 | 超时越长，一台离线设备拖垮整条总线越严重 |
| 写超时说明没写进去 | 只说明没收到确认，可能已经执行；动作类写不能自动重试 |
| 一条总线开多个线程能提速 | 半双工总线必须串行，多线程只会制造冲突 |

### 9.2 最简记忆版

**RS485 侧：**

- RS485 是差分电气层，常由 `UART + RS485 收发器` 实现；`A/B` 是总线，不是 `TX/RX`。
- 总线侧同极性直连（通常 `A→A`、`B→B`），但一定要看设备手册。
- 默认两线半双工，同一时刻只能一个节点发送。
- `DE` / `/RE` 控制方向，默认接收态；发送后必须等 **`TC`** 再释放总线。
- 手拉手拓扑，**两个物理末端各一个约 120 Ω** 终端电阻，中间不装。
- 全总线**只保留一组偏置电阻**，用于保证空闲电平确定。
- A/B 必须走同一对双绞线；跨供电系统考虑隔离。

**Modbus RTU 侧：**

- 帧 = `地址(1) + 功能码(1) + 数据(N) + CRC16(2)`，CRC **低字节先发**。
- CRC-16/Modbus：初值 `0xFFFF`、反射多项式 `0xA001`、覆盖除 CRC 外全部字节。
- 帧边界靠静默：帧内 ≤ `t1.5`，帧间 ≥ `t3.5`，异常后再加 `guard`。
- 严格主从轮询：一条总线 = 一个串口 = 一个通信上下文 = 一个执行任务。
- `0x03` 读保持、`0x04` 读输入、`0x06` 写单个、`0x10` 写多个；注意单次数量上限。
- 地址先验证 0/1 基，这是最常见的坑；32 位数据先确认字序。
- 异常响应（功能码 `| 0x80`）说明设备**在线**，不要判离线。
- 写超时 = 结果未知；只有幂等写能安全重试。

### 9.3 上线检查清单

```text
硬件 / 电气
[ ] 手拉手拓扑，无星形分叉和长支线
[ ] 仅总线两个物理末端配置 120 Ω 终端电阻（断电实测 A-B ≈ 60 Ω）
[ ] 全总线只有一组偏置电阻，空闲时 A-B 压差稳定
[ ] A/B 走同一对双绞线；必要时屏蔽层单点接地
[ ] 所有设备 A/B 极性定义一致，端子已做标识
[ ] 跨供电系统已评估共模 / 地电位差，必要时使用隔离收发器
[ ] 未与变频器等强干扰源长距离并行走线
[ ] 节点数在收发器单位负载能力之内

方向控制
[ ] DE / /RE 上电默认接收态，且有外部下拉电阻保证复位期间不悬空
[ ] 发送后等 TC（而非 TXE / DMA 完成）再释放总线
[ ] 自动方向模块未叠加软件 RTS 控制
[ ] 一条总线仅由一个通信任务操作

协议 / 参数
[ ] 设备确实使用 Modbus RTU，而非 RS485 私有协议
[ ] 全总线串口参数一致（波特率 / 数据位 / 校验 / 停止位）
[ ] 所有 Slave ID 唯一，未误用广播地址 0
[ ] 已用示例帧验证寄存器 0/1 基地址、数据类型、倍率和字序
[ ] 单次读写数量未超协议上限，且发送前做了校验

时序 / 健壮性
[ ] 每笔事务之后保证 t3.5 帧间隔
[ ] 通信异常后有 flush + guard 的迟到响应隔离
[ ] timeout 基于实测 P95/P99，未设成秒级
[ ] 重试基于语义：本地错误不重试，动作类写超时不自动重试
[ ] 单设备状态与总线状态分离，离线设备采用退避探测
[ ] 日志保留原始错误码、异常码、分段耗时和状态迁移
[ ] 已完成单设备、多设备、断线、热插拔和长稳测试
```

## 附录 A 术语速查

| 术语 | 含义 |
| --- | --- |
| `A` / `B`（`D+` / `D-`） | RS485 差分总线的两根线；不同厂家命名可能相反 |
| `DI` / `RO` | 收发器的发送输入 / 接收输出，分别接 MCU 的 `TX` / `RX` |
| `DE` / `/RE` | 发送使能（高有效）/ 接收使能（低有效），常并接一个 GPIO |
| `TC` | Transmission Complete，UART 移位寄存器也已空、最后一位已上线 |
| 终端电阻 | 总线两端匹配线缆特性阻抗、吸收反射的电阻，常用 120 Ω |
| 偏置电阻 | 保证总线空闲时差分电平确定的上下拉电阻（fail-safe bias） |
| 单位负载（UL） | 衡量节点对总线电气负载的单位；传统按 32 UL 估算最大节点数 |
| ADU / PDU | 应用数据单元（含地址与 CRC）/ 协议数据单元（功能码 + 数据） |
| `t1.5` / `t3.5` | RTU 帧内最大字符间隔 / 帧间最小静默时间 |
| guard interval | 通信异常后为隔离迟到响应而额外等待的时间 |
| Slave ID | Modbus 从机地址，`1 ~ 247`，`0` 为广播 |
| Exception Code | 异常响应中的错误原因码，如 `0x02` 地址非法 |
