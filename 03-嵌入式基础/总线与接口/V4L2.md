# V4L2：理解 MIPI CSI 摄像头的帧队列采集流程

## 1. 先说结论

**V4L2（Video for Linux 2）是 Linux 内核的视频采集子系统和用户态接口规范。**它把 USB 摄像头、MIPI CSI 摄像头、HDMI 采集卡等不同硬件，统一呈现为类似 `/dev/video0` 的视频设备节点。

应用不需要直接操作 CSI 控制器、DMA 或摄像头寄存器，而是通过 V4L2 API 完成：

```text
应用程序
    ↓ ioctl / mmap / poll
/dev/video0
    ↓
V4L2 核心与视频设备驱动
    ↓
CSI 接收控制器 / DMA
    ↓
MIPI CSI 数据线 ← 摄像头 Sensor
```

因此，V4L2 不是 MIPI 协议，也不是摄像头传感器驱动；它位于硬件总线和应用之间，负责把连续的视频数据组织成应用可使用的“帧”和“缓冲区队列”。

## 2. 为什么 MIPI CSI 需要 V4L2

UART 的自然模型是连续字节流，I2C/SPI 的自然模型是一次次事务，而 MIPI CSI 传输的是高速、连续的像素数据。应用真正关心的通常不是“从某个寄存器读几个字节”，而是：

- 当前帧的分辨率、像素格式和字节布局；
- 一帧数据何时开始、何时完成；
- 哪个缓冲区正在被硬件填充；
- 哪个缓冲区已经填满，可以交给应用处理；
- 处理完成后，哪个缓冲区可以重新交还给硬件。

如果每帧都通过普通 `read()` 临时申请和复制内存，会产生较大 CPU 和内存开销。V4L2 因此提供以缓冲区为核心的流式采集模型，常用 `mmap` 让应用直接访问驱动准备的帧缓冲区，并通过队列反复循环使用这些缓冲区。

## 3. V4L2 的本质：统一视频设备的操作模型

V4L2 主要由两部分组成：

1. **内核框架和驱动 API**：规定视频设备驱动如何描述能力、配置格式、管理缓冲区和报告事件；
2. **用户态接口规范**：应用通过 `/dev/videoX`、`ioctl()`、`mmap()`、`poll()` 等标准接口访问设备。

典型关系如下：

```text
应用层：采集、预览、编码、保存
        ↓
V4L2 用户态 ABI：open / ioctl / mmap / poll / close
        ↓
V4L2 视频设备驱动：格式协商、队列管理、流状态
        ↓
硬件抽象：CSI 接收器、ISP、DMA、Sensor 子设备
        ↓
MIPI CSI：高速传输像素数据
```

V4L2 屏蔽的是**视频设备的操作差异**，不是把所有硬件都变成简单的文件读写。底层 Sensor 常通过 I2C 配置曝光、增益、分辨率和工作模式；MIPI CSI 负责传输图像数据；CSI 控制器和 DMA 负责接收并写入帧缓冲区；V4L2 再把这些内存组织成帧交给应用。

## 4. 两种采集方式

### 4.1 `read()` 模式

应用调用 `read(fd, buf, size)`，驱动把一帧或部分视频数据复制到应用提供的缓冲区。这种方式简单，适合学习、调试或低性能场景，但每次采集通常涉及内存复制。

### 4.2 流式队列 + `mmap()` 模式

这是嵌入式 Linux 摄像头最常见的方式。驱动申请多个帧缓冲区，应用将它们映射到自己的地址空间。硬件填充哪个缓冲区、应用处理哪个缓冲区，通过 V4L2 队列完成交接。

```text
应用 QBUF：把空闲 buffer 交给驱动
        ↓
硬件/DMA 填充一帧
        ↓
驱动把完成的 buffer 放入完成队列
        ↓
应用 DQBUF：取出一帧进行处理
        ↓
应用处理完成后再次 QBUF
```

这里的队列同时表达了**缓冲区所有权**：`QBUF` 后由驱动/硬件使用，`DQBUF` 后交给应用；应用处理完成后再次 `QBUF`，buffer 才能重新被硬件填充。多个 buffer 形成循环队列，可以减少等待和丢帧，常见做法是准备至少 3 个缓冲区。

## 5. 标准 V4L2 采集流程

```text
open("/dev/video0")
    ↓
VIDIOC_QUERYCAP       查询能力
VIDIOC_S_FMT          协商分辨率和像素格式
VIDIOC_REQBUFS        申请多个视频 buffer
VIDIOC_QUERYBUF       查询 buffer 信息
mmap                  映射到用户空间
VIDIOC_QBUF           所有空闲 buffer 入队
VIDIOC_STREAMON       启动采集
    ↓
循环：poll → VIDIOC_DQBUF → 处理一帧 → VIDIOC_QBUF
    ↓
VIDIOC_STREAMOFF → munmap → close
```

典型的关键调用如下：

```c
int fd = open("/dev/video0", O_RDWR);

ioctl(fd, VIDIOC_QUERYCAP, &cap);
ioctl(fd, VIDIOC_S_FMT, &fmt);
ioctl(fd, VIDIOC_REQBUFS, &req);
ioctl(fd, VIDIOC_QUERYBUF, &buf);
addr = mmap(NULL, buf.length, PROT_READ | PROT_WRITE,
            MAP_SHARED, fd, buf.m.offset);

ioctl(fd, VIDIOC_QBUF, &buf);       // 空闲 buffer 交给驱动
ioctl(fd, VIDIOC_STREAMON, &type);  // 开始视频流

ioctl(fd, VIDIOC_DQBUF, &buf);      // 取出已完成的一帧
process_frame(addr, buf.bytesused);
ioctl(fd, VIDIOC_QBUF, &buf);       // 归还 buffer
```

`VIDIOC_S_FMT` 返回后必须检查实际格式，因为驱动可能修正应用请求的分辨率或像素格式。阻塞模式下 `DQBUF` 会等待一帧完成；非阻塞模式下通常先使用 `poll()` 等待设备就绪，再调用 `DQBUF`。

## 6. 常用 ioctl 的职责

| ioctl | 作用 |
| --- | --- |
| `VIDIOC_QUERYCAP` | 查询设备能力 |
| `VIDIOC_ENUM_FMT` | 枚举支持的像素格式 |
| `VIDIOC_ENUM_FRAMESIZES` | 枚举支持的分辨率 |
| `VIDIOC_S_FMT` / `VIDIOC_G_FMT` | 设置/读取当前格式 |
| `VIDIOC_REQBUFS` | 申请或释放缓冲区队列 |
| `VIDIOC_QUERYBUF` | 查询 buffer 的偏移、长度等信息 |
| `VIDIOC_QBUF` | 将空闲 buffer 入队 |
| `VIDIOC_DQBUF` | 取出已完成的 buffer |
| `VIDIOC_STREAMON` | 开始视频流 |
| `VIDIOC_STREAMOFF` | 停止视频流 |

这些命令体现了 V4L2 的核心：**先协商格式，再建立缓冲区队列，最后控制数据流状态。**

## 7. MIPI CSI 摄像头的完整链路

```text
应用
  │ V4L2 ioctl / mmap / poll
  ▼
/dev/video0（视频节点）
  │ V4L2 capture 驱动
  ▼
CSI 控制器 / ISP / DMA
  │ 接收、解析并写入帧 buffer
  ▼
MIPI CSI-2 数据通道
  ▼
Camera Sensor
  ▲
  │ I2C：配置寄存器、曝光、增益、模式
```

这里有三个不同层次：

- **I2C 是控制通路**：一次次事务读写 Sensor 寄存器，配置摄像头如何工作；
- **MIPI CSI 是数据通路**：高速连续传输图像像素，最终由 DMA 写入多个帧缓冲区；
- **V4L2 是软件框架**：把 CSI 产生的帧缓冲区、格式、队列和流状态提供给应用。

所以不能把“通过 I2C 读 Sensor 寄存器”和“通过 V4L2 获取一帧图像”混为同一种操作：前者是控制事务，后者是帧队列。

## 8. CSI、DSI 与 V4L2 的边界

“MIPI 使用 V4L2”通常主要指 **MIPI CSI 摄像头采集**：CSI 把输入图像交给 V4L2 视频采集框架。

**MIPI DSI 显示输出通常对应 DRM/KMS，而不是 V4L2。** DSI 的目标是把显示控制器产生的图像或显示命令发送到屏幕，应用常通过 framebuffer、DRM/KMS、Atomic Commit、page-flip 等机制提交显示 buffer。

| 场景 | 数据方向 | 常见 Linux 子系统 | 典型模型 |
| --- | --- | --- | --- |
| MIPI CSI 摄像头 | Sensor → 内存/应用 | V4L2、Media Controller | 采集帧、`QBUF/DQBUF`、`mmap` |
| MIPI DSI 显示屏 | 内存/显示控制器 → Panel | DRM/KMS | framebuffer、page-flip、Atomic Commit |

两者都可能使用 DMA、双缓冲或多缓冲，但职责不同：V4L2 管理输入视频帧，DRM/KMS 管理显示 buffer 和提交时序。

## 9. 常见格式与工具

- `YUYV`：未压缩的 YUV 格式，处理简单但带宽较高；
- `MJPEG`：帧内压缩，降低传输带宽，但应用需要解码；
- `H.264`：压缩视频码流，通常依赖硬件编码/解码链路；
- `RGB565`、`RGB888`：常用于显示或图像处理。

```bash
# 查看设备能力和支持的格式
v4l2-ctl --all
v4l2-ctl --list-formats-ext -d /dev/video0

# 使用 MMAP 采集若干帧
v4l2-ctl -d /dev/video0 \\
    --set-fmt-video=width=640,height=480,pixelformat=YUYV \\
    --stream-mmap --stream-count=10 --stream-to=frames.raw

# 使用 FFmpeg 读取 V4L2 设备
ffmpeg -f v4l2 -i /dev/video0 out.mp4
```

`UVC` 与 `V4L2` 也不是同一层：UVC 是 USB 摄像头协议，`uvcvideo` 是基于 V4L2 框架实现的 USB 摄像头驱动；V4L2 则是 Linux 上层统一的视频设备接口。

## 10. 常见工程问题

1. **格式不匹配**：应用请求的分辨率或像素格式不受支持，应先枚举能力并检查 `S_FMT` 的实际返回值。
2. **buffer 数量不足**：处理速度跟不上采集速度时容易卡顿、丢帧，应根据帧率和处理时延调整缓冲区数量。
3. **调用顺序错误**：未 `QBUF`、未 `STREAMON` 就 `DQBUF`，通常会阻塞或返回错误。
4. **错误处理不完整**：需要处理 `EINTR`、`EAGAIN`、设备断开和流停止等状态。
5. **DMA/cache/对齐问题**：非一致性 DMA 平台需要按平台要求处理 cache、stride、对齐和 buffer ownership。
6. **资源未释放**：退出时执行 `STREAMOFF`、`munmap` 和 `close`，确保 DMA 不再访问失效内存。
7. **把 CSI 当普通文件读取**：高分辨率连续视频应优先使用流式 I/O 和缓冲区队列，而不是只依赖普通 `read()`。

## 11. 一句话总结

**V4L2 是 Linux 统一的视频采集框架：应用通过 `/dev/videoX` 协商格式，申请并映射多个帧缓冲区，再用 `QBUF/DQBUF` 循环完成“交给硬件—采集一帧—交给应用—归还硬件”的队列式数据交换。**

放回总线接口的整体视角：**I2C 配置 Sensor 是事务，MIPI CSI 传输图像是帧流，V4L2 管理帧和缓冲区队列；如果是 MIPI DSI 显示输出，则通常由 DRM/KMS 管理显示 buffer 和提交时序。**
