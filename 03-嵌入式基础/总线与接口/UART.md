# UART 基础知识总结

> 目标：这篇文档只作为 UART 入门和项目面试复习使用，不展开复杂的串口驱动框架、DMA 优化和工业总线协议细节。重点记住：UART 是什么、TX/RX 怎么接、波特率和帧格式是什么、TTL/RS232/RS485 有什么区别、常见问题怎么排查。
>
> 来源：围绕UART主题跟AI多轮对话后的总结文档，仅供参考。

## 1. 先用一句话理解 UART

**UART 是一种异步、点对点常见、按约定波特率收发数据的串行通信接口。**

结构可以先按下面这张图理解：UART 通常是两个设备点对点通信，发送端 `TX` 要接到对方 `RX`，接收端 `RX` 要接到对方 `TX`。

```text
设备 A / MCU                         设备 B / 模块
+-----------+                       +-----------+
|        TX | --------------------> | RX        |
|        RX | <-------------------- | TX        |
+-----------+                       +-----------+

方向理解：A_TX 发给 B_RX，B_TX 发给 A_RX。
```

> 关键点：UART 是点对点字节流通信，不共享时钟线；两端必须配置相同波特率和帧格式。TTL 串口实际接线时通常还要共地，但理解数据方向时先抓住 `TX` / `RX` 交叉连接。

它最典型的特点是：

- 不需要单独时钟线。
- 通常只需要 `TX` 和 `RX` 两根数据线。
- 通信双方必须配置相同波特率和帧格式。
- 常用于调试日志、命令交互、模块通信。
- 传的是字节流，本身不规定上层数据协议。

常见用途：

| 用途 | 常见场景 |
| --- | --- |
| 调试日志 | 串口打印、系统启动日志 |
| 命令交互 | AT 指令、Shell、调试命令 |
| 模块通信 | GPS、蓝牙、Wi-Fi、4G 模块 |
| MCU 通信 | 两个控制器之间传状态或控制命令 |
| 工业通信基础 | 通过收发器扩展成 RS485/RS232 |

简单记法：

- `TX`：Transmit，发送。
- `RX`：Receive，接收。
- `GND`：共地，TTL 串口通信通常必须共地。
- `Baudrate`：波特率，表示每秒传输多少个符号，常见近似理解为串口速度。

## 2. UART 在嵌入式项目里做什么

UART 常用于低成本、简单可靠的字节流通信。

以串口打印日志为例，UART 的工作可以理解为：

1. 软件把字符串写入串口发送接口。
2. UART 控制器按照配置好的波特率发送数据。
3. 每个字节被包装成起始位、数据位、可选校验位和停止位。
4. USB 转串口工具或另一块板子的 UART 接收这些位。
5. 上位机串口助手按相同参数解析成字符。

也就是说，UART 更像一条简单的字节流通道：

- 双方不用共享时钟线。
- 发送方按约定速度发。
- 接收方按同样速度采样。
- 上层协议由应用自己定义。

## 3. UART 的 TX 和 RX 怎么接

UART 最容易接错的是 TX/RX。

基本规则：

| 设备 A | 设备 B |
| --- | --- |
| `TX` | 接对方 `RX` |
| `RX` | 接对方 `TX` |
| `GND` | 接对方 `GND` |

也就是交叉连接：

```text
A_TX -> B_RX
A_RX <- B_TX
A_GND -- B_GND
```

注意：

- `TX` 是自己发出去的线。
- `RX` 是自己接收进来的线。
- 两边都叫 TX/RX，所以实际连线要交叉。
- TTL 串口通信通常必须共地，否则电平参考不一致。

直白说法：

> 自己的嘴 TX 要接到对方的耳朵 RX，自己的耳朵 RX 要接到对方的嘴 TX。

## 4. UART 为什么叫异步通信

UART 没有单独的时钟线，所以叫异步通信。

它依靠双方提前约定：

- 波特率。
- 数据位。
- 校验位。
- 停止位。

接收方通过起始位判断一个字符开始，然后按约定波特率在合适时间点采样后面的数据位。

典型一帧结构：

```text
空闲高电平 -> 起始位 -> 数据位 -> 可选校验位 -> 停止位 -> 空闲高电平
```

常见配置：

```text
115200 8N1
```

含义：

- `115200`：波特率。
- `8`：8 个数据位。
- `N`：No parity，无校验。
- `1`：1 个停止位。

## 5. UART 的帧格式

UART 一帧通常由以下部分组成：

| 字段 | 常见状态 | 含义 |
| --- | --- | --- |
| 空闲位 | 高电平 | 总线空闲状态 |
| 起始位 | 低电平 | 通知接收方一帧开始 |
| 数据位 | 5~9 bit 常见，8 bit 最常用 | 真正传输的数据 |
| 校验位 | 可选 | 奇校验、偶校验等 |
| 停止位 | 1/1.5/2 bit 常见 | 表示一帧结束 |

### 5.1 起始位

UART 空闲时通常为高电平。

当发送方要发送数据时，会先拉低一段时间，这个低电平就是起始位。

直白理解：

> 起始位就是告诉接收方：“我要开始发一个字节了。”

### 5.2 数据位

数据位是真正传输的内容，最常见是 8 bit。

UART 通常低位先发，也就是 `LSB first`。

### 5.3 校验位

校验位用于简单检查传输错误，常见类型：

| 校验 | 含义 |
| --- | --- |
| `None` | 不使用校验 |
| `Even` | 偶校验 |
| `Odd` | 奇校验 |

很多调试串口使用 `None`，也就是无校验。

### 5.4 停止位

停止位用于表示一帧结束，常见是 1 bit。

如果双方停止位配置不一致，可能出现接收异常、乱码或帧错误。

## 6. 波特率是什么

波特率可以简单理解为串口通信速度。

常见波特率：

| 波特率 | 常见用途 |
| --- | --- |
| `9600` | 老设备、低速模块、稳定性优先 |
| `38400` | 一些外设或旧模块 |
| `57600` | 中低速调试 |
| `115200` | 最常见调试串口 |
| `921600` | 高速日志或数据传输 |
| `1500000/3000000` | 更高速串口，依赖硬件支持 |

注意：

- 双方波特率必须一致。
- 波特率误差过大时会乱码。
- 波特率越高，对时钟精度、线长、干扰和电平质量越敏感。

直白说法：

> UART 两边必须用同一个节奏说话。一个按 115200 说，一个按 9600 听，结果一定是乱码。

## 7. TTL、RS232、RS485 的区别

UART 是一种串口控制器/通信方式，但实际电气层可能不同。

| 名称 | 电气特点 | 常见用途 |
| --- | --- | --- |
| `TTL UART` | 常见 3.3V/5V 电平，板级短距离 | MCU、模块、USB 转串口 |
| `RS232` | 电平与 TTL 不同，常见正负电压 | 传统串口设备、工控设备 |
| `RS485` | 差分信号，抗干扰强，距离远，常见多节点半双工 | 工业总线、多机通信 |

重点：

- MCU 的 UART 引脚通常是 TTL 电平。
- 不能把 TTL UART 直接接到 RS232 电平设备上。
- RS485 需要收发器芯片，并且常见半双工方向控制。

RS485 要特别注意：

- RS485 收发器不只是“电平转换”，而是把 MCU 的单端 UART TTL 信号转换成 `A/B` 差分信号，同时通过 `DE/RE` 控制发送驱动器和接收比较器。
- `DE=1` 时发送驱动器把 `DI` 转成差分 `A/B`；不发送时驱动器要关闭并进入高阻态，释放总线，避免占用 `A/B`。
- RS485 常见半双工的根本原因不是“线少”，而是多节点共享同一组 `A/B` 总线；同一时间如果多个节点同时驱动总线，会产生总线冲突，所以通常只能一个节点发送，其余节点接收。
- UART 规定的是串行数据帧格式；RS485 改变的是底层电气传输方式。二者是不同层次，不冲突。
- 对比理解：RS485 通常是一组共享差分总线，适合多节点半双工；RS422 通常发送和接收各一组差分线，收发通道分开，因此可以全双工。

直白说法：

> UART 更像“说话规则”，TTL/RS232/RS485 更像“说话用的电气嗓门和线路形态”。
## 8. UART 发送和接收流程

### 8.1 发送流程

典型发送过程：

1. 软件把字节写入 UART 发送寄存器或发送缓冲区。
2. UART 控制器按帧格式自动加起始位、校验位和停止位。
3. 数据从 `TX` 引脚一位一位输出。
4. 发送完成后产生状态标志或中断。

示例：

```text
Write Byte -> Start Bit -> Data Bits -> Parity -> Stop Bit
```

### 8.2 接收流程

典型接收过程：

1. UART 检测到 `RX` 从高电平变为低电平。
2. 认为起始位到来。
3. 按波特率在数据位中间采样。
4. 组装成字节。
5. 放入接收寄存器或 FIFO。
6. 软件轮询或中断读取数据。

注意：

- UART 接收到的是字节流。
- 一次应用层消息可能由多个字节组成。
- 要靠换行符、长度字段、固定帧头或超时来拆包。

## 9. RTOS 中 UART 接收数据的常见方式

在 RTOS 项目里，UART 接收数据通常不是只考虑“能不能收到一个字节”，还要考虑：

- 数据来得快不快。
- CPU 能不能一直等。
- 是否需要低功耗。
- 是否有一帧数据的边界。
- 接收后由哪个任务解析。
- 丢数据的后果是否严重。

常见方式可以分成下面几类：

| 接收方式 | 核心思路 | 常见场景 |
| --- | --- | --- |
| 轮询接收 | 任务主动查 UART 是否有数据 | 简单调试、低速低频数据 |
| 中断逐字节接收 | 每收到 1 个字节进中断，放入软件缓冲区 | 命令行、AT 指令、普通模块通信 |
| 中断 + FIFO/环形缓冲区 | 中断里快速搬数据，任务里慢慢解析 | 通用 RTOS 串口接收 |
| DMA 定长接收 | DMA 自动搬运固定长度数据 | 固定包长、高速连续数据 |
| DMA + 空闲中断接收 | DMA 持续接收，UART 空闲中断判断一帧结束 | 不定长帧、高速数据、常见项目方案 |
| 驱动阻塞读 | 任务调用 `read`，没数据就阻塞等待 | RTOS/类 POSIX 驱动接口 |
| 消息队列/事件通知 | 接收完成后通知解析任务 | 多任务解耦、协议栈处理 |

### 9.1 轮询接收

轮询接收就是任务不断检查 UART 接收寄存器或驱动状态，发现有数据再读取。

伪代码：

```c
void uart_poll_task(void *arg)
{
    uint8_t ch;

    while (1) {
        if (uart_rx_ready(UART1)) {
            ch = uart_read_byte(UART1);
            protocol_parse_byte(ch);
        }

        rtos_delay_ms(1);
    }
}
```

优点：

- 实现最简单。
- 适合验证硬件、调试串口、低速偶发数据。
- 不依赖复杂中断、DMA 或驱动框架。

缺点：

- CPU 会反复查询，效率低。
- 查询间隔太长容易丢数据。
- 查询间隔太短会浪费 CPU。
- 不适合高速连续接收。

适用场景：

- 裸机或简单 RTOS demo。
- 数据量很小、实时性要求不高的调试命令。
- 临时验证 UART 是否能收数据。

不适合：

- 高波特率日志。
- GPS、4G、Wi-Fi 等连续输出模块。
- 对丢字节敏感的协议。

### 9.2 中断逐字节接收

中断接收是最常见的方式之一。UART 每收到一个字节触发接收中断，中断服务函数把字节取走，放入软件缓冲区或直接投递给上层。

伪代码：

```c
ring_buffer_t uart_rx_rb;

void UART1_IRQHandler(void)
{
    uint8_t ch;

    if (uart_rx_interrupt_pending(UART1)) {
        ch = uart_read_byte(UART1);
        ring_buffer_put(&uart_rx_rb, ch);
        rtos_sem_release_from_isr(uart_rx_sem);
    }
}

void uart_parse_task(void *arg)
{
    uint8_t ch;

    while (1) {
        rtos_sem_wait(uart_rx_sem, WAIT_FOREVER);

        while (ring_buffer_get(&uart_rx_rb, &ch)) {
            protocol_parse_byte(ch);
        }
    }
}
```

优点：

- 响应及时，不需要任务一直轮询。
- 实现难度适中，适合大多数普通串口通信。
- 中断只负责搬字节，任务负责解析，结构清晰。

缺点：

- 每个字节都进一次中断，高波特率下中断频率高。
- 中断里处理太多逻辑会影响系统实时性。
- 软件缓冲区太小或解析任务不及时，会溢出丢数据。

适用场景：

- Shell 命令行。
- AT 指令。
- 普通传感器、蓝牙、Wi-Fi、MCU 间低中速通信。
- 不定长文本协议，例如以 `\r\n` 结束的一行命令。

注意：

- 中断里不要做复杂解析。
- 中断里不要长时间打印日志。
- 中断只做“读寄存器、放缓冲、通知任务”。

### 9.3 中断 + FIFO/环形缓冲区

很多 UART 控制器自带硬件 FIFO，软件也常配一个环形缓冲区。中断触发时一次读出 FIFO 里已有的多个字节，放入环形缓冲区，应用任务再慢慢取。

伪代码：

```c
void UART1_IRQHandler(void)
{
    uint8_t ch;
    bool need_wakeup = false;

    while (uart_rx_ready(UART1)) {
        ch = uart_read_byte(UART1);

        if (!ring_buffer_put(&uart_rx_rb, ch)) {
            uart_rx_overflow_count++;
        }

        need_wakeup = true;
    }

    if (need_wakeup) {
        rtos_event_set_from_isr(uart_event, UART_EVENT_RX);
    }
}

void uart_worker_task(void *arg)
{
    uint8_t buf[64];
    int len;

    while (1) {
        rtos_event_wait(uart_event, UART_EVENT_RX, WAIT_FOREVER);

        do {
            len = ring_buffer_read(&uart_rx_rb, buf, sizeof(buf));
            protocol_parse_buffer(buf, len);
        } while (len > 0);
    }
}
```

优点：

- 比单字节处理更稳，能吸收任务调度延迟。
- 环形缓冲区可以把“硬件接收”和“协议解析”解耦。
- 是 RTOS 中最通用、最容易维护的 UART 接收模型。

缺点：

- 要处理缓冲区满、读写并发和临界区保护。
- 缓冲区大小需要按波特率、任务优先级和最大帧长估算。
- 如果上层长期不读，最终还是会溢出。

适用场景：

- 通用串口驱动。
- 多任务系统中一边接收、一边解析协议。
- 数据有突发，但平均速率不高的场景。

经验：

- 环形缓冲区要比最大协议帧更大。
- 解析任务优先级不能太低。
- 溢出计数要保留，方便定位“偶发丢包”。

### 9.4 DMA 定长接收

DMA 接收是让 DMA 控制器把 UART 收到的数据自动搬到内存，CPU 不需要每个字节都进中断。定长接收适合协议包长度固定的情况。

伪代码：

```c
#define FRAME_LEN 32

uint8_t uart_dma_buf[FRAME_LEN];

void uart_start_dma_rx(void)
{
    uart_dma_receive(UART1, uart_dma_buf, FRAME_LEN);
}

void UART1_DMA_RX_DONE_IRQHandler(void)
{
    rtos_queue_send_from_isr(uart_frame_queue, uart_dma_buf, FRAME_LEN);
    uart_dma_receive(UART1, uart_dma_buf, FRAME_LEN);
}

void uart_protocol_task(void *arg)
{
    uint8_t frame[FRAME_LEN];

    while (1) {
        rtos_queue_recv(uart_frame_queue, frame, WAIT_FOREVER);
        protocol_parse_frame(frame, FRAME_LEN);
    }
}
```

优点：

- CPU 占用低。
- 适合高波特率、大数据量。
- 定长协议处理简单，DMA 满一包再通知任务。

缺点：

- 不适合天然不定长的数据，除非上层协议能保证长度。
- DMA 缓冲区管理比中断方式复杂。
- 如果处理不及时，需要双缓冲或队列，否则下一包可能覆盖上一包。

适用场景：

- 固定长度传感器数据包。
- MCU 与 MCU 之间固定协议帧。
- 高速串口数据采集。

不适合：

- AT 指令这种一行一行、长度不固定的文本协议。
- Shell 输入。
- 不知道何时结束的一段数据。

### 9.5 DMA + 空闲中断接收

在实际项目里，`DMA + UART IDLE 空闲中断` 很常用。DMA 持续把字节搬到缓冲区，当 UART 总线一段时间没有新字节时触发空闲中断，软件认为“一帧数据可能结束了”。

伪代码：

```c
#define RX_DMA_SIZE 256

uint8_t uart_dma_rx_buf[RX_DMA_SIZE];

void uart_rx_start(void)
{
    uart_enable_idle_interrupt(UART1);
    uart_dma_receive_circular(UART1, uart_dma_rx_buf, RX_DMA_SIZE);
}

void UART1_IRQHandler(void)
{
    int recv_len;

    if (uart_idle_interrupt_pending(UART1)) {
        uart_clear_idle_interrupt(UART1);

        recv_len = RX_DMA_SIZE - dma_get_remaining_count(UART1_RX_DMA);

        dma_stop(UART1_RX_DMA);
        rtos_queue_send_from_isr(uart_rx_queue, uart_dma_rx_buf, recv_len);

        dma_set_memory(UART1_RX_DMA, uart_dma_rx_buf, RX_DMA_SIZE);
        dma_start(UART1_RX_DMA);
    }
}

void uart_protocol_task(void *arg)
{
    uart_packet_t pkt;

    while (1) {
        rtos_queue_recv(uart_rx_queue, &pkt, WAIT_FOREVER);
        protocol_parse_buffer(pkt.data, pkt.len);
    }
}
```

优点：

- CPU 占用低，不需要每字节中断。
- 适合不定长帧。
- 对高速连续数据更友好。
- 很适合“收到一段数据后再解析”的协议。

缺点：

- 空闲中断只是“线空闲”，不一定等于完整协议帧。
- DMA 长度、缓存复制、重启时机处理不好会丢数据。
- 缓冲区复用要小心，不能队列里只传指针却马上覆盖原数据。
- 对驱动和硬件特性依赖更强，不同芯片接口不一样。

适用场景：

- 串口屏、蓝牙/Wi-Fi/4G 模块。
- 不定长二进制协议。
- 高波特率日志或数据通道。
- 一帧数据之间有明显间隔的协议。

经验：

- 如果队列里传指针，要用双缓冲或内存池。
- 如果直接复制数据，注意复制耗时和最大帧长。
- 空闲中断只负责切分“数据段”，最终是否是一帧还要靠协议层校验。

### 9.6 驱动阻塞读

一些 RTOS 会把 UART 封装成设备文件或驱动对象，应用任务直接调用 `read`。没有数据时任务阻塞，直到有数据或超时。

伪代码：

```c
void uart_read_task(void *arg)
{
    uint8_t buf[128];
    int len;

    while (1) {
        len = uart_read(UART1, buf, sizeof(buf), WAIT_FOREVER);

        if (len > 0) {
            protocol_parse_buffer(buf, len);
        }
    }
}
```

优点：

- 应用层代码简单。
- 任务无数据时阻塞，不浪费 CPU。
- 适合已有成熟 UART 驱动框架的 RTOS。

缺点：

- 具体行为依赖驱动实现：可能按字节返回，也可能按缓冲区/超时返回。
- 如果不了解驱动内部缓冲策略，容易误判丢包原因。
- 多任务同时读同一个 UART 时需要额外设计。

适用场景：

- RT-Thread、NuttX、Linux-like 接口等设备模型。
- 应用只关心“读到一段数据”，不想直接管理中断和 DMA。
- 串口协议解析任务独占一个 UART。

注意：

- 要弄清 `read` 是阻塞、非阻塞还是超时返回。
- 要弄清返回条件是“有 1 字节就返回”还是“满足长度才返回”。
- 要避免多个任务同时抢读同一个串口。

### 9.7 消息队列/事件通知解耦

在 RTOS 里，UART 接收通常会配合信号量、事件标志、消息队列或 stream buffer。底层负责接收，上层任务负责解析。

伪代码：

```c
void uart_rx_done_callback(uint8_t *data, int len)
{
    uart_msg_t msg;

    msg.data = data;
    msg.len = len;

    rtos_queue_send_from_isr(uart_msg_queue, &msg);
}

void uart_protocol_task(void *arg)
{
    uart_msg_t msg;

    while (1) {
        rtos_queue_recv(uart_msg_queue, &msg, WAIT_FOREVER);
        protocol_parse_buffer(msg.data, msg.len);
        uart_rx_buffer_release(msg.data);
    }
}
```

优点：

- 接收层和协议层解耦。
- 可以把解析放到独立任务中，避免中断里做重活。
- 方便多个模块之间传递“收到一包数据”的事件。

缺点：

- 要设计好数据所有权：谁申请、谁释放、什么时候能复用。
- 队列满时要决定丢新数据、丢旧数据还是阻塞。
- 系统复杂度比单任务轮询高。

适用场景：

- 一个 UART 对接一个协议栈。
- 接收任务、解析任务、业务任务需要分层。
- 数据包需要跨任务传递。

### 9.8 几种方式怎么选

简单选择规则：

| 场景 | 推荐方式 |
| --- | --- |
| 临时调试、数据极少 | 轮询接收 |
| 普通命令行、AT 指令 | 中断 + 环形缓冲区 |
| 通用 RTOS 串口驱动 | 中断 + FIFO/环形缓冲区 + 事件通知 |
| 固定长度高速数据 | DMA 定长接收 |
| 不定长高速数据 | DMA + 空闲中断 |
| 已有设备驱动框架 | 阻塞 `read` 或异步回调 |
| 多任务协议处理 | 队列/事件通知解耦 |

面试时可以这样回答：

> RTOS 中 UART 接收常见有轮询、中断、DMA 和驱动阻塞读几类。低速简单场景可以轮询；普通项目多用中断把字节放进环形缓冲区，再通知任务解析；高速或大数据量场景用 DMA；不定长帧常配合 UART 空闲中断判断一段数据结束。关键是中断或 DMA 只负责快速收数据，协议解析放到任务里做，避免中断里处理太久导致丢数据或影响系统实时性。

## 10. UART 驱动里容易出问题的点

做 UART 调试时，常见问题集中在连线、参数和数据解析。

常见风险：

- **TX/RX 接反**：没有任何数据或只能单向通信。
- **没有共地**：TTL 串口电平参考不一致，通信不稳定。
- **波特率不一致**：乱码最常见原因。
- **数据位/校验位/停止位不一致**：出现乱码、帧错误。
- **电平不匹配**：TTL 误接 RS232，可能损坏芯片。
- **串口号选错**：上位机打开了错误 COM 口。
- **引脚复用错误**：TX/RX 没切到 UART 功能。
- **流控配置不一致**：硬件流控 RTS/CTS 开关不匹配。
- **接收缓冲溢出**：数据来得太快，软件读取不及时。
- **应用层拆包错误**：底层收到字节，但上层解析不对。

## 11. UART 不通怎么排查

排查建议从最简单的串口参数和连线开始。

### 10.1 先确认硬件连接

检查点：

- `TX` 是否接到对方 `RX`。
- `RX` 是否接到对方 `TX`。
- `GND` 是否共地。
- 电平是 3.3V、5V、RS232 还是 RS485。
- USB 转串口工具是否正常。
- 板子供电和复位是否正常。

### 10.2 再确认串口参数

检查点：

- 波特率是否一致。
- 数据位是否一致。
- 校验位是否一致。
- 停止位是否一致。
- 是否误开硬件流控。
- 上位机选择的 COM 口是否正确。

### 10.3 看 TX 是否有波形

如果串口完全没有输出：

- 检查代码是否真的调用了打印或发送接口。
- 检查 UART 控制器时钟是否打开。
- 检查 TX 引脚复用是否正确。
- 检查发送函数是否被阻塞。
- 用示波器或逻辑分析仪看 TX 是否有跳变。

### 10.4 看 RX 是否收到数据

如果能发不能收：

- 检查 RX 线是否接对。
- 检查接收中断是否打开。
- 检查接收 FIFO 是否溢出。
- 检查是否有流控限制。
- 检查应用层协议是否正确拆包。

### 10.5 乱码怎么排查

乱码最常见原因：

- 波特率不一致。
- 数据位、校验位、停止位不一致。
- 时钟误差过大。
- 电平不匹配。
- 线太长或干扰太强。
- GND 没接或接触不良。

直白说法：

> UART 乱码先看波特率和 8N1，再看 TX/RX、共地和电平。大多数问题都藏在这几个地方。

## 12. 面试常见问法和直白回答

### 11.1 UART 是什么

> UART 是一种异步串行通信接口，通常使用 TX 和 RX 两根线收发数据，不需要单独时钟线。双方通过相同波特率和帧格式来保证数据能被正确解析。

### 11.2 UART 为什么不需要时钟线

> UART 是异步通信，双方提前约定波特率。接收方通过起始位判断一帧开始，然后按波特率在固定时间点采样数据位，所以不需要单独时钟线。

### 11.3 TX 和 RX 怎么连接

> 交叉连接。一个设备的 TX 接另一个设备的 RX，一个设备的 RX 接另一个设备的 TX，TTL 串口还要共地。

### 11.4 115200 8N1 是什么意思

> 115200 表示波特率，8 表示 8 个数据位，N 表示无校验，1 表示 1 个停止位。这是最常见的调试串口配置。

### 11.5 UART 乱码一般是什么原因

> 最常见是波特率不一致，其次是数据位、校验位、停止位不一致，也可能是电平不匹配、没有共地、线长干扰或时钟误差过大。

### 11.6 UART 和 RS232/RS485 是什么关系

> UART 是串口通信方式和控制器接口，RS232/RS485 更偏电气层标准。MCU UART 通常是 TTL 电平，要接 RS232 或 RS485 设备时需要对应收发器转换。

### 11.7 UART 收到的是一帧一帧消息吗

> 底层 UART 收到的是连续字节流，不知道应用层消息边界。真正的消息边界要靠协议设计，比如帧头、长度、校验、换行符或超时。

## 13. 高频易错点

| 错误说法 | 更准确的说法 |
| --- | --- |
| UART 只接 TX/RX 就一定能通信 | TTL 串口通常还必须共地，并且电平要匹配 |
| TX 接 TX，RX 接 RX | UART 通常要交叉连接，TX 接对方 RX |
| UART 不需要配置参数 | 双方波特率、数据位、校验位、停止位必须一致 |
| 乱码一定是代码解析错 | 更常见是波特率或帧格式不一致 |
| UART 和 RS232 是一回事 | UART 是通信方式，RS232 是电气层标准 |
| TTL 串口可以直接接 RS232 | 电平不同，通常需要转换芯片 |
| UART 自带消息边界 | UART 只传字节流，消息边界要靠上层协议 |
| 波特率越高越稳定 | 高波特率对线长、时钟和干扰更敏感 |

## 14. 最简记忆版

只想快速记住，可以背下面几句：

- UART 是异步串口，不需要时钟线。
- 常见连接是 `TX -> RX`、`RX <- TX`、`GND -- GND`。
- 双方必须配置相同波特率和帧格式。
- `115200 8N1` 表示 115200 波特率、8 数据位、无校验、1 停止位。
- UART 空闲通常是高电平，起始位是低电平。
- UART 底层传的是字节流，不负责应用层拆包。
- TTL、RS232、RS485 不是同一种电平，不能乱接。
- UART 不通先查 TX/RX、共地、电平、波特率、8N1 和串口号。
