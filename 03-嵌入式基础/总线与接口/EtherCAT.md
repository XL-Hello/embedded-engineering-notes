## 第一章、基础认知与应用场景

本章先建立 EtherCAT 的整体印象，说明工业以太网当前的增长态势，再直接给出“为什么它快”的结论，后面章节再逐层拆开。

### 1.1、核心概念与快速理解

**EtherCAT 本质上是一种运行在标准百兆以太网物理层上的工业实时现场总线：主站发出一帧数据，这帧数据像流水线一样依次穿过所有从站，每个从站在帧“路过”自己的瞬间用硬件读走属于自己的输出、写入自己的输入，帧转一圈回到主站，一个控制周期的全网 I/O 交换就完成了。**

这个“一帧走全网”和传统做法的区别，一张图就能看清：

```text
传统一节点一帧：
   主站 ──请求1──▶ 从站1 ──应答1──▶ 主站
   主站 ──请求2──▶ 从站2 ──应答2──▶ 主站
   主站 ──请求N──▶ 从站N ──应答N──▶ 主站
                          N 个节点 → N 请求 + N 应答 ≈ 2N 帧

EtherCAT：
   主站 ──一帧──▶ 从1 ─▶ 从2 ─▶ 从3 ─▶ … ─▶ 从N ─┐
        ◀──────────── 末端回环原路返回 ───────────┘
                                     N 个节点 → 仍然 1 帧
```

它最典型的特点：

| 维度 | 内容 |
| --- | --- |
| 物理层 | 标准 `100BASE-TX` 全双工以太网，也有 `100BASE-T1`、光纤、EtherCAT P 等变体 |
| 数据链路层 | 标准 Ethernet Frame，专用 EtherType `0x88A4` |
| 主站硬件 | 普通以太网网卡即可，不需要专用板卡 |
| 从站硬件 | 必须使用专用 `ESC`（EtherCAT Slave Controller）做“边转发边处理” |
| 报文用法 | 一帧（或少数几帧）完成所有从站的过程数据交换 |
| 拓扑 | 物理上线型或树型，逻辑上永远是一个环 |
| 同步 | 分布式时钟（DC）对齐全网时间，典型抖动远小于 1 µs |
| 典型周期 | `1 ms`、`500 µs`、`250 µs`、`125 µs`，高性能伺服常用 250 µs 以内 |

常见用途：

| 用途 | 常见场景 |
| --- | --- |
| 运动控制 | 多轴伺服驱动器、CNC、数控机床、电子凸轮 |
| 工业机器人 | 六轴机器人、SCARA、协作机器人关节驱动 |
| 半导体设备 | 晶圆搬运、检测设备的高精度轴控与同步触发 |
| 分布式 I/O | 数字量、模拟量、温度、编码器、称重模块 |
| 包装印刷 | 高速同步、飞剪、追剪、张力控制 |
| 测试测量 | 高速采样、同步触发、数据采集 |
| 新能源 | 电池 PACK 产线、光伏组件设备、充电设备生产线 |
| AGV/AMR | 车载驱动器与传感器的实时总线 |

简单记法：

| 缩写 | 含义 |
| --- | --- |
| `Master` | 主站，跑控制算法，构造并发出 EtherCAT 帧 |
| `Slave` | 从站，I/O 模块、伺服驱动器、传感器等 |
| `ESC` | 从站控制器芯片，真正实现“边转发边处理”的硬件 |
| `Datagram` | EtherCAT 子报文，一帧里可以有多个 |
| `WKC` | Working Counter，确认有多少从站真正处理了这个子报文 |
| `FMMU` | 现场总线内存管理单元，把逻辑地址按位映射到从站物理内存 |
| `SyncManager` | 同步管理器，管理从站内存区的访问与数据一致性 |
| `PDO` | 过程数据对象，周期性交换的实时数据 |
| `SDO` | 服务数据对象，非周期的参数读写 |
| `DC` | 分布式时钟，全网时间同步机制 |
| `CoE` | CANopen over EtherCAT，最常用的应用层协议 |
| `ESI` / `ENI` | 设备描述 XML 文件 / 网络配置文件 |

### 1.2、工业以太网的增长与 EtherCAT 的位置

过去十几年工业通信最明显的趋势，就是**工业以太网持续替代传统现场总线**。

从 HMS Networks 等机构每年发布的工业网络市场份额统计可以看到一个稳定的方向：

| 类别 | 趋势 | 说明 |
| --- | --- | --- |
| 工业以太网 | 持续上升 | 新增节点占比已明显超过传统现场总线 |
| 传统现场总线 | 逐年下降 | PROFIBUS、DeviceNet、CC-Link、Modbus RTU 等 |
| 工业无线 | 占比小、增速快 | 多用于移动设备与数据采集 |
| 以太网内部格局 | 第一梯队稳定 | `EtherNet/IP`、`PROFINET`、`EtherCAT`；EtherCAT 在运动控制细分领域占比尤其高 |

具体百分比各家统计口径不同（有的按新增节点，有的按设备出货量，有的按区域），不必背数字，记住趋势和原因即可。

驱动这个增长的原因：

| 驱动因素 | 具体表现 |
| --- | --- |
| 设备软件化 | 控制器需要曲线、日志、参数、诊断、视觉等更大数据量 |
| 网络统一 | 从 I/O 到机器人再到上位系统希望用一张网，以太网天然承载 IP |
| 老总线带宽不足 | 传统现场总线只有几百 kbps ~ 几 Mbps，线缆与工具链还各家不通用 |
| 成本被摊薄 | 以太网芯片、线缆、连接器、测试工具受益于消费电子与 IT 行业规模 |
| 数据要上行 | 智能制造、数字孪生要求数据一路送到 MES/云端 |

EtherCAT 在这一波里的定位很清楚：

> 工业以太网解决“带宽和统一网络”的问题，EtherCAT 在此基础上重点解决“硬实时和多轴同步”的问题。

也就是说，选 EtherCAT 通常不是因为需要大带宽（主流版本只有百兆），而是因为需要：

- 周期短，而且**周期抖动极小**。
- 几十上百个轴要在**同一时刻**采样和执行。
- 网络规模变大时，**周期时间不能跟着线性劣化**。

### 1.3、EtherCAT 为什么可以做到高实时性

这是全篇最核心的问题，先给结论，第二、三、四章再逐条展开。

| # | 机制 | 做法 | 消除的延时来源 |
| --- | --- | --- | --- |
| 1 | 一帧走全网 | 所有从站的数据拼进同一帧的不同区段，帧数与节点数无关 | 逐节点的收发、协议栈处理、交换机转发 |
| 2 | 边转发边处理 | ESC 在比特流经过时就地读写，不等整帧收完 | 存储转发延时（随帧长线性增长） |
| 3 | 从站软件不在实时路径 | 过程数据的总线侧搬运由 ESC 的 DPRAM 和 SyncManager 全硬件完成，从站 CPU 不参与协议处理 | 从站侧协议栈开销与软件抖动 |
| 4 | 分布式时钟解耦同步 | 所有从站按同一全网时间产生 SYNC0，统一时刻动作 | 传播延时差与主站发送抖动对同步的影响 |

补充说明：

- 第 1 点的效果是**网络上的帧数和节点数基本无关**，100 个从站与 10 个从站的帧数一样。
- 第 2 点使**单从站延时固定在百纳秒量级**，几十个从站级联的往返累计通常在十几到几十微秒，具体量级见 3.3。
- 第 3 点意味着从站 MCU 不介入协议栈处理：纯 I/O 从站可以完全不参与，伺服从站虽然每周期都要响应 SYNC0，但触发时刻由硬件决定而非由帧到达决定，因此不会引入通信侧的软件抖动。
- 第 4 点让“数据什么时候到”不再决定“动作什么时候发生”，同步精度不受通信抖动限制。

一句话概括：

> EtherCAT 快，不是因为它的物理层比别人快，而是因为它把“软件协议栈处理”和“逐节点存储转发”这两个最大的延时来源从实时路径上去掉了，再用分布式时钟把剩下的传播延时补偿掉。

一组常被引用的性能量级（来自 ETG 的典型宣传数据，实际值取决于配置）：

| 场景 | 典型周期 |
| --- | --- |
| 1000 路分布式数字量 I/O | 约 30 µs |
| 100 个伺服轴，每轴 8 字节输入输出 | 约 100 µs |
| 200 路模拟量 I/O（16 bit） | 约 50 µs |

这些数字的意义不在于精确，而在于说明一件事：**EtherCAT 的周期时间主要由数据总量决定，而不是由节点数量决定。**

## 第二章、从普通 Ethernet 到 EtherCAT

本章说明标准以太网在实时控制里到底卡在哪，EtherCAT 做了哪些改动，以及改动之后帧格式和拓扑长什么样。

### 2.1、普通以太网在实时控制中的问题

标准以太网本身是很好的网络技术，但它的设计目标是 Best Effort 的通用数据传输，直接拿来做 125 µs 周期的多轴同步会遇到几个硬伤。

一次普通 UDP 通信要走的完整路径：

```text
应用 → socket → UDP → IP → MAC → DMA → PHY → 线缆
  → 交换机（存储转发）
  → PHY → MAC → DMA → 中断 → 协议栈 → 应用
   ▲                                        ▲
   └────── 每一层都有拷贝、查表、中断、调度 ──┘
```

对应的五个硬伤：

| # | 问题 | 原因 | 量级 / 后果 |
| --- | --- | --- | --- |
| 1 | 软件协议栈开销大 | 每层都有拷贝、查表、中断、调度 | 单次往返几十 µs 起，且抖动大 |
| 2 | 交换机存储转发 | 收完整帧、校验 FCS、查 MAC 表再转发 | 1500 字节帧仅串行化就约 120 µs，多级叠加 |
| 3 | 最小帧开销太大 | 以太网最小帧 64 字节，而伺服每周期只需 8~32 字节 | 带宽大部分浪费在帧头、FCS、帧间隙和填充 |
| 4 | 帧数随节点线性增长 | 每节点一收一发 | 100 节点 = 200 帧，见下方计算 |
| 5 | 没有共同时间基准 | 各节点晶振有偏差和漂移 | 多轴采样与执行时刻无法对齐 |

第 4 点的具体计算：

```text
100 个节点 × （1 收 + 1 发）            = 200 帧
百兆最小帧（含前导码与帧间隙）约 6.72 µs
                200 × 6.72 µs ≈ 1.3 ms  ← 仅线上时间
再叠加协议栈与交换机开销 ⇒ 1 ms 周期根本做不到
```

### 2.2、EtherCAT 的改法

EtherCAT 保留了以太网的物理层和帧格式，但把“怎么用这帧”彻底改了。

| 普通以太网的做法 | EtherCAT 的做法 |
| --- | --- |
| 一个报文对应一个节点 | 一帧包含所有节点的数据，各占一段 |
| 节点收完整帧再处理 | 从站硬件在帧流过时就地读写（on the fly） |
| 交换机存储转发 | 从站自带端口转发逻辑，构成逻辑环，无需交换机 |
| 通信靠软件协议栈 | 周期数据路径全硬件，从站 CPU 不参与 |
| 靠 IP/端口寻址 | 靠位置地址、站地址、广播地址、逻辑地址寻址 |
| 时间同步靠软件参与的 PTP | 分布式时钟由 ESC 硬件实现 |
| 半双工/全双工均可 | 必须 100 Mbit/s 全双工，不做降速协商 |

关键的思路转变是：

> 不要把网络看成“多个点对点连接”，而要把整个网络看成**一块共享的分布式内存**，主站每个周期用一帧对这块内存做一次读写。

这也是 EtherCAT 常被说成“以太网形态的现场总线”的原因：它在布线上像网络，在使用方式上更像一条把所有从站内存串起来的总线。

### 2.3、EtherCAT 帧格式

#### 2.3.1、帧与子报文结构

EtherCAT 数据直接封装在标准 Ethernet Frame 里，EtherType 为 `0x88A4`：

```text
┌──────────┬──────────┬───────────┬──────────────┬───────────────┬───────┐
│ Dest MAC │ Src MAC  │ EtherType │ EtherCAT     │ Datagram 1..n │  FCS  │
│  6 Byte  │  6 Byte  │  0x88A4   │ Header 2Byte │  44~1498 Byte │ 4Byte │
└──────────┴──────────┴───────────┴──────────────┴───────────────┴───────┘
                                   │
       ┌───────────────────────────┴───────────────────────────┐
       │ Length 11 bit │ Reserved 1 bit │ Type 4 bit（0x01）    │
       └───────────────────────────────────────────────────────┘

每个 Datagram（子报文）：
┌─────┬─────┬──────────┬─────────┬──────┬────────┬──────┐
│ Cmd │ Idx │ Address  │ Len/R/  │ IRQ  │  Data  │ WKC  │
│ 1B  │ 1B  │   4B     │ C/M  2B │  2B  │  0..n  │  2B  │
└─────┴─────┴──────────┴─────────┴──────┴────────┴──────┘
```

字段含义：

| 字段 | 说明 |
| --- | --- |
| `Cmd` | 命令类型，决定寻址方式和读写方向，例如 LRW、FPRD、APWR |
| `Idx` | 主站用来匹配收发的索引，从站不修改 |
| `Address` | 位置/站地址寻址时拆为 ADP(2B) + ADO(2B)，逻辑寻址时是完整的 32 位逻辑地址 |
| `Len` | 数据长度，11 bit |
| `R` | 保留位，3 bit |
| `C` | Circulating Frame，用于检测帧在环里打转 |
| `M`（More） | 后面是否还有下一个 Datagram |
| `IRQ` | 从站汇总的中断请求信息 |
| `Data` | 实际读写的数据 |
| `WKC` | Working Counter，每个成功处理的从站按规则递增 |

几个约束：

| 约束 | 说明 |
| --- | --- |
| 数据区上限 | 一帧最多约 1498 字节 EtherCAT 数据，超过要拆成多帧 |
| 最小帧 | 数据太少时仍要补齐到以太网最小帧 64 字节 |
| UDP 封装 | 可封装在 UDP（目的端口 `34980`）用于跨网段非实时访问，实时控制基本都用二层直封 |

#### 2.3.2、带宽利用率对比

以“50 个从站各 8 字节输入 + 8 字节输出，共 800 字节过程数据”为例，线上字节统一按含前导码与帧间隙（最小帧即 84 字节）计算：

| 方案 | 帧数 | 线上总字节 | 有效数据 | 利用率 |
| --- | --- | --- | --- | --- |
| EtherCAT 一帧覆盖全网 | 1 | 约 852（800 + MAC 头 14 + ECAT 头 2 + 子报文头 10 + WKC 2 + FCS 4 + 前导码与帧间隙 20） | 800 | 约 94% |
| 一节点一帧（最小帧，一收一发） | 100 | 8400 | 800 | 约 9.5% |

注意这里用 50 个从站而不是 100 个，是因为一帧的 EtherCAT 数据区上限约 1498 字节，1600 字节过程数据就必须拆成两帧了。

### 2.4、拓扑：物理上是线，逻辑上是环

每个 EtherCAT 从站至少有两个端口（很多有 3~4 个），ESC 内部按固定顺序在端口之间转发：

```text
去程（每个从站边转发边处理数据）：

  主站网口 ──▶ P0[ Slave1 ]P1 ──▶ P0[ Slave2 ]P1 ──▶ P0[ Slave3 ]P1
                                                                └ 未接线
                                                                  → 端口闭合
                                                                  → 帧内部回环

回程（同样逐级经过，只转发不再处理）：

  主站网口 ◀── P0[ Slave1 ]P1 ◀── P0[ Slave2 ]P1 ◀── P0[ Slave3 ]
```

每个从站左侧是 Port 0（去程入口、回程出口），右侧是 Port 1（去程出口、回程入口）。两个方向走同一根线缆的不同线对（全双工），因此去程和回程互不影响。

工作方式：

1. 主站从网口发出帧，进入 Slave1 的 Port 0。
2. 帧依次向下游传递，每个从站在转发的同时处理数据。
3. 最后一个从站发现自己的下游端口没有连接（Link 关闭），把帧从内部回环送回。
4. 帧沿原路返回，**返回途中从站不再处理过程数据**，只做转发。
5. 回程帧从 Slave1 的 Port 1 进入，再由 Port 0 送回主站网口。

几个关键理解：

| 现象 | 原因 / 影响 |
| --- | --- |
| 去程回程不冲突 | 全双工，两个方向走同一根线缆的不同线对 |
| 拓扑即插即用 | 端口未插线自动闭合（close），插线后打开（open），硬件不需要配置“我是最后一个” |
| 接线顺序就是逻辑顺序 | 物理可为线型/树型/星型，但逻辑永远是环，顺序错了地址全乱 |
| 线缆冗余 | 主站用两个网口接环的首尾，任一处断线两个方向仍可覆盖全网，切换由端口硬件完成，通常不丢周期 |

### 2.5、与普通以太网的差异对比

| 对比项 | 普通交换式 Ethernet | EtherCAT |
| --- | --- | --- |
| 物理层 | 100BASE-TX / 1000BASE-T 等 | 通常 100BASE-TX 全双工，也有 T1、光纤、EtherCAT P |
| 帧格式 | 标准 Ethernet Frame | 标准 Ethernet Frame，EtherType 0x88A4 |
| 报文与节点关系 | 一般一个报文对应一个目的节点 | 一帧覆盖全网所有节点 |
| 转发方式 | 交换机存储转发 | 从站硬件直通处理（on the fly） |
| 单跳延时 | 微秒到几十微秒 | 典型 100~500 ns 量级 |
| 是否需要交换机 | 需要 | 不需要，普通交换机反而会破坏实时性 |
| 寻址 | MAC / IP / Port | 位置地址 / 站地址 / 广播地址 / 逻辑地址 |
| 主站硬件 | 普通网卡 | 普通网卡即可 |
| 从站硬件 | 普通 MAC+PHY | 必须专用 ESC |
| 实时性 | Best Effort，可用 TSN 增强 | 硬实时，配合 DC 抖动可到亚微秒级 |
| 时间同步 | IEEE 1588 PTP，软件参与较多 | 分布式时钟，ESC 硬件实现 |
| 典型周期 | 毫秒级以上，抖动大 | 125 µs ~ 1 ms，抖动小 |

需要特别强调的一点：

> **EtherCAT 网络中不能随便插入普通以太网交换机。** 交换机的存储转发会破坏“边转发边处理”的时序前提，也会让分布式时钟的传播延时测量失效。需要分支时应使用 EtherCAT 的分支从站或端口扩展模块。

反过来，非实时的 IP 流量可以通过 `EoE`（Ethernet over EtherCAT）隧道封装在邮箱报文里传输，例如给驱动器的网页配置界面用，但它走的是非周期通道，不占用实时预算。

## 第三章、主从结构与“边转发边处理”

本章是 EtherCAT 的技术核心：主站和从站各自负责什么，ESC 在帧经过时到底做了什么，以及寻址、FMMU、SyncManager、WKC 和状态机这些必须理解的机制。

### 3.1、主从结构总览

EtherCAT 是严格的单主站结构：

```text
┌──────────────────────────────────────────┐
│ Master（PC / 工控机 / 嵌入式控制器）      │
│  ├ 应用：PLC 程序、运动控制、机器人算法   │
│  ├ 主站协议栈：PDO 映射、状态机、DC 管理  │
│  ├ 网卡驱动：通常是实时化的专用驱动        │
│  └ 标准以太网 MAC + PHY                   │
└──────────────────┬───────────────────────┘
                   │ 100BASE-TX 全双工（无冗余时一个网口接首个从站；
                   │ 启用线缆冗余时用两个网口接环的首尾，见 2.4）
                   ▼
   ┌──────────┐  ┌──────────┐       ┌──────────┐
   │ Slave 1  │─▶│ Slave 2  │─ … ──▶│ Slave n  │
   │ ESC+MCU  │  │ ESC 纯IO │       │ ESC+伺服 │
   └──────────┘  └──────────┘       └──────────┘
        ▲                                 │
        └────── 回程逐级返回主站 ◀─────────┘
```

职责划分：

| 阶段 | 主站职责 | 从站职责 |
| --- | --- | --- |
| 启动前 | 扫描网络，识别从站类型与顺序 | ESC 上电完成自初始化，打开已连接端口 |
| 配置 | 读取 EEPROM（SII）与 ESI 文件生成网络配置；配置 FMMU、SyncManager、PDO 映射 | 接受寄存器写入，按配置准备内存区 |
| 启动 | 驱动状态机 `Init → Pre-Op → Safe-Op → Op` | 维护自己的状态机，拒绝切换时写 AL Status Code |
| 周期运行 | 每周期构造并发送过程数据帧，检查返回的 WKC | ESC 在帧经过时完成寻址匹配与数据读写，把过程数据映射到本地 I/O 或应用 |
| 同步 | 管理分布式时钟：延时测量、偏移补偿、漂移补偿 | 按 SYNC0/SYNC1 中断执行同步动作 |
| 非周期 | 处理邮箱通信（SDO 读写、诊断、固件升级） | 响应邮箱请求（参数读写、诊断） |
| 异常 | 处理错误、超时、拓扑变化和冗余切换 | 上报错误码，看门狗超时时回落到安全状态 |

一个很重要的不对称性：

> 主站完全是软件实现（普通网卡 + 协议栈），从站必须有专用硬件（ESC）。这正好和“性能瓶颈在哪”对应——实时处理的重活由从站硬件扛，主站只要能准时把帧发出去就行。

### 3.2、从站控制器 ESC

ESC 是 EtherCAT 的关键芯片，常见实现形态：

| 形态 | 例子 | 特点 |
| --- | --- | --- |
| 专用 ASIC | Beckhoff ET1100 / ET1200 | 端口多、功能全、延时最小 |
| 带 MCU 接口的 ASIC | Microchip LAN9252 | 集成 2 路 PHY，SPI/并口接 MCU，开发简单 |
| FPGA IP Core | Beckhoff ET1810/ET1815、各家 IP | 可与运动控制逻辑集成在同一片 FPGA |
| SoC 内置 | 部分工业 MCU/SoC 集成 ESC | 成本与集成度好 |

ESC 内部主要模块：

```text
      Port 0        Port 1        Port 2/3
        │             │              │
   ┌────▼─────────────▼──────────────▼────┐
   │        自动转发单元 / 环路控制          │
   ├───────────────────────────────────────┤
   │  EtherCAT 处理单元（地址匹配、读写）    │
   ├──────────┬──────────┬─────────────────┤
   │  FMMU    │ SyncMgr  │  分布式时钟 DC   │
   ├──────────┴──────────┴─────────────────┤
   │  DPRAM（过程数据区 1K~8KB 常见）        │
   ├───────────────────────────────────────┤
   │ PDI：数字 I/O / SPI / 并口 / 片上总线   │
   └───────────────────────────────────────┘
                   │
              从站 MCU / FPGA / I/O 电路
```

| 模块 | 说明 |
| --- | --- |
| `DPRAM` | 从站的寄存器与数据空间，前 4KB 是标准寄存器区（`0x0000~0x0FFF`），之后是用户过程数据区。过程数据 RAM 容量随芯片不同，常见 1KB~8KB（如 ET1200 约 1KB、LAN9252 约 4KB、ET1100 约 8KB），64KB 是 ESC 的地址空间上限而非实际容量 |
| `PDI` | Process Data Interface，面向从站应用侧的接口；简单 I/O 可直接用数字 I/O 模式而不需要 MCU，复杂设备用 SPI 或并口接 MCU |
| 端口数量 | 决定拓扑能力：2 端口只能作为线型链路中的一个串接节点，3~4 端口才能作为分支节点引出支线 |

### 3.3、帧经过从站时到底发生了什么

这是最该讲清楚的一段。可以把 ESC 想成一个**带旁路读写能力的极短流水线**。

以最常用的 `LRW`（逻辑读写）子报文为例，帧从 Port 0 进入从站：

```text
时间轴 ───────────────────────────────────────────────▶

线上比特流：  [MAC头][ECAT头][Datagram1 ... 本从站数据段 ... ][Datagram2]...[FCS]
                                 ▲              ▲
                                 │              │
                          地址匹配命中      同一时刻：
                                           · 把该段数据读进 DPRAM（输出）
                                           · 把 DPRAM 数据写进该段（输入）
                                           · 重新计算并更新 WKC
                                 │
出端口比特流： ───────────────────┴────────────── 延时约 100~500 ns ──▶
```

具体步骤：

| 步骤 | ESC 动作 |
| --- | --- |
| 1 | **接收与转发同时开始**：不等整帧收完，比特进来几个字节（对应约 100~500 ns 的固定流水线延时）后就开始往下游端口输出 |
| 2 | **解析 Datagram 头**：读到 `Cmd` 和 `Address` 后立即判断是否与自己相关、对应本地哪块内存 |
| 3a | 命中的**输出数据**（主站→从站）：把流过的数据复制进 DPRAM，同时原样转发给下游 |
| 3b | 命中的**输入数据**（从站→主站）：把 DPRAM 内容替换进正在转发的比特流 |
| 3c | `LRW` 在同一段上同时做 3a 和 3b：读走输出，填回输入 |
| 4 | **更新 WKC**：处理成功后把子报文末尾的 Working Counter 加上对应值 |
| 5 | **重算 FCS**：帧内容被改动，转发时重新计算并写入 FCS |
| 6 | **继续向下游**：剩余比特继续流过，下一个从站重复同样过程 |

需要建立的几个直觉：

| 直觉 | 说明 |
| --- | --- |
| 没有“收完再发” | 从站内部延时固定在几百纳秒，与帧长无关；存储转发则随帧长线性增长 |
| 修改的是“正在飞过的帧” | 同一帧传播时可能有多个从站正在处理它的不同部分，这就是 processing on the fly |
| 返程不处理数据 | 末端回环后原路返回，只转发不改数据，一个周期内每段数据只被处理一次 |
| 从站 CPU 全程没参与 | MCU 在自己方便时从 DPRAM 取数据，与帧时序解耦（解耦方式由 SyncManager 和 DC 决定） |

单从站转发延时的典型量级：

| 环节 | 典型值 |
| --- | --- |
| ESC 处理延时（每个方向） | 约 100 ~ 500 ns，取决于芯片与端口配置 |
| PHY 收发延时 | 每个方向几十到一百多 ns |
| 100 m 铜缆传播延时 | 约 500 ns（约 5 ns/m） |

按这个量级估算：100 个从站级联，单向纯硬件转发累计约几十微秒，往返则是数十到上百微秒。所以 125 µs 这样的周期通常对应几十个从站的规模；上百个从站时要按芯片手册的实测单站延时逐项核算，并给主站处理留出时间。

### 3.4、寻址方式

EtherCAT 的寻址分为**设备寻址**（位置、站地址、广播）和**逻辑寻址**两大类，下面按使用阶段分别说明。

#### 3.4.1、位置寻址（Auto Increment）

命令：`APRD` / `APWR` / `APRW`。

地址字段里放一个**负数**，每个从站**无论是否命中都把该地址值加 1 后转发**；其中**收到的地址值为 0** 的那个从站处理这个子报文并递增 WKC：

```text
主站发出 Position = -3
  Slave1 收到 -3 → 不是 0，不响应 → 加 1 → -2
  Slave2 收到 -2 → 不是 0，不响应 → 加 1 → -1
  Slave3 收到 -1 → 不是 0，不响应 → 加 1 →  0（转发给下游）
  Slave4 收到  0 → 命中，响应  → 加 1 →  1（继续转发，下游不再命中）
```

用途：网络扫描阶段，主站还不知道从站是谁，只能按“第几个”访问。这也是 **接线顺序不能错** 的直接原因。

#### 3.4.2、站地址寻址（Configured Station Address）

命令：`FPRD` / `FPWR` / `FPRW`。

主站在初始化时用位置寻址给每个从站写入一个固定的 16 位站地址，之后就按这个地址访问，与物理位置解耦。

用途：初始化阶段的寄存器配置、邮箱通信、状态机切换。

#### 3.4.3、广播寻址（Broadcast）

命令：`BRD` / `BWR` / `BRW`。

不指定具体从站，所有从站都处理同一个子报文：写操作每个从站都执行，读操作各从站按位“或”方式合并结果。

用途：读全网 AL Status、统一清零错误计数器、分布式时钟的时间戳锁存（见 4.3）。因为返回的 WKC 等于参与处理的从站数，`BRD` 也常被主站用来确认在线从站数量。

#### 3.4.4、逻辑寻址（Logical Addressing）

命令：`LRD` / `LWR` / `LRW`。

地址是一个 32 位的全局逻辑地址空间（4 GB），每个从站通过 FMMU 声明“逻辑地址的这一段对应我本地内存的哪一段”。**这是周期性过程数据交换的核心机制**，因为它让主站可以用一个子报文覆盖多个从站：

```text
主站的过程数据映像（逻辑地址空间）：
┌──────────┬──────────┬──────────┬──────────┐
│ 0x1000   │ 0x1008   │ 0x1010   │ 0x1018   │
│ 轴1 数据 │ 轴2 数据 │ 轴3 数据 │ IO 模块  │
└────┬─────┴────┬─────┴────┬─────┴────┬─────┘
     │FMMU      │FMMU      │FMMU      │FMMU
     ▼          ▼          ▼          ▼
  Slave1     Slave2     Slave3     Slave4
  DPRAM      DPRAM      DPRAM      DPRAM

一条 LRW 子报文：地址 0x1000，长度 0x20
→ 四个从站各取各的那一段
```

主站应用侧看到的就是一块连续内存：写某个偏移就是给某个轴发指令，读某个偏移就是读某个轴的反馈。这也是为什么 EtherCAT 常被描述成“把整个网络当成一块共享内存”。

#### 3.4.5、命令汇总

| 命令 | 全称 | 寻址 | 典型用途 |
| --- | --- | --- | --- |
| `APRD/APWR/APRW` | Auto Increment Read/Write | 位置 | 网络扫描、初始配置 |
| `FPRD/FPWR/FPRW` | Configured Address Read/Write | 站地址 | 寄存器配置、状态机、邮箱 |
| `BRD/BWR/BRW` | Broadcast Read/Write | 广播 | 同时读写所有从站，如读状态、清零 |
| `LRD/LWR/LRW` | Logical Read/Write | 逻辑 | 周期性过程数据 |
| `ARMW/FRMW` | (Auto Inc / Configured) Read Multiple Write | 位置/站地址 | 分布式时钟漂移补偿 |

### 3.5、FMMU 与 SyncManager

这两个是从站配置里最容易搞混的东西，分工其实很清楚：

| 模块 | 解决什么 | 一句话 |
| --- | --- | --- |
| `FMMU` | 逻辑地址 ↔ 物理内存的换算 | 管地址映射 |
| `SyncManager` | 主站与从站应用同时访问同一块内存的冲突 | 管数据一致性 |

#### 3.5.1、FMMU

| 项 | 说明 |
| --- | --- |
| 条目内容 | 逻辑起始地址、长度（可精确到位）、物理起始地址、方向（读/写） |
| 位级映射 | 8 个分散的单比特数字量输入可被打包进逻辑映像的同一字节，不浪费带宽 |
| 数量 | 随 ESC 型号不同，常见 3~8 个（ET1200、LAN9252 为 3 个，ET1100 为 8 个），配置前须查芯片手册 |

#### 3.5.2、SyncManager

两种工作模式：

| 模式 | 用途 | 机制 |
| --- | --- | --- |
| Buffered Mode（3 缓冲） | 周期性过程数据 | 硬件维护三个缓冲区，写方和读方永远操作不同缓冲，双方都不会阻塞，读到的永远是完整一致的数据 |
| Mailbox Mode（握手） | 非周期邮箱通信 | 单缓冲 + 握手，写入后必须被读走才能再写，保证不丢报文 |

三缓冲模式是过程数据能“无锁、无阻塞、无撕裂”的关键：主站随时可以写新的输出，从站随时可以读最新的完整输出，不需要互相等待。

一个典型从站的 SyncManager 分配：

| SM | 方向 | 模式 | 内容 |
| --- | --- | --- | --- |
| SM0 | 主站 → 从站 | Mailbox | 邮箱输出（SDO 请求等） |
| SM1 | 从站 → 主站 | Mailbox | 邮箱输入（SDO 响应等） |
| SM2 | 主站 → 从站 | Buffered | 过程数据输出（如目标位置） |
| SM3 | 从站 → 主站 | Buffered | 过程数据输入（如实际位置） |

SyncManager 还带**看门狗**：超过设定时间没有收到过程数据更新，从站会认为主站掉线，自动从 `Op` 退回 `Safe-Op` 并把输出置于安全状态。现场常见的“驱动器突然掉到 Safe-Op”，多半就是这个看门狗触发了。

### 3.6、Working Counter：怎么知道数据真的到了

每个子报文末尾有 16 位 WKC，主站发出时置 0，从站每成功处理一次就按规则递增：

| 操作 | WKC 增量 |
| --- | --- |
| 读成功 | +1 |
| 写成功 | +1 |
| 读写（RW）命令：仅读操作成功 | +1 |
| 读写（RW）命令：仅写操作成功 | +2 |
| 读写（RW）命令：读写均成功 | +3 |

主站在配置阶段就能算出**期望的 WKC**，每周期收帧后对比：

| 观察到的 WKC | 含义 |
| --- | --- |
| 等于期望值 | 所有从站都正常处理了这个子报文 |
| 小于期望值 | 有从站掉线、没进 Op，或 SyncManager 未就绪 |
| 不稳定 | 通常是链路质量问题或某个从站间歇性故障 |

所以 **WKC 是主站每个周期最重要的健康指标**，比“帧有没有回来”更细致：帧回来了但 WKC 少了 3，就能定位到某个特定的从站没参与。

### 3.7、从站状态机（ESM）

每个从站都维护一个状态机，主站通过写 `AL Control` 寄存器请求切换，读 `AL Status` 确认结果：

```text
        ┌────────┐
        │  Init  │  只能做寄存器访问，无邮箱、无过程数据
        └───┬────┘
            │ 配置邮箱 SyncManager（SM0/SM1）
        ┌───▼────┐
        │ Pre-Op │  邮箱可用（SDO 读写参数），无过程数据
        └───┬────┘
            │ 配置过程数据 SM2/SM3、FMMU、DC
        ┌───▼─────┐
        │ Safe-Op │  过程数据输入有效，输出保持安全值
        └───┬─────┘
            │ 主站开始发送有效的输出过程数据
        ┌───▼────┐
        │   Op   │  输入输出全部有效，正常运行
        └────────┘

        另有 Bootstrap 状态，仅用于 FoE 固件升级
```

调试时的关键经验：

| 卡住的位置 | 常见原因 |
| --- | --- |
| Init → Pre-Op 失败 | 邮箱 SyncManager 配置错误，或 ESI/SII 与实际设备不符 |
| Pre-Op → Safe-Op 失败 | PDO 映射长度与 SM 配置对不上（最常见） |
| Safe-Op → Op 失败 | 主站没有按周期发过程数据，或 DC 还没同步上 |
| Op 掉回 Safe-Op | SyncManager 看门狗超时，通常是主站周期抖动过大或丢帧 |

从站在拒绝切换时会把原因写进 `AL Status Code`：

| 常见码 | 含义 |
| --- | --- |
| `0x0011` | 无效的状态切换请求（Invalid requested state change） |
| `0x0016` | 邮箱配置无效（Invalid mailbox configuration，Pre-Op） |
| `0x0017` | 同步管理器配置无效（Invalid sync manager configuration） |
| `0x001A` | 同步错误（Synchronization Error） |
| `0x001B` | 同步管理器看门狗超时 |
| `0x001D` / `0x001E` | 无效的输出 / 输入配置 |
| `0x0030` | DC SYNC 配置无效（Invalid DC SYNC Configuration） |
| `0x0032` | DC PLL 未锁定（PLL Error） |

**遇到状态切换失败先读这个码**，能省掉大量猜测。

### 3.8、邮箱协议：CoE、SoE、FoE、EoE

过程数据走的是周期通道，参数、诊断、固件这类非周期数据走邮箱通道。常见邮箱协议：

| 协议 | 全称 | 用途 |
| --- | --- | --- |
| `CoE` | CANopen over EtherCAT | 最常用。复用 CANopen 对象字典、SDO/PDO 机制，伺服驱动器普遍使用 CiA 402 规约 |
| `SoE` | Servo Drive Profile over EtherCAT | 基于 SERCOS 驱动规约（IEC 61800-7-204），部分驱动器使用 |
| `FoE` | File over EtherCAT | 文件传输，主要用于固件升级（配合 Bootstrap 状态） |
| `EoE` | Ethernet over EtherCAT | 隧道传输标准以太网帧，让从站的网页界面、TCP/IP 工具可用 |
| `AoE` | ADS over EtherCAT | Beckhoff 的 ADS 路由协议 |
| `VoE` | Vendor specific over EtherCAT | 厂商自定义 |

实际项目里最需要理解的是 **CoE**：

| 概念 | 说明 |
| --- | --- |
| 对象字典 | 设备参数用 `Index`（16 bit）+ `SubIndex`（8 bit）访问，如 `0x6040:00` 控制字、`0x6041:00` 状态字、`0x607A:00` 目标位置 |
| SDO | 走邮箱，非周期，用于读写参数（加减速度、限位、模式选择等） |
| PDO | 走过程数据，周期性，用于实时数据（控制字、目标位置、实际位置） |
| PDO 映射 | 把对象字典条目绑定到 SM2/SM3 的过程数据区，映射表本身也是对象字典条目（`0x1600`/`0x1A00` 系列） |

一句话区分：

> SDO 是“慢速、按需、带确认的参数通道”，PDO 是“高速、周期、无确认的过程数据通道”。参数用 SDO 配，运行时数据用 PDO 传。

## 第四章、分布式时钟（Distributed Clocks）

本章解决第三章遗留的问题：即便通信再快，帧到达每个从站的时刻也不可能相同，那怎么让上百个轴在同一时刻动作？

### 4.1、为什么需要分布式时钟

设想一条 100 个伺服轴的线，帧从第 1 个轴流到第 100 个轴需要几十微秒。如果每个从站都“收到数据就执行”：

```text
无 DC：谁先收到谁先动
  轴1 ──┐
  轴2 ──┼─ 错开几十 µs，且随拓扑与主站抖动变化
  ...   │
  轴100 ┘                       ⇒ 插补轨迹产生轮廓误差

有 DC：所有轴按同一系统时间在同一时刻动作
  轴1 ────┐
  轴2 ────┼─ 同一 SYNC0 时刻触发
  ...     │
  轴100 ──┘                     ⇒ 通信抖动与执行时刻解耦
```

对于插补运动、龙门同步、飞剪、多轴协调轨迹，这种偏差会直接变成轮廓误差。分布式时钟要做的事就是：

> 让每个从站都有一个**与全网一致的 64 位系统时间**，然后所有从站按这个时间在**同一个绝对时刻**产生同步中断去执行动作，而不是“谁先收到谁先动”。

### 4.2、时间基准

| 项 | 说明 |
| --- | --- |
| 系统时间 | 64 位、单位 1 ns，起点为 2000-01-01 00:00 |
| 参考时钟 | 网络里第一个支持 DC 的从站的本地时钟，通常就是 Slave 1 |
| 主站角色 | 自身时钟不作为基准（PC 时钟抖动太大），只负责测量和补偿 |
| 从站维护 | 本地时钟、系统时间偏移、传播延时、漂移补偿 |

三个要补偿的量：

| 要补偿的量 | 原因 |
| --- | --- |
| 传播延时（Propagation Delay） | 帧到达各从站的时刻不同 |
| 时间偏移（Offset） | 各从站本地时钟上电时的初值不同 |
| 时钟漂移（Drift） | 各从站晶振频率有偏差，时间会越走越散 |

### 4.3、传播延时测量

ESC 的每个端口都有各自的**接收时间戳寄存器**（`0x0900` / `0x0904` / `0x0908` / `0x090C` 对应 Port 0~3）：当一个特定的广播帧经过该端口时，硬件把当时的本地时间锁存下来。对链路中间的从站，去程和回程进入的是**不同端口**，所以能同时拿到两个方向的时间戳；末端从站因为下游端口闭合、帧在内部回环，只有去程端口有时间戳。

主站发一帧广播写（`BWR` 到时间戳锁存寄存器），每个从站在每个端口上记录该帧经过的时刻，之后主站把这些时间戳读回来算出各段线缆的往返时间：

```text
主站 ──▶ Slave1 ──▶ Slave2 ──▶ Slave3（末端回环）
          ▲ t0/t3    ▲ t1/t2

Slave1：Port0 收到时间 t0（去程），Port1 收到时间 t3（回程）
Slave2：Port0 收到时间 t1（去程），Port1 收到时间 t2（回程）

Slave1 → Slave2 的单向延时 ≈ [(t3 - t0) - (t2 - t1)] / 2
```

原理和 PTP 的往返测量是一样的，但因为时间戳是 **ESC 硬件在 PHY 边界打的**，没有任何软件参与，所以精度非常高。主站把每个从站的传播延时写进它的 `System Time Delay` 寄存器，从站计算系统时间时自动加上这个偏移量。

### 4.4、偏移与漂移补偿

| 补偿项 | 时机 | 做法 |
| --- | --- | --- |
| 偏移补偿 | 一次性 | 主站读取参考时钟和各从站本地时间，算出差值写入各从站 `System Time Offset` 寄存器，使系统时间读数对齐 |
| 漂移补偿 | 持续进行 | 主站周期性发 `ARMW`/`FRMW`：从参考时钟从站读取系统时间并写入后面所有从站；从站比较后通过内部时间控制环路（数字 PLL）微调本地时钟走速，而不是硬跳变 |

补偿帧通常每个周期都发，或按一定频率发。经过这套机制，典型系统的从站间同步抖动可以做到 **远小于 1 µs，良好设计下可到几十纳秒量级**。

### 4.5、SYNC0 / SYNC1 与从站侧的同步执行

时间对齐只是手段，真正起作用的是 ESC 产生的同步信号：

| 信号 | 作用 |
| --- | --- |
| `SYNC0` / `SYNC1` | ESC 按系统时间在设定周期和相位上产生的硬件脉冲，作为从站 MCU 的中断源 |
| `LATCH0` / `LATCH1` | 外部信号触发时硬件锁存当时的系统时间，用于高精度事件打时间戳（探针、编码器锁存） |

一个伺服从站的典型 DC 时序：

```text
系统时间 ──────────────────────────────────────────────▶

  ┌ 主站发帧（时刻有抖动）
  │      ┌ 帧到达本从站（因位置不同而不同）
  │      │                    ┌ SYNC0 触发（全网同一时刻！）
  ▼      ▼                    ▼
──┼──────┼────────────────────┼───────────────▶
         │                    │
         │  数据已进 DPRAM     │  中断里：
         │  等待               │  · 锁存编码器实际位置
         │                     │  · 取目标位置，更新电流环指令
         │                     │  · 把反馈写回 DPRAM
         └── 裕量（由 SYNC0 Shift Time 设定）┘
```

要点：

| 要点 | 说明 |
| --- | --- |
| 帧到达可以有抖动 | 只要在 SYNC0 之前到达即可；这段裕量由 SYNC0 的相位设置（SYNC0 Shift Time，即 SYNC0 相对 DC 周期起点的偏移）决定，把 SYNC0 后移就能保证帧总是先到 |
| 执行时刻严格一致 | 所有从站的 SYNC0 按同一系统时间产生 |
| 输入是同一时刻快照 | 输入数据在 SYNC0 时刻统一锁存，不是先后采样的拼凑值 |

从站侧的三种同步模式（由 ESI 声明、主站配置）：

| 模式 | 说明 | 适用 |
| --- | --- | --- |
| Free Run | 从站自己按本地定时器跑，与总线无关 | 简单 I/O |
| SM Sync（SM2/SM3 事件同步） | 从站在收到过程数据时触发处理 | 一般 I/O、低要求设备 |
| DC Sync（SYNC0/SYNC1 同步） | 从站按分布式时钟中断处理 | 伺服、多轴同步、高精度采集 |

此外，高性能主站通常还会做 **主站周期对齐到 DC**：主站用返回帧里的 DC 时间反过来微调自己发送周期的相位，让“发帧时刻”稳定地落在 SYNC0 之前的固定位置。TwinCAT 的 DC 时基、IgH 主站的 `dc_sync` 都是这个思路。

## 第五章、伺服驱动与机器人应用

本章把前面的机制落到最典型的应用场景：多轴伺服和工业机器人。

### 5.1、CiA 402 驱动规约

伺服驱动器上的 EtherCAT 几乎都是 **CoE + CiA 402**（对应 IEC 61800-7-201/301）。

#### 5.1.1、核心对象与驱动状态机

| 对象 | 名称 | 说明 |
| --- | --- | --- |
| `0x6040` | Controlword | 控制字，驱动状态机切换 |
| `0x6041` | Statusword | 状态字，反馈驱动状态 |
| `0x6060` | Modes of operation | 运行模式设定 |
| `0x6061` | Modes of operation display | 当前实际模式 |
| `0x6064` | Position actual value | 实际位置 |
| `0x606C` | Velocity actual value | 实际速度 |
| `0x6077` | Torque actual value | 实际转矩 |
| `0x607A` | Target position | 目标位置 |
| `0x60FF` | Target velocity | 目标速度 |
| `0x6071` | Target torque | 目标转矩 |

驱动状态机（CiA 402 State Machine）：

```text
Not ready to switch on
        ↓
Switch on disabled
        ↓ Controlword = 0x06
Ready to switch on
        ↓ Controlword = 0x07
Switched on
        ↓ Controlword = 0x0F
Operation enabled  ← 真正使能，可以跟随指令
        ↓ 故障时
      Fault → Controlword = 0x80 复位
```

调试伺服时最常见的流程就是：主站每周期检查 Statusword，按状态机一步步把 Controlword 从 `0x06` 推到 `0x0F`，然后开始下发目标位置。

#### 5.1.2、循环同步模式与 PDO 映射

运动控制中真正常用的三种模式：

| 模式 | 代码 | 主站每周期下发 | 说明 |
| --- | --- | --- | --- |
| CSP（Cyclic Synchronous Position） | 8 | 目标位置 | 最常用，主站做插补，驱动器做位置环 |
| CSV（Cyclic Synchronous Velocity） | 9 | 目标速度 | 主站做位置环，驱动器做速度环 |
| CST（Cyclic Synchronous Torque） | 10 | 目标转矩 | 主站做位置和速度环，力控、柔顺控制常用 |

这三种模式的共同点是：**主站每个通信周期下发一个新指令，驱动器在 SYNC0 时刻取用**。所以周期抖动会直接变成指令抖动，进而变成速度波动和振动——这就是为什么运动控制对抖动比对延时更敏感。

典型 PDO 映射：

| 方向 | 内容 | 字节 |
| --- | --- | --- |
| RxPDO（主站→驱动器） | Controlword(2) + Target Position(4) + Mode(1) | 7~8 |
| TxPDO（驱动器→主站） | Statusword(2) + Position Actual(4) + Mode Display(1) | 7~8 |

需要力矩前馈、多编码器、探针功能时再往上加，一般一个轴 16~32 字节以内。

### 5.2、周期时间与带宽预算

估算是否能跑某个周期，做法很直接。以 **6 轴机器人 + 一些 I/O** 为例，每轴 RxPDO 12 字节、TxPDO 16 字节：

```text
过程数据总量 = 6 × (12 + 16) = 168 字节
加上 I/O 模块           ≈  32 字节
EtherCAT 数据区         ≈ 200 字节
加帧头/子报文头/WKC/FCS ≈ 232 字节
百兆线上时间（只发一次） ≈ 232 × 8 / 100 Mbit/s ≈ 18.6 µs
加上前导码与帧间隙       ≈ 20 µs   ← 线路真正被占用的时间
环路往返转发延时         ≈ 10 个从站 × 1 µs（含 PHY，往返）≈ 10 µs
────────────────────────────────────
主站发出到收回           ≈ 30 µs
```

注意帧只被发送一次，回程是同一帧继续在环上传播，不需要再叠加一遍串行化时间；而且全双工下去程和回程用不同线对，回程也不额外占用发送方向。

对于 250 µs 或 500 µs 周期，帧的往返时间只占周期的约 12% 和 6%，其中线路真正被占用的只有 20 µs，即 8% 和 4%，余量充足。真正的瓶颈往往不在总线，而在：

| 瓶颈 | 说明 |
| --- | --- |
| 主站算法计算时间 | 尤其是机器人运动学、动力学 |
| 主站调度抖动 | 操作系统的实时性 |
| 网卡驱动 | 收发延时与抖动 |

经验上的周期选择：

| 应用 | 常用周期 |
| --- | --- |
| 普通 I/O、温控、PLC 逻辑 | 1 ~ 4 ms |
| 一般伺服定位 | 1 ms |
| 机器人、CNC 插补 | 500 µs / 250 µs |
| 高动态、力控、高精度设备 | 250 µs / 125 µs |

### 5.3、机器人为什么特别需要 DC

六轴机器人做一条直线轨迹时，主站每个周期为 6 个关节各算一个目标位置，这 6 个位置是**同一个时刻的笛卡尔位姿**解算出来的。

| 场景 | 无 DC | 有 DC |
| --- | --- | --- |
| 指令执行时刻 | 6 个关节先后错开几十 µs | 同一 SYNC0 时刻取用目标位置 |
| 反馈采样 | 各关节先后采样，位姿是拼凑的 | 同一时刻锁存编码器，得到一致快照 |
| 末端轨迹 | 偏离直线，产生轮廓误差，随速度放大 | 轮廓误差不再受通信时序影响 |
| 误差可标定性 | 随拓扑和网络负载变化，难标定 | 与拓扑无关 |
| 外部事件 | 视觉触发、探针无统一时基 | LATCH 打上同一时间基准的时间戳，便于视觉引导与运动补偿 |

一个直观的判断标准：

> 如果同步误差要求小于 1 µs，或者多个轴必须协调运动，基本就只能上 DC；只有独立动作的单轴或纯 I/O，才可以用 SM Sync 甚至 Free Run。

### 5.4、功能安全：FSoE

机器人和自动化设备普遍需要安全功能（急停、安全门、STO、安全限速）。EtherCAT 的方案是 **FSoE（Safety over EtherCAT）**：

| 特性 | 说明 |
| --- | --- |
| 共线传输 | 安全数据作为普通过程数据的一部分在同一根线上传输，不需要单独的安全总线 |
| 黑色通道 | 底层通信不需要安全认证，安全性由 FSoE 自身的序列号、CRC、连接 ID、超时机制保证 |
| 认证等级 | 符合 IEC 61508，可用于 SIL 3 应用，相关规范见 IEC 61784-3 |
| 典型架构 | 安全 PLC 作为 FSoE Master，安全 I/O 和带 STO 的驱动器作为 FSoE Slave |

对普通开发者来说，要记住的就是：安全数据和普通过程数据共线但逻辑独立，普通主站只负责把这段字节原样转发，不解析也不需要解析。

### 5.5、EtherCAT 的扩展形态

| 名称 | 说明 |
| --- | --- |
| `EtherCAT P` | 在同一根四芯线上同时传输数据和 2×24 V 电源，减少接线，适合传感器和紧凑设备 |
| `EtherCAT G / G10` | 1 Gbit/s 与 10 Gbit/s 版本，通过分支控制器把高速主干与百兆分支结合，用于视觉、大数据量场景 |
| `EtherCAT over 100BASE-T1` | 单对双绞线物理层，面向线束受限的场合 |
| `Safety over EtherCAT` | 见 5.4 |
| `EtherCAT + TSN` | 用 TSN 网络把多个 EtherCAT 网段跨厂区连接，EtherCAT 段内部机制不变 |

需要说明的是，EtherCAT 主流应用仍以百兆为主，因为它的瓶颈通常是周期和抖动而不是带宽；G/G10 更多用于要传图像或大数据块的场合。

## 第六章、总线对比与主站开发要点

本章横向比较常见工业总线，并给出主站侧实现时真正会踩坑的地方。

### 6.1、与常见工业总线对比

| 对比项 | CANopen | Modbus TCP | PROFINET IRT | EtherCAT |
| --- | --- | --- | --- | --- |
| 物理层 | CAN 差分总线 | 标准以太网 | 标准以太网 | 标准以太网（100BASE-TX） |
| 速率 | ≤ 1 Mbit/s | 100 M / 1 G | 100 M / 1 G | 100 M（G 版本更高） |
| 典型周期 | 1 ~ 10 ms | 10 ms 以上 | 250 µs ~ 1 ms | 125 µs ~ 1 ms |
| 报文与节点 | 一节点一报文 | 一连接一请求响应 | 预留时隙调度 | 一帧覆盖全网 |
| 需要专用硬件 | 从站 CAN 控制器 | 不需要 | 主从都需专用 ASIC/交换机 | 仅从站需 ESC |
| 交换机 | 无 | 标准交换机 | 需支持 IRT 的专用交换机 | 不需要 |
| 同步机制 | SYNC 报文，精度有限 | 无 | IRT 调度 + PTP | 分布式时钟，硬件时间戳 |
| 同步精度 | 几十 ~ 几百 µs | — | 约 1 µs | 远小于 1 µs |
| 拓扑 | 总线 | 星型 | 线型/星型 | 线型/树型（逻辑环） |
| 主站成本 | 需 CAN 卡 | 普通网卡 | 需专用硬件 | 普通网卡 |

直白理解：

> CANopen 便宜但慢；Modbus TCP 简单通用但不实时；PROFINET IRT 实时性好但主从两端都要专用硬件、组网成本高；EtherCAT 把复杂度集中在从站芯片上，换来了主站零成本和最好的周期/同步指标。

其他值得知道的同类协议：

| 协议 | 说明 |
| --- | --- |
| `POWERLINK` | 基于标准以太网的开源实时协议，用时隙轮询机制，不需要专用从站芯片，但周期通常不如 EtherCAT |
| `SERCOS III` | 运动控制出身，实时性好，主要在特定厂商生态中使用 |
| `CC-Link IE TSN` | 三菱主导，基于千兆与 TSN |
| `EtherNet/IP + CIP Sync/CIP Motion` | 罗克韦尔生态，工业以太网份额很大，实时性依赖 CIP Motion 与 TSN |

### 6.2、主站选型

| 主站 | 特点 | 适用 |
| --- | --- | --- |
| `TwinCAT`（Beckhoff） | 功能最完整，工具链成熟，含运动控制与安全 | 商用设备、需要完整 PLC 功能 |
| `IgH EtherCAT Master` | Linux 内核态开源主站，性能好，需要打补丁的内核与网卡驱动 | Linux 平台产品化 |
| `SOEM`（Simple Open EtherCAT Master） | 轻量用户态开源库，代码量小、易移植、无内核依赖 | 学习、嵌入式、快速验证 |
| `Acontis EC-Master` | 商用协议栈，跨平台、支持多种 RTOS | 需要商业支持的嵌入式项目 |
| `CODESYS` | 软 PLC 生态自带 EtherCAT 主站 | PLC 风格开发 |

学习路径上的建议：从 `SOEM` 入手最快——它的代码规模适合完整读一遍，能把扫描、PDO 映射、状态机、DC 配置这几件事看明白；产品化再考虑 IgH 或商用栈。

### 6.3、主站实时性保障

主站是整个系统里**唯一的软件抖动来源**，所以这部分最花功夫。

#### 6.3.1、操作系统层面

| 措施 | 目的 |
| --- | --- |
| `PREEMPT_RT` 实时补丁，或 Xenomai/RTAI 双内核 | 获得可预期的调度延时 |
| 隔离 CPU 核（`isolcpus`、`nohz_full`、`rcu_nocbs`） | 周期线程独占核，不被其他任务干扰 |
| 关闭该核的中断负载均衡，网卡中断绑到同核或相邻核 | 避免中断迁移带来的抖动 |
| 关闭 CPU 频率调节与深度 C-State，BIOS 关掉 SMI 省电与管理功能 | 消除唤醒延时与不可见的 SMI 停顿 |
| 线程用 `SCHED_FIFO` 高优先级，`mlockall` 锁内存 | 避免被抢占和缺页 |

#### 6.3.2、网卡与驱动层面

| 措施 | 目的 |
| --- | --- |
| 优先用有实时驱动支持的网卡（Intel i210/i225、i350 等） | 有成熟的实时收发路径 |
| 关闭网卡中断合并（Interrupt Coalescing，`ethtool -C` 置 0） | 避免收包被人为延后 |
| 关闭各种 Offload | 避免不确定的硬件处理路径 |
| 实时主站常直接用轮询方式收发 | 绕开 NAPI 与中断路径，进一步压低抖动 |
| 有条件时用专用网口，不与普通 IP 流量混用 | 避免非实时流量干扰 |

#### 6.3.3、周期结构

```text
周期开始（定时器唤醒）
  ├ 接收上一周期返回的帧
  ├ 检查 WKC 与从站状态
  ├ 从过程数据映像读取输入
  ├ 运行控制算法
  ├ 写过程数据映像
  ├ 发送本周期的帧（含 DC 补偿帧）
  └ 等待下一个周期
```

注意两点：

| 原则 | 说明 |
| --- | --- |
| 先收后算再发 | 不要在一个周期里等待帧返回，那会把往返延时直接加进周期 |
| 周期线程里不做阻塞操作 | 不打印日志、不申请内存、不加可能等待的锁、不做文件 I/O；诊断信息通过无锁队列丢给低优先级线程 |

衡量指标是**周期抖动**：用高精度时间戳记录每次唤醒的时刻差，好的系统应该能把最大抖动控制在几十微秒以内（对应 1 ms 周期），高性能配置可以做到几微秒。

## 第七章、常见故障与分层排查

本章按“从物理层往上”的顺序整理现场最常见的问题。

### 7.1、常见故障点

#### 7.1.1、扫描不到从站或数量不对

| 可能原因 | 说明 |
| --- | --- |
| 从站未上电 | ESC 逻辑电源与 I/O 电源分开供电时只上了一路 |
| 网线接错端口 | 从站端口有固定的进出顺序（通常 IN 是 Port 0），接反会导致拓扑识别异常 |
| 线序不匹配 | 多数 ESC 支持 Auto-MDIX，但并非全部 |
| 中间插了普通交换机 | 帧被存储转发甚至丢弃 |
| ESC 未完成初始化 | 端口没有打开 |

#### 7.1.2、从站顺序与配置不符

EtherCAT 的初始扫描依赖**位置寻址**，所以接线顺序就是逻辑顺序。换了两个模块的位置，主站按 ENI 配置去写站地址时就会张冠李戴。

| 项 | 内容 |
| --- | --- |
| 表现 | 某个从站一直进不了 Op，或数据对不上号 |
| 排查 | 用主站工具看实际扫描出的拓扑和设备名，与配置文件逐个比对 |

#### 7.1.3、ESI / SII 不匹配

从站 EEPROM 里的 SII 描述了设备的基本能力（邮箱配置、SM 默认值、厂商 ID、产品码、版本号）。主站会用 ESI 文件里的配置去初始化设备，两者版本不一致时：

| 项 | 内容 |
| --- | --- |
| 表现 | `Pre-Op → Safe-Op` 切换失败；PDO 映射长度对不上；主站报 unexpected product code / revision |
| 处理 | 找厂商要与固件版本匹配的 ESI 文件；调试阶段可在主站里允许忽略版本号 |

#### 7.1.4、PDO 映射长度不一致

这是**最高频**的问题。从站实际的 SM2/SM3 长度与主站配置的过程数据长度不一致，从站会拒绝进入 Safe-Op。

| 项 | 内容 |
| --- | --- |
| 常见 AL Status Code | `0x001D`（无效的输出配置）、`0x001E`（无效的输入配置） |
| 排查 | 把主站配置的 RxPDO/TxPDO 逐条与设备手册默认映射比对；注意有的驱动器需要先用 SDO 写入映射表（动态 PDO 映射）才生效 |

#### 7.1.5、WKC 不正确

| 现象 | 常见原因 |
| --- | --- |
| 一直小于期望值 | 有从站没进 Op，或 FMMU 配置错误使其不响应逻辑地址 |
| 偶发变化 | 链路质量问题，先查 CRC 错误计数器 |
| 为 0 | 帧压根没被处理，检查帧是否真的发出去、网口是否选对 |

#### 7.1.6、CRC 错误与丢帧

每个 ESC 的每个端口都有一组错误计数器（`0x0300` 起的 RX Error Counter、Forwarded RX Error Counter、Lost Link Counter 等），主站工具通常能读出来并显示成表。

定位方法很实用：

> 沿着拓扑看错误计数器，**错误开始累加的那个端口的上游链路**就是问题所在。

| 常见原因 | 说明 |
| --- | --- |
| 线缆质量差或超长 | 超出 100 m 或用了非工业级线缆 |
| 接头氧化、松动 | 振动环境尤其常见 |
| 强干扰 | 变频器、电机线附近走线 |
| 屏蔽层没接好 | 接地不良 |
| 拖链线缆疲劳 | 长期弯折导致断裂 |

#### 7.1.7、DC 同步不上

| 项 | 内容 |
| --- | --- |
| 表现 | 从站卡在 Safe-Op，AL Status Code `0x0030`（DC SYNC 配置无效）、`0x0032`（DC PLL 未锁定） |
| 原因一 | 主站没有做延时测量或漂移补偿，或补偿帧发送周期不对 |
| 原因二 | 主站周期抖动太大，从站的 DC PLL 锁不住 |
| 原因三 | SYNC0 周期与主站通信周期不匹配（通常要求成整数倍关系） |
| 原因四 | 参考时钟选错：主站指定的参考时钟从站与实际第一个支持 DC 的从站不一致，或该从站被断开、未进入 Op |
| 原因五 | 链路中存在不支持 DC 的从站：主站若误按支持 DC 给它下发 SYNC0 配置会报 `0x0030`；若它位于网络最前端，参考时钟会落到它后面的第一个 DC 从站上，主站须以该从站为基准重新计算各站传播延时。位于链路中间的非 DC 从站，其转发延时在两个方向上对称，会被并入相邻链路段的测量结果，一般不影响下游从站的延时补偿 |

补充一点：只有当主站把参考时钟指定成**并非最靠前的那个 DC 从站**时，位于参考时钟上游的 DC 从站才会出现负的传播延时，需要主站单独处理。

#### 7.1.8、运行中掉到 Safe-Op

几乎都是 **SyncManager 看门狗超时**（AL Status Code `0x001B`）：主站在看门狗时间内没有更新过程数据。

| 进一步原因 | 排查方式 |
| --- | --- |
| 主站周期线程被抢占（日志、GC、非实时线程、系统中断） | 先看主站自己的周期抖动统计 |
| 网卡驱动偶发延时 | 看收发时间戳分布 |
| 网络丢帧 | 看各端口链路错误计数器 |

### 7.2、分层排查流程

```text
1. 电源与链路：从站是否上电？各端口 Link 灯是否正常？
        ↓
2. 拓扑扫描：主站能否扫描到全部从站？数量与顺序对不对？
        ↓
3. 从站身份：厂商 ID、产品码、Revision 是否与 ESI 匹配？
        ↓
4. 状态机：能否从 Init 走到 Pre-Op / Safe-Op / Op？卡在哪一步？
        ↓
5. AL Status Code：读出具体错误码，对照规范定位原因
        ↓
6. 过程数据：WKC 是否等于期望值？PDO 内容是否符合预期？
        ↓
7. 分布式时钟：DC 是否锁定？各从站系统时间差是多少？
        ↓
8. 链路质量：各端口 CRC / Lost Link 计数器是否在增长？
        ↓
9. 主站实时性：周期抖动统计如何？有没有丢周期？
        ↓
10. 应用层：CiA 402 状态机、控制字/状态字、运行模式是否正确？
```

一个通用原则和排查以太网一样：

> **不要跳层。** 状态机还进不了 Op 就不要研究为什么位置指令不跟随；CRC 计数器在涨就不要先怀疑算法。

### 7.3、调试工具

| 工具 | 用途 |
| --- | --- |
| 主站自带工具（TwinCAT System Manager、`ethercat` 命令行等） | 扫描拓扑、读写 SDO、看状态机、读错误计数器 |
| Wireshark（带 EtherCAT 解析器） | 抓帧分析子报文、WKC、命令类型 |
| ESC 寄存器读取 | 直接看 SM、FMMU、DC、错误计数器等原始寄存器 |
| 网络分接器（TAP） | 在不破坏时序的前提下旁路抓包 |
| 示波器 / 逻辑分析仪 | 观察 SYNC0 脉冲的实际相位与抖动，验证同步精度 |

其中“用示波器看多个从站的 SYNC0 是否对齐”是验证 DC 是否真正工作的最直接方法。

## 第八章、面试复习与速查

本章集中整理面试问答、常见误区和最简记忆要点，便于完成系统学习后快速复盘。

### 8.1、面试常见问法和直白回答

**1. EtherCAT 是什么**

> EtherCAT 是一种基于标准以太网物理层的工业实时现场总线，由 Beckhoff 提出、ETG 维护，已纳入 IEC 61158/61784。它的核心特征是主站发出一帧数据穿过所有从站，从站硬件在帧经过时就地读写属于自己的数据段，一帧完成全网 I/O 交换，配合分布式时钟实现亚微秒级同步。

**2. EtherCAT 为什么快**

> 主要有四点：一是一帧覆盖全网，帧数与节点数无关；二是从站用 ESC 硬件边转发边处理，单跳延时只有几百纳秒，不做存储转发；三是从站软件不参与周期数据路径，没有协议栈开销和软件抖动；四是用分布式时钟把执行时刻与数据到达时刻解耦，同步精度不受通信抖动影响。

**3. 什么是“processing on the fly”**

> 指从站 ESC 在以太网帧的比特流经过时同步完成处理：一边把帧往下游端口转发，一边根据子报文的地址判断是否与自己相关，命中就把输出数据复制进本地 DPRAM、把本地输入数据替换进帧中，同时更新 Working Counter 并重算 FCS。整个过程不等整帧接收完成，因此延时固定在几百纳秒量级。

**4. EtherCAT 和普通以太网最大的区别**

> 物理层和帧格式都是标准以太网，区别在使用方式：普通以太网是一个报文对应一个节点、交换机存储转发、靠软件协议栈处理；EtherCAT 是一帧覆盖所有节点、从站硬件直通处理、不用交换机，寻址也换成了位置地址、站地址、广播地址和逻辑地址。

**5. EtherCAT 的拓扑是什么样的**

> 物理上通常是线型或树型，逻辑上永远是一个环。每个从站至少两个端口，端口没插线时自动闭合，最后一个从站把帧回环送回，返程只转发不处理。因为是全双工，去程和回程共用同一根线缆。主站用两个网口接环的首尾就能实现线缆冗余。

**6. 主站需要专用硬件吗**

> 不需要。主站用普通以太网网卡加软件协议栈就能实现，复杂度集中在主站软件的实时性上。从站则必须使用专用的 ESC 芯片，因为“边转发边处理”只能由硬件完成。

**7. FMMU 和 SyncManager 有什么区别**

> FMMU 负责地址映射，把 32 位全局逻辑地址按位映射到从站本地物理内存，使主站可以用一条 LRW 子报文同时访问多个从站。SyncManager 负责数据一致性和访问协调：过程数据用三缓冲模式保证读写双方都不阻塞且数据完整，邮箱数据用握手模式保证不丢报文，并提供看门狗监控。

**8. Working Counter 有什么用**

> WKC 是子报文末尾的 16 位计数器，主站发出时置 0，每个成功处理该子报文的从站按规则递增。主站在配置阶段就知道期望值，每周期收帧后比对即可判断是否所有从站都正常参与。WKC 少了多少、少在哪个子报文，能直接定位到具体从站，是主站最重要的周期健康指标。

**9. 分布式时钟怎么工作**

> 以第一个支持 DC 的从站的本地时钟为参考时钟，系统时间是 64 位纳秒计数。主站先发广播帧，各从站 ESC 在端口硬件上锁存帧经过的时间戳，主站据此算出每段链路的传播延时并写回从站；再测量并写入各从站的时间偏移；运行中用 ARMW/FRMW 命令周期性把参考时钟的时间广播给其他从站，从站通过内部 PLL 微调本地时钟走速来补偿漂移。对齐之后，各从站按系统时间在同一时刻产生 SYNC0 中断执行动作。

**10. 为什么有了 DC，通信抖动就不影响同步了**

> 因为动作不再由“数据到达”触发，而是由“SYNC0 到达”触发。只要帧在 SYNC0 之前到达从站即可，中间那段裕量吸收了通信抖动。所有从站的 SYNC0 都按同一个全网系统时间产生，所以执行时刻严格一致，同步精度只取决于时钟同步精度而非通信精度。

**11. PDO 和 SDO 的区别**

> PDO 是过程数据对象，走周期性过程数据通道，用于实时数据如控制字、目标位置、实际位置，无确认、延时确定。SDO 是服务数据对象，走邮箱通道，非周期、带确认，用于参数读写和诊断。PDO 映射本身是通过 SDO 配置的。

**12. 从站状态机有哪几个状态**

> Init、Pre-Op、Safe-Op、Op，另有专用于固件升级的 Bootstrap。Init 只能做寄存器访问；Pre-Op 邮箱可用，可以配参数；Safe-Op 输入有效、输出保持安全值；Op 输入输出全部有效。切换失败时从站会写 AL Status Code 说明原因，排查时应该先读这个码。

**13. 伺服驱动器上跑的是什么协议**

> 通常是 CoE（CANopen over EtherCAT）加 CiA 402 驱动规约。参数按对象字典组织，用 Index/SubIndex 访问；运行时通过 PDO 周期交换控制字 0x6040、状态字 0x6041、目标位置 0x607A、实际位置 0x6064 等。运动控制常用循环同步位置 CSP、循环同步速度 CSV、循环同步转矩 CST 三种模式。

**14. EtherCAT 网络里能不能加普通交换机**

> 不能。普通交换机做存储转发，会破坏“边转发边处理”的时序前提，也会让分布式时钟的传播延时测量失效。需要分支时应使用 EtherCAT 的分支从站或端口扩展模块。非实时的 IP 流量可以用 EoE 隧道承载。

**15. 从站运行中突然掉到 Safe-Op，怎么查**

> 最常见原因是 SyncManager 看门狗超时，即主站在规定时间内没有更新过程数据。先看 AL Status Code 确认（0x001B 是看门狗超时），然后从两个方向查：一是主站周期线程的抖动统计和有没有丢周期，二是各端口的 CRC 与 Lost Link 错误计数器是否在增长以定位链路问题。

**16. 主站怎么保证实时性**

> 用 PREEMPT_RT 或双内核方案，隔离 CPU 核并绑定周期线程，用 SCHED_FIFO 高优先级并 mlockall 锁内存，关闭频率调节与深度省电，网卡关掉中断合并与各种 offload。周期结构上先收帧、再算、最后发帧，不在周期内等待帧返回，周期线程里不做任何可能阻塞的操作。

### 8.2、高频易错点

| 错误说法 | 更准确的说法 |
| --- | --- |
| EtherCAT 是一种新的物理层 | 物理层就是标准以太网，改的是帧的使用方式 |
| EtherCAT 需要专用主站板卡 | 主站用普通网卡即可，从站才必须用 ESC |
| 从站收到整帧后再处理 | 从站在比特流经过时就地处理，不做存储转发 |
| 每个从站收到自己的一帧 | 一帧覆盖全网，各从站处理帧中属于自己的数据段 |
| 帧在返程时也会被处理 | 返程只转发，过程数据在去程被处理一次 |
| EtherCAT 拓扑是星型，需要交换机 | 逻辑上是环，从站自带转发，不需要也不应该用普通交换机 |
| 从站顺序无所谓 | 位置寻址依赖物理顺序，接线顺序就是逻辑顺序 |
| DC 就是 IEEE 1588 PTP | 原理相近但实现不同，DC 由 ESC 硬件完成，精度更高且与过程数据帧合一 |
| 主站时钟是参考时钟 | 参考时钟是第一个支持 DC 的从站，主站只做测量和补偿 |
| 同步靠“数据一到就执行” | 靠 SYNC0 在统一系统时间触发，与数据到达时刻解耦 |
| PDO 和 SDO 是两种总线 | 是同一网络上的两个通道：周期过程数据与非周期邮箱 |
| WKC 是校验和 | WKC 是处理计数，用来确认有多少从站真正处理了子报文 |
| FMMU 和 SyncManager 是一回事 | FMMU 管地址映射，SyncManager 管一致性与握手 |
| 带宽不够就换千兆 | EtherCAT 的瓶颈通常是周期和抖动，不是带宽 |
| Link 灯亮就说明通信正常 | Link 只说明物理链路建立，还要看状态机和 WKC |
| CiA 402 是 EtherCAT 专有的 | 它来自 CANopen，EtherCAT 通过 CoE 复用它 |
| 周期设得越短越好 | 周期要与主站算力、抖动和数据量匹配，过短反而丢周期 |

### 8.3、最简记忆版

只想快速记住，可以背下面几句：

- EtherCAT 用标准以太网物理层和帧格式，EtherType 是 `0x88A4`，通常跑 100 Mbit/s 全双工。
- 核心机制是**一帧走全网**：主站发一帧，帧穿过所有从站，回来就完成一次全网 I/O 交换。
- 从站必须用 `ESC` 芯片，**边转发边处理**，单跳延时约 100~500 ns，不做存储转发。
- 主站只要一块普通网卡，复杂度在主站软件的实时性上。
- 物理上是线型/树型，逻辑上是环；端口没插线自动闭合，末端从站回环，返程只转发不处理。
- 四种寻址：位置寻址用于扫描，站地址寻址用于配置和邮箱，广播寻址用于全网状态读取与 DC 时间戳锁存，逻辑寻址（LRW + FMMU）用于周期过程数据。
- `FMMU` 做逻辑地址到物理内存的位级映射，`SyncManager` 用三缓冲保证过程数据一致、用握手保证邮箱不丢。
- `WKC` 是每周期的健康指标：等于期望值说明所有从站都参与了。
- 状态机是 `Init → Pre-Op → Safe-Op → Op`，切换失败先读 `AL Status Code`。
- `PDO` 走周期通道传实时数据，`SDO` 走邮箱通道配参数；伺服普遍用 `CoE` + `CiA 402`。
- 分布式时钟以第一个 DC 从站为参考，补偿传播延时、初始偏移和时钟漂移，同步抖动可远小于 1 µs。
- 同步真正起作用的是 `SYNC0`：全网同一时刻触发，动作时刻与数据到达时刻解耦。
- 伺服常用 `CSP`/`CSV`/`CST` 三种循环同步模式，周期抖动会直接变成运动抖动。
- 网络里**不能插普通交换机**，需要分支用 EtherCAT 分支从站。
- 排查顺序按 `上电 → Link → 拓扑扫描 → 设备身份 → 状态机 → AL Status Code → WKC → DC → CRC 计数器 → 主站抖动 → 应用层` 分层定位。
- 工业以太网整体份额在持续上升，EtherCAT 的优势领域是运动控制这类对周期和同步要求最苛刻的场景。
