# RTOS 常用任务、任务间通信与同步机制

## 1. RTOS 中的任务和进程

### 1.1 本文讨论范围

本文只讨论 FreeRTOS、RT-Thread 这类面向 MCU 的 RTOS，重点是任务、任务间通信、同步以及多核 RTOS 中的核间通信。

Linux、NuttX、Zephyr 等具有更完整进程/用户态模型或独立机制体系的系统不在本文展开；遇到进程、文件、Socket、设备模型等类 Linux 内容，可单独参考 Linux 相关笔记。

### 1.2 任务和进程的区别

在 MCU 型 RTOS 中，通常以 **Task（任务）** 作为调度和运行的基本单位，而不是 Linux 中具有独立虚拟地址空间的 Process（进程）。多个任务一般运行在同一个地址空间内，共享全局变量、外设和堆内存。

| 对比项 | RTOS 任务 | Linux 进程 |
| --- | --- | --- |
| 调度单位 | 任务/线程 | 进程或线程 |
| 地址空间 | 通常共享 | 进程之间隔离 |
| 创建开销 | 较小 | 较大 |
| 通信方式 | 队列、信号量、事件、邮箱等 | 管道、消息队列、共享内存、Socket 等 |
| 典型问题 | 栈溢出、优先级反转、竞态 | 进程隔离、IPC、上下文切换 |

因此，本文中“进程间通信”更多是沿用习惯说法，实际主要指 **任务间通信（Task-to-Task Communication）**。

### 1.3 一个任务通常包含什么

一个任务通常由以下几部分组成：

- 任务入口函数：任务启动后循环执行的函数。
- 任务栈：保存局部变量、函数调用现场和上下文切换信息。
- 任务控制块：保存优先级、状态、栈指针、调度相关信息。
- 优先级和状态：决定任务何时获得 CPU。
- 周期或阻塞条件：通过延时、队列、信号量、事件等让出 CPU。

```c
static void sensor_task(void *argument)
{
    for (;;) {
        sensor_sample();
        queue_send(sample_queue, &sample, WAIT_FOREVER);
        task_delay(MS_TO_TICKS(10));
    }
}
```

### 1.4 任务状态和调度

任务状态决定任务是否具备运行条件，以及何时能获得 CPU。FreeRTOS 的基本状态是 **Running、Ready、Blocked、Suspended**；删除任务后还会进入 Deleted 状态，等待内核回收动态资源。

| 状态 | 含义 | 常见进入/退出条件 |
| --- | --- | --- |
| Running（运行） | 当前正在某个 CPU 核上执行 | 被调度器选中；被抢占、阻塞、挂起或让出 CPU 后离开 |
| Ready（就绪） | 已具备运行条件，等待 CPU | 创建、等待超时或收到事件后进入；被调度器选中后运行 |
| Blocked（阻塞） | 正在等待时间或内核对象，不参与竞争 CPU | `vTaskDelay()`、等待队列/信号量/事件；超时或事件满足后变为 Ready |
| Suspended（挂起） | 被显式暂停，不因时间或事件自动恢复 | `vTaskSuspend()`；仅 `vTaskResume()` / `xTaskResumeFromISR()` 可恢复为 Ready |
| Deleted（已删除） | 已从调度中移除 | `vTaskDelete()`；动态创建的任务通常由空闲任务回收资源 |

**核心记忆**：Ready 是“能运行、等 CPU”；Blocked 是“在等事情发生”；Suspended 是“被人为暂停”。

#### 状态转换与调度

```text
Ready     ──(调度器选中)──────────────────────────────> Running
Running   ──(延时/等待队列、信号量、事件)──────────────> Blocked
Blocked   ──(超时或等待条件满足)────────────────────────> Ready
Running   ──(vTaskSuspend)─────────────────────────────> Suspended
Suspended ──(vTaskResume / xTaskResumeFromISR)──────────> Ready
Running   ──(被更高优先级任务抢占/时间片结束)──────────> Ready
Running   ──(vTaskDelete)──────────────────────────────> Deleted
```

在抢占式调度下，调度器总是优先运行最高优先级的 Ready 任务：当前任务阻塞、主动 `taskYIELD()`，或更高优先级任务由中断/其他任务唤醒变为 Ready 时，都会触发或请求任务切换。同优先级任务是否按 Tick 轮转取决于 RTOS 配置（FreeRTOS 常见为 `configUSE_TIME_SLICING`）。单核同一时刻只有一个 Running 任务；SMP 多核系统中，每个核心可各有一个 Running 任务。

任务通信的本质不是“任务 A 直接调用任务 B”，而是操作内核对象改变任务状态。例如，任务等待空队列时进入 Blocked；生产者发送数据后，等待者变为 Ready；若其优先级更高，抢占式内核会尽快让它获得 CPU。

#### 高频面试问答

**Blocked 与 Suspended 有何区别？** Blocked 是等待延时、队列、信号量或事件，条件满足或超时后可自动转为 Ready；Suspended 没有超时和事件唤醒机制，只能由显式 Resume 恢复。

**什么时候会发生任务切换？** 典型时机是：当前任务阻塞/延时、时间片结束（若启用）、调用 `taskYIELD()`，或更高优先级任务被其他任务或 ISR 唤醒。ISR 中使用 `xxxFromISR()` 成功唤醒更高优先级任务后，通常需在 ISR 退出路径请求调度。

## 2. 任务间通信与同步的总体区别

### 2.1 一句话区分

- **通信机制**：解决“数据或事件如何从一个执行单元传给另一个执行单元”。
- **同步机制**：解决“多个执行单元何时执行、谁先执行、谁能访问共享资源”。

二者经常组合使用。例如，生产者把数据放入队列是通信；消费者等待队列数据是同步；多个任务访问同一个 SPI 总线时，需要互斥锁保护总线是同步。

```text
任务 A ──产生数据──> [队列/邮箱/环形缓冲区] ──读取数据──> 任务 B
任务 A ──释放信号量/设置事件──> 任务 B 被唤醒
任务 A、任务 B ──竞争访问──> [共享资源] <──由互斥锁保护──>
```

### 2.2 选择机制前先回答三个问题

1. 是否需要传递数据？如果需要，优先考虑队列、邮箱、环形缓冲区或共享内存。
2. 是否只需要通知“事情发生了”？如果不需要数据，优先考虑二值信号量、计数信号量或事件标志组。
3. 是否需要保护一段共享资源？如果是，优先考虑互斥锁；不要用普通信号量替代互斥锁来掩盖优先级反转问题。

## 3. 同步机制

### 3.1 临界区

临界区是暂时禁止调度或禁止中断，保证一小段代码不会被并发打断。

```c
enter_critical();
shared_counter++;
exit_critical();
```

适用场景：更新很短的状态、操作位图、修改链表指针等。临界区应尽可能短，不能在其中执行阻塞调用、耗时计算或等待外设。

注意：禁止调度不一定等于禁止中断；禁止中断也不一定适合多核。单核下临界区可以防止任务切换和部分中断竞争，但多核下另一颗 CPU 仍可能同时访问同一片内存，需要自旋锁、硬件原子操作或其他跨核同步手段。

### 3.2 调度器锁

调度器锁只限制任务切换，不一定屏蔽中断。它适用于保护只会被任务访问、且操作时间很短的数据结构。

```c
lock_scheduler();
update_task_owned_state();
unlock_scheduler();
```

如果共享数据会在 ISR 中访问，不能只依赖调度器锁；如果共享数据会被另一颗 CPU 访问，多核系统也不能只依赖单核调度器锁。

### 3.3 二值信号量

二值信号量只有“有”和“无”两种状态，常用于事件通知，尤其适合中断通知任务。

```c
// ISR 中
binary_semaphore_give_from_isr(data_ready_sem);

// 任务中
binary_semaphore_take(data_ready_sem, WAIT_FOREVER);
process_data();
```

典型场景：DMA 完成、串口接收完成、GPIO 中断、定时器到期。

二值信号量通常只表达“至少发生过一次”，连续发生多次时不会自动保留每次事件数量；如果每一次事件都不能丢，应改用计数信号量或队列。

### 3.4 计数信号量

计数信号量内部维护一个计数值，释放一次计数加一，获取一次计数减一。

适用场景：

- 统计多个相同事件。
- 管理固定数量的缓冲区、连接对象或资源令牌。
- 表示资源池中当前可用对象数量。

```c
counting_sem_give();       // 一个缓冲区归还
counting_sem_take(timeout); // 获取一个可用缓冲区
```

计数信号量只提供数量，不携带具体数据；数据本身通常放在环形缓冲区或对象池中。

### 3.5 互斥锁

互斥锁用于保护共享资源，同一时刻只允许一个任务进入临界区域。

```c
mutex_lock(i2c_mutex, WAIT_FOREVER);
i2c_write(device, buffer, length);
mutex_unlock(i2c_mutex);
```

适用场景：共享 I2C、SPI、显示控制器、日志输出、文件对象或复杂数据结构。

互斥锁与二值信号量的主要区别：

| 项目 | 互斥锁 | 二值信号量 |
| --- | --- | --- |
| 主要目的 | 保护共享资源 | 任务/中断通知 |
| 所有权 | 通常有，谁加锁谁解锁 | 通常没有严格所有权 |
| 优先级继承 | 通常支持 | 通常不用于此目的 |
| ISR 中使用 | 通常不能在 ISR 中加锁 | 可使用专用 FromISR 接口 |

### 3.6 优先级反转

假设低优先级任务持有锁，高优先级任务等待该锁，而中优先级任务持续运行，那么高优先级任务反而可能长时间无法运行，这就是优先级反转。

```text
高优先级任务：等待锁 ───────────────┐
低优先级任务：持有锁 ──被抢占───────┼─> 高优先级任务被间接阻塞
中优先级任务：持续运行 ──────────────┘
```

常见处理方法：

- 使用支持优先级继承的互斥锁。
- 缩短持锁时间，不在锁内做阻塞操作。
- 按固定顺序获取多个锁，避免死锁。
- 对硬实时资源设置明确的访问上限。

### 3.7 事件标志组

事件标志组用多个 bit 表示多个事件，任务可以等待任意一个事件或等待多个事件同时发生。

```c
wait_event(EVENT_NET_READY | EVENT_CONFIG_READY,
           WAIT_ALL,
           WAIT_FOREVER);
```

适用场景：系统启动条件、多个外设状态组合、网络连接状态、任务间广播通知。

事件标志组一般只保存状态，不保存事件发生次数，也不携带数据。若同一个 bit 在任务处理前被重复设置，通常仍只表现为“该事件已发生”。

### 3.8 软件定时器和任务同步

软件定时器回调通常运行在定时器服务任务中，不应在回调中执行长时间操作或调用可能永久阻塞的 API。更稳妥的方式是：回调只发送事件或消息，再由业务任务完成实际处理。

```c
static void timer_callback(void *arg)
{
    event_set(EVENT_TIMEOUT);
}
```

### 3.9 同步机制中的常见错误

- 用全局变量配合延时轮询代替可靠同步，导致丢事件或响应延迟。
- 在 ISR 中调用普通任务 API，而不是专用的 ISR 安全接口。
- 持有互斥锁时等待另一个资源，形成锁顺序反转。
- 在临界区中进行日志打印、内存分配或设备读写。
- 把互斥锁当作数据传输工具，实际却没有定义数据所有权。
- 忽略超时返回值，任务永久等待后无法恢复或上报故障。

## 4. 通信机制

### 4.1 队列（Queue）

队列是最常用的任务间通信机制。发送方复制一条固定大小的消息到队列，接收方从队列取出消息。

```c
typedef struct {
    uint16_t type;
    uint16_t length;
    uint8_t  payload[32];
} message_t;

queue_send(message_queue, &message, WAIT_FOREVER);
queue_receive(message_queue, &message, WAIT_FOREVER);
```

优点：数据和同步合一、天然支持生产者/消费者模型、可以设置队列长度形成有限缓冲。

缺点：通常会发生数据复制；消息大小固定；队列满时需要明确处理丢弃、覆盖、阻塞或错误上报策略。

#### 队列满时的处理策略

队列长度是有限的。发送端发现队列已满时，应根据消息的重要性、实时性要求和系统可承受的延迟，明确选择处理策略，而不是默认无限等待。

| 策略 | 核心行为 | 优点 | 缺点 | 典型场景 |
| --- | --- | --- | --- | --- |
| 丢弃新消息 | 新消息直接丢弃，快速失败 | 低延迟，系统稳定 | 消息会丢失 | 实时日志、监控指标、直播流 |
| 丢弃旧消息（覆盖） | 丢弃最旧的消息，放入新消息 | 保证数据“最新” | 历史数据丢失 | 实时态势感知、最新价格展示 |
| 阻塞 | 发送端等待，直到队列有空位 | 消息不丢失 | 增加延迟，可能产生反压 | 金融交易、关键业务通知 |
| 错误上报 | 立即返回错误，由应用处理 | 控制权交给应用，问题可感知 | 需要应用层处理复杂逻辑 | 所有需要明确失败反馈的场景 |
| 反压 | 通过限流，让上游“慢下来” | 从源头保护系统，优雅降级 | 实现复杂，会降低上游吞吐 | 高并发下的分布式系统防护 |

在 MCU 型 RTOS 中，常用的落地方式是为队列发送设置有限超时：超时后丢弃、计数并上报，或通知上游降低生产速率。不要在持有互斥锁或关键资源时无限阻塞发送，以免扩大阻塞范围甚至诱发死锁。

适用场景：命令分发、传感器采样、协议栈消息、任务之间传递结构体。

### 4.2 邮箱（Mailbox）

Mailbox 通常用于传递固定大小的消息或指针，具体实现因 RTOS 而异。它比队列更强调“一个消息槽”或“消息单元”的快速投递。

```c
mailbox_post(mailbox, message_id, WAIT_FOREVER);
mailbox_fetch(mailbox, &message_id, WAIT_FOREVER);
```

Mailbox 可以传递：

- 小整数、事件编号、状态值。
- 指向大数据缓冲区的指针。
- 多核通信中的通知或共享内存消息索引。

传递指针时必须明确缓冲区所有权：发送方何时不能再修改，接收方何时归还，异常超时如何回收。否则容易出现悬空指针、重复释放和数据覆盖。

### 4.3 环形缓冲区（Ring Buffer）

环形缓冲区通过读指针和写指针复用一块连续内存，适合字节流或变长数据。

```text
写入方向：             读出方向：
       write -> [数据 数据 空闲 空闲] <- read
                         ^
              到末尾后回到缓冲区起点
```

典型场景：UART 接收、日志流、网络字节流、DMA 接收缓冲区。

环形缓冲区本身通常只负责存储，不一定负责任务唤醒，因此常与信号量、事件或队列组合：ISR/DMA 写入数据并通知任务，任务再批量读取。

单生产者单消费者模型可以通过读写指针降低锁开销；多生产者或多消费者需要互斥锁、原子操作或专门的无锁算法。

### 4.4 直接任务通知

部分 RTOS 提供直接任务通知，用任务控制块中的字段完成轻量通知、计数或位图传递。

```c
task_notify(task_handle, EVENT_RX_DONE);
task_wait_notification(&value, WAIT_FOREVER);
```

优点是速度快、内存开销小；缺点是通常只能绑定一个目标任务，表达能力和缓冲能力不如队列。适合简单事件、计数器、DMA 完成通知，不适合传输大量消息。

### 4.5 消息队列与指针队列的选择

| 方式 | 传递内容 | 优点 | 风险 |
| --- | --- | --- | --- |
| 消息复制 | 固定大小结构体 | 所有权清晰，接收方安全 | 有复制开销 |
| 指针传递 | 缓冲区地址 | 适合大数据，速度快 | 必须管理生命周期 |
| 索引传递 | 缓冲区池索引 | 所有权容易追踪 | 需要对象池 |

对于大数据，常用“内存池 + 指针/索引队列”：生产者申请缓冲区并填充，队列只传递指针或索引，消费者处理后归还内存池。

### 4.6 流缓冲区和字节流

流缓冲区适合单向字节流，通常不关心消息边界；消息缓冲区则保留完整消息边界。UART、音频和网络数据流更适合流缓冲区，命令结构体和事件更适合消息队列。

如果协议本身有帧头、长度、校验和，接收任务仍需要在流缓冲区上完成拆帧，不能把一次读取当成一次完整协议包。

### 4.7 通信机制组合模式

#### 生产者—消费者

```text
采集任务 ──> 数据队列/环形缓冲区 ──> 处理任务 ──> 存储或发送任务
```

生产者只负责产生数据，消费者负责处理数据，可降低模块耦合并吸收短时速率差异。

#### 事件通知 + 共享数据

事件只负责唤醒，数据放在共享缓冲区中。此时必须配合互斥锁、双缓冲、读写索引或明确的单生产者单消费者约束。

#### 命令队列 + 响应队列

适合设备管理任务：调用方发送命令和事务 ID，设备任务执行后把结果发送回响应队列，避免多个任务直接操作同一外设。

## 5. 多核 RTOS 的通信机制

### 5.1 多核场景与单核场景的本质差异

单核系统中，任务不会真正同时执行，很多问题可以通过短临界区和关中断暂时避免。多核系统中，不同核上的任务可能同时访问同一变量、队列或缓冲区，因此还需要考虑：

- Cache 一致性和内存可见性。
- 原子操作、内存屏障和锁的跨核有效性。
- 中断路由和核间中断（IPI）。
- 共享内存的所有权与缓存刷新。
- 消息乱序、重复、丢失和核复位后的恢复。

多核 RTOS 中的“任务间通信”要先区分两类：同一核内任务之间通信，以及不同核/不同处理器之间的核间通信。后者不能简单把单核队列搬过去就认为完成了。

### 5.2 共享内存

共享内存是多核通信的基础：双方约定一片物理内存作为控制块、环形队列或数据缓冲区。

```text
核 0                                  核 1
生产者任务                            消费者任务
   │                                     ▲
   ├─写入共享数据──> [共享内存环形队列] ──┤
   └─发送核间中断/doorbell ───────────────┘
```

典型结构包括：

```c
typedef struct {
    volatile uint32_t read_index;
    volatile uint32_t write_index;
    uint8_t buffer[BUFFER_SIZE];
} shared_ring_t;
```

但 `volatile` 只能防止编译器直接优化访问，不能自动解决并发安全、Cache 一致性和内存访问顺序问题。实际实现还需要原子读写、内存屏障、Cache clean/invalidate，以及生产者和消费者的所有权约定。

### 5.3 Mailbox 作为核间通知或消息通道

多核系统中的 Mailbox 可能是：

1. 芯片硬件提供的 Mailbox 外设，用寄存器或共享 RAM 在核之间投递消息。
2. RTOS 软件 Mailbox，运行在同一共享内存和核间中断之上。
3. 抽象出的消息槽，用于传递事件号、缓冲区地址或共享内存索引。

常见链路如下：

```text
核 0 任务
  │ 1. 填充共享缓冲区
  │ 2. 写入 mailbox 消息槽（地址/索引/长度）
  │ 3. 触发核 1 的 IPI
  ▼
核 1 Mailbox ISR
  │ 4. 清除硬件通知
  │ 5. 唤醒核 1 的通信任务
  ▼
核 1 通信任务
  │ 6. 读取共享缓冲区并处理
  │ 7. 回写完成状态或发送 ACK
```

Mailbox 适合短消息、事件通知和缓冲区索引；大数据不应直接塞进寄存器或小消息槽，而应放到共享内存，Mailbox 只传递地址、长度和序号。

### 5.4 RPMsg

RPMsg（Remote Processor Messaging）通常建立在 remoteproc、共享内存、virtqueue 和核间通知之上，为异构多核处理器提供标准化的端点消息通信模型。它常用于主核与从核、应用处理器与 MCU、DSP 与 CPU 之间传递控制消息和小块数据。

```text
本地 Endpoint
    │ send
    ▼
Virtqueue / 共享内存环形队列
    │ doorbell / IPI
    ▼
远端 Virtqueue
    │ receive callback
    ▼
远端 Endpoint
```

RPMsg 中需要理解的几个对象：

| 对象 | 作用 |
| --- | --- |
| Endpoint | 逻辑通信端点，通常由地址标识 |
| Virtqueue | 管理共享内存中的消息缓冲区和描述符 |
| Shared Memory | 存放消息和控制结构 |
| Notify/IPI | 通知对端有新消息或缓冲区已归还 |
| Name Service | 在某些实现中用于发现远端服务 |

RPMsg 适合把核间通信封装为“服务 + 消息”的形式，例如传感器服务、音频服务、日志服务和控制命令服务。使用时仍要明确：消息大小限制、端点生命周期、远端未启动/已复位时的错误处理、共享内存 Cache 属性以及是否允许阻塞等待。

### 5.5 Mailbox 与 RPMsg 的关系

Mailbox 和 RPMsg 不是完全同一层次的概念：

| 对比项 | Mailbox | RPMsg |
| --- | --- | --- |
| 抽象层级 | 通知或简单消息通道 | 面向端点的消息框架 |
| 典型载荷 | 事件号、地址、索引、短消息 | 服务消息、控制命令、数据包 |
| 底层依赖 | 硬件 Mailbox 或共享内存 + IPI | 共享内存 + Virtqueue + 通知 |
| 优点 | 简单、低延迟、开销小 | 规范化、可扩展、便于服务发现 |
| 适合场景 | 快速唤醒、状态同步、短消息 | 异构核之间的服务化通信 |

可以把 Mailbox 看成“通知/搬运通道”，把 RPMsg 看成建立在共享内存和核间通知之上的“消息服务框架”。实际项目中也可能由 Mailbox 负责 doorbell，再由 RPMsg 负责消息队列管理。

### 5.6 多核通信的内存顺序

发送方不能只写数据后立刻通知对端，还要保证“数据写入已经对对端可见”。一般顺序应为：

```text
写共享数据
    ↓
写入发布索引/描述符
    ↓
内存屏障 + Cache clean（按平台要求）
    ↓
触发 Mailbox/IPI/doorbell
```

接收方通常应为：

```text
收到 Mailbox/IPI
    ↓
清除通知并执行内存屏障
    ↓
Cache invalidate（按平台要求）
    ↓
读取索引/描述符和共享数据
```

具体屏障指令和 Cache 操作由 CPU、总线和内存属性决定，不能用一个跨平台宏想当然替代所有平台检查。

### 5.7 多核通信的可靠性设计

- 消息带序号，便于发现丢失、重复和乱序。
- 消息带长度和类型，避免把不同协议误解析。
- 大数据采用共享缓冲区，控制消息采用 Mailbox/RPMsg。
- 发送和接收两端明确 buffer ownership，不要同时修改同一缓冲区。
- 对端未启动、端点不存在、队列满和远端复位设置超时与错误码。
- 必要时设计 ACK、重试、取消和版本号。
- 核间 ISR 只做清通知、记录状态和唤醒任务，复杂处理放到任务上下文。
- 记录远端核复位前后的状态，避免本端一直阻塞在已失效的通信对象上。

## 6. ISR、任务和通信 API 的边界

中断服务函数应尽快结束，通常只完成：读取硬件状态、保存少量数据、清除中断、投递队列/信号量/任务通知。耗时协议解析、内存分配、日志打印和业务处理应放在任务中。

```text
硬件中断
  ├─读取状态/搬运数据
  ├─写入环形缓冲区
  └─通知任务
          ↓
通信或业务任务
  ├─拆包、校验、解析
  ├─访问共享资源
  └─发送响应/唤醒下游任务
```

FreeRTOS、RT-Thread 等通常会为 ISR 提供专用 API 或中断安全调用约束。调用前应确认：是否允许在 ISR 中使用、是否可能阻塞、是否需要触发调度、是否需要传入高优先级任务唤醒标志。

## 7. 死锁、竞态和资源设计

### 7.1 死锁的四个必要条件

- 互斥：资源同一时刻只能被一个执行单元持有。
- 占有且等待：持有一个资源的同时等待另一个资源。
- 不可剥夺：资源不能被强制收回。
- 循环等待：任务之间形成锁等待环。

工程上常用的预防方法是统一锁顺序、缩短持锁时间、避免嵌套锁，并为每次等待设置超时。

### 7.2 竞态条件

竞态的本质是结果依赖执行时序。例如任务 A 读取计数器后被切换，任务 B 修改计数器，任务 A 再写回旧值，就可能丢失更新。

解决思路：使用互斥锁保护读-改-写操作、使用原子操作、将数据限制为单一所有者，或改成消息传递而不是多个任务直接改同一全局变量。

### 7.3 数据所有权

通信设计中应始终回答：

- 缓冲区由谁申请？
- 谁可以读、谁可以写？
- 什么时候转移所有权？
- 谁负责释放或归还？
- 发送超时、接收失败、远端复位时怎么办？

“队列传指针”只是传递了地址，不代表自动完成了生命周期管理。

## 8. 机制选择建议

| 需求 | 推荐机制 |
| --- | --- |
| 保护共享 I2C/SPI/日志资源 | 互斥锁 |
| ISR 唤醒一个任务 | 二值信号量或直接任务通知 |
| 统计不可丢失的重复事件 | 计数信号量 |
| 等待多个系统状态 | 事件标志组 |
| 传递固定大小命令/结构体 | 消息队列 |
| 传递大数据缓冲区 | 内存池 + 指针队列 |
| UART/音频连续字节流 | 环形缓冲区 + 信号量/事件 |
| 轻量事件或计数通知 | 直接任务通知 |
| 同核简单短消息 | RTOS 队列/邮箱 |
| 异构核服务化通信 | RPMsg |
| 跨核快速通知或索引投递 | Mailbox + 共享内存 |

### 8.1 常见场景组件对照

下表中的“禁止使用”指该场景下**不应作为首选方案**；部分机制在特定设计约束下可以工作，但容易带来优先级反转、无法在 ISR 中使用、无谓关闭中断或语义不清等问题。

| 使用场景 | 推荐组件 | 不建议使用 |
| --- | --- | --- |
| 任务互斥访问资源（无中断参与） | Mutex | 信号量；调度器锁（不优先） |
| 任务间单纯事件同步、无数据 | 任务通知 / 二值信号量 | 队列 |
| 任务间同步并传递数据 | 消息队列 | 互斥锁 |
| 中断唤醒任务，仅事件通知 | 二值信号量 `FromISR` 接口 / `xTaskNotifyFromISR()` | Mutex |
| 中断向任务传递数据 | 队列 `FromISR` 接口，例如 `xQueueSendFromISR()` | Mutex |
| 任务与中断共同读写共享变量 | 临界区，例如 `taskENTER_CRITICAL()` | Mutex、调度器锁 |
| 等待多路不同事件 | 事件组 | 普通二值信号量 |
| 管理有限数量的同类资源 | 计数信号量 | 互斥锁 |
| 简短的任务—任务保护，且不想新建内核对象 | 调度器锁，例如 `vTaskSuspendAll()` | 临界区（无必要时不应关闭中断） |

> 注意：`taskENTER_CRITICAL()` 的具体中断屏蔽范围和可用上下文取决于移植层；多核场景还必须使用跨核有效的自旋锁、原子操作或其他同步机制。调度器锁只适用于不会被 ISR 或其他 CPU 核并发访问的短操作。

### 8.2 一个实用判断流程

```text
是否需要保护共享资源？ ──是──> 互斥锁/临界区/自旋锁
          │否
          ▼
是否需要传输数据？ ──否──> 信号量/事件/任务通知
          │是
          ▼
数据小且有消息边界？ ──是──> 队列/邮箱
          │否
          ▼
数据大或连续字节流？ ──> 内存池+指针队列/环形缓冲区
          │
          └─跨核？ ──> 共享内存 + Mailbox/IPI，或 RPMsg
```

## 9. 从 RTOS 到 Linux：线程通信与同步机制

Linux 开发中的线程通信与同步机制，与 RTOS 的任务同步工具在核心概念和设计目标上高度相似：两者都用于解决多执行单元并发时的资源竞争、执行顺序协调和数据传递问题。区别在于 Linux 是通用操作系统，机制更丰富，使用场景和实现细节也更复杂。

### 9.1 核心概念与对应关系

| 功能分类 | RTOS 中的工具 | Linux（pthread）中的主要工具 | 核心作用与差异 |
| --- | --- | --- | --- |
| 互斥访问 | 互斥量（Mutex）、信号量 | 互斥锁（`pthread_mutex_t`）、读写锁（`pthread_rwlock_t`） | 保护共享资源，防止并发修改。读写锁允许多个读操作并发，适合读多写少场景。 |
| 条件同步/等待 | 事件标志组、任务通知、信号量 | 条件变量（`pthread_cond_t`） | 线程在条件不满足时挂起等待；被唤醒后重新检查条件并继续执行。它是生产者—消费者等问题的标准工具，语义比单纯信号量更灵活。 |
| 计数与资源管理 | 计数信号量 | 信号量（`sem_t`） | 管理有限数量的资源，或实现通用的计数同步；两者功能非常相似。 |
| 数据传递与同步 | 消息队列、流缓冲区 | 消息队列（POSIX mqueue/System V）、管道（Pipe/FIFO） | 用于传递数据块。Linux 消息队列更常用于进程间通信（IPC）；纯线程间通信常使用共享内存配合互斥锁，或使用轻量级无锁队列。 |

### 9.2 Linux 的特性与设计视角

1. **更丰富的锁家族**：除基础互斥锁外，Linux 还提供读写锁（`pthread_rwlock_t`），可在读多写少时提高并发性。自旋锁（spinlock）适合保护极短的临界区，通常用于内核或驱动开发；普通用户态应用更常使用可休眠的互斥锁。

2. **“互斥锁 + 条件变量”是核心范式**：RTOS 中可用事件标志组或信号量实现复杂等待逻辑；在遵循 POSIX 的 Linux 程序中，互斥锁配合条件变量是处理“等待某个条件成立”的标准做法。`pthread_cond_wait()` 会在等待时原子地释放互斥锁，在被唤醒后重新获取锁，从而避免忙等，并降低竞态和死锁风险。条件变量可能出现虚假唤醒，因此必须始终在循环中检查条件。

3. **futex 是轻量同步的基础**：Linux 许多高级同步机制（如互斥锁、信号量）的底层实现依赖 futex（fast userspace mutex，快速用户空间互斥体）。无竞争时，同步操作通常在用户态完成；发生竞争时才进入内核仲裁，因此兼顾了常见路径的性能与竞争场景下的正确性。

### 9.3 Linux 中的选择建议

- **保护共享数据**：仅需防止多个线程同时修改数据时，优先使用互斥锁（`pthread_mutex_t`）；读多写少时，考虑读写锁（`pthread_rwlock_t`）。
- **等待另一个线程满足条件**：例如生产者产生数据后消费者才能处理，应使用条件变量（`pthread_cond_t`）配合互斥锁。
- **管理有限数量的同类资源**：例如连接池有 10 个连接，可使用信号量（`sem_t`）管理。
- **在线程间传递数据**：数据量小且结构简单时，可在共享内存中保存变量并用互斥锁保护；需要传递复杂数据块时，可使用消息队列（更偏向进程间）或自行实现基于互斥锁和条件变量的线程安全队列。

### 9.4 小结

Linux 线程同步与 RTOS 任务同步的核心思想一脉相承，都是并发编程的工具箱。Linux 提供了更丰富、性能优化更深入的机制，并形成了以互斥锁和条件变量为核心的标准化编程模式。理解 RTOS 中的概念后，再学习 Linux 的 pthread 机制通常只需补充相应 API 和更细致的使用约束即可。

## 10. 总结

1. FreeRTOS、RT-Thread 的基本调度单位是任务，多个任务通常共享地址空间。
2. 同步机制解决执行顺序和共享资源访问，通信机制解决数据和事件传递。
3. 互斥锁用于资源保护，信号量用于通知或资源计数，事件用于组合状态，队列/邮箱用于消息传递。
4. 环形缓冲区负责高效保存流式数据，通常需要再配合信号量或任务通知完成唤醒。
5. 传递大数据时优先使用内存池加指针/索引，必须设计清晰的数据所有权。
6. 多核通信的关键不只是“把消息发给另一个核”，还包括共享内存、Cache 一致性、内存屏障、IPI/doorbell、队列满、远端复位和错误恢复。
7. Mailbox 更适合跨核通知、短消息和缓冲区索引；RPMsg 更适合建立在共享内存之上的服务化消息通信。
8. ISR 负责快速响应和唤醒任务，复杂业务放在任务上下文中完成。
