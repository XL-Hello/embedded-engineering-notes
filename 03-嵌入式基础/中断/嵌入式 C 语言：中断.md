# 嵌入式中断：从主循环被打断到原位恢复

> 目标：从 CPU 的基本执行机制理解中断为什么能在主循环执行到一半时插入、为什么中断处理完成后又能准确回到原来的位置；同时能用面试语言说明现场保护、中断入口与返回。
>
> 来源：围绕 Cortex-M 等常见 MCU 的通用中断机制整理。不同 CPU 的寄存器名称和自动保存范围不同，但核心过程一致。

## 1. 先用一句话理解中断

**中断是 CPU 在“当前一条指令完成的边界”发现有更高优先级事件需要处理时，先保存当前程序的续跑位置和必要状态，跳到固定的中断服务函数（ISR）执行；ISR 返回时再恢复状态，因此主程序像暂停后继续播放一样接着运行。**

它不是 CPU 同时执行主循环和中断，也不是外设直接把 CPU 的代码“挤走”。CPU 仍然一次只执行一条指令，只是在合适的指令边界改走了中断入口。

```text
主循环正在执行                         发生中断后的 CPU 动作
... -> 指令 A -> 指令 B -> 指令 C       完成当前指令 -> 保存现场 -> 查中断向量
                                              -> 跳到 ISR -> 执行 ISR
                                              -> 恢复现场 -> 回到主循环下一条指令
```

> 关键点：通常说“执行到一半被中断”，指的是“主循环的一段业务逻辑还没做完”，而不是一条机器指令真的被切成两半。多数 MCU 在单条指令边界响应中断。

## 2. 先区分：轮询和中断

假设按键或串口收到数据，需要 CPU 处理。

```c
while (1) {
    task_a();
    task_b();
    if (uart_rx_ready()) {       // 轮询：CPU 主动反复问
        handle_uart_rx();
    }
}
```

轮询中，数据即使已经到达，也要等 CPU 再执行到 `uart_rx_ready()` 才处理。中断则是外设把请求送到中断控制器，CPU 在允许响应时尽快转入 ISR：

```c
while (1) {
    task_a();                     // 可能执行到这里时 UART 收到字节
    task_b();
}

void USARTx_IRQHandler(void)      // 中断服务函数 ISR
{
    if (uart_rx_flag()) {
        uint8_t ch = uart_read(); // 尽快取走数据/清标志
        rx_buffer_push(ch);       // 交给主循环后续处理
    }
}
```

中断适合异步、及时性较强的事件：串口收发、定时器到期、DMA 完成、外部引脚边沿等。ISR 应短小，复杂计算、阻塞等待和耗时 I/O 通常留给主循环或任务执行。

## 3. 一次中断从产生到执行的完整链路

以“主循环运行时串口收到一个字节”为例：

```text
UART 收到字节
    |
    v
UART 外设置位 RX 标志，并向中断控制器提出请求 IRQ
    |
    v
NVIC/中断控制器判断：该 IRQ 是否使能、是否挂起、优先级是否能抢占当前上下文
    |
    v
CPU 完成当前机器指令，在中断未屏蔽时接受异常请求
    |
    v
保存现场 -> 根据向量表取得 USARTx_IRQHandler 地址 -> 跳转执行 ISR
    |
    v
ISR 读取数据、清除中断源/标志，执行中断返回
    |
    v
恢复现场 -> 从被保存的返回地址继续执行主循环
```

这里有三类角色：

| 角色 | 做什么 | 例子 |
| --- | --- | --- |
| 中断源 | 发现事件、置状态位、提出请求 | UART、Timer、GPIO、DMA |
| 中断控制器 | 记录挂起、开关使能、仲裁优先级 | Cortex-M 的 NVIC |
| CPU 内核 | 保存/恢复执行状态，跳 ISR 和返回 | Cortex-M 内核 |

外设通常不会因为请求中断就自动停止继续产生事件。比如 UART 接收标志未清、FIFO 未读空，或者定时器更新标志未清，就可能再次请求中断。因此 ISR 必须按照芯片手册规定读取数据或清除相应标志。

## 4. “主循环执行到一半”时，到底发生了什么

先把 C 代码和 CPU 真正执行的东西分开。下面一行 C 代码可能编译成许多机器指令：

```c
sum += read_sensor() * scale;
```

CPU 可能依次完成“取参数、调用函数、读取寄存器、乘法、加法、写回变量”等多条指令。在每条指令完成后，CPU 检查是否有可接收的中断；一旦接受：

1. 当前指令已经完成，其结果符合 CPU 的指令语义。
2. `PC` 已经指向原程序接下来该执行的位置，或 CPU 已具备可恢复该位置的返回地址。
3. CPU 保存必要现场，然后才跳到 ISR。

因此 ISR 返回后，CPU 并非“猜测该回哪”，而是使用保存好的返回地址重新装入 `PC`。主循环从那条下一条机器指令继续。

```text
时间 --->

主程序： [指令 101 已完成] [指令 102 已完成]  |暂停|                [指令 103] [指令 104]
                                             |
中断：                                       保存 -> ISR -> 返回/恢复
```

### 4.1 会不会把一条指令执行一半？

通常不会。CPU 选择在可中断点（一般是指令边界）响应，保证已经完成的指令不会只完成一半。少数架构的复杂指令、流水线、总线事务或特殊异常的细节较复杂，但对软件可见的架构状态仍要满足其规定的精确异常/中断语义。实际开发中应按“中断可能出现在任意两条普通指令之间”来设计共享数据。

### 4.2 为什么看起来像任意位置被打断？

因为一段 C 函数由大量机器指令组成，中断恰好可能落在其中任意两个指令之间。调试器单步或日志看到“函数执行到中间进 ISR”是正常现象；可恢复的最小单位是 CPU 指令，不是 C 语句、函数或 `while` 循环的一整轮。

## 5. CPU 靠什么回到原来位置：PC、栈与现场

### 5.1 PC 是“下一步去哪里”的地址

`PC`（Program Counter，程序计数器）保存当前/下一条指令的地址。普通函数调用时，CPU 也需要记住返回地址；中断可看成一种由硬件触发、优先级更高的特殊调用，只是它还要保护更多上下文。

### 5.2 什么是现场保护

中断发生时，主程序的寄存器里可能正暂存局部变量、计算中间结果和条件状态。若 ISR 随意使用这些寄存器却不恢复，主程序回来后就会把中间数据弄乱。

所以要保存“恢复后继续运行所需的 CPU 状态”，典型包括：

| 现场 | 为什么要保存 |
| --- | --- |
| `PC` / 返回地址 | 知道 ISR 结束后从哪里继续 |
| 状态寄存器（如 xPSR） | 保留条件标志、执行状态等 |
| 通用寄存器 | 保留主程序的局部数据和中间计算结果 |
| 栈指针 `SP` 的上下文 | 让主程序和 ISR 各自的栈帧不混乱 |
| 浮点/扩展寄存器（使用时） | 避免浮点或 SIMD 中间结果被破坏 |

保存位置通常是当前栈。每进入一层中断，就像多压入一层“暂停现场”；返回时按相反顺序弹出，因此支持嵌套中断。

```text
栈从高地址向低地址增长（示意）

中断前：       | 主函数局部变量 / 调用链 |
接受中断后：    | 主函数局部变量 / 调用链 |
                | 自动保存的返回现场      | <- PC、xPSR、部分寄存器
                | ISR 额外保存的寄存器    | <- 编译器/入口代码按需保存
                +-------------------------+
```

> 一句话：**栈里保存的返回地址告诉 CPU 回哪里，栈里保存的寄存器内容让 CPU 回去后仍保有原来的“工作上下文”。**

### 5.3 栈怎样保存一份可恢复的现场

栈可以把它理解为 CPU 专门管理的一块“后进先出”内存：`SP`（Stack Pointer，栈指针）始终指向当前栈顶。压栈（push）会移动 `SP` 并写入数据；出栈（pop）按相反顺序读回数据并还原 `SP`。许多 MCU 的栈向低地址增长，但这是具体架构的约定，不能脱离平台一概而论。

中断进入时，不是把整块 RAM 或整个函数的变量逐字复制，而是保存**恢复执行所必需的寄存器状态**。主函数自己的局部变量、调用链和先前的栈帧原本就在栈中；中断现场帧再压在它们之上。ISR 若调用其他函数，也会继续使用同一栈（或平台规定的中断栈）建立自己的栈帧。ISR 返回并完成现场恢复后，`SP` 回到中断前的值，主程序看到的栈布局就像中断从未发生过。

```text
地址高
  +----------------------------------+
  | 更早的函数栈帧 / 主程序局部变量  |
  +----------------------------------+
  | 被中断函数正在使用的栈帧         |
  +----------------------------------+
  | 硬件异常帧：PC、xPSR、R0...      |  <- 中断入口自动压入（示例）
  +----------------------------------+
  | ISR 保存的额外寄存器 / ISR 局部变量 |
SP -> +----------------------------------+
地址低（许多 MCU 的示意）

ISR 返回：先释放 ISR 自己的栈帧 -> 恢复额外寄存器 -> 硬件弹出异常帧 -> SP 回到中断前
```

这也解释了两个工程现象：中断嵌套一层，栈就多占一层；ISR 内部调用深、局部数组大、使用 `printf` 或浮点运算，都可能显著增加栈需求。栈越界可能覆盖其他 RAM，最终表现为偶发跑飞、返回地址异常或 HardFault，而不一定在“压栈”那一行立刻报错。

### 5.4 硬件保存与软件保存：缺一不可

“现场保护”不等于所有寄存器都由硬件自动保存。实际保护通常分两段：

1. **硬件异常入口**保存一组架构规定的最小现场，至少保证能找到返回位置并恢复基本执行状态。
2. **编译器生成的 ISR 序言/尾声**根据 ISR 实际用了哪些寄存器、调用约定和优化级别，保存并恢复其余需要保留的寄存器；若手写汇编 ISR，则这部分责任由开发者承担。

因此，不能在 C/汇编 ISR 中随意改寄存器后直接返回，也不要因为“某寄存器平时看起来没用”就省略保护。编译器知道普通 C 函数的寄存器使用情况，能自动生成匹配的保护代码；真正容易出问题的是不遵守 ABI 的手写汇编、错误的裸中断函数（`naked`）或不完整的上下文切换代码。

### 5.5 Cortex-M 的典型过程

以常见 ARM Cortex-M 为例，CPU 接受异常/中断时，硬件会自动把 `R0`、`R1`、`R2`、`R3`、`R12`、`LR`、`PC`、`xPSR` 压入当前使用的栈（MSP 或 PSP）。其中保存的 `PC` 就是异常返回地址。

接着内核从向量表取对应异常号的 ISR 地址，装入 `PC`，开始执行 ISR。编译器生成的 ISR 函数序言会根据实际使用的寄存器，再保存其余需要保护的寄存器；若使用 FPU，硬件/软件也会处理浮点寄存器现场（具体受内核和懒压栈配置影响）。

ISR 结束不是普通的 `return` 那么简单：编译器会生成异常返回序列。Cortex-M 识别 `LR` 中的 `EXC_RETURN` 特殊值，自动从栈弹回硬件保存的寄存器、`PC` 和 `xPSR`，恢复被中断的模式和栈，继续执行原程序。

```text
接受 IRQ：硬件压栈 R0-R3,R12,LR,PC,xPSR -> PC = 向量表[IRQ]
ISR 执行：编译器按需保存/恢复额外寄存器 -> 处理并清中断源
异常返回：硬件出栈 -> 恢复 PC/xPSR/寄存器 -> 原程序继续
```

不同架构的实现会不同：有的 CPU 由硬件自动压栈较少寄存器，更多工作由汇编入口完成；有的把现场保存在专用异常帧中。但“保存返回地址与上下文 -> 跳 ISR -> 恢复 -> 用返回地址续跑”的逻辑不变。

### 5.6 用一次“压栈—出栈”串起全过程

假设主程序刚完成一条指令，此时 `R4` 中暂存计算结果，`PC` 指向下一条主程序指令：

```text
1. IRQ 被接受：硬件把返回 PC、xPSR 和规定的核心寄存器压入栈。
2. 跳 ISR：PC 改为向量表中的 ISR 地址；ISR 若会使用 R4 等额外寄存器，编译器再压栈保护。
3. ISR 工作：读取外设数据、清标志、置事件；期间可继续建立自己的函数栈帧。
4. ISR 收尾：编译器恢复它额外保存的寄存器并释放局部变量。
5. 异常返回：硬件从异常帧恢复 PC、xPSR 和核心寄存器，SP 回退。
6. 主程序继续：R4 仍是中断前的值，PC 仍指向那条下一条主程序指令。
```

这正是“中断可恢复”的物理基础：**返回地址决定控制流连续，寄存器和状态寄存器决定计算状态连续，栈指针恢复保证调用链和局部变量连续。**

## 6. 中断优先级与嵌套：ISR 也可能被打断

若低优先级 ISR 正在运行，又出现了更高优先级且允许抢占的中断，CPU 会再次保存当前 ISR 的现场，转而进入高优先级 ISR。高优先级 ISR 返回后，CPU 回到低优先级 ISR 的断点；低优先级 ISR 最后返回后，再回到主循环。

```text
主循环 -> 低优先级 ISR -> 高优先级 ISR -> 返回低优先级 ISR -> 返回主循环
```

是否能嵌套取决于 CPU 架构、优先级分组、中断屏蔽状态以及具体平台配置。嵌套会增加最大栈深度和时序复杂度，不能只按“某 IRQ 优先级数字更小”就想当然；应结合芯片/库的优先级编码规则验证。

## 7. 中断不是魔法：共享数据与可重入问题

中断能准确返回，不代表主程序的数据一定正确。主循环和 ISR 可能在任意指令边界交错访问同一变量。

```c
volatile uint32_t rx_count;

void USARTx_IRQHandler(void)
{
    rx_count++;              // ISR 修改
}

int main(void)
{
    while (1) {
        if (rx_count > 0) {  // 主循环读取并处理
            rx_count--;
        }
    }
}
```

`volatile` 只保证每次访问都真正读写内存，不保证 `rx_count++`、判断加减、读改写是原子的，也不解决多个字段必须一致的问题。常用处理方式：

- ISR 只记录事件、搬运数据到环形缓冲区、置标志；主循环处理耗时业务。
- 对必须一致的共享数据，使用很短的临界区（临时关对应中断/全局中断）或原子操作。
- 多字节变量在小位宽 MCU 上可能需要保护；在 Cortex-M 上也要考虑对齐、访问宽度和读改写。
- ISR 与主循环不要同时调用不可重入函数（如使用同一静态缓冲区的库函数），除非它明确支持。

```c
// 示例：主循环安全地取走“事件次数”，临界区要尽量短
uint32_t take_rx_events(void)
{
    uint32_t n;
    disable_irq();
    n = rx_count;
    rx_count = 0;
    enable_irq();
    return n;
}
```

实际工程应优先采用芯片 SDK/RTOS 提供的临界区接口；不要在 ISR 内盲目开关全局中断，也要避免在已有临界区中错误恢复中断状态。

## 8. ISR 编写与排错清单

一个可靠 ISR 通常遵循：确认来源 -> 尽快清除/应答 -> 保存最少数据/发通知 -> 退出。

```c
void TIMx_IRQHandler(void)
{
    if (timer_update_pending()) {
        timer_clear_update_flag();  // 先按手册规定清中断源
        tick_pending = 1;           // 只通知主循环
    }
}
```

- ISR 要短：避免 `printf`、长循环、轮询等待、Flash 擦写、阻塞锁和复杂协议解析。
- 清标志要正确：有些外设必须“先读状态再读数据”，有些是写 1 清除；顺序错误会反复进中断。
- 注意优先级：高频低优先级 ISR 可能挤占主循环；过高优先级 ISR 会拉高中断延迟。
- 计算栈：主栈、任务栈和最大嵌套深度都要预留，栈溢出会表现为随机跑飞或 HardFault。
- 测量而非猜测：用 GPIO 翻转、逻辑分析仪、DWT 计数器或 trace 看 ISR 频率、执行时间和延迟。

## 9. 面试常见问法和直白回答

### 9.1 主循环执行到一半，中断怎么插进来？

> 外设发生事件后先向中断控制器提出请求。CPU 并不是在任意电路时刻硬切代码，而是在当前机器指令完成的边界检查并接受这个请求。若该中断已使能、没有被屏蔽且优先级允许，CPU 保存现场，按中断向量表跳到 ISR，所以从 C 代码看像主循环运行到中间被打断。

### 9.2 中断执行完后，CPU 为什么能回到原位置？

> 因为进入中断时 CPU 会把返回地址，也就是被打断程序的 `PC`，以及必要寄存器和状态寄存器压栈或保存到异常帧。ISR 执行异常返回时，硬件/汇编恢复这些现场，把保存的 `PC` 装回去，所以 CPU 从原程序下一条指令继续执行，而中间计算结果也不会丢。

### 9.3 PC 保存的是被打断指令还是下一条指令？

> 对可正常响应的外部中断，软件应理解为保存的是“恢复后应继续执行的位置”，通常等价于当前已完成指令的下一条。具体 PC 值会随架构和异常类型而变化，例如同步异常可能需要重试故障指令；不能把某一款 CPU 的字节偏移规则套到所有异常上。

### 9.4 中断和函数调用有什么相同与不同？

> 都要保存返回地址并最终返回。函数调用由当前代码显式发出，通常按调用约定保存寄存器；中断由硬件异步触发，需要响应优先级和屏蔽控制，并要保护被打断上下文。Cortex-M 进入异常时还会自动保存一组核心寄存器。

### 9.5 为什么 ISR 里不能做太久？

> ISR 执行期间会占用 CPU，可能延迟同级/低优先级中断和主循环；如果高频 ISR 太长，系统会一直在处理中断。它还会增加嵌套栈深度、丢失实时事件的风险，所以通常只做清标志、取数据、置标志或投递消息。

### 9.6 `volatile` 能解决中断共享变量问题吗？

> 不能完全解决。它只避免编译器把变量缓存到寄存器或错误优化，不能保证读改写原子性，也不能让多个变量保持一致。共享数据仍需要原子操作、短临界区或合适的队列/缓冲区设计。

## 10. 最简记忆版

- 中断在“主程序的一段逻辑未结束”时发生，但一般在**机器指令边界**响应。
- 外设提请求，NVIC 判断使能/挂起/优先级，CPU 接受后才进入 ISR。
- CPU 保存 `PC`（返回位置）、状态寄存器和必要通用寄存器，通常压到栈中。
- 向量表提供 ISR 入口地址；ISR 返回时恢复现场，保存的 `PC` 让 CPU 从原程序下一条指令继续。
- Cortex-M 硬件自动保存 `R0-R3、R12、LR、PC、xPSR`，其余寄存器由编译器按需保护。
- ISR 要短并正确清中断源；中断和主循环共享数据还需要考虑原子性与临界区。
