## 1. FreeRTOS 是什么

FreeRTOS 是一个小型、可裁剪的实时操作系统内核（RTOS），为资源受限的 MCU 提供任务调度、时间管理、任务间通信、同步互斥和内存管理等能力。它通常运行在单 MCU 上，内核本身不等同于 Linux 那样包含完整进程、文件系统和网络协议栈的通用操作系统。

### 1.1 “实时”不等于“运行快”

实时系统追求的是：在可预期的时间上界内响应关键事件。FreeRTOS 通过优先级抢占、阻塞等待和中断唤醒，使高优先级任务能尽快获得 CPU。

- **硬实时**：错过截止时间即视为系统失败，例如电机保护、制动控制。
- **软实时**：偶尔超时会降低体验或性能，例如界面刷新、日志上报。
- 实际响应时间还受中断关闭时间、临界区长度、最高优先级 ISR、CPU 负载和驱动执行时间影响；RTOS 不能保证任意任务“绝对准时”。

## 2. 内核启动与调度基础

### 2.1 启动过程

1. 完成硬件时钟、外设和 FreeRTOS 配置初始化。
2. 用 `xTaskCreate()` / `xTaskCreateStatic()` 创建应用任务。
3. 调用 `vTaskStartScheduler()`：内核创建并运行空闲任务；若启用软件定时器，还会创建 Timer Service Task；随后启动 Tick 定时器和首次任务切换。
4. 此后一般不再从 `vTaskStartScheduler()` 返回；若返回，常见原因是堆不足或端口层启动失败。

### 2.2 任务优先级与抢占

- 优先级数由 `configMAX_PRIORITIES` 配置，合法优先级为 **0 到 `configMAX_PRIORITIES - 1`**；数值越大，优先级越高。
- 空闲任务的优先级固定为 `tskIDLE_PRIORITY`（通常为 0），应用任务不应长期占满 CPU，必须让空闲任务有运行机会以回收被删除任务的内存。
- 启用 `configUSE_PREEMPTION` 时，较高优先级任务一旦就绪会抢占当前低优先级任务。
- 同优先级任务是否轮转由 `configUSE_TIME_SLICING` 等配置及 Tick 共同影响；不能把“同优先级必然严格均分 CPU”当作绝对结论。
- 关闭抢占式调度可使用合作式调度：任务须主动调用 `taskYIELD()` 或进入阻塞状态后，其他就绪任务才有机会运行。它更易推理但响应性和使用约束更严格，现代产品通常采用抢占式调度。
- 调度器总是选择**最高优先级的就绪任务**；同一时刻单核通常只有一个任务处于 Running 状态。

### 2.3 任务状态与转换

| 状态 | 含义 | 常见进入方式 | 常见退出方式 |
| --- | --- | --- | --- |
| Running | 当前占用 CPU | 被调度器选中 | 被抢占、阻塞、挂起或让出 CPU |
| Ready | 已具备运行条件，等待 CPU | 创建、等待超时、收到事件 | 被调度执行 |
| Blocked | 等待时间或内核对象 | `vTaskDelay()`、队列/信号量等待 | 超时或对象可用 |
| Suspended | 被显式暂停，不参与调度 | `vTaskSuspend()` | `vTaskResume()` / `xTaskResumeFromISR()` |
| Deleted | 已删除，等待资源回收 | `vTaskDelete()` | 空闲任务回收（动态创建时） |

**阻塞与挂起的区别**：阻塞通常可由事件或超时自动恢复；挂起没有超时，必须显式恢复。阻塞比轮询更省 CPU、更利于实时性。

### 2.4 双核 SMP：以 ESP32-S3 / ESP-IDF 为例

很多 FreeRTOS 工程已不局限于单核 MCU。ESP32、ESP32-S3 等双核 SoC 在 ESP-IDF 中使用支持 **SMP（Symmetric Multiprocessing，对称多处理）** 的 FreeRTOS 实现：两个核心可并行运行两个不同任务。它并非“把单核程序放到双核上就天然线程安全”，共享数据和资源的并发风险反而更高。

| 维度 | 单核 FreeRTOS | ESP-IDF 双核 SMP 的关注点 |
| --- | --- | --- |
| 任务执行 | 同一时刻仅一个任务运行 | 两个核心可同时运行两个任务；调度器需为每个核心选择可运行任务 |
| 任务亲和性 | 通常无需指定核心 | 可绑定 CPU0/CPU1，或设为 `tskNO_AFFINITY` 允许在任一核心运行 |
| 创建 API | `xTaskCreate()` / `xTaskCreateStatic()` | 可用 `xTaskCreatePinnedToCore()` / `xTaskCreateStaticPinnedToCore()` 指定 `xCoreID` |
| 临界区 | 短暂关中断可防止本核任务/ISR 并发 | **仅关闭本核中断不足以保护跨核共享数据**；应使用 `portMUX_TYPE` 自旋锁临界区或 Mutex |
| 任务栈单位 | 原生 FreeRTOS 通常按 `StackType_t` 的字数 | ESP-IDF 任务创建 API 的栈深度参数按**字节**计，不能照搬原生 FreeRTOS 的 word 单位 |

ESP-IDF 中，`xTaskCreatePinnedToCore(..., xCoreID)` 的 `xCoreID` 取 `0`、`1` 或 `tskNO_AFFINITY`。一般仅在有明确需求时绑定核心，例如隔离对时延敏感的外设处理任务；普通应用任务可不绑定，让调度器选择合适核心。不要把“CPU0 专门跑 Wi-Fi、CPU1 专门跑业务”当作绝对规则——这是常见工程约定，最终应以 ESP-IDF 版本、组件配置和实际负载为准。

```c
/* ESP-IDF：将时延敏感任务固定在 CPU1；栈大小单位为字节 */
xTaskCreatePinnedToCore(ControlTask, "control", 4096,
                        NULL, 10, NULL, 1);

/* 共享计数器的极短跨核临界区：使用自旋锁而非仅关闭本核中断 */
static portMUX_TYPE countMux = portMUX_INITIALIZER_UNLOCKED;
taskENTER_CRITICAL(&countMux);
sharedCount++;
taskEXIT_CRITICAL(&countMux);
```

**双核面试答法**：ESP-IDF 的 FreeRTOS 是针对双核 SoC 改造的 SMP 实现。它支持任务绑核与非绑核调度，但双核同时访问共享数据会产生真正的并发，因此不能只靠关闭本核中断；短数据操作使用带 `portMUX_TYPE` 的自旋锁临界区，较长的任务级资源保护使用 Mutex。还要注意 ESP-IDF 创建任务的栈大小参数是字节，和原生 FreeRTOS 常见的 word 单位不同。

## 3. 任务设计与时间管理

### 3.1 创建、删除和栈

- 动态创建：`xTaskCreate()` 从 FreeRTOS 堆获取 TCB 和任务栈，使用灵活，但需关注堆空间与碎片。
- 静态创建：`xTaskCreateStatic()` 由应用提供 TCB 和栈数组，内存边界清晰，量产项目更容易保证稳定性。
- 每个任务有独立栈。栈大小参数的单位通常是 `StackType_t` 的**字（word）**，并非一定是字节；以具体端口为准。
- 使用 `uxTaskGetStackHighWaterMark()` 观察历史最小剩余栈，结合最坏路径留足余量；不要只按正常流程估算。
- 开启 `configCHECK_FOR_STACK_OVERFLOW` 并实现 `vApplicationStackOverflowHook()`，将任务名、复位原因等信息记录下来。端口支持时，方法 1 主要检查栈指针是否越界，方法 2 还检查栈边界填充值是否被覆盖；不同端口的具体实现应以 `port.c` 为准。
- **TCB（Task Control Block）** 是内核描述任务的数据结构，保存任务栈指针、优先级、状态/事件列表项等调度信息；应用不应直接修改 TCB，而应通过任务 API 操作。

### 3.2 延时与周期任务

- `vTaskDelay(ticks)`：相对延时，延时从调用 API 时开始累积。处理耗时波动会让任务周期漂移。
- `vTaskDelayUntil(&lastWakeTime, period)`：基于上一次计划唤醒点的绝对周期延时，适合固定周期采样、控制和刷新任务。
- 使用 `pdMS_TO_TICKS(ms)` 完成毫秒到 Tick 的转换，避免把毫秒直接当 Tick；实际精度受 `configTICK_RATE_HZ` 限制。
- 长耗时周期任务如果已经错过下一周期，`vTaskDelayUntil()` 可能立即返回。此时应分析任务负载，而不是误以为 API 失效。

```c
void SensorTask(void *arg)
{
    TickType_t lastWakeTime = xTaskGetTickCount();
    const TickType_t period = pdMS_TO_TICKS(10);

    for (;;) {
        ReadAndFilterSensor();
        vTaskDelayUntil(&lastWakeTime, period);
    }
}
```

### 3.3 软件定时器

软件定时器由 Timer Service Task 执行回调，适合短小、非阻塞的超时处理、状态机触发或周期性轻量工作。

- 一次性定时器：到期执行一次；自动重载定时器：按周期反复执行。
- 回调运行在同一个定时器服务任务上下文，**不能阻塞、不能做耗时 IO、不能长时间占用 CPU**，否则会延迟所有软件定时器命令与回调。
- 启动、停止、复位、改周期等定时器 API 会向**定时器命令队列**投递命令，再由 Timer Service Task 统一处理；因此要配置足够的 `configTIMER_QUEUE_LENGTH`，并检查命令投递是否成功。
- 要求更强实时性或执行时间不确定的工作，应由定时器/ISR 唤醒独立任务处理。

## 4. 任务间通信与同步

先区分目的：**通信**是传递数据；**同步**是等待事件；**互斥**是独占共享资源。选择对象时优先考虑数据量、生产者/消费者数量、是否来自 ISR，以及是否需要优先级继承。

| 对象 | 核心用途 | 关键特点 | ISR 中使用 |
| --- | --- | --- | --- |
| 队列 Queue | 传递定长数据 | FIFO，通常复制数据；可多生产者/消费者 | 用 `xxxFromISR()` |
| 队列集 Queue Set | 等待多个队列/信号量 | 一个任务可等待多个成员对象；有额外 RAM/处理开销 | 成员对象各自使用 ISR API |
| 二值信号量 | 事件同步 | 只有可用/不可用两种状态，不含优先级继承 | 可 GiveFromISR |
| 计数信号量 | 资源计数/事件累计 | 计数范围可配置 | 可 GiveFromISR |
| 互斥锁 Mutex | 保护共享资源 | 所有权概念、优先级继承 | 不可在 ISR 使用 |
| 递归互斥锁 | 嵌套调用的资源保护 | 同一任务可重复获取，释放次数必须对应 | 不可在 ISR 使用 |
| 事件组 Event Group | 多个标志位同步 | 一个或多个 bit 组合等待 | ISR 通过 `...FromISR()` 延后处理 |
| 任务通知 | 一对一轻量通信 | 每任务自带通知值，无额外对象开销 | 有 `...FromISR()` |
| 流/消息缓冲区 | 连续字节或可变长消息 | 常用于串口/网络流；通常单写者、单读者 | 有对应 ISR API |

### 4.1 队列

队列传递的是数据**副本**，发送时拷贝入队列、接收时拷贝出队列，适合传感器样本、命令、UI 消息等定长数据。队列满/空时可设置阻塞时间，避免忙轮询。

```c
/* ISR：投递事件；任务：等待并处理事件 */
BaseType_t higherPriorityTaskWoken = pdFALSE;
xQueueSendFromISR(eventQueue, &event, &higherPriorityTaskWoken);
portYIELD_FROM_ISR(higherPriorityTaskWoken);
```

不要向队列传递指向临时局部变量的指针；若传递指针，应明确对象生命周期和所有权。大块数据频繁复制会影响效率，可使用缓冲池 + 指针队列，或选择流/消息缓冲区。

**队列集**允许一个任务同时等待多个队列或信号量，收到成员对象后再用 `xQueueSelectFromSet()` 判断来源，适合组合事件等待。若只是等待多个 bit 条件，事件组通常更轻量；不要为简单场景滥用队列集。

### 4.2 信号量、互斥锁与优先级反转

- **二值信号量**：用于“事件是否发生”，典型是 ISR `GiveFromISR`，任务 `Take` 后处理。
- **计数信号量**：可表示 N 个同类资源，也可累计多个事件。
- **互斥锁**：用于保护 LCD、I2C、SPI、全局共享结构等临界资源。谁成功获取，通常就应由谁释放；持锁期间不要延时、等待队列或执行慢操作。

**优先级反转**：低优先级任务持有互斥锁，高优先级任务等待该锁；此时中优先级任务不断运行，导致低优先级任务迟迟无法释放锁，高优先级任务被间接阻塞。

FreeRTOS 互斥锁采用**优先级继承**：低优先级持锁任务会临时继承等待者中较高的优先级，尽快运行并释放锁。注意：它不是万能的；缩短持锁时间、避免复杂嵌套锁、统一加锁顺序仍是根本措施。二值信号量不具备此机制，因此不应替代互斥锁去保护共享资源。

### 4.3 任务通知：常被忽略的高效方案

每个任务有一个 32 位通知值。它不需要单独创建对象，RAM 和执行开销通常低于队列/信号量，但天然是**一对一**关系。

- 用作二值/计数事件：`xTaskNotifyGive()`、`ulTaskNotifyTake()`。
- 用作事件位或传值：`xTaskNotify()`、`xTaskNotifyWait()`。
- 典型用法：DMA/UART 中断通知唯一的处理任务；若多个独立消费者都要等待同一事件，选择信号量、事件组或队列更合适。

## 5. 中断、临界区与调度器控制

### 5.1 ISR 编程规则

1. ISR 只完成必要的硬件确认、读写寄存器、搬运少量数据或投递事件；耗时处理交给任务。
2. ISR 中**绝不能调用会阻塞的 API**，也不能调用普通任务版 RTOS API；使用带 `FromISR` 后缀的版本。
3. 传入 `pxHigherPriorityTaskWoken`。如果该 ISR 使更高优先级任务就绪，在 ISR 退出前调用 `portYIELD_FROM_ISR()`，以降低响应延迟。
4. Cortex-M 等端口还必须遵守可调用 FreeRTOS API 的 ISR 优先级限制（如 `configMAX_SYSCALL_INTERRUPT_PRIORITY`）。优先级过高的 ISR 不可调用 `FromISR` API；具体数值和优先级位定义必须以芯片端口为准。Cortex-M 常将实际任务切换延后至 PendSV 执行，从而在 ISR 退出路径中安全完成上下文切换。

### 5.2 临界区与 `vTaskSuspendAll()`

- `taskENTER_CRITICAL()` / `taskEXIT_CRITICAL()`：进入短临界区，端口通常会屏蔽一部分中断；只用于极短的共享数据操作，必须成对退出，不能在其中阻塞。
- `vTaskSuspendAll()` / `xTaskResumeAll()`：暂停**任务调度**，中断仍可响应；适合短暂保持任务级操作的原子性。期间不能调用可能阻塞的 API。
- `portDISABLE_INTERRUPTS()`：屏蔽（端口定义范围内的）硬件中断，影响系统实时性，应尽可能短。它和“挂起调度器”不是同一件事。
- 多字节变量、读改写操作或跨多个字段的一致性更新，都可能需要上述保护；是否“原子”取决于 MCU 位宽、对齐与编译器生成代码，不能仅凭 C 类型名称判断。

## 6. 内存管理

FreeRTOS 可使用静态内存，也提供多种 `heap_x.c` 作为动态分配实现。一个工程通常选择其中一种堆实现，而不是同时使用全部。

| 实现 | 特点 | 适合场景 |
| --- | --- | --- |
| heap_1 | 只分配、不释放 | 对象一次性创建且永不删除 |
| heap_2 | 支持释放，但不合并相邻空闲块，可能碎片化 | 兼容旧工程，通常不作为新项目首选 |
| heap_3 | 直接封装标准 `malloc()` / `free()` | 平台 C 库线程安全与行为可控时 |
| heap_4 | 支持释放并合并相邻空闲块 | 常用默认选择，兼顾功能与碎片控制 |
| heap_5 | heap_4 的多非连续区域扩展 | 内存分散在多个 RAM 区域 |

工程建议：优先静态创建关键任务、队列和定时器；避免在长期运行、实时路径中频繁分配释放。`heap_4` 虽能合并相邻空闲块，长期分配/释放不同大小对象仍可能产生外部碎片，不能理解为“完全无碎片”。启用 `configUSE_MALLOC_FAILED_HOOK` 并实现 `vApplicationMallocFailedHook()`；用 `xPortGetFreeHeapSize()`、`xPortGetMinimumEverFreeHeapSize()` 监控堆余量。注意：栈与 FreeRTOS 堆都是 RAM 消耗项，二者要一起评估。

### 6.1 为什么 ISR 中不能调用 `malloc` / `free`

**工程结论**：ISR 中不调用任何动态内存分配或释放函数，包括 `pvPortMalloc()` / `vPortFree()`、`malloc()` / `free()` 和 `realloc()`。中断只记录必要状态并通知任务，内存操作放到任务上下文。

| 层面 | 真正原因 |
| --- | --- |
| **原生 FreeRTOS** | 没有 `pvPortMallocFromISR()` / `vPortFreeFromISR()`。`heap_2/4/5` 等实现需要保护空闲块链表，典型做法是 `vTaskSuspendAll()` 与 `xTaskResumeAll()`；这是任务级调度器控制机制，不是 ISR API，不能从中断上下文调用。`heap_3` 又依赖 C 库 `malloc/free`，同样没有 ISR 安全和实时性保证。 |
| **实时性** | 堆分配/释放可能遍历或合并空闲块，执行时间随堆状态和碎片变化，无法给出可靠上界。ISR 被拉长会延迟其他中断和任务响应。 |
| **并发与可维护性** | 堆是全局共享结构；若绕过保护或误用非 ISR 安全实现，会造成堆损坏、野指针和随机崩溃。即使某次运行正常，也不构成可量产的正确设计。 |

**ESP32-S3 / ESP-IDF 的例外要准确理解**：ESP-IDF 的 `heap_caps` 分配器与原生 `heap_x.c` 不同；官方列出的 `heap_caps_malloc()`、`heap_caps_free()` 等接口在技术上可从 ISR 调用，但官方**强烈不推荐**，且未来版本可能移除该支持。原因仍是不可预测的分配时延。对于要求 IRAM 安全、可能发生在 Flash/PSRAM Cache 被关闭窗口内的 ISR，还不能依赖 PSRAM，也不能调用位于 Flash 的普通堆代码；此时更应使用预先准备在内部 RAM 的缓冲区。

**正确做法**：

1. 高频数据流（UART、DMA、传感器）使用预分配的静态内存池或环形缓冲区；ISR 只写入/登记索引，操作必须短且有确定上界。
2. 通用场景中，ISR 用 `xQueueSendFromISR()` 或任务通知唤醒高优先级任务；由任务申请、处理和释放动态内存。
3. 极端场景可设计独立的固定块无锁/自旋锁内存池，但它必须脱离系统堆，并经过并发和最坏时延验证，不能把 `pvPortMalloc()` 包装后直接拿到 ISR 用。

**30 秒面试回答**：原生 FreeRTOS 没有中断专用的 `pvPortMallocFromISR`。堆管理要保护全局空闲链表，常用的 `vTaskSuspendAll()` / `xTaskResumeAll()` 是任务上下文机制，不能在 ISR 使用；同时 malloc/free 的耗时受碎片影响、没有确定上界，会破坏中断实时性。ESP-IDF 虽技术上允许部分 `heap_caps` API 在 ISR 调用，但官方强烈不建议。正规做法是 ISR 只通知任务，动态内存在任务中处理；数据流则使用预分配环形缓冲区或内存池。

**额外补充**：FromISR版本和普通版本的区别？
**面试回答**：FreeRTOS 提供 FromISR 版本 API 是因为中断上下文和任务上下文不同。普通 API 可以阻塞当前任务，例如等待信号量、等待队列空间，而 ISR 中不能阻塞，因此必须使用中断安全版本。FromISR API 内部使用适合中断环境的临界区保护机制，并通过 xHigherPriorityTaskWoken 判断是否需要在退出中断后立即触发任务切换。实际开发中通常采用 ISR 快速采集数据，通过 FromISR 接口通知任务，再由任务完成复杂处理。

## 7. 常见故障定位与工程实践

### 7.1 典型问题清单

| 现象 | 常见原因 | 排查/改进 |
| --- | --- | --- |
| 高优先级任务不运行 | 被阻塞、未被事件唤醒、优先级配置错误 | 查看任务状态、队列/信号量返回值和 Tick 是否正常 |
| 随机死机/HardFault | 栈溢出、越界、错误 ISR 优先级 | 开启栈溢出钩子，检查高水位和 Fault 寄存器 |
| CPU 占用 100% | 任务轮询且没有阻塞/延时 | 改为等待队列、通知或事件；保留空闲时间 |
| 偶发卡死 | 死锁、持锁后阻塞、漏释放锁 | 统一锁顺序、限制持锁范围、设置合理超时并记录日志 |
| 中断后任务响应慢 | 未触发 ISR 末尾切换、ISR 太长 | 使用 `portYIELD_FROM_ISR()`，缩短 ISR |
| 消息丢失 | 队列满、忽略 API 返回值 | 检查返回值，评估队列深度、背压与丢弃策略 |

### 7.2 推荐配置与观测点

- 开启 `configASSERT()`：尽早发现非法 API 上下文、参数或优先级配置错误。
- 开启任务运行时间统计和 Trace（视资源而定），观察 CPU 占用与调度行为。
- 提供 `vApplicationIdleHook()` 时不可阻塞；若使用低功耗 Tickless Idle，应确认空闲钩子和外设唤醒策略。
- 队列、信号量、互斥锁的 `x...Take/Send` 返回值必须检查；超时不是“不会发生”的异常路径。
- 任务按职责拆分，而非每个小功能都建一个任务。优先级按截止时间、响应需求和阻塞关系设计，不能简单按“功能重要程度”排列。

## 8. 面试高频问答

### 8.1 FreeRTOS 如何保证实时性？

通过基于优先级的抢占式调度，让高优先级就绪任务优先执行；通过中断、队列、通知等机制及时唤醒任务。它提供的是确定性机制，最终实时性仍取决于优先级设计、最长 ISR/临界区、任务执行时间和系统负载。

### 8.2 互斥锁与二值信号量有什么区别？

互斥锁用于资源互斥，有所有权和优先级继承，不能用于 ISR；二值信号量主要用于事件同步，没有优先级继承，ISR 可以释放它。因此保护共享外设应选互斥锁，中断通知任务应选二值信号量或任务通知。

### 8.3 队列、事件组、任务通知怎么选？

传递定长数据选队列；等待多个标志组合选事件组；一个生产者唤醒一个固定任务、且只需事件/小数据时优先任务通知。要传递连续字节或可变长消息时考虑流缓冲区/消息缓冲区。

### 8.4 什么是优先级反转，如何解决？

低优先级持锁，高优先级等待，中优先级抢占低优先级，导致高优先级任务被间接拖延。FreeRTOS 的互斥锁采用优先级继承；同时要缩短临界区、避免嵌套锁并统一加锁顺序。

### 8.5 `vTaskDelay()` 与 `vTaskDelayUntil()` 的区别？

前者是相对延时，会把本次执行耗时累加到周期中；后者基于基准 Tick 做绝对周期延时，更适合固定周期任务。两者精度都受系统 Tick 分辨率影响。

### 8.6 为什么 ISR 中要用 `FromISR` API？

任务版 API 可能阻塞或依赖任务调度上下文，ISR 不具备这些条件。`FromISR` 版本专为中断设计，并允许通过 `pxHigherPriorityTaskWoken` 和 `portYIELD_FROM_ISR()` 在退出中断时立即调度被唤醒的高优先级任务。

### 8.7 如何避免死锁？

固定多个锁的获取顺序；减少锁的数量和持锁范围；禁止持锁后调用可能阻塞的接口；必要时使用有限超时、错误日志和恢复策略。超时能避免永久等待，但不能替代正确的锁设计。

### 8.8 静态创建与动态创建如何取舍？

静态创建内存由应用预留，资源上界清楚、不会因创建/删除产生堆碎片，适合关键和长期运行对象；动态创建更灵活，但要评估堆大小、失败路径和碎片风险。产品中常采用“关键对象静态化，非关键对象谨慎动态化”的组合。

## 9. 进阶原理与面试层级

### 9.1 Tickless 低功耗

启用 `configUSE_TICKLESS_IDLE` 后，当没有任务需要在短期内运行时，内核可停止周期 Tick 中断并进入低功耗状态；由外部中断或预计的下一个唤醒点恢复，再补偿经过的 Tick。它能降低空闲功耗，但需要结合芯片低功耗定时器、时钟精度、外设唤醒源以及调试器行为进行验证。

### 9.2 Cortex-M 上下文切换要点

- SysTick 常用于产生系统 Tick；SVC 可用于启动首个任务；PendSV 常用于真正的任务上下文切换。
- PendSV 可设置为较低异常优先级，因此不会在高优先级 ISR 中间切换任务；ISR 结束后再保存当前任务的 R4~R11 等软件保存寄存器、切换栈指针并恢复下一个任务上下文。
- `BASEPRI` 可用于屏蔽低于某阈值的中断而不影响更高优先级的紧急中断。`configMAX_SYSCALL_INTERRUPT_PRIORITY` 划定了“可以调用 FreeRTOS API 的 ISR”边界，配置必须与 NVIC 优先级分组及芯片实现一致。

### 9.3 RTOS 与裸机如何选型

裸机适合功能单一、时序简单、资源极小且状态机可控的产品；RTOS 适合存在多路异步事件、通信协议、GUI、存储、网络或明显并发需求的系统。使用 RTOS 的收益是结构化并发与可维护性，代价是额外 RAM/Flash、调度开销和并发同步复杂度。选型应看实时需求、资源预算、团队经验和后续维护，而非“功能复杂就一定上 RTOS”。

### 9.4 按面试阶段准备

| 阶段 | 应达到的深度 |
| --- | --- |
| 初级/校招 | 说清任务状态、优先级、队列基本使用和二值信号量的同步场景 |
| 中级 | 能解释优先级继承、heap_4 的边界、ISR 通信限制、栈溢出与死锁排查 |
| 高级/资深 | 能结合芯片说明 PendSV/SVC、Tickless、ISR 优先级边界、性能与低功耗权衡，并比较 FreeRTOS、RT-Thread、Zephyr 等方案 |

## 10. 项目表达模板

> 在项目中，我把采集、通信、业务处理和 UI 刷新按实时性拆成任务。外设 DMA/中断只做数据就绪确认，再通过任务通知唤醒处理任务；需要传递数据的模块使用队列。I2C/LCD 等共享外设由互斥锁保护，并避免持锁期间等待。周期采集用 `vTaskDelayUntil()` 保证节拍。调试阶段我打开了断言、栈溢出和 malloc 失败钩子，用栈高水位及最小堆余量确定资源边界；发现问题时优先检查任务是否阻塞、对象返回值、ISR 优先级以及是否有长临界区。

将其中的任务名称、外设、数据速率、栈余量和实际问题替换为真实项目数据，回答会比单纯背概念更可信。
