# grill-me 技能总结

> 技能链接：[grill-me（skills.sh）](https://www.skills.sh/mattpocock/skills/grill-me)
>
> 源码仓库：[mattpocock/skills](https://github.com/mattpocock/skills/tree/main/skills/productivity/grill-me)
>
> 目标：在让 AI 开始实现之前，通过一轮有针对性的追问，把需求、边界条件和关键取舍说清楚，减少“AI 做出来了，但不是我想要的”的情况。

## 第一章、先用一句话理解 grill-me

**`grill-me` 是一个让 AI 像严格的需求评审者一样持续提问的技能，用来把一个模糊的想法、方案或设计，逐步梳理成可执行的共识。**

这里的 `grill` 可以理解为“追问、拷问式澄清”，并不是让 AI 直接写代码。

它会围绕你的目标不断追问，例如：

- 这个功能最终给谁使用？
- 正常流程和异常流程分别是什么？
- 有哪些已有代码、接口或兼容性限制？
- 两种实现方案之间，优先性能、开发速度还是可维护性？
- 什么结果才算完成，如何验证？

它会按轮次推进：每轮集中询问所有前置条件已满足的问题；待这些问题的决策澄清，或能由代码库确认的问题完成核实后，再进入下一层分支，直到关键决策都能落地。

## 第二章、它有什么用

### 2.1、解决什么问题

AI 编程中常见的问题不是“不会生成代码”，而是需求本身没有说完整：

```text
用户脑中的需求                 AI 实际理解的需求
      |                                  |
      +-------- 信息未说明 / 理解不同 -----+
                                         |
                                         v
                              实现结果与预期不一致
```

`grill-me` 的作用，就是在编码前尽量补齐这段信息差。

### 2.2、适合使用的场景

| 场景 | 适合原因 |
| --- | --- |
| 新功能开发前 | 明确用户、流程、验收标准和边界，避免返工 |
| 架构或模块设计 | 比较方案取舍，提前暴露耦合、性能和扩展性问题 |
| 修改旧项目 | 结合代码库上下文确认影响范围，避免只改表面问题 |
| 需求描述比较模糊 | 将“做个登录”“优化一下性能”转成具体可执行的需求 |
| 重要决策评审 | 把隐含假设、风险和失败路径提前说出来 |

### 2.3、不太适合的场景

- 只是改一行文字、修一个明确的拼写错误等小任务。
- 需求、接口和验收标准已经写得很完整，只需要直接实现。
- 希望 AI 立刻给出代码、且不愿进行多轮问答时。

> 注意：它的价值是降低后续返工，而代价是前期需要花时间回答问题。任务越复杂、越容易理解偏差，越值得先使用。

## 第三章、它是怎么工作的

可以把使用过程理解为下面这条路径：

```text
模糊想法 / 初步方案
        |
        v
AI 按目标、用户、流程、边界、风险、验收标准持续追问
        |
        v
对需要业务决策的信息逐项回答；能从代码库确认的问题，则由 AI 先检查实际代码和上下文
        |
        v
关键决策形成共同理解
        |
        v
再进入需求文档、任务拆分或代码实现
```

它不是固定的问卷，而是会根据你的回答继续追问。每轮问题通常会编号，并附上 AI 的推荐答案；需要依赖其他未决问题的信息，会留到后续轮次再问。比如你说“要做设备参数保存”，它可能按依赖关系分轮追问：

1. 参数保存在 RAM、片内 Flash 还是文件系统？
2. 是否需要掉电保护、版本迁移和恢复默认值？
3. 参数更新频率多高，是否会影响 Flash 擦写寿命？
4. 参数读写失败时，应用应继续运行、重试还是报错？
5. 如何验证断电、满容量和参数损坏等异常场景？

这样得到的结论更接近工程上可以实施和验收的方案。

## 第四章、安装与调用

### 4.1、安装命令

在目标项目的终端中执行技能仓库提供的安装命令：

```bash
npx skills@latest add mattpocock/skills
```

该命令会进入选择流程，可按提示选择 `grill-me` 和需要安装到的 AI 编程工具。

> 前提：本机需要已安装 Node.js 与 npm。首次执行 `npx` 时通常会下载运行所需工具，因此需要网络连接。

### 4.2、在 AI 编程工具中调用

安装完成后，在支持斜杠命令的 AI 编程工具会话中输入：

```text
/grill-me
```

然后直接说出要讨论的内容，例如：

```text
/grill-me

我想给嵌入式设备增加参数持久化功能。
参数包括网络配置、设备校准值和用户设置；
请先帮我把方案和边界条件问清楚，再决定实现方式。
```

该技能被设计为**用户显式调用**：只有在你主动输入 `/grill-me` 时才开始访谈，不会因为普通聊天自动触发。

## 第五章、使用示例

### 5.1、示例：新增设备 OTA 升级功能

先不要直接说“帮我写 OTA”，而是先启动访谈：

```text
/grill-me

我要给现有 Linux 设备增加 OTA 升级功能。
设备通过 Wi-Fi 联网，升级包由服务器下发；
请先把升级流程、失败恢复和安全要求问清楚。
```

AI 可能按以下方向继续追问：

| 关注点 | 可能的问题 |
| --- | --- |
| 升级对象 | 升级的是应用、根文件系统、内核还是整个固件？ |
| 包获取 | 由设备轮询、服务端推送，还是由用户手动触发？ |
| 安全性 | 是否校验签名、哈希值、版本号和来源？ |
| 可靠性 | 下载中断、写入失败、断电或新版本启动失败后如何恢复？ |
| 存储布局 | 是否有 A/B 分区或备用镜像，空间是否足够？ |
| 验收标准 | 如何确认升级成功？失败时日志和告警如何处理？ |

在这些问题确认后，再让 AI 输出设计文档、接口定义和实现任务，通常会比直接生成代码更可靠。

### 5.2、示例：评审一个 Web 功能方案

```text
/grill-me

我要在管理后台增加“批量导出设备日志”功能。
现在还没确定导出格式、权限规则和大文件处理方式，
请从用户流程、性能、权限和异常处理角度逐项提问。
```

预期结果不是立刻得到代码，而是明确例如：

- 谁可以导出、能导出哪些设备的数据。
- 支持的时间范围、文件格式和字段脱敏规则。
- 大量日志采用同步下载还是后台异步生成。
- 导出失败、超时、重复提交时的提示与重试策略。
- 完成后如何通知用户，以及是否保留审计记录。

## 第六章、与直接提问的区别

| 方式 | 特点 | 适用情况 |
| --- | --- | --- |
| 直接让 AI 实现 | 速度快，但容易按未验证的假设开始编码 | 小改动、需求明确的任务 |
| `grill-me` 后再实现 | 前期多轮澄清，能把关键决策和边界提前暴露 | 新功能、复杂改动、架构设计和高风险任务 |

一句话建议：

> 对“我已经知道具体怎么做”的小任务，直接执行；对“我知道想达到什么效果，但细节还没想透”的任务，先用 `grill-me`。

## 第七章、相关技能

- `grill-me`：只做深度访谈，适合通用的计划、方案与决策澄清。
- `grill-with-docs`：同样进行访谈，但还会帮助沉淀项目术语、上下文文档和架构决策记录，适合长期维护的软件项目。
- `to-spec`：基于已讨论内容和代码库生成规格说明，并发布到项目问题跟踪器；首次使用前需通过 `setup-matt-pocock-skills` 配置跟踪器和标签。可放在 `grill-me` 之后使用。

推荐流程：

```text
模糊需求
   ↓
/grill-me：问清目标、边界和取舍
   ↓
规格说明 / 任务拆分
   ↓
代码实现与测试验证
```
