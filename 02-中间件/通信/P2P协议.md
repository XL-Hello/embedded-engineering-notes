# P2P 协议基础知识总结

> 目标：理解 P2P 通信为何需要信令、NAT 穿透和中继，掌握直连建立流程、常见失败原因及安全边界。

> 来源：围绕 P2P 通信主题整理的学习与项目复习笔记，仅供参考。

## 1. 先用一句话理解 P2P

**P2P（Peer-to-Peer）是让两个终端在发现对方并完成鉴权后，尽量直接交换数据的通信模式；当网络条件不允许直连时，再通过中继服务器转发。**

它不等于“完全没有服务器”。现实网络中，设备通常在路由器和 NAT 后面，仍需要服务器做设备发现、信令交换、身份认证，以及必要时的中继。

```text
设备 A ----> 信令服务器 <---- 设备 B
  |            交换地址/候选信息       |
  +------ 尝试 NAT 穿透并直连 ---------+
                 |
          成功：A <------> B
          失败：A -> TURN/中继 -> B
```

> P2P 的目标是尽量让媒体或业务数据走端到端；控制面和兜底路径仍常依赖中心服务。

## 2. 为什么公网地址不等于“能被访问”

家庭和企业网络通常通过 NAT 共享一个公网 IP。设备 A 向外发包时，NAT 会建立一条临时映射：把内部私网地址和端口映射为公网地址和端口。

```text
设备 A：192.168.1.10:5000
          |
          v
路由器 NAT：公网 IP:40000
          |
          v
互联网
```

外部主机只有命中这条映射、且 NAT 策略允许时，数据才能回到 A。陌生终端无法仅凭私网地址主动找到设备，因此 P2P 的难点通常是 NAT 和防火墙，而不是“知道对方 IP”这么简单。

## 3. P2P 建连需要哪些角色

| 角色 | 主要职责 |
| --- | --- |
| 终端/Peer | 发起或接收实际业务数据，如音视频、文件、控制命令 |
| 信令服务器 | 让双方登录、发现彼此、交换会话描述和候选地址 |
| STUN 服务 | 告知终端从外网看见的地址映射，辅助 NAT 穿透 |
| TURN/中继服务器 | 直连失败时，代替双方转发数据 |
| 鉴权服务 | 校验用户、设备、房间或一次性访问令牌 |

信令内容可以是 HTTP、WebSocket、MQTT 或自定义 TCP 协议；它不规定媒体数据必须如何传输。WebRTC 中常见把信令与 ICE/STUN/TURN 组合使用。

## 4. 典型建连流程

```text
1. A、B 分别登录信令服务，完成身份认证
2. A 请求连接 B；信令服务确认 B 在线和权限
3. 双方收集候选地址：本地地址、NAT 映射地址、中继地址
4. 经信令交换候选地址与会话参数
5. 双方同时向对方候选地址发探测包，尝试打通映射
6. 连通性检查成功：选出最优直连路径
7. 直连失败：改用 TURN/中继路径
8. 建立加密会话，传输媒体/控制数据，并持续保活
```

所谓“打洞”本质上是让两端都先向外发送，使各自 NAT 认为对方地址是允许返回流量的对象；不同 NAT 类型和企业防火墙策略下，成功率差异很大。

## 5. 直连、中继与服务器转发的区别

| 模式 | 数据路径 | 优点 | 代价 |
| --- | --- | --- |
| P2P 直连 | A <-> B | 延迟低，服务器带宽成本低 | 穿透成功率受网络限制 |
| 中继 | A -> Relay -> B | 覆盖复杂 NAT，路径可控 | 消耗服务器带宽，延迟更高 |
| 中心转发/SFU | A -> 媒体服务器 -> 多个 B | 适合多人会议和统一处理 | 架构与成本更重 |

对单路设备预览，直连优先、中继兜底常见；对多人会议、录制、审核或大规模直播，往往需要专用媒体服务器，而不是简单 P2P。

## 6. P2P 中的数据通道如何设计

建立连接后，数据通常分为两类：

| 类型 | 特点 | 例子 |
| --- | --- | --- |
| 控制数据 | 量小但不能乱序或丢失 | 云台控制、开始播放、配置命令 |
| 实时媒体 | 容忍少量丢包，更在意时效 | 摄像头预览、语音通话 |

控制数据可选择可靠有序通道；实时音视频更常选择低延迟、可反馈拥塞状态的传输方式。两类数据不要混用同一个无限排队的发送队列，否则大视频包拥塞时会拖慢停止、挂断等关键控制命令。

## 7. NAT 穿透为何会失败

常见原因：

- NAT 映射策略严格，给不同目标分配不同公网端口。
- 路由器或企业防火墙禁止 UDP，或只允许白名单流量。
- 对称 NAT、运营商级 NAT（CGNAT）使预测映射困难。
- 设备长时间无流量，映射超时失效。
- 双方网络地址或候选信息过期，或时钟/会话状态不同步。

工程上不要承诺“100% 直连”。应统计直连率、中继率、建连耗时、失败原因和地域/运营商分布，再针对性部署 TURN 节点和优化候选策略。

## 8. 保活、重连和网络切换

NAT 映射不是永久存在的，UDP 映射尤其可能很快过期。因此连接建立后需要适度保活；移动端从 Wi-Fi 切到蜂窝网络时，原地址映射会变化，通常要重新收集候选地址并重做连通性检查。

建议：

- 保活周期根据 NAT 类型、功耗和服务端负载设计，不要无意义高频发包。
- 控制面与媒体面都要有超时和状态机，避免“界面显示已连接但媒体早已断开”。
- 重连使用退避策略，避免网络故障时大量设备同时重试压垮信令服务。
- 旧会话、旧令牌和旧候选地址要有过期机制，防止串会话。

## 9. 安全不是“直连后再考虑”

P2P 直接把终端暴露给另一个终端，必须从建连前开始做安全控制：

| 风险 | 基本措施 |
| --- | --- |
| 未授权访问设备 | 设备身份认证、用户授权、短时令牌 |
| 信令被篡改或劫持 | 信令走 TLS，校验会话与候选归属 |
| 媒体被窃听 | 使用 DTLS/SRTP 或等效加密机制 |
| 重放控制命令 | 随机数、序号、有效期和签名/MAC |
| 恶意打洞/资源耗尽 | 限流、候选校验、TURN 鉴权、日志审计 |

注意：STUN 返回的是网络可见性信息，不是授权证明；拿到候选地址的对端仍必须通过身份和会话权限验证。

## 10. P2P 连接失败怎么排查

建议按状态机定位：

```text
登录失败 -> 信令失败 -> 候选收集失败 -> 连通性检查失败
-> 加密握手失败 -> 媒体建立失败 -> 运行中断开
```

检查顺序：

1. 双方是否在线、设备 ID/房间 ID 和访问权限是否正确。
2. 信令是否收到完整的会话描述与候选地址。
3. STUN 是否可访问，候选地址是否合理、是否过期。
4. UDP/TCP 是否被网络策略阻断，是否为复杂 NAT 或 CGNAT。
5. TURN 凭据、地域节点和带宽是否正常；失败时能否正确降级中继。
6. 安全握手、证书或密钥协商是否匹配。
7. 已建立后是否因 NAT 超时、网络切换或码率过高断流。

日志至少记录会话 ID、候选类型、选中链路、建连耗时、失败阶段和中继原因；不要记录长期有效密钥或完整用户隐私数据。

## 11. 面试常见问法和直白回答

### 11.1 P2P 为什么还需要服务器

> 因为两个终端通常在 NAT 后，互相不知道如何到达对方。服务器负责登录鉴权、设备发现和交换候选地址；直连失败时还要由中继服务器兜底。P2P 主要是尽量让业务数据直连，不是取消所有服务器。

### 11.2 STUN 和 TURN 的区别

> STUN 主要帮助终端发现自己映射到公网后的地址，协助尝试直连；TURN 在直连不通时实际转发媒体或数据。STUN 成本低但不能保证连通，TURN 成本高但成功率更高。

### 11.3 为什么 P2P 要做保活

> NAT 的端口映射会超时。保活让路由器持续保留映射，并让双方尽快发现断线；但周期不能过短，否则会增加功耗、流量和服务器压力。

## 12. 最简记忆版

- P2P 是尽量让终端直连传数据，不代表没有服务器。
- 信令负责发现和协商，STUN 帮助发现映射，TURN 在直连失败时中继。
- NAT/防火墙决定直连成功率，因此中继兜底、保活和重连是工程必需品。
- 控制数据和实时媒体的可靠性/时延需求不同，应分通道与队列处理。
- P2P 必须做鉴权、加密、短时令牌和审计，不能因“直连”忽略安全。
