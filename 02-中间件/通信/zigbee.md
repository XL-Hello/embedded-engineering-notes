# ZCL、APS、BZSP、UART：主控与 NCP 如何分工

> 本文基于项目代码，说明主控如何在业务 JSON、ZCL、APS、BZSP、UART 与 NCP 之间完成双向适配。内容不包含项目源码。

## 第一章、接入范围与总体架构

### 1.1、主控与 NCP 的职责边界

NCP（Network Co-Processor，网络协处理器）运行 Zigbee 协议栈，负责 MAC、网络层、路由、安全及射频收发；主控通过串行接口请求其发送数据并接收网络事件。主控不实现空口协议栈，也不直接操纵射频。

BZSP 是本项目 Host 与 NCP 之间使用的串行协议；其具体帧格式、确认和重传语义应以项目代码及对应芯片 SDK 为准。

```text
下行：业务 JSON -> ZCL -> APS -> BZSP -> UART -> NCP/Zigbee 协议栈 -> 空口 -> 子设备
上行：子设备 -> 空口 -> NCP/Zigbee 协议栈 -> UART -> BZSP 回调 -> APS/ZCL -> 业务 JSON
```

主控通常负责：

1. 将业务 JSON 翻译为正确的 ZCL 命令或属性操作；
2. 为 ZCL 补充 APS 地址、端点和发送选项；
3. 通过 BZSP 将 APS 请求提交给 NCP；
4. 将 NCP 回传的 BZSP 回调反向解码为业务 JSON；
5. 管理控制事务、重试、确认和设备状态同步。

### 1.2、分层数据模型

| 层 | 解决的问题 | 典型字段 |
| --- | --- | --- |
| 业务 JSON | 应用要设备做什么、设备当前是什么状态 | 属性名、命令名、值、业务设备标识 |
| ZCL | Zigbee 应用语义及数据表示 | Cluster、帧控制、命令 ID、属性 ID、数据类型、Payload |
| APS | 这条 ZCL 数据发送给网络中的谁 | 网络短地址、源/目的 Endpoint、Profile ID、单播/组播 |
| BZSP | 主控如何通过 UART 调用 NCP 的协议栈能力 | 请求类型、事务标识、APS 数据、串口帧校验 |

```text
业务层：属性与命令的业务含义
协议适配层：业务值 <-> ZCL Payload
Host 接口层：ZCL + APS <-> BZSP
串行驱动层：BZSP <-> UART
NCP：BZSP 接口 -> Zigbee 协议栈（APS/NWK/MAC/PHY）-> 空口
```

网络短地址是当前网络中的路由地址，可能因重新入网而变化；设备身份管理应使用 EUI64 等稳定唯一标识。`短地址 + Endpoint` 用于定位当前节点内的功能实例，而非永久设备身份。

## 第二章、下行控制：从业务请求到空口发送

### 2.1、业务路由与能力映射

以开关控制为例：

```json
{
  "ctrlType": "setProp",
  "properties": {
    "onoff": "on"
  }
}
```

业务路由器根据 `ctrlType`、属性名或命令名、目标设备类型，在能力表中找到处理器。能力表只承担“业务名称 -> 协议适配处理器”的映射；处理器的上下文至少应包含业务请求标识、当前网络短地址、目标 Endpoint 和 JSON 业务值。

### 2.2、JSON 到 ZCL 的编码

协议适配处理器决定 Cluster ID、命令或属性 ID、数据类型及 Payload。例如，`"on"` 可映射为 On/Off Cluster 的开命令；亮度百分比则需按设备能力换算为亮度命令或属性所要求的数值。

ZCL Header 同样是编码的一部分：应正确设置 Frame Control（帧类型、方向、厂商特定标志、默认响应策略）、可选 Manufacturer Code、Transaction Sequence Number 和 Command ID。属性读、写与上报配置属于 ZCL 全局命令，不能仅笼统地理解为“属性 ID”。

```c
handle_property(request) {
    value = read_json(request, "properties.example");
    payload = encode_to_bytes(value);
    send_zigbee_command(request.device, CLUSTER_ID, COMMAND_ID, payload);
}
```

业务处理器不应直接拼装 BZSP/UART 帧。

### 2.3、ZCL 到 APS/BZSP 的封装

Host 层为 ZCL 数据补齐当前网络路由信息：目标短地址、目标 Endpoint、网关源 Endpoint、Profile ID，以及单播、组播或广播等发送方式。一个物理节点可包含多个 Endpoint；多路开关或复合传感器常共享同一短地址，但不同功能位于不同 Endpoint。

随后，Host 层把 APS 参数和 ZCL 数据编码为发送 APS 数据的 BZSP 请求，并写入 UART。

```text
ZCL Header + ZCL Payload
  -> APS 参数 + ZCL 数据
  -> BZSP 发送 APS 数据请求
  -> BZSP 串口帧
  -> UART 字节流
  -> NCP
```

UART 写成功仅表示字节已提交给本机串口驱动，不代表 NCP、空口或子设备已经完成相应动作。

## 第三章、发送事务与状态闭环

### 3.1、区分各层反馈

| 反馈 | 可以证明什么 | 不能证明什么 |
| --- | --- | --- |
| UART 写成功 | 字节已提交给主控本机的串口驱动 | NCP 已收到、空口已发送、设备已执行 |
| BZSP ACK | NCP 已确认收到对应的 Host–NCP 帧 | Zigbee 消息已发送或设备已执行 |
| APS confirm | NCP 已给出该 APS 发送的栈处理结果 | 设备业务状态一定已改变 |
| 属性上报或读属性响应 | 设备报告了可解析的当前属性值 | 上层业务一定已成功持久化或消费该状态 |

具体回调名称和状态语义随 NCP 协议版本与发送 API 而变化，应以所用 SDK 的接口文档为准。应用设计上应把“请求已完成发送”与“设备状态已闭环”分开处理：

```text
控制请求 -> 发送结果或超时结果
设备上报 / 读响应 -> 最终状态同步
```

### 3.2、发送管理器

普通属性控制通常需要发送管理器，至少提供：

1. **属性目标去重**：以 `(短地址, Endpoint, 属性名)` 为键，仅保留最新期望值；
2. **重试**：在限定次数和间隔内重新提交未获可接受结果的请求；
3. **事务关联**：将业务请求标识与 BZSP 消息标签或内部发送事务关联；
4. **结果回传**：收到发送结果后回复正确的原业务请求。

属性去重与事务关联不是同一件事：前者防止旧值覆盖新值，后者确保异步结果回到正确调用方。重试前还应考虑设备休眠、幂等性和命令语义，避免对非幂等命令盲目重发。

## 第四章、上行数据：从 NCP 回调到业务状态

### 4.1、接收与协议解析

子设备主动上报、读属性响应或事件到达 NCP 后，NCP 通过 UART 回传 BZSP 数据；主控完成 BZSP 解帧和校验后，再提取 APS 参数和 ZCL 数据。

```text
子设备 -> Zigbee 空口 -> NCP
  -> UART -> BZSP 解帧与校验 -> BZSP 回调
  -> APS 解析 -> ZCL 解析 -> 属性/命令分发表
  -> JSON 转换器 -> 属性上报或事件上报
```

接收端依次完成：

1. 从 UART 读取字节，并由 BZSP 恢复有效帧、处理转义和校验；
2. 按 BZSP 回调类型区分入站 APS 数据、发送完成、入网事件和其他网络事件；
3. 从入站数据中取得 APS 参数与 Payload，并按 Profile ID 和 Cluster 解析 ZCL Header；
4. 区分 Attribute Report、Read Attributes Response 与 Cluster-specific Command。

### 4.2、ZCL 到业务 JSON 的反向映射

```text
(Cluster ID, Attribute ID, Manufacturer Code*) -> 属性转换器
(Cluster ID, Command ID, Direction, Manufacturer Code*) -> 命令/事件转换器
* 仅厂商特定属性或命令需要 Manufacturer Code。
```

转换器应按 ZCL 数据类型和字节序解码 `value[]`，并结合稳定设备标识、当前短地址及 Endpoint 组装属性或事件上报。对于 Cluster-specific Command，必须将 ZCL Frame Control 中的方向纳入路由；厂商特定命令或属性还应按 Manufacturer Code 区分命名空间。因此，新增可上报属性不能只实现下行处理器；即使多个属性复用同一通用转换器，也必须登记对应的完整协议映射。

## 第五章、私有载荷与设备建模

### 5.1、私有二进制载荷

部分设备会在厂商自定义 Cluster 或厂商自定义命令中承载二进制数据。为避免业务 JSON 与设备私有字段耦合，应维护独立映射：

```text
业务属性名 <-> 私有字段编号、类型、枚举/数值转换规则
```

下行按业务属性查映射并编码私有字段；上行按字段编号查映射并恢复业务属性 JSON。解析任何自定义二进制帧前，至少验证帧头或版本、长度、字段边界、校验和或 CRC（若协议定义）以及字段类型和值域。这些校验属于输入信任边界，不能因接入便利而省略。

### 5.2、入网、发现与逻辑建模

新节点加入网络后，不应立即作为已知设备使用。主控通常需要完成以下发现与建模工作：

1. 记录设备公告或地址查询得到的 EUI64 与当前短地址映射；
2. 读取 Basic Cluster 等基础信息，例如厂商名、型号标识和应用版本，以匹配能力配置；
3. 通过 Active Endpoints Request 获取活动 Endpoint；
4. 对目标 Endpoint 获取 Simple Descriptor，确认其 Profile、Device ID 和输入/输出 Cluster；
5. 依据能力配置创建物理节点和逻辑设备，并触发初始状态同步。

基础信息未齐全时，应先写入待生成对象，而非作为普通属性直接上报。这样设备树才能准确表达“一个物理节点 + 多个逻辑 Endpoint”的关系。并非所有设备都完整支持标准发现或基础属性读取；对于这类设备，应把降级策略明确放在设备能力配置中。

## 第六章、新能力接入与验证

### 6.1、最小闭环清单

新增 `exampleProperty` 时，至少完成以下工作：

| 方向 | 必需工作 |
| --- | --- |
| 下行 | 在能力表登记业务名称；实现 JSON -> Cluster/命令或属性/Payload 编码；调用统一 Host 发送接口。 |
| 主动读取 | 若设备支持，发送读属性请求并处理响应。 |
| 上行 | 在包含 Cluster、属性/命令、方向及厂商信息（如适用）的分发表登记；实现 `value[] -> JSON` 转换。 |
| 组控 | 如需组播，验证组地址、组成员关系和目标 Endpoint 规则。 |
| 发送结果 | 验证 BZSP 发送结果能正确关联回原业务请求。 |
| 状态闭环 | 验证属性上报或读响应能更新业务侧状态。 |

```text
exampleProperty JSON
  -> 下行编码 -> ZCL / APS / BZSP / UART / NCP
  -> 子设备 -> 上行 ZCL 数据 -> 反向转换
  -> exampleProperty JSON
```

### 6.2、分层调试顺序

当“请求已发出但设备没有动作”时，从上向下检查：

1. **业务请求**：控制类型、属性/命令名、目标设备和 Endpoint 是否正确；
2. **能力表**：是否命中目标处理器；
3. **ZCL 编码**：Cluster、命令/属性 ID、类型、Payload 和字节序是否正确；
4. **APS 路由**：短地址、源/目的 Endpoint、单播/组播是否正确；
5. **BZSP/UART**：是否形成有效 BZSP 帧并正常收发；
6. **发送结果**：是否收到对应的 BZSP 回调、APS confirm 或失败状态；
7. **状态闭环**：是否收到对应属性上报或读属性响应；
8. **空口验证**：仍无法定位时，用抓包确认 NCP 是否发出、子设备是否收到并响应。

## 第七章、子设备 OTA：Host 通知，设备拉取

### 7.1、OTA 的任务边界

OTA 不是将完整固件作为普通控制命令持续下发。代理应用层发起的是一项升级任务，典型参数包括目标
设备、目标版本、固件 URL 和完整性校验值。任务管理器负责下载、校验和排队；只有本地镜像准备完成
后，才将本地文件路径和目标节点交给 Zigbee Host。

```text
升级任务 JSON
  -> 下载固件并校验完整性
  -> 本地 OTA 镜像文件
  -> Host 解析镜像头并启动 OTA Server
  -> Zigbee OTA Cluster 交互
```

目标版本可用于任务去重、是否需要升级等业务决策；但 OTA Cluster 中用于设备匹配的厂商标识、镜像
类型、文件版本和镜像大小，应以 OTA 文件头为准。任务层版本与镜像头版本应在启动前保持一致。

本系统按引擎维护 OTA 任务队列，同一引擎在一个时刻只执行一个子设备 OTA 任务；这样可避免共享
镜像和状态机时出现分块数据串扰。

### 7.2、OTA 在四层数据模型中的位置

| 层 | OTA 中承载的内容 |
| --- | --- |
| 业务 JSON | 升级任务、目标版本、文件地址、完整性校验、进度和结果 |
| ZCL | OTA Cluster 命令、镜像标识、版本、偏移量和固件分块 |
| APS | 目标短地址、源/目的 Endpoint、Profile ID、单播和发送选项 |
| BZSP | Host 与 NCP 之间的 APS 数据请求/回调及 UART 帧 |

```text
业务 JSON（任务）
  -> 本地 OTA 文件
  -> ZCL OTA 命令和固件分块
  -> APS 路由参数 + ZCL 数据
  -> BZSP 发送 APS 数据请求
  -> UART -> NCP -> Zigbee 空口 -> 子设备
```

固件字节仅作为 ZCL OTA 分块响应的 Payload 出现；JSON 层只管理任务，APS/BZSP 只负责寻址和承载，
不解析固件内部格式。

### 7.3、OTA Cluster 的下行与反向请求时序

Host 读取并校验 OTA 文件头后，先向子设备发送 `Image Notify`，告知其存在可查询镜像。之后不是
Host 主动连续推送固件，而是由子设备按自身节奏查询和拉取：

```text
Host                              子设备
 |---- Image Notify --------------->|  通知可查询镜像
 |<--- Query Next Image Request ----|  携带当前版本、镜像类型等
 |---- Query Next Image Response -->|  返回可用镜像或“无镜像”
 |<--- Image Block Request ---------|  携带 offset 和 maxDataSize
 |---- Image Block Response ------->|  返回 offset 对应的固件分块
 |              ...                 |  重复至镜像传输完成
 |<--- Upgrade End Request ---------|  设备报告下载结果
 |---- Upgrade End Response ------->|  指定安装/重启时间
```

分块请求中的 `offset` 是续传进度。Host 必须校验镜像标识、偏移量和请求长度，从本地文件读取对应片段，
并按当前 APS 可用负载限制裁剪实际返回长度。设备主动拉取可适应休眠、接收缓冲和链路质量；也使重试
与断点续传有明确的协议依据。

从四层看，子设备的反向请求路径为：

```text
子设备 OTA Cluster 请求
  -> Zigbee 空口 -> NCP
  -> UART -> BZSP 解帧与回调
  -> APS 参数解析 -> ZCL OTA Cluster 分发
  -> OTA Server 读取本地分块并构造响应
  -> APS -> BZSP -> UART -> NCP -> 子设备
```

NCP 仍是无线协议栈黑盒；Host 负责把 BZSP/APS/ZCL 请求路由到 OTA Server，并将响应交回 NCP。

### 7.4、升级状态与成功闭环

下列结果都不能单独证明 OTA 成功：UART 写成功、BZSP ACK、APS confirm，甚至最后一个
`Image Block Response` 已返回。它们最多说明数据已经进入不同层级的发送流程，不能说明设备已完成
写入、镜像校验、安装和重启。

正确的成功闭环是：设备完成下载并发送结束请求后，Host 等待安装/重启窗口，再主动读取设备的软件
版本；只有新版本高于升级前版本，才上报 `completed` 并更新设备版本。文件读取失败、镜像校验失败、
OTA 请求校验失败、版本读取超时或版本未提升，都应上报 `failed`。

```text
分块传输完成
  -> 设备安装并重启
  -> Host 读软件版本
  -> 新版本高于旧版本：completed
  -> 读取超时/版本未提升/协议失败：failed
```

任务管理器根据设备的进度、完成或失败事件重置超时计数；在一段时间没有任何状态反馈时，按限定次数
重新执行任务。重试不能仅重复发送最后一个分块，而应重新遵循完整的 OTA 任务与设备拉取流程。

### 7.5、OTA 分层调试

OTA 卡住或失败时，可按以下顺序排查：

1. **任务层**：目标设备、目标版本、文件 URL 和校验值是否正确；文件是否已成功下载并可读取；
2. **镜像层**：文件头、镜像标识、镜像大小和版本是否有效，且与设备查询条件匹配；
3. **通知层**：是否向正确的短地址和 Endpoint 发出了 `Image Notify`；
4. **拉取层**：是否收到 `Query Next Image Request` 和 `Image Block Request`；未收到时检查设备在线、
   唤醒状态与空口；
5. **分块层**：offset、请求长度、文件读取结果、实际响应长度及 APS 负载上限是否正确；
6. **结束层**：是否收到 `Upgrade End Request`，以及安装时间响应是否正常发送；
7. **版本闭环**：重启等待后是否成功读到更高的软件版本；
8. **任务状态**：完成、失败、超时和重试次数是否与任务队列状态一致。

## 第八章、常见问题速查

### 8.1、控制与确认

**一次属性控制如何到达子设备？** 路由器按属性名在能力表中找到处理器；处理器将 JSON 值编码为 ZCL；Host 补齐 APS 参数并通过 BZSP 经 UART 提交 NCP，由 NCP 发往 Zigbee 空口。

**为什么 UART 写成功不等同于控制成功？** 它只表示本机已提交串口字节。BZSP ACK 只确认 NCP 收到 Host–NCP 帧；APS confirm 只反映一次发送请求的状态；设备上报或读响应才是状态闭环的重要证据。

**为什么普通属性控制需要发送管理器？** 它保留最新目标值、处理超时与重试，并把异步发送结果映射回原业务请求。属性去重避免旧值覆盖新值，事务关联保证结果回复给正确调用方。

### 8.2、适配与上报

**为什么同一业务能力会有标准与自定义两种编码？** 不同设备可能分别采用标准 ZCL 与厂商自定义命令。协议适配层应依能力配置选择编码，业务 JSON 不应暴露这种设备差异。

**标准属性上报如何变为业务 JSON？** 主控依次完成 BZSP 解帧、BZSP 回调解析、APS/ZCL 解析，再用 Cluster、属性 ID 及厂商信息（如适用）找到转换器，将原始值解码为 JSON 属性并归属到对应 Endpoint 的逻辑设备。

**新增一个既能控制又能上报的属性，最少要做什么？** 下行登记属性并实现 JSON 到 ZCL 的编码；上行登记完整的属性或命令路由键（Cluster、ID、方向和厂商信息，如适用），并实现 `value[]` 到 JSON 的转换。读取接口不能替代设备主动上报的处理。

### 8.3、寻址、入网与私有数据

**为什么短地址和 Endpoint 要一起使用？** 短地址定位节点当前网络位置，Endpoint 定位节点内部功能实例。稳定身份应另用 EUI64 等唯一标识维护。

**为什么自定义二进制载荷需要映射配置和完整性校验？** 映射配置负责业务属性名与私有字段间的双向转换；长度、边界和校验等验证可防止异常数据污染状态。

**新设备入网后为什么不能直接按普通设备处理？** 主控应先建立 EUI64/短地址映射、读取基础信息、发现 Endpoint 及其描述符，才可匹配能力配置、创建逻辑设备并同步初始状态。

**控制已下发但设备无动作，应如何排查？** 按“业务请求 -> 能力表 -> ZCL 编码 -> APS 路由 -> BZSP/UART -> 发送结果 -> 状态闭环 -> 空口抓包”的顺序检查。

### 8.4、OTA

**为什么 OTA 要由子设备主动请求分块，而不是 Host 持续主动推送？** 低功耗设备可能休眠，且只有
设备知道其接收缓冲与处理节奏。由设备带着 offset 主动请求分块，可适应链路质量，支持重试和断点
续传，避免主动推送面对离线、速率失配和丢包时的复杂时序。

**从升级通知到设备开始安装，关键的 ZCL OTA 交互是什么？** Host 依次参与 `Image Notify`、
`Query Next Image Request/Response`、多轮 `Image Block Request/Response` 与
`Upgrade End Request/Response`。前两步完成镜像匹配，中间多轮完成按偏移拉取，最后一步约定安装/重启
时间。

**为什么最后一个 OTA 分块已响应仍不能判定升级成功？** 分块响应只说明 Host 已提供镜像数据，不证明
设备已成功写入、校验、安装和重启。应在安装窗口后主动读取设备软件版本；只有版本高于升级前版本
才是 `completed`，读取超时、协议失败或版本未提升均应判为 `failed`。
