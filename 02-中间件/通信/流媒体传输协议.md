# 流媒体传输协议基础知识总结

> 目标：理解音视频数据从采集端到播放器的传输链路，能根据实时性、弱网、兼容性与部署方式选择 RTSP、RTP、RTMP、HLS、WebRTC 等方案。
>
> 来源：围绕流媒体传输主题整理的学习与项目复习笔记，仅供参考。

## 1. 先用一句话理解流媒体传输

**流媒体传输是把连续的音视频按时间顺序封装、分片和发送，让接收端不必等完整文件下载完就能边接收、边解码、边播放的机制。**

它解决的不是“视频文件如何保存”，而是：**数据如何准时到达、丢包或抖动时如何处理、延迟和流畅度如何权衡。**

```text
摄像头/麦克风
      |
      v
编码 H.264/H.265/AAC
      |
      v
封装与分包 FLV / TS / RTP
      |
      v
传输 RTMP / RTP / HTTP / WebRTC
      |
      v
网络抖动、丢包、带宽变化
      |
      v
接收端缓冲 -> 解封装 -> 解码 -> 音视频同步 -> 播放
```

> 关键点：低延迟不等于“没有缓冲”。播放器总要留一点缓冲来吸收网络抖动；缓冲越大越稳，但端到端延迟通常越高。

## 2. 一条流通常分哪几层

| 层次 | 主要职责 | 常见例子 |
| --- | --- | --- |
| 编码层 | 把原始音视频压缩成码流 | H.264、H.265、AV1、AAC、Opus |
| 容器/封装层 | 组织音频、视频、字幕及时间戳 | FLV、MPEG-TS、fMP4、RTP 负载 |
| 会话/控制层 | 建立、描述、控制播放会话 | RTSP、SDP、SIP |
| 传输层 | 真正承载数据 | TCP、UDP、HTTP、QUIC |
| 播放层 | 缓冲、解码、同步与渲染 | 播放器、浏览器、APP |

容易混淆的点：`H.264` 是编码格式，不是传输协议；`RTP` 主要负责实时媒体分包与时间信息，`RTSP` 常用于控制会话；`HLS` 则是基于 HTTP 的分片播放方案。

## 3. 播放器如何知道“什么时候播放”

音视频包中通常带有时间戳：

- `PTS`：展示时间戳，表示这一帧应在何时播放。
- `DTS`：解码时间戳，表示这一帧应在何时送入解码器。
- `关键帧（I 帧）`：可独立解码，是新播放器开始播放、丢包后恢复和切片边界的重要锚点。

```text
发送端：采集时间 -> 编码 -> 写入 PTS/DTS -> 发送
接收端：按时间戳排序 -> 抖动缓冲 -> 解码 -> 按 PTS 渲染
```

若网络乱序或抖动，接收端先把包放进抖动缓冲区；若等待太久仍缺包，实时场景通常宁可丢掉过期数据，也不无限等待。

## 4. 常见协议怎么选

| 方案 | 常见传输 | 延迟特点 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| RTSP + RTP | 常用 UDP，也可 TCP | 低，常见数百毫秒到数秒 | IPC、NVR 等监控生态成熟 | 浏览器原生支持弱，跨网部署复杂 |
| RTMP | TCP | 通常低延迟到秒级 | 推流成熟，服务端生态多 | 浏览器原生播放已不主流，常作上行推流 |
| HLS | HTTP/TCP | 秒级到几十秒；低延迟 HLS 可更低 | CDN、浏览器兼容、穿透防火墙好 | 分片和缓冲带来较高延迟 |
| HTTP-FLV | HTTP/TCP | 常见秒级 | 实现简单、延迟低于传统 HLS | 浏览器兼容依赖 MSE/播放器，抗弱网一般 |
| WebRTC | UDP 为主，必要时 TCP/TLS | 低，常见亚秒级 | 浏览器实时互动、拥塞控制和 NAT 穿透能力强 | 信令、TURN、运维和大规模分发更复杂 |

直白选择：

- 监控内网预览：常见 `RTSP/RTP`。
- 大规模点播或直播分发：常见 `HLS`/低延迟 HLS。
- 传统主播推流到媒体服务器：常见 `RTMP`。
- 视频通话、连麦、互动控制：优先 `WebRTC`。

> 不存在“最好协议”，只有对实时性、并发量、浏览器兼容性和网络环境更合适的方案。

## 5. RTSP、RTP、RTCP 各做什么

这三个常一起出现，但职责不同。

```text
播放器 -- RTSP SETUP/PLAY/PAUSE --> 摄像机或流媒体服务器
播放器 <-- SDP 描述编解码参数 --

媒体数据：视频/音频 -- RTP --> 播放器
质量反馈：丢包、抖动、往返时间 -- RTCP <--> 双方
```

| 协议 | 作用 |
| --- | --- |
| RTSP | 控制会话，如 DESCRIBE、SETUP、PLAY、PAUSE、TEARDOWN |
| SDP | 描述媒体类型、编码、端口、时钟频率等会话参数 |
| RTP | 给实时媒体分包，并携带序号、时间戳、负载类型 |
| RTCP | 上报接收质量、同步信息和发送统计，不直接承载媒体帧 |

RTP 序号有助于发现丢包和乱序；RTP 时间戳支持按采样时间播放。RTP 可走 UDP 以降低等待重传的延迟，也可走 TCP 以换取可靠性，但 TCP 队头阻塞可能使实时画面“越卡越晚”。

## 6. HLS 为什么适合大规模分发

HLS 把持续码流切成一系列短媒体片段，客户端先请求播放列表，再按顺序下载片段。

```text
播放器 -> 请求 m3u8 播放列表
播放器 <- 返回片段列表与码率档位
播放器 -> 请求 seg-001.ts / part-001.m4s
CDN      <- 返回媒体分片
播放器 -> 缓冲若干片段后播放
```

优点：HTTP 容易穿过代理与防火墙，CDN 擅长缓存分片，浏览器/移动端支持广。代价是播放器至少要积累若干片段，因此传统 HLS 延迟高。

降低延迟的方法包括缩短片段、使用部分片段（Low-Latency HLS）和缩短播放列表窗口；但片段太短会增加 HTTP 请求、CDN 元数据和服务器压力。

## 7. WebRTC 为什么能做实时互动

WebRTC 不是单一协议，而是一套浏览器实时通信机制，通常包含信令、ICE、STUN/TURN、DTLS、SRTP、拥塞控制和抖动缓冲。

```text
双方先通过信令交换 SDP/候选地址
      |
      v
ICE 尝试直连；STUN 获取公网映射
      |
      +-- 直连失败 -> TURN 中继转发
      |
      v
DTLS 建立密钥 -> SRTP 加密传输音视频
      |
      v
接收端根据网络反馈调整码率、帧率和分辨率
```

它的核心取舍是：优先保证“现在听到/看到”，网络不好时主动降码率、丢弃过期帧或降低分辨率，而不是无限缓存等待完整数据。

## 8. 延迟从哪里来

端到端延迟通常由多段相加：

```text
采集 + 编码 + 封装/排队 + 网络 + 接收缓冲 + 解码 + 渲染
```

常见优化方向：

- 编码端减少 B 帧、缩短 GOP，但会增加码率或降低压缩效率。
- 让关键帧间隔适合首帧时间与带宽；间隔过长会导致新加入者等很久。
- 控制播放器缓冲上限，避免网络恢复后仍播放很久以前的画面。
- 实时业务使用自适应码率和拥塞控制；不要只靠不断重传。
- 服务器转封装时避免不必要的转码，转码会明显增加延迟和 CPU 消耗。

## 9. 弱网下常见问题与处理

| 现象 | 常见原因 | 处理方向 |
| --- | --- | --- |
| 花屏、马赛克 | 丢失关键帧或参考帧 | 请求关键帧、缩短 GOP、改善丢包恢复 |
| 播放越来越慢 | 缓冲积压、TCP 重传、码率高于带宽 | 丢弃过期帧、限缓存、降码率 |
| 音画不同步 | 时间戳处理错误、缓冲策略不同 | 以音频时钟为基准，检查 PTS/DTS |
| 首帧慢 | 等关键帧、分片太长、连接握手多 | 缩短 GOP/切片，预热连接 |
| 卡顿频繁 | 带宽波动、码率固定过高 | 多码率编码与自适应切换 |

## 10. 排查流播放问题的顺序

1. 确认采集与编码是否持续产出，关键帧间隔是否正常。
2. 确认封装参数、编码参数和 SDP/播放列表描述是否一致。
3. 看发送/接收码率、丢包率、抖动、RTT 和缓冲时长。
4. 区分是网络到不了、服务器转发异常，还是播放器解码/同步异常。
5. 抓包检查 RTP 序号、时间戳、RTSP 状态码或 HTTP 分片请求。
6. 用本地文件或内网直连对比，缩小到编码、网络或播放器中的一段。

## 11. 面试常见问法和直白回答

### 11.1 RTP 和 RTSP 的区别

> RTSP 主要负责建立和控制播放会话，例如开始、暂停和结束；RTP 主要负责承载实时音视频分包，并带序号和时间戳。可以把 RTSP 理解为“遥控器”，RTP 理解为“运货通道”。

### 11.2 HLS 为什么延迟较高

> HLS 先把流切成 HTTP 片段，客户端通常要等待片段生成并缓存多个片段后播放。这样换来 CDN 友好和兼容性，但会增加切片与缓冲延迟；缩短片段能降延迟，但会提高请求和系统开销。

### 11.3 UDP 丢包为什么仍适合实时视频

> 实时视频更在意最新画面。UDP 不会像 TCP 那样因等待旧包重传而阻塞后续数据；少量丢包可能造成短暂花屏，但画面能继续向前。具体仍需通过关键帧、反馈和码率自适应处理丢包。

## 12. 最简记忆版

- 流媒体是边传边播，核心矛盾是延迟、流畅度和可靠性。
- 编码、封装、控制、传输是不同层；不要把 H.264 和 RTSP 混为一谈。
- RTP 运媒体，RTSP 控会话，RTCP 做质量反馈。
- HLS 适合 CDN 大规模分发，WebRTC 适合低延迟互动。
- 缓冲抗抖动但增加延迟；网络变差时实时业务要及时降级和丢弃过期帧。
