# 从温度上报到云端上报：一步步理解 QP

假设你正在做一台 RFID 设备网关。它通过串口连接读写器，接收后台的盘点命令，把识别到的标签上报到云端，还要处理读写器掉线、响应超时和网络重连。

最初，为串口、设备管理和云端通信各建一个任务，程序很快就能运行。后来需求增加：正在盘点时收到停止命令怎么办？读写器断开时，谁负责清理状态？上一次请求超时以后，它的迟到响应还能不能使用？任务数量没有增加多少，状态标志、回调和模块间依赖却越来越难理清。

我们就从这台网关出发，理解 **QP（Quantum Platform）怎样用 Active Object、事件和层次状态机组织程序**。前 3 章建立模型，第 4、5 章处理等待与模块通信，第 6 章选择运行方式，第 7、8 章落到工程验证和适用边界。文中的事件名称和状态图是案例约定，代码用于说明职责，不是可直接编译的完整 QP 工程。

## 第 1 章 从一台网关出发：应用需要怎样组织

先不急着记 QHsm、QActive 和 QF。我们的网关需要把硬件输入、控制命令、业务状态和超时处理接起来。理解 QP，要先看清这些工作之间的关系。

### 1.1 已经有任务和队列，为什么还需要应用框架？

在 FreeRTOS 项目里，可以先这样划分任务：

```text
readerTask   → 接收串口数据
deviceTask   → 管理设备状态
uploadTask   → 向云端上报
timerTask    → 处理超时
controlTask  → 接收控制命令
```

任务之间通过队列、信号量、互斥锁或事件组协作。这些机制本身没有问题，但它们不会自动回答业务层的问题：读写器当前状态由谁修改，停止命令交给谁，失败以后由谁决定重试？

例如，串口回调把全局变量改成“盘点中”，控制任务又把它改成“停止中”，定时器回调同时判定超时。即使每次修改都加了锁，几次操作的业务顺序仍可能不符合预期。锁能保护一次访问，却不能替团队定义完整的状态变化规则。

这里需要补上的，是**模块职责、状态所有权和异步协作规则**。用 FreeRTOS 也能建立这样的架构；QP 则把一套明确的组织方式做成了可复用框架。

### 1.2 QP 在程序中承担什么角色？

QP 由 Quantum Leaps 开发，官方称它为 **Real-Time Event Framework，实时事件框架**。它为嵌入式应用提供 Active Object 模型及运行基础，并支持用层次状态机描述对象行为。可以先把它理解为：

> **QP 用事件连接模块，用状态机表达行为，再由框架安排这些模块运行。**

Quantum Platform 中的 Platform 指这套软件基础。它不是芯片平台，也不负责替代 STM32Cube 一类硬件初始化与 BSP 工具。

在本文网关里，先划分三个业务对象：

| 模块 | 负责什么 | 自己维护的数据 |
| --- | --- | --- |
| Reader AO | 控制读写器、管理盘点与响应超时 | 读写器状态、当前操作、重试次数 |
| Device AO | 汇总标签、处理设备级业务规则 | 标签记录、设备配置、业务状态 |
| Cloud AO | 管理云端连接与数据上报 | 连接状态、待上报数据、重连进度 |

AO 是 Active Object 的缩写。接下来会看到，它不仅是给模块换一个名字，还规定了模块接收工作和修改自身状态的方式。框架定位可对照 [QP/C 官方概述](https://www.state-machine.com/qpc/)。

### 1.3 QP 与 FreeRTOS 怎样配合？

从熟悉的 RTOS 角度看，两者的关注点可以这样对照：

| 关注点 | FreeRTOS 提供的基础机制 | QP 采用的组织方式 |
| --- | --- | --- |
| 并发工作 | Task 与任务调度 | Active Object 与事件处理 |
| 模块协作 | Queue、Semaphore、任务通知等 | 定向事件、发布/订阅 |
| 业务状态 | 由应用自行组织 | 通过状态机集中描述 |
| 等待与定时 | 阻塞等待、软件定时器等 | 等待状态与 Time Event |

这个对照用于理解分工，不代表 FreeRTOS 不能写状态机，也不代表 QP 只是一层消息队列。QP 自带可选内核，也可以通过相应移植层运行在第三方 RTOS 上。

因此，网关可以采用“业务 AO → QP → 自带内核 → MCU”，也可以采用“业务 AO → QP 的 RTOS 移植层 → FreeRTOS → MCU”。是否保留现有 RTOS，要等第 6 章结合驱动和时序要求判断。官方的运行方式说明见 [QP 产品页的独立运行与 RTOS 集成部分](https://www.state-machine.com/products/qp)。

## 第 2 章 跟着一次盘点命令，认识 Active Object

现在后台发来一条“开始盘点”命令。先不讨论它怎样经过网络协议，假设控制入口已经解析出业务要求。我们跟着这条要求走到读写器，看看 AO 怎样接收和处理工作。

### 2.1 谁可以修改读写器的状态？

把 Reader 设计成 Active Object，意味着它拥有自己的状态、私有数据和事件队列，并由框架提供执行安排。可以画成：

```text
Reader AO
├── 状态机：OFFLINE / STARTING / IDLE / INVENTORY / ERROR
├── 私有数据：当前操作、重试计数、读写器配置
├── 事件队列：等待处理的命令、响应与超时
└── 执行安排：由所选内核或 RTOS 移植层提供
```

这里最重要的约定是：**读写器的业务状态由 Reader AO 自己修改。** Device AO 想启动盘点，就向它发送请求，不直接写入它的内部状态。

例如，下面这样的跨模块修改，会绕过 Reader 的状态规则：

```c
/* 反例：其他模块直接修改 Reader 的内部状态。 */
reader->state = INVENTORY;
```

换成事件以后，接收者有机会结合当前状态决定是否执行：

```text
Device AO
    │ START_INVENTORY_SIG
    ▼
Reader AO 的事件队列
    │ 框架取出并分派事件
    ▼
Reader 当前状态的处理逻辑
    │ 检查条件、启动操作
    ▼
更新自身状态并返回
```

如果 Reader 仍然离线，它可以拒绝请求并报告原因；如果已经在盘点，可以按约定忽略重复命令或返回当前结果。发送方不再替接收方决定内部状态。

AO 的执行上下文也不能简单理解成“每个 AO 必须独占一个 RTOS 线程和栈”。具体实现取决于运行内核。Active Object 抽象及事件队列的约定见 [QP/C Active Objects](https://www.state-machine.com/qpc/srs-qp_ao.html)。

### 2.2 一条事件里需要带什么？

事件表达“发生了什么”或“希望做什么”。其中 **Signal** 标识事件种类，必要时还可以附带参数。本例可以先约定：

| Signal | 含义 | 可携带的业务参数 |
| --- | --- | --- |
| `START_INVENTORY_SIG` | 请求启动盘点 | 请求编号、盘点模式 |
| `STOP_SIG` | 请求停止当前操作 | 请求编号 |
| `READER_READY_SIG` | 读写器初始化完成 | 初始化结果 |
| `TAG_REPORT_SIG` | 收到标签数据 | 标签标识、信号强度等 |
| `TIMEOUT_SIG` | 当前等待到期 | 由状态及当前操作识别其用途 |
| `DISCONNECT_SIG` | 读写器连接失效 | 错误原因 |

命名由项目约定，QP 不会根据 `START_INVENTORY_SIG` 自动生成串口命令。具体硬件动作仍由应用调用驱动完成。

事件入队也只是一个中间结果。**投递成功、开始处理、硬件执行完成，是三个不同的时刻。** Device AO 如果需要知道盘点是否真正启动，就应等待 Reader 报告业务结果，不能把发送成功当作执行成功。

同样，发送方不能在事件入队后随意修改接收方尚未读取的数据。事件携带的数据必须在整个使用期间有效；第 5 章再讨论事件池和缓冲区寿命。

### 2.3 从标签识别到云端上报，模块怎样连接？

读写器报告标签以后，Reader AO 负责协议和设备层处理，Device AO 负责业务整理，Cloud AO 负责上传：

```text
读写器 / 串口驱动
        │ 接收完成通知
        ▼
    Reader AO
        │ TAG_REPORT_SIG
        ▼
    Device AO
        │ DEVICE_DATA_SIG
        ▼
     Cloud AO
        │ 网络协议与发送接口
        ▼
       云端
```

这张图描述的是职责和事件流。串口接收可以来自中断、DMA 完成回调或驱动任务；如何把通知接入 QP，需要遵守所用移植层的接口约束。

模块内部仍然可以调用普通函数，例如解析一帧数据、计算校验和、构造上报内容。需要通过事件协调的是跨 AO 的异步工作和状态变化，不必把每个辅助函数都拆成一个对象。

现在我们知道了“工作交给谁”。接下来还要解决“同一个对象在不同阶段怎样处理工作”，这就需要状态机。

## 第 3 章 从平铺状态到层次状态机：把行为放回上下文

读写器空闲时收到开始命令，应启动盘点；盘点中收到同一命令，可能应报告忙；离线时则应报告不可用。事件的含义要结合当前状态理解。

### 3.1 为什么几个状态标志不够直观？

如果分别使用 `connected`、`starting`、`inventory` 和 `error` 等布尔变量，程序就需要不断判断它们能否同时成立。某个异常分支少清理一个标志，便可能出现“已经离线但仍显示盘点中”。

状态机把允许的阶段和变化条件集中起来。本例先约定：

```text
OFFLINE  --CONNECT_SIG-->          STARTING
STARTING --READER_READY_SIG-->     ONLINE.IDLE
IDLE     --START_INVENTORY_SIG-->  INVENTORY
INVENTORY --STOP 完成通知-->       IDLE
```

这里每条箭头都需要实际的事件或条件，不能把 `IDLE → INVENTORY → ERROR` 当作设备必然依次经过的流程。`ERROR` 是异常分支，具体恢复方式由错误类型决定。

状态也要与驱动承诺一致。如果停止命令发出后，读写器还需要一段时间才能停止，那么应增加 `STOPPING` 等待状态，收到完成通知后再回到 `IDLE`，不能只因串口发送成功就宣告已经停止。

### 3.2 多个状态都要处理断开，怎样减少重复？

在平铺状态机中，`IDLE`、单次盘点、连续盘点等状态可能都要处理读写器断开。把同一段清理代码复制多次，以后增加一种工作模式时就容易漏改。

**Hierarchical State Machine，HSM，层次状态机**允许把这些状态归入共同的父状态：

```text
Reader
├── OFFLINE
├── STARTING
└── ONLINE
    ├── IDLE
    ├── INVENTORY
    │   ├── SINGLE_INVENTORY
    │   └── CONTINUOUS_INVENTORY
    └── ERROR
```

这是一张包含关系图。处于 `CONTINUOUS_INVENTORY` 时，也处于父状态 `INVENTORY` 和 `ONLINE`。本例中 `ONLINE.ERROR` 表示连接仍在、业务操作发生错误；如果物理连接已经失效，应转到 `OFFLINE`。

子状态没有处理的事件，可以交给父状态处理。因此 `ONLINE` 可以集中处理 `DISCONNECT_SIG`，统一退出在线工作并转入离线。关闭、配置变更等行为，也可以在确实适用于全部子状态时放到这里；需要特殊处理的子状态仍可自行处理。

这样就不必在各处分散维护类似下面的条件：

```c
/* 平铺判断的示意。 */
if (state == IDLE || state == SINGLE ||
    state == CONTINUOUS || state == ERROR) {
    /* 重复的在线状态公共处理 */
}
```

HSM 的价值在于复用公共行为，并明确行为的适用范围。父子状态处理及状态迁移语义见 [QP/C State Machines](https://www.state-machine.com/qpc/srs-qp_sm.html)。

### 3.3 进入和退出状态时，哪些动作应放在一起？

等待读写器启动时，通常要启动超时计时；等待结束时，要停止该等待对应的计时。把动作与状态的进入、退出关联起来，可以减少成功和失败分支中的重复清理。

例如，本例可以规定：

| 状态 | 进入时 | 处理的关键事件 | 退出时 |
| --- | --- | --- | --- |
| `STARTING` | 启动初始化操作并设置等待超时 | 就绪、失败、超时、取消 | 解除初始化等待的定时安排 |
| `IDLE` | 报告可接收新盘点 | 开始盘点、配置变更 | 按业务需要执行清理 |
| `INVENTORY` | 建立本次盘点上下文 | 标签报告、停止、操作错误 | 清理本次操作资源 |
| `ONLINE` | 建立在线阶段所需上下文 | 子状态未处理的断开等公共事件 | 统一清理在线资源 |

这张表是设计草案，不是框架自动执行的业务规则。调用驱动失败以后转到哪里、什么条件才算在线，都需要应用定义。

父状态还需要明确初始子状态。例如进入 `ONLINE` 后默认进入 `IDLE`；进入 `INVENTORY` 后根据盘点模式选择单次或连续盘点。到这里，命令、当前阶段和清理责任已经能放在同一张图里理解。

## 第 4 章 硬件还没完成：用等待状态和时间事件继续工作

读写器初始化需要时间，串口请求也不一定立即收到响应。如果每次等待都把事件处理函数挂住，Reader AO 就难以及时处理后续停止或断开事件。

### 4.1 Run-to-Completion 要求一次处理做到哪里？

QP 的 AO 采用 **Run-to-Completion，RTC，运行至完成**的事件处理方式。对同一个 AO，当前事件处理结束后，才继续分派下一条事件。

这里的“完成”指本次事件处理步骤结束，不要求一条事件里完成整个硬件业务。以启动读写器为例，可以分成两次处理：

```text
第一次：收到 CONNECT_SIG
    → 发起异步初始化
    → 进入 STARTING
    → 返回

第二次：收到 READER_READY_SIG
    → 检查初始化结果
    → 进入 ONLINE.IDLE
    → 报告就绪并返回
```

事件处理应有界、尽量短，并避免阻塞等待。例如下面的写法会让当前 AO 无法继续处理队列中的事件：

```c
/* 反例：在事件处理函数里等待硬件就绪。 */
case START_SIG:
    while (!reader_ready()) {
        sleep(100);
    }
    break;
```

更合适的思路是：**把等待本身表达成状态，把等待结束表达成另一条事件。** 这需要驱动提供异步操作或由其他执行单元完成阻塞工作，再报告结果。

RTC 也不等于“CPU 全程不能被抢占”。使用抢占内核时，高优先级 AO 可以先运行；关键是同一个 AO 不会因为下一条事件到达，就重入当前事件的处理过程。

### 4.2 不调用 delay，500 ms 超时怎样实现？

QP 提供 **Time Event，时间事件**。AO 可以安排一次性或周期性的超时，到期后由框架把对应事件送入它的队列，随后按普通事件处理。其基本机制见 [QP/C Time Management](https://www.state-machine.com/qpc/srs-qp_tm.html)。

假设 Reader 发出一个请求，要求在约 500 ms 的业务窗口内得到响应：

```text
发送请求
    ↓
WAIT_RESPONSE，并安排超时
    ├── RESPONSE_SIG → 验证响应 → SUCCESS
    └── TIMEOUT_SIG  → 检查次数 → RETRY 或 ERROR
```

在等待期间，Reader 没有停在 `sleep()` 里，可以继续处理取消和断开等事件。原来写成“发送、阻塞等响应、失败后重试”的流程，就变成了几个有明确入口和出口的阶段。

Time Event 依赖工程提供的时钟 tick 服务。把 500 ms 换算成多少 tick，要结合实际时钟频率和取整规则；到期后还存在入队、调度和处理延迟，不能把时间事件理解成处理函数一定在第 500 ms 精确执行。

### 4.3 超时与响应先后到达，怎样避免处理错对象？

把等待写成状态以后，还要处理事件之间的竞争。比如请求已经超时并开始重试，上一次响应这时才到达；或者响应已经入队，超时事件也紧跟着入队。

本例至少需要明确三条规则：

1. 离开等待状态时解除对应的定时安排，同时让后续状态能识别并处理已经排队的无效超时。取消计时不能被当作自动删除所有已入队事件。
2. 响应必须与当前操作匹配。有请求序号就核对序号；协议不能区分请求时，应结合串行化、保护间隔等约束设计恢复流程。
3. 重试必须有上限，超过上限后报告失败并进入约定状态。连续重试不能让停止命令永久失去处理机会。

例如，Modbus 请求等待、重试间隔、迟到响应隔离、黑名单和熔断，都可以分别表达为状态、计数及迁移条件。它们的具体规则由业务和通信协议决定，QP 负责提供事件与状态机的运行基础。

有了这些约定，一次等待才不仅是“定时器到了跳转”，而是能够说明成功、取消、失败和恢复的一段业务过程。

## 第 5 章 模块开始协作：事件路由与内存边界

现在 Reader 能独立处理一次盘点。接下来让 Device 和 Cloud 加入：有的消息只交给一个模块，有的变化需要通知多个模块。通信方式要与接收关系一致。

### 5.1 定向投递与发布/订阅怎样选择？

Device 请求 Reader 开始盘点，接收者明确，适合直接投递。网络断开时，Device、Cloud 和界面可能都关心这个变化，则可以使用发布/订阅：

```text
连接管理入口发布 NETWORK_DOWN_SIG
                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
       Device AO Cloud AO  UI AO
```

发布者报告发生的事情，提前订阅该信号的 AO 各自决定怎样响应。Device 可以调整业务，Cloud 可以进入恢复流程，UI 可以显示离线。

| 情况 | 本例采用的方式 | 需要明确的规则 |
| --- | --- | --- |
| 请求 Reader 执行一次操作 | 定向投递 | 谁负责执行，怎样报告成功或失败 |
| 报告网络已经断开 | 发布/订阅 | 哪些 AO 订阅，各自怎样响应 |
| 函数内部计算校验和 | 普通函数调用 | 输入输出和执行时间 |

发布/订阅并不意味着所有 AO 自动收到，也不保证订阅者同时运行。接收对象仍通过各自队列和调度机制处理事件。QP 的这些事件发生在本地应用中，不能直接等同于 MQTT 的网络主题、Broker 或交付等级。事件交付接口见 [QP/C Event Delivery Mechanisms](https://www.state-machine.com/qpc/srs-qp_edm.html)。

### 5.2 事件已经入队，数据还能放在局部变量里吗？

假设串口回调用局部数组保存一条标签，再把数组地址放进事件。回调返回以后，Reader 可能尚未处理该事件，数组的有效期却已经结束。队列里有一条消息，不代表消息引用的数据仍然有效。

类似问题也会发生在 DMA 接收缓冲区：接收方还没有读完，驱动就开始覆盖下一帧。设计事件时，应优先让所需参数随事件保存，并遵守框架的所有权规则。

QP 支持静态事件，以及通过事件池管理的动态事件。这里的动态事件池不应简单等同于每条消息都调用通用堆的 `malloc/free`。发送、发布和后续回收有配套规则，应用不能在投递以后继续任意修改或自行释放事件。具体机制见 [QP/C Event Memory Management](https://www.state-machine.com/qpc/srs-qp_emm.html)。

对本例，可以先把标签内容复制到有界的事件参数里。若数据很大，需要专门的缓冲区方案，则必须另外定义所有权、使用期限和释放责任，不能仅靠一个裸指针传递约定。

### 5.3 队列满了，能否继续发送？

RFID 连续盘点可能在短时间内产生大量标签。如果 Cloud 上传速度慢于标签到达速度，事件驱动同样会积压。框架不会凭空提供无限队列或无限内存。

在工程设计中，至少要区分：

| 数据或事件 | 可以采用的处理方向 | 不能默认成立的假设 |
| --- | --- | --- |
| 可被替代的状态快照 | 合并或保留最新值 | 每个历史值都必须无限排队 |
| 需要保留的标签记录 | 有界缓存、批量处理、必要时限制采集 | 入队成功就等于云端保存成功 |
| 停止、断开等控制事件 | 为相关队列与资源预留足够容量，验证最坏延迟 | 提高 AO 优先级就能跳过队列中的全部旧消息 |
| 无法继续接受的数据 | 按约定拒绝、降级并记录原因 | 队列满时静默丢弃也算成功 |

采用哪些策略取决于产品是否允许丢数据。具体 API 在资源不足时是返回失败还是触发框架断言，也要查清所用版本和调用方式。

因此，减少共享状态可以降低一类并发复杂度，但事件容量、缓冲寿命和失败处理仍然是应用必须承担的工作。

## 第 6 章 让这些对象运行：选择内核与产品版本

前面的模型回答了“模块怎样协作”。现在需要决定它们在哪里运行：小型裸机系统、需要抢占的实时系统，还是已经集成大量阻塞驱动的 RTOS 工程。

### 6.1 QP 的各层怎样接起来？

把网关放回完整软件栈，可以得到下面的关系：

```text
应用：Reader AO / Device AO / Cloud AO
                  │
QP：状态机、AO 管理、事件队列、发布/订阅、时间事件、事件池
                  │
运行支持：QP 自带内核，或第三方 RTOS / 主机 OS 移植层
                  │
平台支持：BSP、驱动与硬件适配
                  │
                 MCU
```

这是职责分层示意，具体工程中 BSP 和驱动也可能由应用直接调用。QP 不会替你实现全部外设驱动，网络协议栈和硬件访问仍要与相应平台集成。

主机移植可以帮助先验证事件和状态变化，板端移植则需要结合中断、时钟、驱动和调度规则。两者验证的范围不同，主机测试通过以后仍要检查真实硬件时序。

### 6.2 QV、QK 与 QXK 有什么区别？

QP 提供不同的运行内核。先看它们对事件处理和阻塞代码的影响：

| 内核 | 运行特点 | 对本例的影响 |
| --- | --- | --- |
| QV | 非抢占式，协作运行 AO | 当前事件处理结束后，再选择就绪 AO；每次处理耗时直接影响其他 AO 的等待 |
| QK | 抢占式，按优先级执行 RTC 工作 | 高优先级 AO 可以抢占低优先级 AO，AO 处理仍应非阻塞且有界 |
| QXK | 双模式，支持非阻塞 AO 与可阻塞扩展线程 | 可以结合事件驱动业务与需要阻塞等待的线程 |

QV 的“非抢占”指 AO 之间的调度，不代表关闭硬件中断。QK 能抢占，也不代表在普通 AO 事件处理函数里调用阻塞接口就变得合适。QXK 提供的阻塞能力有明确的线程类别和 API 边界。

如果需要可阻塞线程，可以采用 QXK 的相应模式，或使用第三方 RTOS 移植方案。具体组合要检查所选框架版本、处理器与工具链的移植支持；内核名称不意味着任意平台组合都可直接使用。三种模式可对照 [QP/C ARM Cortex-M 移植说明](https://www.state-machine.com/qpc/arm-cm.html)。

对网关而言，若串口操作已经异步化、每次处理都很短，可以从简单的运行方案验证；若存在严格的高优先级响应要求，再分析抢占方案；若现有网络库大量使用阻塞接口，保留 RTOS 或引入专门线程往往需要更少的适配工作。

### 6.3 QP/C、QP/C++、SafeQP 与 QP-nano 怎样理解？

语言和产品版本与内核选择是不同维度。先根据工程语言与产品要求理解它们的定位：

| 产品 | 定位 | 工程中需要核对什么 |
| --- | --- | --- |
| QP/C | 面向 C 应用的框架 | 编译器、接口版本、目标平台移植 |
| QP/C++ | 面向 C++ 应用的框架 | 语言标准、工具链和现有代码适配 |
| SafeQP/C、SafeQP/C++ | 面向功能安全的版本与配套材料 | 所需安全功能、认证材料和项目适用条件 |
| QP-nano | 面向资源受限小型 MCU 的历史精简框架 | 官方已提示逐步退出，不推荐新产品采用 |

QP-nano 的维护定位见 [QP-nano 官方说明](https://www.state-machine.com/qpn/)。阅读旧资料时，要将它与当前主要产品区分；不能仅凭“8 位 MCU、RAM 小”就把它作为新项目的默认选择。标准版本与 SafeQP 的关系可查阅 [QP/C++ 产品版本概述](https://www.state-machine.com/qpcpp/)。

资源占用也不能只看一个框架宣传数字。完整网关的预算至少包括框架代码、应用状态机、AO 数据、事件队列、事件池、栈、驱动缓存与网络协议栈。旧资料中的几 KB ROM、约 KB 级 RAM 只能帮助建立量级认识，不能作为某个版本或完整工程的固定占用承诺。

确定运行方式后，应对目标编译配置查看链接映射文件，再测量栈余量、队列峰值和事件池使用情况。这样得到的数字才适合用于本项目预算。

## 第 7 章 从状态图到可验证程序：建模、追踪与测试

状态图画得清楚，还要确认程序确实按图运行。QP 的配套工具覆盖模型、运行轨迹和自动化测试，可以围绕同一次盘点流程逐步接入。

### 7.1 QM 怎样把状态模型连接到代码？

**QM（QP Modeler）**是配套的图形化建模与代码生成工具。可以在模型中描述状态、事件处理与迁移，再生成相应代码：

```text
QM 中的状态模型与业务动作
            ↓ 生成代码
        QP 应用程序
            ↓ 链接框架与平台支持
      在主机或 MCU 上运行
```

例如先画出 `OFFLINE → STARTING → ONLINE.IDLE`，再为连接、就绪和失败补齐事件与动作。这样模型能成为实现的一部分，而不是一张与代码逐渐脱节的介绍图。

不过，QM 不会替应用决定“什么结果才算初始化成功”，也不会自动实现驱动、超时策略和缓存规则。生成的状态框架与手写业务动作需要共同维护。工具功能见 [QM 官方说明](https://www.state-machine.com/products/qm)。

入门也可以先阅读手写状态机实现，再学习模型生成。关键是理解状态和事件语义，使用 QP 并不要求先掌握完整的图形化工具流程。

### 7.2 收到命令却没有盘点，怎样沿轨迹排查？

单看一条“已收到开始命令”的日志，无法知道事件有没有送到 Reader、当时处于什么状态、驱动有没有完成。需要把观察点放在整条处理路径上。

QP/Spy 提供软件追踪机制，目标端记录运行信息，主机端 **QSPY** 接收并解析。结合相应配置，可以观察事件投递、分派、状态迁移、时间事件和调度等活动。机制见 [QP/Spy 官方说明](https://www.state-machine.com/qtools/qpspy.html)。

例如，期望观察到下面这样的业务过程。这里是便于阅读的示意记录，不是工具原始输出格式：

```text
Reader：IDLE 收到 START_INVENTORY_SIG
Reader：发起盘点操作，进入 INVENTORY
Reader：收到 TAG_REPORT_SIG，交给 Device
Device：整理数据，交给 Cloud
Cloud ：提交上传，随后取得发送结果
```

出现异常时，按断点检查：

| 现象 | 优先查看的证据 |
| --- | --- |
| 控制入口有日志，Reader 没反应 | 投递目标、事件信号、队列容量、AO 是否运行 |
| Reader 收到事件但没有执行 | 当前状态、迁移条件、是否被父状态处理或按规则忽略 |
| 已进入等待状态但始终不超时 | 时间事件是否启动、tick 是否服务、接收 AO 是否正确 |
| 超时明显晚于预期 | 队列积压、事件处理耗时、优先级与调度延迟 |
| 偶发错误标签或数据损坏 | 事件参数、缓冲区寿命、DMA 是否覆盖、事件所有权 |
| 断开后仍显示盘点中 | 断开事件路径、父状态公共处理、退出动作与状态上报 |

追踪同样有配置和传输成本，需要合理选择记录范围、缓冲与输出方式。目标是得到能够解释行为的证据，而不是在每个实时路径里无限增加串口打印。

### 7.3 怎样验证成功、失败和恢复分支？

**QUTest** 是基于追踪的测试工具，可以控制输入并检查输出轨迹，适合验证事件驱动代码、状态机和 AO 的行为，也能用于其他嵌入式 C/C++ 代码。其测试结构见 [QUTest 官方说明](https://www.state-machine.com/qtools/qutest.html)。

对这台网关，先围绕关键业务规则设计测试，比只验证某个事件处理函数被调用更有价值：

| 场景 | 输入过程 | 需要验证的结果 |
| --- | --- | --- |
| 正常启动 | 连接 → 就绪 → 开始盘点 | 状态按约定变化，只启动一次操作 |
| 初始化失败 | 连接后失败或超时 | 资源被清理，调用方取得失败结果 |
| 重复命令 | 盘点中再次要求开始 | 按约定报告忙或当前结果，不重复启动 |
| 盘点中断开 | 盘点 → 断开 | 返回离线，在线资源得到清理 |
| 超时后迟到响应 | 请求超时 → 旧响应到达 | 旧响应不被当作新操作的结果 |
| 压力与恢复 | 标签突发、网络变慢、随后恢复 | 队列和事件池行为有界，按约定保留或拒绝数据 |

纯业务状态逻辑可以先在主机验证，再上板检查中断、驱动和实际时间。测试输入应覆盖响应与超时的不同到达顺序，尤其要验证错误分支能否回到可继续工作的状态。

## 第 8 章 接回现有工程：适用边界与迁移路径

经过前面的案例，QP 的作用已经落在具体工作上：Reader 管理自身状态，Device 汇总业务，Cloud 管理上传，模块通过事件协作。是否采用它，还要看项目的主要复杂度在哪里。

### 8.1 哪些问题适合用 QP 建模？

QP 适合持续响应外部输入、状态与时序相互影响的系统，也就是 **Reactive System，响应式系统**。设备控制、通信协议、网络连接、工业控制、汽车电子和智能家居中的许多控制逻辑，都有这类特征。

本例中的盘点、停止、断开、超时和恢复，正适合用“当前状态 + 事件 → 动作与下一状态”描述。状态明确以后，公共处理可以集中，输入顺序也更容易形成可重复的测试。

纯算法、DSP、图像处理或长时间同步计算，则不必为了采用 QP 而全部改写成状态机。这些代码可以保留为计算模块，再由控制层决定何时启动、怎样取得结果。长运算需要考虑分段或独立执行，避免长期占住一个 RTC 步骤。

### 8.2 团队需要承担哪些成本？

首先是概念学习。接触工程时，可以按职责认识常见名称：

| 名称 | 阅读代码时先关注什么 |
| --- | --- |
| `QActive` | AO 的定义、启动、优先级和事件队列 |
| `QHsm` | 层次状态机及其事件处理 |
| `QEvt`、`QSignal` | 事件结构与事件种类 |
| `QF` | 框架运行和相关服务 |
| `QTimeEvt` | 时间事件的初始化、启动与解除 |
| `QV`、`QK`、`QXK` | 当前工程采用的运行模式 |

其次是协作规则。团队需要遵守状态所有权、事件契约、短且有界的处理步骤，以及清楚的失败反馈。若仍然允许任意模块直接改别人的内部变量，套上 AO 名称也很难获得预期收益。

最后是现有代码适配。阻塞式驱动、同步网络库和共享缓存不一定能直接放进普通 AO。要逐一决定改成异步接口，还是留在专门线程中，通过事件连接到业务对象。学习与迁移成本应和实际减少的复杂度一起评估。

### 8.3 从现有 FreeRTOS 网关开始，第一步做什么？

不必一开始就替换整个系统。先选读写器控制这条边界明确、状态较多的链路：

1. 列出当前状态、外部事件和允许的迁移，明确谁拥有读写器状态。
2. 把开始、停止、响应、超时和断开整理成事件契约，补齐操作结果反馈。
3. 检查所有等待，把适合异步化的部分拆成“发起操作 → 等待状态 → 完成或超时事件”。
4. 根据现有驱动选择 QP 的运行方案，先接通 Reader 与原有模块的边界。
5. 为队列、事件池和缓存设置容量，验证正常流程、失败恢复与突发负载。
6. 确认这条链路可理解、可追踪以后，再决定是否把 Device 和 Cloud 纳入同一模型。

接手一个已有 QP 工程时，也可以沿相同方向阅读：先找 AO 的构造与启动，再找信号定义、状态处理函数、事件投递点、时间事件和驱动回调，最后查看运行内核与资源配置。

回到最初的盘点命令，最值得建立的理解是：**Active Object 决定工作和数据归谁，Event 决定模块怎样协作，Hierarchical State Machine 决定同一个输入在当前阶段怎样处理。** 把这三者接起来，再结合调度、容量和硬件验证，才能让状态复杂的设备程序保持清楚的行为边界。
