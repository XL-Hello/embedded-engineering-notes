# 嵌入式中间件概览

本文整理嵌入式项目中常见的中间件类型。重点是理解中间件要解决的问题、所在位置、主要职责和典型使用场景；具体库的移植、配置与接口细节需要结合芯片、操作系统和产品需求单独分析。

在嵌入式开发中，中间件通常位于 BSP / 驱动与业务应用之间。它向上提供文件、网络、存储、图形、升级和诊断等通用能力，向下使用操作系统、外设驱动或硬件资源。应用层通过稳定接口完成业务，不需要直接面对 Flash 地址、网络报文或显示控制器寄存器。

```text
┌─────────────────────────────┐
│ 应用层：产品功能、控制逻辑、UI │
├─────────────────────────────┤
│ 中间件：网络、存储、GUI、OTA… │
├─────────────────────────────┤
│ OS / BSP / Driver            │
├─────────────────────────────┤
│ 硬件：MCU、Flash、网卡、显示器 │
└─────────────────────────────┘
```

中间件不是一个固定目录，也不等同于某一个库。RTOS、协议栈和文件系统本身有时也会被归入基础软件；工程中更重要的是明确边界：业务只描述“保存配置”“上报状态”“显示页面”，中间件负责提供相应能力，驱动层负责实际访问硬件。

## 一、操作系统与任务适配

### 1.1 操作系统抽象层（OSAL）

OSAL 将任务、互斥锁、消息队列、定时器等操作系统能力封装为统一接口，使上层业务不直接依赖某一个 RTOS。FreeRTOS、NuttX、Zephyr、ThreadX、RT-Thread 等是具体操作系统；OSAL 则是工程为屏蔽它们差异而增加的适配层。

它适合一套业务软件可能运行在不同 RTOS、不同芯片平台，或产品线希望复用公共组件的场景。OSAL 不必覆盖操作系统全部功能，应优先抽象业务真正需要且语义稳定的能力；过度封装会反而丢失底层特性。

```text
业务组件
   │ osal_mutex_lock() / osal_thread_create()
   ▼
OSAL：统一任务、锁、队列、时间接口
   │
   ├── FreeRTOS：xSemaphoreTake() / xTaskCreate()
   └── NuttX：nxmutex_lock() / pthread_create()
```

### 1.2 消息队列与事件总线

消息队列用于把数据或命令从生产者交给消费者；事件总线用于把同一个状态变化通知多个订阅者。两者都能降低模块之间的直接调用关系，但传递的语义不同：队列通常有明确的接收者，事件可被多个模块同时关注。

例如 UI 任务可以把“打开设备”的命令投递给设备控制任务；设备上线后，UI、云端同步和场景模块则可分别订阅“设备状态变化”事件。适合多任务系统、设备管理和场景联动等需要解耦的业务。

```text
UI 任务 ── 控制命令 ──→ [队列] ──→ 设备任务 ──→ Zigbee / RS485

设备状态发布者 ──→ [状态变化事件] ──┬→ UI 刷新
                                      ├→ 云端上报
                                      └→ 场景联动
```

队列需要规定长度、满队列时的处理方式和消息所有权；事件总线需要规定事件数据的生命周期。不能只用一个全局变量同时承担数据保存和事件通知，否则容易产生竞态和状态丢失。

## 二、文件与数据存储

### 2.1 文件系统

文件系统把底层块设备或 Flash 组织为文件和目录，并提供 `open`、`read`、`write` 等接口。应用层按文件名访问日志、配置或资源文件，而不需要了解数据所在的扇区、页和物理地址。

FatFS 常用于 SD 卡和 USB 存储设备；LittleFS、SPIFFS 常用于 SPI NOR Flash；YAFFS、JFFS2 多见于 NAND Flash 或 Linux Flash 场景。实际选择要看存储介质、掉电保护、磨损均衡和资源占用，而不是只看接口是否熟悉。

```text
应用：保存日志
      │ fopen() / fwrite()
      ▼
文件系统：FatFS / LittleFS / SPIFFS
      │
Flash 或块设备驱动
      │
SD 卡 / eMMC / SPI NOR / NAND
```

文件系统适合管理多个可变长度文件、资源包和日志。少量固定参数若直接采用键值存储，通常比自行维护一个小文件更简单可靠。

### 2.2 键值存储与参数管理

键值（KV）存储以“名称—值”的方式保存设备参数，例如音量、Wi-Fi 密码、用户配置和校准数据。NVS（ESP32）、FlashDB、EasyFlash 都属于这类常见实现。

它解决的是“少量配置数据如何可靠保存”的问题。相较直接擦写固定 Flash 地址，KV 中间件通常会处理索引、校验、版本或磨损均衡等问题；应用只需按名称读取或更新参数。

```c
kv_set("volume", 80);
kv_get("volume", &volume);
```

参数设计仍需考虑默认值、数据版本和异常掉电。对于安全相关或特别关键的配置，还应有校验、双备份和恢复策略。

### 2.3 嵌入式数据库

当数据之间存在查询、索引或事务需求时，可使用数据库中间件。SQLite 常用于 Linux 嵌入式设备，例如智能屏保存设备列表、场景配置、用户数据和日志索引。

```text
应用：设备列表、场景、历史记录
              │ SQL
              ▼
           SQLite
              │
          文件系统
              │
         eMMC / NAND
```

数据库适合结构化数据和复杂查询；若只保存少量配置，KV 存储的资源消耗和维护成本通常更低。写入频繁的场景还要评估 Flash 寿命、缓存策略和掉电一致性。

## 三、通信协议中间件

### 3.1 TCP/IP 协议栈

TCP/IP 协议栈向应用提供 Socket 等统一网络接口，并处理 IP、TCP、UDP、ARP 等底层协议。lwIP 是 MCU/RTOS 中常见的轻量协议栈；Linux 环境通常直接使用系统提供的 BSD Socket 接口。

```text
应用：连接服务器、收发数据
      │ socket() / connect() / send()
      ▼
TCP/IP 协议栈：lwIP 或系统网络栈
      │
以太网 / Wi-Fi 驱动
      │
网络硬件
```

协议栈负责网络传输，不等于业务连接一定可靠。上层仍需处理服务器不可达、断线重连、发送超时和业务报文校验等问题。

### 3.2 MQTT 与 CoAP

MQTT 是面向物联网的发布—订阅协议，客户端通过 Broker 发布或订阅主题。中间件通常负责连接管理、心跳、QoS 和报文收发，上层只关心设备状态要发布到哪个主题、要处理哪些订阅消息。

```text
设备应用 ─→ MQTT Client ─→ TCP/IP ─→ Wi-Fi / 以太网 ─→ 云平台 Broker
```

CoAP 面向资源受限设备，常用于低功耗 IoT 网络；它的使用体验类似受限设备上的轻量 Web 请求。两者的选择取决于云平台、网络条件、数据模型和功耗要求：MQTT 更适合持续连接和消息分发，CoAP 更适合轻量请求—响应与受限网络。

### 3.3 BLE 与 Zigbee 协议栈

BLE 协议栈通常分为 Host 与 Controller 两部分，上层通过 GAP / GATT 管理广播、连接、服务和特征值；NimBLE、Bluedroid 是常见实现。应用无需直接处理无线时隙和链路层细节。

```text
应用 ─→ GAP / GATT ─→ BLE Host ─→ Controller ─→ BLE 硬件
```

Zigbee 协议栈则通常包含 ZCL、APS、NWK、MAC 和 IEEE 802.15.4 等层，例如 Z-Stack、EmberZNet。智能家居中的设备入网、属性上报、控制命令和设备模型，通常都建立在这类协议栈能力之上。

```text
设备模型 ─→ ZCL ─→ APS ─→ NWK ─→ MAC ─→ IEEE 802.15.4
```

无线协议栈往往还承担入网、配网、安全、重传和功耗管理。集成时需要明确应用回调的线程上下文，避免在协议栈回调中执行耗时业务。

## 四、人机交互与音视频

### 4.1 GUI 框架

GUI 中间件把控件、布局、输入事件、绘制和刷新流程封装起来，使应用以页面和控件的方式组织界面，而不直接操作 LCD 时序。LVGL 常用于 MCU/RTOS；Qt 常用于 Linux；AWTK、TouchGFX 也常见于相应嵌入式平台。

```text
UI 应用：页面、控件、交互逻辑
              │
GUI 框架：LVGL / Qt / AWTK / TouchGFX
              │
显示驱动与帧缓冲
              │
LCD / 触摸屏
```

以 LVGL 为例，定时处理函数推进动画和输入，绘制完成后通过 `flush_cb()` 将像素数据交给 SPI DMA 或显示控制器。界面逻辑应避免在刷新回调中阻塞，耗时数据读取宜放到独立任务后再更新 UI。

### 4.2 音视频框架

音视频中间件将采集、编解码、封装、传输和播放串成可配置的数据处理链。FFmpeg、GStreamer、OpenMAX 是常见代表，适用于摄像头、可视门铃、监控和多媒体终端。

```text
Camera ─→ V4L2 ─→ GStreamer / FFmpeg ─→ H.264 编码 ─→ RTSP / 网络
```

这类组件资源占用较高，选型时要同时评估 CPU、内存、硬件编解码器、延迟和网络带宽。中间件负责媒体管线，不替代业务侧的录像策略、权限控制和异常恢复。

## 五、设备运维与可靠性

### 5.1 OTA 升级管理

OTA 中间件负责下载升级包、校验完整性和签名、写入备用分区、切换启动项及失败回滚。它将网络传输、Flash 操作和 Bootloader 协同起来，避免应用业务直接处理升级分区。

```text
应用：检查并触发升级
          │
      OTA Manager
      ├── HTTP / MQTT：下载升级包
      ├── 校验：完整性、签名、版本
      └── Bootloader：切换 / 回滚
          │
         Flash 双分区
```

ESP32 的 `esp_https_ota`、MCUboot 等可提供部分或完整能力。可靠 OTA 的关键在于升级包校验、掉电保护、旧版本可恢复，以及新固件首次启动后的确认机制。

### 5.2 日志、诊断与故障转储

日志中间件统一日志级别、格式、输出通道和缓存策略，可将日志输出到串口、文件、Flash 或云端。它帮助定位现场问题，但不能让高频日志挤占关键控制任务。

```text
业务 / 驱动日志 ─→ Log Manager ─→ 串口 / 文件 / Flash / 云端
```

Crash Dump、Backtrace、HardFault Dump 用于在异常后保存寄存器、调用栈和关键状态，供后续分析。对资源有限的 MCU，通常需要限制转储大小，并在下次启动后上传或导出。

### 5.3 安全服务

安全中间件封装加密、密钥使用、安全存储和安全启动等能力。mbedTLS、wolfSSL 可提供 TLS、AES、RSA、ECC 等算法与协议支持；TrustZone、安全芯片（Secure Element）可为密钥和敏感数据提供更强的硬件隔离。

```text
应用：安全连接、保存凭据
          │
安全服务：TLS / 加密库 / 密钥接口
          │
TrustZone / Secure Element / 安全 Flash 区
```

安全的重点不只是“使用了加密库”，还包括密钥不以明文散落在应用中、升级包可验证来源，以及调试接口和错误信息不会泄露敏感数据。

## 六、统一设备模型

设备模型中间件将不同接入方式的设备抽象为统一对象，例如设备 ID、类型、状态、能力和回调接口。上层 UI、场景和云端服务只面对统一模型，不必分别处理 Zigbee、RS485、红外或其他协议的细节。

```text
Zigbee 设备 ─┐
RS485 设备 ──┼──→ 统一 Device Model ──→ UI / 场景 / 云端
红外设备   ─┘
```

```c
typedef struct {
    uint32_t id;
    device_type_t type;
    device_state_t state;
    uint32_t capability;
    void (*on_state_changed)(void);
} device_t;
```

它适合设备种类多、协议多或需要场景联动的智能硬件。模型应表达稳定的业务能力，例如“开关”“亮度”“温度”，而不是把某个协议的原始报文直接泄露给上层。

## 七、常见技术栈与选型关系

| 类别 | 常见实现 | 适用位置 |
| --- | --- | --- |
| 操作系统适配 | OSAL、FreeRTOS、NuttX、Zephyr | 多任务与跨 RTOS 适配 |
| 文件与参数存储 | FatFS、LittleFS、NVS、FlashDB | 文件、日志、设备配置 |
| 数据库 | SQLite | Linux 设备中的结构化数据 |
| 网络与物联网 | lwIP、MQTT Client、CoAP | 联网、云端通信、消息分发 |
| 无线协议栈 | NimBLE、Bluedroid、Z-Stack | BLE、Zigbee 等无线接入 |
| UI 与多媒体 | LVGL、Qt、GStreamer、FFmpeg | 显示、触摸、音视频 |
| 运维与可靠性 | MCUboot、OTA Manager、日志、Crash Dump | 升级、诊断、现场问题定位 |
| 安全服务 | mbedTLS、wolfSSL、TrustZone | TLS、加密、密钥保护 |
| 设备管理 | Device Model、Event Bus | 多协议设备统一管理与联动 |

## 八、使用时的基础原则

- 先按产品需求选择中间件：是否需要文件、联网、显示、升级或多设备管理，而不是为了“分层”引入所有组件。
- 中间件对外暴露业务化接口，对下适配 OS 和驱动；应用不应绕过它直接读写硬件资源。
- 明确每个组件的线程上下文、内存所有权和失败处理方式，尤其是回调、队列、网络和 Flash 写入。
- 资源有限时关注 ROM、RAM、任务数、启动时间和功耗；功能完整不代表适合当前设备。
- 对参数、日志和 OTA 等持久化功能设计掉电恢复、版本兼容、容量上限和异常回退策略。
