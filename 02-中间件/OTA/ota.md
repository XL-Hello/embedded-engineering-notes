
# OTA 基础知识总结

> 目标：梳理企业设备从**获取 OTA 固件包**到安全安装、启动确认、失败回滚的完整链路；重点理解传输、准备、分区架构、Bootloader/Recovery、发布策略和故障处理。
>
> 来源：围绕 OTA 升级主题整理的学习与项目复习笔记，仅供参考。

## 1. 先用一句话理解 OTA

**OTA（Over-The-Air）是设备在不拆机、不人工刷机的情况下，获取可信的新固件并安全替换旧软件；新版本只有通过健康检查才会被确认，失败则回到最后确认可用的版本。**

```text
发现新版本 -> 获取固件包 -> 校验可信性 -> 写入目标分区
                                            |
                                            v
                                  设置“下次试启动”状态
                                            |
                                            v
                            Bootloader 启动新版本 -> 应用健康检查
                                            |                 |
                                            |                 +-- 成功：确认新版本
                                            +-- 失败/超时：回滚或进入 Recovery
```

为什么企业开发离不开 OTA：设备出厂后仍要修复漏洞、修正缺陷和迭代功能，而大量设备往往现场不可达。OTA 让企业能远程统一升级，并把高风险的软件替换做成**安全可验证、失败可回退、过程可追踪**的闭环，避免人工刷机的高成本与大规模误升级风险。

> 关键点：企业级 OTA 不是“把文件写进去然后重启”，而是一套从包可信、写入安全到启动确认和故障恢复的状态机。

## 2. 获取固件：常见的固件传输协议

这一阶段的目标是把完整包放进设备的暂存区或备用槽位。**传输成功不等于允许安装**：后续仍必须校验机型、版本、摘要和签名。

| 方式 | 特点 | 常见场景 | 工程注意点 |
| --- | --- | --- | --- |
| 裸串口分包 | 自定义帧头、序号、长度、CRC、ACK/重传 | 产测、调试口、资源受限 MCU | 处理丢帧、重复包、超时、流控与断点 |
| YModem | 成熟的串口文件传输协议，带块号和 CRC | Bootloader/Recovery 本地救援 | 适合近端维护；CRC 不能替代签名校验 |
| HTTP/HTTPS | 设备主动拉取文件，易配合 CDN 与断点续传 | 常规联网设备的全量包/资源包 | 使用 HTTPS；检查证书、空间、Range 续传与下载摘要 |
| MQTT | 轻量消息协议，适合通知、任务下发和状态上报 | 物联网设备的版本通知与灰度控制 | 不宜直接承载大包；通常 MQTT 通知、HTTPS 下载 |
| BLE/U 盘/局域网 | 近场或离线导入 | 无公网设备、售后、工厂环境 | 导入后进入同一套校验与安装流程 |

### 2.1 小资源 MCU 的 HTTPS 下载与断点续传

`HTTPS` 解决的是**传输链路**问题：TCP 保证字节流可靠，TLS 通过证书校验、加密和防篡改保护设备到服务器之间的通信。它不证明固件本身可信：服务器被入侵后，即使正常 HTTPS 返回恶意镜像，设备仍会收到它。因此放行新固件必须同时满足：**TLS 证书校验通过、实际长度匹配、数字签名验签通过**。

小 RAM MCU 不应把整包放入内存。应以小块流式接收，边写入 OTA 暂存区/非活动槽位，边更新 SHA-256；下载完成后，对最终哈希用内置发布公钥验签。逐扇区 CRC 可辅助发现 Flash 写入错误，但不能代替 SHA-256 或签名。

弱网需要续传时，由 HTTP `Range` 实现，而非 TLS 本身：持久化 `offset`，重新请求 `Range: bytes=<offset>-`，并要求服务端返回 `206 Partial Content`。全部收齐后再验签；若服务端不支持 Range，只能从头重试。恢复 SHA-256 可选择两种实现：

- 一并持久化哈希上下文，续传后继续计算；
- 不保存上下文，收齐后重读 OTA 分区重新计算完整哈希，代码更简单但多一次 Flash 读取。

下载必须限制在元数据声明的长度内：少收、超长、证书失败或验签失败均丢弃临时镜像，绝不引导。不要为方便关闭 TLS 证书校验。


## 3. OTA 的准备

开始擦写 Flash 前，当前旧应用应完成能做的检查，并为失败情况留好退路。

### 3.1 固件与兼容性校验

| 检查项 | 目的 |
| --- | --- |
| 产品型号、板级 ID、硬件版本 | 防止把 A 型号的包刷到 B 型号 |
| 目标芯片、Flash 布局、包类型 | 防止分区不匹配或包放错位置 |
| 当前版本、目标版本、最低安全版本 | 防止错误降级和回到已修复漏洞 |
| 固件大小与目标槽位容量 | 防止越界写入或空间不足 |
| 整包 SHA-256/分块摘要 | 确认传输和存储没有损坏 |
| 数字签名与发布公钥 | 确认包来自可信发布者，未被替换 |

`CRC` 擅长发现传输/存储错误；`SHA-256` 用于强完整性校验；**数字签名**用于验证发布者身份。企业设备通常需要后两项，分块 CRC 可作为写入过程的辅助。

签名通常是“对固件 SHA-256 的签名”：发布方用私钥生成签名，设备用固化公钥验证。验签通过只能说明镜像由配对私钥签发且内容未变；其身份成立还依赖两个前提：私钥未泄露，以及设备内的公钥在 OTP、安全分区或受 Bootloader 保护的位置，不能被普通应用替换。公钥可以公开，不能据此反推出私钥；签名也不等于加密，若需保密须另行加密镜像。

### 3.2 安装前的运行条件

- 电量达到阈值、外部供电稳定，避免擦写中掉电。
- 不在关键业务、录像、产线任务或用户交互期间重启。
- 目标分区已准备好，且当前运行分区绝不作为首选写入目标。
- 升级状态写入非易失存储：如 `VERIFYING`、`WRITING`、`PENDING_REBOOT`。
- 先通知业务模块停止访问 Flash、保存必要数据，并安排看门狗策略。

### 3.3 版本与数据准备

版本策略要明确是否允许降级、是否允许跨大版本升级、差分包依赖哪个基线版本。配置、数据库和校准数据也要有版本号；在新版本确认前不要做不可逆迁移，否则即使代码回滚，旧版本也可能无法读取新数据。

## 4. 常见的 OTA 升级架构

三种架构的区别，核心在于：**新包写到哪里、旧版本是否保留、发生异常后设备靠谁恢复。**

### 4.1 单分区原地覆盖

单分区只有一个主应用区。升级时先擦除旧应用，再把新固件写回同一个分区。

```text
升级前：Bootloader | App（旧版本）
                    |
                    +-- 擦除旧 App -> 写入新 App -> 校验 -> 重启

升级后：Bootloader | App（新版本）
```

升级原理：旧应用负责校验暂存包；随后停止业务、擦除应用分区、按块写入新镜像，并回读或计算摘要。写完成功才重启。由于新旧版本不能同时存在，**擦除开始后旧版本就失去了回滚价值**。

优点：Flash 占用最少、分区与启动逻辑简单。缺点：擦写期间掉电、写入失败或新镜像无法启动，都可能导致主应用不可用。因此它必须有独立的 Bootloader、Recovery 区或串口/YModem 救援通道，适合 Flash 极紧张且允许近端维护的设备。

### 4.2 A/B 双槽位（双分区）

A/B 同时保留两个可启动应用槽位：当前运行 A，新版本只写入未使用的 B。数据写完并校验成功后，才修改很小的启动控制信息。

```text
Flash
+------------+----------------+----------------+----------------+
| Bootloader | Slot A：已确认 | Slot B：新版本 | 启动控制区     |
+------------+----------------+----------------+----------------+
                                      ^              active=A
                                      |              pending=B
                                      +-- 只写非活动槽位  tries=3
```

升级原理：

1. A 正常运行，将新包写入 B，并在写后校验 B 中的实际镜像。
2. 原子记录 `pending=B`、`confirmed=false` 和试启动次数；A 仍完整保留。
3. 重启后 Bootloader 验证 B 并试启动它。
4. B 完成关键自检后调用确认接口，Bootloader 才将 B 标记为已确认。
5. 若 B 未确认、反复复位或次数耗尽，Bootloader 改启 A。

它把“写新固件”和“切换启动版本”分开，因此写入阶段掉电通常不影响 A；这是无人值守设备最常用的可靠方案。代价是需要接近两份应用空间，并要认真设计启动控制区、试启动次数和数据迁移。


#### ESP32（ESP-IDF）项目实例：本地 HTTP A/B OTA

本项目使用 `otadata`、`ota_0`、`ota_1` 三个关键分区；`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y` 开启试启动回滚。升级始终写入 `esp_ota_get_next_update_partition(NULL)` 返回的非运行槽。

```c
const esp_partition_t *target = esp_ota_get_next_update_partition(NULL);
ESP_ERROR_CHECK(esp_ota_begin(target, package_size, &handle));
while ((len = esp_http_client_read(client, buf, sizeof(buf))) > 0) {
    ESP_ERROR_CHECK(esp_ota_write(handle, buf, len));
}
ESP_ERROR_CHECK(esp_ota_end(handle));               // 写后校验
ESP_ERROR_CHECK(esp_ota_set_boot_partition(target));
esp_restart();
```

首次启动新槽时，镜像处于 `ESP_OTA_IMG_PENDING_VERIFY`。只有 LittleFS、Wi-Fi、MQTT、传感器、LVGL 等关键服务自检完成后，才调用 `esp_ota_mark_app_valid_cancel_rollback()` 确认新版本；自检失败则调用 `esp_ota_mark_app_invalid_rollback_and_reboot()` 回到旧槽。

该 demo 的 UI 状态依次为：检查（HTTP `200 + Content-Length`）→ 下载（按块 `esp_ota_write`）→ 安装（切换启动分区）→ 重启确认。它尚未实现版本比较、机型校验、发布签名、断点续传和电量检查，这些应由生产版补齐。

### 4.3 Recovery 分区

Recovery 是一块独立、体积较小且尽量少更新的救援系统。主应用无法启动、原地覆盖中断，或 Bootloader 判断没有有效应用时，设备进入 Recovery，由它重新安装主应用。

```text
Flash
+------------+----------------+------------------+----------------+
| Bootloader | Recovery       | Main Application | 暂存固件包     |
+------------+----------------+------------------+----------------+
                    |                    |
                    +-- 校验可信包 -> 覆盖写主应用 -> 写后校验 -> 重启
```

升级原理：主应用或 Bootloader 先将包放到独立暂存区；当主应用升级失败或被判定不可启动时，Bootloader 选择 Recovery。Recovery 不执行复杂业务，只验证包、擦写主应用分区、校验落盘结果并重启。这样即使主应用已坏，设备仍有独立代码可接管恢复。

Recovery 比单分区安全，但不等于 A/B 回滚：如果旧主应用已被覆盖，Recovery 只能用暂存包、外部介质或再次下载修复，不能瞬间恢复旧版本。它适合主应用较大、Flash 放不下完整 A/B 的设备。

Recovery 的价值在于把“**选择谁运行**”和“**如何修复**”分开：Bootloader 只做基础硬件初始化、读取启动元数据、验证候选镜像并跳转到主应用或 Recovery；Recovery 则在独立的最小运行环境中读取暂存包、验签、擦写主应用、写后复核，以及按需提供串口、USB 或联网下载等救援能力。

不要把 HTTPS 下载、断点续传、复杂包解析和大规模 Flash 擦写都塞进 Bootloader。此类能力需要协议栈、存储管理和重试逻辑，会显著增大最早期可信代码的体积和缺陷面；Bootloader 一旦损坏，通常没有更低层组件能够救援。相比之下，Recovery 仍由 Bootloader 引导，且可作为普通受保护分区迭代其救援逻辑（具体能否独立升级取决于芯片的启动链和分区保护设计）。

典型故障链：主应用已将可信包下载到暂存区，Recovery 覆盖写主分区时掉电；再次上电后 Bootloader 发现主应用无效，只需转入 Recovery。Recovery 使用仍在暂存区的完整包重新安装并校验，成功后重启。这样故障现场的复杂修复不会压在 Bootloader 内。

| 方案 | 失败后的恢复方式 | 主要取舍 |
| --- | --- | --- |
| 单主应用 + Bootloader | Bootloader 自行承担修复或依赖外部救援 | 空间最省，但 Bootloader 易膨胀、维护风险高 |
| 单主应用 + Recovery + 暂存区 | Recovery 重装可信包 | 不保留旧版，不能即时回滚；适合 Flash 紧张设备 |
| A/B 双槽位 | 直接启动最后确认的旧槽位 | 回滚最快，但需要接近两份应用空间 |

#### Recovery 区的伪代码

```c
void recovery_main(void)
{
    boot_record_t rec = boot_record_load_valid();

    if (!recovery_requested(rec) && app_image_bootable()) {
        boot_jump_to_app();
    }

    package_t pkg = load_package_from_staging_or_external_media();
    if (!package_matches_board(pkg) || !package_signature_ok(pkg)) {
        show_recovery_error();       // 留在 Recovery，等待可信包
        return;
    }

    set_recovery_state(RECOVERY_WRITING);
    if (!erase_and_write(APP_PARTITION, pkg.image) ||
        !image_hash_ok(APP_PARTITION, pkg.hash)) {
        set_recovery_state(RECOVERY_WRITE_FAILED);
        reboot_to_recovery();        // 不跳转到未确认的主应用
    }

    boot_record_set_app_pending(pkg.version);
    clear_recovery_request();
    reboot();
}
```

- tips：《Bootloader 在 OTA 中负责什么》

Bootloader 是上电后最早运行的可信程序。它不负责下载大包，而负责读取可靠启动状态、验证候选镜像、选择启动槽位、维护试启动次数、接受应用确认，并在异常时回滚或进入 Recovery。

```text
应用：下载/暂存新包 -> 写目标分区 -> 请求试启动 -> 健康后确认
Bootloader：验镜像 -> 选槽位 -> 限制试启动 -> 回滚/进入 Recovery
```

不要把关键回滚逻辑只放在应用里：应用一旦损坏或无法启动，就没有机会执行自己的回滚代码。

Bootloader 的典型决策伪代码

```c
void boot_main(void)
{
    boot_record_t rec = boot_record_load_valid(); // 双副本 + CRC + 序列号
    slot_t confirmed = rec.confirmed_slot;
    slot_t pending = rec.pending_slot;

    if (pending != SLOT_NONE) {
        if (!image_header_ok(pending) || !image_signature_ok(pending)) {
            boot_record_clear_pending();
            boot_jump(confirmed);
        }

        if (rec.try_count < MAX_TRIES) {
            boot_record_inc_try_count(); // 先持久化，防止掉电后无限重试
            boot_jump(pending);          // 应用健康后调用 mark_boot_success()
        }

        boot_record_mark_rollback(pending, ROLLBACK_TRIES_EXHAUSTED);
        boot_jump(confirmed);
    }

    if (image_signature_ok(confirmed)) {
        boot_jump(confirmed);
    }

    boot_enter_recovery();
}

void mark_boot_success(slot_t running_slot)
{
    // 仅在存储、配置、关键外设和核心业务自检通过后调用
    boot_record_confirm(running_slot);
}
```

## 5. 企业常用的发布与升级策略

设备端能安全安装只是基础，企业还要控制“谁在什么时间升级、出了问题怎么止损”。

### 5.1 灰度发布与分批放量

```text
内部测试 -> 种子设备/1% -> 5%~10% -> 30%~50% -> 全量
```

每一批观察升级成功率、签名/写入失败率、回滚率、崩溃率、启动耗时、功耗与业务错误率。异常时先暂停下一批，而不是继续全量推送。

常见分组维度：产品型号、硬件版本、地区/运营商、客户、当前版本、供电条件和白名单。

### 5.2 错峰、暂停与熔断

- 选择业务低峰或维护窗口，避开关键任务与低电量状态。
- 加随机延迟，避免大量设备同时下载、写 Flash、重启。
- 支持暂停：只阻止尚未进入关键擦写阶段的设备继续升级。
- 支持撤回与熔断：失败率/回滚率超过阈值自动停止放量。
- 记录设备 ID、包 ID、版本变化、升级阶段、失败/回滚原因和重试次数，便于追溯。

## 6. OTA 容易出问题的点及 OTA 失败怎么排查

### 6.1 企业级 OTA 的四道坎

| 四道坎 | 要防什么 | 落地做法 |
| --- | --- | --- |
| 断电保护 | 擦写中断导致控制区或镜像半成品 | 写非活动槽位；状态双副本/日志式记录；写后校验；原子切换 |
| 安全签名 | 恶意包、错机型包、回退到有漏洞版本 | 板级 ID/最低安全版本校验；摘要校验；公钥验签；Bootloader 再验 |
| 版本管理 | 错误放量、差分基线不匹配、问题不可追溯 | 包 ID/版本策略；灰度分组；阶段与失败原因上报 |
| 防砖技巧 | 新版本无法启动后设备失联 | A/B 试启动确认；次数上限；Recovery/串口救援；数据可回退 |

### 6.2 高频问题

- 只做 CRC、不做签名：能发现损坏，挡不住恶意替换。
- 未校验机型、硬件版本或包大小：可能刷进“签名正确但不匹配”的镜像。
- 直接覆盖当前运行分区：掉电时无可启动代码。
- 只校验接收文件、不校验 Flash 实际落盘镜像：写入错误可能漏检。
- 误以为 HTTPS 下载成功就代表镜像可信：HTTPS 防链路中间人，不能防被攻陷服务器下发恶意包；仍须长度、哈希和公钥验签。
- 续传只保存 `offset` 却继续使用中断前的半截哈希：须持久化 SHA-256 上下文，或下载结束后重读整个 OTA 分区重算哈希。
- 为调试关闭 TLS 证书校验：会失去 HTTPS 的身份与防中间人保护。
- 新版本一启动就确认：业务尚未验证就失去自动回滚机会。
- A/B 已有但数据迁移不可逆：代码回滚后仍无法启动业务。
- 灰度只看下载/升级成功率：还应看回滚、崩溃和业务指标。

### 6.3 按状态机排查

```text
获取失败 -> 校验失败 -> 写入失败 -> 未进入新版本
-> 健康检查失败/未确认 -> 回滚 -> Recovery 重装失败
```

| 停留阶段 | 优先检查 |
| --- | --- |
| 获取失败 | 网络/串口链路、断点位置、存储空间、包摘要 |
| 校验失败 | 包大小、型号、硬件 ID、摘要、签名、公钥、最低安全版本 |
| 写入失败 | 分区地址/容量、擦写粒度、电压、看门狗、写后回读摘要 |
| 未进入新版本 | `pending` 是否持久化、控制区 CRC、Bootloader 验签和试启动次数 |
| 启动后回滚 | 健康检查是否过严/过早、复位原因、外设/配置迁移、确认调用 |
| Recovery 失败 | 暂存包是否存在、签名是否通过、主分区写后校验和 Recovery 日志 |

> 排查的第一问应是“失败停在哪个状态”。状态、控制区记录和复位原因比一开始翻业务代码更能缩小范围。

## 7. 面试常见问法和直白回答

### 7.1 企业级 OTA 和普通远程刷机有什么区别

> 普通远程刷机可能只是写镜像再重启；企业级 OTA 会验证机型、版本、摘要和签名，通常写入备用分区，启动后健康检查确认，失败自动回滚，并配合灰度、暂停、熔断和日志统计控制规模风险。

### 7.2 为什么 A/B 分区能防止变砖

> 当前运行 A 时把新包写到 B，只有 B 写完且校验通过才切换启动标志。升级中断时 A 仍完整可启动；B 启动异常时 Bootloader 也能回到 A。

### 7.3 CRC、SHA-256 和签名分别解决什么问题

> CRC 擅长发现随机传输或存储错误；SHA-256 用于强完整性校验；数字签名证明包来自可信发布者、没有被恶意替换。企业 OTA 通常使用摘要加签名，CRC 常用于分块处理。

### 7.4 回滚逻辑为什么放在 Bootloader

> 主应用损坏或无法启动时，应用无法执行回滚代码。Bootloader 最早运行、应保持小而稳定，所以由它验镜像、选槽位、限制试启动次数并选择回滚更可靠。

### 7.5 Recovery 和 A/B 回滚有什么区别

> A/B 是保留旧槽位后快速切回最后确认版本；Recovery 是由极简 Bootloader 调度的独立救援系统，负责重新安装可信包。单槽位场景中 Recovery 很重要，但它不能凭空恢复已擦掉的旧版本；它用较少 Flash 换取“可修复”，A/B 用更多 Flash 换取“可即时回滚”。

### 7.6 为什么公钥验签能确认发布者

> 私钥只由发布者保管，只有它能生成可被设备内置公钥验证通过的签名。设备对收到的固件重新计算哈希并验签；内容被改或签名伪造都会失败。这个结论以私钥未泄露、设备固化公钥未被替换为前提；SHA-256 或 CRC 本身只能说明数据是否一致，不能证明是谁发布的。

## 8. 最简记忆版

- OTA 包含获取固件、安全安装、试启动确认和失败恢复，不是简单远程刷机。
- 传输可用串口分包、YModem、HTTPS、MQTT 通知等；传完仍要验版本、摘要和签名。
- 安装前先查机型/硬件/空间/版本，并保证电源、状态记录和数据迁移可回退。
- 企业级设备优先 A/B：新包写非活动槽位，Bootloader 试启动，应用健康后确认。
- Bootloader 负责验镜像、选槽位、计数与回滚；Recovery 负责主应用损坏后的救援重装。
- 发布要灰度、错峰、暂停、熔断和全程可观测。
- 排查先定位状态机，再查包、分区、控制区、复位原因和健康检查。
