# 编程 ringbuffer 基础

> 目标：从“为什么收串口数据不能只用一个变量”这个问题出发，理解 ringbuffer（环形缓冲区）的数据结构、读写规则和嵌入式并发边界；先能手写一个可靠的单生产者单消费者版本，再扩展到 DMA、RTOS 和多生产者场景。
>
> 核心结论：**ringbuffer 用一块固定数组和两个不断绕回的读写位置保存连续数据流。写端只推进“写索引（常命名为 `head`）”，读端只推进“读索引（常命名为 `tail`）”；当两者相等时为空，写端追上读端前必须明确“丢新数据、丢旧数据还是拒绝写入”的策略。**

## 1. 一句话理解 ringbuffer

`ringbuffer`（环形缓冲区、循环队列）是一段首尾相连来使用的固定大小内存，特别适合“生产速度和消费速度不完全一致”的连续数据。

```text
UART / ADC / 网络 / 中断                  主循环 / 任务 / 解析器
        生产数据                                  消费数据
            |                                        |
            v                                        v
      +----------------------------------------------------+
      |  [0] [1] [2] [3] [4] [5] [6] [7]                   |
      +----------------------------------------------------+
                    tail ---> 已写未读数据 <--- head
```

数组物理上不是环，但索引到达末尾后回到 `0`，逻辑上便成了一个环：

```text
0 -> 1 -> 2 -> ... -> N - 1
^                         |
|_________________________|
```

它不是动态链表，也不会自动让系统“变快”；它的价值是用固定内存暂存突发数据，让生产者和消费者在时间上解耦。

## 2. 为什么需要它：以 UART 接收为例

串口每收到一个字节，硬件或接收中断会立刻给出数据；但主循环可能正忙于显示、控制或其他任务，不能马上处理。

```text
UART RX 中断： A -> B -> C -> D -> ...  （数据持续到来）
                    |
                    v
             ringbuffer 暂存
                    |
                    v
主循环 / 解析任务：按自己的节奏取出 A、B、C、D
```

若只用一个全局字节变量，后到的数据会覆盖先到的数据；若在 ISR 里直接做整帧解析、打印或复杂业务，又会让中断过长，增加丢数据和实时性风险。常见分工是：

```text
ISR / DMA 回调：快速搬运字节到 ringbuffer，通知任务
任务 / 主循环：取字节、拼帧、校验、执行业务
```

## 3. 必须先说清的三个概念

很多资料把两个位置叫作“读写指针”。从逻辑角色看这样叫没有问题；但本文数组中保存的是下标，不是真正的 C 地址指针，因此更准确、也更适合代码命名的说法是**读索引 / 写索引**（或读位置 / 写位置）。

`head` / `tail` 是大量库和资料使用的传统命名：`head` 对应写索引，`tail` 对应读索引。初学代码可以直接使用 `write_pos`、`read_pos`，在面试和阅读第三方代码时再能对应到 `head`、`tail` 即可。

本文统一约定：

- `write_pos`（也常叫 `head`）：下一个**写入位置**，由生产者推进。
- `read_pos`（也常叫 `tail`）：下一个**读取位置**，由消费者推进。
- `capacity`：底层数组大小。

写入一个字节：先写 `buffer[write_pos]`，再将写索引向前移动；读取一个字节：先读 `buffer[read_pos]`，再将读索引向前移动。下文代码为了与常见资料对照，仍使用 `head` / `tail`。

```text
写：buffer[head] = data  ->  head = next(head)
读：data = buffer[tail]  ->  tail = next(tail)
```

这里“先数据、后索引”的顺序很重要：消费者看到新的 `head` 时，对应数据应已经准备好；反过来，生产者看到新的 `tail` 时，表示该位置已经被消费者释放。

## 4. 最容易混淆的问题：如何区分空和满

只使用 `head` 和 `tail` 时，`head == tail` 很自然表示空。但写满一整圈后它们也会相等，产生歧义。

常用解决方案有三种。

### 4.1 空一格法：嵌入式最常见

始终保留一个数组位置不用：

```text
empty: head == tail
full : next(head) == tail
```

优点是判断简单，两个索引足够；代价是容量为 `N` 的数组最多存 `N - 1` 个元素。

```text
capacity = 8，实际可存 7 字节
```

### 4.2 单独维护 `count`

```text
empty: count == 0
full : count == capacity
```

容量可用满，但 `head`、`tail`、`count` 可能被不同上下文修改。ISR 与任务并发时，更新三者往往需要临界区或锁，容易增加复杂度。

### 4.3 使用单调递增计数器

让读写计数器持续递增，仅在访问数组时对 `capacity` 取模；通过 `write - read` 判断已用长度。该方式适合高性能或无锁实现，但要考虑整数回绕、原子读写和内存屏障，初学阶段不建议直接照搬。

**下面的示例使用空一格法。**

## 5. 从零写一个 byte ringbuffer

### 5.1 数据结构

为了用位运算快速回绕，示例要求 `RB_CAPACITY` 为 2 的幂。

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

#define RB_CAPACITY  128U

typedef struct {
    uint8_t buffer[RB_CAPACITY];
    volatile size_t head;   /* 生产者写入位置 */
    volatile size_t tail;   /* 消费者读取位置 */
    uint32_t overflow_count;
} ringbuffer_t;

static size_t rb_next(size_t index)
{
    return (index + 1U) & (RB_CAPACITY - 1U);
}

void rb_init(ringbuffer_t *rb)
{
    rb->head = 0U;
    rb->tail = 0U;
    rb->overflow_count = 0U;
}
```

若容量不是 2 的幂，应使用：

```c
return (index + 1U) % RB_CAPACITY;
```

不要在没有确认容量为 2 的幂时就写 `& (capacity - 1)`；例如容量 `10` 时它会产生错误索引。

### 5.2 写入：满时拒绝新数据

```c
bool rb_put(ringbuffer_t *rb, uint8_t data)
{
    size_t head = rb->head;
    size_t next = rb_next(head);

    if (next == rb->tail) {
        rb->overflow_count++;
        return false;       /* 满：丢弃本次新数据 */
    }

    rb->buffer[head] = data;
    rb->head = next;
    return true;
}
```

### 5.3 读取：空时返回失败

```c
bool rb_get(ringbuffer_t *rb, uint8_t *data)
{
    size_t tail = rb->tail;

    if (tail == rb->head) {
        return false;       /* 空 */
    }

    *data = rb->buffer[tail];
    rb->tail = rb_next(tail);
    return true;
}
```

使用方式：

```c
uint8_t ch;

while (rb_get(&g_uart_rx_rb, &ch)) {
    protocol_feed_byte(ch);
}
```

注意：`rb_get()` 返回 `false` 只表示“当前没有数据”，不是异常。把“是否成功”作为返回值、把数据通过指针输出，可避免 `0x00` 与“无数据”混淆。

## 6. 用一遍流程真正理解 head 和 tail

以容量为 `8` 的数组为例，空一格法最多只能存 `7` 个字节。

```text
初始：head = 0，tail = 0，空

写入 A、B、C：
index:  0   1   2   3   4   5   6   7
       [A] [B] [C] [ ] [ ] [ ] [ ] [ ]
                    H
        T

读取 A、B：
index:  0   1   2   3   4   5   6   7
       [A] [B] [C] [ ] [ ] [ ] [ ] [ ]
                    H
                T

再写 D、E、F、G、H：head 会从 7 回到 0；
只要未追上 tail，逻辑顺序仍是 C、D、E、F、G、H。
```

数组内旧字节不会被主动清零，也不需要清零。数据是否有效由 `head` 与 `tail` 的关系决定；清零只会浪费时间，调试时也不应根据数组残留内容判断队列是否为空。

## 7. 溢出不是实现细节，而是产品策略

当生产速度长期大于消费速度，任何有限 ringbuffer 最终都会满。此时必须明确业务语义：

| 策略 | 做法 | 适合场景 |
| --- | --- | --- |
| 丢新数据 | 满时 `rb_put()` 失败，保留旧数据 | 协议数据、命令流；避免破坏已开始解析的顺序 |
| 丢旧数据 | 满时推进 `tail`，写入最新数据 | 只关心最新状态，如最新传感器值、日志预览 |
| 阻塞等待 | 生产者等待有空间 | 普通任务间通信；不能在 ISR 中使用 |
| 扩容 | 分配更大缓冲区 | 有动态内存且峰值可预估的系统；嵌入式中要谨慎 |

不要静默忽略 `rb_put()` 的失败。至少记录 `overflow_count`，便于定位“协议偶发错帧”“高负载下丢日志”等问题。缓冲区变大只能吸收短时突发，不能解决长期吞吐量不足。

## 8. 并发：什么时候不需要锁，什么时候必须加保护

### 8.1 单生产者、单消费者（SPSC）

最常见的 UART RX 模型：一个 ISR 写、一个任务读。空一格法中：

```text
生产者只写 head，只读 tail
消费者只写 tail，只读 head
```

在满足以下前提时，通常可不使用互斥锁：

- 只有一个生产者、一个消费者。
- `head`、`tail` 的单次读写在目标 CPU 上是原子的且正确对齐。
- 两端不同时修改同一个索引。
- 发布数据 / 释放位置的顺序正确。

`volatile` 只能避免编译器把索引缓存到寄存器或错误合并访问；它**不是锁**，也不能让“读取-判断-修改”这类复合操作原子化，更不能替代多核系统需要的内存屏障。

### 8.2 多生产者或多消费者

若两个 ISR 都写入同一个 ringbuffer，或两个任务同时读取，简单实现会发生竞态：两个上下文可能读取到同一个 `head`，再分别写入并覆盖对方结果。

处理选择：

- 使用 RTOS 的 queue / stream buffer，通常更安全。
- 用 mutex、临界区或自旋锁保护完整的 put/get 操作。
- 每个生产者使用独立 ringbuffer，再由一个任务汇总。
- 只有在明确掌握原子操作、内存序和 ABA / 回绕问题时，再实现无锁 MPMC 队列。

面试中不要笼统回答“加 `volatile` 就线程安全”。应先说明生产者、消费者数量，再给出保护方案。

## 9. 与 DMA 配合：ringbuffer 的进一步用法

DMA 循环接收常见结构是：DMA 不断写入一块循环数组，软件根据 DMA 当前写到的位置，取走“新增区间”。

```text
DMA 硬件写位置 ----> [循环 DMA 缓冲区] ----> 协议解析任务
                                  软件上次处理位置
```

此时 DMA 缓冲区本身就像生产者写入的 ringbuffer，但仍要处理：

- DMA 写位置回绕时，新数据会分为尾部和头部两段。
- 任务太慢时，DMA 会覆盖尚未处理的数据；应检测并计数。
- 从 DMA 位置到软件读取范围的计算必须基于具体 MCU / HAL 的语义。
- 缓存型 MCU 还要处理 D-cache 一致性，否则 CPU 可能读到旧数据。

初学时先实现“中断每字节写入软件 ringbuffer”；理解索引回绕和并发后，再学习 DMA 环形接收，排查会更有把握。

### 9.1 Linux 内核 `kfifo`：当前接口与使用思路

`kfifo` 是 Linux 内核提供的通用 FIFO / 环形缓冲区接口，头文件为 `<linux/kfifo.h>`。本文依据内核官网 `latest` 文档整理；它与前文手写 ringbuffer 的目标相同，但内核已封装了元素类型、长度计数、内存分配、用户态拷贝、DMA 和常见自旋锁辅助接口。

一个重要区别是：本文前面的“空一格法”让数组容量 `N` 实际存 `N - 1` 个元素；`kfifo` 使用单调递增的 `in` / `out` 计数器计算长度，因而一个大小为 `N` 的 FIFO 可容纳 `N` 个元素。底层缓冲区仍要求容量为 2 的幂，内核用掩码完成回绕。

```text
手写示例：write_pos / read_pos + 空一格
Linux kfifo：in（写计数）/ out（读计数）+ len = in - out
```

#### 9.1.1 声明与初始化：优先使用“类型安全”接口

固定大小、静态分配的 FIFO 最直观：

```c
#include <linux/kfifo.h>

DEFINE_KFIFO(rx_fifo, u8, 256);
/* 全局静态对象，定义时已初始化；容量 256 个 u8 */
```

也可以先声明、后初始化：

```c
DECLARE_KFIFO(rx_fifo, u8, 256);

static int __init demo_init(void)
{
    INIT_KFIFO(rx_fifo);
    return 0;
}
```

`size` 是**元素个数**，必须是 2 的幂；这里是 256 个 `u8`。若元素类型改为 `struct message`，容量仍是 256 个结构体，不是 256 字节。`DEFINE_KFIFO` / `DECLARE_KFIFO` 是首选，因为编译器可以检查元素类型。

运行期才确定容量时，使用指针型声明和分配：

```c
DECLARE_KFIFO_PTR(rx_fifo, u8);

ret = kfifo_alloc(&rx_fifo, 1024, GFP_KERNEL);
if (ret)
    return ret;

/* 模块退出或错误路径必须配对释放 */
kfifo_free(&rx_fifo);
```

`kfifo_alloc()` 会将请求的大小向上调整为 2 的幂；不能在硬中断上下文使用会睡眠的 `GFP_KERNEL` 分配。已有外部预分配内存时可使用 `kfifo_init()`；NUMA 场景还有 `kfifo_alloc_node()`。

#### 9.1.2 基本读写 API

| 需求 | 常用 API | 返回值 / 注意点 |
| --- | --- | --- |
| 写一个元素 | `kfifo_put(fifo, value)` | 成功为非 0，满时为 0 |
| 读一个元素 | `kfifo_get(fifo, &value)` | 成功为非 0，空时为 0 |
| 看一个元素但不取走 | `kfifo_peek(fifo, &value)` | 成功为非 0 |
| 批量写入 | `kfifo_in(fifo, buf, n)` | 返回实际写入的元素数，可能小于 `n` |
| 批量读出 | `kfifo_out(fifo, buf, n)` | 返回实际读出的元素数，可能小于 `n` |
| 查询状态 | `kfifo_len` / `kfifo_avail` / `kfifo_is_empty` / `kfifo_is_full` | 分别为已用、可用、空、满 |

```c
u8 ch;

if (!kfifo_put(&rx_fifo, ch)) {
    /* FIFO 已满：统计丢失，或通知上层；不能静默忽略 */
}

while (kfifo_get(&rx_fifo, &ch)) {
    protocol_feed_byte(ch);
}
```

对于驱动的 `.read()` / `.write()`，`kfifo_to_user()` 与 `kfifo_from_user()` 会执行用户态地址拷贝：返回值是 `0` 或错误码，实际复制字节数通过 `copied` 输出参数取得。它们不是“自动同步”接口，仍须按访问模型加锁。

#### 9.1.3 并发规则：`kfifo` 不会替你猜锁

官方文档明确：只有**一个并发读者和一个并发写者**（SPSC）时，`kfifo_in()`、`kfifo_out()`、`kfifo_put()`、`kfifo_get()` 等普通接口不需要额外锁。典型模型是硬件 IRQ 写入、一个进程上下文或工作队列读取。

```text
硬件 IRQ：唯一写者 -> kfifo_in / kfifo_put
进程 / workqueue：唯一读者 -> kfifo_out / kfifo_get
```

只要出现多写者、多读者，或某段代码需要把“检查条件 + 操作”作为一个整体，就必须同步。可使用 `kfifo_in_spinlocked()` / `kfifo_out_spinlocked()`，也可在外部使用合适的 `spin_lock_irqsave()` 临界区；是否禁用本地中断取决于同一把锁会不会被中断上下文获取。`*_spinlocked_noirqsave()` 不会禁用中断，不能在可能被同 CPU 中断重入的场景中随意替换。

`kfifo_reset()` 会直接丢弃全部内容，官方特别标注为危险操作：只有独占锁定，或确认没有任何并发访问时才能调用。`kfifo_reset_out()` 仅由唯一读者调用时相对安全；否则也要与 `reset` 一样受保护。

#### 9.1.4 面试容易问到的点

- `kfifo` 不是等待队列：它只保存数据。驱动要实现阻塞 `.read()`，还需 `wait_queue_head_t`；写入后 `wake_up_interruptible()`，读取前判断 FIFO 是否为空并正确处理唤醒竞争。
- `kfifo` 不是消息边界协议：普通 FIFO 存的是元素序列。存 UART 字节时，帧边界仍应由协议层的长度、分隔符或校验处理。内核也支持 record FIFO 形式，用长度字段保存可变长记录；其 API 会涉及 `kfifo_peek_len()` 等，使用时要从声明方式开始选择记录模式。
- `kfifo_len()` / `kfifo_avail()` 是某一时刻的快照；并发情况下不能先判断再假设下一步仍成立，应依赖实际 `in/out/put/get` 的返回值。
- `kfifo` 的“满”通常表现为本次实际写入数量小于请求数量，而不是自动覆盖旧数据。溢出策略仍属于驱动设计。

因此，`kfifo` 解决的是“可靠的 FIFO 存储与基础并发语义”，不解决事件通知、背压、协议分帧和多方访问策略。把这些层次分开，是 Linux 驱动面试中比背 API 更重要的回答。

## 10. 常见错误与排查

| 现象 | 常见原因 | 排查重点 |
| --- | --- | --- |
| 数据总少一个字节 | 把空一格法的实际容量当成数组容量 | 检查 full 条件和文档说明 |
| 收到数据顺序错乱 | `head` / `tail` 推进方向或读写顺序错误 | 手工模拟 3 次写入、2 次读取、回绕写入 |
| 偶发丢包 | 消费速度不足、缓冲太小、满后失败被忽略 | 统计 overflow、测量最大处理延迟 |
| 高负载后解析错帧 | ISR 中做了耗时工作，或满后无重同步策略 | ISR 只搬运；协议层校验、丢帧和重新找帧头 |
| RTOS 下偶发异常 | 多写者 / 多读者却没有保护 | 画出谁调用 put/get，确认 SPSC 前提 |
| DMA 数据重复或漏掉 | 回绕区间计算错误、未处理缓存一致性 | 记录 DMA 写位置和软件上次位置 |
| 空队列却读到旧数据 | 忽略 `rb_get()` 返回值 | 不以 buffer 内容判断有效性 |

推荐排查顺序：

```text
确认生产者 / 消费者数量
  -> 确认 empty、full 与溢出策略
  -> 单步记录 head、tail、写入字节、读取字节
  -> 统计 overflow 和最大积压长度
  -> 最后检查 ISR、RTOS 调度、DMA 和缓存
```

## 11. 初学者快速学习法

1. 先拿容量 `8` 的纸面数组，亲手演算写 3 个、读 2 个、再写到回绕；每步都写出 `head`、`tail`。
2. 用空一格法写出 `init / put / get / empty / full` 五个小函数，不要一开始加 DMA、协议和 RTOS。
3. 写测试：空读、连续写读、写到回绕、写满、溢出后读取顺序。尤其验证 `0x00`、`0xFF` 等边界字节。
4. 将它接入 UART RX ISR，主循环只做“读出并打印十六进制”；确认无误后才接协议解析。
5. 最后画清并发图：谁生产、谁消费、谁能修改 `head`、谁能修改 `tail`。这一步比背 API 更重要。

## 12. 面试常见问题与回答要点

### 12.1 什么是环形缓冲区？为什么嵌入式常用？

它是固定数组加读写索引构成的 FIFO，索引到末尾后回绕。它不需要频繁动态分配，内存和时间开销可预测，特别适合 UART、日志、采样等连续数据流，用来应对生产和消费节奏不一致。

### 12.2 如何判断空和满？

常见办法是空一格：`head == tail` 表示空，`next(head) == tail` 表示满，代价是容量 `N` 只能存 `N - 1` 个元素。也可使用 `count` 或单调计数器，但并发同步会更复杂。

### 12.3 ringbuffer 满了怎么办？

先由业务决定。协议命令一般丢新数据并计数，避免破坏已有顺序；只关心最新状态的数据可以丢旧数据。缓冲区变大只解决短时突发，还要分析平均吞吐量、峰值和任务最大延迟。

### 12.4 ISR 写、任务读，需要加锁吗？

若严格是单生产者单消费者，且生产者只更新 `head`、消费者只更新 `tail`、索引访问原子且发布顺序正确，通常可无锁运行。若存在多个生产者或消费者，或索引宽度在 CPU 上不是原子访问，就要使用临界区、RTOS 队列等同步手段。`volatile` 本身不能解决竞态。

### 12.5 ringbuffer 与 queue 的区别？

ringbuffer 是底层数据结构，常存字节流或元素；queue 通常是带同步、阻塞/唤醒和对象传递语义的 RTOS 抽象。UART 字节流常用 ringbuffer / stream buffer；任务间传递离散命令或结构体时，RTOS queue 通常更合适。

## 13. 项目回答模板

> 项目中我在 `UART 接收 / 日志 / ADC 数据` 链路使用 ringbuffer。生产端是 `XXX ISR / DMA 回调`，只负责快速写入并推进 `head`；消费端是 `XXX 任务`，读取并推进 `tail`，随后进行协议解析或业务处理。实现采用空一格法，`head == tail` 表示空、`next(head) == tail` 表示满，实际可用容量是 `N - 1`。满时选择 `丢新 / 丢旧`，同时统计溢出次数。该实现是严格的单生产者单消费者；如果扩展为多任务并发访问，我会改用 RTOS queue / stream buffer 或加临界区，而不是只加 `volatile`。

## 14. 关键结论

```text
生产者写数据 -> 推进 head -> ringbuffer 暂存 -> 消费者读数据 -> 推进 tail
```

- ringbuffer 是固定内存的 FIFO，用于解耦数据到达与数据处理的时间。
- 首先定义清楚 `head`、`tail`、空、满和溢出策略，代码才不容易错。
- 空一格法简单可靠，但数组容量 `N` 实际只能存 `N - 1` 个元素。
- 单生产者单消费者可以做得很轻量；多生产者 / 多消费者必须重新考虑同步。
- `volatile` 只解决可见性的一部分问题，不等于原子性和线程安全。
- 优先统计溢出和最大积压，先解决吞吐 / 时序问题，再盲目扩大缓冲区。
