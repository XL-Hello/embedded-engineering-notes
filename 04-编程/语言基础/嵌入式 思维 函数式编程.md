# 嵌入式 思维 函数式编程

> 核心原则：**将换算、校验和控制规则写成依赖明确的函数；将读硬件、写寄存器、保存状态、日志等副作用留在边界层。**
>
> 背景：偶然看到函数式编程的关键词，就总结了这篇文章，不是什么复杂的东西，更多的是一种思维，时刻提醒自己。

## 1. 核心思想

函数式编程不是要求嵌入式项目不用变量或全局状态，而是尽量让业务计算满足：相同输入得到相同输出，且不偷偷依赖或修改外部状态。

```text
硬件读取 → 普通数据 → 换算 / 校验 / 决策 → 动作指令 → 硬件输出
             （尽量纯）                     （副作用）
```

这样规则清晰、易测试，硬件和 RTOS 细节也不会混入业务逻辑。

## 2. 纯函数与副作用

纯函数只通过参数获得输入、通过返回值给出结果：

```c
bool decide_fan_state(float temperature, bool previous_state)
{
    if (temperature >= 60.0f) return true;
    if (temperature <= 55.0f) return false;
    return previous_state;
}
```

读传感器、写 GPIO、修改全局变量、打印日志等都会影响或依赖外部世界，属于副作用。它们不是错误，只应集中在少数边界函数中：

```c
void fan_control_task(void)
{
    float temperature = sensor_read_temperature();
    bool next = decide_fan_state(temperature, g_fan_on);

    if (next != g_fan_on) {
        gpio_write(FAN_PIN, next);
        g_fan_on = next;
    }
}
```

## 3. C 语言中的实用做法

- 用参数和返回值表达依赖与结果；多个结果可返回结构体。
- 只读指针加 `const`，明确函数不会修改输入。
- 将状态迁移写成“当前状态 + 事件 → 下一状态”的函数。
- 大型缓冲区、DMA 和实时数据流可原地修改，不必为“不可变”复制数据；但需明确所有权和并发保护。
- 全局变量不可避免时，减少数量并集中访问；ISR / 多任务场景优先保证原子性、临界区和 `volatile` 使用正确。

## 4. 适用范围

适合函数化的内容：协议编解码与校验、传感器换算和滤波、限幅、阈值与回差、状态机和控制策略。

保留命令式处理的内容：GPIO / 寄存器 / DMA / Flash 操作、任务调度、共享状态和外设驱动。

推荐按职责拆分：

```text
驱动层：读取或写入硬件
计算层：换算、校验、过滤
策略层：阈值、回差、状态迁移
任务层：连接流程，保存必要状态
```

## 5. 对比例子：协议帧处理

需求：收到 UART 数据后，校验一帧 4 字节数据；校验通过则将前两字节组合成命令并执行。

**共享状态式写法**将数据、校验和动作混在一起：

```c
static uint8_t g_frame[4];
static bool g_frame_ready;

void protocol_process(void)
{
    if (!g_frame_ready) return;
    g_frame_ready = false;

    if ((uint8_t)(g_frame[0] + g_frame[1] + g_frame[2]) == g_frame[3]) {
        motor_set((uint16_t)g_frame[0] << 8 | g_frame[1]);
    }
}
```

它很直接，但函数依赖接收中断何时写入 `g_frame`，也难以在不调用 `motor_set()` 的情况下验证解析结果。

**函数式思维**先把规则提取为纯函数，再由边界层执行动作：

```c
bool parse_command(const uint8_t frame[4], uint16_t *command)
{
    if ((uint8_t)(frame[0] + frame[1] + frame[2]) != frame[3]) return false;

    *command = (uint16_t)frame[0] << 8 | frame[1];
    return true;
}

void protocol_process(const uint8_t frame[4])
{
    uint16_t command;

    if (parse_command(frame, &command)) {
        motor_set(command);  /* 边界：真正执行硬件动作 */
    }
}
```

优点：`parse_command()` 的输入、输出和失败条件明确；可用正常帧、错误校验帧直接进行单元测试；UART 接收方式或电机驱动变化时，协议规则通常无需改动。

代价：参数、返回值和数据对象会更多；小型一次性流程可能显得更啰嗦。对大缓冲区还要避免不必要的复制，并明确缓冲区在解析期间不会被 ISR 或其他任务改写。

## 6. 最终结论

嵌入式项目通常采用混合方式：**边界层命令式，核心规则函数式。**

不要追求形式上的“纯粹”。只要能把隐式共享状态变为显式参数，把硬件副作用与业务规则分开，代码就会更容易阅读、验证和维护。
