# 并发编程与底层原理

本文对应 [C++17 学习计划](../C++17学习计划.md)的第六阶段，承接 [C++17 新特性](C++17%20新特性.md)。

本阶段要解决三个问题：线程如何可靠启动与停止，共享数据如何建立正确的同步关系，以及对象布局、运行时机制和 ABI 如何影响部署。

所有 `cpp` 代码使用 C++17，未注明“完整示例”的均为局部片段。Linux 示例通常需要以 `-pthread` 编译和链接；RTOS 是否提供标准线程库，要由目标移植层确认。

## 一、线程生命周期与同步工具

### 1.1 线程启动、参数与退出

#### 1.1.1 `thread`、`join` 与 `detach`


```cpp
#include <thread>

std::thread worker{[] {
    // 执行有限任务。
}};
worker.join();
```

`std::thread` 成功创建后开始执行任务。`join()` 等待线程完成，并回收对应的线程管理关系；`detach()` 放弃这种关联，不等待任务完成，也不会延长回调引用的局部变量生命。

销毁仍然 `joinable()` 的 `thread` 会调用 `std::terminate`，即使底层任务已经执行结束也一样。线程函数有未捕获异常逃出时，同样会终止程序，不能指望创建线程的外层 `try/catch` 自动接住。

不要把 `detach()` 当成避免写退出逻辑的快捷方式。长期设备服务通常需要停止请求、唤醒阻塞等待、结束任务和 `join()` 四个步骤。C++17 没有标准 `jthread` 和 `stop_token`，需要自行组织生命周期。

#### 1.1.2 参数传递与异常路径


```cpp
#include <functional>

int count = 0;
std::thread worker{[](int& output) { output = 42; }, std::ref(count)};
worker.join();
// join 成功返回后，可以读取 count。
```

线程构造通常保存衰减后的参数副本；要传引用，可用 `std::ref`，但必须保证对象活得足够久。这里主线程在线程完成前不访问 `count`，且完成通过 `join()` 与之后的读取建立同步。

成功启动线程之后，若当前函数还有可能抛异常，必须保证异常路径也能完成停止和加入。可以使用 RAII 包装线程；如果线程工作依赖停止标记，包装器析构也必须先发出停止请求，不能直接无限等待。

### 1.2 互斥量与条件变量

#### 1.2.1 `mutex` 与锁对象


```cpp
#include <mutex>

std::mutex mutex;
int sharedCount = 0;

void increment() {
    std::lock_guard<std::mutex> lock{mutex};
    ++sharedCount;
}
```

同一个共享状态的所有冲突访问必须遵守同一同步规则。只给写入加锁、读取不加锁，仍可能产生数据竞争。

| 工具 | 用法与特点 |
| --- | --- |
| `lock_guard` | 进入作用域加锁，离开作用域解锁，适合固定临界区 |
| `unique_lock` | 可延迟加锁、显式解锁再加锁、移动所有权，适合条件变量 |
| `scoped_lock` | C++17 中管理一个或多个互斥量，组合获取时避免相应锁序死锁 |
| `shared_lock` | 配合共享互斥量持有读锁，写入仍须独占锁 |

尽量缩短临界区，不在锁内进行不可控的回调、设备阻塞 I/O 或等待另一个任务。多个资源间的锁顺序仍需系统设计，特别是设备锁与业务锁混合时。

```cpp
std::mutex firstMutex;
std::mutex secondMutex;

void updateBoth() {
    std::scoped_lock lock{firstMutex, secondMutex};
    // 在这里同时修改由两个锁保护的数据。
}
```

#### 1.2.2 条件变量等待的是状态


```cpp
#include <condition_variable>

std::condition_variable ready;
bool stopped = false;

// 等待线程中，mutex 同时保护 stopped：
std::unique_lock<std::mutex> lock{mutex};
ready.wait(lock, [] { return stopped; });
```

`wait` 在等待期间释放锁，被唤醒后重新获取锁。它可能出现虚假唤醒，所以要用谓词版本或循环重新检查状态。

通知本身不是持久保存的事件。先在锁保护下更新条件，再通知等待者；等待者检查的是受保护状态。这样即使通知先于等待发生，谓词为真时仍不会错误地睡下去。

通知通常可以放在解锁之后，减少被唤醒线程立刻阻塞在同一个锁上；但状态修改和对象生命周期必须已经安排正确。超时等待也需要检查返回时条件究竟是否成立。

### 1.3 future 与 async

#### 1.3.1 `promise` 与 `future`


```cpp
#include <future>
#include <thread>
#include <utility>

std::promise<int> promise;
auto result = promise.get_future();
std::thread worker{[p = std::move(promise)]() mutable {
    try {
        p.set_value(42);
    } catch (...) {
        p.set_exception(std::current_exception());
    }
}};
worker.join();
int value = result.get();
```

`promise` 设置共享状态，`future` 等待并取得结果；`get()` 也会重新抛出保存的异常。普通 `future` 通常只消费一次，多个读取者可以考虑 `shared_future`。

销毁未完成承诺的 `promise` 会让对应共享状态产生 broken promise 错误，而不是永远静默等待。异步任务仍要处理线程退出，结果传递不等于生命周期管理。

#### 1.3.2 `async` 与启动策略


```cpp
auto result = std::async(std::launch::async, [] { return 42; });
int value = result.get();
```

`launch::async` 请求异步执行，`launch::deferred` 延迟到相应等待或取值时执行；默认策略允许实现选择。不要用未指定策略的 `async` 保证一定存在后台线程。

来自异步启动的共享状态还存在特殊析构等待规则：最后释放相关共享状态的操作可能等待任务结束。因此丢弃临时 `future` 可能让看似异步的调用变成连续等待。`future` 也不提供通用取消协议，停止仍需额外设计。

## 二、原子操作与内存模型

### 2.1 数据竞争与原子复合操作

#### 2.1.1 数据竞争不是普通的“结果偶尔不准”


两个线程对同一内存位置进行冲突访问，至少一方为写入，且没有相应的原子性和 happens-before 保障时，可能形成数据竞争；C++ 中的数据竞争会导致未定义行为。

```cpp
// 错误设计：两个线程在没有同步的情况下执行 ++count。
// 普通 int 的 ++ 不是天然的线程安全操作。
```

`volatile` 不提供线程间原子性和同步。它常用于特定平台的内存映射 I/O 访问，但寄存器屏障、DMA 一致性和中断规则仍要服从平台要求。

数据竞争与 happens-before 的正式关系可以对照 [C++17 草案的多线程数据竞争章节](https://timsong-cpp.github.io/cppwp/n4659/intro.races)。线程安全设计需要同时考虑生命周期与逻辑不变量。

#### 2.1.2 `atomic` 与复合操作


```cpp
#include <atomic>

std::atomic<unsigned int> count{0};
count.fetch_add(1, std::memory_order_relaxed);
```

`load` 和 `store` 各自原子，不代表“读出、计算、再写回”的组合原子。`count.store(count.load()+1)` 仍可能丢失其他线程的增加；应使用 `fetch_add` 或合适的 CAS 循环。

单个原子值安全，也不代表它旁边的队列、指针目标和其他成员自动安全。多个原子成员组成的业务状态，可能需要一个互斥量来共同维护。

### 2.2 内存序与一次性发布

#### 2.2.1 常见内存序


| 内存序 | 核心作用 | 常见用途 |
| --- | --- | --- |
| `relaxed` | 保证该原子操作本身及相应修改序，不建立跨对象发布同步 | 独立统计计数 |
| `release` | 在匹配的读取关系下发布此前操作 | 发布已初始化数据的标记写入 |
| `acquire` | 读到相应发布值时，接收之前发布的操作 | 检查就绪标记后读取数据 |
| `acq_rel` | 对读改写操作同时具有 acquire/release 作用 | 某些状态转换 |
| `seq_cst` | 默认序，除相应 acquire/release 语义外，对 seq_cst 操作建立统一总序 | 无明确优化证据时的保守起点 |

不是所有内存序都适用于所有操作：普通 load 不能用 release，普通 store 不能用 acquire。C++17 还有 `consume`，涉及依赖排序，入门设计通常先掌握 acquire/release，不依靠复杂依赖链做优化。

#### 2.2.2 一次性发布与 happens-before


```cpp
int payload = 0;
std::atomic<bool> ready{false};

// 生产线程，仅发布一次：
payload = 42;
ready.store(true, std::memory_order_release);

// 消费线程：
if (ready.load(std::memory_order_acquire)) {
    // 若读到上面的发布值，此处可读取 payload。
}
```

关键是 acquire 读取到相应 release 发布的值，由此建立同步，再把之前的写入连接到之后的读取。这不是“等一段时间后缓存自然刷新”。

例子只适用于发布一次，且消费者读取期间生产者不再修改 `payload`。若不断重写数据并复用同一布尔标记，需要设计新的握手、队列或锁协议，不能直接照搬。

### 2.3 CAS 与无锁进展

```cpp
std::atomic<unsigned int> total{0};
auto expected = total.load(std::memory_order_relaxed);
while (!total.compare_exchange_weak(expected, expected + 1,
                                    std::memory_order_relaxed,
                                    std::memory_order_relaxed)) {
    // 失败时 expected 被更新为观测到的值，再次计算目标值。
}
```

弱 CAS 允许伪失败，所以通常放在循环中。这个计数操作实际应优先用 `fetch_add`，示例只展示 CAS 机制。更复杂算法还必须检查成功与失败内存序是否适用。

`atomic<T>` 不保证在所有类型、平台上都无锁，可通过 `is_lock_free()` 或 C++17 的 `is_always_lock_free` 检查。无锁通常指整体进展保证，某个线程仍可能重试很多次，不等于每次操作都在固定时间完成。

无锁链表和队列还涉及 ABA、对象回收和悬空访问。正确使用 CAS 只是其中一部分，初学时不要把裸指针交换当作完整的无锁容器实现。

## 三、底层实现与部署边界

### 3.1 对齐与对象布局

```cpp
#include <cstddef>

struct PacketHeader {
    char type;
    int length;
};

constexpr auto bytes = sizeof(PacketHeader);
constexpr auto alignment = alignof(PacketHeader);
```

成员之间、对象末尾可能有填充，具体大小取决于类型、目标 ABI 和编译选项。`alignas` 可以请求更严格对齐，不能随意减小已有类型的自然对齐要求。

不要把结构体直接当作线上协议格式，也不要用 `memcmp` 作为一般对象相等判断。填充、端序、字段宽度与对象表示都可能不同；协议需要逐字段明确编码。

有虚函数的类常包含虚指针，但其数量和偏移不由标准固定。观察 `sizeof`、汇编和调试器可以了解当前构建，不能据此承诺跨编译器兼容。

### 3.2 RTTI 与模板成本

#### 3.2.1 RTTI 与 `dynamic_cast`


```cpp
struct Device { virtual ~Device() = default; };
struct Uart : Device { void flush() {} };

void flushIfUart(Device* device) {
    if (auto* uart = dynamic_cast<Uart*>(device)) {
        uart->flush();
    }
}
```

运行时向下或交叉转换通常要求源基类是多态类型。指针形式转换失败返回空，引用形式失败抛出 `std::bad_cast`。`typeid` 提供类型信息，但名字文本不能当成跨平台稳定的业务协议。

频繁检查实际派生类型，可能说明基类缺少应有的虚接口。RTTI 的二进制大小和运行成本需要测量；禁用 RTTI 后依赖这些能力的代码也必须调整。

#### 3.2.2 模板实例化与代码膨胀


不同模板参数可能生成不同代码，增加固件大小和编译时间。编译器、链接器可能合并或移除部分代码，但不能指望总能消除所有重复实例。

高层类型安全接口可以保留模板，把大量与类型无关的逻辑放入普通函数，减少重复。是否采用显式实例化、LTO 或类型擦除，需要比较体积、性能和可维护性。

### 3.3 库、ABI 与运行时配置

#### 3.3.1 静态库、动态库与 ABI


静态库是目标文件的归档，通常把所需对象代码链接进最终产物；动态库在运行时由装载器参与解析和加载，增加部署及运行时依赖管理。

ABI 包括名称修饰、调用约定、对象布局、异常展开和标准库类型实现等。修改公开类成员，即使源码接口看似相同，也可能改变二进制接口。

跨独立工具链边界时，常通过 C ABI、固定宽度数据和不透明句柄减少耦合，并约定创建方与释放方。`extern "C"` 改变语言链接规则，不会让 `std::string` 自动变成稳定的跨语言数据格式。

#### 3.3.2 异常与 RTTI 对嵌入式系统的影响


异常支持可能增加展开表和运行时依赖；RTTI 可能增加类型信息。是否禁用应依据目标能力、固件体积和错误处理策略决定，不应直接认为所有 C++ 特性都昂贵或不可用。

禁用异常不会自动让分配失败变成返回状态，也不会改变标准库接口的契约。标准库若需要抛异常但构建无法支持，实际结果取决于实现与配置，必须在工程阶段检查失败路径。

## 四、可关闭队列与综合实践

### 4.1 可关闭队列与自查

#### 4.1.1 队列必须定义关闭语义


生产者消费者队列除了 `push/pop`，还需要约定：容量满时如何处理，关闭后是否接受新数据，已有数据是否排空，以及谁负责唤醒等待者。

嵌入式系统通常需要有界队列和明确的丢弃或背压策略。无界增长会把“处理速度不足”变成不可控的内存耗尽。

#### 4.1.2 完整示例：可以关闭的生产者消费者队列


下面的单文件 Linux 示例可用 `g++ -std=c++17 -Wall -Wextra -pthread queue.cpp -o queue` 编译。为突出关闭协议，采用动态队列，不提供容量上限。

```cpp
#include <cassert>
#include <condition_variable>
#include <mutex>
#include <optional>
#include <queue>
#include <thread>

class Queue {
public:
    bool push(int value) {
        {
            std::lock_guard<std::mutex> lock{mutex_};
            if (closed_) {
                return false;
            }
            values_.push(value);
        }
        ready_.notify_one();
        return true;
    }

    std::optional<int> pop() {
        std::unique_lock<std::mutex> lock{mutex_};
        ready_.wait(lock, [this] { return closed_ || !values_.empty(); });
        if (values_.empty()) {
            return std::nullopt;
        }
        int value = values_.front();
        values_.pop();
        return value;
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock{mutex_};
            closed_ = true;
        }
        ready_.notify_all();
    }

private:
    std::mutex mutex_;
    std::condition_variable ready_;
    std::queue<int> values_;
    bool closed_ = false;
};

int main() {
    Queue queue;
    int sum = 0;
    std::thread consumer{[&] {
        while (auto value = queue.pop()) {
            sum += *value;
        }
    }};

    try {
        for (int value = 1; value <= 3; ++value) {
            if (!queue.push(value)) {
                queue.close();
                consumer.join();
                return 1;
            }
        }
    } catch (...) {
        queue.close();
        consumer.join();
        throw;
    }

    queue.close();
    consumer.join();
    assert(sum == 6);
    const bool accepted = queue.push(4);
    assert(!accepted);
    return 0;
}
```

关闭后不再接收数据，消费者先排空已有数据，随后收到无值结果退出。主线程在 `join()` 后才读取 `sum`，队列也活得比消费者久。生产侧分配失败时同样关闭并加入线程，避免栈展开销毁 joinable 线程。

真实服务还应处理消费者业务异常、超时、队列容量和设备中断。此队列使用标准互斥量，不是可以直接从中断服务函数调用的 ISR 队列。

#### 4.1.3 练习与自查


| 练习 | 要做的事情 | 检查点 |
| --- | --- | --- |
| 生命周期 | 为后台采样服务实现停止与加入 | 不销毁 joinable 线程，不借用失效对象 |
| 条件变量 | 支持先关闭后等待、空队列关闭和排空关闭 | 都能退出，不依赖通知时序 |
| 结果传递 | 让任务通过 future 返回结果或异常 | 工作线程异常不直接逃逸 |
| 发布协议 | 画出 release/acquire 的先后关系 | 指出哪个读取读到了哪个发布值 |
| 原子计数 | 对比复合 load/store 与 fetch_add | 能解释为何前者仍可能丢失增加 |
| 对象布局 | 比较不同字段顺序的 sizeof/alignof | 不把实验结果当成标准固定布局 |
| 二进制边界 | 为设备库设计不透明 C 句柄 | 创建释放成对，不暴露标准库对象布局 |

完成后，应能回答：

1. 为什么任务已经结束，`thread` 析构仍可能终止程序？
2. 条件变量为什么必须围绕共享状态使用谓词？
3. `future`、`async` 是否提供取消？默认策略是否保证后台执行？
4. 原子性、数据竞争与业务状态一致性分别是什么？
5. acquire/release 建立同步需要什么读取关系？
6. 无锁为什么不等于无等待，也不等于固定执行时间？
7. 为什么公开类布局、异常模型和标准库版本会影响 ABI？
