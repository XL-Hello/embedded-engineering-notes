# C++17 工程实践

本文对应 [C++17 学习计划](../C++17学习计划.md)的第七阶段，承接 [并发编程与底层原理](并发编程与底层原理.md)。

本阶段要解决三个问题：如何把代码组织成可重复构建的工程，如何用工具定位内存和并发错误，以及如何把 C++ 的对象模型接到 Linux、RTOS 和 C 驱动接口上。

文中的 C++ 示例使用 C++17。Shell 命令默认在 Linux 或具备相应工具链的环境执行；`sh` 命令块不是 PowerShell 命令。涉及板级 SDK 的片段只表达组织方法，必须替换成实际平台接口。

## 一、可重复构建与接口边界

### 1.1 编译选项与目标式 CMake

#### 1.1.1 GCC / Clang 的常用选项


```sh
g++ -std=c++17 -Wall -Wextra -Wpedantic -g -Og main.cpp -o app
g++ -std=c++17 -Wall -Wextra -Wpedantic -O2 -DNDEBUG main.cpp -o app
```

第一行用于调试，第二行用于较接近发布条件的运行。`-g` 生成调试信息，`-Og` 兼顾调试体验与有限优化，`-O2` 启用更多优化，`-DNDEBUG` 会关闭标准 `assert`。

**有副作用的操作不要放在 `assert` 里面。** `assert(device.open())` 在发布构建可能完全不执行打开动作。应先执行，再断言结果。

GCC 与 Clang 的许多常见选项相似，但诊断和目标支持并不完全相同。`-Wconversion`、`-Wshadow` 可以逐步加入；`-Werror` 是否启用，应结合第三方代码和编译器版本管理。多线程 Linux 程序通常在编译、链接时都使用 `-pthread`。

#### 1.1.2 CMake：优先描述目标


```cmake
cmake_minimum_required(VERSION 3.16)
project(device_app LANGUAGES C CXX)

add_library(protocol STATIC src/protocol.cpp)
target_include_directories(protocol PUBLIC include)
target_compile_features(protocol PUBLIC cxx_std_17)
set_target_properties(protocol PROPERTIES CXX_EXTENSIONS OFF)

add_executable(device_app src/main.cpp)
target_link_libraries(device_app PRIVATE protocol)
target_compile_features(device_app PRIVATE cxx_std_17)
set_target_properties(device_app PROPERTIES CXX_EXTENSIONS OFF)
```

`PUBLIC` 需求传递给依赖方，`PRIVATE` 只用于当前目标，`INTERFACE` 只提供给使用者。头文件中使用 C++17 类型时，库应把相应要求公开。

`cxx_std_17` 表示至少具备 C++17 级别，编译器默认标准更高时，不等于强制精确使用 C++17。需要限制标准版本时，可以组合 `CXX_STANDARD 17`、`CXX_STANDARD_REQUIRED YES` 与 `CXX_EXTENSIONS OFF`。语法要求也不能证明所有标准库组件可用，应通过目标工具链编译确认。参见 [CMake 的编译特性说明](https://cmake.org/cmake/help/latest/command/target_compile_features.html)。

多模块工程可在各模块目录使用 `add_subdirectory()`，通过目标依赖传递头文件路径和库，不要依靠到处添加全局搜索目录维持偶然可用的构建。

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
```

以上 `CMAKE_BUILD_TYPE` 用于单配置生成器；多配置生成器通常在构建时选择 `--config Debug`。不要把某一种生成器的行为当成所有平台的统一规则。

### 1.2 依赖管理与交叉编译

#### 1.2.1 静态库、动态库与依赖管理


`add_library(name STATIC ...)` 创建静态库，`SHARED` 创建共享库。Linux 共享库通常还需要考虑位置无关代码、运行时搜索路径、SONAME 和部署依赖。

依赖应记录版本、来源、许可证和构建选项。可以使用系统包、受控源码依赖或项目约定的包管理器，关键是版本可重复，不在每次构建时静默拉取不断变化的分支。

静态链接不代表完全消除兼容性问题，也不保证所有目标代码都会进入最终文件。动态链接则需要检查目标根文件系统里的 C++ 运行库、libc 和 ABI，不能只确认库文件“名字相同”。

#### 1.2.2 交叉编译：区分构建主机与运行目标


```cmake
# toolchains/aarch64-linux.cmake，路径与工具名需按 SDK 修改。
set(CMAKE_SYSTEM_NAME Linux)
set(CMAKE_SYSTEM_PROCESSOR aarch64)
set(CMAKE_C_COMPILER aarch64-linux-gnu-gcc)
set(CMAKE_CXX_COMPILER aarch64-linux-gnu-g++)
set(CMAKE_SYSROOT /opt/sdk/sysroot)
set(CMAKE_FIND_ROOT_PATH /opt/sdk/sysroot)
set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)
set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
```

```sh
cmake -S . -B build-arm -DCMAKE_TOOLCHAIN_FILE=toolchains/aarch64-linux.cmake
cmake --build build-arm --parallel
```

编译器、头文件、库和 sysroot 必须属于相容的 SDK，不能把主机 `/usr/include` 和目标库随意混用。更换工具链时使用独立构建目录，避免旧缓存污染。

裸机或 RTOS 还涉及链接脚本、启动代码、板级库与输出格式，不能只把 `CMAKE_SYSTEM_NAME` 改一下就认为移植完成。工具链文件的加载与搜索规则见 [CMake 交叉编译说明](https://cmake.org/cmake/help/latest/manual/cmake-toolchains.7.html)。

### 1.3 C 接口与对象回调

#### 1.3.1 `extern "C"`：让 C 与 C++ 共享接口


```c
/* driver.h：同时供 C 和 C++ 包含。 */
#ifndef DRIVER_H
#define DRIVER_H

#ifdef __cplusplus
extern "C" {
#endif

int driver_read(unsigned char* data, unsigned int capacity);

#ifdef __cplusplus
}
#endif

#endif
```

C 源文件仍由 C 编译器编译，C++ 源文件由 C++ 编译器编译，最终链接通常使用 C++ 驱动以带入所需运行库。不要把所有 C 文件改为 C++ 编译来代替接口适配。

C ABI 边界使用 C 可表示的数据和函数，不暴露重载、模板或标准容器。还需要约定缓冲区长度、错误码、线程环境，以及资源由谁释放。异常不能越过不支持相应异常传播的 C 调用链，应该在 C++ 边界内部转换为错误结果。

#### 1.3.2 对象与 C 回调的适配


```cpp
// 假定平台的 C 头文件已声明：
// typedef void (*RxCallback)(void* context, int value);
// void register_rx(RxCallback callback, void* context);
// void unregister_rx(void* context);

class Receiver;
extern "C" void receiveEntry(void* context, int value) noexcept;

class Receiver {
public:
    void onReceive(int value) noexcept {
        last_ = value;  // 仅演示单线程回调；真实并发访问需同步。
    }
private:
    int last_ = 0;
};

extern "C" void receiveEntry(void* context, int value) noexcept {
    if (context != nullptr) {
        static_cast<Receiver*>(context)->onReceive(value);
    }
}

// 调用处：register_rx(&receiveEntry, &receiver);
```

使用普通入口函数再恢复上下文，避免把成员函数指针强转成 C 回调。真实接口还需要检查调用约定、参数类型和平台对语言链接的要求。

注销不仅要阻止未来回调，还要确认正在执行或已排队的回调结束，然后才能销毁对象。若上下文地址注册后对象移动，旧地址也可能失效，因此常需要禁止移动或使用稳定存储。

## 二、调试诊断与行为验证

### 2.1 GDB 与内存根因排查

#### 2.1.1 GDB：从失败现场建立证据


```sh
gdb ./app
```

在 GDB 中可使用 `break main`、`run`、`next`、`step`、`print value`、`bt` 和 `thread apply all bt`。先看崩溃调用栈、相关对象和线程，再追踪导致状态失效的最早位置。

优化后源码行与机器指令并非一一对应，变量也可能被优化掉。必要时对照调试构建和发布构建，不能只凭“Debug 不崩溃”认定问题消失。

远程目标通常使用 `gdbserver` 或硬件调试器；主机 GDB、可执行文件、调试符号与目标运行文件应相匹配。

#### 2.1.2 排查内存问题的顺序


崩溃点经常只是结果。排查时先确认对象由谁拥有、何时销毁，再检查是否因容器扩容、异步回调、线程退出或 C 接口保存地址而悬空。

保留最小复现输入，使用检测器定位首次非法访问，修复后重跑复现路径。把指针置空、扩大缓冲区或增加延时，若没有解释根因，通常不能作为可靠修复。

### 2.2 检测工具与独立构建

```sh
g++ -std=c++17 -g -O1 -fno-omit-frame-pointer -fsanitize=address,undefined main.cpp -o app-asan
g++ -std=c++17 -g -O1 -fno-omit-frame-pointer -fsanitize=thread -pthread main.cpp -o app-tsan
```

| 工具 | 主要用途 | 需要注意的边界 |
| --- | --- | --- |
| ASan | 检测多种越界、释放后使用、重复释放等 | 不等于检查全部内存错误；泄漏检测依平台配置 |
| UBSan | 检测部分未定义行为，如某些溢出、错位访问 | 没有覆盖所有未定义行为 |
| TSan | 检测实际执行路径上的数据竞争 | 不证明没有死锁，不证明所有线程交错都正确 |
| Valgrind Memcheck | 检测非法访问、未初始化值使用、泄漏等 | 较慢，平台支持和目标程序特性有限制 |
| clang-tidy | 静态分析与编码规则检查 | 需要正确编译参数，诊断仍需人工判断 |

ASan 与 TSan 不能组合在同一个构建中，应分开运行。插桩显著改变时间与内存开销，通常先在主机或具备支持的 Linux 目标执行，再结合板端诊断。编译与链接都需要匹配的 sanitizer 选项。支持情况参见 [GCC 插桩选项](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)。

```sh
valgrind --leak-check=full --track-origins=yes ./app
cmake -S . -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
clang-tidy src/protocol.cpp -p build
```

编译数据库生成依赖 CMake 生成器支持。Valgrind 通常用于普通调试构建，不应把多个重型检测器盲目叠加运行。

### 2.3 GoogleTest 与可观察行为

```cpp
// tests/protocol_test.cpp，配合后面的工程示例使用。
#include "protocol.hpp"
#include <gtest/gtest.h>

TEST(ParseChannel, AcceptsValidDigit) {
    const auto result = protocol::parseChannel("3");
    ASSERT_TRUE(result.has_value());
    EXPECT_EQ(*result, 3);
}

TEST(ParseChannel, RejectsInvalidInput) {
    EXPECT_FALSE(protocol::parseChannel("9"));
    EXPECT_FALSE(protocol::parseChannel("12"));
    EXPECT_FALSE(protocol::parseChannel(""));
}
```

`ASSERT_*` 失败会结束当前测试函数，适合后续操作依赖前提成立的情况；`EXPECT_*` 记录失败后继续执行。测试优先关注合法边界、失败结果与状态变化，而不是复制实现细节。

若项目已经提供可被 `find_package` 发现的 GoogleTest，可增加：

```cmake
enable_testing()
find_package(GTest REQUIRED)
add_executable(protocol_test tests/protocol_test.cpp)
target_link_libraries(protocol_test PRIVATE protocol GTest::gtest_main)
include(GoogleTest)
gtest_discover_tests(protocol_test)
```

```sh
ctest --test-dir build --output-on-failure
```

GoogleTest 需要由工程管理版本和安装方式；基础示例不强制联网获取依赖。源码接入与 CMake 集成可参考 [GoogleTest 官方入门](https://google.github.io/googletest/quickstart-cmake.html)。交叉编译测试应选择主机运行、模拟器运行或板端运行，不默认直接执行目标二进制。

## 三、平台适配与资源约束

### 3.1 RTOS 的 C++ 运行时边界

FreeRTOS 内核以 C API 为主，应用可以用 C++，但启动代码需要完成静态对象初始化，工具链也要提供使用到的运行时能力。标准 `thread`、`mutex` 和文件系统不能仅因编译器接受 C++17 就认为已经移植。

任务删除不等于正常退出 C++ 作用域。FreeRTOS 任务应先从内部工作函数或子作用域正常退出，完成局部资源析构，再由外层入口调用任务删除接口；直接删除仍持有局部 RAII 对象的任务，不能依靠内核自动执行这些析构。相关问题见 [FreeRTOS 官方支持讨论](https://forums.freertos.org/t/vtaskdelete-doesnt-trigger-scope-exit-of-class-objects-destructors-not-called-c/14849)。

NuttX 的 C++ 库与运行时支持取决于配置和所选实现，应先确认使用的标准库、异常、RTTI、静态初始化及线程接口，再选择语言与库特性。参见 [NuttX 的 C++ 运行库说明](https://nuttx.apache.org/docs/latest/os/libs/libxx.html)。

中断处理还需要使用平台允许的 ISR API，不能直接搬用会阻塞、分配或持有普通互斥量的标准库实现。

### 3.2 设备事务、DMA 与退出协议

#### 3.2.1 UART、SPI、I2C 封装的边界


封装驱动时，可以把“拥有硬件句柄”与“借用总线进行事务”分开：UART 会话拥有独占端口，多个 SPI 设备可能共享一个总线控制器，I2C 设备对象通常保存地址并借用总线。

| 设计问题 | 必须明确的契约 |
| --- | --- |
| 初始化 | 谁设置引脚、时钟、波特率与总线模式 |
| 所有权 | 对象析构是否关闭硬件，能否复制或移动 |
| 传输 | 同步或异步，超时单位，部分传输如何返回 |
| DMA | 缓冲区对齐、可访问区域、缓存维护与有效期 |
| 并发 | 按设备锁还是按总线锁，能否在 ISR 调用 |
| 失败 | 参数错误、超时、总线忙和设备断开如何区分 |

C++17 没有标准 `span`，可以使用项目已有的缓冲区视图，或用指针与长度明确表达。避免用 `std::string` 代表任意二进制协议而忽略零字节与长度。

#### 3.2.2 线程安全设备管理与嵌入式 Linux


设备管理至少涉及设备生命周期、总线事务和异步完成三个维度。持有管理表的锁不代表整个 DMA 操作都受保护；释放锁后硬件可能仍在使用缓冲区。

可以由单个 I/O 线程串行处理请求，或用总线锁保护完整事务，并通过完成通知归还缓冲区。停止设备时，要先停止提交，取消或等待在途操作，再释放资源。

嵌入式 Linux 还要检查目标运行库、文件权限、服务启动方式、日志、设备热插拔和进程退出路径。交叉编译成功只是第一步，应在目标根文件系统上验证运行与部署依赖。

### 3.3 固定内存池与对象生命周期

内存池管理存储块，对象池还要管理对象的构造、析构与占用状态。固定块策略可以约束最大容量，但仍要处理耗尽、对齐、并发和重复归还。

```cpp
#include <cstddef>
#include <new>

struct Sample { int value; };
alignas(Sample) std::byte slot[sizeof(Sample)];
Sample* object = new (slot) Sample{42};
object->~Sample();
// slot 不是普通 new 分配的，不能 delete object。
```

placement new 在给定存储中构造对象，本身不提供池的管理能力。复用槽位时必须处理生命周期规则，不能继续把旧对象引用当成新对象的通用访问凭证。

避免碎片的常见措施是：初始化阶段分配、固定容量容器、预留空间、按大小分类的池，以及限制运行期分配。一次 `reserve` 不能证明以后绝不分配；字符串、回调和其他成员仍可能动态申请内存。

### 3.4 异常与 RTTI 的整体配置

部分项目使用 GCC/Clang 的 `-fno-exceptions`、`-fno-rtti`，但这必须作为整体构建约定，检查依赖库是否采用兼容配置。

禁用异常时，接口可以通过状态码、`optional` 或显式结果类型报告失败。`optional` 的空值本身不能说明分配失败原因；也不能假定容器分配失败就自动变成空返回值。

`new (std::nothrow) T` 能对相应分配失败返回空，但不会神奇地把 `T` 构造过程中所有可能失败的行为都转换为状态码。对严格受限目标，需要选择本身满足失败策略的对象与分配器。

禁用 RTTI 时避免运行时类型识别需求，优先用明确虚接口、标签枚举或 `variant` 表达已知类型集合。标签也必须与实际对象状态一致，不能用手动标签掩盖不安全转换。

## 四、完整工程与综合验收

### 4.1 分模块通道解析工程

下面的文件共同构成一个完整工程，只依赖 C++17 标准库，不访问硬件。目录结构如下：

```text
channel-demo/
├── CMakeLists.txt
├── include/
│   └── protocol.hpp
└── src/
    ├── protocol.cpp
    └── main.cpp
```

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.16)
project(channel_demo LANGUAGES CXX)

add_library(protocol STATIC src/protocol.cpp)
target_include_directories(protocol PUBLIC include)
target_compile_features(protocol PUBLIC cxx_std_17)
set_target_properties(protocol PROPERTIES
    CXX_STANDARD 17 CXX_STANDARD_REQUIRED YES CXX_EXTENSIONS OFF)

add_executable(channel_demo src/main.cpp)
target_link_libraries(channel_demo PRIVATE protocol)
set_target_properties(channel_demo PROPERTIES
    CXX_STANDARD 17 CXX_STANDARD_REQUIRED YES CXX_EXTENSIONS OFF)

if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
    target_compile_options(protocol PRIVATE -Wall -Wextra -Wpedantic)
    target_compile_options(channel_demo PRIVATE -Wall -Wextra -Wpedantic)
endif()
```

`include/protocol.hpp`：

```cpp
#ifndef PROTOCOL_HPP
#define PROTOCOL_HPP

#include <optional>
#include <string_view>

namespace protocol {
std::optional<int> parseChannel(std::string_view text) noexcept;
}

#endif
```

`src/protocol.cpp`：

```cpp
#include "protocol.hpp"

namespace protocol {

std::optional<int> parseChannel(std::string_view text) noexcept {
    if (text.size() != 1 || text[0] < '0' || text[0] > '7') {
        return std::nullopt;
    }
    return text[0] - '0';
}

}
```

`src/main.cpp`：

```cpp
#include "protocol.hpp"
#include <iostream>

int main(int argc, char** argv) {
    if (argc != 2) {
        std::cerr << "usage: channel_demo <0..7>\n";
        return 2;
    }
    const auto channel = protocol::parseChannel(argv[1]);
    if (!channel) {
        std::cerr << "invalid channel\n";
        return 1;
    }
    std::cout << "channel=" << *channel << '\n';
    return 0;
}
```

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
./build/channel_demo 3
./build/channel_demo 9
```

预期合法输入输出 `channel=3` 并返回 0；非法输入报告 `invalid channel` 并返回 1；参数数量错误返回 2。接口返回整数，不保存输入视图，所以调用结束后不依赖 `argv` 字符范围。

没有 CMake 时，也可验证相同源码：

```sh
g++ -std=c++17 -Wall -Wextra -Wpedantic -Iinclude src/protocol.cpp src/main.cpp -o channel_demo
```

### 4.2 毕业项目与练习自查

#### 4.2.1 综合项目：把七个阶段连成一条数据链


建议以“设备采集与命令控制服务”为毕业项目：模拟传感器产生数据，协议模块解析命令，任务模块传递采样结果，应用负责启动、停止与报告错误。

| 步骤 | 交付内容 | 验收条件 |
| --- | --- | --- |
| 主机模型 | 可替换的模拟设备和独占资源封装 | 所有权明确，成功获取的资源只释放一次 |
| 协议模块 | 命令解析与错误分类 | 空输入、非法通道、截断帧都有确定结果 |
| 数据通路 | 有界队列、超时与关闭协议 | 满队列行为明确，停止不会永久等待 |
| 构建与质量 | CMake、行为测试、独立检测构建 | 干净构建可复现，关键失败路径有验证 |
| 平台适配 | UART/SPI/I2C 中选择一个接口实现 | 不把主机线程与硬件时序假设直接照搬 |
| 部署与测量 | 目标运行说明、体积与延迟记录 | 明确 SDK、依赖版本、容量和时延边界 |

性能优化应先测量代码体积、峰值内存、端到端延迟与分配次数，再决定预分配、池化、批处理或替换容器。不要只凭某个语言特性名称判断快慢。

#### 4.2.2 练习与自查


| 练习 | 要做的事情 | 检查点 |
| --- | --- | --- |
| 模块构建 | 按完整示例创建库与应用 | 公共头文件路径与标准要求正确传递 |
| C 接口 | 把一个 C 驱动接入 C++ 对象 | C 文件保持 C 编译，错误与资源边界明确 |
| 内存诊断 | 为越界或悬空建立最小复现 | 能定位首次非法访问，而非只看最终崩溃 |
| 回调注销 | 模拟回调排队期间销毁对象 | 停止提交、等待完成、销毁顺序明确 |
| 资源限制 | 为发送队列设置容量与耗尽行为 | 不依赖无界分配掩盖处理能力不足 |
| 目标部署 | 使用独立工具链目录构建运行 | 主机库不混入目标，运行依赖可追踪 |

完成学习计划后，应能独立回答：

1. 编译、链接和运行时加载分别解决什么问题？
2. CMake 的依赖范围如何影响多模块构建？交叉编译为什么需要 sysroot？
3. ASan、UBSan、TSan、Valgrind 与静态分析分别适合什么错误？
4. 为什么发布构建不应依靠 `assert` 执行业务动作？
5. 对象作为 C 回调上下文时，注销与销毁之间还需要等待什么？
6. FreeRTOS 任务删除为什么不能替代正常的 C++ 作用域退出？
7. 如何证明容量、所有权、错误处理和停止协议满足实际目标约束？

当你能够构建、诊断并部署这个项目，同时解释对象、缓冲区和线程各自在何时结束生命周期，就达到了学习计划中独立开发 Linux/RTOS 应用所需的主要阶段目标。真实硬件和实时性要求仍需要在具体目标上继续验证。
