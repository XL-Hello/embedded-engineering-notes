# 面向对象与资源管理

本文对应 [C++17 学习计划](../C++17学习计划.md)的第二阶段，承接 [C++ 核心基础](C++%20核心基础.md)。适合已经理解类、构造析构和复制操作，准备设计设备接口与资源类型的读者。

本阶段要解决三个问题：如何让不同设备使用统一接口，如何让资源可靠释放，以及如何让失败后的对象仍然保持有效状态。

文中的 `cpp` 代码块使用 C++17；未注明“完整示例”的代码块都是局部片段。Linux 文件描述符等平台接口会单独注明，不能直接用于所有 RTOS。

## 一、设备接口与资源生命周期

### 1.1 设备接口与多态

#### 1.1.1 封装：把状态约束留在类型内部

封装不只是把成员改成 `private`。更重要的是，只允许外部通过合法操作改变对象，使“已打开”“可读”“已停止”等状态有明确含义。

例如串口打开失败时，应保持关闭状态；关闭已经关闭的串口，不应再次释放句柄。只提供成员的任意读写接口，通常无法维护这些规则。

优先用组合表达“拥有一个”：协议解析器拥有缓冲区，通信服务使用传输接口。只有确实存在“可以替代”的关系时，再考虑公有继承。

#### 1.1.2 公有继承与抽象类

下面的接口表达“任何传感器都能读取一个采样值”：

```cpp
class Sensor {
public:
    virtual ~Sensor() = default;
    virtual int read() const = 0;
};

class TemperatureSensor final : public Sensor {
public:
    int read() const override { return 25; }
};

int acquire(const Sensor& sensor) {
    return sensor.read();
}
```

`= 0` 声明纯虚函数。含有尚未实现的纯虚函数的类是抽象类，不能直接创建对象。派生类实现接口后，才能作为具体类型使用。

`public Sensor` 表达公有继承，允许把派生对象当作基类使用。`private`、`protected` 继承改变基类成员的可访问性和对外转换关系，不适合作为普通公共接口的默认选择。

**公有继承要求派生对象遵守基类约定。** 如果基类承诺读取不阻塞，派生类却可能无限等待，语法上能继承，接口设计仍有问题。

#### 1.1.3 静态绑定、动态绑定与 `override`

普通非虚成员函数的调用主要按表达式的静态类型确定。虚函数通过基类指针或引用调用时，可以选择对象实际类型对应的实现。

```cpp
TemperatureSensor concrete;
const Sensor& interface = concrete;
int value = interface.read();  // 调用 TemperatureSensor::read()
```

`override` 要求编译器确认它确实覆盖基类虚函数。参数类型或末尾 `const` 写错时，编译器会报错，避免意外定义了另一个函数。

`final` 可以禁止继续派生，也可以放在虚函数上禁止进一步覆盖。它表达设计约束，不保证带来某一种优化效果。

构造和析构过程中，虚调用不会分派到尚未构造或已经析构的更下层派生部分。不要依靠基类构造函数调用派生类完成初始化，也不要在其中调用纯虚接口。

#### 1.1.4 虚析构函数：让删除路径与实际类型一致

如果允许通过基类指针删除派生对象，基类通常需要公有虚析构函数：

```cpp
Sensor* sensor = new TemperatureSensor{};
delete sensor;  // 基类析构为 virtual，能够正确销毁派生部分
```

C++17 中，经非虚析构的基类指针删除派生对象会导致未定义行为。并非所有类都需要虚析构；没有多态删除用途的值类型通常不需要。

另一种接口设计是使用受保护的非虚析构，明确禁止外部通过基类指针删除对象。初学时先掌握公有虚析构这一常见方案。

#### 1.1.5 对象切片与多重继承

当一个具体派生对象被按值复制到可实例化的基类对象中时，目标只保存基类部分，这称为对象切片。

```cpp
struct Base { int id = 0; };
struct Derived : Base { int channel = 1; };

Derived device;
Base base = device;  // base 不包含 channel
```

多态参数通常使用基类引用或指针；保存异构对象时，可以使用后续学习的 `std::unique_ptr<Base>`。抽象基类本身不能按值创建，因此也不能作为这类切片的目标。

多重继承允许一个类继承多个基类，但会引入同名成员歧义和基类子对象转换等问题。菱形继承中，虚继承可以共享同一个虚基类子对象，其初始化由最派生类负责。嵌入式接口设计中，多个无状态接口的继承往往比多个有状态实现类的继承容易控制。

#### 1.1.6 vtable 与 vptr：常见实现，不是固定布局

常见编译器通过对象中的虚指针找到虚函数表，再间接调用目标函数。由此可能增加对象大小、间接调用和缓存访问成本。

但 C++ 标准没有规定对象必须带一个位于起始地址的 vptr，也没有规定虚表布局。多重继承、虚继承和 ABI 都可能改变实现。不能把网上某个对象内存图当成所有平台的固定规则。

### 1.2 RAII 与资源生命周期

#### 1.2.1 资源不只包括动态内存

文件、socket、互斥量、串口句柄和 DMA 缓冲区都有获取与释放规则。RAII 用对象表示这段持有关系：构造或工厂获取资源，析构释放资源，离开作用域时自动清理。

```text
伪代码：
获取资源 A → 构造管理对象 A
获取资源 B → 构造管理对象 B
执行工作
正常返回或异常展开 → 先释放 B，再释放 A
```

RAII 不能处理所有终止方式。进程被强制终止、固件断电或直接跳过 C++ 栈展开的控制流，不保证执行局部对象析构。应把它用于正常作用域退出和语言支持的异常展开。

#### 1.2.2 构造失败与部分构造

构造函数抛异常时，最外层对象没有构造完成，其自身析构函数不会执行；但已经完成构造的基类和成员会被销毁。

因此，资源应尽早交给 RAII 成员管理。若先把资源保存在裸指针成员里，随后另一个成员构造失败，不能依赖最外层析构函数补救。

在支持异常的环境中，构造可以用抛异常表达“无法建立有效对象”。禁用异常时，可以用返回状态的工厂或显式 `open()`，并完整定义失败状态，避免对象看似有效却没有可用资源。

### 1.3 Rule of Three / Five / Zero

| 规则 | 关注的操作 | 使用场景 |
| --- | --- | --- |
| Three | 析构、拷贝构造、拷贝赋值 | 手工管理资源时，一项自定义往往意味着其他项也要检查 |
| Five | Three 加移动构造、移动赋值 | 需要明确资源转移行为的资源类型 |
| Zero | 尽量不自定义以上操作 | 用标准容器、智能指针等成员组合业务对象 |

这些是设计规则，不是要求所有类机械地手写五个函数。若类只包含 `std::string` 和 `std::vector`，默认复制和移动通常就能正确工作。

若对象独占某个设备句柄，可以删除复制，只允许移动。用户声明析构函数会影响隐式移动操作的生成，不能假设“写了析构就仍自动拥有移动”。移动语义将在下一阶段展开。

## 二、异常安全与资源类型实现

### 2.1 异常处理与失败后的状态

#### 2.1.1 `try/catch/throw` 与栈展开

```cpp
#include <stdexcept>

int checkedChannel(int channel) {
    if (channel < 0) {
        throw std::invalid_argument{"negative channel"};
    }
    return channel;
}

// 在函数中使用：
try {
    int channel = checkedChannel(-1);
    (void)channel;
} catch (const std::exception& error) {
    // 记录 error.what()，决定恢复还是向上报告。
}
```

通常按值抛出异常，按 `const` 引用捕获，避免复制或切片。`throw;` 在处理器内重新抛出当前异常，保留实际异常类型；`throw error;` 是一次新的抛出，可能切片。

异常经过函数边界时，正常栈展开会销毁已经构造完成的局部对象。不要捕获后无条件忽略错误，让调用者继续使用无效结果。

#### 2.1.2 异常安全保证

| 保证 | 失败后的要求 | 例子 |
| --- | --- | --- |
| 基本保证 | 不泄漏资源，对象仍满足自身有效性约束 | 内容可能改变，但仍能析构和继续按约定使用 |
| 强保证 | 操作失败时，对外可观察状态不变 | 先建立新配置，成功后再提交 |
| 不抛保证 | 操作不会把异常传给调用者 | 析构清理、经确认不会失败的交换 |

“先准备，后提交”常用于实现强保证：先在临时对象中完成可能失败的工作，再用不会抛异常的操作替换旧状态。写硬件寄存器、向网络发送数据等外部副作用可能无法回滚，不能仅凭复制临时变量就声称拥有强保证。

#### 2.1.3 析构与 `noexcept`

析构应完成清理并避免抛异常。栈展开时，如果析构又抛出异常并逃出析构函数，会调用 `std::terminate`。

```cpp
void releaseHandle() noexcept {
    // 只放不会向外抛异常的清理操作。
}
```

`noexcept` 是“不让异常逃出”的契约，不是自动捕获异常的机制。违背它会终止程序。它也会影响标准容器在搬迁元素时对移动和复制的选择。

如果关闭资源可能失败，应提供可检查结果的显式 `close()` 或 `flush()`；析构负责兜底清理，不能依赖析构返回错误。是否重试、记录还是忽略关闭错误，需要结合具体平台 API 约定。

### 2.2 运算符重载与显式转换

#### 2.2.1 常见运算符与接口约定

运算符重载为自定义类型提供接近普通值的操作方式，但不能改变运算符优先级、结合性或操作数数量，也不能创造新的运算符符号。

```cpp
struct Sample {
    int value = 0;

    Sample& operator+=(const Sample& other) {
        value += other.value;  // 实际项目要定义数值范围与溢出策略。
        return *this;
    }
};

inline Sample operator+(Sample left, const Sample& right) {
    left += right;
    return left;
}

inline bool operator==(const Sample& left, const Sample& right) {
    return left.value == right.value;
}
```

赋值、下标和函数调用等操作符可以用于相应类型接口。保持 `+` 表示相加、`==` 表示等价等直觉含义，不要把设备发送隐藏在令人意外的算术表达式中。

#### 2.2.2 复制与移动赋值

```cpp
class Buffer {
public:
    Buffer& operator=(const Buffer& other);  // 复制资源或成员状态
    Buffer& operator=(Buffer&& other) noexcept;  // 转移资源
};
```

赋值通常返回 `*this` 的引用，支持连续赋值。管理独占资源时，需要先考虑原资源如何释放、自赋值是否安全、获取新资源失败时如何维持状态。能交给容器或智能指针完成的，优先采用 Rule of Zero。

#### 2.2.3 `explicit` 与类型转换运算符

```cpp
class Port {
public:
    explicit Port(int number) : number_(number) {}
    explicit operator bool() const { return number_ >= 0; }

private:
    int number_;
};

// Port port = 1;  // 不允许隐式转换
Port port{1};
// if (port) { ... }  // 条件判断允许使用 explicit operator bool
```

`explicit` 构造函数避免整数等值悄悄变成资源对象。显式的 `operator bool` 可以表达有效性检查，同时避免对象参与意外的整数运算。

### 2.3 UniqueFd：独占句柄的完整路径

#### 2.3.1 Linux/POSIX 完整示例：独占文件句柄的 RAII 类型

下面的完整示例使用 Linux/POSIX 的 `open/close` 和 `/dev/null`，可用 `g++ -std=c++17 -Wall -Wextra raii.cpp -o raii` 编译。它不适用于没有这些接口的 RTOS。

```cpp
#include <cassert>
#include <cerrno>
#include <fcntl.h>
#include <system_error>
#include <unistd.h>
#include <utility>

class UniqueFd {
public:
    explicit UniqueFd(int fd) noexcept : fd_(fd) {}

    ~UniqueFd() noexcept { reset(); }

    UniqueFd(const UniqueFd&) = delete;
    UniqueFd& operator=(const UniqueFd&) = delete;

    UniqueFd(UniqueFd&& other) noexcept
        : fd_(std::exchange(other.fd_, -1)) {}

    UniqueFd& operator=(UniqueFd&& other) noexcept {
        if (this != &other) {
            reset();
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

    int get() const noexcept { return fd_; }
    explicit operator bool() const noexcept { return fd_ >= 0; }

private:
    void reset() noexcept {
        if (fd_ >= 0) {
            // Linux 上不要因 close 返回错误而盲目重试旧 fd。
            // 本例只做兜底清理；需要报告错误时另设计显式关闭接口。
            ::close(fd_);
            fd_ = -1;
        }
    }

    int fd_ = -1;
};

int main() {
    const int raw = ::open("/dev/null", O_RDONLY);
    if (raw < 0) {
        throw std::system_error{errno, std::generic_category(), "open"};
    }

    UniqueFd first{raw};
    UniqueFd second{std::move(first)};
    assert(!first);
    assert(static_cast<bool>(second));
    return 0;
}
```

对象的有效状态只有“持有一个描述符”或“空”。复制被禁止，移动后源对象为空，析构只释放当前拥有的描述符。`get()` 返回的是借用句柄，外部不能再次关闭它，否则会破坏所有权约定。

Linux `close` 的错误与重试细节可查阅 [Linux man-pages 的 close 说明](https://man7.org/linux/man-pages/man2/close.2.html)。其他平台需要按其接口契约实现清理。
